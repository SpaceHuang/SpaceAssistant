## 1. 方案结论

将审批建设为工具执行前的独立、有界、可解释阶段。用户始终能回答四个问题：**哪个操作在等待、为什么等待、最终有没有获批、接下来能做什么。**

推荐采用以下方案：

1. **审批不再消耗用户任务的小时启动配额**，改用独立审批并发池、有界队列和供应商限流保护；真实模型成本仍单独记账。
2. **审批状态与工具执行状态分离**。没拿到裁决显示“审批未完成，操作未执行”，拿到否定裁决显示“审批未通过”，禁止继续混称“已拒绝”。
3. **同一工具使用稳定卡片承载整个生命周期**，结论和理由持续保留；不靠延长动画解决闪烁。
4. **以同会话多工具并发和多会话等待让位为交付主线（D）**。B 只提供应用/安全配额隔离与最小有界准入，不先建设完整调度平台；D 不等待配置中心、窗口改造或快模型优化。
5. **独立审批 Profile 使用经过评估的快模型，默认保留 `off`（关闭思考）**；模型、端点、凭证与能力适配一起解析。
6. **结构化结果成为实时界面、历史重建、模型反馈和审计的共同事实来源**；桌面、飞书、微信的信任操作共用一次提交协议，持久提交成功后才批准，并返回可查询的明确结果。

**本轮完成条件：**不能仅以配额分账或审批排队上线结项。必须验证一个工具等待审批时，同会话独立工具仍可推进；一个会话全部等待审批时，其他会话仍能取得应用运行槽。

本方案保留：审批 Agent 只读、裁决不写授权记忆、无批准不执行、递归守卫、locked 规则、执行前权限复核。服务故障不自动转人工，不增加审批 Agent 的第三种裁决。

### 1.1 架构归属是实施约束

本方案按整体架构的端口方向实施：**Core 管一次调用内的工具调度；Runtime 管跨调用的准入、运行租约与嵌套调用；产品宿主负责配置、身份、投递、存储和具体工具副作用。** B 的配额隔离与 D 的并发能力不要求先完成整个 SDK 迁移，但新逻辑必须形成可独立测试的 SDK 闭包，不能继续堆入 Electron 主循环。

| 能力 | SDK 所有权 | 产品宿主职责 |
| --- | --- | --- |
| B：应用/安全准入 | Runtime 的独立资源域、队列与票据生命周期 | Product Assembly 注入额度、lane 映射、时钟与计数存储 |
| D1：同调用工具并发 | Core 的节点、依赖、调度、结果顺序；经 Safety/Capability 端口执行 | 工具适配器提供可信资源声明、事实快照、执行与互斥能力 |
| D2：等待让位 | Core 判定可挂起；Runtime 管租约归还、恢复排队与唤醒 | Storage Adapter 保存快照；Driver 只观察状态和发取消意图 |
| 审批回答者 | Safety Boundary 定义回答与校验语义；Runtime 用同一入口发起审批子调用 | 注入产品审批 Profile、提示材料与只读工具实现 |
| C1：人工提交 | Safety Boundary 的提交状态机、主体绑定、permit 与结果契约 | IPC/IM 验证身份和反馈；Storage Adapter 原子保存授权、回执、事实 |
| A：事实与展示 | SDK 定义审批/工具/调用事实与重建语义 | shared/renderer 投影工具卡，处理 i18n、按钮及 UI 通知 |
| C2：模型配置 | Runtime 装配 Profile；Provider Port 暴露规范化能力、用量与错误 | Assembly 提供配置/凭证；Provider Adapter 映射实际模型参数 |

本文保留的 `electron/toolChatLoop.ts`、`CallAdmissionGate` 等路径是**现有接线与迁移位置**，不是新增 SDK 逻辑的永久归属。新增接口在 SDK 内定义，宿主实现接口；禁止 SDK 反向 import Electron、SQLite、Renderer 或厂商客户端。具体接口与最小落地路径见 §17。

## 2. 现状核对与独立判断

### 2.1 已核实事实

| 位置 | 当前行为 | 对方案的影响 |
| --- | --- | --- |
| `electron/confirmation/agentChannel.ts` | 嵌套准入使用 `role=approval-answerer`、`disposition=reject`；失败压缩成 unavailable | 仅调大保留位无法解决速率拒绝和原因丢失 |
| `electron/runtime/callAdmission.ts` | 小时速率先于并发判定；`applyAdmit` 对所有角色增加启动计数 | 必须分离任务计费口径和审批容量口径 |
| `electron/runtime/callAdmissionGate.ts` | 等待队列只在 release 时唤醒；无取消/截止时间参数；单次只检查一个等待者 | 不能只把 reject 改成 queue，否则可能残留等待、空闲槽不被利用 |
| `electron/confirmation/approvalAgent.ts` | 每次内部会话、只读工具集、默认 off、输出上限 2048；装配方可覆盖模型 | 优先优化模型解析和预算，保留会话隔离 |
| `src/shared/assistantFactAggregator.ts` | `tool-confirmed` 可先把工具置 rejected；之后 `tool-result` 被终态守卫挡住 | 拒绝详情必须随审批终态原子提交，不能依赖晚到结果 |
| `src/renderer/components/Chat/ToolCallCard.tsx` | 自动审批提前返回提示行；结束后换回工具行；失败文案读 result | 卡片身份与审批数据均需改造 |
| `electron/ipc/agentProtocolIpc.ts` | 确认响应返回 void；旧信任配置、内存信任与缓存分别写入 | 增加响应契约，并将信任写入与批准结果纳入同一提交边界 |
| `electron/confirmation/imChannel.ts` | remember 先 resolve 再 onMemory；approve_and_trust 则先 onTrust；桌面代答另有 resolve 入口 | 三种路径必须统一，不能仅交换两行顺序 |
| `electron/feishu/feishuImChannel.ts`、`electron/wechat/weChatImChannel.ts` | onMemory 在无 db 时直接返回 | 请求记忆却无法持久化必须显式失败，不能静默批准 |
| `electron/toolConfirmRegistry.ts`、`electron/remote/pendingRequestRegistry.ts` | 当前是内存 pending/resolve/timeout，无 submitting 及提交回执状态 | 超时、撤销、桌面代答和入站回答需共用状态机 |
| `electron/browser/browserConfigDb.ts`、`electron/shell/shellConfigDb.ts`、`electron/database/transaction.ts` | 旧配置存数据库；已有同连接同步事务与嵌套 SAVEPOINT 支持 | 优先采用现有事务入口，不用跨文件补偿模拟原子性 |
| `electron/mcp/mcpSessionTrust.ts` | 独立 Set 表达会话信任，重启清空 | 数据库事务不能回滚 Set；须改为提交后可重建的派生投影 |

### 2.2 对需求描述的补充与修正

- **同步 await 是工具序列阻塞，不是 JavaScript 主线程阻塞。** 同一消息当前按顺序处理工具；不同会话仍可发起多个审批，问题在于共享容量与拒绝策略，不能表述为“系统只能审批一件事”。
- **一次审批拒绝不必然使后续所有工具失败。** 当前 `toolChatLoop.ts` 的拒绝分支写入结果后通常 `continue`，达到连续安全拒绝阈值才 `break`。应分别验证“等待导致延迟”“达到阈值导致中止”，不能把二者合并。
- **双计不严格等于每回合固定 2 次。** 一次外层取票加 N 次内层审批，现实现可消耗 1+N 个启动单位；需求中的约 60/h 是每回合恰好一次审批时的估算。
- **惰性窗口刷新本身未必降低有效吞吐。** 真正要解决的是窗口定义不直观、等待者缺少时间驱动唤醒；不把“实际配额下降”当作已实测结论。
- **不把缺少历史裁决复用视为必修缺陷。** 自动批准的复用可能造成过期授权和上下文污染。本期保留逐次裁决，允许以后复用非授权性的静态材料。
- **P-9 尚不能证明自动审批卡有可点击信任按钮。** 当前该卡明确只读。需要排查人工残留卡、取消竞态或归属错误；解决方向是身份约束和明确 ACK，而不是给自动卡增加信任按钮。

### 2.3 新发现的生命周期风险

`AgentChannel.request` 的通道定时器直接设置 settled 并 resolve，没有经过会释放票据的 finish。之后异步 finish 因 settled 提前返回，存在已持票据不释放的代码风险；准入成功回调也没有先检查 settled，迟到的票据可能启动已结束的审批。

这是静态代码判断，需以 fake timers 和可控 Promise 复现。无论是否启用排队，都应先统一终结和清理出口。扩展同回合并发前，还必须将 `${requestId}:approval` 改为每次 attempt 唯一的子请求 ID，避免取消串扰；单个 AgentChannel 的 inflight 字段不能被多个并发请求复用。

### 2.4 评审阻断项的独立判断

采纳评审 P0。问题不只是“远程回调顺序错误”，而是**确认资格、记忆生效、工具放行与回执送达没有共同的提交边界**。将 onMemory 移到 resolve 前，只能修复一种同步抛错，不能解决双写部分成功、超时竞争、桌面代答抢先、提交成功后网络回执丢失。

进一步发现：远程 onMemory 缺失或 db 不可用也可能被当作成功；MCP 内存信任不能随 SQLite 事务回滚；现有一次性 MemoryWritePermit 在数据库写入前即被消费，写入失败后不能原样复用。§9 因此明确同连接事务、内存投影、permit 失败重发与未知提交结果查询，不使用笼统的“失败就回滚”。

本文对“失败不留下信任”的承诺精确限定为：**提交明确未成功时，本次新增或扩大的授权不可生效；提交已成功但回执未送达时，应查询并补发成功事实，不谎报写入失败，也不自动重放工具。** 原本就存在的合法信任不应被失败回滚误删。

### 2.5 未核实项的处理

| 待核实项 | 验证方法 | 本方案当前结论 |
| --- | --- | --- |
| V-1 实际准入压力 | 受控环境构造 1/4/8/16 会话与配额耗尽；记录原因、等待与成本 | 不声称当前线上错误率或延迟数值 |
| V-2 历史是否恢复理由 | 同一 rejected 工具对比实时、切会话、重启三份投影 | 尚未完整核对历史重建白名单；作为阶段 A 发布门槛 |
| V-3 闪卡/信任按钮归属 | 采集脱敏的 answerer、confirmId、pending 状态和事件序号 | 不将观察现象直接归咎于 Agent 卡 |

## 3. 用户任务与体验边界

面向长时间使用桌面工作台的半技术用户；主要任务是理解并推进当前工作，不是学习配额或审批实现。桌面卡片采用既有 PRODUCT.md / DESIGN.md 的工具行、暖橙行动色、语义状态色与紧凑排版，不增加新视觉体系。

| 场景 | 用户期望 | 目标表现 |
| --- | --- | --- |
| 快速自动批准 | 工作继续、需要时可追溯 | 原工具行直接出现“自动审批通过”，随后显示执行结果 |
| 多任务拥堵 | 知道在等什么，能够取消 | “等待审批资源 · 已等 3 秒”，在原行更新 |
| 审批否决写操作 | 理解具体边界 | 展示操作对象、否决理由、可行的修改方向 |
| 模型服务故障 | 不被误告知操作危险 | “审批服务暂不可用，操作未执行”，提供合适恢复动作 |
| 人工确认已过期 | 知道点击是否生效 | 明确“此确认已结束，未写入信任”，同步最新状态 |
| 无人值守任务 | 无需弹窗且可恢复决策 | 结构化失败给主 Agent；运行详情可查；在父任务预算内改方案或结束 |
| 切换会话/重启 | 看到一致事实 | 终态及理由保留；中断请求不伪装为批准 |

不在本期做：跨任务授权缓存、无人场景人工兜底、多 Agent 投票、所有工具无条件并行、故障时自动改成宽松安全档位。

## 4. 状态与数据契约

### 4.1 两条状态轴

工具轴表达是否执行：`pending → executing → completed / failed`；未执行以 `not-executed` 表达。兼容阶段可继续映射现有 rejected，但界面不得单独据此生成理由。

审批轴表达批准过程：

```text
requested → queued → evaluating → approved
                  ↘             → denied
requested / queued / evaluating → unavailable / timed-out / cancelled
人工通道：requested → awaiting-user → submitting → approved / denied
                                 ↑       ↓
                                 └─ 可确认回滚且仍有效
awaiting-user / submitting → timed-out / cancelled / unavailable（按 §9 仲裁）
```

快速准入可以跳过 queued。`approved` 只表示具备本次批准结论，工具仍可能因权限撤销、事实变化或执行错误而未执行/失败。服务不可用不是模型 verdict；模型输出仍只有 approve / deny。

### 4.2 建议共享契约

以下是设计草图，审批事实、提交结果与生命周期类型由 SDK 公共契约拥有；`src/shared/confirmation/` 只保留迁移转发或产品展示类型，不再作为最终真源。`ToolCallRecord` 等聊天投影通过显式适配消费 SDK 事实，不让 SDK 引用 renderer/domainTypes。当前 SDK 包与目标 `packages/agent-sdk` 的承接方式见 §17.4。

```ts
type ApprovalStatus =
  | 'requested' | 'queued' | 'evaluating' | 'awaiting-user' | 'submitting'
  | 'approved' | 'denied' | 'unavailable' | 'timed-out' | 'cancelled'

interface ApprovalRecord {
  schemaVersion: 1
  approvalId: string       // 一次工具确认的逻辑标识
  attemptId: string        // 每次实际审批尝试唯一
  toolUseId: string
  answerer: 'agent' | 'user' | 'policy'
  status: ApprovalStatus
  cause?: ApprovalCause   // 新建封闭联合，见下表
  reason?: { summary: string; nextStep?: string }
  requestedAt: number
  queuedAt?: number
  startedAt?: number
  settledAt?: number
  deadlineAt?: number
  retryAfterAt?: number
  revision: number
}
```

| 语义 | 建议 cause | 可重试性 |
| --- | --- | --- |
| 批准/安全否决 | agent-approved、agent-deny、policy-denied、user-denied | 否决不可通过原样自动重试争取不同答案 |
| 本地资源不足 | approval-queue-full、approval-queue-timeout | 在父任务预算允许时可重新发起，本期不自动重试 |
| 供应商故障 | provider-rate-limit、provider-unavailable | 返回可重试时间；本期不自动退避重试 |
| 配置/解析错误 | config-error、unparsable | 前者修改配置后重试；后者本期不自动重试 |
| 人工提交失败 | memory-storage-failed、commit-unknown | 已确认回滚才可重新提交；结果未知先查询，不自动重试 |
| 运行边界 | evaluation-timeout、cancelled、interrupted、recursion-blocked、facts-changed、authorization-revoked | 按原因重新规划，绝不沿用旧批准 |

详细 admissionCause、provider 错误码、profileId、policyVersion、事实指纹等留在内部诊断记录；不是每个字段都下发聊天卡片。`retryable` 等执行能力由 SDK 安全/生命周期状态推导；宿主结合操作者权限决定按钮展示，不能根据模型 reason 文本推断。

### 4.3 事件、持久化与投影

1. 增加 `approval-updated` 事实事件，携带完整 ApprovalRecord 快照。以 `approvalId + attemptId + revision` 去重，同 attempt 的终态单调不可回退。
2. 终态事件同时携带规范化的未执行结果（若未获批准），由 reducer 一次更新审批详情与工具未执行状态，消除“先 rejected 后丢 result”的竞态。
3. `tool-result` 仍负责真实执行结果。不应简单删除全部终态守卫；兼容旧事件只允许同工具、同 attempt 的缺失详情补齐，不允许覆盖终态。
4. 统一结果构造函数，为用户界面、模型工具结果、安全审计生成一致的 cause 和说明。模型收到 machine code、是否执行、是否可重试和 reason；不用自行解析中文判断故障。
5. SDK 经 History Port 保存审批记录、终态与事件版本；宿主 Storage Adapter 实现持久化，实时订阅、历史查询、重建白名单同步更新。先提交事实再通知 UI；事件发布失败后通过同一 canonical history 补齐。C1 的授权与事实由同一次原子提交产生，不能再由 Core 追加一份不同 ID 的审批终态。
6. 老记录没有 cause 时显示“操作未执行，原因未记录”，不能凭 rejected 猜测 agent-deny。无需为历史消息补造裁决。
7. 重试是新 attempt，保留旧记录；旧 attempt 的迟到批准只记录诊断，不得改变新 attempt 或触发执行。

## 5. 卡片与交互方案

### 5.1 稳定工具行

始终以 `toolUseId` 为卡片 key，内容结构为“工具和对象 → 当前状态 → 理由/操作”。审批开始、结束和执行完成均在这个容器内更新，不再用一个独立代码提示块替换整行。

```text
修改文件  src/config.ts                   审批未通过
审批认为这次修改会扩大配置的可写范围。
建议只修改本次任务涉及的字段。
[查看操作详情]  [调整请求]
```

```text
执行命令  npm run build                   等待审批资源 · 3 秒
当前审批较多，轮到后会自动继续。
[查看详情]  [取消此操作]
```

以上仅为布局和文案示例，不代表实际裁决内容。

### 5.2 状态、信息和动作

| 状态 | 主文案 | 默认展开内容 | 可用动作 |
| --- | --- | --- | --- |
| queued | 等待审批资源 | 已等待时间；有可靠估计才显示预计等待 | 取消此操作 |
| evaluating | 正在检查操作安全性 | 对象、简短操作摘要；不展示思维链 | 取消此操作、查看详情 |
| approved | 自动审批通过 | 简短标记；理由和耗时折叠 | 查看详情 |
| agent-deny | 审批未通过，操作未执行 | 人话理由与具体下一步 | 查看详情、调整请求 |
| policy-denied | 安全规则禁止此操作 | 命中规则的用户描述 | 查看规则说明 |
| user-denied | 你已拒绝此操作 | 保留用户操作事实 | 查看详情 |
| unavailable / timed-out | 审批未完成，操作未执行 | 区分繁忙、服务错误、超时、配置缺失 | 条件满足时重试；配置错误时打开设置 |
| cancelled / interrupted | 审批已取消 / 审批因应用关闭中断 | 明确原操作未获执行许可 | 查看详情；有效时重新发起 |
| submitting | 正在保存确认结果 | 提交期间不得显示已经批准 | 查询状态；暂不允许重复提交 |
| awaiting-user | 等待你确认 | 操作、影响范围、可选记忆档位 | 允许一次、拒绝及合法信任选项 |

规则否决不展示绕过按钮；“调整请求”只把建议填入输入框，由用户编辑发送，不自动执行。自动审批卡不显示“信任并允许”，不写 decision_cache。

### 5.3 防闪烁与降噪

- 先展示稳定工具行；审批状态持续超过建议 200ms 才显示动态等待指示。快速结束直接展示终态标记，不人为延迟工具执行。
- 无论耗时多短，最终审批结论都保留在工具详情。失败理由默认可见，批准只保留低强调标记。
- 多工具时会话摘要可以显示“2 项等待审批、1 项未执行”，点击定位对应工具；摘要必须由工具事实派生，不能维护第二份计数。
- 不为每次自动批准弹通知。前台在卡片内反馈；后台仅对任务因审批停滞/失败且需要用户动作的情况做聚合通知，沿用通知权限。
- 使用文本和图标共同区分状态，不只用红绿。等待状态用 polite live region，按状态变化播报，不每秒朗读计时器。
- 折叠按钮可键盘操作；切换状态保留焦点；取消按钮消失后将焦点移到对应状态说明。长路径可换行并可复制，长理由先展示摘要再展开；使用现有 i18n 资源，正文遵循产品中文字号与对比度要求。
- 详情预览与 answerer 解耦：自动卡也可查看有界、脱敏的 diff/命令/目标。大文件懒加载，不把额外读取放入审批关键路径；隐藏凭据，禁止渲染模型返回的原始 HTML。

### 5.4 重试的真实语义

“重试”不是重放已批准工具，也不是直接重新调用模型后执行：

1. 宿主校验当前操作者归属；SDK 根据权威工具事实与调用状态确认原工具确实未执行、父任务仍可恢复。
2. 原子创建新 attempt；刷新权限、policy、事实摘要与截止时间，再走完整 gate。
3. 父 turn 仍活跃且支持恢复时，按钮叫“重试审批”；已结束时叫“重新发起此操作”，进入新的任务请求并重新取顶层票据。
4. 阶段 A 尚无恢复能力时不展示不可用的“重试审批”；只提供“调整请求”或明确的重新发起入口。
5. 未知是否已经执行的非幂等操作禁止一键重放，先核对执行日志/外部结果。

## 6. 资源模型与 Q-1 / Q-2 决议建议

### 6.1 三种限制分别负责什么

| 维度 | 作用对象 | 计数/限制建议 |
| --- | --- | --- |
| 用户任务启动配额 | 新的顶层任务 | 按成功受理一次计数；恢复不重复计数 |
| 审批服务容量 | 所有审批 attempt | 独立活跃数、队列、截止时间、每父任务预算 |
| 供应商实际用量 | 所有模型请求，包括审批侦查轮 | token/请求数/费用真实归账；遵守供应商上限 |

**Q-1：审批不应计入用户任务小时启动配额。** 用户已经为顶层工作支付一个启动单位，必要的安全控制不应因相同计数器耗尽而随机拒绝。SubAgent 的既有准入语义不随本改动顺带改变。

**Q-2：审批应受资源约束，但不沿用普通任务的小时启动约束。** 无上限会放大恶意工具调用和服务成本；硬性复用顶层配额则会使安全机制失去可用性。采用独立容量、成本观测、父任务预算和供应商背压，预算耗尽仍不放行。

这改变设计母本 §12“嵌套调用不豁免”的统一准入口径，实施时需同步更新其定义：审批不豁免安全与资源约束，但从顶层启动配额中拆分。不得只改代码而让两份设计互相矛盾。

### 6.2 B 的最小实现范围

B 是 D 的小型基础改动，只解决“安全调用与应用调用不要互相扣额度、占同一份槽位”。

| 资源域 | 顶层任务准入 | 审批准入 |
| --- | --- | --- |
| 应用启动额度 | 沿用现有 global/lane 小时计数 | 不读取、不增加 |
| 应用运行槽 | 顶层任务持有，D 中等待时归还 | 不占用 |
| 安全运行槽 | 不占用 | 独立有界并发计数 |
| 安全等待队列 | 不进入 | 槽满进入短队列，支持取消与到期 |
| 模型真实用量 | 归应用用途 | 归安全用途；都受供应商真实容量限制 |

实现上在 SDK Runtime 内引入一个小型 `ApprovalAdmissionGate`（建议名），由 runtime 实例持有，通过运行时装配注入审批通道，提供 `acquire({ parentId, attemptId, signal, deadlineAt })` 和幂等 release；接口可复用准入模块的类型，但安全状态必须独立。不是给 role 增加一条“跳过小时限制”却继续占应用槽，也不是简单再建一套相同的小时配额。

**安全域首期不新增小时硬额度**：独立并发、短队列、总截止时间和父 turn 尝试上限足以形成有界保护；真实成本继续统计。将来若有明确成本预算需求，再添加只属于安全域的预算，不能重新依赖应用额度。

首期只保留四个容量/时限参数：

| 参数 | 建议初始值 | 作用 |
| --- | --- | --- |
| approval.maxConcurrent | 4 | 跨会话共享安全槽；为单会话并发及其他会话同时留空间 |
| approval.queueLimit | 32 | 有界排队；由 D 限制每父任务预提交数量 |
| approval.totalTimeoutMs | 45,000 | 单次逻辑审批从提交起的总上限，含排队 |
| approval.evaluationTimeoutMs | 30,000 | 获得槽后的裁决上限，实际取剩余总时限与本值较小者 |

这些是待实测的起点，不是延迟承诺。保留父 turn 尝试上限 20 作为内部防循环常量，UI 不新增配置面板；首期不做自动服务故障重试，避免引入另一套调度状态机。失败准确返回，由已有任务流程或用户决定重新发起。

B 的退出条件只有：应用额度耗尽不拦已受理任务的安全审批；安全调用不增加应用计数；槽满能有界等待；取消/超时无泄漏、迟到结果不执行。B 不以“提升同回合并发”为验收项，这由 D 验证。

### 6.3 最小队列规则与不可删减的生命周期

- 安全队列首期 FIFO，不做 lane 权重、老化、预计等待时间或动态优先级。有限队列中既有请求不被新请求插队；D 用每父任务提交上限防止单个会话塞满队列。
- 释放槽后连续取有效队首，填满可用槽；跳过已取消/到期项。等待定时器按 deadline 生效，不依赖下一次请求或某个槽释放才超时。
- acquire 接收 AbortSignal；取消移除队列项并结算，不能只结束外层 Promise。
- 票据成功获取后走唯一幂等释放出口。取消与获取竞争时，迟到票据立即归还，不启动已结束审批。
- 子请求 ID 按 attempt 唯一；每个请求独立取消句柄，不共享单一 inflight 字段。
- 日志只要求统一 ID、cause、等待/裁决耗时和安全/应用用途分类。独立诊断面板和指标平台不属于 B 前置。

这部分虽小，但不能省略：配额拆开后，如果队列不可取消或票据释放有洞，仍会把新安全池耗尽。

### 6.4 供应商容量不是本地任务配额

本地安全槽和应用槽可以分开，供应商的 RPM/并发额度却可能共享。按“实际 HTTP/模型请求在途”持有供应商许可；父 turn 等工具/审批期间不得持有已结束模型请求的许可，否则会在供应商层重新造成父子互锁。

B 复用已有供应商限制与错误处理；如当前没有独立 provider gate，不将新建该系统作为 B 前提，先准确返回 429/不可用、保持本地总量有界。D 的验收必须核对真实网络许可生命周期，不能仅看本地计数正确。

模型客户端无法立即中断时，逻辑审批仍按时结束，迟到结果作废；未结束网络请求仍占物理容量，不得无限启动替代请求。该槽直到物理请求结束/连接关闭才释放，卡住时明确服务不可用。保留 orphanedInFlight 诊断，不以提前清零制造“无泄漏”。

### 6.5 从 B 移出的工作

以下问题仍记录，但不阻挡 D：

| 工作 | 本轮处理 |
| --- | --- |
| 普通 lane 配额配置入口（P-3） | 后续治理；先保留现有默认值，不新建设置页 |
| 普通小时窗口边界改造（P-4） | 后续治理；安全池不使用该窗口；D 的恢复不能复用受小时额度限制的启动 acquire |
| 复杂公平调度/优先级老化 | 延后；先使用 FIFO + 每父任务有限提交与运行上限 |
| 自动重试、退避与熔断平台 | 延后；本轮准确分类并有界终结 |
| 独立可观测面板 | 延后；本轮先保证卡片、结构化日志与唯一关联 ID |

旧 `approvalReservedSlots` 在安全池启用后不再参与审批，避免新旧池双计。无需为本次改动迁移普通任务的小时计数或修改其窗口定义。后续配置改造仍需校验、有效值展示和重启语义，但不放入本轮关键路径。

## 7. D：同会话多工具与多会话运行的核心改造

### 7.1 目标与最小交付拆分

当前瓶颈有两层：**同会话被逐工具 await 阻塞；多会话被等待审批的父任务占住应用槽。** B 解决资源域混用，D 才改变这两种等待行为。跨会话不是天然全部串行，但当前持票等待会降低可用槽，在满载时使其他会话无法推进。

D 拆成两个可验证子阶段，作为本轮主线连续交付：

- **D1：同会话工具调度。** 从“执行完当前工具再看下一个”改为“为已知工具建立节点，调度所有已满足依赖的节点”。审批是节点的一种等待状态，不阻塞调度其他独立节点。
- **D2：跨会话等待让位。** 没有本地运行中的模型/工具、也没有可立即执行节点，只剩审批或其依赖等待时，父任务让出应用全局及 lane 运行槽；审批完成后按恢复队列重新取运行槽，不重扣启动额度。

不把完整工作流引擎、跨进程自动恢复、所有工具语义建模列为 D 前置。首期采用已知工具元数据与保守依赖规则，未知副作用工具作为串行屏障；同进程可恢复，重启明确中断且不自动重放副作用。

### 7.2 D1：节点调度而非整批 Promise.all

节点调度器归 SDK Core，现有 `toolChatLoop.ts` 只负责迁移接线，不再拥有一套平行调度状态。节点至少有 `pending / waiting-approval / ready / running / completed / not-executed`，保存 toolUseId、原始顺序、输入快照、依赖、资源声明与审批 attempt。调度循环每次状态改变后选择所有可运行节点，受单会话工具并发上限约束；“准备事实 → 发起审批 → 等结果”的等待不占本地工具执行槽。

首期产品默认值由 Assembly 注入 Runtime/Core 的调用配置，不硬编码为 SDK 通用规则：每父任务至多 2 个在途审批（排队和裁决合计），同会话至多 2 个实际执行工具。前者与 B 的安全池总并发 4 配合，使单会话可同时审批两个操作，也给其他会话留出容量；到上限的后续节点留在父任务计划里，不预先塞入全局队列。这些是首期产品运行参数，先不新增用户配置。

| 工具关系 | 处理 |
| --- | --- |
| 不同文件的已知只读操作，无前序写依赖 | 可并行；不因另一个独立节点待审批而等待 |
| 同文件先修改再读取，或参数依赖前一步输出 | 建依赖边，保持顺序 |
| 同浏览器 tab、同终端、未知副作用 MCP/Shell | 默认为冲突资源或串行屏障，后续节点不得擅自跨越 |
| 两个已证明独立的文件写入审批 | 可同时裁决；获批后分别复核事实，再按资源冲突决定执行 |
| 写操作无法确定影响范围 | 保持原工具顺序；不能因为模型声称“独立”而放开 |

资源声明经 Capability Registry/Port 由可信工具适配器提供，包含读/写目标和上下文身份。文件路径规范化、别名/符号链接解析由宿主文件能力实现；Core 只消费规范化资源标识与访问模式，不直接 import fs、浏览器管理器或 MCP 客户端。未注册能力不可执行，无法判断的目标保守冲突。只凭输入字符串不同，不能证明不冲突。

不要设置“这一批审批全部结束才能执行”的 barrier。一个节点获批且依赖满足后即可运行；未获批节点只影响自己和其依赖。不同工具的事件按各自 ID 更新，原工具行稳定不重排。

**资源锁与审批事实：**审批等待期间不持有文件/浏览器执行锁，否则会通过另一条路径阻塞独立任务。实际执行前获取必要资源锁，复核最新事实摘要和授权；若已变化，释放锁并重新 gate。不能锁内等待新审批，也不能复核后放锁再用过期事实执行。锁范围覆盖最后复核与对应副作用；审批侦查只读取证，不拥有写执行权。

每个 tool_use 恰好产生一份 tool_result，发给模型时按原始工具序列组装；只在该批全部结算后开启下一次模型请求。首期不做“部分结果先续跑模型”，避免并发修改会话历史。一个审批失败使依赖节点标记 dependency-not-satisfied，不影响独立节点。

### 7.3 D2：拆开任务受理身份与运行租约

应用准入需要暴露两个概念，而不是把现有票据简单 release 后再次 acquire：

| 对象 | 生命周期 | 计数语义 |
| --- | --- | --- |
| 已受理任务身份 | 顶层任务从受理到结束 | 仅首次受理消耗小时启动额度 |
| 应用运行租约 | 父任务实际推进模型/工具时 | 可让出/重新取得；只更新全局与 lane 活跃计数 |
| 安全运行票据 | 独立审批请求运行时 | 只更新安全域；不依赖父任务仍持应用租约 |

在 SDK Runtime 的准入组件上增加受理身份校验和运行租约接口；现有 `CallAdmissionGate` 作为过渡适配/接线点，不再创建第二份票据账本。Core 只通过注入的生命周期接口请求让位/恢复，不访问全局 gate。Runtime 内部的 `resume(admittedTaskId)` 只能由仍有效的已受理任务调用，不能由任意新任务利用该入口绕过小时额度；resume 仍遵守应用全局/lane 并发。

挂起/恢复顺序：

1. Core 调度器确认不存在仍在运行的工具/模型，也没有可执行节点；尚未完成节点都在等待审批或依赖这些审批，向 Runtime 提交带状态版本的挂起请求。
2. 经 History Port 提交最小等待快照并取得提交凭据后，Runtime 将父任务标记 parked，幂等归还运行租约；保留任务身份、事件订阅、取消信号与审批关联。快照写失败则有界终结或保持原租约，不能伪称已可恢复。
3. 审批完成先提交 SDK 事实，再通知 Runtime 唤醒父任务。审批结果若在“检查等待条件—归还租约”之间到达，由 runtime 实例内串行状态转换/版本 CAS 和待唤醒标记保证不丢通知；不能将“Electron 主线程单线程”当成可移植契约。
4. Runtime 将父任务加入运行等待队列，重新取得租约并返回 Core；Core 经 Safety Boundary 检查取消、deadline、策略与权限，再调度 ready 节点。重复审批通知只合并成一次恢复请求。
5. 同时等待的其他审批无需结束；已获批节点可以先运行。再次只剩等待时再次让位，不重复受理/扣额度。

新任务与恢复任务使用同一有界运行队列，按到达顺序选择当前全局/lane 可准入者，跳过被 lane 限制的候选而不丢弃；不做恢复任务永远插队。槽释放、取消和队列 deadline 都触发调度。该最小队列行为属于 D2，不能沿用当前“只检查一个队首、等下一次释放”的不足。

让出运行槽后还要限制 parked 数量，否则可积累无限任务上下文。首期独立常量 `maxParkedTurns=32`：到限时新增挂起请求以明确资源错误结束，取消其未完成审批并释放所占资源，不偷偷保留槽无限等待。进入恢复队列的等待上限建议 30 秒，且不得超过父任务已有 deadline；超时记为“等待恢复运行资源超时”，不要误报模型审批超时。恢复不等于重新给审批完整时限。

### 7.4 恢复边界与最小快照

快照只保存父任务身份、节点状态、输入快照引用、依赖、审批 attempt、policyVersion、事实指纹、执行租约版本和 deadline；不引入可任意跳转的通用工作流 DSL。敏感原文不落诊断日志。

同进程恢复时，批准仅对原事实有效；参数、目标版本、工作目录、授权或策略变化则重新 gate。跨进程重启时，未完成审批/parked turn 标记 interrupted；已获批准但尚未执行的副作用操作不自动执行。执行已开始但结果未知时先核对，不盲目重放。本轮必须经 History Port 重建消息、审批事实和 interrupted 状态；延后的只是跨进程自动续跑，不是历史读取与重建。

同一会话首期仍只有一个活动 turn，改善的是该 turn 内多工具调度；不同时启动多个模型 turn 来绕开审批。多会话并行仍受应用容量约束，但等待审批的会话不应继续占用可执行容量。

### 7.5 本轮核心验收场景

| 场景 | 必须观察到的行为 |
| --- | --- |
| 同会话 A 修改文件甲待审批，B 读取独立文件乙 | A 尚未返回时 B 已执行完成；不能等审批后才看 B |
| 同会话两个独立写操作都需审批 | 两个审批生命周期存在重叠；不能仅把串行任务移进另一个队列 |
| 同会话先改甲再读甲 | 后续读取等待修改完成，禁止为追求吞吐破坏依赖 |
| 两个会话占满 2 个应用运行槽，均只剩审批等待，第三会话执行只读任务 | 前两个会话 parked 后，第三个在审批结束前拿到槽并推进 |
| 应用启动额度已耗尽，先前受理的 parked 任务获批 | 能重新获得运行槽；额度不再扣减；新任务仍受额度限制 |
| 应用和审批使用同一供应商，供应商只有一个模型请求槽 | 父模型响应完成后归还供应商槽，审批可运行；无父子互锁 |
| 审批结果恰逢 park，或一个结果重复通知两次 | 恢复不丢失、租约至多一份、工具至多执行一次 |
| 审批等待期间另一个会话修改目标 | 执行前发现事实变化，重新 gate，不能使用旧批准 |

以上为 D 的发布门槛。只改善审批 p95、只拆分计数、只显示排队状态，均不能替代这些验收。

### 7.6 失败与防循环

agent-deny / policy-denied 进入安全拒绝桶；unavailable / timeout 进入服务失败桶；cancelled 不计入错误。服务故障首期不自动重试审批，主 Agent 改方案/重发仍受父 turn 尝试上限。指纹与尝试计数由所属 Runtime 的调用状态维护，不能通过节点重建或 park/resume 重置预算。

## 8. 审批模型与输入优化

1. 在统一 Runtime 装配流程中增加 `approvalProfileId` 解析，产品 Assembly 提供 Profile 配置和凭证端口；通过 Provider 能力解析固定 model、serviceId、requestedEffort、effectiveEffort、输出与轮数预算。baseUrl/credential resolver 留在宿主与 Provider 适配层，不进入 Core 的调度状态或持久事实。独立 Profile 不等于独立执行引擎：审批通过同一个 Runtime 嵌套调用入口运行，绑定 parentInvocationId、取消链和 security 资源域；禁止审批模块自行创建绕过 Runtime 的厂商客户端。
2. 默认请求保持 `off`，不随独立 Profile 或快模型切换自动开启思考。这是 2026-09-22 对原需求 P-5 的调整：本轮优先控制审批延迟，`off` 不再作为待修缺陷。`low` 仅作为后续评估选项，不是本轮交付或验收要求；只有安全评估收益与延迟、成本对比支持时，再另行决定是否启用。记录 requested/effective；候选模型不支持关闭时须显式报告能力不匹配，不得静默升为 `low`。关闭思考不保证跨模型等时延，仍以实测为准。
3. 不继续默认继承外层昂贵模型，也不硬编码一个可能在用户服务中不可用的模型。首次迁移仅在已配置服务存在经过验证的审批候选时启用；否则明确提示配置缺失，或保持带标记的旧模型兼容模式，不能静默更换供应商。
4. 同一套审批标准、工具白名单与结果解析器用于所有 lane。服务端点与密钥从同一个 Profile 解析，禁止模型切换但复用不匹配凭证。
5. 每次内部会话隔离继续保留。优先优化系统提示复用、有限线索包、流式提早解析完整合法结果等工程开销；不共享可变会话历史，不缓存 approve。
6. 操作描述、文件内容、外部网页均视为证据而非指令。任务摘要只来自可信父任务；保持侦查只读、递归守卫和来源标注。
7. 建立固定评估集：明确允许、明确禁止、授权不足、命令组合、重定向、外发、提示注入、证据不足、解析失败。以错误批准为阻断指标，结合否决误报率、p95 和 token 成本选型。
8. 本文不指定“当前最快模型”。具体快模型选择由现有服务能力与评估决定，不能仅按产品名称承诺安全和性能。

## 9. 全通道人工确认与信任提交协议

### 9.1 唯一提交入口与身份

由 SDK Safety Boundary 拥有 `ConfirmationSubmissionService`（建议名）的提交状态机与绑定校验，经原子提交端口调用宿主存储；Electron 主进程只装配该服务和适配器。桌面、飞书、微信及桌面代答统一提交 allow-once、deny、remember-and-allow。通道只负责解析、身份验证材料和发送反馈，不直接写信任或 resolve 批准。SDK 核心不感知 webContents、飞书/微信客户端、SQLite 连接或 outbox 表。

- 桌面：`agentProtocolIpc` 校验发送窗口，提交原始动作及服务端待确认项引用。
- IM：`ImChannel.tryResolveFromInbound` 接收 `remember`、`approve_and_trust`、普通 Y/N 后统一提交；`onMemory` / `onTrust` 改为服务内部的同步事务写适配器，不再作为通道副作用回调。
- 飞书/微信：保留 owner、私聊/白名单、chat/user、authorizationGeneration 等现有约束，服务在最终提交前重新校验。桌面代答沿用原授权边界，不能凭知道 requestId 就提交。
- `toolConfirmRegistry` 和 `PendingRequestRegistry` 不再各自决定批准；只能登记 waiter 或转发 deadline/取消事件，所有入口引用同一份逻辑确认状态。不得复制两份可独立 resolve 的 pending。
- 客户端只能选择服务端提供的 `memoryTierOptionId` 或受限 trust action；缓存键、命令范围、sessionId 和写入计划从冻结的待确认项派生，不能信任 payload 自报范围。

提交最少包含内部不可复用的 confirmId、confirmationRevision、submissionId、actor、action、可选档位。actor 由可信适配器生成。绑定 requestId、toolUseId、sessionId、answerer、事实/计划摘要、policyVersion、授权代际与 deadline；现有 MemoryWritePermit 继续绑定这些主体，不能用提交服务替代写入侧授权检查。

IM 短码只是查找索引，不是授权或幂等键。幂等键采用“平台/账号/会话/入站 messageId”，并关联完整 confirmId；桌面使用生成后持续复用的 submissionId。保留短码退休墓碑和消息时间校验，防止延迟旧消息撞上重用短码；无法证明归属时只提示重新获取确认，不执行。

### 9.2 单次提交状态机

```text
pending --有效提交 CAS(revision)--> submitting(submissionId)
submitting --事务 COMMIT---------> committed(approved / denied)
submitting --已确认 ROLLBACK-----> pending(revision + 1) 或 ended
pending / submitting --先发生的取消、到期、撤销--> ended
submitting --提交结果无法确定----> reconciling --查持久回执--> committed / ended
```

这是内部提交状态机；UI 的 submitting 覆盖提交及结果核对阶段。committed 映射 approved/denied，ended 根据真实原因映射 timed-out/cancelled/unavailable。committed 为不可逆的“用户回答已提交”事实，不表示工具已执行。授权撤销仍可在执行前阻止工具。

**顺序与唯一成功点：**

1. 完成必要异步加载和数据准备，此时不写有效信任、不批准、不消耗用户一次性授权。
2. SDK Safety 校验绑定与合法档位，CAS 抢占 pending；其他 submission 返回 processing 或已提交结果，同 submission 重放同一回执。调用存储端口前消费本次 permit，并生成仅绑定该 submission 的受限提交凭据；失败后的重新签发规则见 §9.3。
3. SDK 调用原子确认提交端口。SpaceAssistant 的 SQLite Adapter 在短小、同步、无网络/无 await 的临界区，通过 `runInTransaction(getDbConnection(db), ...)` 使用同一连接：复核受限提交凭据及 deadline、取消标志、授权代际、revision、事实与策略所对应的当前有效版本；写旧配置/decision_cache、持久提交回执、审批终态和待发布事件。写入结束、COMMIT 前再次检查实际时间未越过 deadline。
4. **原子提交端口成功是唯一批准与记忆生效点；当前 SQLite 实现对应数据库 COMMIT。** 事务中严禁 resolve waiter、更新有效内存信任、发送网络成功消息或写不可回滚的成功审计。
5. COMMIT 后更新派生投影；凭持久回执幂等结算 waiter，发布事实与审计，再由适配器返回 ACK/IM 结果。发送反馈失败不改变已提交结果；工具执行仍经过当前权限/租约检查。

同连接同步事务内不会穿插同主进程事件回调，但等待准备/锁期间会发生撤销或超时，所以必须在事务内复核。来自其他进程的授权变更必须以数据库版本条件参与提交，不能靠本地 Map 保证顺序。

不承诺分布式消息“恰好送达一次”；承诺逻辑提交至多一次、持久回执可查询、工具放行至多一次。消息消费成功也不等于批准成功。

### 9.3 双写事务与内存信任

SpaceAssistant Storage Adapter 选择**同库同连接事务**作为本期实现；这是宿主实现约束，不是 SDK 对存储技术的要求。SDK 只要求授权、回执与确认事实原子可见，可用内存适配器验证同一语义。明确不采用“先写有效信任，失败后尽力删除”的补偿方案。

| 写入对象 | 处理方案 | 失败保证 |
| --- | --- | --- |
| shell 旧配置 + decision_cache | 在同一事务读取最新配置、合并目标条目并写两份；去重沿用规范化规则 | 第二次写入或回执写入失败，全部回滚；保留原有授权及其他提交 |
| browser 域名/act 旧配置 + decision_cache | 同一事务写配置与缓存；不得用事务外旧快照覆盖整个配置 | 无新增域名或扩大范围残留 |
| IM 记忆与远程 shell trust | 使用同一事务写适配器，不得 resolve 后回调；缺 db/缺适配器显式失败 | 无落盘能力不能伪装成记住成功 |
| MCP 会话信任 | 以事务内的会话授权记录为权威，内存 Set 改成提交后可重建的投影 | 事务失败不增 Set；投影缺失回查权威记录或保守不放行 |
| 提交回执、终态、待发送事件 | 与信任写入同事务；通过 outbox 在提交后发送 | 不出现成功审计对应已回滚授权 |

MCP 会话记录必须绑定 sessionId 和进程启动 epoch；应用重启后旧 epoch 不可命中，保留当前“重启清空”的语义。所有相关信任读取路径需识别这一约束，不能一边新增权威记录、一边让旧 decision_cache 或 Set 无条件旁路。已有会话信任迁移时保持原作用域，不扩大为持久授权。

现有 writer 的日志、广播和内存刷新拆为“事务内纯存储写”和“提交后派生通知”。`AuditedDecisionCache` 的成功审计不能在外层事务提交前不可逆地发出；事务内写 outbox，提交后按 eventId 幂等发送。设置页与其他信任写入口的读改写也要使用同一事务规范，避免并发覆盖。

MemoryWritePermit 当前是内存一次性消费，不能随 SQLite ROLLBACK 还原。失败后废弃旧 permit；仅在明确回滚、pending 仍有效、用户重新提交新 revision 时重新签发。禁止因重试恢复旧 permit，或绕开 permit 直接调用系统管理写入口。

如果后续发现某个写入对象无法加入同连接事务，本期不得继续提供该对象的“记住并允许”：保留“允许一次”并解释记忆不可用。未来若需要跨存储，必须另行引入所有读取端均识别的 staged/committed 授权状态与恢复日志，经验证后再开启；普通补偿删除不满足本方案要求。

### 9.4 失败、超时、撤销和崩溃仲裁

| 时点/竞态 | 仲裁与恢复 | 用户/执行语义 |
| --- | --- | --- |
| 校验失败或抢占失败 | 不写任何授权；返回当前状态 | 无权/过期/处理中有区别 |
| COMMIT 前取消、撤销或达到 deadline | 校验失败并回滚；转 ended，清理 waiter 与 permit | 不执行；本次新增或扩大的信任不生效 |
| 存储写入抛错且确认回滚 | 若父请求仍有效则回 pending 并增加 revision；否则 ended | 本次提交未批准；可重新选择允许一次或重试保存 |
| COMMIT 是否成功无法确定 | 转 reconciling，禁止 resolve 和再次写入；重连后查 submissionId 回执 | 显示“正在核对确认结果”，不能宣称未写入 |
| COMMIT 后 ACK/IM 网络回复丢失 | 查询并重发同一持久回执，不重复写入/执行 | 已确认成功，不能返回 storage-failed |
| COMMIT 后、执行前取消或权限撤销 | 已提交事实保留，执行 gate 拦截；按既有撤销语义使相关授权失效 | 展示“已确认，但操作因取消/撤销未执行” |
| COMMIT 后崩溃且 waiter 未获结果 | 启动时读取回执修复展示/outbox，不自动重放副作用 | 已保存记忆与未执行事实分别显示；MCP 旧 epoch 失效 |
| COMMIT 前进程崩溃 | SQLite 回滚未提交事务，旧 pending 标记 interrupted | 不自动恢复成批准，重新请求确认 |

COMMIT 后的普通“取消操作”不会自动撤销用户明确保存的持久信任；界面须如实显示已记住并提供既有撤销入口。撤销授权与取消本次工具是不同动作。不能删除已存在的信任来制造“零残留”测试通过。

submission 准备阶段不能冻结超时；提交不延长原确认 deadline。同步数据库事务须设置有界锁等待，禁止长时间阻塞主进程。到期判定的线性化时刻为最后校验；COMMIT 先成功后的 timeout 只能影响尚未执行的任务，不能把批准回执改写成未批准。

进入提交前对本次可能新增/扩大的授权键登记读取隔离标记；正常已知 COMMIT/ROLLBACK 后释放。结果未知时保持隔离，所有旧配置、cache 和 MCP 信任读取端对受影响键暂不自动放行，不能仅阻止当前 waiter。进程启动时先核对未完成提交记录、清理旧 epoch，再开放信任读取；数据库不可读时对依赖该库的自动信任命中保持关闭。隔离期间不删除原有授权，核实后恢复真实状态。

reconciling 到诊断截止仍不可查时，终结本次执行等待为 unavailable/commit-unknown，继续后台核对持久事实；未核实的授权记录不得被读取端放行。恢复后即使查到成功也只修复确认/记忆事实，不自动执行已结束的工具。

### 9.5 ACK、远程反馈与查询契约

以下是共享协议草图，IPC 和 IM 适配器都消费同一结果；`tool:confirm-response` 不再返回 void。

```ts
type ConfirmResponseAck =
  | { kind: 'committed'; confirmId: string; submissionId: string;
      revision: number; action: 'approved' | 'denied';
      memory: 'written' | 'none' }
  | { kind: 'processing'; confirmId: string; submissionId: string;
      phase: 'submitting' | 'reconciling' }
  | { kind: 'not-committed'; confirmId: string; submissionId: string;
      code: 'stale' | 'wrong-owner' | 'wrong-answerer' |
        'invalid-memory-tier' | 'storage-failed' | 'cancelled' | 'timed-out';
      canResubmit: boolean; revision?: number }
```

查询接口按 submissionId 返回同一回执/当前状态，必须复核调用者归属；不存在不等于“可直接重放工具”。同 submissionId 携带不同 action/档位须拒绝为协议冲突。未知 confirmId 或无权者返回不泄露会话信息的错误，不回传真实持有人和工具详情。

飞书/微信适配器将三类结果映射成人话回复，并用入站 messageId 去重。原 `tryResolveFromInbound` 的 boolean 只能表达“已识别并消费消息”；应增加独立异步结果处理，不能让调用者把 true 当批准成功。失败反馈发送也有界重试；未送达状态落诊断，不能重新触发提交。

幂等回执至少覆盖确认有效期、平台重投递期和本地恢复保留期，具体期限纳入现有保留策略。清理后旧请求仍按旧 revision/退休确认码拒绝，不能变成一次新授权。

### 9.6 界面与 IM 文案

- 提交中禁用重复确认动作，显示“正在保存确认结果”；processing 时持续查询，不新建 submissionId 自动重试。
- committed：按事实显示“已允许一次”或“已允许并记住”；这是批准回执，不是执行成功通知。
- stale：若已有成功回执则展示成功事实；确实未提交才显示“此确认已结束，本次点击未生效”。
- wrong-answerer：显示“此操作由自动审批处理，不能在这里写入信任”。
- invalid-memory-tier：显示“此记忆范围已失效，请重新选择”。
- 已确认回滚的 storage-failed：显示“未能保存信任，本次提交未批准操作”。仅服务返回 canResubmit 且新 revision 有效时提供“允许一次”或“重试保存”。
- reconciling：显示“正在核对确认结果，请勿重复操作”；不显示“未写入信任”。
- IM 使用相同语义，明确确认短码、结果及可采取动作；重复消息重发原结果，不再次授予权限。

不因失败新建无归属 waiter，不把残留卡变成有效授权入口。飞书/微信回答者策略保持不变，变更的是提交协议与反馈可靠性。

## 10. 可观测性与排障入口

### 10.1 一次审批一条可查链路

统一使用 parentRequestId、toolUseId、approvalId、attemptId、innerRequestId，不再依靠 `:approval` 后缀猜关联。内层请求 ID 必须含 attemptId。

事件包含 requested、queued、started、retry-scheduled、settled、execution-started；核心终态含 answerer、cause、admissionCause、profile/model、policyVersion、queueMs、evaluationMs、totalMs、attemptCount、是否执行以及脱敏 reason。递归守卫等提前退出也必须补齐请求和终态的关联。

人工确认另记录 submissionId、revision、commit/rollback/reconcile、回执送达状态和 outbox eventId；区分“提交成功但通知失败”与“提交失败”。

保留 Agent 日志与 SecurityAudit 的职责，但在安全审计终态直接附上准入/服务失败原因；提供按 approvalId 查询的诊断视图。正常排障不再要求手工打开两个文件拼接。

### 10.2 指标口径

| 指标 | 定义 |
| --- | --- |
| 裁决可用率 | 获得合法 approve 或 deny 的自动审批逻辑请求数 / 自动审批已结束逻辑请求数；主动取消单列，重试不重复计分母 |
| 安全否决率 | agent-deny / 已获得合法模型裁决数；policy-denied 另列 |
| 系统未完成率 | 队列满、资源超时、服务故障、配置/解析错误 / 自动审批已结束逻辑请求数 |
| 审批延迟 | queueMs、evaluationMs、totalMs 分开统计 p50/p95/p99；取消不混入成功耗时 |
| 调度健康 | 活跃数、等待数、最老等待时间、迟到响应、孤儿 in-flight、释放异常 |
| 成本 | 每逻辑审批与每 attempt 的实际请求/token/费用；服务不提供用量时记 unknown，不能记 0 |
| 体验一致性 | 缺理由终态数、过期点击数、实时/重建不一致数 |

指标维度限 lane、profile、cause 等低基数字段。requestId 放日志关联，不作为时序指标标签。原始命令、完整路径、文件内容和凭证不进入指标；导出诊断默认脱敏。reason 为不可信文本，限制长度并脱敏后落日志。

### 10.3 用户入口

工具卡“查看详情”展示操作概要、结果、理由、等待/裁决时间；“复制诊断信息”仅复制脱敏关联 ID 与原因。设置中的审批状态面板显示有效模型、服务连接状态、当前等待数和配置问题，不在聊天卡展示内部票据或调度器术语。

### 11.2 压测与建议目标

在固定模型、固定证据包、固定网络条件下，分别跑 1/4/8/16 父任务；每任务 1/5/20 工具；区分全独立和有依赖组。记录样本量、模型版本、错误分布与真实成本。受控故障用 stub，真实服务评估另跑，不把两者延迟混为一组。

建议发布目标：

- 安全不变量、未批准不执行、计数准确、票据不泄漏和重建一致性：必须 100% 通过确定性测试。
- 所有未执行新记录有明确分类；所有模型 deny 有可读理由或受控解析失败说明。
- 无队列积压的典型审批 total p95 目标 ≤5 秒；首次真实基线若不满足，记录差距后调整模型/证据，不通过延长 UI 动画掩盖。
- 使用立即返回 stub 时，本地调度与事件投影额外开销 p95 目标 ≤100ms，单独测量，不含模型网络耗时。
- 每次请求在有效总 deadline 内逻辑收敛（允许事件循环调度误差），没有因遗漏时间唤醒导致的超期等待。
- D1/D2 必须通过 §7.5 的时序断言，再对独立工具样本验证相对顺序基线的耗时改善；依赖组不得改变执行顺序。未达成则本轮吞吐目标未完成，不能以 B 已上线结项。

实施依赖按能力组织，字母不是串行排期：

- **吞吐主线：冻结 §17 最小契约 → A 的唯一 ID/终结清理/状态契约 + B 最小隔离 → D1 → D2。** A 的其余视觉完善可与 D 推进，不必先建完诊断页。
- **安全修复线：C1 按 §9 完整收口所有通道。** C1 仍是新信任提交承诺的发布前置，但它的 outbox/回执存储不是自动审批调度的技术前置；不把两条线人为串成大瀑布。共享取消、确认终态和 revision 契约需先对齐，涉及人工确认并行/恢复的联合发布必须通过 C1 回归。

本轮吞吐交付必须包含 D1+D2；B 可以先合入作为小型基础补丁，但不能视为本轮问题已解决。C1 内仍按“共享状态机与事务 → 全部写/读入口 → ACK/IM 反馈 → 故障验收”完成，不只上线桌面端。

### 12.1 兼容和灰度

- C1 对桌面、IM 和桌面代答必须原子切换到同一提交服务；旧进程内 pending 在切换前排空或明确取消，不能同时接受旧 resolve 和新提交。数据库 schema 可先上线，但新信任读取/写入语义未就绪前不开启新记忆提交。
- 若需回退到不认识新提交协议的版本，禁用“记住并允许”并保留安全的允许一次；不得恢复先批准后写记忆路径。先排空 outbox 并保存回执；MCP 旧 epoch 不得被旧读取端误当长期信任。
- 先发布可兼容旧字段的读取与投影，再发布新写入；统一 schemaVersion，旧事件进入单向兼容适配器。
- 独立开关：新投影、独立审批池、独立 Profile、同回合调度。安全规则、批准校验与 fail-closed 不设可绕过开关。
- 灰度从开发环境故障注入开始，再到少量桌面会话，最后覆盖 automation。IM 回答者策略保持原样，仍回归其人工确认路径。
- 切换调度器只影响新请求，正在运行的 attempt 由原调度器完成/取消，不跨池迁移票据。回滚必须先停止新准入并排空或显式终结队列。
- 回滚可退回顺序调度或旧模型；不回滚已修复的 cause 显示，不删除新审计字段，不通过自动批准缓解故障。
- 数据迁移采用新增字段/表，不破坏旧结果；新任务恢复逻辑未上线前不写可被误判为可自动恢复的 checkpoint。

### 12.2 评审必须确认的选择

本文已给出推荐方向，以下事项由实现评审确定具体值，不影响方案完整性：

1. 安全池并发 4、队列 32、裁决/总时限 30s/45s，及 D 的每父任务在途审批 2、工具执行 2、parked 上限 32、恢复排队上限 30s，是否符合压测容量。
2. 独立 Profile 的默认候选、能力降级与旧模型兼容期；必须附安全评估结果。
3. 阶段 D 的资源键覆盖工具范围；未覆盖工具一律串行。
4. 审批诊断保留期限与内部会话清理策略，沿用现有保留设置并确保理由摘要不会提前丢失。
5. 将母本“统一准入不豁免”更新为本方案三维资源口径，并明确迁移说明。

## 15. v0.3 范围收敛与优先级调整

根据本轮反馈，将“配额治理”和“任务推进”分开交付。B 收窄为安全/应用资源隔离及最小可取消队列；删除其复杂优先级、独立排队时限、自动重试、普通 lane 设置和小时窗口改造要求。完整可观测面板亦不在关键路径。

## 17. v0.5 SDK 架构对齐与最小落地契约

### 17.1 对齐结论与不变项

按 [SDK 架构设计](./architect/agent-sdk-architecture-design.html) 的 Runtime / Core / Ports / Host 边界修订。B 仍是最小配额隔离，D1+D2 仍是本轮核心目标，思考默认仍为 off，C1 的原子提交与全通道安全要求不减弱。新增的是职责与依赖约束，不是要求先交付完整 SDK V1–V3。

以下接口名为设计建议，不声称仓库已具备；应沿现有公共契约扩展，不另造完整通用调度框架。

### 17.2 最小端口与唯一事实源

| 契约/组件 | 调用关系 | 必要语义 |
| --- | --- | --- |
| InvocationLifecycle | Core → Runtime | 调用级 opaque handle；请求 park、获取有效运行租约、结束；不暴露全局 gate 或可伪造的裸恢复 ID |
| Runtime admission | Runtime 内部 | 应用启动身份与运行租约分离；安全资源域独立；新任务/恢复队列有界；同一身份只有一个活跃租约 |
| History Port | SDK Core/Runtime → Storage Adapter | 提交带 expectedVersion 的等待快照、追加有稳定 eventId 的事实、读取/重建；幂等重放与失败显式返回 |
| Safety/Answerer Port | Core → SDK Safety → 配置的回答者 | 每节点 gate、事实/权限复核、审批结果及取消；Agent 回答者通过 Runtime 子调用，不成为另一套工具执行路径 |
| ConfirmationCommit Port | SDK Safety → Storage Adapter | 一次原子提交绑定主体、期望版本、受限授权变更和 canonical 确认事实；返回 committed/not-committed/unknown，可按 submissionId 查询 |
| Capability Port | Core → 已注册工具适配器 | 可信资源声明、事实快照、执行前校验和执行；宿主负责系统路径、浏览器/MCP 等具体副作用与互斥 |
| Provider Port | Core → Provider Adapter | 规范化响应、能力、usage/error 与取消；底层请求许可的释放不依赖父 turn 结束 |

**一次事实只有一个权威提交入口：**普通审批结果经 History Port；C1 需要授权与确认事实同时生效时，由 ConfirmationCommit 的宿主实现将同一 canonical 事件写入同一历史存储事务，并返回 history version/eventId。Core 收到成功只消费/转发该事实，不再次写一份审批终态。独立 History 与授权存储无法满足原子语义的宿主，必须明确拒绝 remember-and-allow 或提供合格的提交实现，不能先批准再补历史。

原子提交端口接收结构化、受限的提交计划及主体证明，不接收任意 SQL/任意回调，也不把数据库连接传入 SDK。Storage Adapter 复核其控制的版本/持久授权状态；SDK Safety 维护 permit 与调用内状态。异步适配器必须承诺线性化的提交/撤销顺序与明确 unknown 结果；不能依赖当前同步 SQLite 恰好不穿插回调来定义公共安全契约。

### 17.3 park/resume 的跨层握手

Core 与 Runtime 各自只有一份状态：Core 的节点状态决定“是否可等待”，Runtime 的租约状态决定“是否可执行”，History 保存可重建事实。Renderer、Driver 和 SQLite Adapter 都不能独立驱动工具节点。

1. Core 通过调用级 handle 提交 `park(expectedExecutionVersion, checkpoint)`；不自己 release 全局计数。
2. Runtime 串行仲裁 park 与审批完成通知，经 History Port 提交快照，再归还运行租约。若期间有完成通知，则保留待唤醒位；若尚未释放就有 ready 节点，可取消这次 park，避免无意义地反复取票。
3. 审批完成不要求父任务持有应用租约。先提交结果，再由 Runtime 将父任务送入恢复队列。
4. 恢复只返回绑定 runtimeId、invocationId 与 generation 的租约；Core 验证它仍有效后再调度节点。重复、跨实例、过期 handle 均不可取得执行权。
5. History 写失败不得静默降级成内存成功：显式失败并清理，或在既有 deadline 内保留原状态；不能以虚假提交凭据让出运行槽。
6. 应用退出/崩溃后由宿主恢复装配经 SDK History 语义标记 interrupted；重建事实必须支持，自动续跑副作用仍不在本轮范围。

此握手是本次 D2 的最小生命周期扩展；不要求对外公开所有内部节点，亦不要求能将一个运行中调用迁移到另一进程。

### 17.4 包边界、实例所有权与迁移

**当前承接与最终归属：**整体架构目标是 `packages/agent-sdk`；当前可用门面是 `packages/agent-core`。若实施时目标包尚未建立，新增纯契约及调度/runtime 模块先放在现有 SDK 包内部并从公共入口导出，不能新增到产品 shared 后再从 SDK 反向转发。目标包就绪时整体迁移这些模块，旧入口单向兼容转发；不并存两份实现，不为本需求提前迁移全部旧主循环。

最小落地顺序：

1. 冻结 §17.2 契约与禁止依赖；把新增纯节点调度、准入和提交状态机放进 SDK 可测试闭包。
2. 为现有 Electron 主循环、调用准入、数据库和确认通道增加薄适配层。旧代码只接入新组件；涉及新功能的路径不再维护第二份 queue/pending/租约状态。
3. 先用无 Electron 的内存宿主跑核心时序，再接 SQLite/IPC/IM。生产接线仍可以暂留现有文件，但不得把 AppDatabase、webContents 或厂商客户端带回 SDK。
4. SDK 全量包迁移按架构路线另行推进。本轮不声称消除了旧代码所有依赖，只要求新增闭包和接线方向符合目标。

**实例所有权：**应用/审批准入、parked 表、恢复队列、确认 pending、permit 和取消关联归 runtime 实例；父子调用继承所属实例。禁止新增模块级共享 Map 或进程单例。生命周期句柄由 Runtime 创建，不信任 Driver 自报 instanceId/requestId 取得恢复权。

同一宿主若需跨 Runtime 共享真实物理资源，例如供应商并发、文件锁或同一数据库中的授权写入，由 Assembly 显式注入共享资源适配器，标明作用域与命名空间；这是资源共享，不是共享两个 Runtime 的逻辑 pending/取消状态。取消一个实例不得误取消另一个实例，即使两者局部 requestId 相同。

产品 lane、并发默认值、私聊身份、审批提示材料和模型选择都由 Assembly 注入；SDK 保持统一机制。桌面、飞书、微信、automation 只在身份/投递适配上不同，不能为每个入口复制 D1/D2 的实现。
