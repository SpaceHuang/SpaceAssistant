# 三、许可与调度

> 本篇回答一件事：**一个 Turn 什么时候能执行它的下一个调用。**
>
> 答案分成两段，分别由两个角色回答——**信号量**回答"就绪还是阻塞"，**调度器**回答"上不上、什么时候上"。两者缺一不可，也不可互相替代。
>
> 术语：本篇的"**许可**"（permit）指可获取、可归还的计数对象，即 [04-quota-and-guards.md](./04-quota-and-guards.md) 所说的配额中的容量类。

---

## 1. 反模式与正模式的真正分界

反模式不是"有调度器"，而是——

> **让调度器去判断"谁该被唤醒了"。**

```text
loop():
  while true:
    for each 等待中的 Turn:
      if 它的许可现在够了吗: 推它执行      ← 调度器在做"检查谁就绪"
    sleep
```

这是 **O(等待者数) 的重复检查**，CPU 烧在"复查条件"上，而调度器成了最忙的角色。

**正模式**是把"发现谁就绪"下放给 `V`：

```text
V(permit):
    atomic {
        count += 1
        if (waiters 非空) wake_one(waiters)     ← 就绪化：把这个等待者移进【就绪队列】
    }
```

`V` 在临界区里顺手完成移交——**O(1)**。调度器从此只面对"已经就绪的人"。

> **一句话**：信号量负责"就绪化"，调度器负责"执行"。前者是状态的判定，后者是执行的决定。

---

## 2. 四个角色与三个状态

| 角色 | 职责 | 归属 |
| --- | --- | --- |
| **许可**（信号量） | 决定"**就绪 or 阻塞**"——能不能执行 | 机制（§3–§5） |
| **等待队列** | 因许可不足而等待的 **Call** | **许可对象的字段**（`permit.waiters`） |
| **就绪队列** | 已具备执行资格、等待被执行的 **Call** | **调度器** |
| **调度器** | 从就绪队列**选取**（优先级 / 公平）并**正式启动** | 机制（§6） |

对应的三个状态——**主体是 Call**（[02](./02-runtime-core.md) §2：同一 Turn 可以有多个 Call 同时处于不同状态）：

```text
running ──P 失败──▶ blocked（离开就绪队列，进入 permit.waiters）
blocked ──V 唤醒──▶ ready  （进入 scheduler.readyQueue）
ready   ──调度器选中──▶ running
```

### "就绪 ≠ 执行"为什么必须分开

| 原因 | 说明 |
| --- | --- |
| **临界区要短** | `V` 在临界区内，只做最小操作（`count += 1` + 移队列），**不在里面执行 Turn 的下一步** |
| **批量就绪需要选择** | 一次归还多个许可会唤醒多个等待者；此时要**挑一个**执行（交互式优先于后台）——而 JS 微任务队列是 FIFO，**没有优先级概念** |
| **执行是调度器的决定** | "就绪"只表示"可以上"，"上不上、什么时候上"由调度器说了算 |

**第 2 条是关键**：把"唤醒"直接做成"执行"，就等于把调度权交给了 `resolve` 的调用顺序——而那只是个 FIFO 队列。

## 3. 许可对象

```ts
type Permit = {
  count: number                  // 剩余许可 —— 唯一真相
  waiters: Queue<Waiter>         // 等待队列（按唤醒策略排序）
}

type Waiter = {
  callId: CallId
  priority: number
  seq: number                    // 到达序
}
```

### 另一处必需状态：谁持有着它

`count` 只说"还剩几个"，不说"被谁占了"。而**结算时必须知道"该归还哪些名字"**，所以：

```ts
type Call = {
  ...
  heldQuotas: QuotaName[]        // P 成功时写入；V 时据此归还
}
```

**`heldQuotas` 记在调用上，不记在许可上**——因为"归还"发生在调用结算时，从调用读它最直接，许可对象不必维护反向索引。

**`count` 与 `heldQuotas` 的一致性由临界区保证**：两者必须**同步地一起改**——

| 操作 | `count` | `heldQuotas` |
| --- | --- | --- |
| `P` 成功 | 每个名字 `-1` | `push(那组名字)` |
| `V` 归还 | 每个名字 `+1` | 清空 |

这就是"`count` 由临界区保证一致"的完整含义（[02-runtime-core.md](./02-runtime-core.md) 不变量 I3）——**不是"每次遍历数一遍"，而是"两者永远同步地一起改"**。

### 许可 ≠ 物理资源

全篇最要紧的一句话：

> **许可只是"通行的名额"，不是资源本身。**
>
> 机制保证的是"**同时最多 N 个持有者**"，而不是"持有者拿到的是它想要的那个资源"——**后者是上层的责任。**

| | 保证 | 不保证 |
| --- | --- | --- |
| OS 信号量 | 并发 ≤ N（计数 + 原子性 + 唤醒） | 你拿到的句柄是不是你要的那个 |
| 本设计 | 同名许可的持有者数 ≤ 容量 | 资源如何分配、谁与谁应当互斥 |

**因此机制不回答**：有哪些许可、容量多少、哪些操作去获取哪些许可、谁与谁应当互斥——全部属配置与声明。

**"互斥"不需要机制的任何支持**：它就是"两个操作获取同一个容量为 1 的许可"。**推论**：机制里没有"冲突判定"、没有"资源等价类"、没有"屏障"。

### `count` 是权威

`count` 是被临界区保护的整数，与"持有者集合"必须始终一致，**由原子操作保证**（不变量 L1）。它不靠"每次遍历数一遍"，靠"临界区保证"；重启后可从事实重建（见 [07-failure-and-recovery.md](./07-failure-and-recovery.md)）。

## 4. P：获取

```text
P(call, names, { bWaitAll, timeout }):
  atomic {
    for (;;):
      if 满足条件(names, bWaitAll):
        for each taken name: count -= 1
        return success
      blocked = 第一个不满足的 name
      把 waiter 加入 blocked.waiters     // ← 检查与入队【同一临界区】
      （离开临界区）挂起：返回未决议的 Promise
      若设了 timeout，同时 schedule 一个到期唤醒
      // 被唤醒或超时后，回到 for 顶部重新检查
  }
```

| 要点 | 原因 |
| --- | --- |
| **检查与入队同一临界区** | 否则"检查到 count==0 → 释放锁准备入队 → 他人 V 并唤醒 → 队列里还没有我" ⇒ **丢唤醒** |
| **`for(;;)` 而非一次判断** | 唤醒后必须**重检**：可能多个被同时唤醒抢一个许可，也可能虚假唤醒 |
| **"被唤醒"只是"重检"的触发** | 唤醒不等于授予（不变量 L3） |

## 5. V：释放与就绪化

```text
V(call, names):
  atomic {
    for each name in names:
      count += 1
      if (waiters 非空) wake_one(name)   ← 把该 waiter 从等待队列移入【就绪队列】
  }
  // 移入就绪队列（ready.push）内部会唤醒阻塞中的调度器，无需额外触发
```

| 要点 | 原因 |
| --- | --- |
| **`count += 1` 与 `wake_one` 同临界区** | 否则丢唤醒（他人在窗口内入队，却没人叫它） |
| **`wake_one` 是默认，不是优化** | 归还**一个**许可只需唤醒**一个**等待者。唤醒全部会造成"多个醒来、一个拿到、其余又睡回去" |
| **`wake_one` 只做"移入就绪队列"** | 执行留给调度器（§6）——临界区里不做重活 |

### 唤醒策略决定等待队列的顺序

`wake_one` 选谁，由 `waiters` 的排序键决定：

| 策略 | 效果 |
| --- | --- |
| **FIFO**（按 `seq`） | 先等先得，公平；可能有护送效应（convoy） |
| **优先级**（按 `priority`，同级按 `seq`） | 交互优先于后台 |

**只有同一个许可的等待者之间才存在竞争**，所以"等待者按名字分散存放"本来就是对的（OS 也如此）——公平性不需要全局视野。

### 多许可的活性问题（`wake_one` 不够）

**上面的"`wake_one` 是默认"只对单许可成立。** 它与 `bWaitAll` 不能同时成立——一个反例：

```text
许可 A、B 均无余量
W1 等 [A, B]、W2 等 [A]     → 两者都先挂在 A 的队列上

A 被归还 → wake_one(A) 唤醒 W1
W1 重检：A 有了、B 还没有 → 它改挂到 B 的队列
此时 A 有余量，但 W2 已不在「被唤醒」的位置
→ 若再无 A 的归还事件，W2 永远不运行        ← 丢唤醒
```

**根因**：被唤醒者**消费不掉**这个许可（它还需要别的），却把唤醒机会用掉了。

**解法**：唤醒时**跳过不满足的等待者**，直到找到一个能真正拿到的：

```text
wake_one(name):
  while (waiters 非空):
    w = 队列头部
    如果 w 声明的全部许可现在都满足 → 移入就绪队列；return
    否则 → 移出队列、改挂到它下一个不足的许可上
```

**代价**：`V` 不再是严格 O(1)，而是 O(跳过的等待者数)。**但这是必需的**——现状 `ResourceLockRegistry` 的"循环扫描队列、找第一个能满足的"**不是低效，而是多许可的必需**。

> **多许可要单独设计、单独测试**（§8）。先用单许可把主路径跑通，是多许可的前置。

## 6. 调度器：一个阻塞在就绪队列上的循环

调度器**不是"被触发的一次性函数"，而是一个循环**——它阻塞在"就绪队列有内容"上：

```ts
async function schedulerLoop() {
  for (;;) {
    const call = await ready.take()    // 空则挂起；有内容则被唤醒
    await start(call)                  // ★ 只等"启动"，不等外部结果
  }
}
```

**★ `start` 的契约必须精确**——它只做两件事：

1. 把该 **Call** 交给它的执行器（`executor.start(call, onOutcome)`）——**非阻塞**
2. 立即返回，回循环取下一位

**它绝不等待外部结果**——否则一个慢调用会卡住整个调度循环（那就退化成"调度器做循环等待"的反模式）。

换句话说：**调度循环的每一次迭代都是"启动式"的**——`start()` 本身非阻塞（§2 要点 1），`step` 只是等这个非阻塞调用返回。

### 这不是轮询

| | 行为 | 空闲时 |
| --- | --- | --- |
| **反模式** | 循环 + **检查条件**（`while (ready.length === 0)` 空转、周期性扫描） | **烧 CPU** |
| **本设计** | 循环 + **阻塞等待**（`await` 一个可等待对象） | **挂起，零消耗** |

**"循环"本身从来不是问题，"循环里轮询检查"才是。** 判据是**空闲时它在干什么**——空转，还是挂起。

### 对称性：就绪队列本身就是一个可等待对象

`ready.take()` 与 §4 的 `P` 是**同一套机制**：

```ts
class ReadyQueue {
  private items: CallId[] = []
  private takers: Waiter[] = []           // 等"有内容"的（这里就是调度器）

  push(call) {
    items.push(call)
    takers.shift()?.resume()              // ← 与 V 的 wake_one 同构
  }

  async take(): Promise<CallId> {
    for (;;) {
      if (items.length > 0) return items.shift()   // ← 与 P 的"检查 + 占用"同构
      await suspend()                               // ← 与 P 的"入队 + 挂起"同构
    }
  }
}
```

**"就绪队列"就是一个 `count = 队列长度` 的可等待对象。** 于是整个设计收敛到**一个原语**：

> **可等待对象 = 条件（`count` / 长度）+ `waiters` + 原子操作 + 挂起/唤醒。**
>
> 许可（等"有余量"）与就绪队列（等"有内容"）都是它的实例。

**"这套把戏"的正确用法就是：凡"等某个条件成立"，就用它——而不是用循环去检查它。**

### 调度器的三点

| 要点 | 说明 |
| --- | --- |
| **阻塞而非轮询** | 无就绪者时挂起在 `ready.take()`，不消耗资源 |
| **选择权在它** | `ready` 内部按优先级排序——非空不等于立即执行，**"上不上、何时上"由调度器决定** |
| **执行权只从它出** | 由它**启动 Call**（越过派发边界）——它就是"正式执行下一个调用" |

**"启动 Call"即执行**：调度器把该 Call 交给执行器启动（`start()` 非阻塞），随后立刻回来取下一个——**它不等任何外部结果**。

**所以"一次调度"推进的粒度是一个 Call**——不是"整个 Turn"，也不是"恢复某个协程"：**状态机的主体是 Call**（[02](./02-runtime-core.md) §2）。编排协程的恢复只是 `call()` 的 Promise 被 resolve 的结果，**不是调度动作本身**。

## 7. 底层机制：JS 提供了什么，我们要做什么

| 能力 | 由谁提供 |
| --- | --- |
| 协程挂起（让出） | **JS**：`await` 一个未决议的 Promise |
| 定时唤醒 | **JS**：`setTimeout` |
| 临界区 | **JS**：一段不含 `await` 的同步代码（单线程，天然互斥） |
| **等待队列 / 就绪队列** | **我们** |
| **"就绪化"的时机**（`wake_one`） | **我们** |
| **"执行"的选择与时机** | **我们**（调度器） |

**所以"底层机制帮我们把该唤醒的对象自动推过来"指的是上半张表**：我们不必自己实现线程阻塞与唤醒。**但"谁就绪、谁执行"仍是 Runtime 的职责**——这就是调度器存在的位置。

## 8. 多许可：`bWaitAll` 与 `bWaitAny`

标准原语（对应 `WaitForMultipleObjects`），不是需要各自发明的策略：

| 选项 | 语义 | 主用场景 |
| --- | --- | --- |
| `bWaitAll: true` | 全部就绪才返回 | **一个调用需要多个许可**（如 `[tool:concurrent, process:shell]`） |
| `bWaitAll: false` | 任一就绪即返回 | 保留语义 |
| `timeout` | 到期返回失败 | 审批等待、槽位等待 |

**实现要点（`waitAll`）**：全部满足时在临界区内**一起减**（避免部分持有）；不满足时挂到**第一个不满足的**许可队列上；被唤醒后**重检全部**。

**但"唤醒一个"对多许可不够**——§5「多许可的活性问题」给出了反例：被唤醒者若**消费不掉**许可，会把唤醒机会用掉。所以多许可的唤醒必须**跳过不满足的等待者**，`V` 的代价是 O(跳过的等待者数)。

**因此多许可要单独设计、单独测试**（用确定性时序覆盖"部分满足 → 改挂 → 丢唤醒"这类反例）。**先用单许可把主路径跑通，是多许可的前置。**

**死锁归业务**：`waitAll` 天然可能死锁（A 持 P1 等 P2，B 持 P2 等 P1）。机制**不负责预防**——那是配额设计的事（见 [04-quota-and-guards.md](./04-quota-and-guards.md) §9）。机制只保证"每个许可的持有者数不超过容量"。

## 9. 五条"被动化"纪律

**判据**：一旦出现"**循环地检查条件是否满足**"，就是反模式。

| 场景 | 反模式 | 正模式 |
| --- | --- | --- |
| 发现谁就绪 | 调度器扫描等待者 | `V` 内 `wake_one` 就绪化（§5） |
| 获取 | 循环尝试直到成功 | 挂队列，等唤醒（§4） |
| 收尾（`drain`） | 循环检查"还有在途吗" | 等信号：在途计数归零时 resolve |
| 超时 | 周期性检查是否到期 | 挂起时 `schedule`，到点唤醒；成功获取时取消定时器 |
| 观测 | 定期轮询状态 | 状态钩子主动推送（[05-extension-points.md](./05-extension-points.md)） |

**区分**：调度器的循环**不是**反模式——它**阻塞**在可等待对象上（`await ready.take()`），而不是**轮询**条件。判据是"空闲时它在干什么"：空转，还是挂起。

## 10. 不变量

| # | 不变量 |
| --- | --- |
| **L1** | `capacity - count` 等于"该许可的持有者数"（`count` 是**剩余**许可），由临界区保证 |
| **L2** | `waiters` 中的 **Call** 一律不持有任何许可 |
| **L3** | 唤醒只把 Call 从"阻塞"变为"就绪"，**不等于授予、不等于执行** |
| **L4** | `count += 1` 与**唤醒动作**在同一临界区（防丢唤醒） |
| **L5** | "检查是否可获取"与"入队"在同一临界区（防丢唤醒） |
| **L6** | 一个 **Call** 在同一时刻**至多位于就绪队列或某个等待队列之一**，不可能同时 |
| **L7** | 进入 `running` 前必须已在就绪队列中被调度器选中——**没有"首次直达"的例外** |

**L6** 保证不出现"幽灵就绪者"；**L7** 保证执行权只从调度器出。

> **注意主体是 Call，不是 Turn**：同一 Turn 可以有多个 Call 同时处于不同队列 / 状态（[02](./02-runtime-core.md) §2）——这是并行工具链的正常形态，也正是"执行流状态"表达不了、必须改以 Call 为主体的原因。

## 11. 与其他模块的关系

| 模块 | 关系 |
| --- | --- |
| **CallTable** | 权威：记录每个调用声明了哪些许可、是否已派发 |
| **租约** | 长生命周期的**独占占用**（如 `session:<id>`）——**不随调用结算归还**，由所有者显式释放 |
| **许可对象** | `count` + `waiters`，被临界区保护 |
| **调度器** | **就绪队列 + 选择 + 启动**；被动触发，不扫描等待者 |
| **执行器** | **不接触许可与就绪队列**——只负责执行与回报 |
| **Hooks** | 只观测（可观测许可与调度变化，不参与判定） |
| **FactLog** | 不记许可占用（可重建）；只记"派发边界越过" |
| **时钟** | 仅用于 `timeout` 与定时唤醒 |
| **装配** | 提供许可清单（名字、容量）与"哪个调用获取哪些许可"的映射 |
