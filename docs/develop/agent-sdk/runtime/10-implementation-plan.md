# 十、实施计划

> **定位**：把 01–09 的目标设计落成可执行的阶段计划。第八篇 §5 给了路径骨架（五步 + 并行线），本篇把它展开成"**每步做什么、动哪些文件、怎么验收、怎么回退、什么时候删旧机制**"。
>
> **状态**：计划稿（未开工）｜**编制**：2026-10
> **与设计稿的关系**：设计稿（01–09）回答"目标形态是什么"；本篇回答"**从现状走到那里，按什么顺序、分几步、每步的出口判据是什么**"。术语一律沿用 README §5。

---

## 1. 五条纪律

这五条约束整个执行过程，越靠前越容易被违反、代价越大。

| # | 纪律 | 为什么 |
| --- | --- | --- |
| **D1** | **每一步都必须能独立回退** | 五步里有三步改行为；没有回退开关的重构会变成"只能往前走"的赌博 |
| **D2** | **新旧并行 + 结果对拍** | 前两步"不改行为"，所以可以逐 turn 比对两套认知；差异率是唯一的客观信号 |
| **D3** | **每一步设明确的删除截止点** | park 的教训：新机制上线、旧机制因"还有测试罩着"永久留下。**没有截止点的迁移等于没迁移** |
| **D4** | **出口判据（gate）不达成，不进下一步** | 尤其阶段 1——它的产出是"状态机是否描述得完整"，这个答案决定后面四步是否成立 |
| **D5** | **必需件缺失 ⇒ 启动即失败** | 禁止静默降级。空参 `createAgentRuntime()` 造出"看起来在跑、实际没限流、没审计、不能恢复"的系统，现状已吃过一次 |

**依赖关系**：

```text
阶段 0  契约冻结（0 行为改变）
   │
   ├──────────────▶ 并行线 S  影子调用收编（只需 call()，不依赖主线）
   ▼
阶段 1  登记（只观测）      ← 出口判据最重要：状态机够不够用
   ▼
阶段 2  回报（settling + outcome，行为仍由旧机制决定）
   ▼
阶段 3  接管最内层（turn.ts 的三个 2 消失）      ← 第一次改行为
   ▼
阶段 4  逐层收敛（4.1 → 4.5，每收一处配额实现数 −1）
   ▼
阶段 5  切换执行模型（判据 1–6 全部达成）
```

**为什么这个顺序不可换**：阶段 0 的"派发意图"是阶段 2 `settling` 的前置（没有它，崩溃后分不清"未派发"与"不确定"）；阶段 1 的状态机如果不完整，阶段 3 的调度器就没有权威状态可依据；阶段 3 不先把最内层的三个 `2` 交出来，阶段 4 的收敛会失去参照点。

### 范围（评审要求写明）

- **首轮范围 = 迁移方案验证**（阶段 0 → 阶段 2 出口，含 §4.4 的两条真实链路）：目标是**证明迁移方法成立**、量出真实成本、暴露契约缺口。
- **生产全量接管（阶段 3 → 5）= 一次独立的执行架构重构**，单独排期——**首轮不承诺工期，也不承诺低成本**。
- **分别验收，不互相推导**：①"状态机可实现"（类型 + 假执行器）；②"生产调用可接入"（阶段 B）；③"所有等待可见"（判据 6）；④"统一配额"（阶段 4）；⑤"恢复可继续"（阶段 5）。**一个 `call()` 门面证明不了其中任何一条。**

## 2. 阶段 0 · 契约草案与职责迁移设计

> **目标**：把第六篇的契约**落成类型草案**（标注 `@unstable`），但**不接线**——纯新增，0 行为改变。
> **为什么先做**：派发意图、`settling`、四类停止语义是整个改造的地基。地基若在阶段 2 才定，会边改行为边改契约，风险叠加。
>
> ⚠️ **"草案"≠"冻结"（评审修正）**：本阶段产出的是**可以改**的契约草案——**冻结推迟到阶段 B（真实调用链验证）之后**。而"不冻结"必须配两条纪律：**① 不稳定性标记（`@unstable`）；② 变更留痕（每次改动记一行理由）**——否则"边写边改"会带来返工。

### 2.1 改动面

| 动作 | 位置 | 内容 |
| --- | --- | --- |
| **新增** | `packages/agent-sdk/src/runtime/contracts.ts` | `CallRequest` / `CallResult` / `CallState` / `BlockReason` / `Executor` / `ExecutorKind` / `Outcome`（照抄 [06-contracts.md](./06-contracts.md) §2、§3、§5 与 [05-extension-points.md](./05-extension-points.md) §2） |
| **新增** | `packages/agent-sdk/src/history.ts` | 事件 kind 枚举（当前第 8 行的联合类型）**新增 `call-dispatch-intent`**；仅在类型与 schema 校验层注册，**写入路径不动** |
| **明确** | `contracts.ts` 注释 | 四类"停止"的字段归属：`P` 的 `timeout`（等许可）/ `deadline`（执行时长）/ `cancel()`（请求）/ 执行器回报（确认停止）——见 [06](./06-contracts.md) §6 |
| **不动** | `packages/agent-sdk/src/runtime/createAgentRuntime.ts` | 它现在仍是"组件袋"（`audit` / `mcpGate` / `builtinRegistry`…）。**本阶段只加类型，不改它** |

### 2.2 出口判据

- `npm run typecheck:agent-sdk` 通过
- `npm run check:agent-sdk` 通过（SDK 零宿主依赖护栏）
- `npm test` **与改造前逐条一致**（0 差异——本阶段没有行为，任何测试变化都说明接错了线）
- 契约逐条对照第六篇评审通过（尤其：`CallResult` 四个值只回答"我方两个事实"，不含任何副作用判断）

### 2.3 回退

删除新增文件即可。**本阶段不存在回退风险**，这是它排第一的另一个理由。

## 3. 阶段 1 · 登记（Registration）

> **目标**：每次模型请求 / 工具调用 / 人机交互**在 CallTable 中有一个条目**，执行路径完全不变，Runtime 只观测。
> **这一步的真正产出不是代码，是答案**：*"这套状态机能不能描述现实？"*（第八篇 §5 步 1）

### 3.1 改动面

| 动作 | 位置 | 内容 |
| --- | --- | --- |
| **新增** | `packages/agent-sdk/src/runtime/callTable.ts` | 调用表 + `project(events)` 的最简实现（纯函数，无 IO） |
| **插桩** | `packages/agent-sdk/src/turn.ts` | 在**每个 `await` 外部响应**处登记调用：`preflightModelRequest` / `turnBoundary` / `recoverProviderAttempt` / `recoverOutputLimit` / `safetyGate.evaluate` / `confirmation` / `toolExecution.execute`（对应 [08](./08-mapping-and-acceptance.md) §4 的收缩预测表） |
| **插桩** | `packages/agent-sdk/src/turn.ts` | 在模型请求与工具执行处登记 `capability`（`model` / `tool`）+ `scope`（sessionId / turnId / stepId） |
| **复用** | `electron/runtime/agentSdkDesktopObserver.ts` | 宿主侧观测面已存在，先让它把 CallTable 的状态一起投出去 |
| **保持不动** | `turn.ts:1195-1197` 的三个 `2`、`mapWithConcurrency`(1587)、`ApprovalCandidateSlots`(1641) | **本阶段一行都不改**——登记必须能与旧机制并行观测 |

### 3.2 验收（本阶段的重点）

| # | 判据 | 怎么测 |
| --- | --- | --- |
| 1 | **调用序列 = 事实序列** | 跑一个完整 turn（含多工具、含审批），比对 CallTable 的调用序与 `history.ts` 事件序，逐项一致 |
| 2 | **异常路径也能表达** | 四类场景各跑一次：`P` 超时、用户取消、审批超时、进程杀重启。**任何"状态机里没有对应的状态"都是本阶段的产出**，必须记录并回设计稿 |
| 3 | **判据 3 的雏形**（[01](./01-positioning.md) §5） | `project(events)` 的产出与 UI 实际渲染一致（可写成属性测试） |
| 4 | **零行为改变** | `npm test` + `npm run test:electron` 与改造前一致 |

> **D4 在这里最硬**：判据 2 若发现表达不了的状态（很可能出现——比如"审批候选槽等待"与"审批槽等待"这两个现状概念，在目标状态机里是否都对应 `blocked`？），**必须先改状态机，再进阶段 2**。

### 3.3 回退与截止点

- **回退**：插桩用一个开关（如 `runtime.registerOnly`）包住；关闭即回到今天的行为
- **删除截止点**：无——登记本身是后续四步的地基，**长期保留**（它最终变成 Runtime 的 `call()` 内部实现）

## 4. 阶段 2 · 回报（Outcome Reporting）

> **目标**：执行器回报 `done` / `failed` / `uncertain`，Runtime 拥有权威状态；**行为仍由旧机制决定**。
> **这一步开始真正写"派发意图"**（阶段 0 只登记了 kind）。

### 4.1 改动面

| 动作 | 位置 | 内容 |
| --- | --- | --- |
| **改写** | `electron/tools/builtinExecutors.ts` | 按**执行边界**拆成多个执行器：`local`（`read_file` / `grep` / `write_file`）、`process`（`run_shell` / `run_script` / Skill CLI）、`http`（模型请求等）——见 [09](./09-assembly.md) §6 |
| **合并** | `electron/mcp/mcpToolExecutor.ts` | 作为 `mcp` 执行器（**先不删**它的 `globalSemaphore` / `perServerSemaphores`，阶段 4.3 再收） |
| **新增** | Runtime 侧 | `Outcome` 三值 + `settling` 提交路径；commit 钩子**先接现有的 `packages/agent-sdk/src/confirmationCommit.ts`**（它已是提交状态机的雏形，先复用不重写） |
| **新增** | 写入路径 | 「派发意图」的持久化写入（[02](./02-runtime-core.md) §4）——**它是"未派发 vs 不确定"的分界线** |
| **保持** | `electron/runtime/turnCoordinatorStorage.ts` / `TurnCoordinator` | 继续驱动行为；本阶段只做**对拍** |

### 4.2 验收

| # | 判据 | 怎么测 |
| --- | --- | --- |
| 1 | **两套认知一致** | 逐 turn 比对 Runtime CallTable 状态 vs `TurnCoordinator` 的 8 个 Map，**差异率 0** |
| 2 | **崩溃点注入** | 在"派发意图写入前 / 写入后 / `step/end` 前后"各杀一次进程，验证恢复规则给出预期结算（未派发 ⇒ 可重建；已派发 ⇒ `uncertain`） |
| 3 | **`uncertain` 的频次可接受** | 统计改造前后 `uncertain` 出现次数——按设计它会**变多**（[05](./05-extension-points.md) §2 已提示）。**若多到产品不可接受，是本阶段必须暴露的结论** |
| 4 | **零行为改变** | 工具执行结果、审批流程、UI 呈现与改造前一致 |

### 4.3 回退与截止点

- **回退**：回报路径可停（Runtime 退回"只登记"模式），旧机制未动故行为不变
- **删除截止点**：无（旧机制在阶段 5 才退场）

### 4.4 出口：生产装配验证（评审新增，不可跳过）

阶段 2 结束后**不直接进阶段 3**，而是先用**两条真实调用链**验证"装配、取消、提交"能否接通、以及到底要改多少东西：

| 样本 | 覆盖什么 | **覆盖不了什么** |
| --- | --- | --- |
| **一条模型调用**（如技能路由） | 装配、`deadline`、取消、结果提交 | 授权、资源锁、并行工具 |
| **一条含授权 + 资源约束的工具链** | 派发前授权复核、许可等待、资源互斥、审批队列 | 嵌套 Agent |

**出口证据（缺一不可）**：

1. 实际改动范围（哪些文件、多少行）
2. 保留的旧机制清单
3. **尚未表达为调用的等待点**（判据 6 的缺口清单）
4. 授权与提交的顺序（含"最终授权紧贴派发"是否保住）
5. 回退方式
6. **可以删除的具体重复逻辑**

**用这些证据重新估算整体成本，并允许调整契约——但不提前冻结公共 API。**

> ⚠️ **一条硬约束**：如果适配器**包住整段旧工具链**，其内部的审批、资源等待、限流**依然存在**。此时该阶段**只能**验证"调用登记 / 结果回报 / 生命周期接入"，**不能声称"所有等待可见"或"统一调度"**（判据 6 未达成）。

## 5. 阶段 3 · 接管最内层（第一次改行为）

> **目标**：`turn.ts:1195-1197` 的三个硬编码 `2` **消失**，工具阶段由"配额 + 调度器"驱动。
> **这是设计判据里最干净的一条**（[04](./04-quota-and-guards.md) §2、[01](./01-positioning.md) §5 判据 4）：三个 `2` 还在，说明 SDK 仍在绕过分配者自己做主。

### 5.1 改动面

| 动作 | 位置 | 内容 |
| --- | --- | --- |
| **替换** | `turn.ts:1197` `mapWithConcurrency(toolCalls, maxConcurrentTools ?? 2, …)` | 改为提交 K 个工具调用，由**调度器**推进（[03](./03-scheduler.md) §6） |
| **替换** | `turn.ts:1195` `ApprovalCandidateSlots(2, …)` | 改为配额 `approval:candidate`（容量 2） |
| **替换** | `turn.ts:1196` `new Semaphore(2)` | 改为配额 `approval:slot`（容量 2） |
| **新增** | 装配 | 三个配额名进 `permits` 名单（[09](./09-assembly.md) §4）；`tool:concurrent` 容量 2 |
| **新增** | SDK | 许可对象（`count` + `waiters` + 临界区）+ `P`/`V` + 就绪队列（[03](./03-scheduler.md) §3–§6） |
| **新增** | SDK | 调度器循环（**阻塞在 `ready.take()` 上**，`step` 只等"启动"） |

### 5.2 验收

| # | 判据 | 说明 |
| --- | --- | --- |
| 1 | **判据 6 的第一块**（[01](./01-positioning.md) §5） | 工具链路里"会等待"的环节都是可见调用（策略评估、审批等待不再是 worker 内的隐式阻塞） |
| 2 | **关键行为用例（必写进测试）** | **"2 个工具在等审批时，同轮第 3 个免审批工具仍能立刻执行"**——这正是孤儿 `ToolScheduler` 的 `isWaiting` 当初想解决而没接上的问题 |
| 3 | **并发行为等价** | 常规路径（无审批、有审批、混合）下，工具执行的并发度与顺序与改造前一致 |
| 4 | **调度循环不退化** | 断言调度循环内**不 await 外部响应**（否则退化成"调度器做循环等待"的反模式，[03](./03-scheduler.md) §6） |
| 5 | **两个类各自有了归宿** | `scheduler.ts` 里**命运相反的两个类**必须分别处理：`ToolScheduler`（**真孤儿**——从未接线）→ **删除**；`InvocationRuntime`（**在生产**——`acquireLease` / `release` 在执行链上跑，见 [08](./08-mapping-and-acceptance.md) §1）→ 由新的**租约**机制取代。**不允许出现第二个孤儿，也不允许同一机制两套并存** |

**验收要分两栏**（评审要求——**不要把"改善"混进"等价"**）：

| 类别 | 内容 | 判据 |
| --- | --- | --- |
| **保真项**（不可回归） | 常规路径（无审批 / 有审批 / 混合）的并发度与顺序、审批流程、失败语义 | **决策对拍零差异**（且不双跑副作用） |
| **改善项**（新收益，单独登记） | "2 个等审批时第 3 个免审批工具立刻执行"（**C2**）；链路中"会等待"的环节都成为可见调用（判据 6） | 新用例通过 + 已在 §10「行为变更登记」中登记 |

### 5.3 回退与截止点

- **回退**：保留一个版本的旧路径，用开关切换（D1）
- **删除截止点**：**切换到新路径并稳定一个发布周期后**，删除：`ApprovalCandidateSlots`（及它的测试）、`mapWithConcurrency` 的限流职责、旧路径开关。**未删则视为本阶段未完成**（D3）

## 6. 阶段 4 · 逐层收敛

> **量化目标（[08](./08-mapping-and-acceptance.md) §6）**：配额 / 队列实现数 **≥16 → 1（配额机制）+ 1（调度器）**；唤醒协议 **3 种 → 1 种**；MCP 并发闸 **3 份 → 1 份**。
> **每一子步的验收口径统一：配额实现数减一，且行为等价对拍通过。**

### 4.1 审批配额

| 项 | 内容 |
| --- | --- |
| 改动 | `packages/agent-sdk/src/approval.ts` 的 `ApprovalAdmission` → `approval:*` 具名配额 |
| 验收 | 审批并发行为等价；`approval:candidate` 与 `approval:slot` 的语义差异被显式记录（若二者的区别只是"两个阶段的并发限制"，应能合并为一个名字） |
| 截止点 | 合并后删 `ApprovalAdmission` 及其测试 |

### 4.2 资源锁

| 项 | 内容 |
| --- | --- |
| 改动 | **只迁移生命周期**：何时获取、何时释放、谁负责释放交给 Runtime；`ResourceLockRegistry` 的**冲突判定保留不动**（[04](./04-quota-and-guards.md) §3）。评审纠正：祖先 / `unknown` 屏障属"关系推理"，**配额名字表达不了**，不能用"声明展开"替代 |
| 验收 | **golden 用例对照**：祖先冲突（`/src` vs `/src/a.ts`）、`unknown:*` 全局屏障、兄弟文件可并行——三类用例逐条与现状**完全一致**（因为它们本来就没改） |
| 截止点 | 生命周期切换稳定后，**单独评估**是否替换锁算法（读写式层级锁 / 更保守的串行策略）——**不与执行装配切换叠加** |
| ⚠️ 风险 | 曾计划用"容量 1 配额 + 声明展开"替换它，那会**改变互斥语义**（兄弟文件互斥、祖先失效）——**已否决**，登记在 §10 的 **C4** |

### 4.3 MCP 三份合一

| 项 | 内容 |
| --- | --- |
| 改动 | `electron/mcp/semaphore.ts`、`electron/mcp/mcpToolExecutor.ts` 的 `globalSemaphore` / `perServerSemaphores`、SDK 的 `McpConcurrencyGate` → 一个 `mcp` 执行器 + 配额 `mcp:global`(8) / `mcp:server:*`(4) |
| 验收 | server 级并发与全局并发行为等价；**三处实现删到一处** |
| 截止点 | 立即删（这是纯重复实现，无兼容负担） |

### 4.4 宿主准入 + park 家族清理

## 7. 阶段 5 · 切换执行模型

> **目标**：编排经 `runtime.call()` 提交，Runtime 统一调度。**判据 1–6 全部达成。**

### 7.1 改动面与验收

| 项 | 判据（[01](./01-positioning.md) §5） | 目标 |
| --- | --- | --- |

| 删掉所有 timer 后系统是否仍正确 | 判据 2 | **是**。4 类"猜状态"timer 全部消失（2s checkpoint、5s finishing、30s 进度、120s 流空闲） |

| 业务代码里的配额词汇 | 判据 4 | **0 处** |
| turn loop 体积正比于什么 | 判据 5 | 编排的步骤数（**1643 行 → 百行量级**） |
| 链路中"会等待"的环节都是可见调用 | 判据 6 | 是（含阶段 3 之后新引入的调用） |

### 7.2 恢复与持久化（本阶段最大的收益点）

| 项 | 现状 | 目标 | **验证方式（关键）** |
| --- | --- | --- | --- |
| checkpoint | 正确性机制（失败即状态丢失） | **性能优化** | **关掉 `SnapshotStore` 仍能完整恢复**（这是"降级"成立与否的唯一证明） |

| `recoverTurn` | 三路归属推断（`owned` / `residue.turnId` / `owned.turnId`）+ cancelled/failed 分流 | `project()` + **一条规则** | 崩溃点注入矩阵全绿 |
| 半完成 Step | 无算法 | 按**调用**粒度重入：已提交结果复用 / 未派发重建 / 已派发 `uncertain` | 在 `step/end` 前杀进程的用例 |

> ⚠️ **依赖提醒**：checkpoint 降级的前提是"事实流足以重建一切"，而"派发意图"是阶段 2 才落地的。**若阶段 2 的判据 3（`uncertain` 频次）显示事实仍不完整，本项承诺必须推迟，不得假装兑现**（见 [08](./08-mapping-and-acceptance.md) §6 承诺表）。

### 7.3 回退

阶段 5 的回退成本最高（编排层整体切换）。因此它的做法是**按调用类型分批切换**（先模型请求，再工具执行，最后人机交互），每类切换后跑一次全量对拍。

## 8. 并行线 S · 影子调用收编

> **依赖关系（评审修正）**：**S0（整理上游）不依赖主线**，可以最早开工；但 **S1 需要"可用的 `call()`"**——即阶段 1（登记）与阶段 2（回报）提供的执行、事实与取消链路。此前写的"只需 `call()`、不依赖主线"是错的：**`call()` 可用本身就是主线的产出**。
> **为什么值得优先**：它不占关键路径，收益立即可见；而且它是**检验这个 Runtime 是否好用的第一个真实用例**——连一个影子调用都收编不顺，说明 `call()` 的接口形状有问题，那时改动成本最低。
> ⚠️ **样本代表性**：技能路由是**最特殊**的一条（turn 级调用、无授权、无资源锁）——它能验证装配与取消，**但覆盖不了工具链的复杂度**，不应作为"整体迁移可行"的依据。

| 步 | 内容 | 验收 |
| --- | --- | --- |
| **S0** | **整理上游**（收编的前置，已调研确认）：① 删除 `skill:route` IPC 旧通道（handler + preload + `api.ts` 类型 + 测试 mock）；② 给 `skillManager` 注入提交端口（照 `getDefaultAgentRuntime()` 惯例，同 `mcpToolExecutor` 取 `mcpGate`）；③ 落稿"turn 级调用"语义（[06](./06-contracts.md) §2） | 渲染端不再有任何路径可绕过会话准入发起路由；`skillManager` 能提交调用 |
| **S1** | `routeSkills` 改为经 `runtime.call()` 提交（`capability: 'skill-route'`，`scope: { sessionId, turnId }`——**turn 级调用，无 `stepId`**；`deadline` = 原 15s） | 行为等价，但**变得可观测、可限流、可取消**，且**不再绕过 LLM 配额与事实流**（计入 provider usage） |
| **S2** | 删自建件：死参数 `timeoutMs`（`callRoutingLlm` 里那个）、`AbortController`、`inFlightBySession` + `prev?.abort()`；`createAnthropicClient` 改走 `ModelProviderRegistry` | 三项能力分别由 `deadline`、`cancel()` / `signal`、会话准入提供；**"覆盖"语义随之消失**（其唯一触发源是 S0 已删的 IPC 入口） |
| **S3** | 全仓扫描**其它**影子调用（判据：**宿主侧带 `await` 且直接构造外部客户端**） | 输出清单；每个都按 S1/S2 处理或注明"为什么不收编" |

### ⚠️ S2 最容易做错的一处

现状那个 15 秒超时覆盖**整个外部调用**（含 LLM 往返），而 **`P` 的 `timeout` 只覆盖"等待容量"**（[06](./06-contracts.md) §6 的"四种停止"）。**直接用 `P.timeout` 替代 15s 超时会静默改变行为**——正确的映射是：

| 现状的超时 | 正确的目标表达 |
| --- | --- |
| `P(names, { timeout })` | 等**许可**的上限（新增，不是替代） |
| 15s（整个外部调用） | `CallRequest.deadline`（执行时长上限） |

这是在 [08](./08-mapping-and-acceptance.md) §2 末被点名的具体回归风险，**S2 必须逐项确认语义后再删**。
