# 一、定位与目标

> 本篇说明：现状是什么、为什么补丁无法收敛、目标模型是什么、Runtime 的职责边界在哪、如何判定设计达成。

---

## 1. 现状：一对一执行模型

现状是**一会话一条执行流**：一个会话对应一个 async 调用栈，栈内串行地 `await` 模型请求、工具执行、审批等待。调度完全交由 JS 运行时的事件循环。

三个直接表现：

**（1）执行进度藏在调用栈里**

进度不是数据，而是"代码执行到哪一行"。因此只能旁路记录、事后推断：

- 宿主 `TurnCoordinator`（400+ 行）用 **8 个状态 Map** 与 **3 处定时器**跟踪进度：`checkpointTimers`、`checkpointRetries`、`checkpointInFlight`、`checkpointFailed`、`committedVersions`、`finishing`、`recovered`、`executions`；2s checkpoint 轮询、100ms 重试退避、5s 取消收尾窗口（`finishingWindowMs`）。
- `callAdmissionGate.ts` 里 `queued: this.waiters.length + this.resumeWaiters.length` 手工重算 **9 次**。
- 恢复逻辑必须同时理解两套身份空间（`turnId` vs `requestId`）并为迁移前数据保留兼容回退（`electron/turnCoordinatorStorage.ts` 的 `recoverTurn`）。

**（2）并发限制内联在业务代码里**

`packages/agent-sdk/src/turn.ts`：

```ts
const candidateSlots = new ApprovalCandidateSlots(2, Math.max(toolCalls.length, 1))
const approvalSlots = new Semaphore(2)
const settledTools = await mapWithConcurrency(toolCalls, input.maxConcurrentTools ?? 2, async (tool) => {
  await candidateSlots.acquire(...)    // 等审批候选槽
  await approvalSlots.acquire(...)     // 等审批槽
  await input.confirmation(...)        // 等用户（可能几分钟）
})
```

三个硬编码的 `2`（worker 数、审批候选、审批槽）彼此重叠、纯属巧合地相等，没有任何一个携带"全局份额"语义。

**（3）同一类机制在多层各实现一遍**

"配额 + 队列"至少 **14 处**（SDK 内 9 处、宿主机 5 处），其中 MCP 并发闸有 **3 份**独立实现。每处自带一套唤醒协议、abort 竞态处理、持久化失败重试。**唤醒协议互不相同**：`Semaphore.release()` 是交接式（不减 active）、`ResourceLockRegistry` 是循环扫描、`CallAdmissionGate.wakeNext()` 需要把两个队列合并排序（注释自陈：*"普通请求与恢复请求必须共享一个按到达序排序的候选视图"*）。

**（4）被删除的机制留下多地残骸**

park/resume 在 **5 个地方以 5 种状态存活**：SDK `InvocationRuntime` 已删（2026-09-30）、SDK 契约 `invocation.ts` 仍留 `park(...)` 方法签名、`history.ts` 仍留 `invocation-parked` 事件 kind 与恢复分支、宿主 `CallAdmissionGate` 完整保留 `park`/`resume`/`ResumeWaiter`/`stale-park-handle`（**生产零调用者，仅测试覆盖**）、`docs/develop/interface/host-ports.md` 专设一节说明差异。

## 2. 为什么补丁无法收敛

以上四类症状反复出现在**不同的层**，且成因相同。这不是"实现有 bug"，而是**抽象缺失**：同一类问题在新位置以相同形态重现，说明缺一个统一的归属地。

一个关键事实决定了这个归属地的形状：

> **在异步执行模型里，"并发"不消耗本机执行能力。**
>
> 启动一个调用是廉价的、非阻塞的——发出请求、注册回调、立刻返回。若不限制，Ready 队列会被瞬间抽干（可以一路启动上万个在途调用）。**并发上限在异步模型里天然不存在。**

对比：

| | 一对一（OS 线程） | 异步（现状） |
| --- | --- | --- |
| 并发上限来源 | CPU 核数，**物理硬约束** | **无** |
| 超发的表现 | 立刻性能下降 | 只在外部服务爆炸（429 / 配额打满） |
| "执行槽"的地位 | 必需的本体概念 | **外部引入的策略** |

**因此限额从来不是本机的物理约束，而是替业务保护外部资源的手段。** 这就是它必须做成组件、不能进入 Runtime 本体的根本原因。

## 3. 目标模型：调用分片调度

**Runtime 持有执行状态；"就绪还是阻塞"由许可回答，"上不上、何时上"由调度器回答。**

```text
// 提交一个调用
P(许可) 成功 → 进入【就绪队列】，等调度器选中后执行
        失败 → 阻塞（进入 permit.waiters），交出执行权
        预算耗尽 → 立即失败

// 归还许可（调用结算时）
V(许可)  → count += 1；如有等待者 wake_one → 它进入【就绪队列】

// 调度器：一个阻塞在就绪队列上的循环
for (;;):
  call = await ready.take()    // 无内容则挂起（零消耗）
  start(call)                  // 正式启动这个 Call（非阻塞）
```

与现状的三个根本差异：

| 维度 | 现状 | 目标 |
| --- | --- | --- |
| 执行状态 | 藏在 async 栈（旁路记录） | Runtime 持有的显式数据 |
| 并发约束 | 分散在 14 处、内联在业务代码 | 具名配额 + `P`/`V`（机制统一） |
| 等待 | 各队列各自维护唤醒协议 | 每个许可自带 `count` + `waiters`，`V` 定向唤醒 |

**注意"槽位"不是本体的要件。** 许可只是"通行的名额"，机制保证的仅是"同名持有者数 ≤ 容量"——资源如何分配、谁与谁互斥，是业务**如何声明**的事。

### 发起与调度的分离

| | 谁负责 |
| --- | --- |
| **发起** | **去中心化**：任何执行体都可以在自己的执行逻辑里主动发起调用，结果返回给它自己 |
| **调度** | **中心化**：无论谁发起，所有调用一律由 Runtime 统一调度 |

执行体包括：模型执行体（发起模型请求）、工具执行体（发起子进程 / 远程调用）、**安全策略模块（发起"问 Agent / 问人"的调用）**、（未来）SubAgent（发起子任务调用）。

两个直接结论：

1. **新增一类"会等待的操作"不需要新增机制**——它只是又一个调用。
2. **"安全审核"不需要特例**：它由安全策略模块按自身逻辑决定是否发起（宽松策略可直接放行、零等待）。因此它是一次**可选的**调用，不是流程上固定的一个阶段。相应地，一个 Step 的调用数是 `1 + K + M`（`M ∈ [0, K]` 为实际发生的审核次数），**不固定**。

## 4. Runtime 的职责与边界

### 做什么

- **持有执行状态**（唯一权威），推进 **Call 状态机**
- **管理等待与唤醒**：每个配额自带 `waiters`，`V` 时定向唤醒；调度器从就绪队列取出执行
- **追加事实**（经端口持久化），并从事实投影状态
- **提供扩展点**：执行器、状态钩子、时钟、排序、持久化端口
- **异常处置**：调用级失败结算、Runtime 级错误的兜底

### 不做什么

| 不做 | 原因 |
| --- | --- |
| 不认识 Turn / Step / 审批 / 压缩 | 这些是**语义分组**，是标签，不是 Runtime 的概念 |
| 不认识边界类型（HTTP / IPC / stdio） | 边界是**执行器的实现细节** |
| 不做业务决策（要不要重试、要不要降级） | 决策属编排层；Runtime 只执行被提交的调用 |
| 不把队列当语义权威 | 队列是缓存，可随时从状态重建 |
| 不定义"槽位" | 配额就是具名的可等待对象，Runtime 不理解它保护什么 |

### 界限：业务不感知调度，但能观测原因

| | 业务**不感知** | 业务**能观测** |
| --- | --- | --- |
| 调度机制 | 就绪队列、配额名、唤醒时机、优先级策略 | — |
| 当前状态 | — | 某个调用在什么状态（`inspect`） |
| 卡住的原因 | — | 它在等什么（`explain(callId)`） |

这条界限的接口表达是 `explain(callId)`（[06-contracts.md](./06-contracts.md) §5）：**业务拿不到"队列长度""排队位次""被谁唤醒"，但能回答"我的调用为什么还没跑"。**

**为什么这样划**：把机制封起来（业务不感知）是为了让配额与调度能统一演进；把原因暴露出来（能观测）是因为产品必须能回答"为什么我的任务没执行"——而这靠**状态查询**，不靠让业务去理解队列。

## 5. 设计判据

以下六条用于判定设计是否达成。它们都**可测量**，不依赖主观感受。

| # | 判据 | 现状 | 目标 |
| --- | --- | --- | --- |
| 1 | **新增一条约束需要改几处** | 多层多处（额度、校验、唤醒各写一遍） | **1 处**，且不在 Runtime 核心，而在组件/配置 |
| 2 | **是否还有"猜状态"的轮询 timer** | 有：2s checkpoint 轮询、5s 取消收尾、30s 进度超时 | **0 处**。保留的 timer 必须对应**真实的超时 / 外部无进展**语义——如 `model.ts` 的流空闲超时（它识别"Provider 无进展"，**统一状态机消除不了这类故障**） |
| 3 | **`project(snapshot, events)` 是否与实际渲染一致** | 无此投影，一致性靠人工对账 | 是（可写成属性测试） |
| 4 | **业务代码里是否还有配额词汇** | `turn.ts` 中有 `Semaphore` / `acquire` / `limit` / `concurrency` / `disposition` | 0 处 |
| 5 | **turn loop 的体积正比于什么** | 正比于"内联的操作数"（1643 行） | 正比于"编排的步骤数"（预期百行量级） |
| 6 | **链路中"会等待"的环节是否都是可见调用** | 否：策略评估、审批等待、资源等待内联在工具调用的 worker 内 | 是：链路只做本机处理，所有等待都以调用形态提交给 Runtime |

**判据 6 是"执行粒度"的守门人**：只要有环节在链路里隐式等待，分片就变粗了，park 那类问题会以新形式回来。

判据 1 是核心指标，它直接测量"约束是状态的函数"还是"控制流上的插桩"。
