# 七、异常与恢复

> 本篇定义三层异常（调用级 / Runtime 级 / 跨边界）的处置，以及**重入与恢复**——这是本次设计收益最集中的地方。
> 核心结论：**恢复不需要推断，只需要"投影 + 一条规则"。**

---

## 1. 异常的分类

| 层 | 内容 | 归属 |
| --- | --- | --- |
| **调用级** | 执行器失败、超时、取消、结果不确定 | 契约（第六篇）+ 本篇 §2 |
| **保护性** | 预算耗尽、轮次超限 | 预算（[04](./04-quota-and-guards.md) §8） |
| **Runtime 级** | 事件处理抛错、事实追加失败、关闭 | 本篇 §4 |
| **跨边界** | 嵌套 Runtime 崩溃、取消传播、进程重启 | 本篇 §5 |

---

## 2. 调用级异常

### 结算规则：由"是否已派发"唯一决定

| 情形 | 已派发 | 结算 |
| --- | --- | --- |
| 预算耗尽 / `P` 超时 | 否 | `failed`（零副作用，可安全重做） |
| 未启动即被取消 | 否 | `cancelled` |
| 执行器回报 `done` | 是 | `done` |
| 执行器回报 `failed` | 是 | `failed` |
| 执行器回报 `uncertain` | 是 | **`uncertain`** |
| 执行器抛错，无法判定是否已派出 | 是 | **`uncertain`**（保守） |
| 超时 | 否 | `failed('timeout')` |
| 超时 | 是 | **`uncertain`**（保守） |
| 提交失败进入 `reconciling` | 是 | **`uncertain`** |

**"是否已派发"是唯一的判据**，而它不需要额外记录——**调用处于 `running` 就等于已派发**（[05-extension-points.md](./05-extension-points.md) §2）。

**注意表里没有任何"副作用"判断**：`uncertain` 出现的地方一律是"我方不知道对面做没做"，**与工具类型无关**。所有"已派发 + 结果未知"的情况一律保守处理。

### `uncertain` 的语义与保守性

`uncertain` 的含义是**"我的请求发出去了，但我不知道对面做没做"**——它不是"我判断它可能有副作用"（后者是需要语义理解的判断，不在这里做）。

它**不可自动重做**，因为：

- 若重做，可能重复效果（重复发消息、重复写文件）
- 若视为失败，会遗漏真实已发生的效果

**这个矛盾在技术上无解**——没有可靠的事实来源能回答"对面做没做"，因此 `uncertain` 必须作为显式状态上抛。它是唯一需要人参与的终态。

**"要不要重做"**的决策与依据都在上层（见本节末），Runtime 不做表态。

## 3. 持久化与恢复

### 3.1 持久化什么、不持久化什么

判据：**持久化"不可重建"的，其余都是缓存。**

| 类别 | 内容 | 持久化？ |
| --- | --- | --- |
| **事实**（真相） | 用户输入、模型响应、工具结果、审批决议、**派发边界越过** | **必须** |
| **状态**（权威，但可投影） | 调用表、Turn / Step 归属、许可声明、**租约占用**（`session:<id>` 当前归哪个 Turn） | 否（从事实投影） |
| **缓存** | 就绪队列、许可的 `waiters`、`count` 占用 | **否**（可重建） |

**队列与计数不持久化**——这解释了一个看似矛盾的点：`count` 在运行时是权威整数（[03](./03-scheduler.md) §3），但它**不必持久化**，因为它可以从"事实 + 声明"重建。

**由此消掉一类复杂度**：现状把 `queued`、`activeInteractive`、`laneActive` 等**计入持久化状态**（`saveAdmissionState`），于是"释放时持久化失败"会让计数永久偏高，不得不加 `onceRelease` 幂等守卫与指数退避重试——**这些在目标设计里全部不存在**。

### 3.2 checkpoint（快照）的地位：从正确性机制降级为性能优化

| | 现状 | 目标 |
| --- | --- | --- |
| 快照内容 | 消息状态（`Message`） | 投影快照（`RuntimeSnapshot` + `eventCursor`） |
| 失败的影响 | **状态丢失**（正确性问题） | 只是多重放一些事件（**性能问题**） |
| 需要的保护 | 3 次重试、100ms 退避、`checkpointFailed` 集合、`retryCheckpoint()` | **不需要** |
| 时机 | 2s 轮询 + 10 种事件白名单 | **任意**——只要快照带 `eventCursor` |

**这是本次设计最大的单点简化**：把一个问题从正确性降级为性能。

**为什么时机可以任意**：快照记录了"它对应到事件流的哪个位置"（`eventCursor`）。恢复时"快照 + 该游标之后的事件"总能拼出完整状态。所以时机不再重要，**2s 轮询与事件白名单可以一并删掉**。

**自然的快照点是 `step/end`**——那里事实已提交、状态一致（见下文「重入点」）。

### 3.3 恢复流程

```text
进程重启 / Runtime 重建
  │
  ├─ 1. snapshot = SnapshotStore.load()           ← 可能不存在（首次启动）
  │
  ├─ 2. facts = FactLog.read(since: snapshot?.eventCursor ?? 0)
  │
  ├─ 3. state = project(snapshot, facts)          ← 纯函数：快照作起点 + 增量重放
  │
  ├─ 4. 对每个非终态调用应用恢复规则（下表）
  │
  ├─ 5. 重建缓存：就绪队列为空；各许可的 count / waiters 由"声明 − 持有者"推导
  │
  ├─ 6. phase := draining | closed                ← 由产品策略决定
  │
  └─ 7. 编排层从最后的 Step 边界重建控制流
```

### 3.4 恢复规则

对 `state` 中每个非终态调用 `c`：

| `c` 的状态 | 规则 | 为什么安全 |
| --- | --- | --- |
| 未派发（`blocked` 或 `ready`） | 可取消，或重新入队 | **零副作用（确定事实）** |
| 已派发 | **`uncertain`** | 对面做没做无法确定 |

**只有两个分支**，分界线是"是否已派发"这一**确定事实**。

**这就是全部规则。** 对比现状的 `recoverTurn`：它需要读宿主 persisted turn 表、读 SDK history、为"新版用 turnId / 旧版用 requestId"维护两套身份空间、判断 `owned` / `residue.turnId` / `owned.turnId` 三路归属、再按 `cancelled` / `failed` 分流——**那全是在推断"它当时在哪"，因为状态没有被记为数据。**

**但"一条规则"要跑得起来，恢复协议必须补齐下面这些**（评审指出的缺口——只有"投影 + 一条规则"是不够的）：

| 需要什么 | 为什么 | 目标形态 |
| --- | --- | --- |
| **稳定调用身份** | 重入时要能区分"复用旧结果"与"提交一个新调用" | 由编排层生成、**幂等**的 `callId`（现状的 `requestIdempotencyKey` 可作参考） |
| **可重建的输入** | 只重放控制流，无法重建"当时到底提交了什么" | `intent` 的可序列化引用（或摘要 + 原文引用） |
| **能力 / 映射的版本** | 配置变了，重建出的配额声明可能与当时不同 | 记录"当时用的能力元数据与映射版本" |
| **派发意图** | 它是"未派发 vs 不确定"的分界线 | 见 [02](./02-runtime-core.md) §4 |
| **Turn / Step 完成标记** | 判断"半完成 Step 的边界在哪"（§3.5） | `step/end` 完成标记 |
| **租约的占用** | Turn 级所有权跨多个调用，不能靠"调用状态"重建 | 见 [04](./04-quota-and-guards.md) §2 的第三类配额 |

⚠️ **半完成 Step 还需要"稳定匹配规则"**：仅靠重走控制流，**无法可靠区分"这个调用是上次那个（该复用结果）"还是"一个新的调用"**——这正是**稳定调用身份必须持久化**的原因。

### 3.5 重入点：Step 边界

[README](./README.md) 共识 3：**Step 边界是跨进程的重入点。**

| 边界 | 事实 | 事务性 |
| --- | --- | --- |
| `step/start` | 本轮模型请求开始 | — |
| `step/end` | 本轮模型响应 + 全部工具结果**已提交** | **完成标记**（不是原子事务） |

**`step/end` 是"完成标记"，不是"跨全部外部调用的原子事务"。** 一个 Step 内部有多个调用（模型请求 + K 个工具），它们**各自提交**——所以崩溃可能落在"模型响应已提交、部分工具已结算"之间。

**这就是"半完成 Step"**，它需要一条明确的中途重入算法：

| 该 Step 内的调用状态 | 恢复时的处置 |
| --- | --- |
| **已提交结果**（有终态事实） | **复用**，不重放 |
| **未派发**（无"派发意图"记录） | **重建**（重新提交） |
| **已派发、无结果** | 标为 **`uncertain`** |

**编排层怎么接收这些事实**：它不是"从头重跑这个 Step"，而是**重放控制流**——遇到已提交的调用就复用结果，遇到 `uncertain` 就交给产品策略。

**所以重入的粒度是"调用"而不是"Step"**：`step/end` 只是"这一轮结束了"的标记，用来告诉恢复逻辑"不必再期待这个 Step 的后续调用"。

### 3.6 产品决策 vs 技术推断

这是本次设计一个重要的职责分离：

| 判定 | 归属 | 依据 |
| --- | --- | --- |
| 我的请求发出去了吗 | **技术（确定）** | 事实里记着（`running`） |
| 我拿到确定回应了吗 | **技术（确定）** | 事实里记着 |
| **要不要重做** | **上层 / 产品策略** | 幂等键、自有工具元数据，或**问模型 / 问人**（见 [05-extension-points.md](./05-extension-points.md) §2 要点 3） |
| **不确定的如何呈现给用户** | **产品策略** | 同上 |

技术层不"猜"，只提供两个**确定性事实**。这也让"崩溃后是否自动继续"从"实现细节的副作用"变成"一个可以被明确讨论和配置的产品行为"。

**如果上层也没有可靠依据**，那它唯一安全的做法就是不自动重做、上抛给人——这正是 `uncertain` 必须存在的原因。

## 4. Runtime 级异常

| 异常 | 处置 | 依据 |
| --- | --- | --- |
| 事件处理中抛错 | **Runtime 不崩**：该调用结算 `failed`，继续处理后续事件 | 单个调用的失败不得中断调度 |
| 事实追加失败 | 提交状态机 → `rolled_back` / `reconciling` | [02-runtime-core.md](./02-runtime-core.md) §6 |
| 快照写入失败 | **仅性能影响**（重放更多事实） | 快照是性能优化，不是真相 |
| 就绪队列 / `waiters` 被污染 | **从 CallTable 重建** | 缓存地位（[02-runtime-core.md](./02-runtime-core.md) §1 四层纪律） |
| `count` 异常 | 从"声明 − 持有者"重算 | 可重建（[02-runtime-core.md](./02-runtime-core.md) 不变量 I3） |
| 关闭 | `drain()` → `close()` | 收敛条件是状态查询 |

**"缓存可重建"是 Runtime 级容错的根基**：就绪队列、`waiters`、`count` 占用全都可从"事实 + 声明"重建，因此它们损坏不是致命问题。这直接来自四层纪律（真相 / 权威 / 缓存 / 可重建）。

**预算的持久化**：预算是否跨重启累计，取决于它的作用域（装配决策，见 [04-quota-and-guards.md](./04-quota-and-guards.md) §7）。一次执行内的预算（轮次、token）随执行终结而失效；全局预算（如每日成本）则需要持久化。

## 5. 跨 Runtime 边界

嵌套是常态：审核 Agent 有自己的 Runtime、Turn、Step、调用。

### （1）取消向内传播

```text
外层 cancel(scope)
  → 外层调用的执行器（它持有内层 Runtime 的引用）
  → 内层：innerRuntime.cancel(innerTurnId, reason)
  → 内层执行自己的取消流程（drain 该 Turn 的非终态调用）
```

**取消是请求，不是强制**（[06-contracts.md](./06-contracts.md) §6）。内层已派发的调用无权被断言"已停止"，因此内层仍走正常结算路径。

### （2）事实各自独立，只在边界交汇

| | 外层 | 内层 |
| --- | --- | --- |
| 事实流 | 记录"调用 #42 的结果是 X" | 记录自己的 Turn / Step / 调用全过程 |
| 恢复 | 按 §3 规则处理 | **独立**按 §3 规则处理 |
| 关联 | 外层 `callId` ↔ 内层 `turnId` | 同左 |

**内层事实流是独立的、自洽的。** 外层恢复时不需要理解内层细节——这保证了嵌套不会让恢复复杂度相乘。

### （3）递归风险与深度预算

```text
主 Agent 调工具 → 触发审核 Agent → 审核 Agent 调工具 → 又触发安全策略 → ?
```

这需要一个**深度 / 次数预算**（如 `agent:depth`）。它是业务配置的预算（[04-quota-and-guards.md](./04-quota-and-guards.md) §8），不是 Runtime 内置。

**注意**：这个问题在现状架构里无处安放——没有任何一层能看到"嵌套深度"。它是"统一配额表"带来的直接收益。

### （4）内层崩溃

内层 Runtime 崩溃时，外层看到的是"调用的结果未知"，因此**一律按 `uncertain` 结算**——外层无法知道内层做到了哪一步（这正是"我不知道对面做没做"的嵌套形态）：

| 外层的选择 | 依据 |
| --- | --- |
| 重做 | 需上层有可靠依据（幂等键 / 自有工具元数据；或问模型） |
| 上抛给人 | **无可靠依据时的安全默认** |

## 6. 死锁与饥饿

| | 手段 | 归属 | 详见 |
| --- | --- | --- | --- |
| **死锁预防** | 配额隔离（如审核独立配额）、固定获取顺序 | **业务策略** | [04](./04-quota-and-guards.md) §9 |
| **死锁检测** | 等待图环检测 | **Runtime 机制** | 本篇下文 |
| **饥饿** | 唤醒策略（先等先得 / 优先级） | **策略**（队列排序键） | [03-scheduler.md](./03-scheduler.md) §5 |

### 死锁检测

等待图由"许可 → 持有者 → 等待者"构成：

```text
调用 A ──等待──▶ workspace:/a.ts ──持有者──▶ 调用 B
调用 B ──等待──▶ process:shell   ──持有者──▶ 调用 A     → 环
```

检测条件：**没有就绪者、没有待唤醒的 `waiters`、而仍有许可被持有**——此时若还存在等待中的调用，等待即构成环。

**判定时机是"每次 `V` 之后仍无进展"，不需要周期性扫描**（见 [03-scheduler.md](./03-scheduler.md) §9 的被动化纪律）。

处置选择（属策略）：

| 处置 | 说明 |
| --- | --- |
| 选牺牲者 | 按优先级 / 已等待时长选一个 `deny`，打破环 |
| 告警上抛 | 不自动处置，落审计 + 上抛 |

**这是现状架构做不到的能力**——等待者分散在 14 处方队列里，没有任何一处能看到完整持有图。
