# 四、配额与保护

> 与 [03-scheduler.md](./03-scheduler.md) 的分工：**03 讲机制**（一个可等待对象 + `P`/`V` + 调度器），**本篇讲配额的分类、命名、作用域、保护与死锁**。
>
> 术语：**配额**（quota）是统称，含两类——**许可**（permit，可获取可归还）与**预算**（budget，单向消耗）。
>
> **本篇是"第一原则"（机制与策略分离）最集中的体现**：配额是 Runtime 提供给业务的机制，而配额的一切具体安排都是业务策略。

---

## 1. 准入就是一次 P

**没有独立的"判定链"**——申请许可本身就是准入。

在 [03](./03-scheduler.md) §4 的 `P` 里，"能不能执行"这个问题的答案就是 `count > 0`（可能是一个名字，也可能是一组名字的合成条件）。

### 三类失败行为

| 失败原因 | 行为 | 为什么 |
| --- | --- | --- |
| **许可不足**（capacity 类） | **挂起**：进入该许可的 `waiters`，等 `V` 唤醒 | 额度会归还，等得到 |
| **预算耗尽**（budget 类） | **立即失败**，不挂起 | 额度只减不增，等不到 |
| **超时到期**（`P` 的 `timeout`） | **立即失败** | 等待是有代价的，业务可以设定上限 |

**"挂起 vs 立即失败"的判据是"这个条件会不会变好"**：会（有人归还）→ 等；不会（单向消耗）→ 立刻拒绝。

### 为什么"依赖检查"不在机制里

调用 A 依赖调用 B 的结果——这**由控制流表达**：

```ts
const b = await runtime.call(B)   // A 在这行之前根本不会被提交
const a = await runtime.call(A)
```

**A 的提交本身就是 B 完成的结果。** 机制若再检查一遍"依赖是否满足"，就是在理解一个已被控制流说清的关系——**越界**。

> **判据**：当机制需要理解"两个对象之间的关系"时，它就越界了。机制只该知道"一个名字和它自己的额度"。

## 2. 配额的形态：许可 / 预算 / 租约

```ts
type QuotaName = string          // 具名，如 'llm:global'、'process:shell'、'session:<id>'
type QuotaSpec =
  | { kind: 'capacity', capacity: number }                              // 许可：可获取可归还
  | { kind: 'budget',   limit: number, consumeOn: 'start' | 'settle' }  // 预算：单向消耗
```

| | **许可**（capacity） | **预算**（budget） |
| --- | --- | --- |
| 语义 | 同时占用的上限 | 累计消耗的上限 |
| 行为 | `P` → `V`，**可循环** | `consume`，**单向**，不归还 |
| 消耗/获取点 | 调用启动前 `P`，结算时 `V` | `start`（提交即消耗）或 `settle`（终结时按实耗） |
| 耗尽后 | 挂起 → 等 `V` 唤醒 | **立即失败** |
| 典型例子 | LLM 并发、工具并发、审批位 | 重试次数、模型轮次、token（**注**：会话所有权属**租约**、嵌套深度是**路径属性**——均不在此表内，见下） |

**两者的机制完全相同**（具名 + 额度 + 原子操作 + 可等待），只是"是否归还"不同。这正是把现状中散落的"限额、上限"统一起来的地方。

### 第三类：租约（lease）

除许可与预算之外，还有一类约束**不能用"计数"表达**：**"这个资源当前归谁"**。

```ts
type QuotaSpec =
  | { kind: 'permit', capacity: number }                                // 许可：可获取可归还
  | { kind: 'budget', limit: number, consumeOn: 'start' | 'settle' }    // 预算：单向消耗
  | { kind: 'lease',  ownerRequired: true }                             // 租约：容量恒为 1 + 归属校验
```

| | 许可 | 预算 | **租约** |
| --- | --- | --- | --- |
| 生命周期 | 一次调用 | 一次调用 / 整个执行 | **跨多个调用**（Turn 受理 → 整轮收尾） |
| 释放者 | 持有它的那次调用结算时 | 无需释放 | **必须是所有者**（非所有者释放 = 拒绝） |
| 冲突语义 | 无余量 → 挂起 | 已耗尽 → 立即失败 | **"已被他人占有"与"自己不匹配"是两种不同结果** |
| 典型例子 | LLM 并发、审批位 | token、轮次 | **`session:<id>`：会话当前由哪个 Turn 占有** |

**为什么它必须是独立一类**——这是评审发现的实质错误：把 `session:<id>` 写成"容量 1 的许可"会有两个后果：

1. 许可在**每次调用结算时归还** ⇒ 两个 Turn 可以**交替**进入同一会话（"一会话一 Turn"失效）
2. 同一 Turn 的多个工具都去申请这个许可 ⇒ 它们被**相互串行化**

而现状 `InvocationRuntime.acquireLease`（重复获取抛 `invocation already leased`）本来就有正确的语义**与归属校验**——把它降级成许可，是**能力倒退**。会话准入、压缩互斥、持久化 Turn 归属各自的生命周期不同，迁移时必须分别标注获取点、释放点与恢复规则。

### 声明是一组，获取是原子的

一个调用可以声明**多个**配额，例如一次工具执行可能声明：

```text
tool:concurrent              （工具并发位）
process:shell                （子进程槽）
workspace:/project/src       （工作区写锁）
turn:<turnId>:tokens         （token 预算——**必须带实例 id**）
```

> **命名规则：凡"按实例"的额度，名字里必须含实例 id。**
>
> 反例：`turn:tokens` 会让**所有 Turn 共享同一个预算**——先跑完的 Turn 用光额度，后面的 Turn 一开始就没额度。正确写法是 `turn:<turnId>:tokens`，每个 Turn 一份。

**必须原子获取**（[03](./03-scheduler.md) §8 的 `bWaitAll`）：全部有余量才一起占用；否则挂起在**第一个不足的**那个上。

> **"分层配额"不需要层级数据结构——它靠"声明一组具名配额 + 原子获取"实现。**
>
> 例如 `llm:global` + `lane:desktop` + `turn:<turnId>` 三条同时声明，即表达了"全局 ∩ lane ∩ Turn"的叠加约束。（**注意 `session:<id>` 不在此列**——它是**租约**，见本章第三类。）

### 声明由谁填写：能力元数据

**结论**：知识只有一份归属地——**能力元数据**。三层各写各的：

| 层 | 写什么 | 例子 |
| --- | --- | --- |
| **① 业务编排** | 只写"**我是什么**" | `call({ kind: 'tool', toolName: 'grep', input })` |
| **② 能力元数据** | **声明"我需要什么"** | `grep: { requires: (input) => ['tool:concurrent', 'process:shell'] }` |
| **③ 装配映射器** | 查表 + 叠加通用规则 | `quotasOf(req) = table(req).requires(req.input) ++ ['call:global']` |

**业务编排什么都不写**；② 是唯一的知识归属地；③ 是薄薄的一层（查表 + 通用规则，不承载业务知识）。

**三个必须定下来的细节**：

1. **声明是"函数"不是"列表"**——因为它依赖 `input`：

   ```text
   write_file('/a.txt') → ['workspace:/a.txt']
   write_file('/b.txt') → ['workspace:/b.txt']
   ```

   所以它在**每个调用**上计算（静态部分可缓存，动态部分按输入算）。

2. **未声明 = 保守**，不是"不限流"。没声明必须等同于"未知副作用"（占全局屏障）——否则忘记声明的工具会不受限。**现状已是此语义**（`resourceKeys` 返回 `undefined` ⇒ 未知副作用）。

   **"必填"的精确含义是"必须写出这个函数"**：函数体**允许显式返回 `undefined`**（表态"我不知道，按保守处理"），但**不允许整个字段缺失**。这样"忘了写"在编译 / 注册期就被拦住，而"故意不写"是一次显式决策——**两者在审计上必须可区分**。（若强制"必须给出具体名字"，MCP 工具只能编造假声明——而它正确的保守形态是 server 级，见下文。）

3. **映射器必须是纯函数，且 fail-closed**。它在调用的关键路径上执行（提交后、`P` 之前）：不能有 IO、不能改状态；**抛错则拒绝该调用**（不能"当作无限制"放行）。

**与现状的对应——签名已经对了**：

```ts
// electron/tools/plannedToolRegistry.ts
resourceKeys?: (input: I, context?) => readonly string[] | undefined
```

只需三件事：① 明确返回值是**许可名**（而非现状的 `workspace:` / `unknown:` 前缀格式）；② 复用 `undefined` 的保守语义；③ **从"可选"提为"注册时必填"，但允许显式返回 `undefined`**（见本小节细节 2）——**字段必填、取值可空**。

### MCP 的元数据空白

MCP 协议**不提供**"给机制读的语义元数据"（它只有 `inputSchema` 语法 + `description` 自然语言）。但这不构成空洞，因为**不同机制对元数据的需求强度不同**：

| 机制 | 需要什么 | MCP 无声明时 |
| --- | --- | --- |
| **限流** | 只要粗粒度归属 | **`mcp:server:<id>`**——协议层天然有，且粒度本就正确（一个 server 一个连接池） |
| **安全** | 语义（危不危险） | **走既有路径**——策略本来就有"不确定 → 问模型 / 问人" |
| **互斥** | 影响范围 | **默认不假设跨 server 冲突**——业务若知道，就配同一个名字 |

**唯一"每次调用都要过"的机制（限流）恰好是需求最弱的那个。** 而"保守"在 MCP 场景下的正确形态是 **server 级**（`mcp:global` + `mcp:server:<id>`，即现状 `McpConcurrencyGate(8,4)` 的形状），**不是全局屏障**——后者会把 MCP 串死。

**归属地唯一 ≠ 来源单一**：注册表是唯一归属地，但填充来源可多样（作者声明 / 宿主配置 / 保守默认 / 语义判定）。MCP 通常落在"保守默认"。

## 3. 许可 ≠ 物理资源

全篇最要紧的一句话：

> **许可只是"通行的名额"，不是资源本身。**
>
> 机制保证的是"**同时最多 N 个持有者**"，而不是"持有者拿到的是它想要的那个资源"——**后者是上层的责任。**

| | 保证 | 不保证 |
| --- | --- | --- |
| OS 信号量 | 并发 ≤ N（计数 + 原子性 + 唤醒） | 你拿到的句柄是不是你要的那个 |
| 本设计 | 同名许可的持有者数 ≤ 容量 | 资源如何分配、谁与谁应当互斥 |

**因此机制不回答**：有哪些配额、容量是多少、哪些操作去获取哪些配额、**谁与谁应当互斥**。

### "互斥"可以用名字表达——**但只限"精确同名"**

互斥就是"两个操作获取**同一个**容量为 1 的许可"。业务侧的映射由业务自己决定（**这是策略，不是机制规定**）：

```text
若业务认为"写同一目录要互斥"：
  写 /src/a.ts   → 获取 [workspace:/src, workspace:/src/a.ts]
  写 /src/b.ts   → 获取 [workspace:/src, workspace:/src/b.ts]   ← 撞上同一个名字 ⇒ 互斥
  写 /src2/b.ts  → 获取 [workspace:/src2, workspace:/src2/b.ts] ← 无重叠 ⇒ 可并行
```

**但这里有一条硬边界，必须写明**：

> **配额是"具名计数"，只能表达"精确同名"的互斥与共享；任何需要"关系推理"（前缀、层级、包含、祖先—后代）的语义，都不能用配额表达。**

原因很直接：**名字匹配是等值判断，不是关系判断**。上例中的"写同目录要互斥"是**业务选择的权衡**——它付的代价正是"**兄弟文件也互斥**"（`/src/a.ts` 与 `/src/b.ts` 都取 `/src`）。若业务想保留"兄弟可并行"，就只能取精确路径——那又失去了"目录与文件互斥"。

**现状 `resourceConflict`（`packages/agent-sdk/src/resourceLock.ts`）做的正是这种关系推理**：

| 现状规则 | 用名字能否表达 |
| --- | --- |
| `a === b` 冲突 | ✅ 能（取同一个名字） |
| `workspace:` 下**祖先 / 后代冲突** | ❌ **不能**（后代集合是无限的，声明展开做不到） |
| `unknown:*` **与一切冲突**（全局屏障） | ❌ **不能**（所有调用都取它会全部串行；只有 unknown 取它则挡不住别人） |

**因此：资源互斥在迁移中保留现有的冲突判定**——先只把**生命周期**（何时获取、何时释放、谁负责释放）交给 Runtime，**不重写锁算法**（见 [10-implementation-plan.md](./10-implementation-plan.md) 阶段 4.2）。

同理，**把 MCP 的未知影响范围从"全局 `unknown` 屏障"降为 server 级，是一次行为变更，不是等价迁移**——需要登记该变更并给出验收方式。

## 4. `count` 是权威

`count` 是被临界区保护的整数，与"持有者集合"必须始终一致（[03](./03-scheduler.md) 不变量 L1）——**靠临界区保证，不靠"每次遍历数一遍"**。

它与 [02-runtime-core.md](./02-runtime-core.md) 的不变量 I3 相呼应：I3 说的"占用可由调用集合导出"是**投影与重建**的视角（重启后可从事实重建 `count`）；运行时它就是权威整数。

**配额占用不进事实流**（可重建），因此配额状态损坏不是致命问题——与就绪队列、等待队列同级。

## 5. 与各模块的关系

| 模块 | 与配额的关系 |
| --- | --- |
| **CallTable** | 权威：记录每个调用声明了哪些配额、是否已派发 |
| **许可对象** | `count` + `waiters`，被临界区保护（[03](./03-scheduler.md) §3） |
| **调度器** | 不接触配额——它只面对"就绪的 Turn" |
| **执行器** | **不接触配额**——只负责执行与回报 |
| **Hooks** | 只观测（可观测配额变化，不参与准入） |
| **时钟** | 仅用于 `P` 的 `timeout` 与定时唤醒 |
| **FactLog** | **不记配额占用**（可重建）；只记"派发边界越过" |
| **装配** | 提供配额清单（名字、容量）与"哪个调用获取哪些配额"的映射 |

**注意：配额只在两个时刻被碰**——`P`（调用启动前）与 `V`（结算时），且两者都在临界区内完成。**没有第三个接触点。**

## 6. 配额表的实物形态

它不是一张可枚举的清单，而是"**命名规则 + 动态占用表**"：

```ts
// ① 命名规则（装配提供，静态）：名字模式 → 额度
rules = [
  { pattern: 'call:global',   capacity: 100 },
  { pattern: 'llm:global',    capacity: 8   },
  { pattern: 'llm:audit',     capacity: 2   },   // 与 llm:global 异名 ⇒ 隔离
  { pattern: 'process:shell', capacity: 4   },
  { pattern: 'lane:*',        capacity: 8   },
  { pattern: 'session:*',     lease: true   },   // ← 按会话动态出现（**租约**，不是许可）
  { pattern: 'turn:*',        capacity: 4   },
  { pattern: 'workspace:*',   capacity: 1   },   // ← 按路径动态出现
  { pattern: 'turn:tokens',   budget: 200000, consumeOn: 'settle' },
  { pattern: 'turn:rounds',   budget: 30 },
]

// ② 占用表（运行时，动态）：名字 → 剩余 + 等待者
permits = {
  'call:global':        { count: 96, waiters: [] },
  'llm:global':         { count: 6,  waiters: [T7, T9] },
  'session:S1':         { count: 0,  waiters: [T3] },
  'workspace:/src':     { count: 1,  waiters: [] },
  ...
}
```

两个关键点：

- **`capacityOf` 是一个函数**，对没出现过的名字也能给出容量（`session:*` 匹配 `session:S99`）。因此**不存在"创建配额"这个动作**——某个名字被第一次声明时，它自动就有额度。
- **表是扁平的。** "分层"不体现为树，而体现为**一个调用同时声明多个名字**（§2 的"原子获取"）。

### 命名约定（层级靠名字表达）

| 名字模式 | 含义 | 容量语义 |
| --- | --- | --- |
| `call:global` | 进程内全部调用 | 全局并发上限 |
| `llm:global` / `llm:audit` | 模型请求（主流程 / 审核） | **异名 = 隔离** |
| `lane:<lane>` | 驱动源 lane | 每 lane 上限 |
| `session:<id>` | 单个会话 | **租约**（不是许可）——一会话一 Turn，带归属校验 |
| `turn:<id>` | 单个 Turn | 该 Turn 内并发 |
| `step:<id>` | 单轮工具 | 该轮工具并发 |
| `process:shell` | 子进程 | 进程数上限 |
| `workspace:<path>` | 工作区路径 | 1（写锁） |
| `approval:slot` | 审批位 | 同时处理的审批数 |
| `mcp:server:<id>` | 某个 MCP server | server 并发能力 |
| `skill:<name>` | 某个 Skill（若自带 CLI） | 该 Skill 的命令并发 |

### 跨 Runtime 实例：一张表还是多张

嵌套（审核 Agent 有自己的 Runtime）时，表的数量由**装配的作用域**决定（§7）：

```text
进程
 ├─ QuotaRegistry（装配为「进程级」时）
 │    └─ 一张表，被下面所有 Runtime 共享
 │
 ├─ Runtime A（主 Agent）     ─┐
 │                             ├─ 经端口访问同一张表
 └─ Runtime B（审核 Agent）   ─┘
```

### 一个调用在表上留下的痕迹

| 时刻 | 表上的变化 |
| --- | --- |
| 提交 | 无（配额声明由映射器推导，尚未落表） |
| 启动前 `P` | 命中的每个名字 `count -= 1` |
| 运行 | 持有（`count` 反映占用） |
| 结算 `V` | `count += 1` → `wake_one`（如有等待者） |
| 预算（`consumeOn: 'start'`） | 启动前 `used += 1`，**永不减** |
| 预算（`consumeOn: 'settle'`） | 结算时 `used += 实际用量` |

## 7. 配额作用域：一个装配决策

**配额状态存在哪里，不在 Runtime 里写死**——它是一个可注入端口：

```ts
interface QuotaRegistry {
  specOf(name: QuotaName): QuotaSpec | undefined
  permitOf(name: QuotaName): Permit                 // 许可：count + waiters
  tryTake(callId: CallId, names: readonly QuotaName[]): QuotaName | undefined  // 返回第一个不足者
  giveBack(callId: CallId): readonly QuotaName[]    // 归还许可，返回被释放的名字
  consume(name: QuotaName, amount: number): void    // 消耗预算

  // —— 租约（[README](./README.md) 共识 10 的第三类）——
  acquireLease(name: QuotaName, ownerId: string): LeaseAcquire   // 'granted' | 'held-by-other' | 'blocked'
  releaseLease(name: QuotaName, ownerId: string): boolean        // 非所有者 ⇒ 拒绝（false）
  leaseOwnerOf(name: QuotaName): string | undefined
}
```

**租约接口里 `held-by-other` 与 `false` 必须可区分**：前者是"资源被别人占着"（正常冲突），后者是"**你不是所有者**"（越权释放 / 编程错误）。把两者混成一个"失败"，会掩盖真正的 bug。

| 装配方式 | 效果 |
| --- | --- |
| 实例内 | 多个 Runtime 实例各自独立 |
| 进程级 | 同进程多实例共享 |
| 持久化 | 跨重启保持 |

**"隔离"与"共享"不是特殊机制，而是配额命名的结果**：

```text
主流程模型调用声明   llm:global   （容量 8）
审核 Agent 声明      llm:audit    （容量 2）
→ 两个不同的具名配额，天然互不干扰 ＝ 隔离
→ 若要共享，让两者都声明 llm:global 即可
```

**作用域与命名是正交的两件事**：作用域决定"表有几张"，命名决定"谁和谁互相约束"。所以"给审核独立配额"既可以靠异名（同表），也可以靠独立表——**前者更常用，因为它可观测、能统一审计**。

## 8. 保护逻辑 = 预算类

"熔断、上限"这类东西不是正常业务逻辑，而是**护栏**。在统一模型里它们就是预算：

| 保护 | 配额形式 | 耗尽时 |
| --- | --- | --- |
| 模型调用重试上限 | `budget` | 立即失败 `retry-budget-exhausted` |
| 输出上限续写次数 | `budget` | 立即失败 `output-recovery-exhausted` |
| `maxModelTurns` / `maxToolRounds` | `budget` | 立即失败 |
| token 预算 | `budget`（`consumeOn: 'settle'`）；**要"硬上限"则必须支持预留 + 核销**（见下） | 立即失败 |
| 审核嵌套深度 | ⚠️ **不是 `budget`**——深度是**调用路径属性**（`depth = parent.depth + 1`），随 `scope` 继承并在提交时校验 | 立即失败 `audit-depth-exceeded` |
| 审批准入的**队列长度**与**每父任务在途上限** | **独立语义**（现状 `ApprovalAdmission({ concurrency, queueLimit, maxInFlightPerParent })` 三者并存）——**塞不进一个配额名** | 拒绝（`queue-full` / `parent-limit`） |

**两处此前未定义的语义（评审指出）**：

1. **深度不是"单向累计次数"**：累计次数记的是"总共嵌套了几次"，深度记的是"**当前这条链有多深**"——两条并列的审核调用深度都是 1，累计却是 2。所以深度必须**随 `scope` 继承**，不能当成预算。
2. **token 预算要支持"预留 + 核销"**：只在结算时扣减，只能限制**后续**调用，给不出硬上限（一个超大请求就能把额度用穿）。硬上限需要：启动前按预估**预留** → 结算时按实耗**核销**（多退少补）。

**保护逻辑不侵入业务流程**：业务只需处理"被拒绝了 + 一个可展示的原因"，不需要知道背后是哪种配额。

**具体数值是策略**：上限设多少、哪些动作算一次消耗——全部由配置决定，Runtime 不内置。

> **纪律**：统一入口有价值，但**不应让尚未定义完整的 `QuotaSpec` 承担所有保护责任**。语义已经明确的**容量许可**（并发限流）先统一；速率窗口、深度、队列长度、父任务在途上限等护栏**各自定义清楚再接入**——不要为了"统一"先把它们塞进一个含糊的名字里。

### 超时不在这里

**超时不是预算，是 `P` 的一个参数**（对应 `WaitForSingleObject(h, timeout)`）：

```ts
P(names, { bWaitAll, timeout })
```

它属于"获取操作"，不占配额表，也不需要"时间类预算"这个概念。到期返回失败即可。**这减少了一个概念。**

## 9. 死锁：预防属业务，检测属 Runtime

多资源并存时可能出现等待环：

```text
调用 A 持有 workspace:/a.ts，等待 process:shell
调用 B 持有 process:shell，   等待 workspace:/a.ts   → 环
```

**这是真实的、业务已经遇到过的问题。** 现状的业务设计给出了解法：**给安全审核独立的配额**。原因是——如果审核与主流程共享 LLM 配额：

```text
主流程占满 N 个 LLM 位，全部在等审核结果
审核需要 LLM 位（审核 Agent 要调模型）
→ 占着配额的调用在等审核，而审核拿不到配额 ＝ 死锁
```

给审核独立配额，等于给审核通道留一条**永不被主流程占满**的路。这是"资源隔离预防死锁"的经典手法。

**两者的归属必须分清**：

| | 手段 | 归属 |
| --- | --- | --- |
| **预防** | 配额隔离、固定获取顺序 | **业务策略**（配置配额时决定） |
| **检测** | 等待图环检测 | **Runtime 机制**（它能看到完整等待图） |

**Runtime 提供检测能力，不替业务做预防决策。** 检测的价值在于：配置疏漏时能发现，而不是保证不出问题。等待图由"许可 → 持有者 → 等待者"构成，因此环检测是可能的——**这是现状架构做不到的**：等待者分散在 14 处方队列里，没有任何一处能看到完整的持有图。

## 10. 优先级

> 本节与 §9（死锁）是同一主题的两面：**死锁是"谁都不放"，优先级是"谁先拿"**。

### 10.1 落点：许可的 `waiters`（就绪队列是次要的）

| 队列 | 争什么 | 优先级的作用 |
| --- | --- | --- |
| **许可的 `waiters`** | 谁能先拿到配额 | **主要**——真正的争用在这里 |
| 调度器的就绪队列 | 谁先被"执行" | **次要**——"执行"只是启动执行器，很快返回 |

所以优先级机制的主体就是 `wake_one` 的**排序键**：从 `seq` 换成 `(priority, seq)`（[03-scheduler.md](./03-scheduler.md) §5）。

**就绪队列为什么次要**：异步模型下"执行"不消耗稀缺资源——**不存在"当前正在跑的调用"需要被切走**。这是与 OS 最关键的不同：

> **OS 的优先级主要为"抢 CPU"，我们的优先级只为"抢配额"。**

### 10.2 属性从来源推导，不由业务编写

**第一版就是"把现状的映射搬进装配"**——现状已有 **4 处赋值点**，且判定已是纯函数（`judgeAdmission(req, state, policy)` + `applyAdmit` / `applyRelease`，`electron/runtime/callAdmission.ts`）：

| 现状位置 | 来源 | 级别 |
| --- | --- | --- |
| `electron/claudeStreamHandlers.ts:350` | 聊天流 | `interactive` |
| `electron/remote/imRemoteAgent.ts:95` | 远端 IM | `interactive` |
| `electron/outbound/outboundAcceptor.ts:523` | 出站 | `interactive` |
| `electron/butler/butlerInvoker.ts:128` | 管家（自动化） | `background` |

目标把它搬成 `priorityOf(scope)` 的装配映射，**级数与取值不变（两级）**：

```text
用户直接输入 / 聊天流 / IM / outbound → interactive
automation（管家 / 定时 / 事件）        → background
```

> ⚠️ **不引入第三级 `normal`**：现状**没有任何来源**能映射到它；凭空多出一级，会让阶段 3 / 4 的"行为等价对拍"失去基准。
>
> ⚠️ **lane 容量数值也原样平移**（`desktop:100 / wechat:8 / feishu:8 / automation:4`，`queueLimit:100`）——不要照抄本文档早先示例里的 `lane:*: 8`，那是示意、不是决策。**数值是策略，第一版不改。**

与配额名一样，这是装配层的映射。**业务编排只表达"我是谁（哪个 lane / 哪个会话）"，不表达"我该多优先"**——否则它会变成"谁都能插队"（又一次业务感知调度）。

**级数少 ⇒ 不需要 aging**：级数越多，低级别的饥饿压力越大（OS 靠"动态提升"补偿）。两级下暂不引入这个复杂度。

### 10.3 优先级必须与配额隔离配套

单靠优先级不够。反例：后台任务**已经占满**配额，交互式调用此时到来——它再高优先级也只能等。

| 手段 | 解决 |
| --- | --- |
| **优先级** | "同时在等时谁先" |
| **配额隔离** | "后台不该占满"（预留） |

**两者缺一不可。** 现状的 `laneMaxConcurrent` 就是第二件事；在目标形态里它是具名配额（`lane:desktop` 与 `automation:*` 各自独立）——**隔离即防挤死**，优先级只是补充。

### 10.4 优先级反转：在我们的模型里它简化了

OS 的反转需要三个环节：

```text
H 等锁 ← 被 L 持有
L 上不了 CPU ← 被 M 抢占
→ H 饿死
```

**中间那一环在我们这里不存在**（执行不稀缺）。所以反转链缩成：

```text
H 等配额 Q1 ← 被 L 持有
L 卡在"等它需要的 Q2" ← 被别人持有
→ H 饿死（若链条继续延伸……）
```

于是"优先级继承"的内容也随之改变：

| | OS 的继承 | 我们的继承 |
| --- | --- | --- |
| 做什么 | 给持有者 **CPU**（让它尽快跑完、释放锁） | 给持有者**优先级**（让它先拿到它要的下一个配额） |

**但实现继承需要一个反向索引**（`permit.holders`）——而 [03-scheduler.md](./03-scheduler.md) §3 明说"`heldQuotas` 记在调用上，不记在许可上"。**所以继承与现有设计冲突：它是一笔实打实的结构代价。**

### 10.5 反转的两层零成本解法

| 根因 | 解法 | 成本 |
| --- | --- | --- |
| **A. 占着资源等外部** | **顺序**：等外部结果（如审核）时**不占任何配额**（§1 的"准入即 P"，以及 [02-runtime-core.md](./02-runtime-core.md) §2 的编排边界） | **零**——它就是既有原则 |
| **B. 被不需要它的人占满** | **隔离**：审核独立配额（§9）、lane 配额（§10.3） | **零**——配置一行 |
| （兜底，必须有） | **有界等待**：`P` 的 `timeout`（§1、[03-scheduler.md](./03-scheduler.md) §8） | **零**——已有 |

**只要坚持 A，OS 意义上的反转就不会发生**——因为"等审核的调用"什么都没占，别人释放后它就能拿到。

**现状恰恰违反了 A**：`mapWithConcurrency(toolCalls, 2)` 在**外层**——工具调用**先占了执行槽**，然后才走 `safetyGate.evaluate`（可能等审批）。**这就是"占着资源等外部"，正是反转的温床。**

### 10.6 取舍

| 项 | 第一版 | 理由 |
| --- | --- | --- |
| 属性 + `waiters` 分级 + 选择算法 | **做**——**两级、平移现状** | 成本为零（排序键）；级数与取值不变，避免对拍失去基准 |
| 配额隔离（lane / 审核） | **做**——**数值原样平移** | 配置一行 |
| 有界等待（`timeout`） | **做** | 已有 |
| **抢占** | **不做** | 执行不稀缺；靠"让执行保持短"替代（§10.1） |
| **优先级继承** | **不做**（留待必要时） | 需反向索引；而反转的两个根因已被 A / B 覆盖 |
| 动态提升 / aging | **不做** | 级数少 ⇒ 饥饿压力小 |

**"留待必要时"的判据**：出现"**既无法隔离、又必须共享同一配额**"的真实场景，且实测到低优先级的持有者长时间卡住——**那时才为继承引入反向索引**。它会是一个有依据的决定，而不是预防性设计。

### 10.7 本节的机制 / 策略边界

| 机制 | 策略 |
| --- | --- |
| `waiters` 的排序键支持 `(priority, seq)` | 有几级、各级是什么 |
| `wake_one` 按排序键选 | 哪些来源映射到哪一级 |
| 具名配额（隔离能力） | 谁与谁隔离 |
| `P` 的 `timeout` | 超时设多久 |

## 11. 机制 / 策略边界

| 机制（Runtime 实现） | 策略（配置决定） |
| --- | --- |
| 可等待对象的结构（`count` + `waiters` + 临界区） | 有哪些配额、容量各是多少 |
| `P`/`V` 语义（含 `bWaitAll`、`timeout`） | 哪些操作获取哪些配额 |
| 三类配额（许可 / 预算 / **租约**）的语义差异 | 预算的消耗点（`consumeOn`）与数值、租约的归属规则 |
| `QuotaRegistry` 端口 | 作用域（实例内 / 进程级 / 持久化） |
| 等待图与环检测能力 | 是否启用、如何处置 |

**两条自查**：

1. 若某项设计需要 Runtime "知道"配额的**业务含义**（这是给审核用的、那个是给压缩用的），它就越界了——正确的做法是把它降级为**一个名字加一行配置**。
2. 若某项设计需要 Runtime 理解"**两个资源之间的关系**"（前缀包含、祖先—后代、全局屏障），它也越界了——**而且机制做不到**：配额是"具名计数"，只能表达**精确同名**的互斥与共享；**关系推理必须留在拥有该知识的组件里**（如现状 `resourceConflict`，见 §3 与 [10](./10-implementation-plan.md) 阶段 4.2）。
