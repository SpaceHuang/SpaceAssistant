# Agent Runtime 目标设计

> **状态**：设计稿（未实施）｜**编制**：2026-10
> **定位**：本目录描述 Agent Runtime（Core）的**目标形态**——把执行模型从"一会话一线程"的一对一模型，改为"调用分片调度"模型。
> **与既有文档的关系**：`docs/develop/interface/*.md` 描述**现状接口**；本目录描述**目标设计**。两者逐项差异见《[八、与现状的映射与验收](./08-mapping-and-acceptance.md)》。
> **范围**：01–09 只设计 Runtime 的形状与契约，**不含排期**；迁移路径骨架见第八篇 §5，**可执行的阶段计划见第十篇**。

## 1. 核心命题

> **把"调用的执行"从控制流变成数据。**

现状的**调用进度**藏在 async 调用栈里——不可枚举、不可序列化、不可观测，因此只能旁路记录（checkpoint）、事后推断（recover）、用 timer 猜（轮询）。目标形态把它取出来，变成 Runtime 持有的显式状态。

**但要区分两件事**（这是本设计最容易被误读的地方）：

| | 是否成为数据 |
| --- | --- |
| **调用的状态**（是否派发、结果、终态、持有哪些配额） | **是**——Runtime 显式持有 |
| **编排的控制流**（Turn 的协程走到哪一行） | **否**——它仍在 JS `async` 栈里，**不可序列化** |

所以跨进程恢复**不是"重放调用状态"**，而是"**从已定义的重入点重建控制流**"（见 [七、异常与恢复](./07-failure-and-recovery.md) §3.5）。

> **"执行进度全部成为数据"是过度承诺。** 准确的表述是：**调用进度是数据；编排进度是可重建的控制流。**

一句话概括目标：

> **Runtime 持有执行状态；调度器负责"就绪队列 → 选择 → 执行"；一切"限制"都是具名配额，由 `P`/`V` 生效。**

### 第一原则：机制与策略分离

> **Runtime 提供机制，业务提供策略。Runtime 给业务提供保护其所关注资源的手段，但不替业务做决策。**

这条原则统摄全篇，也是判断设计是否走偏的标准：

| Runtime 提供**机制** | 业务提供**策略** |
| --- | --- |
| 具名配额的概念（许可 / 预算 / **租约**） | 有哪些配额、容量多少、**谁与谁共享、谁与谁隔离** |
| 具名配额 + `P`/`V`（含 `bWaitAll` / `timeout`） | 有哪些配额、容量多少、哪些操作获取哪些 |
| 每个配额自带 `waiters` + `V` 内 `wake_one` | 谁与谁共享一个配额（即唤醒范围） |
| **Call 状态机**与事实纪律 | 一次任务如何组织成 Turn / Step |
| 与边界无关的调用原语 | 实际使用哪些边界（HTTP / IPC / stdio / Agent） |
| 等待图（可见性） | 死锁的**预防**策略（如配额隔离） |

**推论**：任何"Runtime 替业务做决定"的设计都是走偏的信号，包括但不限于——Runtime 内置某类配额的共享范围、Runtime 认识"审核""压缩"这类业务概念、Runtime 规定重试上限的具体数值。

**配额的作用域是这条原则的典型应用**：配额状态存在哪里（实例内 / 进程级 / 持久化）由装配决定，不在 Runtime 里写死；**隔离与共享不是特殊机制，而是配额命名的结果**——同名即共享，异名即隔离。

## 2. 概念对齐

| 概念 | 定义 | 编号规则 |
| --- | --- | --- |
| **Turn** | 一次完整的任务执行。`turn/start` 开启，`turn/end` 结束。可包含零次或多次模型调用 | **跨进程延续**，会话恢复后从上次编号继续递增 |
| **Step** | Turn 内部的一步，指**一次模型请求**以及这次请求产生的所有工具调用。由 `step/start` / `step/end` 包住 | 每个 Turn 内**从 1 重新计数** |
| **调用**（Call） | 单次对模型的请求、单次工具调用，或单次人机交互 | 属于某个 Step |

**Runtime 的调度单位是"调用"。** Turn / Step 是**语义分组**，其状态由调用状态派生。

### 粒度关系

一个 Step 至少包含一次模型请求，加上该轮每个工具的处理。而**每个工具产生的调用数不是固定的**：

```text
[调用#1] 模型请求
[调用#2] 安全审核 A ─┐  ← 可能不存在：策略可直接放行
[调用#3] 工具执行 A  │  ← 有审核时，两者串行依赖
[调用#4] 安全审核 B  ├─ K 个工具并行
[调用#5] 工具执行 B  │
[调用#6] 工具执行 C ─┘     ← C 未触发审核
```

即 **Step 的调用数 = 1 + K + M**，其中 K 为该轮工具数、**M ∈ [0, K] 为实际发生的外部审核次数**。

**是否发起审核，由安全策略模块按其自身执行逻辑决定**（策略宽松时可直接放行，零等待）。因此调用数是**执行逻辑分支的结果，不是结构必然**——不应把它写成 Runtime 的约束。

### "调用"的统一性

调用的本质是 **向某个边界发起请求 → 等响应 → 提交结果**。边界类型是**执行器的实现细节**，Runtime 不知道：

| 边界 | 通道 | 对面 |
| --- | --- | --- |
| 远程服务 | HTTP / WS | LLM、MCP server |
| 本地子进程 | stdio / 进程退出 | grep、shell、OCR |
| 另一个进程 | IPC | 渲染进程（弹卡片、等用户） |
| 本地服务 | socket | embedding、本地模型 |
| 另一个 Agent | 同进程 Runtime 实例 / 独立进程 | 安全审核 Agent（**现已在用**）、SubAgent |

**"等用户点交互卡片"是调用**：从主进程看，它和调用一个工具本质相同——请求另一个进程，等一段时间，拿回一个结果。

## 3. 前置共识

以下十四条是各篇设计的前提，来自设计讨论中对现状的逐项核对。

**分层**

1. **Runtime 的调度单位是 Call**；Turn / Step 是语义分组。**状态机的主体是 Call**——同一 Turn 可以有多个 Call 同时处于不同状态（并行工具链的正常形态），**而"一个 Turn 一个执行流状态"表达不了它**（见 [02](./02-runtime-core.md) §2 与 [03](./03-scheduler.md) §10 的 L6/L7）。
2. **一个 Step 的调用数不固定**（= 1 + K + M，见上节）；一个 Turn 由若干 Step 组成，编号规则见上表。
3. **Step 边界是跨进程的"重入点"**。Turn 编号跨进程延续，意味着现场无法跨进程携带，只能从 Step 边界重建。

**调用**

4. **等待必须以 Runtime 可见的调用形态出现**，不能是执行器内部的隐式阻塞。上下文压缩、请求投影、大文件解析都会等待外部响应，因此都是调用（不是某调用的内部阶段）。
5. **安全审核是由执行体主动发起的调用**。安全策略模块有自己的执行逻辑：策略宽松时它直接放行（零等待），需要外部判断时它主动发起一次"问 Agent / 问人"的调用，结果返回给它自己。

   更一般地——**发起是去中心化的**（模型、工具、安全策略模块、SubAgent 都可发起），**调度是中心化的**（一律由 Runtime 统一调度）。因此"安全审核"对 Runtime 就是普通调用，不需要任何特例。
6. **每个模型请求 = 一个新 Step**，含截断续写。
7. **一切"重新发起"是同一个模式**：

   ```text
   新 Step 的输入 = 任务意图 + 全部已知事实（失败原因 / 执行情况 / 已发生副作用）+ 新期待
   ```

   续写、模型重试、工具出错重试、崩溃恢复、用户追加，都是它的不同触发源。**正常逻辑里不存在"重试"这个机制。**
8. **"重做还是继续"取决于"是否已派发"，不是"有无副作用"**：未派发 → 可安全重做；已派发且结果未知 → 一律 `uncertain`。

   **"副作用是否已发生"无法判定**——没有可靠的事实来源（外部工具协议不要求声明副作用、同一工具不同参数性质不同、参数语义无固定算法）。因此 Runtime 不做这个判断；确需判断时，由**决策方（编排层）**发起**一个调用**去问模型 / 问人——这与安全判断是**正交**的两件事，不属于安全策略模块的职责。这也是"结果不确定"必须是一等状态的原因。
9. **调用的结果需要提交**（落为事实），提交可能失败，因此存在"提交状态机"。它是**所有调用的通用机制**，不是审批专有。

**配额与保护**

10. **配额表统一承载三类约束**——**许可**、**预算**、**租约**：

    | | 许可（permit） | 预算（budget） | **租约（lease）** |
    | --- | --- | --- | --- |
    | 语义 | 同时占用的上限 | 累计消耗的上限 | **独占所有权**：某资源当前由谁占有 |
    | 行为 | `P` → `V`，**可循环，无所有者** | `consume`，**单向消耗** | **获取 → 释放，且带归属校验**（非所有者不能释放） |
    | 生命周期 | 一次调用 | 一次调用 / 整个执行 | **长于单个调用**（跨多个调用） |
    | 冲突 / 耗尽后 | 挂起（等 `V` 唤醒） | 立即失败 | **拒绝或阻塞**——"已被他人占有"与"自己不匹配"是两种不同结果 |
    | 例子 | LLM 并发、工具并发、审批位 | 重试次数、轮次、token | **会话当前由哪个 Turn 占有**、执行租约 |

    **为什么必须把"租约"独立出来**：`session:<id>` **不能**用"容量 1 的许可"表达——许可在**每次调用结算时就归还**，于是两个 Turn 可以交替进入同一会话；而"会话由谁占有"的生命周期是 **Turn 受理 → 整轮收尾**，并且需要**归属校验**（现状 `InvocationRuntime.acquireLease` 抛 `invocation already leased` 就是这一语义）。把它降级成容量 1 的许可，是**能力倒退**。

11. **保护逻辑（熔断、上限）是预算类配额**，不属于正常逻辑。业务只需知道"被拒绝了"，不需知道背后是哪种配额。**超时不是配额，是 `P` 的 `timeout` 参数。**

**Runtime**

12. **Runtime 主体** = **Call 状态机** + 事实流 + 状态投影；**调度器** = 就绪队列 + 选择 + 启动；**配额** = 具名的可等待对象（许可 / 预算 / **租约**）——准入就是一次 `P`。**主体是 Call，不是"执行流"**（理由见 [02](./02-runtime-core.md) §2）。
13. **队列是缓存，状态是权威，事件流是真相。** 队列/索引可随时从状态重建，不被信任为语义来源。
14. **事实流是"构造下一次请求输入"的来源**（不只是持久化与审计）——因此事实必须完整，遗漏会导致语义误判（例如把"已执行"当成"未执行"）。

## 5. 术语约定

本目录中以下词汇有严格含义，与现状代码中的同名概念可能不同（映射见第八篇）：

- **调用**：一次物理交互（模型请求 / 工具调用 / 人机交互）；**调度的推进单位**，不是"函数调用"。
- **执行流**：跑一个 Turn 的**协程**（`async` 函数）。**它不是状态机的主体**——主体是 Call（见 [02](./02-runtime-core.md) §2）；协程只是编排的实现手段，而它的状态就是它正等待的那个 Call 的状态。
- **影子调用**（**反例**）：带等待、却**绕过框架**的代码——自己实现超时 / 取消 / 并发去重，通常还直接构造外部客户端。它不占配额、不进事实流、**恢复时无从得知**。**判据**：宿主侧带 `await` 且直接构造外部客户端的代码。**任何"等外部"都必须以调用的形态出现**（实例见 [08](./08-mapping-and-acceptance.md) §1 末）。
- **Runtime / Core**：持有执行状态的整体，即本设计的对象。**不等于"调度器"**。
- **调度器**：Runtime 内部负责"就绪队列 → 选择 → 执行"的模块；是一个**阻塞在就绪队列上的循环**，不扫描等待者。
- **可等待对象**：`条件`（`count` / 长度）+ `waiters` + 原子操作 + 挂起/唤醒。**许可**与**就绪队列**都是它的实例。
- **许可**：配额在运行时的形态——带 `count` 的可等待对象。**配额**是统称（含**许可**、**预算**、**租约**三类）。
- **租约**：带**所有者**的独占占用（容量恒为 1 + 归属校验），生命周期**长于单个调用**——如"会话当前由哪个 Turn 占有"。
- **P / V**：获取 / 归还。**准入就是一次 `P`**——不再有"判定链"。
- **事实**：来自外部世界、不可重建的信息（模型响应、工具结果、审批决议、用户输入）。
- **重入点**：Step 边界，跨进程恢复时控制流重新进入的位置。
