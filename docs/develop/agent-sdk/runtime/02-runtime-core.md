# 二、Runtime 主体

> 本篇定义 Runtime 的组成、**Call 状态机**、不变量、事实流与状态投影。
> **调度器不是本篇的内容**——它是 Runtime 的一个内部模块，见 [03-scheduler.md](./03-scheduler.md)。

---

## 1. 组成

```text
┌──────────────────────────── Agent Runtime（Core） ────────────────────────────┐
│                                                                               │
│   核心状态（本篇）                    事实层（本篇）                            │
│   ┌────────────────────┐             ┌──────────────────────────────────┐    │
│   │  CallTable 调用表   │◀──投影──────│  事件流（经端口持久化）           │    │
│   │  Phase    运行阶段   │             │  project(events) → RuntimeState  │    │
│   └─────────┬──────────┘             └──────────────────────────────────┘    │
│             │                                                                 │
│   调度器（第三篇）                     配额（第四篇）                            │
│   ┌─────────┴──────────┐             ┌──────────────────────────────────┐    │
│   │  就绪队列           │◀──P / V─────│  许可：count + waiters            │    │
│   │  选择 + 执行        │             │  预算：单向消耗                    │    │
│   └────────────────────┘             └──────────────────────────────────┘    │
│                                                                               │
│   扩展点（第五篇）：执行器 · 状态钩子 · 时钟 · 排序 · 持久化端口                │
└───────────────────────────────────────────────────────────────────────────────┘
```

**四层纪律**（贯穿全篇的约束）：

| 层 | 地位 | 可否重建 |
| --- | --- | --- |
| 事件流 | **真相** | 不可（外部世界的信息） |
| CallTable | **权威状态** | 可由事件流投影 |
| 就绪队列 / `waiters` | **缓存** | 可由 CallTable + 声明重建 |
| `count` 占用 | **运行时权威 / 可重建** | 可从"事实 + 声明"重建 |

## 2. 状态机主体：Call

```text
created ──P 成功──▶ running ──▶ settling ──▶ terminal
   │                  ▲
   │ P 失败           │ 被调度器选中
   ▼                  │
blocked ──V 唤醒──▶ ready
```

### 状态定义

> **状态机的主体是 Call（调用）。** 每一次模型请求、工具执行、人机交互都是一个独立的 Call，各自持有状态；Turn / Step 只是**语义分组**（[README](./README.md) §2），不持有执行状态。

**为什么要改这一条**（此前写的是"主体是跑 Turn 的协程"）：现状 `turn.ts` 用 `mapWithConcurrency` **并行**处理多个工具——同一 Turn 会同时存在"等审批的工具""运行中的工具""等资源的工具"。**一个"执行流状态"表达不了同一 Turn 的多个并行状态**，而"每个 Call 各自持有状态"天然表达得了。

编排的协程仍然存在（`await runtime.call()` 的写法不变），但它是**实现手段**，不是状态机的主体：协程在等 `call()` 返回时，**它的状态就是那个 Call 的状态**。

| 状态 | 含义 | 判据 |
| --- | --- | --- |
| `created` | 已登记，尚未请求许可 | 内部过渡态，通常不可观测 |
| `blocked` | 许可不足，**本 Call** 挂在某个 `permit.waiters` 上 | 已 `P` 失败并入队（[03](./03-scheduler.md) §4） |
| `ready` | 可执行，位于**调度器的就绪队列** | 已被 `V` 唤醒（[03](./03-scheduler.md) §5） |
| `running` | **已派发**：已启动执行器，等响应 | 越过派发边界 |
| `settling` | **结果已得、正在提交事实**（**非终态**） | 执行器已回报，但事实尚未落库 |
| `terminal` | 终态：`done` / `failed` / `cancelled` / `uncertain` | 不可再转移 |

**队列项与配额持有者一律用 `callId`**——不是 Turn 身份，也不是"执行流"身份（[03](./03-scheduler.md) §10 的 L6 / L7 由此成立）。同一 Turn 可以有多个 Call 同时处于不同状态，这是并行工具链的正常形态。

### 三个刻意的设计选择

**（1）`blocked` 与 `ready` 是两个不同状态，分属两个不同的队列。**

| 状态 | 它在哪 | 谁负责把它推进 |
| --- | --- | --- |
| `blocked` | 某个**许可**的 `waiters` | 许可（`V` 时 `wake_one`）——只做"就绪化" |
| `ready` | 调度器的**就绪队列** | 调度器（选中并正式执行） |

**这个区分是必要的**（[03](./03-scheduler.md) §2）：若把"唤醒"直接做成"执行"，调度权就落到了 `resolve` 的调用顺序上——而 JS 微任务队列是 FIFO、**没有优先级**，"交互优先于后台"便无法表达。

**（2）`running` 包含"在等外部响应"，包括长期等待。**

`running` 的语义是"已派发"，**不是"正在消耗本机 CPU"**。异步执行模型里，已派发的调用在等外部响应（HTTP、子进程、用户点卡片），本机不消耗任何执行能力。

因此：

- 等用户几小时的审批调用也是 `running`——它不占 LLM 配额、不占工具并发，只占它自己声明的配额（如审批位）
- **"等待中的工作不占容量"这条规则，在这里是`配额声明`的自然结果，不需要 park 那类显式让出机制**

**（3）每个 Call 都经就绪队列——没有"首次直达"路径。**

`P` 成功**不做"直接执行"**，而是入就绪队列、等调度器选中。理由：若保留一条"首次成功即直达"的快速路径，**调度器就只调度"曾经阻塞过"的调用**，优先级也只对它们生效——这与"统一调度"直接冲突（[03](./03-scheduler.md) §10 的 L7）。

### 转移规则

| 转移 | 触发 | 由谁驱动 |
| --- | --- | --- |
| `created → ready` | `P` 成功（许可足够） | 提交方（[03](./03-scheduler.md) §4） |
| `created → blocked` | `P` 失败（许可不足） | 提交方 |
| `created → terminal(failed)` | 预算耗尽 / `P` 超时 | 提交方 |
| `blocked → ready` | 许可被归还（`V` → `wake_one`） | **许可对象**（[03](./03-scheduler.md) §5） |
| `ready → running` | 被调度器选中 | **调度器**（[03](./03-scheduler.md) §6） |
| `running → settling` | 执行器回报结果 | 执行器 |
| `settling → terminal` | **事实提交成功** | commit 钩子（[06](./06-contracts.md) §4） |
| `settling → settling` | 提交失败 → **幂等重试**（只重试"写事实"，**不重新派发**） | Runtime |
| `settling → terminal(uncertain)` | 提交最终失败 | Runtime |
| 任意非终态 → `terminal(cancelled)` | 取消 | 控制接口 |

**`settling` 为什么必须是"非终态"**：因为"结果已得、提交未完成"是一个**真实状态**。若把它当终态，提交失败时就只能把 `done` 改成 `uncertain`——那**违反终态不可逆（I2）**。详见 §6。

### 边界：编排不是调用

Runtime 只提供**一个原语**：

```ts
runtime.call(req) → Promise<Result>
```

`call` 的语义是"提交一次交互并等待结果"，**不是"执行一段逻辑"**。由此划出一条边界：

> **Runtime 不运行编排逻辑。编排是 JS 协程，由调用方运行；Runtime 只提供 `call()`。**

协程可以嵌套（JS 原生能力），因此实际的执行结构是：

```text
turn loop（协程）
  ├─ await runtime.call(模型请求)
  └─ 工具调用链路（协程）
       ├─ 本机环节：解析参数、归一化资源键……（同步，零等待）
       ├─ 询问安全策略组件（它有自己的执行逻辑）
       │    └─ await runtime.call(问审核 Agent)      ← 可见调用
       │         └─ 内层：审核 Agent 自己的 Runtime（自己的 Turn / Step / 调用）
       └─ await runtime.call(工具执行)                ← 可见调用
```

**推论：工具调用链路是一段编排，不是一个调用。**

若把它建模为一个调用，它内部"询问策略 → 等 Agent / 等用户"那个环节就会变成**执行器内部的隐式阻塞**——不可观测、不可取消、不可独立限流。这与"等待必须 Runtime 可见"（共识 4）直接冲突。

**唯一的硬要求**：

> 链路里所有"会等待"的环节，都必须以 `runtime.call(...)` 的形态出现。

链路的中间状态不可观测，这是**可接受**的——因为链路本身只做本机短处理（解析、归一化、签发）。**不可接受的只有一种情况：在本机处理里藏一个隐式的等待。**

#### 工具链路的正确顺序（含"最终授权紧贴派发"）

一个工具链路内部有**多个可见调用**与**多个本机环节**，顺序是有讲究的：

```text
① [本机] 解析参数、归一化资源键
② [调用] 策略评估（它内部可能再发起"问审核 Agent / 问用户"的调用）
③ [本机] 等待许可（`P`）——这不是调用，是配额等待
④ [本机] 最终授权复核（recheck）        ← 必须紧贴派发
⑤ [调用] 工具执行（派发）
```

**第 ④ 步不能省**：从"策略评估"到"真正派发"之间隔着**许可等待**（可能很久）。等待期间**授权可能变化、参数状态也可能变化**，所以派发前必须**重新复核一次**。

这是 TOCTOU（check 与 use 之间的窗口），**它消除不了、只能显式化**。现状的 `prepareTool(recheck)` + `safetyGate.authorize` + `matchesRecheckBinding` 正是这一步——**"准备前移为编排"不能把它抹掉**。

**注意 ④ 本身若需要"等外部"，它就该是一次可见调用**，而不该是本机环节（见上方"唯一的硬要求"）。

### 判据：执行器还是编排

"这段逻辑该做成执行器，还是编排？"——**看它是否需要发起并等待新的调用**：

| 逻辑 | 归属 | 判据 |
| --- | --- | --- |
| 模型请求、grep、IPC 问用户、MCP 查询 | **执行器** | 一次派发、一次回报，内部不产生新调用 |
| 安全审核（可能问 Agent、可能问用户） | **编排** | 它会 `await runtime.call(...)` |
| turn loop、工具调用链路 | **编排** | 同上 |

**执行器是"单次派发适配器"**：收到一个已获准派发的调用，执行一次边界操作，回报结果。它**不发起子调用、不重试、不决定后续动作**——一旦它需要这些，那段逻辑就属于编排。

**推论**：所谓"父调用等待子调用"**不需要显式建模**。父是协程，`await` 就是等待，恢复由 Promise resolve 驱动——**父子关系就是"父的协程挂起在某次 `call()` 上"**。

> 注意：安全审核**本身不是调用**，它是编排；它 `await` 的那个"问 Agent / 问用户"才是调用（见 [01-positioning.md](./01-positioning.md) §3「发起与调度的分离」）。

## 3. 不变量

| # | 不变量 | 违反后果 |
| --- | --- | --- |
| **I1** | **派发不可逆**：越过派发边界的调用不可回到未派发状态 | 已发出的副作用被当成未发生 |
| **I2** | **终态不可逆** | 重复结算、事实冲突 |
| **I3** | **占用与持有者一致**：`capacity - count` 等于"持有者数"（`count` 是**剩余**许可），由临界区保证（[03](./03-scheduler.md) 不变量 L1） | 超发或漏计 |
| **I4** | **`blocked` 的 Call 不持有任何许可**（= [03](./03-scheduler.md) 不变量 L2） | 未派发的工作占用外部额度 |
| **I5** | **一个 Call 至多位于就绪队列或某个 `waiters` 之一**（= [03](./03-scheduler.md) 不变量 L6） | 幽灵就绪者、重复执行 |
| **I6** | **事实单调**：事件流只追加，不修改、不删除 | 投影不可重放 |

**I3 的措辞要点**：`count` **不是**"每次遍历调用集合数出来的"（那是 O(n)），而是**被临界区保护的权威整数**。它靠"所有变更都在临界区里完成"保证一致——因此既不需要"同步点"，也不可能"忘记同步"。

> 这与 [07-failure-and-recovery.md](./07-failure-and-recovery.md) §3.1 一致：`count` **不必持久化**（可从"事实 + 声明"重建），但**运行时它是权威的**。

## 4. 事实流

### 什么必须进事件流

判据：**来自外部世界的信息，或"外部世界已经改变"的证据——即不可重建的信息。**

| 事实 | 为什么不可重建 |
| --- | --- |
| 用户输入 | 来自外部 |
| 模型响应（已提交） | 来自外部；重新请求得到的结果不同 |
| 工具结果 | 来自外部；且副作用可能已发生 |
| 审批 / 人机交互决议 | 来自外部 |
| **派发意图**（"我决定要派发这个调用"） | **"未派发 vs 不确定"的分界线**——本地写入，且映射配置可能已变，无法推导 |
| **派发边界的确认**（若执行器能提供） | 用于缩小不确定范围；不可推导 |
| 压缩 / 投影后的内容 | 原文已丢，不可重建 |
| 提交结果（成功 / 失败） | 决定该调用是否已产生事实 |

**为什么要单独记"派发意图"**：执行器从"被调用"到"请求真的出去"之间有窗口——序列化参数、建立连接都可能失败，而**本地写入与外部派发无法组成原子事务**。没有这条记录，崩溃后就无法区分"还没派发"（可安全重做）与"可能已派发"（必须 `uncertain`）。见 [05](./05-extension-points.md) §2 的**边界三态**。

### 什么不能进事件流

| 不进 | 原因 |
| --- | --- |
| 内部状态转移（`ready` / `blocked` / `running` / `settling` → `terminal`） | 可由事实 + 判定函数推导 |
| 队列 / `waiters` / `count` 占用 | 缓存与派生值（可重建） |
| **流式预览（token 增量）** | 高频、可丢弃、可回滚。**只有已提交的响应是事实** |
| 重试决策 | 编排层的判断，可从事实推导 |

**"流式预览不是事实"这条必须显式执行**：模型流每秒产生数十个 chunk，若进事件流会让投影成本爆炸。预览是派生数据，需要时可从事实重算，不需要时可丢弃。

**反例（现状）**：`invocation-parked` 出现在事件 kind 枚举里——内部状态转移被误当作事实。这正是它删不掉、并横跨五处残存的原因。

## 5. 状态投影

```ts
project(snapshot: Snapshot | undefined, events: readonly Fact[]) → RuntimeState
```

**`snapshot` 是可选起点**：没有它就从零重放全部事件；有它则"快照 + `eventCursor` 之后的增量"。

**前提条件**：快照之所以"只是性能优化"，前提是**事件流足以重建一切**。而 §4 的"派发意图"等事实**尚未进入持久协议**——**在补齐之前，checkpoint 还不能算纯优化**（见 [07-failure-and-recovery.md](./07-failure-and-recovery.md) §3.2）。

- **纯函数**：无 IO、无时钟、无随机
- **可重放**：同一事实序列必得同一状态
- **可 diff**：两个状态可比较
- **可单测**：不需要 mock 时序

`RuntimeState` 的构成：

```ts
type RuntimeState = {
  calls: Map<CallId, Call>          // 权威：所有非终态调用 + 近期终态
  phase: 'idle' | 'running' | 'draining' | 'closed'
  // 注意：不含就绪队列、waiters、count
}
```

投影是 Runtime 的四项能力共同的底座：

| 能力 | 如何由投影得到 |
| --- | --- |
| 可观测 | 直接读状态（无需 timer 猜） |
| 恢复 | `project(events)` + 重入规则（见第七篇） |
| 审计 | 事实流本身 |
| **构造下一次请求的输入** | 从状态读"已知事实"（见共识 7、14） |

## 6. 提交状态机

调用的结果需要**提交**为事实，而提交可能失败（数据库错误、进程崩溃）。因此调用在**终态之前**要经过一段提交：

```text
settling（结果已得）
   │
   ├─▶ committed   → terminal（done / failed）
   │
   └─▶ failed      → 重试（幂等）──▶ 最终失败 → terminal(uncertain)
```

### 关键区分：重试"提交" ≠ 重新"派发"

这是最容易搞混的一点：

| 失败发生的位置 | 外部效果 | 可做什么 |
| --- | --- | --- |
| **未派发**时失败 | **确定未发生** | **重新派发**（安全——"零副作用"是**确定事实**） |
| 已派发 + 明确失败 | **可能已发生部分效果** | **Runtime 不表态**——交由上层依幂等协议判断 |
| 已派发 + 结果未知 | **未知** | `uncertain` |
| **已派发 + 结果已知 + 提交失败** | **已发生** | **只能重试"写事实"**——**绝不能重新派发** |

**第二行是评审纠正的一处实质错误**（此前写作"已派发 + 明确失败 ⇒ 未发生 ⇒ 可安全重新派发"）：**"明确失败"不等于"没产生效果"**——脚本写完文件后退出非零、消息已投递但返回错误，都是"明确失败 + 已产生效果"。

⚠️ 更深一层：那行写法**违反了本篇自己确立的原则**（[05](./05-extension-points.md) §2："Runtime 不判断副作用"）——它拿"失败"当作"无副作用"的证据。**能确定的只有"有没有派发"，不是"有没有效果"。**

第四行是**本节的要点**：结果已经拿到了，只是没落库。此时"重做调用"是错的（外部操作可能已经执行过），**能安全重试的只有"幂等提交"这一个动作**。

所以：

- **提交重试**：幂等（同一 `callId`、同一事实），安全
- **重新派发**：仅在"未派发"或"明确失败"时才安全
- **提交最终失败** ⇒ `terminal(uncertain)`——**因为结果丢了，而外部可能已经执行**

### 为什么这要求 `settling` 是非终态

如果把"提交"当作终态**之后**的动作，那么"提交失败"就只能把 `done` **改成** `uncertain`——**那会违反终态不可逆（I2）**。

所以顺序必须是：**结果已得 ⇒ `settling`（非终态）⇒ 提交 ⇒ `terminal`**。

**这是所有调用的通用机制，不是审批专有。** 现状中 `confirmationCommit.ts` 为审批实现了它，而工具结果走的是另一套（`AgentTurnHistoryAppendError` + `kinds` 检查 + `interrupted` 结算）——两者应该统一。

## 7. Runtime 运行阶段

```text
idle ──有新调用──▶ running ──取消 / 关闭──▶ draining ──在途收敛──▶ closed
```

**Turn 的「配置阶段」（受理后、第一个 Step 前）属于 `running`**：它的调用带 `turnId`、无 `stepId`——技能路由就在这个阶段（见 [06-contracts.md](./06-contracts.md) §2「turn 级调用（无 `stepId`）」）。

`draining` 的语义：**不再接受新调用提交，等待所有非终态调用收敛。**

- 收敛条件是**状态查询**（"是否还有非终态调用"），不是时间赌博
- 现状对应物是 `finishing` Map + 5s `finishingWindowMs` + `isFinishingEventAllowed` 白名单——用定时器赌在途工作能在窗口内收敛。显式阶段替代它。
