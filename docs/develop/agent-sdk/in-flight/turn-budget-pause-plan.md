# 回合预算耗尽改为「阶段暂停」方案

> 日期：2026-10-18
> 文档性质：**技术方案（在途草稿，未实施）**
> 基线：`main` `28dd3223`（2026-10-17）
> 上游关联：[`agent-long-task-stability-improvement-plan.md`](../../agent-long-task-stability-improvement-plan.md)。**该文未覆盖本课题**——它只在 §5「后续 L」提到「无人值守跨轮次任务」（属跨轮自动推进，与本课题不同）；本文是对「回合预算耗尽后如何收场」这一缺口的独立补充。

## 一句话

任务跑到工具轮次或模型往返次数上限时，现在会**整个报错结束**；本方案改成「这一班到点收工」——把还没来得及执行的动作逐条标成「没做」、给一段阶段小结、状态记为暂停，用户点「继续」从原处接着干。

## 第 0 层：决策层 【人必读】

### 只有 3 分钟的话

先读 `D-4`（界面怎么显示，**未获批则本方案不排期**）和 `D-5`（要额外记录些什么）。
`D-1`～`D-3` 已在讨论中定稿，列出来只为留档；如果与你的理解不一致，现在推翻成本最低。

### 需要你决定的事项

#### D-1 一个任务最多允许「收工几次」

**背景**：任务跑到上限会暂停，点「继续」就开新的一段，新的一段又有同样的额度。如果不数总共用了几段，这个上限等于取消了——当初加上限就是为了防止模型不停调工具把费用烧光。

**要决定什么**：

- A：按段数计，一个任务最多 5 段（推荐，且为当前共识）
- B：按累计费用或累计字数计（更精确，但用户对数字没直觉，且不同模型价格差几倍）
- C：不设总数（等价于放弃这条保护）

**每个选项的后果**：选 A——用户看到「第 3/5 段」，能预期还剩几次；选 B——更省钱的精度，但用户看不懂「还剩多少」；选 C——长任务可能整夜跑，醒来发现账单。

**可逆性**：可逆，是个取值，改起来只影响提示文案与停止时机。

**依据强度**：没有实测数据——当前线上没有「撞到上限的频率」统计，所以 5 是经验值不是测出来的。

**推荐与默认**：A，5 段。你不改就是 A。

#### D-2 每一段的额度要不要一起调大

**背景**：现在一段的上限是 500 轮工具调用 / 1000 次模型往返。

**要决定什么**：保持不动（推荐），还是调大。

**后果**：保持不动——绝大多数正常任务远到不了 500 轮，能连续撞满 5 段说明任务描述本身有问题、或模型陷入了该被人看一眼的失败模式，那时停下问人比继续烧更对；调大——跑得久一点，但单次失控的代价也一起变大。

**可逆性**：可逆。

**依据强度**：`F-7`（当前取值已核实）。

**推荐与默认**：保持不动。你不改就是保持。

#### D-3 没人看着的定时任务撞到上限怎么办

**背景**：定时任务（按间隔或每天跑一次的那种）没有人在旁边点「继续」。

**要决定什么**：

- A：停在第一段，等下次调度时间再跑一轮（推荐，且为当前共识）
- B：让它自己一路续到 5 段

**后果**：选 A——行为可预期、不会偷偷花钱；代价是同一件事可能每次都只做一半，如果你真有一个「需要连跑几小时」的定时任务，它会永远做不完。选 B——能做完，但它会在没人同意的情况下自己决定再花几段，与 `D-1` 的「不能顺手继续」自相矛盾。

**可逆性**：可逆，但改回 A 时已经花掉的钱回不来。

**依据强度**：`F-5`（定时任务把「成功」当「完成」判定，已核实）。

**推荐与默认**：A。真需要连跑几小时的任务，应等「自动推进」那套机制单独做（属另一课题），不该靠续跑硬凑。

#### D-4 【未获批】界面上怎么呈现「暂停」

**背景**：现在跑到上限，界面显示失败。改完之后会有三种新状态需要出现在界面：这一班结束了（但任务没完）、还能继续、以及「已经用了几段」。这些是用户能看见的东西。

**要决定什么**：是否批准这三处界面呈现，以及由谁定具体样式（按交互设计指南需要先出一张「界面归属卡」，5 行，说明这次改的是哪个界面、改什么、谁负责）。

**每个选项的后果**：不批——本方案的阶段 4 不排期，其余阶段照做（后台行为会变，但用户暂时看不到「继续」入口，等于只有自动化任务受益）；批——用户能一键接着干。

**可逆性**：界面改动可逆，但用户会形成习惯。

**依据强度**：无（尚无界面归属卡）。

**推荐与默认**：**需要你批准，或指定人来出这张卡。** 没有批准时本方案默认**不做界面**，阶段 4 保持不排期——不会出现「先实现、界面待评审」。

#### D-5 额外记哪些东西

**背景**：要支持「第几段」和「已用多少」，系统得多记一些信息。这属于数据格式改动，不能由我替你拍。

**要决定什么**：

- A：只记「这是第几段」（最小改动，只够支撑 `D-1` 的段数）
- B：再记累计工具轮次与累计费用（推荐——用户会在意钱，而费用数据现在已经在记了，只是没有跨段汇总）

**每个选项的后果**：选 A——够用，但用户看到「第 3/5 段」时不知道已经花了多少；选 B——能给出「累计已用 X 轮 / 约 Y 元」，代价是多一个字段和一次汇总。

**可逆性**：不可逆（一旦写入历史就很难重算，旧数据补不回来）。

**依据强度**：`F-6`（费用已在按每次尝试记录，缺的只是跨段汇总）。

**推荐与默认**：B。

### 不需要你决定（Agent 已查证或负责）

- 暂停时那批没执行的动作怎么标记：逐条写「未执行」，理由见 `INV-1`。
- 为什么不能复用系统里已有的「暂停」状态：见 §1.3 排除方案，三条证据已查证。
- 旧历史数据（没有这些新记录的任务）怎么处理：按「真完成」处理，见 `AC-6`。
- 崩溃、断电、重启时各窗口怎么收场：见 §2.4。
- 测试怎么写、验收怎么判定：见 §2.6。

## 第 1 层：概要 【人机共读】

### 1.1 要改什么行为

| 时刻 | 现在 | 改后 |
|---|---|---|
| 工具轮次用满 | 整个任务报错结束 | 本轮剩余动作标「未执行」→ 阶段小结 → 暂停 |
| 模型往返次数用满 | 整个任务报错结束 | 同上 |
| 暂停后用户点继续 | （做不到） | 开新一段，从原处接着干，背景不用重讲 |
| 累计用满 5 段 | （不存在） | 不再给「继续」，改为需要明确确认的入口 |
| 定时任务撞顶 | 记「失败」 | 记「未完成」而非「失败」，等下次调度 |

### 1.2 为什么这件事比看起来便宜

系统里已经有一整套「继续」的能力——防重复点击、记录从哪儿接、恢复哪些上下文、校验配置有没有被改过。**这套东西一行都不用重写**（`F-3`、`F-4`）。

但它挑食：只认三种结束方式——正常结束、失败、被中断。

所以本方案不新造第四种，而是：**用「正常结束」收场，额外加一句备注「这次结束是因为额度用完，不是任务做完」**。这样整套继续能力立刻可用。

这也是本方案改动量被压到「一个可选备注 + 一个判定函数」的原因（阶段 1、2 加起来是 S 级）。

### 1.3 排除方案（选了什么、为什么不要另一个）

| 方案 | 结论 | 理由 |
|---|---|---|
| 复用系统里已有的「暂停」状态 | **排除** | 它本是给「等你点同意、你不在」用的，硬套会得到最差组合：①它强制绑定一个待办事项，而额度用完没有待办；②它给用户的交付是空白；③它偏偏不在「可以继续」的名单里——用它等于既不可继续又什么都不显示（`F-3`、`F-4`） |
| 新造一个独立的结束状态 | **排除** | 会波及 4 处按「结束状态」写死的数据库查询、状态推导函数及其 3 个消费点、界面事件投影；收益只是语义更漂亮，不值得 |
| 直接把上限调大 | **排除** | 不解决「撞了之后怎么收场」，只是把问题推后，且单次失控代价变大（见 `D-2`） |
| 撞顶后自动续跑 | **排除** | 属另一课题（自动推进），需要独立的授权策略；混进来会把「额度边界」和「授权边界」搅成一件 |
| 收尾轮让模型自己写小结 | **列为可选（阶段 5）** | 更好看，但要额外请求一次模型，且不确定所有服务商都接受「这一轮不准用工具」（见 `U-1`） |

### 1.4 主要风险

1. **假成功**（`INV-4`）：定时任务现在只要任务返回「成功」就记「已完成」。暂停如果也算成功，用户会在列表里看到「做完了」，实际只做了一半——比报错更糟。必须一起改。
2. **无限续跑**（`INV-3`）：分段本身会把原来的保护漏掉，必须有跨段累计。
3. **暂停成为绕过核查的后门**（`INV-2`）：暂停不能清除「上次某个动作可能执行了但结果不明」这件事，续跑仍须先进只读核查。

### 1.5 术语对照

见附录 C。正文尽量用业务词。

## 第 2 层：规格 【机｜人工可跳过】

### 2.1 不变量

| ID | 不变量 | 为什么 | 违反时的表现 | 验证 |
|---|---|---|---|---|
| `INV-1` | 暂停终态写入时，本回合提出的每个动作都必须已有明确结算（执行了 / 未执行 / 失败）；不存在悬空提案 | 续跑校验要求账目齐平（`F-3`），漏一条即拒绝 | 用户点「继续」被拒，且提示无意义 | `AC-1`、`AC-2` |
| `INV-2` | 暂停不构成任何副作用的结算证据；存在未解决副作用时，续跑仍须进入只读核查模式 | 暂停是行政动作，不是事实 | 用户以为点「继续」就安全，实际可能重复执行外部动作 | `AC-3` |
| `INV-3` | 跨段累计消耗单调不减；达到总预算后不再为同一任务提供续跑 | 否则分段等于取消原有的费用保护 | 长任务整夜烧钱 | `AC-4` |
| `INV-4` | 凡是把「任务返回成功」当作「任务完成」的地方，都必须能区分暂停 | 否则出现假成功（§1.4） | 列表显示已完成，但没有结果 | `AC-5` |
| `INV-5` | 暂停终态写入失败时沿用既有 fail-closed 处理，不得降级为普通失败或成功 | 不确定的终态不能猜 | 恢复时误判为已完成 | `AC-6` 同族回归 |

### 2.2 状态与所有权

**状态机**（一段的生命周期）：

```
运行中 ──额度耗尽──> 暂停（正常结束 + 备注）
      ──正常产出──> 完成
      ──出错──────> 失败 / 被中断 / 已取消
暂停 ──用户点继续──> 新的一段（运行中）
暂停 ──累计用满────> 不再提供继续
```

**唯一 writer / 唯一恢复者**：

| 事实 | 唯一 writer | 唯一提交点 | 唯一恢复者 |
|---|---|---|---|
| 暂停备注（含段号、额度、累计） | 回合内核终态写入（`turn.ts` `runAgentTurn` 终态分支） | 与 `invocation-completed` **同一次**历史追加 | — |
| 跨段累计 | 宿主创建续跑事务（`agentContinuation.ts` `createOrGetAgentContinuation`） | 与目标上下文提交**同一事务**（沿用现有做法） | 启动对账 `reconcileRunningAgentContinuations` |
| 用户点「继续」 | 界面 IPC → `agentProtocolIpc.startAgentContinuationFromSource` | `claimAgentContinuation` | 同上 |

**不允许的写法**：界面或统计模块自行推断段号；模型生成段号；从提示文案里回读累计值。

### 2.3 契约

#### 2.3.1 暂停备注（`invocation-completed` payload 扩展）

| 字段 | 类型 | 缺省 | 归属 | 说明 |
|---|---|---|---|---|
| `pause` | 可选对象 | 不出现 = 真完成 | 第 2 层 | 旧数据无此字段，行为完全不变 |
| `pause.reasonCode` | 固定大写码 | 必填 | 同上 | 工具轮耗尽 / 模型往返耗尽 / 段时长耗尽 |
| `pause.segmentIndex` | 整数，从 1 起 | 必填 | 同上 | 本任务是第几段 |
| `pause.budget` | `{ maxToolRounds?, maxModelTurns, segmentDeadlineMs? }` | 必填 | 同上 | 本段额度快照（便于日后复现判定） |
| `pause.spent` | `{ toolRounds, modelTurns, elapsedMs, wrapUpTurns? }` | 必填 | 同上 | 本段消耗 |
| `pause.notDispatchedToolCallIds` | 字符串数组 | 必填（可为空） | 同上 | 本段末被标「未执行」的提案 |

#### 2.3.2 跨段累计（`invocation-context-committed` payload 扩展）

| 字段 | 类型 | 说明 |
|---|---|---|
| `budgetLineage` | `{ segmentsCompleted, totalToolRounds, totalModelTurns, totalTokens? }` | 由源调用链累加写入；`totalTokens` 的取舍由 `D-5` 决定 |

#### 2.3.3 返回值与判定

| 名称 | 位置 | 说明 |
|---|---|---|
| `AgentTurnResult.paused?` | SDK 内部结果 | 形态对齐既有的 `parked?` 先例 |
| `AgentInvocationResult.paused?` | 宿主对渲染层的返回 | 与 `parked?` 并列；上层据此判定 |
| `isPausedTerminal(terminal): boolean` | `electron/runtime/terminalOutcome.ts` | **新增旁路判定**；`decodeTerminalOutcome` 的返回值与枚举**不变** |

> 刻意不给「结束状态枚举」加新值：它只有 3 个消费点（`sessionStorage/coordinator.ts`、`hostedTurnHandoff.ts`、`sqliteAgentHistory.ts`），加值会连带改它们，而 `isPausedTerminal` 能让这 3 处零改动（`AC-7`）。

#### 2.3.4 保留的错误类型

`ToolLoopRoundLimitError`、`ModelTurnLimitError` 两个类**保留**，只是不再由「额度耗尽」抛出。它们仍是内部熔断的逃生门（`SHELL_DIALECT_MISMATCH` 路径仍使用 `ToolLoopRoundLimitError`，且 `hostedTurnHandoff.ts` 特意保留其诊断不被覆盖）。

### 2.4 失败与崩溃窗口

| 窗口 | 现象 | 唯一恢复动作 |
|---|---|---|
| W1 暂停备注写入前崩溃 | 无终态 | 沿用既有「终态缺失」路径：标 `commit-uncertain`，要求对账，不猜 |
| W2 备注写入成功、界面未收到 | 用户看不到「继续」 | 重新打开会话时从历史读（既有机制），无需新代码 |
| W3 用户点继续、新段启动前崩溃 | 续跑记录停在「运行中」 | 启动对账置为「被中断」，**不自动重放**（既有语义） |
| W4 累计消耗写入与目标上下文提交之间崩溃 | 两个事实可能不一致 | 二者必须**同一事务**提交（沿用现有写法，不新增事务边界） |
| W5 暂停瞬间存在未结算动作 | `INV-1` 有被破坏的风险 | 终态写入前强制结算扫描；扫描失败则按 `W1` 处理，不写暂停备注 |

### 2.5 并发与顺序

- 暂停只在「本轮全部动作已结算」之后发生，因此与工具并发无关（并发数 `F-8` 不影响本方案）。
- 跨段累计的读改写必须在创建续跑的事务内完成，不允许先读后写。
- 同一任务重复点击继续：沿用既有幂等键语义，不新增去重机制。

### 2.6 验收

| ID | 验收（可执行断言） | 关联不变量 |
|---|---|---|
| `AC-1` | 构造工具轮耗尽场景 → 既有续跑校验**通过**（这是整个方案的成立前提） | `INV-1` |
| `AC-2` | 同场景下历史中不存在未结算提案（逐条断言） | `INV-1` |
| `AC-3` | 造一个「派发后结果不明」的动作，再触发暂停 → 续跑进入只读核查模式，且写操作在派发前被拒 | `INV-2` |
| `AC-4` | 随机操作序列：累计消耗单调不减；达总预算时拒绝开新段 | `INV-3` |
| `AC-5` | 定时任务场景暂停 → 运行记录不得为「已完成」 | `INV-4` |
| `AC-6` | 旧数据（无 `pause` 字段）回归：完成 / 失败 / 中断 / 取消四类判定与改动前一致 | `INV-5` |
| `AC-7` | 结束状态推导的 3 个消费点行为不变（以改动前行为为基准做对拍） | §2.3.3 |
| `AC-8` | 暂停终态写入失败 → 结果为「被中断」，不得为完成或失败 | `INV-5` |

**不变量测试**（按仓库测试纪律，此类改动必须有一条）：随机生成工具序列与随机额度 → 断言「任一暂停终态 ⇒ 不存在悬空提案，且不存在被吞掉的未解决副作用」。

### 2.7 阶段

**阶段 1（S）——内核暂停语义**
输入：本方案 §2.3.1、§2.3.4。输出：额度耗尽不再抛错，改为收尾 + 暂停备注；返回值新增暂停标记。
出口证据：`AC-1`、`AC-2`、`AC-8` 通过。可回退实体：单个提交（新增分支，删除即回到现状）。

**阶段 2（S）——宿主透传与假成功修复**
输入：§2.3.3、§1.4。输出：结束原因能透传到上层；`isPausedTerminal` 落地；定时任务的「成功即完成」判定改为三态。

## 与上游方案的关系

本方案只处理「回合预算耗尽后的收场语义」，不改动上游已完成的阶段 0–3，也不涉及它的其他课题：跨轮自动推进（其 §5「后续 L」）、自动压缩摘要的栏目质量（其 §2.4）、只读核查白名单（其 §4.2）。

其中**自动压缩的摘要质量与本方案有交互**：暂停时写的确定性小结，与自动压缩的摘要应当共用同一套「从执行记录抽事实」的来源，否则用户在暂停与压缩两个时点会看到两套说法。该统一留待摘要质量那一项处理，本方案不重复建设。
