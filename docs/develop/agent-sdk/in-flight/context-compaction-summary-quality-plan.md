# 自动压缩：摘要质量与触发时机方案

> 日期：2026-10-18
> 文档性质：**技术方案（在途草稿，未实施）**
> 基线：`main` `28dd3223`（2026-10-17）
> 上游关联：[`agent-long-task-stability-improvement-plan.md`](../../agent-long-task-stability-improvement-plan.md) §2.4。该文把「固定栏目 checkpoint」记为 Phase 3 完成，但**实际只覆盖手动压缩路径**（`F-1`）。本文同时修两个问题：自动压缩的摘要质量，以及触发时机过晚。
> 读者分层：第 0 层决策 → 第 1 层概要 → 第 2 层规格 → 附录

---

## 一句话

长对话压缩时，模型拿到的「交接单」只有两段各 1200 字的散文，没写哪些操作做完了、哪些结果不明；而且压缩要等到上下文用到 90% 才启动，来不及就整轮报废。本方案让自动压缩与手动压缩走同一个方法，并把触发线提前到 80%（可调）。

---

## 第 0 层：决策层 【人必读】

### 只有 3 分钟的话

方向已定：**自动压缩不再另写一套逻辑，直接调用手动压缩那套方法**；**触发线从 90% 提前到 80%，可调范围 60%–90%**，设置项放在「模型」页 Thinking 强度之后。
两处细节都已定（范围 60%–90%、卡片显示状态与占用比例）。**本方案在决策层已无待定项**，可直接进入实现评审。

### 已经定下来的（不用再讨论）

**1. 自动压缩与手动压缩共用同一个方法。**
不再为自动压缩单独设计摘要逻辑。自动压缩的等待与失败，用聊天消息里的一行状态承载（进行中 / 已压缩 / 失败），与工具调用的显示方式一致。因此**不需要**短超时、**不需要**「失败退回截断版」这类降级设计——失败就如实显示失败；但**用户主动取消不算失败**（见 `INV-9`），卡片收敛为「已取消」。

**2. 触发线提前：默认 80%，用户可调，放在「模型」页 Thinking 强度之后。**
现在这条线写死在 90%，且另有一层保护把任何配置最高钳到 90%（`F-2`）。90% 意味着离爆满只剩一成余量，压缩慢一点或失败就没有退路。

**3. 两件事必须一起做，原因如下（这是本方案的核心判断）。**

- 只在 90% 压缩失败 → 没有余量 → 本次请求发不出去 → 会话死。
- 改在 80% 压缩失败 → 还有两成余量 → 本次请求照常发出 → 压缩卡片显示失败 → 下次再压。

**提前触发把「压缩失败」从致命问题降级成可重试的小问题。** 这就是为什么第 1 条可以做得那么简单。

### 需要你确认的两处细节

#### D-1 阈值可调范围（已定：60%–90%）

**背景**：如果允许用户调到 95%，等于允许把「快爆才压」这个毛病重新配置回来。

**要决定什么**：

- A（**已选定**）：可调范围 60%–90%，默认 80%
- B：上限放宽到 95%
- C：不给用户调，固定 80%

**后果**：A——有调整空间，但调不出「快爆才压」；B——灵活性最大，但用户可能把系统调回今天这个有问题的状态；C——最安全，但不同模型、不同使用方式的人没法按需调。

**可逆性**：可逆（范围可再改）。

**依据强度**：现状 90% 是硬编码且另有 90% 钳制（`F-2`），因此这不是从零设计，是把死值改成可配值。

**已定（2026-10-18）**：A，范围 60%–90%，默认 80%。

#### D-2 压缩卡片上显示什么（已定：A）

**背景**：压缩卡片是用户唯一能看到「系统在压缩」的地方。

**要决定什么**：

- A：状态 + 压缩前后的占用比例（例：已压缩，占用 82% → 41%）（推荐）
- B：只显示状态文字（进行中 / 完成 / 失败）
- C：状态 + 摘要正文预览

**后果**：A——用户知道省了多少，也顺便理解了「为什么会慢」；B——最简，但用户不知道效果；C——信息最多，但把交接单原文摊在聊天流里，噪音大，且摘要属于系统内部上下文。

**可逆性**：可逆（文案与字段可加）。

**依据强度**：现有工具行已有折叠式显示（`F-9`），承载两行信息不增加新组件。

**已定（2026-10-18）**：**A** —— 显示状态 + 压缩前后占用比例（例：已压缩，占用 82% → 41%）。不显示摘要正文。

### 不需要你决定（Agent 已查证或负责）

- 哪些内容必须由系统生成、不能让模型写：见 `INV-1`。
- 压缩失败后本次请求怎么办：有余量就继续，没余量按既有超预算处理（`INV-2`）。
- 会不会「压缩的压缩」无限套娃：摘要请求不进入压缩链路（`INV-4`）。
- 手动压缩会不会被改坏：结构与校验统一，行为对拍（`AC-3`）。

## 第 1 层：概要 【人机共读】

### 1.1 现状：两条压缩路径，两种质量

| | 你点「压缩」 | 自动压缩（每次请求前 / 回合结束） |
|---|---|---|
| 交接单内容 | 七个栏目 + 未解决操作清单 + 最近工具结果 | 用户文本截断 1200 字、助手文本截断 1200 字、一句「如需完整历史请查询」 |
| 是否调模型 | 是（90 秒超时） | **否**（纯字符串拼接） |
| 触发时机 | 你主动点 | 上下文用到 90% 时 |
| 失败表现 | 有界面提示 | 不调模型，所以没有「失败」这回事；但压缩不成功时就直接撞超预算 |

### 1.2 两个改动各自解决什么

| 改动 | 解决 | 不解决 |
|---|---|---|
| 共用同一个摘要方法 | 压缩后忘了「哪些做完了、哪些结果不明」；两条路径格式漂移 | 压缩来不及 |
| 触发线 90% → 80% 可调 | 压缩来不及 / 临近爆满时服务质量下降 | 摘要内容质量 |

**两者叠加才成立**：第二个改动让第一个改动的失败变得不致命。

### 1.3 排除方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 为自动压缩单独写一套摘要逻辑 | **排除** | 两份实现必然漂移，今天的毛病就是漂移造成的 |
| 保留「失败退回截断拼接」的降级 | **排除** | 有了提前触发与压缩卡片，失败不再是致命问题，降级分支只会掩盖真实故障 |
| 设 20 秒短超时 | **排除** | 压缩卡片让等待可见，没必要牺牲摘要质量去换时间 |
| 把状态塞进设置页或独立面板 | **排除** | 它是过程状态，不是配置；与工具调用同区显示，用户不需要学新位置 |
| 只提前触发、不改摘要 | **部分排除** | 能缓解「来不及」，但压缩后仍然不知道做到哪 |
| 顺手放开「有工具调用不压缩」 | **排除在主体外** | 见阶段 4，性质不同（启用一条从未走通的校验路径） |

### 1.4 主要风险

1. **压缩频率上升**：阈值从 90% 提前到 80%，同样长度的对话会多压一两次。缓解：压完占用下降，下一次触发距离拉长；摘要按输入指纹缓存，不重复生成。
2. **摘要调用变多 → 延迟与费用**：缓解同上（缓存）+ 失败不再重试整轮。
3. **事实被模型改写**：模型可能把「结果不明」写成「已完成」。缓解：这两项由系统写入，模型输出里的同名字段丢弃（`INV-1`）。
4. **同一概念被迫复制三份**：触发比例目前在预算对象、决策指纹、判定钳制三处各自写字面量 `0.9`（`F-2`）。根因是生成预算的函数**没有接收该参数的入口**（`F-11`），只能硬编码。本次必须一次消除，只留一个来源；否则「界面显示 80%、实际仍按 90% 判定」会持续复发。
5. **两个「80%」混淆**：触发比例 80% 与「压缩后目标降到 80%」是两个独立参数（`F-4`）。文档与代码注释必须写全称。

## 第 2 层：规格 【机｜人工可跳过】

### 2.1 不变量

| ID | 不变量 | 为什么 | 违反时表现 | 验证 |
|---|---|---|---|---|
| `INV-1` | 未解决操作清单与工具结果只能由系统从执行记录生成；模型输出中的同名字段一律丢弃 | 模型会把文字承诺当成已解决 | 压缩后模型以为某操作已完成，实际没做 | `AC-4` |
| `INV-2` | 只要当前请求仍在预算内，**摘要自身失败**（超时 / 格式非法）不得使回合失败；**父级取消不适用本条**——取消直接按回合取消收场（见 `INV-9`），不进入「继续发送」分支 | 压缩是优化，不是任务前提 | 有 20% 余量却整轮报错；或用户取消后仍被当成「继续发送」 | `AC-2`、`AC-14` |
| `INV-3` | 摘要过程与结果必须在聊天流中可见（进行中 / 成功 / 失败 / 已跳过 / 已取消）；**「跳过」也算结果，必须可见** | 否则用户不知道系统在做什么，或误以为压缩已经发生 | 用户以为卡死；或以为已压缩而实际未压缩 | `AC-9` |
| `INV-4` | 摘要请求自身不进入压缩链路 | 会无限套娃 | 死循环 | `AC-5` |
| `INV-5` | 交接单结构只有一个定义处；手动与自动压缩产出同一结构、走同一校验 | 两份格式必然漂移 | 一处改另一处没改 | `AC-1`、`AC-3` |
| `INV-6` | 交接单不比被压缩内容省空间时不做压缩 | 否则压缩无收益 | 越压越大 | `AC-6` |
| `INV-7` | 触发比例的默认值、下限、上限各自只有一处定义；预算对象、决策指纹、判定钳制、配置校验全部引用同一来源，代码中不得出现第二个字面量 | 两份副本必然不一致，且用户看到的与实际生效的会分叉 | 界面显示 80%、实际仍按 90% 判定 | `AC-8`、`AC-13` |
| `INV-8` | 触发判定与展示口径一致：均以「扣除系统提示与工具定义后的正文预算」为分母 | 口径不一致会让用户看到的百分比与实际触发不符 | 用户按界面理解调参，行为却不是那样 | `AC-8` |
| `INV-9` | 摘要等待受父回合信号约束：父回合取消或超时后，不得继续等待、不得继续提交、不得进入「仍在预算内就继续发送」分支 | 否则用户点了停止，系统仍在后台跑请求、甚至改写上下文 | 取消后仍发出请求、仍提交替换 | `AC-14`、`AC-15` |
| `INV-10` | 摘要返回后必须先复核再提交：父回合未取消、上下文纪元未变、本次执行令牌仍有效；任一不满足即丢弃结果（不提交、不改写、不使回合失败） | 迟到的响应会把旧内容盖到已经变化的上下文上 | 压缩结果覆盖了更新的上下文，或取消后的结果被采用 | `AC-16` |
| `INV-11` | 摘要已开始后，任何**未提交**的结局（收益不足 / 结构性压不动 / 复核失败 / 缓存命中后仍无收益）都必须收敛到五态之一；不得残留「进行中」，也不得显示为「已压缩」或虚构压缩比例 | 否则实现只能二选一：留悬空状态，或谎报成功 | 卡片永久停在「进行中」；或显示「已压缩」但上下文未变 | `AC-20`、`AC-21`、`AC-22` |

### 2.2 状态与所有权

| 事实 | 唯一 writer | 唯一提交点 | 恢复者 |
|---|---|---|---|
| 交接单内容 | 压缩提交路径 | 与上下文替换**同一次**提交（沿用现有事务边界） | 既有提交不确定路径 |
| 未解决操作 / 工具结果 | 系统查询执行记录 | 同一次提交（生成时读取） | 同一次读取可重放 |
| 触发比例 | 配置表（单一键） | 写入配置时 | 读取失败时用默认 80% |
| 压缩卡片 | 压缩执行者（进行中 / 成功 / 失败） | 压缩卡片随消息一起落库 | 以执行记录为准，界面不自行推断 |

**不允许**：界面自己算「该不该压缩」；模型生成未解决操作 ID；两个调用点各自读阈值。

### 2.3 契约

#### 2.3.1 交接单内容结构（唯一结构）

| 字段 | 归属 | 是否可由模型生成 |
|---|---|---|
| 目标 / 已完成 / 决定 / 约束 / 待办 / 阻塞 / 下一步 | 模型 | 是（但「已完成」不得作为工具成功的证据） |
| 未解决操作清单 | 系统 | **否** |
| 最近工具结果（成功 / 已知失败 / 结果不明 / 未执行） | 系统 | **否** |

字段长度上限：每栏 ≤2000 字符（沿用现状）。

#### 2.3.2 兼容

- 旧交接单只有「用户文本 / 助手文本 / 提示句」三字段，读取方按「缺字段」处理，**不迁移、不回填**。
- 判定依据：是否存在七栏目字段。

#### 2.3.3 触发阈值

| 项 | 取值 |
|---|---|
| 默认值 | 80% |
| 可调范围 | 60%–90%（已定，`D-1`） |
| 存储 | 配置表单一键 |
| 缺省 / 损坏 | 回退 80%，不阻断 |
| 判定分母 | 扣除系统提示与工具定义后的正文预算（`INV-8`、`F-8`） |
| 唯一来源 | 默认值 / 下限 / 上限三个常量只在一处定义；预算对象、决策指纹、判定钳制、配置校验全部引用它 |
| 本次必须一并消除的三份副本 | ① 预算对象内的字面量 ② 决策指纹内的字面量 ③ 判定处 `Math.min(..., 0.9)` 的上限钳制（`F-2`）。钳制机制本身可以保留，但上限必须引用同一常量 |
| 根因修复 | 生成预算的函数增加「触发比例」入参（带默认值），使调用方能传入配置值（`F-11`） |

#### 2.3.4 摘要调用约束（共用边界）

**共用什么**：摘要生成函数、七栏目校验、提示词与输出上限——这一层可以直接复用。

**不共用什么**：手动压缩的**提交编排**。它带 busy 检查与独立压缩锁（`F-5`），只适用于「用户主动点击、生命周期独立」的场景。自动压缩发生在已有回合内部，照搬会与回合自身的串行假设打架，可能死锁或让后续回合永久 busy。自动压缩的提交必须走回合内既有的上下文替换提交点。

| 项 | 取值 | 说明 |
|---|---|---|
| 摘要生成 | 与手动压缩同一函数 | 共用 |
| 提交 | 回合内既有上下文替换提交点 | **不复用**手动路径的 busy 检查与独立锁 |
| 超时 | 90 秒 | 与父回合信号联合生效（§2.3.5） |
| 输出上限 / 温度 | 1536 token / 0 | 沿用现状 |
| 失败处理 | 压缩卡片显示失败（取消除外，见 §2.3.5）；本次请求按 `INV-2` 继续 | 无「退回截断」分支 |
| 父回合取消 | 立即停止等待；不提交；**不进入**继续发送分支 | `INV-9` |

#### 2.3.5 信号、取消与迟到提交

**信号组合**：摘要等待的取消来源有两个——父回合信号（用户取消 / 回合超时）与 90 秒摘要超时。任一触发即停止等待；两个来源必须以可区分的方式记录，不得在错误分类上合并。

| 情况 | 错误分类 | 卡片表现 | 写缓存 | 是否进入继续发送分支 |
|---|---|---|---|---|
| 摘要自身超时 | `SUMMARY_TIMEOUT` | 「压缩失败」，可展开原因 | 否 | 是（`INV-2`） |
| 父回合取消 | `SUMMARY_CANCELLED` | 显示「已取消」（**不移除该条**，与 `AC-9`、`AC-14` 对齐） | 否 | **否**（`INV-9`） |
| 父回合超时 | `SUMMARY_CANCELLED`（原因为超时） | 同上 | 否 | **否** |
| 返回时父已取消 | `SUMMARY_LATE_DISCARDED` | 不显示失败 | 否 | 否 |
| 返回时上下文纪元已变 | `SUMMARY_LATE_DISCARDED` | 不显示失败 | 否 | 是（按新上下文重新判断） |

**提交前复核**（`INV-10`）：即使返回时父信号尚未触发，提交前仍须复核三项——父未取消、上下文纪元与发起时一致、本次执行令牌有效。复核失败一律丢弃结果，且**不得**记作压缩失败（用户不该看到一条由自己取消引起的「失败」）。

**摘要已开始后不提交的所有结局**（原有四态无法覆盖的一类，必须显式收敛）：

| 结局 | 分类 | 卡片终态 | 写缓存 | 替换提交 | 是否继续发送 |
|---|---|---|---|---|---|
| 收益不足（交接单 ≥ 被压缩内容） | `SUMMARY_SKIPPED_NO_GAIN` | **已跳过**：显示「未压缩（无收益）」，**不得显示压缩比例** | 是（成功结果仍可复用） | 否 | 是 |
| 结构性压不动（既有不可压缩判定） | `SUMMARY_SKIPPED_UNCOMPRESSIBLE` | **已跳过**：显示「未压缩（无法获得收益）」 | 否 | 否 | 是（若当前请求已超预算，走 W3） |
| 提交前复核失败（纪元 / 令牌失效） | `SUMMARY_LATE_DISCARDED` | 已跳过：不显示失败、不显示比例 | 否 | 否 | 是（按新上下文重新判断） |
| 缓存命中 + 重装系统字段后无收益 | `SUMMARY_SKIPPED_NO_GAIN` | **已跳过**，同上 | 不新增 | 否 | 是 |

**为什么这是一类独立结局**：摘要生成成功 ≠ 压缩发生了。收益不足、结构性压不动、复核失败都属于「已开始、未提交」——既不是成功（未提交）、不是失败（没有出错）、也不是取消（用户没干预）。不给显式终态，实现就只能留下「进行中」，或者谎报「已压缩」。

**不残留进行中**（`INV-11`）：任何终止路径——成功 / 失败 / 已取消 / 已跳过 / 迟到丢弃 / 进程退出——都必须收敛到上述五态之一；重启后不得残留「进行中」，也不得因未释放的等待让后续回合永久 busy。

**为什么必须写死**：复用摘要函数不会自动继承回合的取消语义——它只接受一个信号，不会自行关联父回合。若不要求接线，实现完全可以在取消后继续等待并提交，而两种做法都不违反原文任何条款。

#### 2.3.6 缓存契约

**缓存什么**：只缓存**模型生成的七栏目**（且必须通过格式校验）。**系统字段（未解决操作、工具结果）不缓存**——每次从当前执行记录重新装配（`INV-1`）。

**为什么**：同一段对话文本下，执行事实仍会变化（新工具结果、新出现的未知副作用）。连系统字段一起缓存，就会把旧事实带回新上下文，直接违反 `INV-1`。

**缓存键**：被压缩内容指纹 + 模型标识 + 服务标识 + 语言 + 提示词版本 + 七栏目结构版本。不含会话标识，但缓存作用域限定在会话内，不跨会话共享。

**只缓存成功**：

| 结果 | 写缓存 | 下次同输入 |
|---|---|---|
| 成功且校验通过 | 是 | 直接复用，不再调用模型 |
| 超时 | 否 | **允许再次调用** |
| 格式非法 | 否 | 允许再次调用 |
| 取消 / 迟到丢弃 | 否 | 允许再次调用 |

**与重试承诺的关系**：`AC-10` 的「只调用一次」**只约束成功结果的复用**，不是「同一输入永远只允许调用一次」。失败必须允许重试，否则一次瞬时故障会把该段内容永久固化成「摘要不可用」。

#### 2.3.7 压缩卡片的状态（五态）

| 状态 | 触发 | 用户可见 |
|---|---|---|
| 进行中 | 摘要请求已发出 | 「正在自动压缩…」 |
| 成功 | 上下文替换提交完成 | 「已压缩，占用 X% → Y%」（`D-2` 选 A） |
| 失败 | 摘要超时 / 格式非法 / 提交失败 | 「压缩失败」+ 可展开原因 |
| 已跳过 | 摘要成功但未提交：收益不足 / 结构性压不动 / 复核失败（§2.3.5） | 「未压缩（无收益）」等，**不显示比例** |
| 已取消 | 父回合取消或超时 | 「已取消」（不移除该条） |

### 2.4 失败与崩溃窗口

| 窗口 | 现象 | 唯一恢复动作 |
|---|---|---|
| W1 压缩未触发（未达阈值） | 正常请求 | 无需处理 |
| W2 摘要失败但当前请求在预算内 | 压缩卡片失败，回合继续 | 下次请求重新判断（`INV-2`） |
| W3 摘要失败且当前请求已超预算 | 按既有超预算处理 | 沿用现有错误，不新增分支 |

| W5 摘要生成中进程退出 | 无提交 | 下次重新判断；压缩卡片不得残留「进行中」 |
| W6 压缩卡片写入失败 | 界面缺一条过程记录 | 不得因此中断回合（属可丢投影） |

### 2.5 并发与顺序

- **手动压缩**沿用既有全局压缩锁（`F-5`），本方案不改变。
- **自动压缩不使用该锁**：它已在回合内顺序等待，再套一把独立锁会与回合生命周期互锁。其互斥由「回合内串行 + 提交前复核（`INV-10`）」保证。
- 缓存在会话作用域内，按 §2.3.6 的键索引；不跨会话共享。
- 阈值在压缩判定入口读取，单次判定内只读一次（`INV-7`）。

**阶段 1（S）——触发线 90% → 80%，并一次消除三份副本**
输入：`D-1`、§2.3.3。输出：生成预算的函数增加比例入参；预算对象与决策指纹共用同一变量；判定钳制的上限引用同一常量；装配层从配置读值（缺省回退 80%）；测试夹具同步更新。

2. **形态**：一行状态 + 可折叠。进行中显示「正在自动压缩…」；成功显示「已压缩，占用 82% → 41%」并默认折叠；失败显示「压缩失败」，可展开看原因；**已跳过**显示「未压缩（无收益）」等，**不显示比例**；**用户取消时显示「已取消」且不移除该条**（`INV-9`、`INV-11`）。
3. **样式来源**：复用现有工具行的容器、折叠交互与间距；不新增图标族（用现有图标）、不新增配色（失败沿用现有错误色）。
4. **新增还是改造**：新增一种**系统操作卡片**的数据类型（现有工具行绑在工具调用上，压缩不是工具调用）。**该机制由重试方案共用**——重试卡片是同一家族的第二类条目，因此类型与组件一次留出扩展位，不各建一套。
5. **成本**：新增 4 条文案（进行中 / 成功 / 失败 / 已取消）；要测的组合：成功折叠、失败展开、**用户取消后卡片收敛为「已取消」而非失败**、连续多次压缩、压缩过程中切换会话、进程重启后无残留「进行中」；与重试卡片同时出现时的排列顺序。

### 卡 B：「模型」页触发比例设置项

1. **放哪个入口**：「模型」设置页，Thinking 强度之后。因为同属「模型请求行为」参数，且紧邻上下文窗口相关设置，用户调模型时自然看到；**不进通用页**（避免与界面语言等无关项混在一起）。
2. **形态**：一行设置项 = 标签 + 数值/滑杆 + 一句说明（「上下文用到该比例时自动压缩对话」）。
3. **样式来源**：复用现有设置项的标签、控件与说明文字样式；不新增控件类型。
4. **新增还是改造**：在既有页签内**新增一行**，不改动其他设置项。
5. **成本**：新增 1 条标签 + 1 条说明 + 1 个范围校验（60–90）；要测：越界输入（55 / 95）、配置缺失回退 80%、修改后下一次判定即生效（无需重启）。

**批准记录**：审批人 = 项目负责人（本仓库即你本人）；批准时间 = 2026-10-18；批准内容 = 卡 A（压缩卡片：位置为聊天流工具调用同区，显示状态 + 压缩前后占用，不显示摘要正文）+ 卡 B（「模型」页 Thinking 强度之后的阈值设置项，范围 60–90）。卡 A 建立的「系统操作卡片」机制由重试方案共用，不重复建设。
