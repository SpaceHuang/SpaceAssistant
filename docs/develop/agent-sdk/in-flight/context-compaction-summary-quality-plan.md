# 自动压缩摘要质量对齐方案

> 日期：2026-10-18
> 文档性质：**技术方案（在途草稿，未实施）**
> 基线：`main` `28dd3223`（2026-10-17）

## 一句话

长对话压缩时，模型拿到的「交接单」现在只有两段各截断 1200 字的散文；而用户手动点压缩时，走的是另一条实现，出来的是七个栏目加执行事实。同一次会话、两种质量。本方案让自动压缩也对齐后者。

## 第 0 层：决策层 【人必读】

### 只有 3 分钟的话

先看 `D-2`（自动压缩要不要额外调一次模型——这是本方案唯一的体验取舍）。
`D-1` 是「先做不花钱的那半」，我建议必做。

### 需要你决定的事项

#### D-1 先补「确定性部分」，还是等整体方案

**背景**：压缩后的交接单里，有两类内容完全不需要模型参与——「哪些操作已经做完了、结果如何」和「哪些操作可能执行了但结果不明」。这两项系统自己就能从执行记录里查出来，现在的自动压缩**根本没写进去**。

**要决定什么**：是否先独立交付这一半（不增加任何延迟、不增加任何模型调用），还是等 `D-2` 定了之后一起做。

**每个选项的后果**：
- 先做——立刻缓解「压缩后重复劳动」和「压缩后忘了有个操作没结算」。代价是交接单结构会先变一次，`D-2` 落地时再变一次（两次都要测）。
- 等一起做——只变一次结构；代价是这一半的收益被 `D-2` 的讨论拖着。

**可逆性**：可逆（只是写入历史的内容更丰富了，旧数据不受影响）。

**依据强度**：已核实——这两项的数据来源已存在且被手动压缩使用（`F-2`、`F-3`），不是新造。

**推荐与默认**：先做 `D-1`。它是纯增量，没有取舍成本，而且能立刻验证「未解决操作」这条链路是通的。

#### D-2 自动压缩允许额外调一次模型吗

**背景**：要把摘要写成七个栏目（目标、已完成、决定、约束、待办、阻塞、下一步），得让模型读一遍被压缩的内容再输出。而自动压缩发生在**每次请求模型之前**，等于「为了发请求，先发一个请求」。

**要决定什么**：

- A：允许，但设短超时（建议 20 秒）+ 失败时退回现在的截断拼接 + 同一段内容只生成一次（缓存命中直接复用）
- B：允许，不设短超时（跟随手动压缩的 90 秒）
- C：不允许自动压缩调模型，只做 `D-1` 那半

**每个选项的后果**：
- 选 A——长对话时每次压缩最多多等 20 秒；摘要是七栏目，压缩后模型更不容易重复劳动。超时或解析失败时用户看到的是和今天一样的截断版，不会更糟。
- 选 B——摘要质量更稳，但一次压缩可能让用户干等 90 秒，而这发生在「用户按下发送之后、模型开始回话之前」，体感是「卡住了」。
- 选 C——零延迟，但交接单永远只有确定性事实、没有「下一步该干什么」，压缩后模型仍可能不知道任务方向。

**可逆性**：可逆（超时值、开关都能调）。

**依据强度**：手动压缩路径已在生产使用（`F-4`），其摘要质量与耗时表现有真实数据；但**自动压缩场景下的耗时分布没有测过**（每次请求前都可能触发，频率远高于手动）。属未验证项 `U-1`。

**推荐与默认**：A。你不决定时按 A 走。

#### D-3 交接单允许写多长

**背景**：七个栏目每个最多 2000 字符（现状手动压缩的上限），合计理论最大约 1.4 万字。而自动压缩**只有在「压缩后确实省了空间」时才做**——如果交接单本身太大，压缩就没有意义。栏目变多会让这个门槛更容易被触发。

**要决定什么**：是否接受「因为交接单太大，某些压缩被跳过」这个结果。

**每个选项的后果**：
- 接受——不会为了写交接单而制造更大的上下文；代价是极端情况下压缩反而做不成。
- 不接受（放宽上限）——交接单更完整；代价是压缩收益变小，可能白花一次模型调用。

**可逆性**：可逆。

**依据强度**：现有手动路径已有「交接单不比被压缩内容省空间就不做」的保护（`F-5`），本方案沿用即可，不需要新机制。

**推荐与默认**：接受，沿用现有保护，不调上限。

### 不需要你决定（Agent 已查证或负责）

- 未解决操作、工具结果这类事实由谁提供：由主机查执行记录，模型不得生成（见 `INV-1`）。
- 摘要生成失败怎么办：退回现状的截断拼接，任务不因此失败（见 `INV-2`）。
- 会不会陷入「压缩的压缩」：摘要请求本身不触发压缩（见 `INV-4`）。
- 手动压缩的行为会不会被改动：不改，只让它和新格式共用同一套校验（见 `AC-6`）。

## 第 1 层：概要 【人机共读】

### 1.1 现状：两条压缩路径，两种质量

| | 用户手动点「压缩」 | 自动压缩（每次请求前 / 回合边界） |
|---|---|---|
| 交接单内容 | 七个栏目 + 未解决操作清单 + 最近工具结果 | 用户文本截断 1200 字、助手文本截断 1200 字、一句「如需完整历史请查询」 |
| 是否调模型 | 是（90 秒超时） | 否 |
| 是否带执行事实 | 是 | **否** |

这不是设计选择，是两次改造没对齐的结果（`F-1`）。

### 1.2 分三个阶段推进（这是本方案的核心安排）

**阶段 1：只补确定性事实，不调模型。**
「哪些操作做完了、结果如何」「哪些操作结果不明」——这两项从执行记录里直接查，写进交接单。零延迟、零额外费用、零外部依赖。**这是本方案最高性价比的部分，且它不依赖 `D-2`。**

**阶段 2：让摘要变成七个栏目。**
需要模型参与，因此要处理超时、失败退回、缓存（同一段内容不重复生成）。

**阶段 3（可选，风险最高）：放开「有工具调用时不压缩」这条限制。**
现状是：只要模型这一轮提出了工具调用，压缩就整体跳过。查证后发现**这不是漏写，是保护性写法**（`F-6`、`F-7`）——压缩结果必须原样保留待执行的工具提案，而这条强校验从未被真正走到过。放开等于启用一条没验证过的路径，所以单独列为可选项。

### 1.3 排除方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 把自动压缩直接换成手动压缩那套实现 | **部分排除** | 会造成「每次请求前都多一次模型调用且无超时保护」，等于把 D-2 的坏选项变成默认；改为带超时/缓存/降级 |
| 让模型自己维护待办清单，不依赖压缩 | **排除** | 依赖模型自觉，压缩后照样会丢 |
| 干脆关闭自动压缩 | **排除** | 长对话直接因超预算失败 |
| 提高压缩后保留的消息数 | **排除** | 治不了「压缩后不知道做到哪」这个问题本身 |
| 顺手放开「有工具调用不压缩」 | **排除在主体外** | 见阶段 3，风险性质不同，不混入 |

### 1.4 主要风险

1. **延迟**：阶段 2 让每次压缩可能多等最多 20 秒，而这发生在用户按下发送之后。缓解：短超时 + 缓存 + 失败退回（不新增第三种失败态）。
2. **成本**：每次压缩多一次模型调用。缓解：同一输入只生成一次；交接单太大时直接跳过压缩（沿用现有保护）。
3. **事实被模型改写**：模型可能把「结果不明」写成「已完成」。缓解：`INV-1` —— 这两项由主机写入，模型输出里即使出现也不采纳。
4. **递归**：摘要请求本身可能再次触发压缩。缓解：`INV-4`，摘要请求走独立通道，不进压缩链路。

## 第 2 层：规格 【机｜人工可跳过】

### 2.1 不变量

| ID | 不变量 | 为什么 | 违反时表现 | 验证 |
|---|---|---|---|---|
| `INV-1` | 未解决操作清单与工具结果只能由主机从执行记录生成；模型输出中的同名字段一律丢弃 | 模型会把文字承诺当成已解决 | 压缩后模型以为某操作已完成，实际没做 | `AC-4` |
| `INV-2` | 摘要生成失败（超时/格式非法）不得使回合失败，必须退回现有截断拼接 | 压缩是优化，不是任务前提 | 长对话直接报错 | `AC-2` |
| `INV-3` | 摘要生成有超时且可取消；同一输入不重复生成 | 否则卡住用户且白花钱 | 用户感知「卡住」；同一压缩反复调用 | `AC-3` |
| `INV-4` | 摘要请求自身不进入压缩链路（不得递归触发压缩） | 会无限套娃 | 栈溢出 / 死循环 | `AC-5` |
| `INV-5` | 交接单结构只有一个定义处；手动与自动压缩产出同一结构、走同一校验 | 两份格式必然漂移 | 一处改了另一处没改 | `AC-6` |
| `INV-6` | 交接单不比被压缩内容省空间时不做压缩 | 否则压缩无收益 | 越压越大 | `AC-7` |

### 2.2 状态与所有权

| 事实 | 唯一 writer | 唯一提交点 | 恢复者 |
|---|---|---|---|
| 交接单内容 | 压缩提交路径 | 与上下文替换**同一次**提交（沿用现有事务边界） | 既有提交不确定路径 |
| 未解决操作 / 工具结果 | 主机查询执行记录 | 同上（生成时读取，随交接单一起写） | 同一次读取可重放 |
| 摘要缓存 | 摘要生成器（按输入指纹索引） | 生成成功后写入；提交失败时缓存保留也无害 | 指纹不符即失效 |

**不允许**：模型在摘要里生成未解决操作 ID；界面或统计从交接单文本回推执行状态。

### 2.3 契约

#### 2.3.1 交接单内容结构（唯一结构）

| 字段 | 归属 | 是否可由模型生成 | 说明 |
|---|---|---|---|
| 目标 | 模型 | 是 | 任务目标 |
| 已完成 | 模型 | 是 | 但不得作为工具成功的证据 |
| 决定 | 模型 | 是 | |
| 约束 | 模型 | 是 | |
| 待办 | 模型 | 是 | |
| 阻塞 | 模型 | 是 | |
| 下一步 | 模型 | 是 | |
| 未解决操作清单 | 主机 | **否** | 稳定 ID 列表，来自执行记录 |
| 最近工具结果 | 主机 | **否** | 按「成功 / 已知失败 / 结果不明 / 未执行」表示 |

字段长度上限沿用现状（每栏 ≤2000 字符），不调。

#### 2.3.2 兼容

- 旧交接单只有「用户文本 / 助手文本 / 提示句」三字段。读取方按「缺字段」处理，**不迁移、不回填**。
- 新结构与旧结构共存的判定：以是否存在七栏目字段为准。

#### 2.3.3 摘要生成的调用约束

| 项 | 取值 | 备注 |
|---|---|---|
| 超时 | 20 秒（自动）/ 90 秒（手动，不变） | 由 `D-2` 决定 |
| 温度 | 0 | 沿用现状 |
| 输出上限 | 1536 token | 沿用现状 |
| 失败处理 | 退回截断拼接 | `INV-2` |
| 缓存键 | 输入指纹（窗口 + 被遮蔽范围 + 内容指纹） | `INV-3` |

### 2.4 失败与崩溃窗口

| 窗口 | 现象 | 唯一恢复动作 |
|---|---|---|
| W1 摘要生成中进程退出 | 无提交，上下文未变 | 等价今天：下次请求重新判断是否压缩 |
| W2 摘要成功、压缩提交失败 | 走既有提交不确定路径 | 沿用（不新增分支） |
| W3 摘要成功、缓存写入失败 | 下次重新生成 | 不影响正确性 |
| W4 交接单含主机事实但提交被回滚 | 事实未落库 | 下次压缩重新查询，不依赖缓存里的旧事实 |
| W5 摘要请求自身超预算 | 摘要请求不进入压缩链路 | `INV-4` |

### 2.5 并发与顺序

- 同一会话同时只有一个压缩提交（既有互斥，`F-8`）；本方案不改变。
- 摘要缓存按输入指纹索引，多窗口并发时各自独立，不共享。

### 2.6 验收

| ID | 验收（可执行断言） | 关联 |
|---|---|---|
| `AC-1` | 自动压缩产出的交接单含七栏目 + 未解决操作清单 + 工具结果 | `INV-1`、`INV-5` |
| `AC-2` | 强制摘要超时 / 返回非法 JSON → 回合继续，交接单退回截断版，不报错 | `INV-2` |
| `AC-3` | 同一输入连续触发两次压缩 → 模型只被调用一次（缓存命中） | `INV-3` |
| `AC-4` | 未解决操作清单与执行记录查询结果逐条一致；模型输出里的同名字段被丢弃 | `INV-1` |
| `AC-5` | 摘要请求不会触发二次压缩（构造超长被压缩片段验证） | `INV-4` |
| `AC-6` | 手动压缩行为不变（对拍：预览文本、提交结果、界面状态一致） | `INV-5` |
| `AC-7` | 交接单 ≥ 被压缩内容时不做压缩（沿用现有保护） | `INV-6` |
| `AC-8` | 旧交接单（三字段）读取无异常，不触发迁移 | §2.3.2 |

### 2.7 阶段

**阶段 1（S）——确定性事实进交接单**
输入：§2.3.1 的两行主机字段。输出：自动压缩的交接单里出现「未解决操作清单」与「最近工具结果」，由主机查询填写。
出口证据：`AC-1`（主机部分）、`AC-4`。可回退实体：单个提交，删除即回到现状。

**阶段 2（M）——七栏目摘要（含超时/缓存/降级）**
输入：`D-2`、§2.3.3。输出：自动压缩调模型生成七栏目，失败退回截断。
出口证据：`AC-1`（模型部分）、`AC-2`、`AC-3`、`AC-5`、`AC-6`、`AC-7`。
可回退实体：单个提交；`D-2` 选 C 时本阶段不启动。

**阶段 3（可选，待批）——放开「有工具调用不压缩」**
输入：`D-4`（见附录 B）。输出：回合边界在存在待执行工具提案时也允许压缩，且压缩结果必须原样保留提案。
出口证据：`AC-9`（新增：压缩后待执行提案逐字段一致，否则拒绝压缩并保持现状）。
**默认不做**：这是启用一条从未被走通的校验路径（`F-7`），风险高于阶段 1–2。
