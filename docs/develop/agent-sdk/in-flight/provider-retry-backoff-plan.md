## 一句话

模型服务偶尔会「忙不过来」「自己出错」或「网络断一下」，现在系统会立刻重发，最多试三次就放弃。短对话里够用；跑几十分钟以上的任务，几乎一定会被这类瞬时故障打断。本方案把「等多久、试几次、什么时候放弃」变成一套有上限、可解释的规则。

## 第 0 层：决策层 【人必读】

### 只有 3 分钟的话

先看 `D-1`（试几次、每次等多久）和 `D-4`（要不要让用户看见/可调）。
`D-2`、`D-3` 是配套的上限，跟着 `D-1` 走。

### 需要你决定的事项

#### D-1 瞬时故障试几次、每次等多久

**背景**：所谓瞬时故障，指这几种——服务端说「你请求太快了」、服务端自己出错了、网络连接断了一下。这些通常等几秒再试就好。现状是：**除了服务端明确告诉你「等 N 秒再来」以外，系统会立刻重发，不等**。最多试 3 次，然后整个回合失败。

**要决定什么**：

- A：保持试 3 次，但加入「越失败的次数越久」的等待（第 1 次等 0.5 秒、第 2 次等 1 秒……上限 8 秒），并加随机抖动
- B：试 5 次 + 同样加入等待与抖动（推荐）
- C：只加等待，次数不变（= A）
- D：试更多次（超过 5 次需要同时改另一处上限，见 `U-1`）

**每个选项的后果**：
- 选 A / C——比今天稳，但连续两次瞬时故障耗尽后还是会失败。
- 选 B——最常见的一分钟内限流（很多服务按分钟配额）有机会自动恢复；代价是最坏情况下失败前多花约 20 秒。
- 选 D——更抗故障，但一次回合可能在"什么都没做"的状态下耗掉一分钟以上，且需要改动另一层代码。

**可逆性**：可逆（改常量）。

**依据强度**：现有代码事实清楚（`F-2`）；但**各服务商实际的限流窗口与故障时长分布没有测过**（`U-2`），所以 B 是经验值。

**推荐与默认**：B（5 次 + 递增等待 + 抖动）。

#### D-2 单次最多等多久

**背景**：服务端有时会说「请等 120 秒再来」。现在系统**把这类要求硬砍到 30 秒**，然后就重发——等于没照做，通常会再被拒一次。

**要决定什么**：

- A：保持 30 秒上限（现状）
- B：提到 60 秒（推荐）
- C：完全照服务端说的等（不设上限）

**后果**：选 A——用户不会等太久，但服务端的长要求基本无效；选 B——能真正按服务端节奏走，代价是最坏情况下用户多等 60 秒；选 C——最守规矩，但极端情况下可能卡住几分钟，而用户不知道发生了什么。

**可逆性**：可逆。注意这个上限目前写在**两处**，都要改（`F-3`）。

**依据强度**：`F-3` 已核实两处硬编码。

**推荐与默认**：B（60 秒）。

#### D-3 一次回合最多总共等多久

**背景**：如果允许「试 5 次、每次最多等 60 秒」，理论上一次回合可以光等待就耗掉 4 分钟以上。

**要决定什么**：

- A：不设总额（单次上限就够）
- B：设 60 秒总额，超过就放弃并提示可重试（推荐）

**后果**：选 A——简单，但用户可能面对「界面静止四分钟」；选 B——到点就明确放弃，用户知道发生了什么。

**可逆性**：可逆。

**依据强度**：无数据；属保守设计。

**推荐与默认**：B。

#### D-4 要不要让用户看见、要不要可调

**背景**：这两件事都会触发产品层审批——**显示状态属于界面改动，可调属于新增配置项**。所以必须问你。

**要决定什么**（可分别回答）：

- **D-4a** 是否在界面上显示「正在重试（第 2/5 次，约 3 秒后）」
- **D-4b** 是否把「试几次 / 单次等多久」做成设置项，让用户能调

**每个选项的后果**：
- 都做——用户知道系统在努力，不会以为卡死；但多一处界面和多一个开关要维护，且用户可能把次数调得很高导致费用上升。
- 只做 a——透明度够了，策略仍由我们定。
- 都不做（推荐）——行为改善照常生效，界面零改动，本方案不触发界面与配置项审批。

**可逆性**：都不做是可逆的；一旦上了界面/开关，收回成本较高。

**依据强度**：现状已有「重试已安排」的内部事件记录但**没有交给界面**（`F-4`），所以做 a 属于新增界面语义，不做则零改动。

**推荐与默认**：都不做。先让策略在后台生效，观察真实故障分布（`U-2`）后再决定要不要暴露。

### 不需要你决定（Agent 已查证或负责）

- 哪些错误该重试、哪些绝不该重试：见 §2.3 分类表，依据是现有实现 + 明确排除项。
- 重试期间用户取消怎么办：立即停止等待，沿用现有可取消机制（`F-5`）。
- 每次重试是否要单独记账：已实现，本方案不改（`F-6`）。
- 会不会重复执行工具：不会。工具执行与模型请求是两回事，本方案只动模型请求（`INV-1`）。

## 第 1 层：概要 【人机共读】

### 1.1 现状

| 故障类型 | 现在试几次 | 两次之间等多久 |
|---|---|---|
| 服务端太忙 / 服务端出错 / 网络断 | 3 次 | 服务端给了等待时间就等（但硬砍到 30 秒），没给就**立即重发** |
| 模型流静默超时 | 2 次 | 立即重发 |
| 上下文超长 | 2 次 | 立即重发 |
| 认证失败 / 参数不对 | 0 次（正确） | — |

三处「几次」和两处「30 秒」都是写死在代码里的（`F-2`、`F-3`）。上游方案声称已实现「指数退避 + 抖动」，实际没有（`F-7`）。

### 1.2 要改成什么

1. **加入递增等待与随机抖动**（避免多个会话在同一毫秒一起重发）。
2. **按 `D-1` 调整次数**。
3. **放开单次等待上限**（按 `D-2`，两处一起改）。
4. **加入整轮总等待预算**（按 `D-3`），到点明确放弃。
5. **保持**：adapter 自身不重试（现状正确——重试次数必须集中在一处才数得清）、每次尝试独立记账、取消可立即打断等待。

### 1.3 排除方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 让各家服务商的 SDK 自己重试 | **排除** | 请求次数会被藏起来，账目不可核，且不同 SDK 策略不一（现状已在上层统一，方向正确） |
| 无限重试（`always` 模式） | **排除** | 费用不可控，用户无法感知 |
| 跨服务商自动切换 | **排除** | 不同模型的工具格式、上下文长度、能力不同，切换会导致行为漂移；需独立设计 |
| 对认证失败也重试 | **排除** | 把配置错误伪装成延迟，用户更难排查 |
| 只调次数不加等待 | **排除** | 立即重发对上「按分钟限流」的服务无效，等于浪费次数 |

### 1.4 主要风险

1. **变慢**：最坏情况下一次回合多等约 60 秒（`D-3` 兜底）。缓解：总预算到点即放弃。
2. **放大费用**：重试的是模型请求，每次都产生用量。缓解：现有实现已对每次尝试独立记账，且被丢弃的尝试也计入；本方案不引入隐藏尝试。
3. **抖动引入不确定性**：测试难写。缓解：等待实现接受可注入的时钟/随机源（`AC-4`）。
4. **两处上限漏改**：只改一处会导致「宿主允许 60 秒、实际仍被砍到 30 秒」。缓解：`AC-2` 直接断言最终生效值。

## 第 2 层：规格 【机｜人工可跳过】

### 2.1 不变量

| ID | 不变量 | 为什么 | 违反时表现 | 验证 |
|---|---|---|---|---|
| `INV-1` | 重试只发生在「响应未被接受」之前；已被接受的响应（含流中途）不得重发 | 重发会重复工具调用或产生双份输出 | 用户看到重复内容；工具被执行两次 | `AC-3` |
| `INV-2` | 每次尝试（含被丢弃的）必须独立记账，总量守恒 | 否则费用与用量对不上 | 账单高于统计 | `AC-5` |
| `INV-3` | 等待必须可被取消，取消后立即停止且不再发起新尝试 | 用户点了取消还在等 | 取消失效 | `AC-6` |
| `INV-4` | 一次回合的总等待时间有上界；到上界即放弃并返回可重试的明确错误 | 否则界面无反应 | 用户以为卡死 | `AC-7` |
| `INV-5` | 认证/授权/参数类错误不重试 | 配置错误不该被延迟掩盖 | 用户等 60 秒后看到「认证失败」 | `AC-8` |
| `INV-6` | 重试次数的唯一决定处是宿主策略；adapter 不得自行重试 | 两处计数必然对不上 | 实际尝试次数超过配置 | `AC-9` |

### 2.2 状态与所有权

| 事实 | 唯一 writer | 唯一提交点 | 恢复者 |
|---|---|---|---|
| 尝试次数 / 剩余预算 | 宿主恢复策略（每次决定后由内核持有） | 每次发起尝试前 | 回合结束即丢弃（不跨回合继承） |
| 重试记录与用量 | 内核（每次尝试落一条） | 尝试结束后立即 | 既有用量对账 |
| 总等待消耗 | 宿主策略 | 同回合内累加 | 同上 |

**不允许**：adapter 内部计数；界面自行推算「已重试几次」。

### 2.3 错误分类（决定是否重试）

| 类别 | 是否重试 | 示例（业务说法） |
|---|---|---|
| 瞬时可重试 | 是 | 服务端说你请求太快、服务端自己 5xx、连接被重置、DNS 暂时失败、流静默超时 |
| 输入/配置永久错误 | 否 | 请求格式非法、模型不支持该参数 |
| 凭据/授权错误 | 否 | 密钥无效、无权限 |
| 特殊兼容恢复 | 走既有专用分支 | 思维档位不被支持 |
| 上下文溢出 | 走既有专用分支 | 超长（已有独立预算） |
| 用户取消 / 回合超时 | 立即停止 | — |
| 流格式非法 | **默认不重试** | 事件序列非法、重复工具 ID；只有被证明是传输截断才允许恢复 |

### 2.4 退避参数（`D-1` 取 B 时）

| 项 | 取值 | 说明 |
|---|---|---|
| 基础等待 | 500 ms | 第 1 次重试前 |
| 倍增 | 2× | 500 / 1000 / 2000 / 4000 |
| 单次上限 | 8 s | 指数增长封顶 |
| 抖动 | 全额抖动（0～计算值） | 避免同步重试 |
| 服务端指定等待 | 优先于计算值，受 `D-2` 约束 | 两处上限都要放 |
| 最大尝试次数 | 5（含首次） | 超过 5 需同时改内核钳制（`F-1`） |
| 整轮总等待 | 60 s（`D-3`） | 到点放弃 |

### 2.5 失败与恢复

| 窗口 | 现象 | 唯一恢复动作 |
|---|---|---|
| W1 等待中被取消 | 定时器清除 | 立即抛取消，不发起新尝试 |
| W2 等待中进程退出 | 无新尝试 | 回合按既有「中断」收场，不自动续 |
| W3 已达总等待预算 | 计算出的等待会超预算 | 不再等待，直接放弃并给出可重试时间 |
| W4 服务端要求的等待超过剩余预算 | 同上 | 明确告知「可于 X 后重试」，不静默截断 |
| W5 重试成功但有被丢弃的输出 | 已实现：丢弃尝试仍记账并标记 | 沿用 |

### 2.6 验收

| ID | 验收 | 关联 |
|---|---|---|
| `AC-1` | 服务端返回「太快了」且无重试提示 → 5 次尝试内成功，每次等待符合递增 + 抖动区间 | `INV-6` |
| `AC-2` | 服务端指定等待 45 秒 → 实际等待在 30～60 秒内（证明两处上限都已放开） | `D-2` |
| `AC-3` | 响应已被接受后再发生错误 → 不重发（对拍：只产生一份输出、工具只执行一次） | `INV-1` |
| `AC-4` | 注入固定随机源与时钟 → 等待序列可精确断言 | 测试可行性 |
| `AC-5` | 连续 5 次失败 → 用量记录含 5 条尝试（含被丢弃） | `INV-2` |
| `AC-6` | 等待中取消 → 100 ms 内停止，无新尝试 | `INV-3` |
| `AC-7` | 累计等待达 60 秒 → 放弃并返回稳定错误码 | `INV-4` |
| `AC-8` | 认证失败 → 立即失败，零等待 | `INV-5` |
| `AC-9` | adapter 侧重试次数恒为 0（以调用记录断言） | `INV-6` |
| `AC-10` | 静默超时 / 上下文溢出分支的预算不被本方案改变（回归） | 排除影响面 |

### 2.7 阶段

**阶段 1（S）——退避与抖动**
输入：`D-1`、§2.4。输出：瞬时可重试错误按递增 + 抖动等待；随机源与时钟可注入。
出口证据：`AC-1`、`AC-4`。可回退实体：单个提交。

**阶段 2（S）——放开单次等待上限**
输入：`D-2`。输出：宿主解析与内核等待两处上限一致放开。
出口证据：`AC-2`。可回退实体：单个提交（两处同时回退）。

**阶段 3（S）——整轮总等待预算**
输入：`D-3`。输出：到点放弃 + 稳定错误码 + 可重试时间提示。
出口证据：`AC-7`。可回退实体：单个提交。

**阶段 4（M，未获批不排期）——次数上限与用户可见性**
输入：`D-1` 若选 D（超过 5 次需改内核钳制 `F-1`）、`D-4a`/`D-4b`。
**阻塞于 `D-4` 获批**：界面状态与配置开关均属必须人批项，未批不实现。

## 三份文档的关系

- **压缩摘要质量**：不改变重试策略；但压缩若引入额外模型调用，会放大重试频次（`U-3`）。
- **回合预算耗尽（阶段暂停）**：重试造成的额外等待会占用该方案的段时长；两份都落地时，段时长预算应把重试等待计入（在暂停方案里已按"段时长"预留字段，无需改契约）。
