## 一句话

模型服务偶尔会「忙不过来」「自己出错」或「网络断一下」，现在系统会立刻重发，最多试三次就放弃。短对话里够用；跑几十分钟以上的任务，几乎一定会被这类瞬时故障打断。本方案把「等多久、试几次、什么时候放弃」变成一套有上限、可解释的规则。

## 第 0 层：决策层 【人必读】

### 只有 3 分钟的话

已定：**重试对用户可见、对模型不可见**——用户能在聊天流里看到一行「正在重试」，而模型看到的仍然是「一次请求、一次响应」，重试痕迹不进入对话上下文（见 `INV-7`）。

全部决策已批复（2026-10-29）：`D-1`～`D-4` 为行为与可见性、`D-5`～`D-6` 为数据格式，详见各自标题。**决策层已无待定项，可进入实施评审。**

### 已经定下来的（留档，无需再讨论）

#### D-1 瞬时故障试几次、每次等多久（已定：B）

**背景**：所谓瞬时故障，指这几种——服务端说「你请求太快了」、服务端自己出错了、网络连接断了一下。这些通常等几秒再试就好。现状是：**除了服务端明确告诉你「等 N 秒再来」以外，系统会立刻重发，不等**。最多试 3 次，然后整个回合失败。

**要决定什么**：

- A：保持试 3 次，但加入「越失败的次数越久」的等待（第 1 次等 0.5 秒、第 2 次等 1 秒……上限 8 秒），并加随机抖动
- B：试 5 次 + 同样加入等待与抖动（推荐）
- C：只加等待，次数不变（= A）
- D：试更多次（超过 5 次需要同时改另一处上限，见 `U-1`）

**每个选项的后果**：
- 选 A / C——比今天稳，但连续两次瞬时故障耗尽后还是会失败。
- 选 B——最常见的一分钟内限流（很多服务按分钟配额）有机会自动恢复；代价是最坏情况下失败前多花约 20 秒。
- 选 D——更抗故障，但一次回合可能在"什么都没做"的状态下耗掉一分钟以上，且需要改动另一层代码。

**可逆性**：可逆（改常量）。

**依据强度**：现有代码事实清楚（`F-2`）；但**各服务商实际的限流窗口与故障时长分布没有测过**（`U-2`），所以 B 是经验值。

**已定（2026-10-29）**：B —— 5 次总尝试（含首次，即最多 4 次重试）+ 递增等待 + 抖动。

#### D-2 单次最多等多久（已定：B）

**背景**：服务端有时会说「请等 120 秒再来」。现在系统**把这类要求硬砍到 30 秒**，然后就重发——等于没照做，通常会再被拒一次。

**要决定什么**：

- A：保持 30 秒上限（现状）
- B：提到 60 秒（推荐）
- C：完全照服务端说的等（不设上限）

**后果**：选 A——用户不会等太久，但服务端的长要求基本无效；选 B——能真正按服务端节奏走，代价是最坏情况下用户多等 60 秒；选 C——最守规矩，但极端情况下可能卡住几分钟，而用户不知道发生了什么。

**可逆性**：可逆。注意这个上限目前写在**两处**，都要改（`F-3`）。

**依据强度**：`F-3` 已核实两处硬编码。

**已定（2026-10-29）**：B —— 单次最多等 60 秒。

#### D-3 一次回合最多总共等多久（已定：B）

**背景**：如果允许「试 5 次、每次最多等 60 秒」，理论上一次回合可以光等待就耗掉 4 分钟以上。

**要决定什么**：

- A：不设总额（单次上限就够）
- B：设 60 秒总额，超过就放弃并提示可重试（推荐）

**后果**：选 A——简单，但用户可能面对「界面静止四分钟」；选 B——到点就明确放弃，用户知道发生了什么。

**可逆性**：可逆。

**依据强度**：无数据；属保守设计。

**已定（2026-10-29）**：B —— 一次回合累计最多等 60 秒。

#### D-4 可见性与可调性（D-4a 已定：用户可见；D-4b 已定：不做）

**已定（2026-10-18）**：**D-4a = 用户可见**。聊天流里显示一行「正在重试（第 2/5 次，约 3 秒后）」，失败时显示「重试失败」。卡片复用压缩方案要建的那套「系统操作卡片」，不新建组件类别。

**同时已定**：**模型不可见**。重试痕迹不进入发给模型的对话，模型侧看到的仍是「一次请求、一次响应」（`INV-7`）。

**已定（2026-10-29）：D-4b = 不做。** 不把「试几次 / 单次等多久」暴露成设置项。
背景：这类开关属新增配置项，需要审批。
- 做——高级用户可按服务商限流特性调；代价是多一个开关要维护，且用户可能把次数调得很高导致费用上升。
- 不做（**已选定**）——策略由我们定，界面只多一张状态卡片，不多开关。先观察真实故障分布（`U-2`）再评估。

**可逆性**：卡片可撤（收回即可回到"看不见"）；一旦上了可调开关，收回成本较高。

**依据强度**：现状已有「重试已安排」的内部事件，但渲染层从未消费（`F-4`），所以 D-4a 属于新增界面语义——已获批准。

### 数据格式两项（已定 2026-10-29）

#### D-5 重试记录里加哪些字段（已定：B）

**背景**：你已批「用户能看到正在重试（第 2/5 次，约 3 秒后）」。要显示这句话，系统得在「重试已安排」这条记录里多存几项：第几次、总共几次、计划等多久、最早何时能重试。这属于新写进数据库的字段，按规矩要你批。

**要决定什么**：

- A：只存最小集（第几次、总共几次）——卡片只能显示「正在重试（2/5）」，看不到还要等多久
- B：再加「计划等待毫秒」与「最早可重试时刻」（推荐）——卡片能显示「约 3 秒后」
- C：什么都不加，卡片只显示「正在重试」——最省事，但与你已批准的那句话不符

**每个选项的后果**：A——信息够用但等待时长未知，60 秒的等待仍像黑箱；B——用户知道还要多久，代价是 4 个字段；C——回到「不知道在等什么」，等于把已批准的体验打折。

**可逆性**：不可逆——写进历史后，旧记录补不回这些字段。

**依据强度**：已批准的卡片要求显示「约 N 秒后」，没有这些字段就做不到（`F-4`、`F-10`）。

**已定（2026-10-29）**：**B**。字段清单：`attemptInRequest`、`maxAttempts`、`plannedWaitMs`、`retryAt`。

#### D-6 失败的尝试要不要单独留痕（已定：B）

**背景**：现在只有「拿到完整回复、但被丢弃」的尝试才留下用量记录。连接被拒、DNS 失败、服务端返回里没有用量的限流——这几种**完全没有痕迹**。结果是：系统重试了 5 次，账本里查不到任何一次，事后无法复盘，也无法解释费用。

**要决定什么**：

- A：维持现状（只有拿到完整回复才记）
- B：每次尝试都留一条记录；没拿到用量时显式标「未报告」（推荐）
- C：每次尝试都留一条，没拿到用量就按 0 计

**每个选项的后果**：A——零用量故障仍然无痕，本方案的预算与卡片验收都缺账本支撑；B——能复盘、能对账，代价是统计里出现「未报告」这个新状态（用户可能会问那是什么）；C——数字好看，但**把未知当成 0**，会让人以为没花钱，实际已经扣费。

**可逆性**：不可逆——历史一旦按 A 写入，后面补不出当时失败了几次。

**依据强度**：`F-6` 已核实「无 usage 的失败尝试当前没有记录」；这是本方案 `INV-2`、`INV-9` 成立的前提。

**已定（2026-10-29）**：**B** —— 每次尝试都留一条记录，未拿到用量时显式标「未报告」。

### 不需要你决定（Agent 已查证或负责）

- 重试是否让模型知道：**不让**（已定）。重试不进入发给模型的对话，模型侧仍是"一次请求、一次响应"（`INV-7`）。
- 哪些错误该重试、哪些绝不该重试：见 §2.3 分类表，依据是现有实现 + 明确排除项。
- 重试期间用户取消怎么办：立即停止等待，沿用现有可取消机制（`F-5`）。
- 每次重试是否要单独记账：已实现，本方案不改（`F-6`）。
- 会不会重复执行工具：不会。工具执行与模型请求是两回事，本方案只动模型请求（`INV-1`）。

## 第 1 层：概要 【人机共读】

### 1.1 现状

| 故障类型 | 现在试几次 | 两次之间等多久 |
|---|---|---|
| 服务端太忙 / 服务端出错 / 网络断 | 3 次 | 服务端给了等待时间就等（但硬砍到 30 秒），没给就**立即重发** |
| 模型流静默超时 | 2 次 | 立即重发 |
| 上下文超长 | 2 次 | 立即重发 |
| 认证失败 / 参数不对 | 0 次（正确） | — |

三处「几次」和两处「30 秒」都是写死在代码里的（`F-2`、`F-3`）。上游方案声称已实现「指数退避 + 抖动」，实际没有（`F-7`）。

### 1.2 要改成什么

1. **加入递增等待与随机抖动**（避免多个会话在同一毫秒一起重发）。
2. **按 `D-1` 调整次数**。
3. **放开单次等待上限**（按 `D-2`，两处一起改）。
4. **加入整轮总等待预算**（按 `D-3`），到点明确放弃。
5. **保持**：adapter 自身不重试（现状正确——重试次数必须集中在一处才数得清）、取消可立即打断等待。**注：**「每次尝试独立记账」不是现状——现有实现只有拿到完整响应的路径才留用量记录（`F-6`），本方案新增 `provider-attempt-result` 补齐（§2.5.2）。
6. **可见性按 `D-4` 分开**：重试过程对用户可见（聊天流里一行状态卡片）；对模型不可见（痕迹不进对话上下文）。

### 1.3 排除方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 让各家服务商的 SDK 自己重试 | **排除** | 请求次数会被藏起来，账目不可核，且不同 SDK 策略不一（现状已在上层统一，方向正确） |
| 无限重试（`always` 模式） | **排除** | 费用不可控，用户无法感知 |
| 跨服务商自动切换 | **排除** | 不同模型的工具格式、上下文长度、能力不同，切换会导致行为漂移；需独立设计 |
| 对认证失败也重试 | **排除** | 把配置错误伪装成延迟，用户更难排查 |
| 只调次数不加等待 | **排除** | 立即重发对上「按分钟限流」的服务无效，等于浪费次数 |

### 1.4 主要风险

1. **变慢**：最坏情况下一次回合多等约 60 秒（`D-3` 兜底）。缓解：总预算到点即放弃。
2. **放大费用**：重试的是模型请求，每次都可能产生用量。**现有实现只在获得完整响应时记录用量**，无 usage 的失败尝试没有记录（`F-6` 已更正）。本方案把「每次尝试都必须有审计记录」补成 `INV-2`，但**不能**据此声称费用已完全可对账：未报告的用量是**未知**，不是 0。
3. **抖动引入不确定性**：测试难写。缓解：等待实现接受可注入的时钟/随机源（`AC-4`）。
4. **两处上限漏改**：只改一处会导致「宿主允许 60 秒、实际仍被砍到 30 秒」。缓解：`AC-2` 直接断言最终生效值。

## 第 2 层：规格 【机｜人工可跳过】

### 2.1 不变量

| ID | 不变量 | 为什么 | 违反时表现 | 验证 |
|---|---|---|---|---|
| `INV-1` | 重试只发生在「响应未被接受」之前；已被接受的响应（含流中途）不得重发 | 重发会重复工具调用或产生双份输出 | 用户看到重复内容；工具被执行两次 | `AC-3` |
| `INV-2` | 每次尝试（**含无 usage 的传输失败**）都必须有一条可关联的审计记录；审计完整性与是否收到用量无关 | 否则零用量故障（连接拒绝、DNS 失败、无 usage 的 429）会毫无痕迹 | 重试了 5 次，账本里却查不到任何一次 | `AC-5` |
| `INV-9` | 实际用量只在收到 usage 时累计一次；未收到记为「未报告」，**不得补零、不得推算** | 补零会把未知伪装成确定，并让费用统计失真 | 统计显示 0 token，实际已产生费用 | `AC-5`、`AC-21` |
| `INV-3` | 等待必须可被取消，取消后立即停止且不再发起新尝试 | 用户点了取消还在等 | 取消失效 | `AC-6` |
| `INV-4` | **计划**等待有上界（等待余额）；计划等待**超过**余额时放弃并返回可重试的明确错误；**恰好等于**余额时允许等待并执行该次已安排的尝试（等待后不复查、不中途放弃）。实测超支只记录事实，不追溯已安排的尝试 | 否则规格与验收会给出两种结果（到点放弃 vs 允许成功） | 同一场景两种实现都自称合规 | `AC-7`、`AC-14` |
| `INV-5` | 认证/授权/参数类错误不重试 | 配置错误不该被延迟掩盖 | 用户等 60 秒后看到「认证失败」 | `AC-8` |
| `INV-6` | 重试次数的唯一决定处是宿主策略；adapter 不得自行重试 | 两处计数必然对不上 | 实际尝试次数超过配置 | `AC-9` |
| `INV-7` | 重试痕迹（含次数、错误类别、失败尝试）不得进入发给模型的对话消息 | 会让模型处理与任务无关的基础设施噪音，并破坏「一条助手消息对应一次请求」的配对假设 | 长任务里模型被大量「重试」消息干扰；历史重建出现有请求无响应的空洞 | `AC-11` |
| `INV-8` | 重试状态必须对用户可见：进行中与最终失败都要有可见呈现 | 界面静止 60 秒会被当成卡死 | 用户以为程序挂了，强行重启 | `AC-12` |

### 2.2 状态与所有权

本方案有**三个必须分开**的计数器。上一轮写成「专用恢复独立、三者互不影响」，与 `D-1` 的「5 次总尝试（含首次）」直接冲突——**本轮统一为：物理尝试总额共享，分类计数只决定该类型还能不能再试**。

| 计数器 | 作用域 | 初值 / 上限 | 递增规则 | 唯一 writer |
|---|---|---|---|---|
| **物理尝试序号** | 每次模型请求 | 从 1 起，上限 **5**（含首次，即最多 4 次重试） | **每次真正发出请求** +1 | 内核 |
| **分类恢复计数** | 每次模型请求 | effort / 静默超时 / 溢出各 1 次；瞬时最多 4 次 | 该类型每被使用一次 +1 | 内核 |
| **等待余额** | 整个回合（invocation） | 60000 ms（`D-3`） | 每次等待后按**单调时钟实测量**扣减，下限钳 0 | 内核 |

**三者的关系**（R1 的解法）：
- 分类计数只回答「这一类恢复还能不能用」，**不解除**物理总额；
- **物理总额是硬上限**：混合序列（如 effort → 429 → 静默超时）中，物理请求数到 5 即停，无论分类计数是否还有余量；
- 因此**删除"三者互不影响"的说法**——它与 `D-1` 不相容，也与现状不符：现有代码里 effort、静默超时、溢出**共用同一个** `providerAttempt`（`F-11`）。

**为什么余额由内核持有**：只有内核知道等待实际持续了多久（定时器可能被事件循环延迟，也可能被取消提前打断）。若由宿主持有，它只能拿到「计划等待量」——那会把「安排等 40 秒、实际取消于 5 秒」记成 40 秒，与 `INV-3` 的取消语义冲突。

**端口契约**：`recoverProviderAttempt` 输入增加三项——
- `waitBudgetRemainingMs`：当前余额
- `attemptInRequest`：物理尝试序号
- `recoveryCounts`：`{ transient, idleTimeout, overflow, effort }` 各自已用次数

输出增加两项——
- `plannedWaitMs`：决定等待的毫秒数
- `recoveryKind`：`'transient' | 'idle-timeout' | 'overflow' | 'effort'`；内核据此递增对应分类计数并写审计

**专用恢复与余额**：静默超时、溢出、effort 通常不等待（0 ms），**不消耗等待余额**，但**消耗物理尝试序号**（因为它们也真的发出了请求）。

**边界动作（唯一动作，不再分叉）**：
- `计划等待 > 余额` → 不等待，直接拒绝（`PROVIDER_RETRY_BUDGET_EXHAUSTED`），带可重试时间
- `计划等待 == 余额` → **允许**等待；等待结束后**不再复查余额**，直接发出该次已安排的尝试（允许它成功）——与 `INV-4`、`AC-7`、`AC-14` 统一
- 实测超过计划（事件循环延迟）→ 余额**钳 0** 并记录超支事实；**不影响**已安排的尝试
- `余额 <= 0` → 不再安排任何等待（即使服务端只要求 1 秒）

| 事实 | 唯一 writer | 唯一提交点 | 恢复者 |
|---|---|---|---|
| 重试记录与用量 | 内核（每次尝试落一条 `provider-attempt-result`，见 §2.5.2） | 尝试结束后立即 | 按幂等键去重的历史重放 |
| 重试卡片的显示状态 | 内核（经观察端口上报） | 安排时 / 终结时（见 §2.5.1） | 以账本事件为准，界面不自行推算 |

**不允许**：adapter 内部计数；界面自行推算「已重试几次」；重试事件写入对话消息；宿主用「计划等待量」替代实测量。

**可见性三档**（本方案的定位）：

| 档 | 内容 | 本方案 |
|---|---|---|
| 模型可见 | 发给模型的对话里出现重试痕迹、次数或错误类别 | **否**（`INV-7`） |
| 用户可见 | 聊天流里的重试卡片（进行中 / 失败） | **是**（`INV-8`） |
| 审计可见 | 账本里的每次尝试记录与用量 | **本方案补齐**：新增 `provider-attempt-result`（§2.5.2）；现状只有完整响应路径有记录，零用量失败无痕 |

### 2.3 错误分类（决定是否重试）

| 类别 | 是否重试 | 示例（业务说法） |
|---|---|---|
| 瞬时可重试 | 是 | 服务端说你请求太快、服务端自己 5xx、连接被重置、DNS 暂时失败、流静默超时 |
| 输入/配置永久错误 | 否 | 请求格式非法、模型不支持该参数 |
| 凭据/授权错误 | 否 | 密钥无效、无权限 |
| 特殊兼容恢复 | 走既有专用分支 | 思维档位不被支持 |
| 上下文溢出 | 走既有专用分支 | 超长（已有独立预算） |
| 用户取消 / 回合超时 | 立即停止 | — |
| 流格式非法 | **默认不重试** | 事件序列非法、重复工具 ID；只有被证明是传输截断才允许恢复 |

### 2.4 退避参数与裁决顺序

| 项 | 取值 | 说明 |
|---|---|---|
| 基础等待 | 500 ms | 第 1 次重试前 |
| 倍增 | 2× | 500 / 1000 / 2000 / 4000 |
| 单次退避上限 | 8 s | 指数增长封顶（**不是**服务端等待上限） |
| 抖动 | 全额抖动（0～计算值） | 避免同步重试 |
| 最大尝试次数 | 5（含首次，即最多 4 次重试） | 超过 5 需同时改内核钳制（`F-1`） |
| 单次等待上限 | 60 s（`D-2`） | 服务端要求的等待也受此约束 |
| 回合等待总额 | 60 s（`D-3`） | 按实测量累计 |

**三个值必须分开保留**（B2 的核心）：`serverAskedMs`（服务端原始要求，**不钳制**）、`singleCapMs`（60 s）、`remainingMs`（余额）。现有实现把服务端要求直接钳到 30 秒后返回（`F-9`），原始值就此丢失——既无法执行 W4，也给不出真实的可重试时间。

**裁决顺序**（固定，不允许实现自行调换）：

1. 算本地退避：`localBackoff = min(8s, 500ms × 2^(重试序号-1))`，再在 `[0, localBackoff]` 内取随机抖动
2. 算候选等待：
   - 服务端给了 `serverAskedMs` → `candidate = max(serverAskedMs, localBackoff)`
   - 没给 → `candidate = localBackoff`
   （取 `max` 而非「服务端优先」：服务端说 1 秒时立刻重发几乎必然再被拒，白耗一次尝试）
3. `candidate > singleCapMs` → **不重发**，终止并返回 `PROVIDER_RETRY_AFTER_EXCEEDS_SINGLE_CAP`，携带 `retryAt = now + serverAskedMs` 与 `serverAskedMs`
   （不把 120 秒钳成 60 秒再试：W4 要求不静默截断，且提前重发几乎必然再次被拒）
4. `candidate > remainingMs` → **不重发**，终止并返回 `PROVIDER_RETRY_BUDGET_EXHAUSTED`；有服务端提示时同样携带 `retryAt`
5. 否则安排等待 `candidate`；实际等待结束后按实测量扣减余额

**时间字段语义**：
- `retryAt` 只在服务端给出等待提示时提供，表示**服务商要求的最早可重试时刻**
- 没有服务端提示时只说「稍后重试」，**不编造具体时间**（本地退避是估计，不是服务商保证）

### 2.5 失败与恢复

| 窗口 | 现象 | 唯一恢复动作 |
|---|---|---|
| W1 等待中被取消 | 定时器清除 | 立即抛取消，不发起新尝试 |
| W2 等待中进程退出 | 无新尝试 | 回合按既有「中断」收场，不自动续 |
| W3 等待需求超过余额 | 按 §2.4 第 4 步判定 | 不等待，终止并给 `retryAt`（若服务端有提示） |
| W4 服务端要求超过单次上限 | 按 §2.4 第 3 步判定 | 不等待，终止并回传**原始** `serverAskedMs` 与 `retryAt`，不静默截断 |
| W5 重试成功后仍有被丢弃的尝试 | 丢弃尝试的用量按已实现路径记录 | 沿用 |
| W6 「重试已安排」事件追加失败 | 无法向用户证明重试已登记 | **不得静默继续等待**：中止重试，按历史追加失败收场（见 §2.5.1） |

### 2.5.1 事件时序、卡片关联与终态

**问题**：现有实现先 `await waitForRetry(...)`、再写「重试已安排」事件（`F-10`）。照这个顺序消费事件，卡片只能在等待**结束后**出现——最长 60 秒的空白依旧存在，`INV-8` 等于没实现。

**固定时序**（不可调换）：

1. **决定重试**：策略层按 §2.4 裁决出 `plannedWaitMs`
2. **追加「重试已安排」并投影**：先落库、再让卡片可见
3. **开始等待**（单调时钟实测）
4. **执行尝试**
5. **追加尝试结果并收敛卡片**（成功 / 失败 / 取消 / 中断）

**为什么必须先追加再等待**：等待最长 60 秒。若先等待，用户整段等待里看不到任何东西；而且「等待中取消」根本不会产生安排事件，事后无法解释卡片为何存在过。

**事件字段**（支撑已批准的卡片；字段清单与批准状态见第 0 层 `D-5`）：

| 字段 | 用途 |
|---|---|
| `requestId` | 关联键：`${invocationId}:round:${modelTurn}` |
| `attemptInRequest` / `maxAttempts` | 卡片显示「第 2/5 次」 |
| `plannedWaitMs` | 卡片显示「约 N 秒后」 |
| `retryAt` | 仅服务端给出提示时出现（可选） |
| `code` | 稳定错误类别码 |

**卡片身份与终态**：
- 身份 = `requestId`；**同一请求的多次重试共用一条卡片、原地更新**，不刷屏
- 跨 modelTurn 是新的 `requestId`，因此是新卡片
- 终态推导（唯一，不留二选一）：
  - 后续尝试成功 → 「已恢复」，默认折叠
  - 尝试耗尽 / 超单次上限 / 超余额 → 「重试失败」+ 原因
  - 回合取消 → 「已取消」
  - invocation 中断或进程退出 → 重启后不得残留「重试中」，按既有对账标为「已中断」

**等待前追加失败**（W6）：`provider-retry-scheduled` 追不进去时**不得静默执行**——那会让用户看到一次没有任何记录的重试。按历史追加失败收场（中止重试并报错），与「不确定的终态不能猜」一致。

### 2.5.2 尝试结果与卡片终结契约

**事件**：新增 `provider-attempt-result`。不复用 `model-attempt-discarded`——后者要求有完整 response 与 usage，纯传输失败根本进不去（`F-12`）。

| 字段 | 取值 | 说明 |
|---|---|---|
| `requestId` | 字符串 | 关联键，与「重试已安排」同值 |
| `attempt` | 整数 | 计划或实际的物理序号 |
| `physical` | 布尔 | `true` = 真的发出了请求；`false` = 只做了决策（拒绝 / 取消），**不增物理计数** |
| `recoveryKind` | `transient` / `idle-timeout` / `overflow` / `effort` | 该次由哪类恢复触发 |
| `outcome` | `succeeded` / `failed` / `discarded` / `not-dispatched` | 终态 |
| `errorClass` | 稳定大写码，可选 | 如 `PROVIDER_RATE_LIMIT`、`PROVIDER_RETRY_AFTER_EXCEEDS_SINGLE_CAP` |
| `usage` | `{ status:'reported', …tokens }` / `{ status:'unreported' }` / `{ status:'none' }` | `none` 只用于 `not-dispatched` |
| `retryAt` | 毫秒时间戳，可选 | 仅服务端给过等待提示时出现 |

**幂等与去重**：幂等键 = `${invocationId}:${modelTurn}:${attempt}`。重放同一结果按幂等键跳过；用量累计时同样按 attempt 去重。

**唯一累计点**：用量只由本事件的 `reported` 分支累计**一次**。既有 `model-attempt-discarded` 若同时存在（有 response 的丢弃路径），二者按 attempt 去重，**不得重复累计**。

**未实际发请求的终结**（R3 的反例）：
- 首次即超单次上限（策略直接拒绝，**没有**「重试已安排」事件）→ 仍写一条 `provider-attempt-result`：`physical=false`、`outcome='not-dispatched'`、`errorClass` 为拒绝码、`usage.status='none'`。卡片据此显示「重试失败」，不必靠安排事件反推。
- 等待中取消 → 同样写 `not-dispatched`（`errorClass='TURN_CANCELLED'`），**不增加物理尝试数**；卡片收敛为「已取消」。

**旧账本重放**：缺 `provider-attempt-result` 的历史，卡片重建退化为「只显示已知的安排记录」，**不推断结果、不补写、不猜成功或失败**。

**追加结果失败**：与 W6 同规矩——不得静默继续；按历史追加失败收场，并把卡片置为「结果未知」，**不得写成成功**。

**外部依赖与交付边界**：
- 卡片的容器与折叠交互由压缩方案的「系统操作卡片」提供，本方案只新增条目类型
- 若压缩方案未落地：阶段 4 要么自带最小卡片（成本增加、需重新评估），要么推迟；**不得**只写后端而不给反馈（`INV-8`）

### 2.5.3 新增事件的影响面与迁移

`provider-attempt-result` 是**新增事件 kind**（已定，2026-10-29）。已核实其落地位置与影响面：

| 层 | 位置 | 需要做什么 |
|---|---|---|
| 类型定义 | `packages/agent-sdk/src/history.ts` 的 `HistoryEvent.kind` 联合类型 | 增加一个成员（TS 联合，无运行时枚举） |
| 存储 | `electron/database/schema.ts` 的 `agent_history_events`（`kind TEXT NOT NULL`） | **无需迁移**：kind 列是自由文本、无 CHECK 约束，旧库可直接写入 |
| 读取与组装 | `electron/runtime/sqliteAgentHistory.ts`（约 443、446 行） | 识别新 kind 并映射到对应账本字段 |
| 投影校验与修复 | `electron/runtime/sqliteAgentHistory.ts`（约 1882–1894、2019 行） | 决定是否需 `requestUsage` / `requestRetry` 账本，以及修复路径是否覆盖 |
| 账本外发 | `electron/sessionLedgerOutbox.ts`（约 182、191 行） | 增加投影分支 |
| 观察者关联 | `electron/runtime/agentSdkDesktopObserver.ts`（约 427 行） | 按 `requestId` 关联到对应请求 |
| 卡片重建 | 界面侧 | 读取新事件重建终态 |

**风险：漏改是静默失效，不是报错。** 上述消费点都是 `if (kind === '…')` 的加性判断，未知 kind 通常被直接忽略——事件虽已写库，但投影、修复、卡片都读不到它。因此不能靠"没报错"判断接入完整。

**验收要求**：新 kind 必须在**每一个**消费点被显式识别（`AC-28`）；旧账本缺该事件时的行为由 §2.5.2 定义（不推断结果）。
