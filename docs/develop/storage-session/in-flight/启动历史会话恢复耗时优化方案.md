# 启动时历史会话恢复耗时优化方案

> 状态：草稿（未实施）｜日期：2026-10-17｜源码核对基线：`c01116c8`（2026-10-17）
> 范围：`electron/main.ts` 启动历史恢复、`electron/runtime/sqliteAgentHistory.ts` 历史分类与恢复、对应 SQLite 表及维护生命周期。
> 篇内路由：负责人先读第 0 层与 §1；实现者读 §2–§7；复核证据见附录。

## 第 0 层：决策界面【人必读】

**一句话：** 启动时只处理能确认尚未结束的对话；历史对话的后台运行记录，等某项功能实际需要时再检查那一个对话并补上确实缺少的记录。正常启动不逐一检查所有旧对话。

**只有 3 分钟的话：** 先读 §1 推荐方向、§3 根因、§5 技术方案。

### 决策状态

本方案按“发现确切问题就当场修复”设计，不要求用户在“所有旧对话修完”与“跳过修复”之间选择：

- 启动入口只处理索引明确标记为未结束的对话回合。
- 当上下文、压缩回放或审计等功能需要后台运行记录时，只检查当前对话；确认属于旧进程遗留的开放记录才收口，确认缺少记录才补齐。正在运行的回合保持开放。
- 普通聊天历史继续从数据库读取，不等待其他对话的后台记录。

### 需要你决定的事项

**某个旧会话的事件记录文件已经不存在时，是否允许用现有对话记录生成一个新的事件记录文件？**

这个文件保存对话正文之外的工具运行、上下文和审计信息；部分内容只存在于此，无法从对话正文重新生成。

| 选择 | 用户能看到的结果 | 可逆性与代价 |
|---|---|---|
| A（推荐，默认） | 普通聊天历史仍可看；依赖该事件文件的上下文、压缩回放或审计功能暂停，直到找回原文件或另行批准恢复方式 | 找回原文件后可恢复；不会把缺项误报成完整记录 |
| B | 重新生成事件文件并恢复依赖功能 | 只会包含可从数据库重建的部分；缺失的工具/审计事实无法找回，后续可能基于不完整记录工作 |

依据是静态代码对照，尚未检查用户设备上的具体会话文件。默认采用 A；选择 B 需要接受历史附属事实可能永久缺失。

下钻：D-1 → §5.2 readiness 状态迁移、AC-3。

### 不需要你决定

- 如何记录未结束回合、如何确认后台记录完整、以及首次核对时如何只查一个会话，由工程侧设计并验证。
- 不删除历史对话、不清理聊天正文、不改变现有保留规则；数据库压缩不列为本轮方案。
- 当前方案根据代码给出结论和验收要求；用户设备上的具体记录规模与启动日志尚未核验。

## 1. 概要【人机共读】

### 1.1 验收边界

| 当前环境可验证 | 需要真实安装环境或用户运行日志 |
|---|---|
| 代码调用顺序、SQLite 查询计划、活动工作表、单会话台账差异修复、崩溃续跑和隔离 | 用户当前数据库的迁移状态/异常数量、真实设备冷启动 p95、首次访问旧台账的实际延迟 |

当前没有读取用户数据库，也没有采集本次启动日志。源码可确定阻塞位置和随历史规模增长的工作；具体用户此次等待由哪一类待办主导，仍需用聚合日志验证。

### 1.2 目标与非目标

**目标**

- 缩短从数据库打开到主窗口显示的等待；启动等待不随已完成历史会话或延后修复积压量线性增加。
- 保证异常退出的对话最终被标记为中断；未确认的后台记录可精确续跑、不重复写入。
- 保持对话正文、消息身份、会话归属和现有路径授权规则不变。

**非目标**

- 删除历史、减少保留期、压缩或 VACUUM 数据库、改写历史正文。
- 更换数据库、重写会话事件协议或 IPC。
- 把普通历史正文清理任务当成这条启动提示的原因。该任务在打包应用中窗口工作阶段之后延迟启动，见 F-4。

### 1.3 推荐方向

采用两个各自触发、命中即修复的入口：启动时只处理明确未结束的对话；某个对话的上下文、压缩回放或审计功能需要后台运行记录时，只检查那个对话并修复有证据确认的缺项。正常启动不再检查所有对话的后台记录。旧库的一次性索引回填不得让后续启动重复扫描；未核验的对话在第一次需要时定向核验。

## 2. 现状事实卡【机｜人工可跳过】

### F-1：提示文字对应的启动阻塞点

`main.ts` 在 `canonical-history.classification` 与 `canonical-history.recovery` 前后显示“正在整理历史会话数据”，随后还调用 `reconcileSessionEventFilesDetailed(workDirState)`：该函数枚举 `sessions/` 下所有会话目录、读取每份 `events.jsonl`，并为未闭合的 turn/step/tool event 追加中断记录。主窗口在这些步骤之后创建，所以两类历史检查都可能给每次启动增加成本。

复核：

```text
rg -n "正在整理历史会话数据|canonical-history\\.classification|canonical-history\\.recovery|createMainWindow" electron/main.ts
```

### F-2：未结束 invocation 已有精确工作表；全量分类只是旧库的一次性回填

v50 的 `canonical_history_recovery_work` 已由 SQLite trigger 随新 stream/event 事务维护：新增无终态 stream 时加入；写入 completed/failed/interrupted terminal 后移除。启动分类游标是为已存在的旧 stream 回填这张工作表。回填完成后，正常启动只查工作表；但回填未完成期间，`listStartupRecoveryWorkset()` 会走兼容全量 stream 查询。该全量查询应被限制为一次性迁移路径，不能成为正常启动路径。

同一个 classifier 还会为每个带有效 `sessionLedger.location` 的旧 History event 登记 projection repair，即使没有先确认 `events.jsonl` 缺失对应项。因此该队列代表“可能要核对的投影”，不是准确异常集合；本方案建议取消对它的全历史启动回填，改为会话按需核验。

复核：

```text
rg -n "classifyLegacyProjectionRepairs|listStartupRecoveryWorkset|canonical_history_recovery_work_migration" electron/main.ts electron/runtime/sqliteAgentHistory.ts electron/database/schema.ts
```

### F-3：两处重复成本来自全局候选发现，不是异常修复本身

一处是 `recoverInterruptedInvocations()` 全量读取 pending projection repair，再在 JavaScript 中过滤退避期；另一处是 `reconcileSessionEventFilesDetailed()` 启动时逐目录读取所有 `events.jsonl`。后者会识别未闭合 turn/step/tool，并追加 synthetic interrupted/result event。两者都先检查全体候选再实际处理，和用户提出的“异常发生或会话被使用时直接处理该对象”不同。

建议启动只查未结束 invocation 表中的行；台账读取入口只检查请求会话的 canonical facts 与 event ledger。只有找到具体缺失/矛盾的 event ID 才调用对应幂等修复器。检查结果无差异时直接继续，不生成 repair 工作项。

复核：

```text
rg -n "getStartupRecoveryWorkSummary|listStartupRecoveryWorkset|FROM canonical_projection_repairs|await this\\.read\\(invocationId\\)" electron/runtime/sqliteAgentHistory.ts
```

### F-4：延迟的正文清理任务与当前提示不是同一任务

`session-content-cleanup` 在打包应用中由存储生命周期调度，初始延迟为 60 秒、间隔 15 分钟，每轮至多 2 个会话、每会话 1 个 100 行批次；安全数据库压缩则在主窗口创建之后启动。两者不对应 F-1 的启动提示。

复核：

```text
rg -n "session-content-cleanup|initialDelayMs: 60_000|batchSize: 100|maxSessionsPerRun: 2|safe-db-maintenance|void createMainWindow" electron/main.ts
```

### F-5：已有优化和测量给出的边界

- v50 已新增持久化未完成恢复工作表、游标和 History 变更触发器；分类完成后，已完成的 History 增长不会进入恢复工作集。现有测试验证 128→640 条已完成 stream 时工作集保持不变，查询计划不扫描 `agent_history_streams/events`。分类尚未完成时仍走兼容路径。实现与历史测量详见[会话存储重构技术方案](../session-storage-refactor-technical-design.md)。
- 历史冷进程样本记录过：约 235.8 MiB 数据库的一次启动中，分类 373 ms、canonical-history 恢复 2,318 ms、台账 reconcile 10 ms；该样本为热文件系统缓存的单次观察，不是当前用户现状，也不是 p95。
- 历史合成测量中清理并 VACUUM 减少约 708 KB，但启动配对差中位数为 −2 ms，未证明启动改善。因此本方案不把数据库压缩当主措施。

复核：

```text
rg -n "v322|v323|247,304,192|canonical-history\\.classification.*373" docs/develop/storage-session/session-storage-refactor-technical-design.md
```

### F-6：本次真实规模和耗时归因未知

当前阶段计时已覆盖 `canonical-history.classification`、`canonical-history.recovery`、`session-ledger.reconcile` 和 `canonical-history.total`。但当前无法确定用户设备上各阶段的耗时分布、active workset/未确认 target 数量以及旧库回填是否已完成。不得将 F-5 历史单次样本外推成当前设备收益。

复核：

```text
rg -n "canonical-history\\.classification|canonical-history\\.recovery|canonical-history\\.total|session.history.recovery" electron/main.ts electron/startupTiming.ts
```

### F-7：旧版应用拒绝打开更高 schema version 的数据库

`runMigrations()` 在发现数据库版本高于当前应用支持版本时抛 `DatabaseUpgradeRequiredError`。若本方案新增 schema migration，不能把回滚到任意旧二进制当作可用回滚方式；必须把支持新 schema 的版本作为 rollback floor。

复核：

```text
rg -n "DB_SCHEMA_VERSION =|DatabaseUpgradeRequiredError|version > DB_SCHEMA_VERSION" electron/database/schema.ts electron/database/migrations.ts
```

### F-8：应用已有单实例进程锁，可用于建立进程代次边界

`app.whenReady()` 后调用 `app.requestSingleInstanceLock()`；未取得锁的第二实例立即退出。方案复用该进程互斥基础，再增加持久化 generation 与 writer 校验；generation、事件 owner 字段和 session readiness 表都是拟新增机制，不是当前实现。

复核：

```text
rg -n "requestSingleInstanceLock|second-instance" electron/main.ts
```

### F-9：台账索引包含可用于 readiness proof 的文件水位

`events.index.json` 记录格式版本、JSONL 最大 seq、eventCount、字节数和末条时间；sink 初始化时会将其与 JSONL 读取结果对照，JSONL 是事件提交边界，索引是可重建派生数据。新方案把这些字段与文件 identity/末尾帧校验值一起保存为 ready proof；索引领先于 JSONL 时按可能丢失已提交事件处理，索引缺失或落后时先完整核验目标 session，再重建索引。

复核：

```text
rg -n "formatVersion: 2|eventCount|lastAt|writeIndex" electron/sessionEvents.ts
```

### 绕过通道

`--safe-db-maintenance` 明确跳过本次启动的完整 canonical History 恢复，后续在窗口可用后运行压缩维护，并将恢复留给下一次普通启动。优化方案要保留该安全分支，不得让启动恢复或按需 ledger repair 与该分支的 compact 争用数据库或 spill root。

复核：

```text
rg -n "safeDbMaintenanceRequested|canonical full recovery skipped|runSafeDbMaintenance" electron/main.ts electron/storage/safeDbMaintenance.ts
```

## 3. 问题模型与候选根因【人机共读】

### 3.1 与源码相符的耗时来源

| 优先级 | 来源 | 如何延长启动 | 证据状态 |
|---|---|---|---|
| P1（旧库迁移期） | 未结束 invocation 工作表回填 | v50 游标每批回填最多 100 个旧 invocation；游标未完成期间，启动恢复走兼容全量扫描。回填完成后，新写入由 trigger 精确维护工作表 | 代码事实已核验，用户数据库 migration 状态待测；属于迁移成本，不应常态化 |
| P1 | 全历史台账核对 | projection recovery 物化全部 pending obligations；`session-ledger.reconcile` 还逐目录读所有 `events.jsonl`。健康会话也进入检查 | 代码事实已核验，用户库候选数和阶段耗时待测 |
| P2（按需触发后） | 首次打开某会话时核对该会话 | 首次访问需要台账的功能可能读取该会话的 History 与 JSONL；成本局限于一个会话，且只补实际缺失事件 | 目标方案，需测量单会话上限和损坏恢复边界 |

### 3.2 目前不应采用的解释

- “数据库文件太大，所以压缩就会变快”：F-5 的历史测量未证明此因果关系。
- “pending 数量就是用户可见异常数”：旧分类按有效 ledger location 登记义务，不验证对应事件是否真的缺失。目标方案应在具体会话入口核验，并只修实际差异。
- “整理提示来自旧正文清理”：该任务延迟启动且属于另一条调度链。

## 4. 目标状态与关键不变量【机｜人工可跳过】

### 4.1 目标状态

```text
DB 打开
  └─ 取得单实例进程锁，推进并持久化本进程 generation
       ├─ 旧 owner 被确认失去写权限，旧 process_generation 标记为 fenced
       ├─ 读取精确 active invocation 工作表并直接恢复命中项
       ├─ workset 命中的 session 在恢复完成前禁止新执行；其他 session 不等待
       └─ 主窗口显示
            └─ 某会话进入依赖台账的功能 / 开始新执行
                 ├─ 取得该 ledger_location_key 生命周期锁；若旧 owner 核查代次落后，只检查该 session 的开放项
                 ├─ 再检查台账投影就绪状态和本次新增 target
                 ├─ unknown → 只核验该 session 的 canonical facts 与 events.jsonl
                 ├─ 旧代开放项 → 按持久 owner generation 确认其 owner 已 fenced 后收口
                 ├─ 当前代 active registry 中的 turn/step/tool → 保持开放，不合成中断结果
                 ├─ 精确缺失投影 → 在本入口直接幂等补齐
                 └─ 无法安全核验或修复 → 只阻止该 session 的依赖操作，保留台账
```

本应用以单实例进程锁阻止第二个应用进程同时成为 writer；启动先取得锁，再单调推进并持久化 generation。每个 History / ledger writer 还须在写入前校验 fencing generation。持有旧 generation 的迟到 callback 被拒绝；无法取得单实例锁或 generation 校验失败时，不开放执行准入。新数据的未结束工作表由 History stream/event trigger 同事务维护，启动直接恢复工作表命中的项；旧代 ledger 开放项不做全目录扫描，在该 session 被使用时按 owner generation 定向收口。按需核验不得把“当前代仍活跃”解释成异常，也不能将“未知”当作“无异常”。

### 4.2 不变量

| ID | 不变量 | 机制与核验点 |
|---|---|---|
| INV-1 | canonical History 与正文不因提速而删除、跳过或改写 | 按需操作只补有 canonical 依据的确切缺项；前后 canonical fold、message ID 和 session owner 对拍 |
| INV-2 | 活动 invocation 被精确登记；只有失去执行所有权的旧代对象可被收口；本代仍活跃的 turn/step/tool 不会收到 synthetic terminal | History triggers 维护 active workset；进程代次与执行准入屏障；关闭前核验 owner generation；会话级 gate |
| INV-3 | 事件台账修复只写入已授权 workDir/session，且每个 target 幂等 | 继续使用现有 session 授权边界、scope 检查和幂等键；越界时 fail closed |
| INV-4 | 未经核验的未知/增量待处理台账、失败投影及仍有 writer 的台账不能被直接压缩或 retention 删除 | retention 候选先用同一 session gate 达到有效 `ready`，并与投影写入/修复共用生命周期锁；删除前重读 readiness、outbox 与 compaction 依赖 |
| INV-5 | 正常启动不随已完成历史或健康台账规模增长 | 启动只查询 active invocation workset；台账核验限定在实际使用的单个会话 |
| INV-6 | 用户可见历史读取不因事件台账尚未补齐而丢正文 | canonical reader 继续作为会话正文依据；依赖台账的能力须检查 readiness，不可回退成空历史 |
| INV-7 | `ready` 只证明指定 canonical 水位已完整投影到指定 ledger generation；任何新义务、sink 失败或文件修复都会使证明失效 | 持久化 session projection state；每次依赖操作核对当前水位、generation 与 pending targets |

### 4.3 状态所有权

| 状态 | 唯一 writer | 持久点 | 恢复者 |
|---|---|---|---|
| unfinished invocation workset / active owner | History writer 在 invocation 开始时登记 `owner_generation + running`；进入终态收口时写 `settling`；终态 History event 与删除/销项在同一事务 | `canonical_history_recovery_work(invocation_id, session_id, owner_generation, execution_state)` | 启动 fencing 后只直接处理旧 generation 的行；terminal trigger 同事务销项；本代按 invocation/session 匹配 active owner |
| 旧库 active workset backfill | 单调迁移 cursor | `canonical_history_recovery_work_migration` | 后台续跑；旧会话首次恢复前可定向核验 |
| 进程执行所有权 | Electron 单实例锁持有者推进唯一 generation；所有 History / ledger writer 写入前校验 generation；新执行必须经准入屏障 | SQLite process owner/fencing 状态及每个开放执行的 owner generation | 新进程先取得单实例锁并递增 fence；目标 session 读取时只收口 generation 已失效的旧对象；不能取得锁/通过校验时保持 blocked，不合成终态 |
| canonical→ledger 投影确认 | History writer 在 canonical 事务中登记义务；session event sink 按 session 生命周期锁写入并确认 | 精确到 `(ledger_location_key, canonical_event_id, projection_kind)` 的投影 outbox，包含 canonical 水位和该投影应有的 event identity 集合 | 目标 session 被使用时直接处理 target；只有 expected identity 集合全部存在且内容/顺序一致才能确认 |
| 会话台账就绪证明与旧 owner 核查水位 | session event sink / 核验器，均持有同一 session 生命周期锁 | `session_ledger_projection_state` 以 `ledger_location_key` 唯一定位；状态为 `unknown/checking/ready/dirty/blocked`，保存已核验/当前 canonical 水位、ledger generation、文件 identity/长度/末尾帧、`events.index.json` 的 seq/eventCount/bytes/lastAt、核验 token、retry scope、失败类别，以及独立的 `owner_reconciled_process_generation` | 崩溃遗留的 `checking` 由下次持锁者 CAS 回 `unknown`；`unknown` 首次使用时做完整对拍；`ready` 仅在 projection 水位、ledger/file/index proof 仍匹配且无 pending 时可复用；新增 target 进入 `dirty` 并增量消费；进程代次变化只触发目标 session 的旧 owner 开放项核查，不使 projection proof 失效；文件证明失效回 `unknown`，sink 失败进入可按 target 重试的 `blocked` |
| 会话事件台账 | session event sink；所有追加、修尾、修复、retention 删除遵守同一生命周期锁 | 每个 session ledger 的幂等 event identity 与 generation | 按会话串行处理；不能并发覆盖同一 writer；retention 仅在锁内复核后删除 |

`ledger_location_key` 精确绑定现有 ledger location `(authorized workDir, sessionId, createdAt)`，同一 session ID 在不同 profile root 或创建日期下不会串用状态；绝对路径不写入日志。`process_generation` 用来判断执行 owner 是否仍有效，`ledger_generation` 用来判断 `events.jsonl` 的文件版本，两者不可混用。每次进程启动会推进 `process_generation`；它本身不使 session ledger 的 ready proof 失效，否则每次启动又会触发全量 session 核验。另存的 `owner_reconciled_process_generation` 只记录某 session 已检查过哪些旧 owner generation。进程代次变化后，session gate 仅扫描被选中 session 的开放项，关闭 owner 已 fenced 的旧项并更新这条水位；只有该 session 所有开放项处置成功且 ledger file/index proof 已更新后才推进水位，否则保持旧值并阻止依赖操作。该核查不重做 canonical→ledger 全量投影核验。`ledger_generation` 仅在该 ledger 被替换、重写、截断/修尾或重建时递增。ready proof 覆盖已核验 canonical watermark、ledger_generation、文件 identity/length/tail-frame proof，以及索引的 `formatVersion=2/seq/eventCount/bytes/lastAt`。active workset 的 `execution_state` 只沿 `running → settling → terminal+销项` 有序变化；只有匹配当前 process generation 且处于 `running` 的行能证明事件仍活跃，`settling` 由 writer 完成终态后再释放 session 锁。

`canonical_history_recovery_work` 同时是 active invocation registry，不另建第二份活跃真相。executor 在开始时登记一条 `running` 行，进入终态收口时改为 `settling`，标准 terminal 与销项在同一事务提交。所有新写入的开放 turn/step/tool 与投影事件都携带 `owner_generation` 并关联 invocation_id。只有同时匹配当前 generation 且 workset 行仍为 `running` 的对象才视为活跃；只有低于当前 fencing generation、且 owner 已被单实例锁释放所证明为失效的记录才可收口。迁移前没有 `owner_generation` 的 legacy 开放记录一律视为“旧代、待该 session 首次核验”，不得仅凭它仍开放就在当前回合读取中关闭；首次 session gate 在持有锁并完成旧代 fence 后收口这些记录。同代但没有匹配 running workset 行、又没有 canonical terminal 可投影的开放记录进入 `blocked`，不猜测性生成终态。进程级锁保证 writer 不会跨进程重叠，单调 generation 校验用于拒绝释放锁后迟到的旧 callback。

开放事件的处置判据：

| 证据 | 处置 |
|---|---|
| 当前 `process_generation`，对应 workset 为 `running` | 保持开放；不能写 synthetic end/result |
| 当前 generation，对应 workset 为 `settling` | session 生命周期锁由终态 writer 持有；依赖读取等待该写入完成，不能并行收口 |
| 对应 invocation 已有 canonical terminal，workset 已销项 | 按 terminal 与对应 canonical result/step facts 补齐确切缺失的 end/result；没有可对拍来源的开放项进入 `blocked` |
| owner generation 已被 fencing，且没有 canonical terminal | 直接将旧 invocation 的开放记录收口为 interrupted；禁止影响其他 invocation/session |
| 同代 workset 缺失且没有 canonical terminal | 进入 `blocked` 并报告 `active_owner_unresolved`；不能推断该回合已中断 |

## 5. 技术方案【机｜人工可跳过】

### 5.1 阶段 A：先补充安全聚合观测

每次启动记录以下聚合值，不记正文、绝对路径、session ID、invocation ID 或 tool ID：

- active workset 项数、旧库 backfill 是否仍 pending 及其耗时；
- 启动恢复直接处理的 invocation 数与耗时；
- 按需台账核验的 session 数、检查 event 数、实际缺项数、修复结果与耗时；
- 全局启动耗时中分类、History 恢复和 `session-ledger.reconcile` 各阶段的耗时。

先收集至少 10 次正常启动和 3 次冷进程样本，按版本、系统、数据库大小分桶汇总 p50/p95。数据库大小只记分桶，不记录本地路径。用现有 `[startup]` 阶段日志配合 `session.history.recovery` 聚合日志；不得读取或导出用户消息内容。

### 5.2 阶段 B：用精确触发入口替代全历史待办扫描

1. **异常退出入口：** 保留 v50 `canonical_history_recovery_work`。新 invocation 开始事务写入 owner generation 与 `running`；新 stream 写入时 trigger 登记未终态项；进入收口阶段先标 `settling`；写入 canonical terminal 时同事务销项。启动只查询这张索引工作表，并直接恢复旧 generation 返回的项。历史回填完成后，正常启动不得再访问全量 `agent_history_streams/events`。
2. **执行所有权入口：** 每次进程启动先取得 Electron 单实例进程锁，再在数据库事务中递增 generation。只有单实例锁确认前一进程已退出、且旧 generation 已失效后，才能收口该代开放对象。未结束 invocation 从精确工作表在启动期直接恢复；旧代 ledger turn/step/tool 在目标 session 首次 gate 时定向收口。无法取得单实例锁或 generation 校验失败时，不开放执行准入，也不猜测性地追加中断结果。
3. **会话台账入口：** `readCompactionReplay`、`ContextMeter` 等依赖台账的功能先取得 `ledger_location_key` 生命周期锁，读取持久 `session_ledger_projection_state`。若 `owner_reconciled_process_generation` 落后于当前 generation，只扫描该 session 的开放项并收口已 fencing 的旧 owner；成功后更新 owner 核查水位，这一步不重做 canonical→ledger 全量对拍。之后按 canonical watermark / ledger generation / pending targets 核验投影状态。`ready` 只能在水位匹配、ledger_generation 匹配、file identity/length/tail-frame proof、`events.index.json` 的 `seq/eventCount/bytes/lastAt` 仍匹配且没有未确认 target 时复用；process_generation 变化本身不触发 session 全量投影核验。支持的文件替换、重写及修尾路径必须递增 ledger_generation。若文件元数据不可读取、身份不匹配、尾帧校验不符或索引落后于 JSONL，则状态回到 `unknown` 并完整核验该 session；索引记录领先于 JSONL 时说明已提交事件可能丢失，状态进入 `blocked/baseline`。`unknown` 必须完整核验，即使 outbox 为空或 JSONL 可解析也不能快捷返回。
4. 新 canonical fact 在同一 SQLite 事务中：递增该 session 的 projection watermark，写入精确 outbox projection key 及 expected event identity 集合；若原状态是 `ready`，置为 `dirty` 并保留旧 verified watermark，若为 `unknown`/`blocked` 则维持原状态。sink 成功后，对全部期望事件核对 identity、归属、内容与顺序，再确认 outbox；该 session 所有待处理 target 均成功且文件 proof 有效时，将 verified watermark 推进至当前水位并设为 `ready`。append 成功但 ack 前退出时，重开后只核验命中的 target；已经齐全则确认，不重复追加。完整基线核验持有同一 session 锁，因此 canonical write 不能并发越过核验；若锁外有迟到的旧 ack，CAS 拒绝它。
5. 多事件投影按 `(ledger_location_key, canonical_event_id, projection_kind)` 管理完整 expected set；一个 canonical fact 可为不同 projection_kind 创建多项 outbox。每个 expected event 有稳定业务 identity；完整集合逐项核对 identity、payload 和顺序后才可 ack。已存在但 payload 不同、同一 identity 重复或顺序矛盾都进入 `blocked`，不覆盖旧数据、不追加冲突副本。具体映射如下：

| canonical fact / projection kind | ledger identity 与完整条件 | 冲突处理 |
|---|---|---|
| `model-request-started / request` | `(requestId, attempt)` 的 `request_header` 与初始 `request_context` 各一条，payload 中 request/turn/attempt 一致 | 缺任一项则补齐；重复或字段不一致则 blocked |
| `provider-retry-scheduled / retry` | `(requestId, attempt)` 一条 `request_retry`，code/backoff 与 canonical fact 一致 | 重复或字段不一致则 blocked |
| `model-response-committed / usage`、`model-attempt-discarded / usage` | `(requestId)` 一条 `request_usage`，turn 与 usage 一致 | 重复或字段不一致则 blocked |
| `model-response-committed / tool-proposals` | canonical sidecar 中每个 `toolUseId` 对应一条 `tool_call`，name/args 与 model response 一致；expected set 全部存在 | 缺项补齐；多余、重复或 payload 不一致则 blocked |
| `model-response-committed / final-context` | `(requestId, attempt, projectionStage=final)` 一条 `request_context`，turn/context usage 一致 | 重复或字段不一致则 blocked |
| `tool-call-finished` / `tool-call-not-dispatched / result` | `(toolUseId)` 一条 `tool_result`，step/turn 与 canonical result sidecar 一致 | 重复或字段不一致则 blocked |
| `invocation-completed` / `invocation-failed` / `invocation-interrupted / terminal` | `(turnId)` 一条 `turn_start` 与一条匹配 reason/status 的 `turn_end`，且 start 在 end 前 | 缺项按组补齐；重复、终态矛盾或缺少可验证 start 依据则 blocked |
| `transcript-compacted / compaction` | `(compactionId)` 一条 `compaction_start`、一条 `compaction_summary`、一条 committed `compaction_end`；顺序 start < summary < end，hash/window fingerprint 与 canonical envelope 相同 | 部分组保持 pending 并补齐；重复、次序或内容冲突则 blocked |

不属于 canonical projection 的 `step_start/end`、`assistant_chunk`、`session_end_seed` 等 ledger-only 记录不生成 canonical outbox。它们在首次 baseline 中作为原台账内容保留，并校验 JSONL 顺序/序号/完整性；缺少可重建 source 的记录不得自动补造。未知 session 的原台账缺失时不能证明这些记录仍完整，因此按 `blocked/baseline` 处理。
6. 文件替换、畸形尾部修复或 ledger_generation 重建使旧 ready proof 失效并令状态回到 `unknown`，随后对该 session 做完整核验；新 canonical watermark 产生精确 outbox 时进入 `dirty` 并只增量检查新 targets；从 `dirty` 进入 sink 写失败时设置 target retry scope，重试只处理失败 target，成功且其他 target 已 ack、文件 proof 有效时直接回 `ready`；处于 `checking` 的 baseline 修复失败时设置 baseline retry scope，重试完成后继续完整核验；身份/内容冲突进入 baseline retry scope 的 `blocked`，冲突解除后完整核验。受支持的 ledger 写入/替换均须通过单一 sink；ledger_generation、文件对象 identity、字节长度和末尾完整帧校验值组成 ready proof。未能证明文件对象仍是已核验版本时，将它视为 `unknown` 并做 session 全量核验。修尾必须在 session 生命周期锁内完成；修复后重新验证当前 session 的完整性，再将状态置为 `ready`。唯一 writer 负责持久化状态转换，使用 CAS/代次比较拒绝迟到的旧 ack。
7. 旧数据不预先为每个有 location 的 event 建立全局 repair 队列。`unknown` session 首次进入依赖台账的功能时，在该 session 范围内完整对比 canonical facts 与 ledger identities，只对实际缺项调用对应 ensure；健康项只建立核验水位，不产生修复写入。移除窗口前 `reconcileSessionEventFilesDetailed(workDirState)` 的全目录扫描。
8. session-scoped reconcile 按上方开放事件处置判据处理：当前代 `running` 对象保持开放；`settling` 对象等待终态 writer；已有 canonical terminal 的对象只按可对拍事实补齐；只有经 fencing 证明属于失效旧 generation 且无 canonical terminal 的对象才收口为 interrupted。新执行准入前先通过该 session gate，关闭该 session 已知旧代残留；后续同代上下文读取只检查 canonical 投影差异，不关闭当前执行。若同代开放项无 active owner 且无 canonical terminal，阻止该 session 的依赖操作，不猜测 synthetic result。canonical→ledger 缺项补齐与旧执行残留收口是不同判定，不得由一个“发现开放记录即关闭”的通用 reconcile 混做。畸形尾部按 fail-closed 规则处理，不能静默跳过或跨 session 扩散。

台账 readiness 的状态迁移固定如下：

| 当前状态 | 事件 | 下一状态与动作 |
|---|---|---|
| `unknown` | session 首次进入依赖台账功能 | `checking`；持锁完整对拍该 session |
| `checking` | 完整对拍、所有 expected projection 均通过 | `ready`；保存 canonical watermark 与 ledger file proof |
| `ready` | 新 canonical fact 与精确 outbox 同事务提交 | `dirty`；保留旧 verified watermark，只增量检查新 targets |
| `dirty` | 所有 pending targets 完整确认且 file proof 有效 | `ready`；推进 verified watermark |
| `checking` | repair/sink 失败、身份冲突、unknown ledger 不存在 | `blocked`，retry scope 为 `baseline`；恢复后重新做完整对拍 |
| `dirty` | 某 target sink 失败 | `blocked`，retry scope 为 `target`；只重试该 target，全部成功且旧 verified watermark proof 有效后回 `ready` |
| `ready` / `dirty` | 文件 identity、ledger generation、长度、末尾帧或索引 seq/count/bytes/lastAt 证明变化 | `unknown`；持锁重新完整对拍；索引领先于 JSONL 时 `blocked/baseline` |
| `checking` | 进程崩溃并释放 session 锁 | 下次持锁者 CAS 回 `unknown`，再完整核验 |
| `blocked` | 按 retry scope 重试成功 | `baseline` scope 回 `checking` 并重跑完整核验；`target` scope 回 `dirty` 处理剩余 targets，全部 ack 后回 `ready` |

`ready` 必须同时表示 canonical watermark 已完整对拍、expected projection 全部确认、ledger generation/file/index proof 未变化且无 pending target。缺失的 unknown ledger 无法证明其中原有 ledger-only 事件，进入 `blocked/baseline`；不得自动新建空台账并标记 ready。缺失或落后于 JSONL 的索引使状态回到 `unknown`；完成完整对拍后才可重建索引。索引领先于 JSONL 表明有已提交事件可能丢失，进入 `blocked/baseline`。canonical 正文仍可读，依赖事件台账的操作失败关闭。只有明确批准的数据恢复策略才能处理这类不可逆缺件。

### 5.3 阶段 C：两类异常入口直接处理命中的对象

1. **启动异常入口**先完成 process generation fencing，再读取 `canonical_history_recovery_work` 中的异常 invocation 并直接写唯一 interrupted terminal；触发器在 terminal 事务中移除工作项。workset 命中的 session 在该 invocation 收口前不能开始新回合；其他 session 不等待。无活动项时不访问已完成历史。
2. **按需台账入口**在目标 session 生命周期锁内先检查 `owner_reconciled_process_generation`。代次落后时只收口该 session 经 fencing 证明失效的开放项，然后核验 projection readiness：`unknown` 时完成该 session 的一次完整基线核验；`dirty` 时只核对精确新增 targets；`blocked/target` 只重试失败 target。实际缺项由同一入口直接补齐，齐全项直接 ack；无关 session 不被检查。
3. **旧代开放记录入口**只关闭 owner generation 已被 fencing 的 turn/step/tool。当前 generation 且 active invocation registry 中仍有匹配 owner 的 `step_start`、工具运行记录，即使暂时没有结束事件也属于合法活跃状态；上下文读取、压缩回放或审计读取不得为它们生成 interrupted / failed synthetic event。session 锁只负责串行化写入，不能充当 owner 已失效的证据。
4. 两类异常入口相互独立：active invocation 的 startup recovery 不等待未使用的事件台账；按需台账核验不扫描其他 session，也不要求先运行全局 classifier。启动 fencing 是安全准入条件，不是第三类历史扫描；它只核验当前 process owner 记录并收口确知已失效的旧代对象。
5. 旧库 active workset migration 作为一次性后台/按需回填推进。迁移未覆盖的 invocation 在允许其恢复/继续前按 session 定向核验；不得每次启动重复全库兼容扫描。保留 per-session writer、workDir/session 绑定、spill fence、retention 依赖和 cleanup fence。

### 5.4 调度与并发

| 工作 | 时机 | 并发与停止 |
|---|---|---|
| 进程代次 fencing 与旧代收口 | 创建本代 generation 后、允许新回合前 | 持有 Electron 单实例进程锁；只有确认旧 owner 已失效才收口；不确定时相关 session 保持 blocked |
| 已知未结束 invocation 恢复 | 完成旧代 fencing 后读取活动工作表；workset 命中 session 的新执行准入前复核 | 单写者，按 invocation 顺序；失败只阻止所属 session，其他 session 不等待 |
| 旧库 active workset 回填 | 窗口显示后后台续跑，或目标 session 首次恢复前定向回填 | 一个 classifier 实例；每批提交游标；不调用全量兼容恢复阻塞窗口 |
| session ledger 核验/修复 | 该 session 首次开始新执行、当前 process generation 首次读取该 session、某功能首次读取其 ledger，或 ready 水位出现新增 target 时 | 同一 `ledger_location_key` 生命周期锁串行化 owner 开放项核查、投影核验、写入、ack 与删除；current `running` owner 的开放记录不做中断收口 |
| ledger retention 删除 | 现有保留策略选中候选目录时 | 先取同一 `ledger_location_key` 生命周期排他锁；unknown/dirty/pending 使用相同的单 session readiness gate 核验/修复该候选，再复核 projection state、canonical watermark、file/index proof、active writer 和 compaction guard；只有 ready 且原保留条件成立才在锁内删除，核验失败则保留 |

`ledger_location_key` 锁由所有会产生或修复该 location 事件的 writer 共用：先取锁，再提交 canonical fact 与 outbox 的 SQLite 事务，之后追加 JSONL、确认 outbox/readiness，最后释放锁；ledger-only append、baseline 核验、修尾和 retention 删除也取同一把锁。锁覆盖单次持久化/核验操作，不覆盖整个模型或工具执行过程，因此 ContextMeter 可以在两个事件写入之间读取台账；此时 `running` owner 行保护当前回合的开放记录。

retention 状态规则如下：

| session ledger 状态 | retention 处理 | 释放依赖的唯一条件 |
|---|---|---|
| `unknown` / `checking` / `dirty` | 只有成为原保留策略选中的删除候选时，才持锁调用同一 session readiness gate；核验成功后继续原保留判断，失败则保留目录 | baseline 核验完成或所有增量 target 完整对拍并 ack，持久化 `ready` 水位；未被选中的 session 不触发核验 |
| 有 pending target / 活跃 writer | 候选核验可在锁内消费 pending target；仍有活动 writer 或 target 失败则保留目录 | 所有 target 完整对拍并 ack，writer 退出临界区 |
| `blocked` / terminal repair failure | 保留目录 | 修复重试成功并进入 `ready`；不能按空 outbox 自动放行 |
| `ready` 且水位/generation 有效 | 继续执行原有保留策略；仅在排他锁和既有 compaction guard 都允许时删除 | 删除操作在锁内完成并记录状态；随后新的 session 写入按既有会话生命周期规则处理 |

所有 session event profile roots 均适用该矩阵。retention 只核验它已选中的单个删除候选，不枚举所有 unknown session；它复用同一 session gate，不新增独立全局 repair 队列。首版不并行处理同一 session 的 ledger 文件；不同 session 只有在用户同时使用或分别成为 retention 候选时才可能分别触发核验。单个 session 的大 ledger 首次核验仍可能慢，需记录大小分桶和单项耗时。

## 6. 失败、迁移、回滚与未验证项【机｜人工可跳过】

### 6.1 失败场景

| 场景 | 处理 | 需证明 |
|---|---|---|
| 进程在 active-workset 回填中退出 | 当前事务回滚；游标从已提交位置继续。目标 session 在回填前被继续时执行定向检查 | kill/reopen 后无漏掉的未结束 invocation |
| 正常回合写入 `step_start` 后马上读取 ContextMeter / compaction replay | 读取入口识别当前进程 generation 的 active owner；只做 canonical 投影核验，不合成 interrupted step/turn/tool result | 活跃 step 保持开放，原执行可正常写入结束事件 |
| 工具运行中另一个同 session 审计/上下文读取到开放 tool_call | session 生命周期锁串行化读写；匹配的 active invocation registry 项证明该 tool 仍活跃，读取继续但不收口它 | 不出现 synthetic failed tool_result 或 interrupted terminal；旧代残留仍能在启动 fence 后收口 |
| 启动时发现旧代开放事件，但旧 owner fence 未取得 | 不写终态；拒绝该 session 的新执行并报告稳定 failure class，待 owner 可证明失效后重试 | fence 失败不会被 session writer 互斥误当成“旧代已死” |
| 进程在 canonical History 与 events.jsonl 双写之间退出 | 精确 target 的 outbox 保持未确认；该 session 下次进入台账功能时核验 event identity 并直接补缺/确认 | 注入两个写入边界退出；无重复事件、无跨 session 修复 |
| 旧 session 首次核验时 outbox 为空但 canonical-backed event 缺失 | 持久状态 `unknown` 优先于 outbox 为空；完整对拍发现缺项并修复后才写入 `ready` | 空 outbox、JSONL 语法有效不能使 unknown session 快捷通过 |
| 按需修复回调写入失败 | 精确 target 保持未确认；状态设为 `blocked` 并使 readiness 失效；当前依赖操作明确失败，后续该 session 再次使用时重试 | 无关 session 可继续；目标 session 不会静默使用部分台账；retention 保留目录 |
| session 已 ready 后新增 canonical fact，但 sink 追加失败 | canonical 事务同步增加 watermark/outbox 并使旧 ready 失效；后续读取消费新 target | ready 不会被缓存复用；重试只处理新增 target |
| compaction 多事件投影只追加了 start 或部分事件 | projection key 保持 pending；核验 expected identity 集合和顺序，补齐剩余事件后整体 ack；冲突则 blocked | 部分投影不被 ack；崩溃重开后无重复、无缺项 |
| ledger 文件替换、修尾、generation 或 index metadata 改变 | 持有 session 生命周期锁、使旧 ready 失效并重新核验；index ahead 进入 blocked/baseline | 旧 generation 的 ready proof 不被复用；CAS 拒绝迟到 ack |
| 某 session owner/workDir 漂移 | 该 session fail closed，不扩散到健康 session | 越界 callback/executor 不调用；健康 session 仍可恢复 |
| session 处于 write-stopped/pending/complete | 遵守清理 fence，不复活正文或追加被禁止的 History 写入 | 各 cleanup 状态下 source/body 不变、修复不越界 |
| execution owner 或 ledger 修复失败 | 按稳定 failure class 阻止该 session 依赖操作；不阻断其他 session，不写猜测性终态 | failure class 保持为 `owner_fence_unavailable`、`active_owner_unresolved`、`ledger_missing`、`ledger_integrity_invalid`、`projection_identity_conflict`、`projection_sink_failed` 或 `session_owner_mismatch`；日志不含 session ID/路径/正文 |
| retention worker 选中 unknown/dirty/pending session | 只对已选中的单一候选持锁运行同一 session readiness gate；成功且 ready 后才继续原保留判断，失败/blocked/active writer 则保留；其他未知 session 不被扫描 | 不依赖 compaction-only guard；空 outbox 不代表可删；所有 profile roots 同规则 |
| retention guard 放行后并发新增义务或开始写入 | 检查、最终状态复核与目录删除持有同一 `ledger_location_key` 生命周期排他锁；canonical writer、ledger repair、retention 都必须遵守该锁 | guard 检查与删除之间不能插入新 target/writer；无法持锁即保留目录 |
| unknown session 的 ledger 文件已不存在 | 状态设为 `blocked/baseline`；不凭 canonical facts 重建并声称 ledger-only 事件完整；保留 canonical 正文读取，阻止依赖台账的功能 | 无原始 ledger 时不会误报 ready；只有显式批准的恢复策略能清除此状态 |
| 维护 worker 与正常 session 写入/修复并发 | 同 session 走同一生命周期锁；无法取得边界时保留待办/目录 | 正常写与修复不互相覆盖、重放仍幂等 |
| schema 升级或旧库回填中途失败 | schema 迁移事务回滚；active workset cursor 可续跑；普通启动不因全库 backfill 阻塞 | 旧版本 fixture、迁移失败重开、未回填 session 定向恢复 |

### 6.2 迁移与回滚

- schema 采用 additive migration；active workset 增量 trigger 与精确投影确认状态可续跑，不删除 canonical History 或幂等 event identity。
- 增加持久进程 generation/fencing 与逐 session projection state；迁移后的历史 session 默认 `unknown`，不能根据空 outbox、文件存在或 JSONL 可解析推成 `ready`。只有完整 session-scoped 对拍后才写 ready proof。旧 workset 行缺 owner generation 时，在取得单实例进程锁后归入已失效旧代；legacy JSONL 开放项没有 generation 时也只可在同一 process fence 后由 session-scoped gate 收口。
- 旧 repair obligation 表可在迁移期保留用于兼容，但不得继续作为全局启动扫描源；目标 session 首次使用时按 session_id 消费并核验。新 canonical 写入、sink 失败、文件替换、修尾和水位变化都必须使 ready proof 失效。
- retention guard 扩展到所有 profile roots，并在 session 生命周期排他锁内组合 projection state、pending/failed target、active writer 和现有 compaction 依赖；锁覆盖检查至实际删除。`unknown`/`checking`/`dirty`/`blocked`/pending 在完成该候选的核验/target 修复前一律保留，只有达到有效 `ready` 后才回到原保留政策判断。
- 当前代码已确认旧版会在 schema version 高于自身支持版本时拒绝打开；新增 migration 后，rollback floor 必须是支持该版本的应用，不能回退到尚不支持它的包。
- 按需修复误判或稳定性回归时，回退为仅对被调用功能的目标 session 同步核验；不恢复全目录启动扫描作为常态。
- 不直接编辑真实用户数据库、不强制提前重试、不清空 repair queue。

### 6.3 未验证项

1. 用户当前安装包/数据库中 active-workset migration cursor 是否仍为 pending，以及实际未结束 invocation 数量；此项影响真实耗时归因，不改变本方案的启动触发边界。
2. 实现前需逐一枚举读取 session `events.jsonl` 的调用者，把 session 生命周期锁、readiness gate 和 failure propagation 接入 compaction/context meter、审计、备份、retention 等入口；遗漏的消费者不得继续绕过 gate。
3. generation/fencing、outbox/ack、文件 generation 变化、CAS 与 retention 排他锁须通过 file-backed SQLite 和临时 ledger 的可控故障/竞态用例验证；这是实施门禁，不是待设计项。单个大 ledger 首次核验上限及真实设备收益仍待安装包与日志实测。

## 8. 排除方案【人机共读】

| 方案 | 处置原因 |
|---|---|
| 删除旧会话或缩短保留期 | 直接损失用户历史，且当前问题未证明由存储容量导致 |
| 启动时 VACUUM / 大规模 compact | 会增加同步 I/O；既有合成测量没有证实可缩短启动 |
| 跳过活动工作表恢复 | 可能把中断 turn 当成可继续状态；活动表命中的异常仍必须直接处理 |
| 通过扩大分类批次缩短全历史回填 | 只改变一次性迁移的阻塞大小，不解决每次启动核对健康历史的问题 |
| 为每条可投影事件都建立全局启动待办 | 把“可能要核对”扩大成启动候选集，重新引入用户指出的架构税 |
| 同时并发修复同一 session ledger | 可能破坏事件顺序与单 writer 约束；没有并发收益证据 |
