# 启动时历史会话恢复耗时优化方案

> 状态：草稿（未实施）｜日期：2026-10-16｜核对基线：worktree HEAD `a353d691`（2026-10-16）
> 范围：`electron/main.ts` 启动历史恢复、`electron/runtime/sqliteAgentHistory.ts` 历史分类与恢复、对应 SQLite 表及维护生命周期。
> 篇内路由：负责人先读第 0 层与 §1；实现者读 §2–§7；复核证据见附录。

## 第 0 层：决策界面【人必读】

**一句话：** 启动窗口前会分类历史数据、恢复未完成对话，并处理到期的附属记录修复；历史规模、分类进度和待办候选规模都可能影响等待，但队列中的待办不等于用户可见的异常。本方案建议只把恢复未完成对话所必需的工作放在窗口前，其余旧记录修复在窗口显示后分批续跑。

**只有 3 分钟的话：** 先读 D-1、§1 推荐方案、§5 风险。

### 需要你决定

#### D-1：旧会话的附属记录尚未修完时，应用是否可以先显示窗口？

旧会话的主要对话内容保存在本地数据库；另有供会话日志、历史维护等功能使用的附属记录。现在应用会等启动时能执行的修复结束后再显示主窗口。待修复项很多时，这会延长每次启动。

| 选项 | 用户能感受到的结果 | 代价与风险 | 可逆性 | 依据强度 |
|---|---|---|---|---|
| **A（推荐）**：先恢复未完成的对话，再显示窗口；旧会话附属记录在后台分批修复 | 有积压时主窗口更早出现；少数旧会话的日志或依赖日志的维护可能暂时显示未就绪，修复完成后恢复 | 需要在尚未修好的会话上明确拦住依赖附属记录的操作，并证明普通历史读取仍完整 | 可通过恢复“修复完成后才显示窗口”的启动顺序回退；新增待办保留可重试 | 源码确认修复队列与主要对话记录分离；受影响功能清单和逐会话围栏仍需实现验收 |
| **B**：所有当前可执行的旧记录修复结束后再显示窗口 | 打开窗口时附属记录更完整 | 大型历史库或反复失败的修复会继续拖长启动等待 | 保持现状，无数据迁移 | 当前实现与既有启动顺序已确认 |

**建议：** 选择 A，但先完成 §6 的依赖围栏和故障验收。若本项暂不决定，默认保持 B，不提前改变启动行为。

### 不需要你决定

- 启动阶段拆分、查询索引、游标和恢复计数的实现方式由工程侧完成。
- 不删除历史会话、不清理 canonical History 正文、不改变保留策略；压缩数据库不列为本轮方案。
- 本方案先给出代码侧结论和可执行验收边界；实际用户数据库的记录规模与本次启动日志尚未核验。

## 1. 概要【人机共读】

### 1.1 验收边界

| 当前环境可验证 | 需要真实安装环境或用户运行日志 |
|---|---|
| 代码调用顺序、SQLite 查询计划、合成大历史库的分类/恢复耗时、崩溃后续跑、修复幂等和会话隔离 | 用户当前数据库中待办数量、真实设备冷启动 p95、旧记录修复延后后对用户实际使用的影响 |

当前没有读取用户数据库，也没有采集本次启动日志。源码可确定阻塞位置和随历史规模增长的工作；具体用户此次等待由哪一类待办主导，仍需用聚合日志验证。

### 1.2 目标与非目标

**目标**

- 缩短从数据库打开到主窗口显示的等待；启动等待不随已完成历史会话或延后修复积压量线性增加。
- 保证中断的对话最终被标记为中断；延后的附属记录修复可断点续跑、可重试、不重复写入。
- 保持 canonical History 内容、消息身份、会话归属和现有路径授权规则不变。

**非目标**

- 删除历史、减少保留期、压缩或 VACUUM 数据库、改写历史正文。
- 更换数据库、重写会话事件协议或 IPC。
- 把普通历史正文清理任务当成这条启动提示的原因。该任务在打包应用中窗口工作阶段之后延迟启动，见 F-4。

### 1.3 推荐方向

分两步实施：先补齐不泄露内容的阶段计数和启动基线；再把恢复查询改成有索引、只取到期且分页的查询。随后将「未完成对话终态恢复」与「历史附属记录修复」拆开：前者留在启动关键路径，后者使用持久待办在窗口显示后限额运行。若历史分类尚未完成，必须先补逐会话就绪判断，避免未分类记录被误当成已修复。

## 2. 现状事实卡【机｜人工可跳过】

### F-1：提示文字对应的启动阻塞点

`main.ts` 在 `canonical-history.classification` 与 `canonical-history.recovery` 前后显示“正在整理历史会话数据”，随后还有会话台账恢复等步骤；主窗口是在这些启动步骤之后创建。因此该提示持续期间，主窗口创建尚未开始。

复核：

```text
rg -n "正在整理历史会话数据|canonical-history\\.classification|canonical-history\\.recovery|createMainWindow" electron/main.ts
```

### F-2：历史分类按 100 个 invocation 有界续跑，但它是在发现修复义务，不是在确认损坏

`classifyLegacyProjectionRepairs(100)` 使用两个持久游标分类历史投影修复与未完成恢复工作；每批最多处理 100 个 invocation，但会读取这些 stream 的事件，并解析带有效 `sessionLedger.location` 的事件，为其登记幂等投影修复义务。登记不先检查对应附属日志是否缺失，因此一条 `pending` 记录不能直接解释为一条已确认损坏或用户可见异常。游标和当批结果在同一事务提交。分类未完成或失败时，启动仍走旧的兼容恢复路径；分类完成前，这一路径会扫描 stream 来找未完成 invocation。

复核：

```text
rg -n "classifyLegacyProjectionRepairs|listStartupRecoveryWorkset|canonical_history_recovery_work_migration" electron/main.ts electron/runtime/sqliteAgentHistory.ts electron/database/schema.ts
```

### F-3：恢复入口扫描全部 pending 候选，只实际执行到期的修复

分类完成后，`getStartupRecoveryWorkSummary()` 取得全部未完成工作项和全部未终止、未停写的 pending repair，再在 JavaScript 中逐项判断退避时间。随后 `recoverInterruptedInvocations()` 再次取得全部 pending repair，在进程内过滤到期项；它把恢复项与到期修复项合并后，逐 invocation `read()` 完整 canonical History，并依次等待对应会话日志修复回调。当前启动路径没有按时间或工作项数量设上限。分类未完成时，摘要被短路跳过，但正式恢复仍扫描兼容工作集和全部 pending repair。

即使大部分 pending repair 尚在退避期，摘要与恢复入口仍会物化并扫描这些 pending 行；只有到期项目会进入实际回放。到期项目的额外耗时还包括逐 invocation 读 History 和串行文件写入。这里存在两种不同成本：历史分类/候选扫描可随历史数据规模增长；实际修复执行则取决于到期义务及其涉及的事件量。

复核：

```text
rg -n "getStartupRecoveryWorkSummary|listStartupRecoveryWorkset|FROM canonical_projection_repairs|await this\\.read\\(invocationId\\)" electron/runtime/sqliteAgentHistory.ts
```

### F-4：延迟的正文清理任务与当前提示不是同一任务

`session-content-cleanup` 在打包应用中由存储生命周期调度，初始延迟为 60 秒、间隔 15 分钟，每轮至多 2 个会话、每会话 1 个 100 行批次；安全数据库压缩则在主窗口创建之后启动。两者不对应 F-1 的启动提示。

复核：

```text
rg -n "session-content-cleanup|initialDelayMs: 60_000|batchSize: 100|maxSessionsPerRun: 2|safe-db-maintenance|void createMainWindow" electron/main.ts
```

### F-5：已有优化和测量给出的边界

- v50 已新增持久化未完成恢复工作表、游标和 History 变更触发器；分类完成后，已完成的 History 增长不会进入恢复工作集。现有测试验证 128→640 条已完成 stream 时工作集保持不变，查询计划不扫描 `agent_history_streams/events`。分类尚未完成时仍走兼容路径。实现与历史测量详见[会话存储重构技术方案](../session-storage-refactor-technical-design.md)。
- 历史冷进程样本记录过：约 235.8 MiB 数据库的一次启动中，分类 373 ms、canonical-history 恢复 2,318 ms、台账 reconcile 10 ms；该样本为热文件系统缓存的单次观察，不是当前用户现状，也不是 p95。
- 历史合成测量中清理并 VACUUM 减少约 708 KB，但启动配对差中位数为 −2 ms，未证明启动改善。因此本方案不把数据库压缩当主措施。

复核：

```text
rg -n "v322|v323|247,304,192|canonical-history\\.classification.*373" docs/develop/storage-session/session-storage-refactor-technical-design.md
```

当前阶段计时已覆盖 `canonical-history.classification`、`canonical-history.recovery` 和 `canonical-history.total`。但当前无法确定用户设备上各阶段的耗时分布、待办总量、到期数量以及分类是否已完成。不得将 F-5 历史单次样本外推成当前设备收益。

复核：


### F-7：旧版应用拒绝打开更高 schema version 的数据库

`runMigrations()` 在发现数据库版本高于当前应用支持版本时抛 `DatabaseUpgradeRequiredError`。若本方案新增 schema migration，不能把回滚到任意旧二进制当作可用回滚方式；必须把支持新 schema 的版本作为 rollback floor。

复核：

```text
rg -n "DB_SCHEMA_VERSION =|DatabaseUpgradeRequiredError|version > DB_SCHEMA_VERSION" electron/database/schema.ts electron/database/migrations.ts
```

### 绕过通道

`--safe-db-maintenance` 明确跳过本次启动的完整 canonical History 恢复，后续在窗口可用后运行压缩维护，并将恢复留给下一次普通启动。优化方案要保留该安全分支，不得让后台 repair 与该分支的 compact 争用数据库或 spill root。

复核：

```text
rg -n "safeDbMaintenanceRequested|canonical full recovery skipped|runSafeDbMaintenance" electron/main.ts electron/storage/safeDbMaintenance.ts
```

## 3. 问题模型与候选根因【人机共读】

### 3.1 与源码相符的耗时来源

| 优先级 | 来源 | 如何延长启动 | 证据状态 |
|---|---|---|---|
| P1 | 遗留历史分类与恢复候选发现 | 分类游标每次处理最多 100 个 invocation，并检查其事件；分类未完成时，兼容恢复还会扫描 stream 来发现未完成 invocation。成本可能随历史规模增长，与最终发现多少实际异常不是一回事 | 代码事实已核验，用户数据库分类状态与历史规模待测 |
| P1 | pending repair 候选扫描与到期修复 | 摘要与正式恢复会扫描全部符合条件的 pending 行，包括仍在退避期的行；仅到期项执行回放。队列记录是幂等的投影修复义务，不等同已确认损坏 | 代码事实已核验，用户库候选数、到期数和单项成本待测 |
| P2 | 单 invocation 历史很大或需修复事件很多 | 单项 `read()` 和文件修复耗时可能超过普通小批次预算；串行处理放大总耗时 | 代码结构已核验，实际事件分布待测 |

### 3.2 目前不应采用的解释

- “数据库文件太大，所以压缩就会变快”：F-5 的历史测量未证明此因果关系。
- “pending 数量就是用户可见异常数，启动会修完全部”：分类生成的是投影修复义务，不保证目标附属日志当前缺失；启动会扫描退避中的候选，但只执行到期项目。候选数、到期数和实际损坏数应分开统计。
- “整理提示来自旧正文清理”：该任务延迟启动且属于另一条调度链。

## 4. 目标状态与关键不变量【机｜人工可跳过】

### 4.1 目标状态

```text
DB 打开
  ├─ 启动关键恢复：只恢复已发现的未完成 invocation，保证旧 turn 不以“仍运行”状态进入正常执行
  ├─ 启动有界预算：分类/恢复在可配置的批次与软时间预算内推进
  └─ 主窗口显示
       └─ 背景修复：按持久游标与 next-attempt 时间分页处理历史附属记录
            ├─ 成功 → completed
            └─ 失败 → 保留 pending，按既有退避规则重试
```

如果历史分类尚未完成，未分类会话的就绪状态必须是“未知/未核验”，不能推导为“无待办”。访问该会话的功能要么先做该会话的定向分类与恢复，要么在修复完成前明确返回未就绪；不能静默跳过。

### 4.2 不变量

| ID | 不变量 | 机制与核验点 |
|---|---|---|
| INV-1 | canonical History 与正文不因提速而删除、跳过或改写 | 延后操作只触及既有派生投影待办；前后 canonical fold、message ID 和 session owner 对拍 |
| INV-2 | 未完成 invocation 在可执行新回合前进入明确终态，或其所属会话仍被阻止执行 | 完整 History transition 校验与会话级 readiness fence；故障重启后重试 |
| INV-3 | 附属记录修复只写入已授权 workDir/session，且每个 target 幂等 | 继续使用现有 session 授权边界、scope 检查和幂等键；越界时 fail closed |
| INV-4 | 未完成/失败的附属记录修复不会被压缩或保留策略提前删掉 | repair 状态是 ledger compaction/retention 的依赖；阻断时保持待办并记录稳定失败类别 |
| INV-5 | 启动恢复工作量有可复现的每轮上限 | 固定页大小 + 单调时钟软预算；到达上限只停止当前批次，持久待办保留到下一轮 |
| INV-6 | 用户可见历史读取不因附属日志尚未回填而丢正文 | canonical reader 继续作为会话正文依据；依赖侧写数据的能力须检查 readiness，不可回退成空历史 |

### 4.3 状态所有权

| 状态 | 唯一 writer | 持久点 | 恢复者 |
|---|---|---|---|
| 历史分类 cursor/status | classifier | `canonical_projection_repair_migration` 与 `canonical_history_recovery_work_migration` 的现有事务 | 启动/后台 classifier；每批提交 cursor 后退出可续跑 |
| unfinished invocation workset | History stream/event 事务触发器；终态恢复器只通过标准 History writer 收口 | `canonical_history_recovery_work` | startup-critical recovery；触发器按新终态移除 |
| projection repair status 与重试时刻 | repair coordinator | `canonical_projection_repairs` | 后台 repair worker；成功后 complete，失败保留 pending |
| 会话附属日志 | session event sink | 每个 session ledger 的幂等 event id | repair worker 或之后的正常重试；不得并发覆盖同一 session 写者 |

## 5. 技术方案【机｜人工可跳过】

### 5.1 阶段 A：先补充安全聚合观测

每次启动记录以下聚合值，不记正文、绝对路径、session ID、invocation ID 或 tool ID：

- 分类耗时、分类条数、剩余是否未完成；
- 未完成 invocation 数、pending repair 总数、到期数、退避中数量；
- 本轮读取的 invocation 数、History event 数、成功/失败修复数；
- 历史恢复总耗时与是否因预算而停止。

先收集至少 10 次正常启动和 3 次冷进程样本，按版本、系统、数据库大小分桶汇总 p50/p95。数据库大小只记分桶，不记录本地路径。用现有 `[startup]` 阶段日志配合 `session.history.recovery` 聚合日志；不得读取或导出用户消息内容。

### 5.2 阶段 B：使待办查询按“到期且有限”读取

1. 在 repair 表持久化 `next_attempt_at`，新建 pending 行设为当前时刻，失败时按现有退避策略计算，成功时清除；已有 pending 行用可续跑迁移填充。
2. 增加支持 `(status, terminal_failed, next_attempt_at, repair_id)` 的索引；查询只选到期行并使用 `ORDER BY next_attempt_at, repair_id LIMIT ?`。
3. 让启动摘要和恢复器复用同一个页查询，避免两次各自物化整张 pending 队列。未到期行不进本轮结果集。
4. 分类/repair 处理采用固定页（建议 100 条）并在页与页之间检查 250 ms 软预算。单条 SQLite 事务或一个文件 sink 操作不可被中断，故预算只限制批次间继续；日志需报告实际超预算的单项。
5. 对仍待处理的到期项只保留持久 pending 状态，传给窗口后的 maintenance worker；不提高单次启动批量上限来换取更少的重启次数。

`next_attempt_at` 的精确计算必须保持现有 `projectionRepairRetryDelayMs(attempts, invocation_repair_count)` 语义。应在 invocation 级只计算一次 repair count，再更新其修复项；迁移期间若 `next_attempt_at` 缺失，按保守规则视为到期并记录迁移状态，不得静默漏掉旧待办。

### 5.3 阶段 C：拆分必需恢复与历史投影回填

1. 将当前混合的 `recoverInterruptedInvocations()` 拆为两个窄职责：
   - **critical recovery**：对已发现的非终态 invocation 写入 interrupted terminal，收敛 durable turn 状态；此阶段不重放所有已终态事件的附属 ledger。
   - **projection repair**：按 `canonical_projection_repairs` 修复已终态事件的 session ledger 等派生记录，遵守页大小、退避与 250 ms 批间预算。
2. critical recovery 保留在窗口前，且只读取持久 workset。分类未完成时，用 classifier 当前批次发现的非终态 work 继续 critical recovery；不要退回到无界全表恢复。
3. classifier 与 projection repair 由生命周期维护调度器在窗口可用后继续推进；进度、失败原因类别和下次尝试时间可观测，退出时停止领取新工作并等待当前单项写入 quiescent。
4. 任何尚未分类的会话记录为 `unknown`。会话被打开、继续或被依赖 session ledger 的维护操作使用之前，须对该会话完成定向分类/critical recovery，或明确阻止该操作直到就绪。健康会话不被坏会话的待办拖住。
5. 保留现有 per-session writer、workDir/session 绑定、spill fence、ledger retention 依赖和 cleanup fence；背景修复不能重放已清除正文或绕过 `write-stopped/pending/complete`。

### 5.4 调度与并发

| 工作 | 时机 | 并发与停止 |
|---|---|---|
| 未完成 invocation critical recovery | 窗口创建前；会话准入前作最终检查 | 单写者，顺序处理；预算结束后未完成项所属会话继续 fail closed |
| 历史分类 | 窗口可用后，先小批推进 | 一个 classifier 实例；每批事务提交 cursor，退出后从 cursor 继续 |
| 已终态 projection repair | 窗口可用后，分类产出后可继续 | 有限页、同 session 串行、不同 session 小并发（初始建议 1）；退出时停止新领取 |

首版不并行处理同一 session 的 ledger 文件。不同 session 并行度先保持 1；取得真实单项延迟和 I/O 锁证据后再调整。

## 6. 失败、迁移、回滚与未验证项【机｜人工可跳过】

### 6.1 失败场景

| 场景 | 处理 | 需证明 |
|---|---|---|
| 进程在分类/修复批次中退出 | 当前未提交事务回滚；已提交页的游标/状态保留；重开继续 | kill/reopen 后无重复事件、无跳页 |
| 修复回调写入失败 | repair 保持 pending，记录现有稳定 failure class，设下次尝试时间 | 失败重试到期后成功；backoff 中不重复扫描全行 |
| 某 session owner/workDir 漂移 | 该 session fail closed，不扩散到健康 session | 越界 callback/executor 不调用；健康 session 仍可恢复 |
| session 处于 write-stopped/pending/complete | 遵守清理 fence，不复活正文或追加被禁止的 History 写入 | 各 cleanup 状态下 source/body 不变、修复不越界 |
| 维护 worker 与正常 session 写入并发 | 同 session 走同一 writer/互斥边界；无法取得边界时保留待办 | 正常写与修复不互相覆盖、重放仍幂等 |
| schema 升级中途失败 | 新列/索引/回填 cursor 使用事务化、版本化、可续跑迁移 | 旧版本 fixture 和迁移失败重开 |

### 6.2 迁移与回滚

- schema 采用 additive migration；保留 repair 原行、已有 idempotency key 和现有 migration cursor，不删除历史字段或待办。
- 双读兼容期：旧行 `next_attempt_at IS NULL` 可被迁移器补齐；迁移完成前保持保守读取。新增列与索引不删除旧状态。当前代码已确认旧版会在 schema version 高于自身支持版本时拒绝打开；新增 migration 后，rollback floor 必须是支持该版本的应用，不能回退到尚不支持它的包。
- 背景工作误判或启动稳定性回归时，回退为“窗口前完成 critical recovery；projection repair 在启动时恢复旧同步路径”。已提交的 idempotent sidecar event 不删除。
- 不直接编辑真实用户数据库、不强制提前重试、不清空 repair queue。

### 6.3 未验证项

1. 用户当前安装包/数据库中分类 cursor 是否仍为 pending，以及 unfinished invocation、pending/due repair 的实际聚合数量。
2. 打开尚未分类 session 时，哪些读取/继续/备份/retention 操作依赖其 session ledger，逐调用者 readiness fence 清单仍需从代码闭合。
3. 250 ms 软预算和 100 条页大小为工程起始值；需在合成 fixture 与目标设备上实测修订。单个慢文件写可能超过软预算。

## 7. 验收映射【机｜人工可跳过】

| 验收 | 断言 | 验证证据 |
|---|---|---|
| AC-1 启动预算 | 10,000 已完成 stream、10,000 条退避 repair 的合成库中，窗口前不因已完成项或退避项全量扫描；历史恢复 phase p95 ≤ 250 ms（10 次相同设备冷进程样本），单项超预算另报 | Electron 冷启动 profile；`canonical-history.*` p50/p95；`EXPLAIN QUERY PLAN` 使用到期索引 |
| AC-2 到期分页 | 每个启动页最多取 100 条 repair；只返回 `next_attempt_at <= now`；同一页被摘要与 worker 复用，无重复全表读取 | `sqliteAgentHistory`/maintenance 定向测试与 SQL 查询计划 |
| AC-3 终态安全 | 对未终态 invocation，启动准入前已落唯一 interrupted terminal；若预算/失败使其未完成，则所属 session 的继续/新回合入口拒绝，不阻塞其他 session | crash/reopen；session-level turn recovery 和健康/损坏双 session 测试 |
| AC-4 修复续跑 | 在 DB commit 前后、ledger 写入前后注入退出/失败，重启后待办不丢，sidecar event 不重复 | file-backed SQLite、session sink 故障注入与 idempotency key 断言 |
| AC-5 内容一致 | 前后 canonical transcript、消息 ID/顺序、session owner 完全一致；无读取到空正文或恢复出已删除正文 | canonical L1/L2 对拍、cleanup fence/History corruption 回归 |
| AC-6 隔离和依赖 | 归属异常的 repair 不写文件；repair 未完成时 retention/compaction 不删依赖日志；无关 session 正常使用 | authorization scope 与 compaction dependency guard 边界测试 |
| AC-7 可观测性 | 能由启动聚合日志区分 classification、critical recovery、due repair、backoff queue；日志不含正文、路径或稳定对象 ID | agentLogger 脱敏测试及已发布候选包启动日志抽样 |

AC-1 的目标是相同目标设备、相同冷进程样本的 p95，不将 CI 虚拟机数字当作真实用户设备结论。若 10 次样本无法稳定满足 250 ms，先按阶段定位慢单项，不放宽数据正确性与权限围栏。

## 8. 排除方案【人机共读】

| 方案 | 处置原因 |
|---|---|
| 删除旧会话或缩短保留期 | 直接损失用户历史，且当前问题未证明由存储容量导致 |
| 启动时 VACUUM / 大规模 compact | 会增加同步 I/O；既有合成测量没有证实可缩短启动 |
| 跳过所有 History 恢复 | 可能把中断 turn 当成可继续状态，或遗漏其日志修复 |
| 简单把分类批次从 100 调大 | 可能减少迁移启动次数，但会增加单次阻塞；无法限制大型单条读/写 |
| 同时并发恢复所有 invocation | SQLite 与 per-session ledger 仍有顺序和单写者约束；没有并发收益证据 |
