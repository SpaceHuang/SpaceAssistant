## 0. 需要决定什么【人必读】

同一次会话有多种记录，其中一些保存聊天内容，一些保存执行当时的输入，还有一些只是缓存或导出。现在这些用途没有被清楚隔开，多个地方各自判断“可信、可读、可执行”，已经出现对同一输入给出不同结论的情况。

本方案把写入、历史规则、读取、恢复、清理分别交给明确的负责者。保留必要的执行记录和故障保护，逐步撤去多处重复判断。

**只有三分钟：读本节、§1 与 §8。**

**裁决记录（2026-10-21，用户确认）**：以下四项均采用 A，选项说明保留供追溯。

| 决策 | 已批准范围与条件 |
|---|---|
| D-1：A | 分步重构；本轮不删除旧正文，不授予真实数据清理权限 |
| D-2：A，附条件 | 允许逐步调整内部表和字段；批准继续绑定 §7.2.1 的兼容回退包 R。开发和隔离演练可先开展，生产切换前必须完成该节全部 R 产物、验证及先 R 后 C 的发布证据；批准不代表 R 已交付，不得豁免或改用任意旧安装包 |
| D-3：A | 锁定现有编辑、重试、排队及接纳时冻结输入行为；行为变更另行裁决 |
| D-4：A | 保持现有全局搜索失败行为；部分结果方案 B 未批准、不进入本轮 |

### D-1：是否分步改造，并把删除旧正文排除在本轮之外

目前部分会话保留两份正文，既有迁移和回退保护也依赖这些副本。A：先统一规则与调用入口，再逐步调整内部存储，旧正文删除另行验收；短期磁盘占用不下降，但每一步都能单独验证和撤回。B：同时完成边界调整、存储迁移和删除副本；可能更早节省空间，但故障时更难判断是哪一步引起，回退要求也更高。**推荐 A**。代码分步调整可撤回；删除数据后，回退受兼容版本限制。依据是代码和内存夹具，尚无用户真实数据库的迁移统计。当前裁决为 A，按本方案分阶段实施。下钻：§6–§8，AC-1、AC-6、AC-8。

### D-2：是否允许调整本地数据库的内部结构

现在“某个读取结果已经核验”和“这个会话采用哪份正文”分散保存，字段间的组合由多处代码解释。A：允许逐步调整内部表和字段，让同一种读取结果只有一份当前核验结论；能减少组合状态，但需要升级数据库，并先交付能打开、读写升级后数据库的兼容回退包，再发布迁移版本。B：只统一代码，保留现有结构；实施范围较小，但长期仍需维护分散状态及其同步。**推荐 A，先完成不改格式的阶段，再实施迁移**。此项不改变导出文件、界面或外部接口。迁移前可以撤回；迁移后不能直接运行不支持新格式的旧版本。依据已核实的表结构和调用关系，真实旧库分布待隔离副本验证。当前已附条件批准 A，生产切换继续受本节裁决记录及兼容回退包要求约束。下钻：§4、§7.1.1–§7.2.1，INV-3、INV-4，AC-4、AC-8。

### D-3：是否在本轮改变“编辑历史”和“接纳时冻结输入”的行为

聊天记录、已经执行时保存的模型输入、下一次执行读取的记录，目前具有不同用途；编辑聊天后，部分后续执行仍可能采用此前保存的输入。A：本轮先把这些用途区分并锁定现有行为，单独提出后续行为变更；用户体验保持当前规则，但暂时保留各路径差异。B：本轮同时规定编辑如何影响后续执行，以及排队时还是开始执行时确定输入；行为会更统一，但会改变重试、排队和远程会话结果。**推荐 A**。代码选择可撤回，已经发给模型的请求无法撤回。当前已查明读取分支，尚未完成各渠道行为对照。当前裁决为 A；本方案不把 B 排入实施阶段。下钻：§2.2、§3.2、§9，AC-2、AC-3。

### D-4：跨会话搜索遇到损坏会话时，是否改为返回部分结果

现在搜索按顺序检查消息，达到数量上限就停止；如果检查途中遇到读不出的会话，整次搜索报错，已找到的消息不返回，后续文件搜索也不执行。A：本轮保持这个行为；不会把不完整结果当成完整搜索，但一个被检查到的坏会话仍可能使本次搜索失败。B：跳过坏会话并返回其余结果；健康内容更容易找到，但必须同时说明结果不完整、遗漏哪些范围，以及文件结果是否继续返回。**推荐本轮采用 A，将 B 留作单独的产品变更。**A/B 代码可切换，已经遗漏的内容不能靠“本次没搜到”证明不存在。现状已从代码核实，尚无部分结果体验与完整性标记的验证。当前裁决为 A；B 未批准、不进入本轮阶段，未来选 B 须另补接口契约、界面归属卡与交互评审。下钻：§4.3.1、§4.4、§5.1.1，AC-2、AC-9。

**不需要你决定**：代码入口、事务参与者、字段比较范围、缓存失效规则、故障注入和依赖检查由实现者依据本方案完成；不再把“查清当前代码”留作产品决策。

**范围外扩声明**：新增持久化字段及内部状态模型仅归 D-2；改变编辑、重试或冻结输入语义仅归 D-3，当前不实施；部分搜索结果及其完整性标记仅归 D-4 的 B，未批准、不排阶段。当前实施基线没有新增界面、用户开关、IPC、备份格式或 IM 行为。D-1 不构成任何真实数据清理授权。

## 1. 架构结论与范围【人机共读】

### 1.1 打算改成什么：以数据库事实为中心的会话存储内核

**推荐把现有几套相互校验的机制，收敛为一个 `SessionStorage` 会话存储内核：以 SQLite 中的已提交事实为准，以 History（数据库中的 canonical 事件流）作为已由 canonical 接管的已提交正文和执行事件的主干；消息表负责身份、排序和展示字段，执行快照负责保存当时承诺采用的模型输入，其余读取结果、文件和界面状态从这些明确的来源产生。**

业务模块只向这个内核提交命令、读取结果。内核负责判断数据从哪里来、一次修改需要同步哪些记录、发生中断后恢复哪一笔；桌面聊天、Hosted、IM、备份和维护代码不再各自选择正文来源或另写一套历史判据。

沿用现有 `SessionStorage` 入口，把目前散落在 runtime、database、ledger 和调用方中的对应职责收回并替换旧实现；不在现有门面外再包一层后就算完成。

目标数据关系如下，箭头表示业务写入或数据派生方向：

```text
桌面聊天 / Hosted / IM / 编辑 / 压缩
                  │ 命令
                  ▼
          会话存储内核的统一提交
                  │ 同一次数据库事务
                  ▼
┌──────────────── SQLite 已提交事实 ────────────────┐
│ History：正文与执行事件主干                       │
│ messages：消息身份、顺序、展示字段                │
│ 执行快照与收据：当时采用的模型输入、版本和提交结果 │
└──────────────────────────────────────────────────┘
                  │ 统一规则与查询
                  ▼
      聊天历史 / 模型上下文 / 路由输入 / 搜索导出
                  │
                  ▼
       可重建缓存 / 文件台账 / 明文备份 / 界面状态
```

这是最终架构；旧格式在迁移期由内核里的兼容适配器承接。接管条件未满足的旧会话继续显式使用 legacy 来源，不能仅因更换接口就被标成已经迁移。JSONL 中尚未入库的压缩等事实也须先迁入数据库，才能完成图中的派生关系。

### 1.2 以谁为主：正文主干统一，其他事实各有明确归属

最关键的取舍是：**已接管会话的聊天正文以 History 为主，`messages.content` 不再是另一份可以独立修改、独立兜底的正文；保留副本只服务迁移核验与指定兼容路径。**同时，消息身份和已经承诺的执行输入具有各自语义，继续由其负责的表保存，避免强行把不同事实当成同一份正文。

| 数据 | 重构后的主来源 | 其他表示如何处理 |
|---|---|---|
| 已由 canonical 接管的消息正文、工具和审批执行事件 | History 及其源 spill（大正文的外置存储）；正文编辑也通过统一提交形成对应事实 | 聊天显示、搜索和导出使用统一查询得到正文；缓存、旧正文副本不能反过来决定写权威 |
| 尚未接管的 legacy 历史正文 | 由兼容适配器读取的 legacy 消息行，达到迁移条件后再交接 | 迁移状态决定来源；读取失败不临时换主 |
| 消息 ID、顺序、状态、附件及尚未被事件完整覆盖的展示字段 | 消息骨架及其字段负责者；当前主要落在 `messages` | 与 History 正文按消息身份组合，禁止各消费者自行拼装；排队输入和流式未提交正文仍是明确的工作态 |
| 某次执行已经保存或承诺采用的模型输入 | 带版本的 Hosted 执行快照、提交收据及其来源引用 | 保留执行快照，不把它当成另一套可编辑聊天记录；不把“当前聊天内容”冒充“当时实际执行输入” |
| 文件台账中的关键持久事实 | 完成覆盖迁移后，以数据库里的对应事件或专用事实记录为准 | JSONL 经持久投影待办生成；普通 chunk 可保持日志/显示用途。旧文件无法证明完整时保留既定阻断行为 |
| 读取缓存、明文备份、Renderer 状态 | 对应数据库事实的派生结果 | 缓存可失效重建，备份走显式导入；界面工作态不能授予历史可信资格 |

因此，“以 History 为主”有明确边界：主的是会话正文与执行事件。消息骨架、执行输入承诺、排队/执行控制继续各有一个负责者；不要求每种数据都改写成事件，也不允许几个来源对同一事实各自裁决。

### 1.3 怎么统一：把散落的判断收进同一个内核

| 要统一的职责 | 具体改法 | 统一后的调用关系 |
|---|---|---|
| 写入 | 会话源事实的新增与修订经一个提交协调者，按命令调用消息、History、执行快照和待办的事务参与者；同一结果要求一起成功的记录在一笔 SQLite 事务提交。投影状态、缓存和文件待办的后续处理仍由各负责者按协议推进 | 调用方表达“提交终态”“编辑正文”“提交压缩”，不再直接更新几份记录并自行补偿 |
| 历史规则 | 事件顺序、工具/审批转移、活动/终态定义各保留一份规则；聊天、模型上下文和路由分别定义其字段与顺序规格 | append、全量读取、缓存增量和恢复复用相同规则；API 认证、写权接管和清理保留各自额外条件 |
| 读取与核验结果 | 由统一查询负责选来源和组装结果；同一会话、同一用途的正负资格等合为一份投影状态。跨会话搜索作为查询编排组合来源，不另建全局资格 | 有效状态下复用缓存或处理增量；跨会话的失败策略保持既有整次失败，按 D-4 单独决定是否改变 |
| 可用性 | 分开维护正文、执行、台账、维护四类事实，再由一个服务汇总“哪些能力可用、为什么不可用” | 业务端读取汇总结果；既不自行重算完整规则，也不靠一个全局 ready 布尔值代表全部功能 |
| 恢复 | 一个编排者按“启动与换库对账 → 执行事实恢复 → 视图恢复 → 按需文件投影”组织现有恢复动作 | 每类状态仍由原领域协议修复，统一安排依赖、重试和失败范围，不增加第二套独立恢复循环 |
| 模块闸门 | 把低层 SQL、文件投影和迁移实现收进内核，以解析后的依赖图限制访问；业务端只拿绑定端口 | 新增低层函数/文件自动属于实现层；无需逐次把函数名补进禁止列表 |

例如，一轮回复结束后，调用方只提交一次终态；内核在同一事务写入 History、必要消息状态、执行快照/收据和文件投影待办。随后聊天页、搜索和备份从统一查询读取，文件投影异步补齐。文件写入失败只留下这笔待办，不让其他模块再猜该回合是否已经完成。

### 1.4 精简什么：替换旧职责，并退休对应实现

| 现有重复或交叉机制 | 目标处理 | 精简后的边界 |
|---|---|---|
| API 认证、shadow、写权接管、清理中四份近似 cache/fold 比较 | 提取一份按用途定义的比较与摘要规格，各入口调用它 | 同一种等价关系只有一份实现；不同操作的准入条件仍分别保留 |
| UI 正资格、负资格、API 资格三套表，加上切换表的 `api_read_mode` | 迁入按会话和用途定位的一份投影状态；切换表只保留正文权威、迁移和清理职责 | 同一用途只有一份当前结论，不能同时保存“已通过”和“已拒绝”两套裁决 |
| 读取入口、后台重验、恢复各自决定来源、拼正文和 fallback | 收到统一查询与投影服务，替换原入口中的决定逻辑 | 消费者不持有第二套正文选择规则；旧入口只在过渡期作适配 |
| History/outbox 与 observer、手动压缩直接写文件交叉 | 把持久事实先提交数据库，再统一生成文件；迁完使用文件作为事实输入的消费者 | JSONL 退出正文和上下文事实的独立裁决，保留可追踪的文件投影职责 |
| 业务侧直接取数据库连接、调用低层会话操作，以及整文件 owner 豁免 | 收口为内部仓储/事务参与者，移除对应桶导出和白名单例外 | 文件所在模块决定它能依赖什么，不再靠维护长名单授予访问权 |
| Renderer 中已无生产调用的旧模型上下文构造、其他旧迁移/重验入口 | 核实调用与兼容责任后删除；有消费者的先迁移再删 | Renderer 只负责显示和暂态合并，模型输入由主进程存储/执行端口提供 |

保留的必要机制也明确：Hosted 执行快照、消息骨架、执行 claim/queue、提交不确定状态、源 spill、按 location 的文件证明，以及破坏性清理发布/授权门禁。这些各自保护不同事实或资源，不以“减少副本”为由删除。

**本轮结构重构完成时，要减少的是可独立决策的写入、校验、来源选择和恢复实现。旧正文的物理删除是另行授权的空间回收，不用“减少了几张表/几份文件”代替架构完成判据。**

### 1.5 比现有架构好在哪里，以及要付出的代价

| 维度 | 现有架构 | 目标架构的优势与验证方式 |
|---|---|---|
| 修改的影响面 | 新增正文/状态行为要排查多个写入口、比较器、失效与恢复分支 | 修改集中在对应事实负责者和视图规格，其他消费者走相同端口；用字段变更、冷暖/恢复一致性测试验证传播完整 |
| 一致性 | 多套结论依靠调用顺序和触发器约定保持同步，已出现摘要范围与终态口径漂移 | 同一提交协调、同一规则、同用途单一结论；用事务故障和规则反例测试验证，不靠新增更多事后对账补齐 |
| 日常读取成本 | 资格、负缓存和重验来源分散，部分不相关字段变化也可能扩大重验 | 按读取用途绑定水位与规则版本，有效结果复用、增量变化增量处理；用同库配对测量全量重验次数和延迟，保持源文件完整性检查强度 |
| 故障定位和恢复 | “正文坏了”“执行未对账”“文件没补齐”可能一起表现为不可执行，需要跨模块追查 | 可用性结果指明受影响的能力和负责者，恢复定位到具体会话/执行/文件待办；用中断、重启及故障隔离用例验证 |
| 测试维护 | 各实现分别覆盖 happy path，跨入口分歧容易漏掉 | 规则集中测，加同快照跨路径对照与随机状态序列；减少重复实现对应的测试维护，保留各边界的故障测试 |
| 架构约束 | 新文件/函数需要人工补名单，门禁通过仍可能绕开内核 | 依赖类别自动覆盖新增实现，非法 raw DB/internal/转导出探针必须失败，减少对维护者记忆的依赖 |

代价是需要迁移调用方、升级投影状态结构、保留一段受控兼容期，并完成文件台账的事实覆盖。短期不会承诺磁盘占用下降，也不预先承诺具体毫秒收益。采用分阶段提交和指定兼容构建回退，把这些成本限制在可独立验证的步骤中。

**已批准的架构方向是上述主从关系、内核职责和退休清单；实施节奏与旧正文不清理归 D-1，内部存储调整归 D-2，编辑/冻结输入按 D-3 保持，跨会话搜索失败行为按 D-4 保持。**后文规格用于约束这个方向如何落地。

### 2.2 三个必须先分清的词

1. **聊天记录**：用户看到的消息、顺序与正文修订，包含 UI 独有的结构字段。
2. **执行上下文**：某一次执行实际采用或承诺采用的模型消息、工具协议状态、压缩窗口/track 范围与版本。它与聊天记录允许不同，但必须有明确来源。
3. **事件台账**：运行事件及其文件投影。目前仍有独立生产事实，只有完成事实覆盖和消费者迁移后，才能降为派生文件。

例如 canonical 编辑追加上下文事件，却不提交 Hosted transcript；Hosted 在特定分支读取最新已提交 checkpoint。`AcceptedTurn.transcriptVersion` 已存在，也不意味着 handoff 当前严格读取接纳时版本。两者都是要显式建模的既有分支，不能在整理接口时顺手改语义。见 F-3、F-9。

### 2.3 已复现的判据漂移

| 核验 | 最小差异与结果 | 含义与限制 |
|---|---|---|
| R-1：全量与缓存接口 | 同一 legacy 输入增加 `toolCalls: []`；全量返回 `legacy-mismatch`，缓存返回 `matched` | 同 scope 接口的规整规则不统一；当前主要 UI 调用预先裁成四字段，不能据此断言 UI 已出错 |
| R-2：负缓存摘要范围 | 只将 Message.status 从 completed 改为 failed，`id/role/content/timestamp` 不变，摘要却改变 | 摘要实现覆盖整对象，超出注释声明的 L2 字段范围；会扩大失效/重验范围，不等于正文丢失 |
| R-3：活动回合判定 | 合法 `state=terminal,outcome=completed`，`hasActiveTurn=false`，正文 write-stop 仍拒绝；只删夹具 turn 后允许 | 清理查询把 state 与 outcome 混用，存在不同模块对“活动”定义不一致；生产清理仍受独立发布门禁 |

另外，缓存内容与独立 fold 相等的检查，在 API 认证、shadow、写权接管和清理入口有四份近似实现；正常文本输入下这四份本身仍一致（F-10）。应提取共享 comparator，同时保留各入口的额外准入条件。不能把下面三项漂移误写成“这四份比较已经各不相同”。

这三项均使用隔离内存数据库复现，脚本、断言和输出见核验记录。MessageStatus 本身没有 `interrupted`；恢复将相应展示状态映射为 failed，不能再将清理状态列表缺少 interrupted 判成另一个缺陷。

### 2.5 P0 必交：编辑 → 下一轮输入的渠道/执行分支基线

D-3 的 A 依赖下面这份**动态行为基线**。Hosted 是 desktop、飞书、微信可能共同使用的 runtime，不是第四个渠道；应同时覆盖渠道适配和真正的执行分支：非 Track 且 checkpoint=0、非 Track 且 checkpoint>0、Track scoped。每个可达组合关联下表用例，不能把几个名词做无意义的笛卡尔积。IM 没有历史编辑原生命令的路径，使用同一会话的合法桌面编辑入口，再触发 IM 入站；不可通过 SQL 强改伪造产品可达性。

| ID | 动作时序（均有不编辑的配对控制） | 必须覆盖/记录 |
|---|---|---|
| B01 | 已提交回合 → 分别编辑旧 user/assistant → 编辑成功 → 下一条新消息 | desktop、飞书、微信实际适配入口；关联 checkpoint 0/正版本、Track 分支，观察最终模型收到旧值/新值还是稳定拒绝 |
| B02 | 桌面 prepare → 挂起 skill route → 编辑依赖历史 → route 完成 → 提交配置/执行 | route 输入/选择与 fence；若返回 `TURN_CONTEXT_CHANGED_DURING_PREPARATION`，provider 调用数=0；不假定 IM 也经过桌面 skill route |
| B03 | 当前输入已提交 fingerprint → 暂停 accepted messages 加载 → 合法编辑当前 user → 继续 | 记录编辑入口是否允许及 accepted fingerprint 的后续判断；入口拒绝也是基线，禁止换 SQL 强改为“成功” |
| B04 | 一轮失败终态 → 编辑目标 user/历史 assistant → 桌面点击重试 | 新 requestId、reuse-user、retry target、boundary/exclude/required user 与最终模型输入；不将 IM 新消息/重投/wake replay 当成同一种按钮重试 |
| B05 | 已 prepared/accepted → 编辑历史或推进 checkpoint → 同 requestId 重投/恢复 | 原 turn/config/AcceptedTurn 复用、调用次数、fingerprint；飞书/微信 prepared wake 各有适配用例，与 B04 分开 |
| B06 | 正在执行 H0 → 桌面入队 Q1/Q2 → 编辑 Q1 → H0 提交 → 领取 Q1 | 顺序、原 requestId、编辑后 fingerprint、required user 只出现一次；再测领取后迟到的 queued edit 及其错误/状态保护 |
| B07 | 飞书/微信持久 inbox/wake 等待 → 合法编辑历史 → worker 领取 → 执行 | 各 adapter 的 Track view/accepted 输入；不把 desktop queue edit 自动套到 IM 队列，无公开编辑能力的组合列 N/A 与代码依据 |
| B08 | 第二回合已接纳但未获执行权 → 第一回合提交新 checkpoint → 第二回合 claim/handoff | 同时保存接纳时 transcriptVersion 与领取后实际 checkpointVersion，不预设二者相等；这是共享内核分支，不是新渠道 |
| B09 | 同 session 的 Track A/B → 分别编辑 A 已含历史及 B 被排除历史 → A 新入站/恢复 | included IDs/viewVersion、锚点与最终模型输入；用不同 sentinel 检查共享 checkpoint/session tail/其他 Track 未串入 |

覆盖清单至少包含 legacy、canonical-retained、canonical-only 的受支持编辑或明确拒绝路径；每种渠道与可达 runtime 分支须有 case 关联。每格冻结一个确定观测值，不能写“旧值/新值均可”；未测或无可达性依据的 N/A 不计完成。

P0 的行为卡须记录固定 commit/schema/fixture、channel/lane/runtime 分支/authority、操作 barrier、消息身份/sequence/编辑前后 digest、route 或 IM Track 输入、required user/boundary/exclude、accepted fingerprint/config/transcriptVersion、claim 后 checkpoint/receipt/History 来源及最终错误。**断言落到实际 `ModelProvider.stream(PreparedModelCall)` 的 messages、route 和调用次数**，而不是只核对数据库、assembler 或 handoff 入参。隔离测试可用不重复文本 sentinel 保存请求正文，生产日志继续不落正文。

可复用 recording provider 的深拷贝逻辑；`CanonicalFakeProvider` 每实例只能消费一次，多轮/工具循环必须有明确实例分配或支持多次 stream 的具名录制 provider。只 mock 外部网络/IM 收发，不 mock 掉本次待测的真实 loop/Hosted 分支，也不得使用自动把 accepted user 正文写回数据库的夹具包装器。至少对 B05/B06/B07 增加 file-backed reopen。现有 mock handoff/invocation 测试仅为局部证据，本轮未执行上述矩阵，不能标作已经形成跨渠道基线。

P0 交付物为渠道×分支×B01–B09 的覆盖/实际结果卡、录制请求 fixture、可运行测试清单及 N/A 依据；真实 IM 送达仍属外验。P1/P2/P3 切换前后复跑相应卡片，D-3 未批准改变的分支须保持相同输入、错误和调用次数，否则阶段不关闭。

## 3. 目标架构与状态所有权【机｜人工可跳过】

### 3.1 模块边界

以下为目标目录，文件名是实施落点提案，不代表现在已经存在。先提取职责，再移动文件；不因改目录重写协议。

```text
electron/sessionStorage/
  public/                 业务端口与 DTO；保持现有外部 IPC 行为
  domain/                 历史规则、字段规格、状态转移、读取来源决策
  application/            提交协调、查询编排、按会话恢复、迁移编排
  infrastructure/sqlite/  会话表仓储、事务参与者、兼容旧格式
  infrastructure/ledger/  location、outbox、文件 proof、文件投影
  infrastructure/blob/    适配现有 spill 协议与引用索引
  maintenance/            retention、缓存回收、旧正文回收
  host/                   装配与生命周期，绑定当前数据库连接
```

依赖方向：业务消费者 → public → application → domain/基础设施端口；SQLite、ledger、spill 适配器实现基础设施端口。`domain` 不依赖数据库、文件系统或 Electron。共享领域类型仍以 `src/shared/domainTypes.ts` 为真实来源；SDK History 协议仍由其现有归属维护，会话适配层不复制一份。

物理移动允许按阶段进行；依赖检查以解析后的模块归属为准。共享数据库的其他业务域仍拥有自己的 adapter，不将整个 `electron/database` 都并入会话模块。

### 3.2 事实与状态所有权矩阵

| 状态/事实 | 唯一负责者与提交点 | 恢复/销毁路径 |
|---|---|---|
| 已提交 History、事件身份与水位 | `SessionCommitService` 通过 History 事务参与者提交；SDK 仍通过原 HistoryPort 调用适配器 | 同一协议 reducer 校验，精确 active workset 恢复；删除依赖源 spill 引用协议 |
| 已接纳消息正文修订 | 根据显式 authority 交给 legacy adapter 或 canonical writer；调用方不能选择“哪份成功算成功” | canonical 已接管后不得因缓存坏而恢复 legacy 权威 |
| 消息骨架与展示元数据 | 消息仓储，变更由提交服务或具名 command 编排；字段 owner 单列 | 原始字段未被事件覆盖前保留；禁止声称整条 Message 可由 History 重建 |
| 排队输入、requestId 接纳凭据 | 现有接纳/队列事务；被接纳前的 queued 正文属于输入命令事实 | 相同幂等键与内容重复返回原结果；内容冲突稳定拒绝；领取时明确转移正文所有权 |
| Hosted 执行快照、commit receipt | 执行提交参与者；继续与 terminal History 原子提交 | 按版本/receipt 读，保留原始 payload；未证明逐版本可重放前不删除 |
| turn/claim/lease/未知副作用 | 现有执行状态机，存储模块只持久化并提供协议操作 | 恢复只能重建有证据的状态；未知副作用不能被改成成功或自动重派发 |
| 读取视图及核验结论 | 逻辑 owner 为 `ProjectionService`；初始化、领取/发布、恢复接管及重试元数据由其推进。源提交只在同事务调用其同步 invalidation participant，撤销 token/可用引用并置 invalid | 缓存回收也使用该失效协议；源事务、仓储、scheduler 不授予 valid/rejected/rebuilding；无有效结论则按 authority 重建或拒绝 |
| ledger 义务与 readiness | canonical 提交登记 outbox；location projector 在共锁内确认 | target 幂等补齐；保留现有 bootstrap、旧文件缺失及 retention 协议 |
| 进程内启动屏障 | host 恢复编排者，仅代表当前进程已完成必要 fencing | 重启重新建立；不保存成另一个会话 ready 字段 |
| 备份与 Renderer 状态 | export adapter / Renderer 显示层 | 显式导入走验证命令；不参与在线正文权威选择 |

### 3.3 一次提交的边界

`SessionCommitService` 是事务编排者，不是通用 `saveEverything()`。提供接纳、History append、终态提交、正文修订等具名操作，内部使用窄事务参与者。

1. 先取得 host 维护屏障的操作许可，再依既有顺序取得已排序的 ledger location locks、spill root fence。同类多资源按稳定 key 排序；换库先停止接纳新操作并等待在途操作结束，不能使提交继续使用旧连接。
2. **在上述 fence 保护区内**完成事务外异步 spill 准备，再进入 `runInTransaction`；保护持续到引用提交或回滚结束，防止 GC/换库抢在引用提交前回收新文件。准备失败按既有协议保留完整 inline 数据，不先修改权威行；禁止持 SQLite 事务等待异步锁。
3. 在同步事务内重读 session generation、process fence、消息 revision、事件水位与 execution lease；检查 expectedVersion、幂等键及 cleanup 写围栏。
4. 用统一规则验证新增事件和当前协议状态，提交本命令所需的 History、消息骨架/兼容镜像、Hosted snapshot/receipt、execution 状态、spill 引用与 durable outbox。必需参与者任一失败整笔回滚。
5. SQLite commit 成功后才返回提交结果和发布展示通知；异步更新可重建缓存、导出/备份以及 drain outbox。若缺少可复用缓存，只影响读取成本，不撤销已提交事实。

terminal History + Hosted transcript + assistant mirror 当前已同事务提交（F-1），重构必须保留。进程内事件通知、JSONL 和备份不与 SQLite 宣称跨资源原子；由 outbox/重读处理迟到和重复。允许丢弃的 chunk 与不可丢的已提交结果使用不同接口。

### 3.4 最小内部契约

公开业务签名在适配期保持不变；下表规定新的内部语义，返回结果由旧适配器映射为现有 DTO/错误码，不增加 IPC。

| 操作 | 必须给定/由可信端补齐 | 结果与失败 |
|---|---|---|
| `commitHistory` | 绑定的 session、调用方 expected stream version、事件幂等键；仓储补当前 session/process fence | 提交 receipt 或结构化 version/identity/idempotency conflict；无部分提交 |
| `commitTerminal` | execution lease、base transcript version、terminal 与完整 snapshot/mirror 意图 | 返回 committed receipt；不确定时查同一收据，禁止调用方另写终态 |
| `readView` | 必填 view kind、request selection；session 从绑定端口取得 | 返回 DTO + 内部 source identity，或 content-unavailable；空会话与读取失败显式区分 |
| `rebuildView` | scope key、服务生成的源 identity 与 token；不接受消费者提供“已经验证”的 proof | 发布 valid/rejected 或 source-fence-changed；旧结果不覆盖新结果 |
| `ensureView`（application 层异步） | 绑定 session/scope、调用方已有 deadline/取消信号；按同 key 合并前台准备与后台任务 | 准备后重读来源再让同步查询选取；不把现有同步 SessionQueries 签名伪装成可 await 的接口，不改变外部 IPC channel/DTO |
| `inspectAvailability` | session 与已授权 ledger location（如该能力需要） | 返回 §4.4 的 facts；不触发工具执行、不授予清理授权 |

内部 failure case 固定为 `SOURCE_FENCE_CHANGED`、`SPEC_UNSUPPORTED`、`CONTENT_UNAVAILABLE`、`VIEW_REJECTED`、`IDEMPOTENCY_CONFLICT`、`EXECUTION_COMMIT_UNCERTAIN`、`RECOVERY_PENDING`、`BUSY`，分别归属于来源、视图、执行和恢复协议；细化 case 在各 owner 中唯一声明。已有外部错误如 `CANONICAL_SESSION_CONTENT_UNAVAILABLE` 保持兼容映射。scope/spec 缺失不取“最近一次”或默认当前会话；拒绝为 SPEC_UNSUPPORTED，避免静默跨用途读取。

## 4. 统一规则、视图与可用性【机｜人工可跳过】

### 4.1 一份规则，三个检查位置

| 位置 | 检查什么 | 明确不做什么 |
|---|---|---|
| 协议规则 `HistoryRules` | 事件 shape、owner、顺序、tool/approval 转移与 terminal 约束；pure reducer 返回状态与稳定 failure case | 不决定来源切换或重试授权 |
| 视图规则 `ProjectionSpec` | scope 的字段、顺序、筛选、编码、摘要、reducer 版本；冷全量与暖增量共用 | 不将 chat、provider、route 结果硬比为全对象相等 |
| 提交/破坏性动作前 fence check | 指定 generation、revision、水位、lease、授权代次及批准材料仍匹配 | 不重新发明“活动回合”“终态”或审批风险判断 |

append、full replay、cache seed+tail、恢复使用同一组协议转移函数；快路径只重放已校验证明之后的 tail。数据库结构、文件 checksum、内存 DTO shape 属不同检查位置，可以保留，但都引用同一语义规格。

`ProjectionSpec.chatBodyV1` 统一把输入规整为有序 `id/role/content/timestamp`；摘要也只覆盖此 shape。工具显示结构、附件等有各自 owner/spec。API 上下文和 route 继续使用各自完整字段，不能为让对拍通过而丢字段。规则/编码版本改变时，旧结论失效并重建，不默默复用旧摘要。

终态与活动状态以领域枚举和纯状态函数定义；SQL 谓词由同一状态规格生成/绑定，并有“枚举全覆盖”的契约测试。不能只共享一个 TypeScript `isActive()`，SQL 里仍手写另一套列表。R-3 优先作为跨模块反例纳入测试。

#### 4.1.1 scope × 字段 × 失效矩阵

下表分别定义**输出摘要**和**选择/资格依赖**，不能把二者合为“hash 整个 Message”。`M` 表示当前存储映射实际返回的完整 Message DTO：`id/sessionId/role/content/timestamp/status/schemaVersion/attachments/imagesDeliveredToApi/toolUse/toolCalls/thinking/contentSegments/skillHints`，缺省值与嵌套字段按统一 codec 处理；`sequence` 与 `queue_scope` 是独立的选择元数据。展示层派生的 `activity` 按其源字段更新，不虚构一个未持久化列。P0 将此清单与 `rowToStoredMessage`、共享类型和调用方逐字段核对；增加字段必须明确归属和依赖，不能靠省略未知字段使对拍通过。

| scope / 用途 | 输出/摘要覆盖 | 选择、资格和外部依赖 | 失效/更新触发 |
|---|---|---|---|
| `chatBodyV1` | 有序 `id/role/content/timestamp` | session generation、History 水位/规则版本、实际消息顺序与正文权威/存储状态 | 正文、身份、timestamp 或实际顺序改变更新正文结果；单改 status/附件/thinking/toolCalls/contentSegments 不改变正文摘要，但仍处理其所属资格/DTO 变化 |
| `chatMessageV1` | M | `queue_scope=desktop`；sequence 最新页、beforeSequence、limit | 任一 M 字段刷新 DTO；queue_scope/sequence/增删刷新页选择。元数据变化复用仍有效的正文 payload，不强制重复 fold |
| `exportMessageV1` | M + sequence | 当前导出只选 desktop queue_scope，sequence ASC 游标/pageSize，无独立 queued/status 排除 | M 变化刷新导出 DTO，queue_scope/sequence/增删刷新集合/游标；保留 status/附件/thinking 等导出字段 |
| `searchCorpusV1`（单会话） | M + sequence；搜索片段使用 content/thinking/skillHints/contentSegments/toolCalls | sequence ASC；排除 queued user；当前不按 desktop queue_scope 限定；live 合并仍属其独立 adapter | M 变化不能复用旧语料 DTO；status/role/sequence/增删刷新筛选。附件即使不产生片段，也属于返回 DTO |
| `globalMessageSearchV1`（跨会话编排） | messageId/sessionId、authoritative content、sessionName；无持久聚合摘要 | profile/ownership、timestamp DESC、literal LIKE、limit；当前无 queued/status 或 queue_scope 过滤 | 正文/身份/timestamp 改变命中与候选；name/profile/ownership/增删改变目录或标题。下次查询重取快照，不把 thinking/status 变化误当新增全局过滤条件 |
| `apiBaselineV1` | M + sequence | sequence 最新 N 条，返回 ASC；该 DTO 本身未过滤 status | M/sequence/增删改变基线；它不是已经过滤/压缩后的 provider 输入 |
| `acceptedContextV1` / provider surface | 实际模型消息的身份/正文/timestamp、工具协议字段和附件解析后的图片/结果内容，按 provider 分支 codec | role/status、turn 关联/状态、required user 锚点、sequence/boundary/exclude、附件引用/实际解析内容及压缩 window/continuation/track 来源 | 资格、顺序或实际模型字段/引用内容变化刷新对应输入；图片送达标记保留于 M/既有 fence，是否影响具体 provider 分支须由 P0 取证；thinking/contentSegments 也不能仅因在 DTO 中就认定进入模型 |
| `routeV1` | `recentMessages.role/content`、userInput、hasVision | status、sequence、turn 关联/terminal 状态、boundary/exclude/limit；attachments 决定 hasVision | 正文/role/status/sequence/turn/attachments 的相关变化刷新路由选择。当前无证据说明 thinking/toolCalls/contentSegments/timestamp/sessionName 改变路由输出，不把它们混入语义摘要 |
| Hosted 已提交 checkpoint | 保存的完整 canonical model messages、version/turn/outcome、receipt/hash/源 spill | claim、checkpoint status、当前引用选择；trackScoped 是否采用共享 checkpoint | 新提交推进当前引用；过去快照不因当前 chat edit/status/展示元数据改变而重写。是否影响后续输入由 P0/D-3 的既有分支决定 |

共同前提是正文 authority、generation、源 blob 完整性与 codec/spec 仍可信；这些条件变化不能因输出摘要相同而被忽略。boundary/exclude/limit/query 不各建持久资格；跨会话目录字段不塞进每个 chatBody 摘要。

矩阵是 `ProjectionSpec` 的依赖登记：比较器、摘要、源提交的 scope 失效集合和 SQL trigger 失效逻辑从同一登记生成或用契约测试对拍。必须有“逐个依赖字段变化会更新相应结果”及“非输出字段不改变该摘要”的双向测试。当前单一 message_revision 的保守失效与异步 selection/acceptance fence 须单独登记；缩窄投影计算范围不等于获准放宽既有执行 fence，P0 已观察到的拒绝/重试行为按 D-3 保持。

### 4.2 证明必须绑定对象和用途

内部核验结果至少绑定以下身份；字段不能承担多种不同版本含义。

| 字段 | 含义与来源 |
|---|---|
| `sessionId + sessionGeneration` | 会话身份与重建代次，来自当前会话仓储 |
| `scope + specVersion` | chat/provider/route 的确切视图契约；provider 另含 track/window、来源 checkpoint 引用 |
| `historyWatermark` | sessionSeq、commitOrder、eventId、invocationId；来自同一数据库快照的事件仓储 |
| `messageRevision` | 该规格所依赖的骨架/字段 revision；不以 row count 或 MAX(rowid)冒充内容新鲜度 |
| `payloadDigest + validatedRange` | 该规格输出摘要与已覆盖区间；预期值由读取源生成，不由待校验缓存自报 |
| `connectionEpoch` | 仅用于内存句柄/在途结果防换入；数据库 reopen 后推进，不作为持久证明的唯一来源 |

stream version、Hosted transcript version、process generation、ledger generation 都有独立含义，不互换。物理 ledger proof 继续绑定 location、文件身份/长度/尾帧/index，不能只复用上述会话元组。

业务调用方只拿 DTO，不构造“已核验”对象；内部 branded 类型配合仓储核验减少误用，但 TypeScript 品牌不是安全隔离。异步准备结束后用可信源重读的 expected identity 做 CAS；旧 callback 不能自证新鲜。

### 4.3 合并资格记录，而不是再加第四套 ready

D-2 目标：用 `session_projection_state(session_id, scope_key)` 统一**同用途**的正资格与负资格（现状依据 F-11）。状态互斥为 `invalid / rebuilding / valid / rejected`，保存 §4.2 的持久字段，以及 rebuild token、结构化 failure case、attempts、retryAfter。**ProjectionService 独占初始化、推进 rebuilding/valid/rejected、恢复接管和重试元数据；失效由源提交在事务内代其执行同一同步 invalidation participant。**“唯一 owner”指一套转移协议，不是假设只有一个函数会执行 UPDATE。

| 转移/写操作 | 唯一授权调用方与提交点 | 边界 |
|---|---|---|
| 初始化、领取 rebuilding、发布 valid/rejected | ProjectionService 的对应协议命令，短事务 CAS | 需匹配状态、token、process/source fence；不接受调用方自报“已验证” |
| 源事实变化 → invalid | 源提交事务内执行 ProjectionService 提供的同步失效参与者 | 撤销旧 token、解除 payload 可用引用、按 §4.1.1 记录 dirty scope；不授予正负结论、不另算重试策略 |
| 缓存回收 → invalid | cache maintenance 调用同一失效参与者并在回收事务内提交 | 不改正文 owner，不自行生成新的资格 |
| 崩溃回收、检查点接管、retry 元数据 | 恢复/scheduler 仅请求 ProjectionService 命令 | 旧 callback 任一身份不匹配都为 no-op，不把新 valid 降为 invalid |

底层 trigger 的失效 SQL 由同一协议定义/生成并受契约测试约束；它不调用异步服务，也不具备授予 valid 的分支。不得把“源事务可失效”扩成第二个独立状态管理器。

- 此表管理 chat/API/route 等可重建视图，不为每个历史 Hosted checkpoint 再保存一份可变资格。冻结执行快照仍归执行协议，引用精确 sessionGeneration、turnId、transcriptVersion、payloadHash/codecVersion；不能用当前 chat 水位更新过去的承诺。
- `scope_key` 由唯一 codec 对 view kind、specVersion 及该视图实际依赖的 track/window 做规范编码；不包含 request limit/exclude 等选择参数。cache 使用相同 `(session_id, scope_key)`，增加不可混用的 payload generation/digest/source identity；替代现有泛用 cache_key 的隐式约定。
- checkpoint/version/watermark 是该 key 下可替换的源身份，不进入 key，避免每轮新增一条资格。track/window 关闭且无在途 reader/rebuild 引用时，按原保留策略回收其投影行与 payload；不连带删除执行快照、commit receipt 或源事件。
- rebuild 在事务外准备 payload，在同一同步事务内发布完整 cache manifest（inline payload 或已完整准备的派生 blob 引用）与 valid 状态，二者绑定相同 source identity、payload generation 和 digest；CAS 失败整笔回滚。invalid/rejected 不引用可用 payload，cache 回收同事务解除引用并将对应视图置 invalid。cache 缺失或配对不符没有可复用结果，不能因 state=valid 就返回空值；大 payload 的预算与 fence 见 §7.1.2。
- `canonical_session_projection_eligibility`、`canonical_session_projection_rejections` 与 API eligibility 的资格部分迁入此模型；按 scope 保存，不再同时出现同 scope 的有效正结论和负结论。
- `session_message_content_cutover` 保留**正文权威、迁移与清理**职责及必要 revision；其 `api_read_mode` 在兼容读者退出后删除，读取偏好由既有配置和有效视图状态推导。不开新用户开关。
- execution checkpoint、claim/queue、cleanup ledger、ledger readiness 保留各自状态机，不并入 projection state。rejection 的退避是调度信息，不是永久失去正文所有权。
- 不为每个请求保存一份资格；request 的 boundary/exclude/limit 从已核验的同 scope 快照选择，不能由局部窗口匹配授予整个会话资格。

转换示例：`invalid → rebuilding(token) → valid`。token 不匹配时旧 callback 直接丢弃，**不写任何状态**；仍持有本 token 但源 fence 改变时，才经该失效协议 CAS `(rebuilding, ownToken) → invalid` 并持久重排。完整比较不匹配为 rejected；源变化使 rejected 失效，按预算重建。rebuilding 进程崩溃后恢复编排只请求 ProjectionService 回收/接管，不自行修改资格，不把半份 payload 标成 valid。

重试可达性由持久状态保证：按 `(status,retry_after,session_id,scope_key)` 的 due 索引有界领取 invalid/rejected；rebuilding token 绑定当前 process generation，启动只收回已 fenced owner 的任务。进程内队列仅唤醒，不承载唯一待办；重启后即使源未变、没有新读取，也能重试到期任务。初期保留现有 backoff/permanent TTL 口径，集中到一个调度 owner；永久标记不是永不复查。每批让步，避免把全量重验放回同步读路径。核验记录 §5 的重启风险须增加 file-backed 回归。

#### 4.3.1 单会话视图与跨会话查询的边界

`session_projection_state` 只证明一个 session 的基础视图，不证明全局搜索完整。两种搜索分别定义：

| 项目 | 单会话 `readSearchCorpusPage` | 跨会话 `searchMessages` |
|---|---|---|
| scope | `searchCorpus` 的会话语料，保持 sequence 升序分页、现有 queued user 排除与 DTO 字段 | 当前 profile 范围的消息查询，保持 profile/ownership、LIKE、timestamp 排序及 limit；现有全局查询没有 corpus 的 queued 过滤，不能直接取 corpus 并集 |
| 源身份 | session generation、该语料依赖的正文/状态/sequence/metadata revision、History 水位及 specVersion | 一次数据库读取快照下的候选关系与会话目录字段，加实际访问会话的源身份集合；query/profile/limit、筛选与排序规格版本属于本次查询身份 |
| 持久资格 | 使用 `(session_id, scope_key)`；分页/query 参数不另建资格行 | 无全局资格行，无跨请求聚合结果缓存；本次调用内部只按完整源身份复用已访问会话的读取结果 |
| 失效 | 依赖字段变化只使该会话/规格失效 | 重用各会话的失效；新建/删除/改名/profile/ownership/候选排序字段变化由下一次查询重新枚举，不能靠旧 session 水位证明全局目录未变 |

全局查询在同一个 `runInTransaction` 的**同步**读取快照内完成候选枚举与实际访问的正文解析；保留 limit 短路，不预先全量认证所有候选会话。需要异步 `ensureView` 时，退出当前快照并准备，然后从新快照重跑整个消息查询，不能把旧候选页与新正文拼成成功结果；重复变更时沿调用方既有取消/错误协议退出。源 spill 继续独立核验物理完整性。

单次 corpus 分页调用只保证其来源快照；多次 IPC 加载语料和 live 工作态合并仍保持现有语义，不宣称跨页冻结快照。若未来增加续页快照 token，须另走接口/行为裁决。本轮也不承诺文件搜索与数据库消息搜索共享一个快照。

#### 4.3.2 旧 cache 整体作废，不搬运 cache_key 语义

本节旧 cache 专指 `canonical_session_projection_cache` 及其派生 payload，不包含 Hosted 执行快照或未决执行协议状态。P3 格式切换时，旧 projection cache **逻辑上整体失效**：以常量大小的格式/namespace 控制记录和新 codec/version 明确拒绝旧 payload/proof，不将 `cache_key=transcript` 等旧键改名、复制或映射成新 scope。新 cache 只能从源事实按新规格生成；C、新格式兼容 reader 和 R 都不做新旧 cache 双读、比较后择优或失败兜底。旧 owner 尚未切换的会话，也只能使用源事实冷读/有界准备，不能再次生成或消费旧 cache。

旧 cache 行/派生文件由 maintenance 按稳定 cursor、行数与字节预算回收，不在启动 migration 中全表 DELETE；中断后旧行仍不可读取。回收仅作用于已确认属于旧 cache namespace 的派生对象，不动源 spill、执行快照和 receipt。逻辑失效不能连带把 legacy 正文或其他源数据判成缓存。

验收包括“旧 cache 水位/hash 看似有效但 payload 故意错误，C/R 都忽略”“物理回收中断 → reopen 后仍拒绝旧格式”“新 namespace 缺 cache 时不回空正文/不切 source owner”。整体失效带来的一次冷重建成本计入 P3 升级后首访预算，不因 cache 可重建就免除性能验收。

### 4.4 可用性是组合结果，不是万能布尔值

`SessionAvailabilityService` 从当前事实一次性生成只读结果；不持久化一个额外 `session.ready`。维度包括：`content`（可读/不可用）、`execution`（可执行/忙/待恢复/提交不确定/阻断）、`ledger(location)`（现有 readiness）、`maintenance`（可运行/暂停及原因）。每维带来源 fence 与稳定 reason。

| 场景 | 唯一解释 |
|---|---|
| canonical 可读，旧 ledger 缺失 | 正文仍可读；仅依赖该 ledger 的功能阻断，保持已确认行为 |
| projection cache 丢失 | 按正文 authority 重建；不能切换写权威，也不能把空 legacy 当成功 |
| 执行提交不确定 | 可独立读取可验证正文；执行先对账 receipt/lease，不重复 dispatch |
| 某 session History 损坏 | 不污染其他 session 的资格与独立执行状态；涉及它的跨会话查询仍按 §5.1.1 整次失败。隔离不等于隐式返回部分结果；共享数据库/进程 fencing 故障仍全局阻断 |
| cleanup 尚未批准 | 不具清理资格；不影响正常已支持的读取路径 |

先保持当前全局恢复阻断行为并纳入回归，再依据故障域细化。只有确认异常局限于某 session 且全局 fencing 完成，才能缩小阻断范围；不能仅删除 `completed.status === blocked` 分支就声称隔离完成。

## 5. 查询、恢复与文件台账【机｜人工可跳过】

### 5.1 单一读取决策

公开 `SessionQueries` 区分单会话的聊天页、导出页、语料页、route、accepted context、Hosted transcript，以及跨会话的 `searchMessages` 编排；不把它们都当成一个 session scope。查询服务先确定权威，再选择数据，再映射 DTO；调用方不自行 fold、选最新 invocation、比较正文或决定 fallback。

| 正文所有权 | 数据有效 | 数据不可用 |
|---|---|---|
| legacy | legacy adapter 读取；canonical shadow 只用于迁移观测 | 返回原有明确错误，不以其他副本默默覆盖 |
| canonical + retained mirror | canonical 规则和视图读取；保留副本用于兼容/迁移核验 | 只有既有、明确授权的兼容路径才可读副本；不得靠 catch 改 owner |
| canonical-only | History + 源 spill + 骨架读取 | 结构化 content-unavailable；不回退到已清空 messages.content |

缓存命中、全量重建、分页、单条、搜索、导出必须对同 scope 的同快照给出相同结果；不同 shape 的返回通过共同规格映射后比较。修复/重建按 session+scope 合并；同一源元组不因 UI 多次读取反复全量认证。涉及源 spill 时仍验证现有强度的文件完整性，不能用 SQLite 水位代替文件核验。

#### 5.1.1 跨会话搜索的失败契约

按 D-4 的 A 保持 `search:execute → searchMessages → 文件搜索` 的顺序和现有返回数组。访问某 canonical-backed 候选时正文不可用，整次消息搜索抛既有 `CANONICAL_SESSION_CONTENT_UNAVAILABLE`，丢弃本次已积累结果，不继续文件阶段；禁止 catch 后跳过或返回空正文。已经命中 limit 后未访问的坏会话不额外触发失败。文件阶段沿用现有错误语义，不为它新增部分结果策略。

两组反例必须同时成立：坏会话排在 limit 前时整次失败，其他会话仍可独立读取；坏会话排在 limit 后时本次不访问它、正常返回。同一查询中的源快照、profile 隔离、literal LIKE、queued 差异和 limit 位置均纳入 AC-2/AC-9。部分结果需要 D-4 的 B 获批及新的完整性契约，当前不实现。

### 5.2 唯一恢复编排者

延续已有 `SessionRecoveryPort`，将它改为显式依赖阶段的编排器，而非增加独立恢复入口：

1. **host 屏障**：取得既有单实例所有权 → 在打开数据库前完成换库崩溃对账 → 打开/迁移数据库 → 在事务中推进 process generation → 构造 writer 并开放恢复。保持 `reconcileInterruptedCompaction` 的前置顺序，避免缺失路径被静默建成新空库；共享存储损坏继续全局阻断。
2. **执行事实恢复**：按精确 active workset 处理旧 generation；核验 receipt 与 terminal History，再恢复 turn/claim/queue/continuation。保留 unknown-effects，不推断工具成功。
3. **视图恢复**：只失效或按需重建投影；不能借重建修补源事件。每个修复命令有 session+generation+target 幂等身份。
4. **文件投影恢复**：实际使用的 location 通过既有 lifecycle gate 补 outbox、核验 proof；后台 maintenance 按预算重试。

`inFlight` 只是合并并发工作；`completed` 只代表指定恢复代次完成，不能缓存成永远有效的业务可用性。后续 source/connection/process fence 变化，由服务失效相应结果。

已有启动优化已实施 active workset、process fencing、location gate/outbox 及 retention 共锁；真实设备性能仍待外验。不得退回启动时扫描全部 ledger，也不能把旧库一次性 backfill 说成已经消失。见 F-12 与原[执行计划](启动历史会话恢复耗时优化执行计划.md)。

#### 5.2.1 与旧启动优化方案/执行计划的归属

旧[启动优化方案](启动历史会话恢复耗时优化方案.md)及其执行计划 P0–P8 是已落地行为和交付证据；文件头仍写“执行中”，本轮不把它解释为源码阶段尚待重做。新方案承接这些行为，职责归属变更和新增测试只在本方案及其后续执行计划登记，不再向旧计划追加同一批源码任务。

| 旧阶段 | 本方案吸收的已有机制 | 新旧真源边界 |
|---|---|---|
| P1–P3 | 精确 active workset、repair backoff、process generation/fencing | 在新 P2/P4 内调整代码归属；旧协议作为兼容基线，不重新发明启动扫描 |
| P4–P5 | location readiness、bootstrap/check token、canonical outbox 与 proof | 新 P4 收敛 owner/调用关系，保留既有缺文件行为、锁和 ack；改变行为须另行裁决 |
| P6–P7 | 消费者按需 gate、移除全目录对拍、retention 共锁和故障边界 | 新 P4/P5 维护入口迁移与回归，不能以目录搬迁替代功能验证 |
| P0/P8 | 旧基线、源码集成验收与明确未完成的真机外验 | 历史结果继续留在旧执行计划；新方案不重复记作本轮通过 |

**旧任务剩余外验的唯一记录位置仍是旧执行计划**：当前用户库迁移状态、真实设备 10 次正常启动/3 次冷进程的 p50/p95、旧 ledger 首访延迟。新 AC-9 的投影升级/回填性能是新增验收，不替代这些项；即使新 P4 源码关闭，也不替旧任务签收外验。主题 README 负责导航与状态说明。

### 5.3 JSONL 的收敛要先补事实覆盖

第一阶段保留 JSONL 的现有生产语义，只把 direct writer、outbox projector、compaction consumer 归到 ledger adapter，避免调用方各自解释 readiness。

长期降为派生台账须满足覆盖表：request/context、usage/retry、工具/审批、terminal、手动/自动 compaction、ContextMeter/replay 的每一项都有明确数据库事实及重建规则。当前缺口最明确的是手动 compaction transaction 和以 JSONL 为输入的 surface replay。实施时将其 start/summary、window、source fingerprint、checkpoint replay identity 等完整 payload 通过具名提交命令持久化，保留当前压缩语义；禁止只补一个摘要字符串。

数据库事实与 outbox 在同事务提交；file write 成功但 ack 前崩溃，用 target 的 event identity、内容和顺序验证后重试确认。只有覆盖表、文件删除/rebuild 对拍与消费者迁移全部通过，才撤去对应功能对文件存在的硬依赖。旧缺失文件仍执行已批准的行为，不凭新模型伪造它原来完整。

### 6.2 崩溃与竞态矩阵

| 窗口/反例 | 唯一动作 | 必须观察到的结果 |
|---|---|---|
| spill 已准备，SQLite 未提交/回滚 | 事实保持原值；既有 orphan/引用回收处理未引用文件 | 不返回成功 receipt，不新增可见已提交消息 |
| History 插入后，Hosted/镜像/outbox 参与者报错 | 回滚整个提交 | 事件水位、正文、receipt、队列与引用均不前进 |
| commit 后通知丢失 | 以 receipt 重读；相同 requestId 返回原结果 | 不重复事件、不重复执行；冲突 payload 稳定拒绝 |
| JSONL 写成功、ack 失败 | 幂等 drain 同一 target，再精确核验确认 | 无重复关键事件，无过早 ready |
| 暖缓存被篡改/源 spill 缺失 | 失效缓存；按 authority 重建或返回 unavailable | 不以保留/空旧正文冒充 canonical 成功 |
| 重建期间 source revision/generation 变化 | token/fence CAS 拒绝迟到结果，失效并合并重排 | 新源结果不被旧结果覆盖；同 key 无并发 rebuild 风暴 |
| 投影 worker 在块准备、检查点提交或最终发布前被终止 | staging 不对 reader 可见；以已提交检查点为界恢复，先 fence 旧 process/token，再由 ProjectionService 核对源身份并以新 token 接管 | 未提交块可重做，已提交块可续跑；无半份 valid；旧 worker/迟到消息不能推进检查点或发布；实际 quiesce 前不换库、不释放资源许可 |
| cache blob 写完但 manifest 未提交，或 manifest 已提交而发布 ack 前崩溃 | 前者无 reader 可用引用，仅在旧准备者已被 fence 且实际 quiesce、无检查点/其他在途引用后按派生对象 GC；后者先对账当前 manifest/资格/source identity，不能按“未收到 ack”推定未提交 | 未发布 blob 不可读，无引用残留最终可回收；已提交且有效的引用保留、结果可重读；blob 缺失则失效并从原 authority 重建/明确失败，不能空成功或删源 spill |
| compact/swap/reopen 后旧 store 继续使用 | 操作时取当前连接；旧在途结果受 epoch/fence 拒绝 | 不操作已关闭连接，不复用旧句柄 proof |
| 取消/超时与 terminal commit 交错 | 同一 lease/turn 状态机决定可达转移 | 保留已有 outcome 映射、未决审批/工具及 unknown-effects 规则 |
| 一个 session 损坏、另一个健康 | 全局 fencing 完成后按故障域隔离 | 健康会话不被局部错误永久拖住；全局故障不能被绕过 |
| retention 与投影/修尾并发 | 共用 location 生命周期锁，删除前重读 proof/outbox/owner | 未核验、仍有义务或活动 writer 时不删 |
| 迁移中断或旧库覆盖不全 | 按 cursor 续跑；只对已核验对象切 owner | 不因全局迁移标记就把未覆盖会话视为完整 |
| legacy 导入、重复/乱序或越域身份 | 显式 import adapter 和统一规则拒绝/隔离 | 不凭备份、eventId 或相同 sessionId 跨 profile 串用数据 |

超时、取消、重复、乱序、部分失败、重启和旧数据均有对应行；性能验证另在 AC-9，不能用“所有测试通过”代替预算判断。

本节“新增主线程历史扫描/fold 次数为零”定义为**相对 P0 冻结运行时基线的正增量为零**，不是总次数为零。每个场景按 session、scope、源身份和操作窗口分别记录基线 B 和候选 C 的主线程历史扫描次数/读取行数、fold 调用次数/处理 event 数，并逐项报告 `C-B`；允许减少，不允许跨对象/用途抵扣，也不允许用少一次调用掩盖更多处理量。metadata 索引发现、worker 读取/fold、主线程发布单列，不能混进基线或抵扣主线程历史工作。首次访问未回填会话时，§7.1.1 旧 owner 原路径已有的扫描/fold 必须原样计入 B，C 可保留它，但不能再追加一轮主线程核验：B=1/C=1 可通过，B=1/C=2 或 B=0/C>0 不通过。

配对卡固定同一源库副本、动作、正文 owner、缓存初始条件、limit/错误注入与进程冷暖状态，记录 B/C 的实际命中和 fold 路径。升级会整体作废旧 cache，因此另保留“P0 旧 cache 有效 → C 升级后新 cache 尚未准备”的真实升级配对；由此产生的 C 冷读全部计入增量与首访耗时，不能把 B 改成冷 cache 来消掉成本。若新增主线程历史工作大于零，该场景就不满足此断言，须调整准备路径或重新评审门槛，不能以“原路径也可能 fold”豁免。耗时按预算卡噪声容差判断，计数不套用耗时容差。

## 7. 迁移、兼容与回滚【机｜人工可跳过】

### 7.1 迁移算法

1. 固定 fixture 和源清单；清查 legacy/canonical-retained/canonical-only/mixed、坏 History、缺 spill、未决执行、旧 ledger 等状态。真实数据仅使用授权的隔离副本。
2. 先统一行为与纯规则，不改 schema。旧入口逐步委托同一个实现；shadow 只观测，不同时产生第二份权威决定。
3. 依已附条件批准的 D-2 A 采用下一可用 schema migration，**不预占版本号**；隔离演练可先开展，生产切换另须满足 §7.1.1。启动阶段只增加必要空表/索引、常量大小的迁移控制/新 cache namespace 记录；按 §4.3.2 整体禁用旧 cache，不搬键/值/资格，物理回收留后台。索引归属与落点见 §7.1.3；新增既有大表索引、全库 inventory/INSERT SELECT、全表 DELETE cache 或全量重验不能混入这个启动阶段。已有数据/触发器先保留。
4. 以 session+scope 分块读取；每块使用同一短读取快照，跨块按 §7.1.2 的源 fence 验证连续性，不声称跨让步持有一个全程 WAL 快照。旧资格只作候选，不复制为 valid。迁移编排请求 ProjectionService 用统一规则生成新结论，绑定精确 generation/revision/watermark。失败经其协议保存 rejected/invalid，不能跳过后宣称该对象迁移完成。
5. 每批由 ProjectionService 的同步事务 CAS 源元组，按协议写新状态并由迁移参与者保存 cursor/已处理结果；重启从已提交 cursor 继续。`scan_complete` 只表示已扫描覆盖范围，不表示所有会话 valid，也不开放未核验对象。
6. 切换采用单一协议 owner。旧接口只读取/映射新结果；需要兼容旧表的短期阶段，由同一事务参与者维护旧格式，禁止两个后台队列各自授予资格。新状态仍 shadow 时，旧系统保持唯一 owner；owner 切换记录与必要状态在同事务提交。
7. 所有读者切换、旧字段使用归零且回退演练通过后，移除旧资格表/模式字段及其 trigger；每个 trigger 的身份保护、失效和清理职责逐项有去向，不直接整段删除。

投影迁移不等于正文权威迁移。含 legacy 行的会话继续经现有认证/写权威协议接管；迁移后的正资格不能自动设置 `write_mode=canonical`，更不能设置 cleanup complete。

#### 7.1.1 P3 样本、覆盖标注与生产切换门槛

本方案需要**一份可解释的样本及其覆盖边界，不是所有用户的数据或全量用户分布**。可直接以当前开发环境实际安装数据的一致性隔离副本作为真实样本，在副本上测量和故障注入，不对正在使用的源库执行迁移实验；其他人的数据仍须相应授权。P3 不因尚未取得真实样本卡而不能开工，可先完成实现、合成夹具和本地验证，实施中补齐样本与测量。硬门槛设在 **P3 生产切换（发布迁移版本并开放正式迁移/owner 切换）之前**，不是 P3 开工之前。

迁移负责人维护“样本 + 标注 + 风险接受”卡：

| 内容 | 必交标注 |
|---|---|
| 样本 | 来源为当前开发环境实际安装数据或其他获授权样本、取样时间/脱敏标识/hash、schema/History/spill 格式；实测 session/message/event 数、单会话规模与单事件/源 spill 大小的 p50/p95/max。所有统计只描述该样本，不外推为用户总体分布 |
| 覆盖 | legacy/retained/canonical-only/mixed、资格缺失/拒绝、活动/提交不确定、缺失/损坏 ledger 等逐项标“真实样本观测到 / 合成或注入覆盖 / 未覆盖”。未知写未知，不把未出现当成不存在；用合成小库、多会话大库、单会话大库及故障注入补充边界 |
| 风险接受 | 明列代表性不足与仍未覆盖的版本/规模/状态、可能影响、计划生产切换范围、保留路径与停止切换条件；由迁移负责人提出，发版负责人和独立复核人具名确认接受范围与依据，不用“样本通过”替代风险判断 |

生产切换前签收该卡及 AC-8/AC-9 的对应证据；不要求继续收集所有用户的数据。风险接受仅处理样本代表性和覆盖外推的剩余不确定性，不能豁免已经失败的一致性/恢复/性能断言、每对象的源 fence/预算检查或兼容包先发布要求；不在已验证且接受范围内的对象保留同一权威来源的现有 reader，不强行切 owner。证据或风险签收未齐时继续开发和隔离演练，不开放生产切换。

| 时序 | 允许工作 | 不等待的工作 |
|---|---|---|
| 启动屏障内 | §5.2 的必要启动/换库/fencing 与原有安全恢复；新格式 DDL、空索引、创建迁移控制行。旧 rebuilding token 在任务实际领取时按 process fence 回收 | 本轮格式迁移不枚举已完成会话、不回填投影、不调用旧 migration inventory/full fold，不等待迁移比例达到阈值；P0 已确认必要的既有恢复工作单列基线 |
| 主窗口可用、host 调用 `allowBackgroundWork()` 后 | 注册独立 `derived-index` 维护任务，按下表预算发现/领取/准备/发布；持久 cursor 和 due 索引驱动续跑 | 不把历史回填挂到窗口 ready 或全局 executable 的完成条件 |
| 首次访问一个未回填会话 | 旧投影 owner 仍有效时只走原有语义读路径，并定向安排新视图准备；已切换且无可用新视图时，由异步 `ensureView` 合并准备，CAS 发布后在新快照重读 | 不等待其他会话或整库完成，不读 canonical-only 的空 legacy 副本，不在主线程追加第二次全量对拍 |
| 暂停、退出、换库 | 停止领取；任务检查取消，完成/回滚当前短提交，等待 worker quiesce 并关闭连接后换库；重开从已提交 cursor/token 续跑 | 未发布 staging 不算迁移完成；退出不强制排空全部历史待办 |

目前 `SessionQueries` 为同步接口，不能在其实现内直接加 await。P3 必须列全调用方，在 application 层先调用 `ensureView`，现有 Promise IPC 外壳再执行同步 selection；内部 Hosted/备份/维护调用也经相应异步编排。跨会话搜索按 §4.3.1 重新取得查询快照。准备超时/取消沿调用方已有错误协议，不额外引入用户可见超时值；后台任务的预算到期不直接拒绝健康前台读取。

#### 7.1.2 回填预算与大项处理

以下数字均为**内部试验的占位上限/目标，尚无实测来源，未实测前不作为性能或停止时限承诺**，不增加用户配置项。64/1 的页数与并发、256/128 行、1 MiB、256 MiB、256 KiB 和 20 ms 是限制首轮试验工作量的工程假设，不代表已知最佳值。8 ms 的设计依据是为主线程事件循环中的输入、IPC 与展示处理预留滞后预算；5 秒的设计依据是为后台调度片设置停止请求检查点，服务于暂停/退出的 worker 停止 SLA 设计，**不是已验证的 quiesce SLA**。二者均须由 P0 延迟基线和 P3 分布实验校准。

P3 开发期预算卡可先登记占位试验限额，随样本取得补测基线；生产切换前冻结验证通过的数值、设备/样本、依据和实际停止 SLA，并随 §7.1.1 的样本/风险卡签收。占位数字不能直接签成验收证据，也不阻止实现开工。优先收紧；如需调大，先补相同的配对、内存和 quiesce 证据并复核，不以“低优先级”代替限额。

| 单位 | 占位试验预算与执行位置 |
|---|---|
| metadata 发现页 | 每次至多 64 个 session key，按稳定 cursor 续跑；只读索引/必要元数据，不顺带 fold |
| 领取与并发 | 每轮最多领取 1 个 session+scope，后台最多 1 个准备 worker；让步并检查取消后才领下一个 |
| 源数据读取块 | worker 内每块至多 256 个 event 或 128 个消息骨架，累计序列化字节目标不超过 1 MiB；先达到任一界限即让步。单记录超限作独立大项，不声称能在 JSON parse/SQLite step 中途抢占 |
| 主线程同步片段 | metadata 页和发布事务分别以 8 ms 为待校准目标；冻结后按实测门槛验收，不是能抢占同步 SQLite 的硬 deadline，超出冻结值即预算验证不通过 |
| 准备 worker | 新增专门投影准备 worker，不能把现有压缩 worker 当成已具此能力；单调度片 5 秒为停止请求阈值，JS heap 预算 256 MiB，RSS/Buffer 总内存另在预算卡登记与测量。单块 20 ms 为让步目标；AbortSignal/Worker.terminate 均不承诺即时中断同步 SQLite/native 调用 |
| 结果发布 | 一次只发布 1 个 scope 的 cache manifest + valid 状态；主线程 inline payload 上限 256 KiB。更大派生 payload 由受 fence 保护的 adapter 准备可丢弃 cache blob，短事务只发布引用/digest；不能把 worker 的大结果搬回主线程做一次巨大 JSON 解析/写入 |

worker 使用同一规则版本和捕获的来源身份准备候选，不授予 valid；有界读取的各块都核对源 fence，发布者在当前连接短事务内最终 CAS，漂移就丢弃。源 spill 与派生 cache blob 必须按 kind/owner 区分，派生文件准备、引用发布和 GC 遵守 §3.3 的同一 fence 协议。

**连接与快照归属：**主线程 ProjectionService 持有领取/检查点/最终发布的写协议，始终从当前 store 取连接；worker 不接收主线程 `DatabaseSync`，只在 host 登记的维护许可内，自行用 `openSqliteDatabaseReadOnly` 打开绑定数据库身份/connectionEpoch 的只读连接，并负责关闭。该工厂不做初始化、迁移、WAL 配置或 checkpoint；禁止改用会自动初始化的写工厂。现有只读工厂无 busy timeout 参数，P3 如需锁等待上限须显式扩展并纳入停止耗时测试，不能假设已继承写工厂配置。许可还绑定 process generation、session/source identity、scope/spec、token 和 spill/cache root，路径相同不代表换库前后是同一对象。worker 不写资格、migration cursor 或持久检查点，只把有界候选交给 ProjectionService 经同步 CAS 提交。

每块通过 `runInTransaction` 执行同步只读事务，以首次读取建立该块的 WAL 读取快照；在此快照内读取源身份和有界事件/骨架，并耗尽/结束游标后退出事务，才解析/归并已复制数据、发消息或让步。下一块新建快照并比对完整源 fence，源变化则拒绝旧分段组合；不靠 `PRAGMA data_version` 单独证明来源一致，不把跨块组合说成一个持续 WAL 快照。源 spill 读取另持有效资源许可并核验引用/digest；任何 SQLite 事务均不跨 await。这样既不把长读取快照留在 WAL 上，也不把主线程写连接借给 worker。

按预算卡冻结的调度片阈值到期（初始占位 5 秒）后不再接收该调度片的最终发布，请求保存检查点并暂停；安全检查点仍需匹配当前 token/source fence，不能响应时请求终止。暂停/退出/换库先停止领取并撤销发布许可，等待当前短读事务结束或回滚、文件句柄与只读连接关闭，再由 worker 确认 closed；强制终止则须等实际退出完成。两者都由 supervisor 确认后才算 quiesce。此前保持 inFlight、不领取下一项、不释放源资源许可、不关闭主 store 或执行 swap/截断 WAL；超时只报告未停妥，不能伪造 closed。预算卡记录调度片到期、停止请求、检查点确认、连接关闭/worker 退出、最终 quiesce 各时刻及实际停止 SLA，不将请求时刻当成完成时刻。

大视图必须能跨调度片继续：持久准备检查点绑定 session/scope/spec、源 fence、token、已验证事件/骨架游标、可序列化的协议 reducer 状态（含未决工具/审批）及输出分块 manifest/digest。完成块后经短事务 CAS 保存进度；同进程只续用本 token，重启则先 fence 旧 owner，新领取者核验检查点与当前源身份后 CAS 移交给新 token，旧 callback 不再有写权。源漂移则丢弃派生中间态并重新定位源。检查点不授予 valid，不产生第二份会话事实；完整块全部验证后才发布最终 manifest。超大单事件/blob 也须有流式/分段路径，不能以每片重放整个 session 充当续跑。

派生 blob 的 GC 引用根包含已发布 manifest、可续跑检查点及存活 preparing/reader 引用；在同一资源 fence 下确认 kind/namespace/owner 与引用后才可删除。未发布不等于无引用，接管检查点仍需的块必须保留；发布 ack 丢失不撤销已提交引用。blob 缺失/损坏时，仅按所观测 payload generation/source fence CAS 失效，迟到 reader 不能撤销后来发布的新结果。源 spill 缺失另按既有源完整性协议失败，即使 cache 尚在也不能放宽保护。

超过上述大项预算的对象在 invalid/rejected 的调度元数据中持久记为 `deferred-large`，不是第五种业务资格状态；不在主线程强行 fold，也不无界重试同一整段历史。在该类对象完成分段/大项路径的预算验证前，不切换其投影 owner、不退休原有权威读取路径。P3 生产切换前覆盖所选真实样本的最大项及合成大项边界，明确标注未覆盖范围并按 §7.1.1 签收风险；不要求取得全体用户的最大库，也不能把样本通过声明为所有规模均已验证。

对已经切换后继续增长的会话，同一分段协议必须支持“增长超单片预算 → 派生缓存回收/损坏 → 重启冷重建”，保持既有读取/取消契约；不能永久 deferred 使健康 canonical-only 不可读，更不能切回旧正文 owner。该反例通过是 P3 切换和 P5 退休现有读取路径的共同前置证据；尚无合格大项路径时，保留同一权威来源的现有 reader，不把缺覆盖解释成迁移完成。

现有 lifecycle 只有启动/暂停/quiesce，scheduler 的 signal 及旧 coordinator 的批间让步都不保证上述预算；这些限制是 P3 的新增实现和验收责任。每批记录无正文的耗时、行数、字节、主线程最长片段、worker 峰值内存、快照持续时间和 WAL 变化。所选样本与合成大库的基线、预算卡或 quiesce 证据缺失时，禁止 P3 生产 owner 切换，不阻止隔离夹具中的切换开发与演练。

#### 7.1.3 索引落点与维护边界

本方案**不预设在既有大表新增索引**。P3 用当前可得的真实样本或合成夹具做 `EXPLAIN QUERY PLAN` 和有界页实测，生产切换前按 §7.1.1 样本卡确认以下复用路径，不得仅凭索引存在宣称查询有界；缺少合格访问路径时不启动相应生产回填任务：

| 查询/对象 | 复用或新增位置 | 建立时序 |
|---|---|---|
| session key 发现、消息骨架分页 | 既有 sessions 主键、`idx_messages_session_seq(session_id, sequence)`；相应选择条件保留 | 复用现有索引，不在升级时重建 |
| History 分段读取/水位定位 | 既有 `idx_agent_history_events_session_seq` 和 `idx_agent_history_events_session_commit_order`；查询满足部分索引的非空条件 | 复用现有索引，不在升级时重建 |
| 新资格、due 领取与新 cache manifest | 新空 `session_projection_state` 的 `(session_id,scope_key)` 主键及 §4.3 due 索引；新空 `session_projection_cache` 的同键主键，保存 manifest/inline payload | P3 启动 DDL 创建空表和索引，后续有界写入；不从旧 cache `INSERT SELECT` |
| 旧 cache 物理回收 | 复用 `canonical_session_projection_cache` 现有 `(session_id,cache_key)` 主键做稳定 cursor 分页 | namespace 已禁用后在 maintenance 有界删除，不加旧表索引 |

新 cache 明确新建空表；**不复用旧 `(session_id,cache_key)` 唯一索引，也不搬运其键语义**，避免在旧大表上改键/重建索引。复用的是源表读取索引及旧 cache 回收索引。若实测表明新读取必须依赖额外的源表索引，P3 实施中需拆出具名的索引变更任务，明确建索引维护窗口/资源占用、quiesce、兼容与失败恢复证据，完成后才能依赖它切 owner；本方案不授权把不可分片的 `CREATE INDEX` 偷放普通回填批或同步启动中。

上述限制针对本轮新增迁移工作；从更早 schema 升级仍可能执行历史迁移中的索引/清理操作，必须在 AC-9 配对记录其原有成本，不能据此宣称所有旧版本升级都只有空表 DDL。

现有 `sessionStorageMaintenanceWorker` 的文件复制、校验与 `VACUUM INTO` 仅是文件级维护实现，不提供投影分块快照、检查点或结果发布协议；其 client 的结果完成分支发出 `terminate()` 后立即 settle，也不能当作新 worker 的实际 quiesce 屏障。这是新协议的实现要求，不据此认定既有完整压缩流程缺少保护。

### 7.2 可回退实体与限制

| 边界 | 可回退实体 | 限制 |
|---|---|---|
| 纯规则与内部归属调整，未改格式 | 对应代码提交与兼容入口 | 回退必须同时恢复对应契约，不能留下两种规则 |
| 增量 schema 已写入，新状态未接管 | 支持该 schema 的兼容构建，旧状态仍是 owner | 旧二进制会拒绝更高 schema；不能直接降 `user_version` |
| 新状态已接管，旧字段仍保留 | 具新格式 reader 的固定兼容构建，通过同一权威服务读取 | 保留字段不证明其仍新鲜；不得直接改回旧读者 |
| 旧字段/表已退休 | 支持新 schema、History、spill 与各中间态的回退产物 | 必须先演练；只支持指定回退地板，不承诺任意旧版 |
| 旧正文已在其他已授权流程被清理 | canonical-only 兼容构建及源事实 | 本轮不发起；不回填旧正文伪造回退，不从空正文兜底 |

隔离快照回退仅限同一次离线演练。生产迁移后若已有新写入，恢复迁移前整库快照会丢后续数据，不能作为常规回滚方案。

#### 7.2.1 兼容回退包是 P3 发布前置产物

P3 执行计划必须实名登记迁移实现负责人、发版负责人、独立复核人；分别负责兼容代码/样本矩阵、各平台打包与分发、回退证据复核，不能以“届时准备”关闭。候选包 C 与回退包 R 从同一冻结 P3 格式/集成基线 B 产生，各自记录 source commit/tree、相对 B 的精确差异、version、schema/History/spill 支持范围、build ID、平台/架构、签名信息、包 SHA-256 与分发地址；功能不同的 C/R 不要求二进制 hash 相同。

R 保留保守执行/查询编排，支持升级后的结构、所有迁移中间态、已切换的 owner、canonical-only 和新写入；默认不主动进行批迁。R 必须尊重持久 owner 并读取其新格式事实，不得因为暂停批迁而采用陈旧旧资格或空正文。这是指定兼容构建，不能以任意旧安装包或仅修改 schema 版本号替代。

| 发布顺序 | 必交证据 |
|---|---|
| 先产 R，再在本地用 C 制造升级状态 | 同基线来源与差异、目标平台包 hash、签名/打开结果；无跨格式假定 |
| 用 C 升级并正常新写后的隔离真实库副本验证 R | 逐项执行下列中间态矩阵；每份样本读取/搜索/正常写入/关闭重开、integrity/FK、receipt 幂等，以及源 spill 缺失时明确失败；仅“能 open”不通过 |
| 复核 R 并先发布到约定回退分发位置 | 每个 C 支持的平台/架构都有可下载 R，下载后 hash 核对，具名复核人签收；用户可实际取得回退产物 |
| 最后发布 C，开放正式迁移/owner 切换 | C 的发布记录绑定 B 与已发布 R 的 manifest、升级库测试结果和分布/性能卡；证据不齐只允许本地 P3 演练 |

R/C 中间态矩阵是上述冒烟的必交样本清单，记录状态、源/owner、cache manifest 与预期结果；真实隔离副本缺少的组合由其副本上的故障注入或合成夹具补齐并标明来源，不冒称真实分布。按可达组合覆盖，不要求无意义的全状态笛卡尔积。各项均保留 C 新写数据再交 R 验证，R 正常新写后再回 C 检查数据与失效协议；R 默认不主动批迁，但前台按需准备与恢复必须可达。每格记录读取/错误、状态/token/引用变化和实际续跑游标，性能另按 AC-9 签收。

| 中间态/故障 | R 的必验行为 |
|---|---|
| DDL 已扩展、尚未回填；回填检查点已提交后中断；旧/新投影 owner；旧字段退休前 | 不依赖全局完成标志或陈旧旧资格；持久 owner 决定来源；检查点只经 ProjectionService 核 fence 后接管，不要求整库回填后才可读写 |
| `invalid` | 无可用旧 payload；按需准备后读取或按既有错误契约失败，不自动赋 valid |
| `rebuilding`，含旧 C worker/token 与已提交/未提交块 | 先 fence 旧 process/token，接管已提交检查点；迟到消息无效，未发布 staging 不可见；按 §7.1.2 完成资源 quiesce |
| `valid`，inline 与 cache blob 两种 | 核对源身份、spec、generation/digest 和完整 manifest 后读取；不能只信状态字；发布成功但 ack 丢失的结果可重读 |
| `rejected`，分别未到期/已到期 | 保持既定错误与退避；未到期不忙循环，到期重试可达且不要求新写入/新 terminal 事件 |
| `deferred-large`，分别附于 invalid/rejected；含 owner 切换后会话增长与冷重建 | 识别为调度元数据；沿同一源的分段/大项路径完成或保持既有取消契约，不新增第五态、不永久卡住健康正文 |
| 旧 cache namespace 尚未物理回收，含看似匹配但错误的旧 payload | 一律忽略，不搬键、不双读、不回退；新 cache 缺失也不重新启用旧 namespace |
| cache blob 写完但未引用；有效 manifest 指向的 blob 缺失/损坏 | 前者不可读且按 §6.2 安全 GC；后者失效并按原 authority 重建/明确失败，不返回空正文、不转用旧 cache；仍被有效引用的 blob 不因 ack 丢失被 GC |
| 源 spill 缺失 | C/R 均按既有源完整性协议明确失败，不用派生 cache、旧镜像或兼容包放宽保护；与派生 cache blob 缺失分别取证 |

P5 退休旧表/字段前，另用退休后的升级副本复验 R，必要时先发布更新的兼容包，再发布退休版本。此顺序是结构迁移的发布门槛，与正文清理 release/authorization gate 独立；满足它不授予任何清理授权。

### 7.3 安全阶段归属

- **facts**：仓储提供水位、generation、引用、失败范围和覆盖率；不生成 allow/confirm/deny。
- **policy**：本轮不新增风险规则；保留现有授权与可查询 trace，不将 locked policy 改包装成 invariant。
- **final-check**：清理执行前核对既有批准对象、scope、授权代次、有效期、候选/回退材料；失败保留稳定 case，executor/dispatch 零调用。
- **invariant**：事务、身份隔离与协议完整性沿用既有约束。新增系统约束时登记 owner、依据、范围、审计与边界测试，并运行 `npm run check:system-invariant-registry`。

静态模块边界门禁与破坏性清理发布门禁是两类责任。资源当前 `allowContentCleanup:false`、compatibility 为 null；本方案不改变这些材料。候选版本/schema/格式、接受记录 digest、回退平台产物 hash、profile/session 集、授权撤销与逐批复核继续保留。

上述清理材料和调用位置的原始核验见 F-14；它不是新投影资格或 cache namespace 可替代的门禁。

## 附录 A. 模块边界检查规格【机｜人工可跳过】

P2 以 TypeScript AST 和实际解析后的依赖图检查模块类别，处理相对路径、别名、namespace、转导出、require、dynamic import 与 type-only 依赖。public DTO 不暴露 `AppDatabase`、`DatabaseSync` 或内部 SQL 类型。非静态动态入口在业务域禁止，确需加载的受控入口属于 host 并有专门测试；不靠无法解析时默默跳过。

规则保护整个实现类别，不逐项枚举函数名。会话 SQL 收入会话 SQLite 仓储，共库其他域只获得其自有仓储；泛用连接只向 infrastructure/host 开放。依赖检查无法证明运行期 SQL 权限或抵抗恶意同进程代码，这里是可维护性边界；数据库约束与身份 fence 仍保留。仓储内的原始 SQL 通过共享领域谓词、表归属清单与边界行为测试约束，不能声称 AST 看见字符串就证明所有访问正确。

当前门禁已经使用 AST 和模块解析（F-13）；本轮替换的是依赖规则、保护范围与整文件豁免，不能宣称“从正则升级 AST”即完成。过渡例外只允许精确依赖边，记录 source/target/symbol/type-only、owner、理由、退出阶段、替代端口及核销证据；不能原样搬运旧 baseline 为永久允许表。

#### A.1 构建接线与最终退出条件

保留稳定命令 `npm run check:session-storage-boundary`。P2 将此入口改为**旧扫描 + 新模块依赖图检查串行运行，任一失败都阻断**；旧 parser 的过渡导出和测试仅服务兼容。现有 `build:electron` 与 `build:electron:incremental` 已调用这个入口，P2 必须以注入非法边的受控 fixture 证明两个 build 路径都会执行新检查，不能只跑一个手工专项命令。CI 的 Electron build 继续走同一入口；不加跳过新 gate 的环境开关。

P2 首次新图扫描发现的表外漏检边须整改后才能退出；不能通过生成 baseline 自动放行。P2 出口仅允许 A.2 中尚未核销且有完整责任记录的具名过渡边；之后禁止新增、源代码已无对应边时强制删除记录。测试覆盖 raw connection/低层 checkpoint/internal import、别名/转导出/动态入口/type leak、新低层文件自动受保护，以及其他域合法 adapter 不误报。

P5 要求**过渡例外为零**，不是只删“过期条目”；同时删除 legacy 扫描实现、旧 baseline 和整文件 `implementationOwners` 豁免，公共入口只保留新图检查。合法 infrastructure/host 依赖由模块类别允许，不算例外，不能为核销而把 main 整文件标成 privileged。`check:session-storage-cleanup-boundary` 保持独立并继续接在两条 build 中，不随旧依赖门禁删除。
