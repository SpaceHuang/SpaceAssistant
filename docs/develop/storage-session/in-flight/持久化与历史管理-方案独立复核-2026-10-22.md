## 4. 方案未点名的两处判据缺口

### F-X1 [P1｜待复现] canonical 事件指纹与 tool_call 宽容口径不同步

- **位置**：`runtime/sessionProjectionRevalidation.ts:24`（`computeCanonicalProjectionFingerprint`，对 `payload_json` 顺序 sha256）、`:34-60`（`permanent` 判定用 `existing.fingerprint === fingerprint`）；`sessionLedgerProjectionCompatibility.ts:4`（`toolCallProjectionPayloadMatches`，忽略旧记录缺省的 `requestId`/`invocationRequestId`/`lane`）。
- **问题**：同一条旧 tool_call 记录，在宽容口径下"相等"，在 canonical 指纹下其 `payload_json` 已变。`attempts >= 5 && fingerprintUnchanged → permanent` 因此可能把"被宽容口径视为一致的差异"升级为永久拒绝。
- **与方案 R-1/R-2 的区别**：R-1 是"全量 vs 缓存接口规整不一致"，R-2 是"legacy 摘要覆盖整对象"；两者都不涉及 **canonical 侧指纹 × 事件 payload 宽容集** 的组合。
- **建议归属**：不新增机制；作为 §4.1.1 `chatBodyV1` 依赖登记的边界用例，并纳入 AC-2 对拍夹具。**需先用隔离内存库复现**（构造 `toolCalls: []` + 缺省 `requestId` 的旧记录，观察 `permanent` 与实际一致性结论是否互斥）。

### F-X2 [P2｜待确认] 编辑路径写入 fence 时不与当前水位自校

- **位置**：`runtime/sessionContentWriteAuthority.ts:99-122` `writeCanonicalBackedMessageContent` 构造并追加 `canonicalWriteFence`，但**不比对**当前 `(sessionGeneration, sessionSeq, commitOrder, watermarkEventId, watermarkInvocationId)`。
- **与方案的关系**：§4.1 的第三检查位置规定"提交/破坏性动作前"做 fence check；编辑追加本身即为一次提交，因此这不是方案缺失的机制，而是**方案规则在一处具体路径上的落点未被点名**，偏差只能由后续重验/审计延迟发现。
- **建议归属**：AC-4 的一条用例（编辑与 checkpoint 推进交错 → 断言 fence 在提交点被校验或明确记为延迟校验），不新增独立机制。
- **需确认**：这是否为 plan 已知并接受的"延迟校验"取舍；若接受，应在 §4.1 该行备注，避免后续实现误判为遗漏。

## 5. 建议补入方案的两条验收用例

1. **四入口同 scope 等价性**（补 AC-2）：用同一夹具跑"全量 fold / L1 缓存 / shadow / 写权威接管"四个入口，断言**同 scope 结论相同、跨 scope 允许不同**；夹具至少含 `toolCalls: []`、缺省 `requestId`、`status` 改值三类。目的：把 §2.3"正常输入下四份一致"这句静态判断变成可执行约束，防止后续任一入口单独加字段。
2. **proof 生产与消费的独立性**（补 AC-6）：构造"proof 形状合法但与物理文件不符"的夹具，断言消费侧不返回 ready。目的：把 §4.2"物理 proof 绑定 location/文件身份"从生产者责任变为可观测约束。
