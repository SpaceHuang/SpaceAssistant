# 会话存储方案复杂度重审

> 2026-10-31；模型重审结果，未实施。审查基线为主方案提交`8b781d6d`，运行时代码沿原`58d28d76`。用户安全代码修改不纳入。关联[主性能方案](./会话存储全链路性能改进方案.md)、[检查点讨论稿](./会话上下文检查点机制.md)。本轮审的是设计，不新增产品行为或授权数据库操作。

## 结论【人必读】

**前版降低了运行量，但没有证明系统复杂度下降；不按原版整体实施。** 最大问题是为摆脱每轮全文副本，又设计了一套通用差分、跨版本正文引用和逆向转换，而原有“运行时如何拼消息”与“恢复时如何拼消息”仍未统一。

替代方向：由执行内核维护一套模型上下文推进规则，运行和恢复共同使用；History保存真实输入、回答、工具结果、压缩替换及有限的终态取舍。取消通用数组差分与任意正文引用协议。当前信息存储、执行权限和聊天展示分别保留自身职责，检查点只加速恢复。

这不是宣称新方向已证明净减少代码。主方案现已给出SDK状态接口、复用事件的上下文协议2、有限终态intent，以及不反向改写历史的兼容构建R。后续按这些契约实施、对拍和核销删除；两项既有P1按窄追加与claim前目标恢复的具体设计解决，不把作者工作停在等待评审。没有实现结果前仍不冒称缺陷已修复。

## 1. 用什么判定复杂度下降【人机共读】

| 维度 | 判断问题 | 不能用什么代替 |
| --- | --- | --- |
| 规则数量 | 同一消息的内容／顺序／失败保留规则是否只写一次 | 少一个公开类或换一个名字 |
| 表示数量 | 是否减少需长期互转的正文表示 | 把全文从表挪到事件封套 |
| 协调数量 | 是否删掉协调器和依赖，而非新旧同时保留 | 从同步改异步、换Worker |
| 故障组合 | 少了哪些“甲成功乙失败／引用缺失／版本漂移”状态 | 仅报告正常路径更快 |
| 路径数量 | 日常动作是否只走必需路径，恢复与兼容边界是否明确 | 把附带任务安排到后台 |
| 维护总账 | 长期生产代码是否实际净减少，迁移／测试是否单列 | 压缩代码行、移到另一个包或称为临时代码而不计数 |

必要机制增加少量代码可以改善结构，但整个主线仍必须给出净减少的证据。不能为了达标删除审批、幂等、租约、引用完整性和未知工具效果处理。

## 3. 当前代码证据：为何不是直接搬一个ContextManager就结束【机｜人工可跳过】

SDK `turn.ts`在同一用户轮次内已有Canonical消息数组。它处理压缩替换、工具结果按调用顺序进入，以及用户批准工具后的system说明。宿主`canonicalHistory.ts`另有从事件生成Claude旧格式消息的规则，会过滤system，并可合成未知工具结果；`canonicalSessionTranscriptEvents`还会剔除工具交互供另一消息面使用。不同输出有不同用途，不能都叫“同一上下文”。

因此重构目标不是把旧750行整文件搬进SDK，而是：

1. 提取Canonical模型消息的内容／顺序规则，让热执行与冷恢复共同使用。
2. 宿主旧模型格式转换降为单向适配，不再自行决定该保留哪段上下文。
3. 聊天投影可以保留压缩前交互，不强行用模型上下文覆盖聊天历史。
4. 工具结果缺失仍是执行安全事实；为特定恢复场景生成提示，不得将提示当真实工具结果或自动重试依据。

## 4. 替代模型：运行和恢复共用规则【人机共读】

| 责任 | 唯一放在哪里 | 不再承担什么 |
| --- | --- | --- |
| 模型消息如何追加、排序、替换及终态选择 | SDK共享上下文推进规则 | 宿主不再平行拼一份同义数组 |
| 活跃上下文生命周期 | 会话执行宿主持有SDK状态 | 不按用户轮次重新建全文，不另写宿主归约器 |
| 持久化执行事实 | History原提交入口 | 不比较累计数组求通用差分，不每轮存完整输入 |
| 谁能接纳、领取与执行 | 原业务事务／授权规则 | 不因有上下文或检查点就授予执行权 |
| 当前未完成输出 | 当前信息存储 | 不保管累计历史工具正文 |
| 展示和搜索 | 原查询与投影 | 不决定模型下一轮的有效消息 |
| 恢复加速 | 独立检查点模块 | 不作为唯一事实或可执行性证明 |

普通输入保存实际新输入和确定边界；回答／工具保存实际新增内容；压缩和人工复核保存本来就需要的完整替代内容。失败结束保存明确的业务取舍，仍保留“失败时采用基线／压缩后截至本次用户输入”的现有行为。系统提示、临时审批说明和动态工具配置的冻结／重建必须证明等价，不能为简化而默默丢掉。

只共享上下文规则，不强行把追加合法性校验、执行权限和UI投影合成一个万能状态机。它们回答不同问题，保留边界比少几个文件更重要。

## 6. 主方案的设计修改与剩余门禁【机｜人工可跳过】

主方案§2.2明确committed／working／failure三个内存视图、同一apply规则、普通输入与失败基线输入的不同、压缩失败截止及工具顺序；新增载荷只扩展原事件payload，不增加事件种类、表或正文引用协议。新intent用封闭选择代替全文，与终态事件同事务验证。

主方案§3.1确定兼容构建R回退：上一稳定业务实现保留同一新reader／提交核心，可以读写升级后事实。取消反向历史转换、旧文件重建及其迁移调度。代价是不能直接降级任意旧安装包，已纳入D-1及发布范围。R也不恢复全局扫描和热路径全文副本。具体职责删除表见主案§1.14，实施阶段必须同步删除，不允许只新增共享函数而保留原双实现。

新增主案INV-10／AC-19：使用同一代码计数口径核销旧职责、长期生产代码必须净减少；迁移／回退、测试、独立检查点分别列账。下列五项都必须满足：

1. 共享规则覆盖成功、失败、压缩、park、审批、工具乱序完成、媒体／签名、人工复核与track输入，不依赖每天读取全文作运行时证明。
2. B-01真实writer到SQLite的热追加没有前缀读取；provider幂等和提交不确定语义不退化。
3. B-02真实继续handler／首次执行在启动完全不恢复的情况下可处理目标旧占用；unknown不重试，不偷取真实活跃owner。
4. 按主案协议2及R执行旧→新→R继续写→再升级演练，检查点全部删除也可正确恢复；不做历史逆向转换，不靠升级前备份丢掉新写。
5. 删除核销、净代码量与实际访问规模同时成立；不以压行／迁文件／删安全约束达标。若模型仍不能净减少，继续重审，不把“性能提升”当作复杂度目标已完成。

没有新增产品界面、设置、IPC或真实库操作。旧测试60项和探针只证明既有问题；本轮文档自检不关闭P1，也不证明新模型性能达标。
