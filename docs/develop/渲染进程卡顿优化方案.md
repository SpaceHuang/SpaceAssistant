# 渲染进程卡顿优化方案（Agent 大量工具调用场景）

| 字段 | 内容 |
| --- | --- |
| 文档状态 | v3.25，复用现有确认事实并修正 Phase 边界 |
| 唯一主线 | bounded display meta → renderer coalescing → on-demand tool detail |

## 1. 目标与不变量

高频工具事件不得反复传输累积大字段；普通展示允许短暂延迟但必须最终收敛；确认是稀少的低频控制数据，走独立读取/通知链路并在完整快照就绪后才可批准；通知丢失、renderer 重载或通道暂时乱序都不能丢失确认入口；正文、思考、工具调用和 Skill 的既有交错顺序不得改变；完整工具事实继续支持历史和下一轮 API context。

事实权属始终在主进程：活动 turn 由内存中的完整 `Message`、turn 状态和 runtime version 表示，checkpoint 后由现有 Message/turn 存储承接；二者是同一事实链路在不同生命周期阶段的表示，不是两套事实源。`TurnRuntime.consume`/`TurnCoordinator.consume` 由既有 reducer 更新活动事实后，再尝试派生普通展示投影并发布变更；projection 计算或通知失败必须被隔离并记录，不能回滚或阻断 reducer、checkpoint、terminal 提交和后续 turn。数据库持久化与崩溃恢复沿用现有 checkpoint/terminal 提交语义，不成为 renderer 接收或展示的前置条件。renderer 只在内存分别保存 `TurnDisplay` 和 pending confirmation 快照，不持久化 receipt、不发送 terminal ack、不参与主进程保留或清理决策。普通消息通知是可合帧的实时路径；确认通知只用于唤起专用读取，不能进入普通消息队列或被普通投影覆盖。

本文所称“主进程事实”，包括活动态 runtime 中的完整 `Message`/turn 状态，以及 checkpoint 后由现有 Message/turn 存储承接的同一事实；不包括任何 renderer projection 或 detail cache。本方案只借鉴 DSH 的边界，不复制其存储模型：既有 reducer/runtime 负责事实完整性，投影负责读取效率，合帧/编码只负责降低重复开销。任何投影或 renderer 问题都不能回写、截断、丢弃主进程事实，也不能终止正在执行的 turn。

全文中的 `canonical fact` 与“主进程事实”同义；本文的 `runtime version` 即现有 `turn.version`；`display version` 与 `TurnDisplay.version` 同义，且直接复用该版本，不新增 display version tracker；`reconciliation read`、`active-turn reconciliation` 与“恢复读取”同义。它们都不表示新的存储层、renderer ack 或 renderer 已确认版本。

## 2. 领域事实与展示元数据

“有界”分为两类，不能混用：

1. 主进程事实的完整性和 API context 语义沿用现有事实链路，本方案不新增事实截断、blob、manifest、GC 或备份系统。展示投影只对 preview/progress/skill hints 做 UTF-8 字节上限，绝不把截断值写回 Message；事实持久化若已有错误，沿用现有 turn/storage 错误处理，不把它扩展为 renderer 同步协议。
2. display meta 的展示上限：preview、progress、skill hints 按 UTF-8 字节截断，保留 `truncated` 和 `hasDetails`；它们不改变主进程事实。`MAX_TOOL_CALLS_PER_TURN` 是既有执行策略上限，达到后按既有 loop 语义结束，不是 renderer 投影上限。任何展示预算不足都只能影响 display projection，不能拒绝事实更新、终止 turn 或改变 API context。

领域常量必须可计算展示预算。所有字符串先按 UTF-8 字节限制，`JSON.stringify` 编码预算另加固定转义余量：

```text
MAX_BOUNDED_DISPLAY_META_BYTES = MAX_FIXED_BYTES
  + MAX_TOOL_CALLS_PER_TURN * MAX_TOOL_SUMMARY_BYTES
ACTUAL_TURN_DISPLAY_BYTES = MAX_BOUNDED_DISPLAY_META_BYTES
  + UTF8_BYTES(message.content)
  + UTF8_BYTES(message.thinking)
  + UTF8_BYTES(message.skillHints)
  + ACTIVITY_INDEX_BYTES
ACTIVITY_INDEX_BYTES = activity.length * MAX_ACTIVITY_ITEM_BYTES
```

`MAX_FIXED_BYTES` 覆盖 turn/session/request/message id、version、lifecycle、字段名和 JSON 转义余量；`MAX_ACTIVITY_ITEM_BYTES` 只覆盖一个交错索引项的 kind、正文区间、segment index、id 和序号，不重复传输正文、thinking 或 Skill 文本；`MAX_TOOL_SUMMARY_BYTES` 覆盖 id、toolName、status、risk、时间字段及 `ToolCallDisplaySummary` 全部 preview/标记。确认快照不属于普通 display meta，也不进入 `MAX_BOUNDED_DISPLAY_META_BYTES`；它有独立的完整性和重试语义。`ACTUAL_TURN_DISPLAY_BYTES` 只遥测普通 TurnDisplay 的实际 payload，不是拒绝、截断、分页、轮询频率或切换协议的阈值。`MemoryTier` 选项只暴露有界 optionId/label，主进程保留真实 key 映射。普通 display meta 按 UTF-8 code point 安全截断；协议 schema 不因某条 Message 的实际大小而改变，实际 payload 仅由事实内容决定。

## 3. 唯一展示类型

```ts
type ToolCallDisplaySummary = {
  inputPreview?: string
  inputPreviewTruncated: boolean
  progressPreview?: string
  progressPreviewTruncated: boolean
  resultPreview?: string
  resultPreviewTruncated: boolean
  hasDetails: boolean
  confirmLabel?: string
  confirmRisk: RiskLevel
}

type ActivityDisplayItem =
  | { kind: 'text'; contentStart: number; contentEnd: number; segmentIndex: number }
  | { kind: 'thinking'; segmentIndex: number }
  | { kind: 'tool'; toolId: string }
  | { kind: 'skill'; hintId: string }

type ContentSegmentDisplay = {
  segmentIndex: number
  start: number
  end: number
}

type ConfirmationDisplay = {
  toolCallId: string
  memoryTiers: Array<{ optionId: number; label: string }>
  riskLevel: RiskLevel
  effect: 'read' | 'write' | 'execute' | 'navigate' | 'connect' | 'unknown'
  shellSecurityHints?: {
    requiresRiskAck: boolean
    outsideWorkDirRisk: boolean
    canTrust?: boolean
    warnings?: string[]
    scannedPaths?: string[]
    violationCodes?: string[]
    validatorId?: string
    denyType?: 'strong' | 'weak'
    securityWarning?: string
  }
  browser: {
    currentPageUrl?: string
    dangerInfo?: {
      userReason: string
      consequence: 'money' | 'data-loss' | 'account' | 'file' | 'unknown-site' | 'generic'
      source: 'page-effect' | 'target-effect' | 'keyword'
      fillPreview?: Array<{ selector: string; method: string; value: string }>
    }
    sessionTrustedHint?: true
  }
  mcp?: {
    serverId: string
    serverName: string
    originalToolName: string
    mappedToolName: string
    description?: string
  }
  autoApproveFallback?: { reason: string; reasonCode: string }
  diff: string
  /** 该快照已包含批准所需的全部安全与授权事实；不是“详情已读” receipt。 */
  complete: true
}

type ConfirmationSnapshot = {
  sessionId: string
  turnId: string
  requestId: string
  turnVersion: number
  toolCallId: string
  confirmation: ConfirmationDisplay
}

type TurnDisplay = {
  turnId: string
  sessionId: string
  requestId: string
  version: number
  lifecycle: 'running' | 'awaiting-confirmation' | 'completed' | 'failed'
  message: {
    id: string
    content: string
    contentSegments: ContentSegmentDisplay[]
    thinking?: ThinkingView
    toolCalls: Array<{
      id: string
      toolName: string
      status: ToolCallStatus
      startedAt?: number
      completedAt?: number
      duration?: number
      display: ToolCallDisplaySummary
    }>
    skillHints: SkillHintView[]
    activity: ActivityDisplayItem[]
  }
}
```

`TurnDisplay.version` 直接等于主进程现有的 `turn.version`：事实事件由 `TurnCoordinator` 消费后递增，checkpoint 也沿用该版本。renderer 用它丢弃旧快照和发起 `known` 恢复读取；它不是 renderer 已确认版本，也不表示 renderer ack。消息身份只保留 `message.id`，不在 turn 外层复制第二个 `messageId`。`ConfirmationSnapshot` 只复用现有 `turnId + turn.version + requestId + toolCallId` 关联当前 `confirming ToolCallRecord`，不新增 pending registry、counter、pendingVersion 或第二套确认状态。`ToolCallDisplaySummary`、`ConfirmationDisplay`、`ContentSegmentDisplay` 和 `ActivityDisplayItem` 都是临时派生 DTO，不是 `Message` 字段，也不是 canonical fact。本方案沿用现有 `Message` schema：`toTurnDisplay` 在主进程内调用与现有 `buildAssistantActivityTimeline` 相同的排序逻辑，从 `contentSegments`、thinking segments、tool `startedAt`、Skill `shownAt` 生成 `activity`；正文项只携带 `content` 的 UTF-16 区间和 segment index，不再次复制正文。相同时间戳必须沿用现有 kind tie-break（thinking → skill → text → tool）及同类原始索引；缺少时间线字段时沿用现有 legacy fallback，不能让 renderer 依据到达顺序猜测。

实时路径在既有 reducer 更新主进程 runtime 事实后更新展示投影；历史、terminal、reload 和切换时，主进程从同一 runtime/已提交 `Message` 事实一次生成完整 activity。正文项只携带区间，工具项只携带 ID，activity 本身不重复传输大字段。`TurnDisplay` 的协议 schema 固定，完整 activity 始终随 display 返回；不因为 activity 数量或某条 Message 的实际大小切换旧协议、分页、截断或终止 turn。性能预算只记录 `ACTIVITY_INDEX_BYTES`、结构化克隆和 renderer apply 成本，不能改变事实语义。

activity 必须保持正文、thinking、工具和 Skill 的交错顺序；不能静默丢弃、把不同活动合并成一个末尾正文，或由 renderer 截断。正文区间始终指向同一份 `message.content`；若历史遗留 Message 超过正文上限，主进程沿用现有 message page/正文读取按区间返回，不能以省略号替代事实。若实际 activity 索引成为独立性能瓶颈，另行优化其编码或 renderer 消费，但仍使用同一协议语义。

## 4. 展示投影与 renderer 合帧

```ts
chatGetTurnDisplays({
  known: Array<{ turnId: string; version: number }>
}): Promise<{ changed: TurnDisplay[] }>
```

主进程按 `known` 查询当前会话中已知 turn 的最新投影；terminal 与 active 使用同一读取路径，不要求 renderer ack 或证明已观察。对本地仍标记为 `running`/`awaiting-confirmation` 的 known turn，renderer 必须维持 single-flight 恢复读取；主进程按 turnId 查询，即使 turn 已从 active 列表移除也返回最新 terminal projection。观察到 `completed`/`failed` 后停止该 turn 的恢复读取。renderer 仅保留内存 `known`，reload/切换时从主进程的 active snapshot 和已提交消息页重新建立；丢失通知由恢复读取自动收敛，不改变主进程事实。若采用 invalidation，只发送 `{ turnId }`，不携带事实正文。

renderer 采用现有订阅加按需恢复读取；同一 turn 的普通展示更新在 renderer 合帧，单帧只应用 latest projection。普通展示的恢复读取只覆盖本地仍 active 的 known turns，必须 single-flight，并在 terminal 后停止；它不是全局固定 polling，不读取无活动 turn，也不形成 renderer 侧的持久交付状态。确认提交、切换会话和窗口恢复分别触发一次专用 pending confirmation 读取，不借用普通 TurnDisplay 的合帧结果。实现可以使用已有生命周期调度的重试，但在 turn 仍为 active 时不能因为一次普通展示读取失败就放弃；协议不暴露轮询游标、确认 receipt 或交付阶段。即使没有后续用户动作，terminal 通知丢失也必须由普通恢复读取最终观察到终态；只有 renderer 与主进程持续不可达时，才等待下一次连接恢复。

确认使用独立的低频读取，不进入普通 projection 合帧队列或 `TurnDisplay` 类型；它复用现有确认通知、active-turn snapshot 和主进程确认执行注册表，不建立新的 pending 事实链路：

以下接口名只描述 Phase 1 对现有确认读取/确认提交入口需要满足的参数契约；实现应复用现有 IPC，不新增 pending registry 或第二套执行入口。

```ts
chatGetPendingConfirmation({
  sessionId: string
  turnId: string
  requestId: string
  turnVersion: number
  toolCallId: string
}): Promise<ConfirmationSnapshot | { status: 'not-awaiting' | 'stale' }>

chatResolveConfirmation({
  sessionId: string
  turnId: string
  requestId: string
  turnVersion: number
  toolCallId: string
  action: 'approve' | 'reject' | 'cancel'
  optionId?: number
}): Promise<{ status: 'accepted' | 'rejected' | 'cancelled' | 'stale' }>
```

主进程已有的确认通知只作为低延迟提示，不携带完整确认事实；renderer 从 active-turn snapshot 或最新 `TurnDisplay` 得到 `awaiting-confirmation` 和 confirming `toolCallId` 后，使用同一 `turnId + turn.version + requestId + toolCallId` 读取完整确认快照。renderer 启动、重载、窗口重新可见、IPC 连接恢复、会话切换，以及 active-turn 恢复读取观察到 `awaiting-confirmation` 时，都重复这次读取，不需要 session 级 pending ref 列表或 removed 协议。读取失败、响应迟到或主进程返回 `stale` 时，确认 UI 保持不可批准；普通 `TurnDisplay` 的丢帧或合帧不影响这次低频读取。

renderer 只维护确认快照的临时状态：`absent → loading → ready`。读取失败回到 `loading`，主进程不可达时保留不可批准的 error/loading 状态并在连接恢复后重试；最新 turn version、requestId 或 confirming toolCallId 改变时先清除旧快照。只有最新普通投影明确为 `awaiting-confirmation`，且当前快照的四元组与最新投影完全匹配时，批准按钮才可用。

两个通道在 renderer 侧只做最小安全合成，不互相覆盖：普通 `TurnDisplay` 的 `lifecycle` 和 confirming toolCall 用于定位卡片，完整确认事实来自低频读取。若确认快照先到而普通投影仍是旧版本，先展示确认信息但批准保持禁用；若普通投影先到而确认快照未到，展示“正在加载确认信息”但批准保持禁用。普通投影版本倒退、confirming toolCall 改变、turn 已进入 terminal，都会立即撤销批准资格；异步旧响应即使随后返回，也不得重新激活旧卡片。

确认生命周期继续由现有主进程确认执行注册表和 turn 状态唯一推进；本方案不定义第二套 `approving/approved/rejected/cancelled/expired` 状态机。批准、拒绝、取消复用现有确认入口，并携带当前 `turnId + turn.version + requestId + toolCallId` 作为条件；主进程按现有注册表原子校验，过期或不匹配直接返回 `stale`，不执行旧意图。

renderer 接收失败、进程重启或本地展示缓存丢失只影响展示，不改变主进程 turn 状态；下一次 reconciliation read 重新读取 `TurnDisplay`。只有主进程 canonical fact 写入/校验失败才产生 `storage-error`。主进程在确认、新 turn、queued drain 等所有相关 IPC 入口强制检查该状态并拒绝依赖缺失事实的操作；renderer 只据此禁用界面和展示错误，不能作为正确性裁决者。

必须覆盖：terminal 在两次通知间提交、最后 terminal 通知丢失且无用户动作、窗口隐藏期间 terminal、重载/切换恢复、renderer 合帧和 display meta 预算。

## 5. 终态与上下文

主进程内部沿用现有 terminal Message/turn state/queue receipt 提交边界，成功后更新 runtime；展示通过同一投影读取，不向 renderer 暴露提交对象。assistant streaming overlay 在主进程完成边界收口，不能覆盖 DB completed message。renderer 卡顿、通知丢失或展示读取失败只影响展示收敛，不改变 turn 的执行和终态；只有主进程自身事实提交失败才沿用现有 storage error 处理。

下一轮 API context 继续从现有已提交完整 Message hydrate；本方案不改变 input/result 的协议、持久化、blob 或错误语义。工具详情只在用户展开时从主进程现有事实读取，不能从 TurnDisplay 或 renderer cache 反推上下文。既有事实存储问题另行处理，不作为本次 renderer 卡顿优化前置。

## 6. 按需工具详情与历史

```ts
chatGetToolCallDetails({
  sessionId, turnId, messageId, toolCallId
})
```

主进程验证四级归属后读取现有完整 input、diff、result、scrollback。进入 awaiting-confirmation 时，主进程必须通过 Phase 1 的专用确认读取，按现有 `turnId + turn.version + requestId + toolCallId` 返回该确认所需的完整 diff、完整安全警示和授权字段；这部分不是普通 detail，也不受预览上限约束。普通 `TurnDisplay` 只提供工具摘要、confirming toolCall 和 `awaiting-confirmation` 生命周期，不携带确认事实。确认快照缺失、读取失败、响应迟到，或其四元组与当前投影不匹配时，renderer 必须保持批准禁用，只能重试专用确认读取或拒绝/取消，不能基于摘要批准。普通的长 shell 输出、完整 result、完整 MCP 描述等非批准必需内容仍通过 `chatGetToolCallDetails` 按需读取。`ToolCallDisplaySummary.confirmRisk` 只是列表卡片的风险徽标；确认流程的权威风险字段是完整 `ConfirmationDisplay.riskLevel` 及其安全字段，二者都由主进程从同一事实生成，不允许 renderer 自行推导或修改。renderer 的普通 detail cache 是短期、有 TTL 和容量上限的可丢弃展示缓存，不是事实源，不参与 API context hydrate、terminal 判断、retry/confirm 状态、历史恢复或确认正确性，缺失时重新调用 detail IPC。renderer 回传的 optionId/用户选择仅是意图，且只有当前 `turnId + turn.version + requestId + toolCallId` 全部匹配且完整确认快照已取得时才可产生批准意图；主进程仍通过现有确认执行注册表映射真实确认事实，并重新校验 risk、trust、来源和归属后才执行。确认读取失败可重试，确认结束清除；“详情已加载”不写入事实、receipt 或持久状态。普通详情不进入高频 projection。

读取和命令失败的处理必须区分：turn 仍为 `awaiting-confirmation` 且主进程可达时，renderer 保留“等待确认信息”并重试，不保留可批准的旧快照；现有确认入口返回已结束/已替换或 turn 已终态时，renderer 清除确认卡片并接受终态结果；主进程暂时不可达时，保留不可批准的 loading/error 状态，连接恢复后按最新 turn snapshot 重新读取。不能无限保留旧快照，也不能把一次读取失败转换成批准或自动拒绝。

历史继续使用现有 message `sequence/beforeSequence` 分页，assistant message 通过一次批量查询调用 `toTurnDisplay`；不新增 tool-result 或 activity cursor。正文区间使用 UTF-16 code unit 的半开区间 `[start, end)`，由主进程按 `contentSegments` 的拼接结果计算，renderer 不自行重建边界。正文先按模型输出上限测量，只有 profiler 证明是独立热点才另行设计虚拟化。

## 7. 分阶段实施

### Phase 0：事实契约与测量

建立真实 50-tool、大 result fixture；记录每事件 IPC 字节、activity 索引字节、结构化克隆、renderer apply/React commit、主进程 stringify/SQL、checkpoint 和 event-loop delay。Phase 0 验证完整 activity 在固定协议下的顺序等价，并量化 activity 索引是否值得单独编码优化；测量结果不改变协议、不拒绝既有事实更新、不终止 turn，也不污染下一轮 context。只定义大字段 projection 的展示上限与测量口径，不新增事实存储系统。

### Phase 1：最小读取替换

实现 `toTurnDisplay`、复用 `buildAssistantActivityTimeline` 的排序器、现有订阅或 invalidation + read、renderer latest-per-turn 合帧/store，以及复用现有确认通知/执行注册表的专用完整确认读取；停止旧完整 `chat:turn-projection` payload。单个 `TurnDisplay` 必须已经携带完整 activity，不能依赖 Phase 2 的读取补全；确认不得嵌入该类型，但 Phase 1 必须同时保证确认建立、恢复、批准、拒绝和清理可用。验证终态可通过主进程查询收敛、确认读取失败时批准门控有效、重载/切换/隐藏窗口、并行 turn、通道乱序和旧响应回放、最坏实测 activity 索引和 renderer apply 成本；任何 renderer 性能问题都不能终止 turn。若性能门槛达成，立即停止实时链路扩展。

### Phase 2：详情与历史复用

实现 `chatGetToolCallDetails` 和历史 display page；验证普通详情归属、历史恢复与下一轮上下文。确认读取不属于 Phase 2 的补全依赖，Phase 2 不新增确认事实、pending registry 或确认生命周期协议。blob、manifest、GC、备份和新的事实存储层不属于本方案；只有未来独立证明 canonical storage 本身存在问题时，另立存储方案评审。

## 8. 通过条件

- terminal 不依赖 renderer acknowledgement；active-turn reconciliation 按 turnId 查询并在终态停止，重载/切换通过主进程 active snapshot 和已提交消息页重新读取并收敛。
- pending confirmation 不依赖单次通知：renderer 启动、重载、窗口恢复、连接恢复、会话切换和 active-turn 观察到 awaiting-confirmation 时，都能从现有 active-turn snapshot 得到 confirming toolCall，再按 `turnId + turn.version + requestId + toolCallId` 重新读取；不新增 session ref 列表或 removed 协议。
- 所有摘要由主进程从 runtime 增量摘要或已提交 Message 按需生成，renderer 不访问大字段；确认字段走独立低频读取，从现有 confirming ToolCallRecord/确认执行注册表和同一事实生成，历史、重启和实时路径的 summary 字段一致。
- `TurnDisplay.message.activity` 与现有 `buildAssistantActivityTimeline` 逐项等价：正文 → 工具 → 正文、thinking → Skill → 工具 → 正文以及相同时间戳 fixture 的可见顺序一致；renderer 不按到达顺序重排。
- `MAX_BOUNDED_DISPLAY_META_BYTES` 覆盖可裁剪的 display meta、固定字段和全部 tool meta；完整 `ConfirmationDisplay` 位于独立控制面，单独按安全完整性校验，不截断、不以大小失败放行批准。正文/thinking 与完整 activity 计入 `ACTUAL_TURN_DISPLAY_BYTES` 遥测，不因实际数量改变协议或事实语义。activity 不分页、不追页、不截断，renderer latest-per-turn 合帧不重复 apply 中间 progress。
- 固定协议下，主进程既有 reducer 始终完整接收并更新 runtime `Message`/turn 事实，再按现有 checkpoint/terminal 策略写入存储；projection 或 renderer 性能问题只能通过合帧、编码或后续消费优化处理，不得影响 reducer、checkpoint、终态提交、丢弃事实或改变 API context。
- 确认 fixture 覆盖 memory tier、完整 diff、shell 安全警示、browser danger/current URL、MCP 来源、session trust 和 auto-approve fallback；完整确认快照加载失败、迟到、pending 被替换或已结束时，批准入口必须保持禁用，只能重试或拒绝/取消。
- `ConfirmationDisplay` 与现有确认领域类型逐字段映射测试：完整 diff、MemoryTier optionId、ShellSecurityHints、BrowserActDangerInfo、AutoApproveFallback、McpToolSnapshotEntry；只有独立读取返回的快照匹配当前 `turnId + turn.version + requestId + toolCallId` 且完整信息已取得时 renderer 才能回传批准意图，主进程仍验证后才执行。
- 确认读取测试覆盖通知丢失、renderer 重载、连接恢复、confirming toolCall 替换/移除、普通投影与确认快照乱序、旧响应迟到；旧快照不能复活，未匹配完整快照时批准始终禁用。
- Phase 1 必须覆盖现有确认入口的建立、恢复、批准、拒绝、取消和清理；确认读取失败不能永久卡住，也不能留下可批准旧快照。Phase 2 不得成为确认可用性的前置条件。
- 使用真实确认 fixture 测量完整 diff、安全警示和结构化克隆成本；在没有数据证据前不新增确认分段、blob 或第二套存储协议，任何体积优化都不得截断批准所需事实。
- 记录 IPC、结构化克隆、renderer commit、主进程写放大和 event-loop delay；达到性能门槛即停止，不因测量结果扩展为另一套事实存储或交付系统。
