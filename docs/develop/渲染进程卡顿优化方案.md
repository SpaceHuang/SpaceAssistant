## 0. 问题与根因分析

### 0.1 现象

Agent 一轮中发生大量工具调用（典型场景：多轮 grep / read_file / run_shell，含大体积 grep 结果）时，聊天区滚动、输入、按钮响应明显卡顿，且随工具调用次数增多卡顿加剧。

### 0.2 数据链路与字节量级

一条 turn 的事实事件链路：

1. 主进程 `TurnRuntime.consume`（`electron/turnRuntime.ts:59-66`）每消费一个事实事件，经 `onEvent` 回调向渲染进程发送 `webContents.send('chat:turn-projection', { turn, event })`（`electron/main.ts:360-363`）。
2. 其中 `turn.assistantMessage` 是**含全部历史 tool result 的整条消息快照**。工具结果持续累积在同一条消息的 `toolCalls[].result.data` 中（reducer：`src/shared/assistantFactAggregator.ts:93-94`，`tool-result` 事件就地写入对应 toolCall）。
3. 单条工具结果体积可观：grep 单次输出上限约 400KB（`electron/tools/builtinExecutors.ts:827` 截断标记 `[输出过大，仅展示前 400KB]`），read_file 单次上限为 `READ_FILE_MAX_CHARS`。
4. 渲染端 `initTurnProjectionBridge`（`src/renderer/services/turnProjectionService.ts:42-56`）对每个事件**同步**执行：`routePatchMessage`（→ Redux dispatch）→ `pendingConfirmStore.syncFromProjection` → 终态/usage 处理，无 throttle / 合帧。

设一轮中有 N 个工具事件，第 k 个事件到达时快照体积约为 O(k · S)（S 为单条 result 平均体积），则整个 turn 的 IPC 序列化 + 结构化克隆 + 渲染端反序列化总字节量为 O(N² · S)。N=50、S=100KB 时，总传输量约 125MB，且每次反序列化都发生在渲染主线程，直接阻塞 UI。

### 0.3 三层叠加的渲染开销

| 层 | 代码证据 | 开销 |
| --- | --- | --- |
| IPC / 反序列化 | `electron/main.ts:360-363` 发送整条 assistantMessage | O(N²) 字节，主线程结构化克隆 |
| Redux / store | `chatSlice.patchMessage`（`src/renderer/store/chatSlice.ts:169-176`）经 `patchDisplayEntryMessage` 重建整个 displayEntries 数组并 `syncMessagesFromEntries` 重建 messages 数组；`pendingConfirmStore.syncFromProjection`（`src/renderer/services/pendingConfirmStore.ts:50-71`）每事件无条件 `notify()` | 每事件一次完整 dispatch + 订阅者通知 → ChatView 级重渲染 |
| React 组件 | `ChatBubble.tsx:236-265` `activityModel` useMemo 以 `message.toolCalls` 等为依赖，每事件全量重建时间线（`buildAssistantActivityTimeline` + `groupActivityTimeline`）；`ToolCallCard.tsx:89` 为普通函数组件、无 `React.memo`，N 张卡片每事件全量重渲染；展开卡片在 `ToolCallCard.tsx:287-298`（`resultStr` useMemo）、`571-578` 渲染处对大 result 做 `JSON.stringify` | 每事件 O(N) 卡片重渲染 + O(N) 时间线重建 |

此外主进程侧同样有放大：`checkpointTurnAtomically`（`electron/database/operations.ts:1136-1155`）把全部 toolCalls `JSON.stringify` 后同步写 SQLite；`tool-result`、`confirm-requested`、`tool-confirmed` 等事件属于立即 checkpoint 类别（`src/shared/turnCoordinator.ts:256-264`），每个 tool-result 都触发一次全量序列化写库（调度路径见 `src/shared/turnCoordinator.ts:266-303`）。主进程写库不是本次渲染卡顿的直接原因，但与改进项 1 的「大 result 瘦身」共享同一份数据结构调整。

### 0.4 结论

卡顿是「快照式 IPC（O(N²) 字节）× 逐事件同步 dispatch × 无 memo 的 N 卡片全量重渲染」三者相乘的结果。按收益排序的三个改进项：

1. **改进项 1**：turn-projection 快照 IPC 改增量 + 大 result 瘦身 —— 消除 O(N²) 字节根因。
2. **改进项 2**：渲染端事件合帧批处理 —— 把每事件一次 dispatch/commit 降为每帧一次。
3. **改进项 3**：流式气泡渲染优化（ToolCallCard memo + 时间线增量缓存）—— 把每事件 O(N) 组件工作降为 O(1) 摊销。

三项互相独立、可分批上线；改进项 1 收益最大但也涉及协议变化，改进项 2/3 是纯渲染端改动、风险低，应先落地兜底。

## 1. 改进项 1：turn-projection 快照 IPC 改增量 + 大 result 瘦身

### 1.1 问题定位

- `electron/main.ts:360-363`：`onEvent` 把剥掉 `executionConfig` 的完整 `TurnStarted`（含 `assistantMessage` 全文）发给渲染进程。
- `src/shared/assistantFactAggregator.ts:62-126`：reducer 本身是增量的（每事件只改一处），但投影协议丢弃了这个增量信息，改为整包重发。
- `src/renderer/services/turnProjectionService.ts:42-56`：渲染端拿到快照后整体 patch，无法利用「本次只有一条 toolCall 变了」。

### 1.2 优化方案

采用**分层增量协议**：投影事件不再携带整条消息，而是携带「事件本身 + 该事件对消息的最小补丁」。快照只在新订阅者加入（`chatListActiveTurns` 冷启动）时发送。

#### 1.2.1 新事件负载设计（`src/shared/` 新增 `turnProjectionProtocol.ts`）

渲染端本地维护「投影中的 assistant 消息」组装器，复用主进程同一个 reducer 保证两端事实一致：

```ts
// 与 AssistantFactEvent 一一对应，但负载已经过瘦身
export type TurnProjectionEventPayload =
  | { type: 'content-delta'; text: string }
  | { type: 'thinking-delta'; text: string }
  | { type: 'tool-use'; id: string; toolName: string; input: Record<string, unknown>; riskLevel?: ToolRiskLevel }
  | { type: 'tool-progress'; id: string; seq: number; text: string }
  | { type: 'confirm-requested'; id: string; /* 完整确认字段，体积小，不裁剪 */ }
  | { type: 'tool-confirmed'; id: string; approved: boolean; reason?: string }
  | { type: 'tool-result'; id: string; result: ProjectedToolResult }   // 见 1.2.2 瘦身
  | { type: 'usage-updated'; usage: SessionUsage; projected?: boolean }
  | { type: 'skill-hint'; text: string }
  | { type: 'source-completed' | 'source-failed' | 'source-cancelled' | 'source-timeout' }

export type TurnProjectionFrame = {
  turnId: string
  requestId: string
  sessionId: string
  assistantMessageId: string
  version: number        // 单调递增；缺口检测依据
  event: TurnProjectionEventPayload
}

// 冷启动 / 缺口重拉的完整快照（现状 chatListActiveTurns 的语义保留）
export type TurnProjectionSnapshot = {
  turnId: string; requestId: string; sessionId: string
  assistantMessage: Message   // 完整快照，仅在 snapshot 通道出现
  version: number
}
```

关键点：**渲染端复用 `reduceAssistantFact`**。该 reducer 已在 `src/shared/`，是纯函数，渲染端对本地保存的消息副本执行同一 reducer，可保证与主进程逐字节一致，不需要为投影发明第二套合并逻辑。这也消除了「渲染端组装与主进程事实漂移」的风险——两端跑的是同一份代码。

#### 1.2.2 大 result 瘦身（`ProjectedToolResult`）

`tool-result` 是字节量主体。分两级处理：

- **投影内联上限**：`result.data` 序列化后超过阈值（建议 64KB，常量 `PROJECTION_INLINE_RESULT_MAX_BYTES`）时，投影中替换为 `{ ref: { kind: 'tool-result', turnId, toolCallId }, preview: string（前 2KB）, byteSize: number, truncated: true }`。完整数据渲染端按需经新 IPC `chatGetToolResult({ messageId, toolCallId })` 拉取（从 DB 读该消息的对应 toolCall，主进程已有 `getMessage`）。
- **DB 层不动**：`checkpointTurnAtomically` 仍写完整消息（包括完整 result）。DB 是事实源，投影只是视图协议；这样不改持久化格式、不影响搜索语料、不影响 `sessions/<id>-<date>/` 明文备份。

不做「大结果落盘为 artifact、消息里只存引用」的持久化结构改造——那会同时牵动 DB schema、API 上下文（模型需要看到完整 result）、搜索和备份，远超本次范围。仅投影层瘦身即可消除 IPC 字节量。

#### 1.2.3 主进程改动点

| 文件 | 改动 |
| --- | --- |
| `electron/turnRuntime.ts` | `onEvent` 回调签名增加投影 frame 构造；瘦身在发往渲染前的边界函数 `toProjectionFrame(turn, event)` 中完成（新文件 `electron/turnProjectionFrame.ts`），不污染 Runtime |
| `electron/main.ts:360-363` | 改为发送 `TurnProjectionFrame`；`usage-updated` 等不改消息的事件只发标量 |
| `electron/preload.ts` / `src/shared/api.ts` | `chat:turn-projection` 负载类型更换；新增 `chatGetToolResult` invoke 通道 |
| `electron/appIpc.ts` | 注册 `chat:get-tool-result` handler（读 DB 消息，校验 session 归属） |

瘦身边界函数必须是纯函数并单测：给定 `AssistantFactEvent` + 当前消息，产出 frame，断言大 result 被替换为 ref + preview。

#### 1.2.4 渲染端改动点

| 文件 | 改动 |
| --- | --- |
| `src/renderer/services/turnProjectionService.ts` | 维护 `projectedMessages: Map<turnId, Message>`；每事件调 `reduceAssistantFact` 本地推进，再 `routePatchMessage`；保留 version 单调去重逻辑（现有 `versions` Map 复用） |
| `src/renderer/services/pendingConfirmStore.ts` | `syncFromProjection` 输入改为本地组装出的消息（接口不变） |
| `ToolCallCard` 等消费 `result.data` 的组件 | 遇到 `ref` 形态时展示 preview + 「加载完整结果」按钮，点击后调 `chatGetToolResult` 并缓存（配合改进项 3 的 useMemo） |

#### 1.2.5 断线 / 重连一致性

- **version 缺口检测**：渲染端记录每个 turnId 已应用的 version；收到 `version > local + 1` 的 frame 时，说明中间丢帧（窗口重建、事件在订阅前发出），立即走 `chatListActiveTurns` 重拉快照重建该 turn 的本地消息，再应用后续 frame。现有「先订阅再请求 snapshot、按 version 择新」机制（`turnProjectionService.ts:60-66`）原样保留。
- **与 `checkpointTurnAtomically` 的一致性**：checkpoint 写 DB 的是主进程 reducer 产物；渲染端本地 reducer 产物只用于显示，不回写 DB。两者由同一份 `reduceAssistantFact` 保证等价。turn 终态后渲染端丢弃本地组装副本，后续一律以 DB / snapshot 为准。
- **对下游的影响**：`apiContextService.cloneMessage`（`src/renderer/services/apiContextService.ts:45`）等消费者拿到的是 `routePatchMessage` 写入的完整 `Message` 对象，协议变化对其透明。唯一要注意的是投影中的 `ref` 形态不能泄漏进 API overlay——因此渲染端本地 reducer 应用事件时应使用**瘦身前**的 result（frame 里带 `ref` 时，渲染端本地消息也存 ref + preview；API 上下文对当前 turn 的 assistant 消息本就不依赖流式中间态，终态后从 DB 读取完整消息）。若审计后发现 overlay 确实可能读到流式中间态的 tool result，则在 `routePatchApiContextMessage` 前用 DB 终态消息校准，作为防御。

### 1.3 兼容性 / 风险分析

| 风险 | 评估与对策 |
| --- | --- |
| 两端 reducer 漂移 | 复用同一 `reduceAssistantFact` 纯函数，禁止渲染端自写合并逻辑；共享单测 fixture 同时跑两端 |
| 大 result 按需加载失败 | `chatGetToolResult` 失败时卡片展示 preview + 错误提示，不阻塞其余 UI；消息本身的 status/label 不依赖 result 全文 |
| 远程会话（飞书/微信 lane） | 远程 lane 不消费 `chat:turn-projection` 渲染通道，只走主进程内部 listener；协议变化不影响远程桥接 |
| 测试面 | 现有 `turnProjectionService.test.ts`、`turnProjectionConfirmLifecycle.test.ts` 需要迁移到 frame 协议；fixture 构造工作量集中在测试 |
| 事件顺序 | frame 仍由同一 `webContents.send` 顺序发出，IPC 有序性不变；version 缺口检测兜底 |

### 1.4 验收标准

- **单事件 IPC 字节量上限**：构造 50 次工具调用、每条 grep result 400KB 的 fixture，统计 `chat:turn-projection` 单事件负载，`content-delta` / `tool-progress` 事件 ≤ 8KB，`tool-result` 事件 ≤ 64KB + preview 开销；整轮累计字节量从 O(N²·S) 降为 O(N·S_inline)，50×400KB 场景总传输 < 4MB（现状约 125MB）。
- **渲染端单事件处理耗时**：`TurnProjectionMetric.durationMs`（现有埋点，`turnProjectionService.ts:30-36`）p95 < 4ms。
- **正确性**：50 次工具调用结束后，渲染端显示的消息与 DB 中 `getMessage` 读出的消息深度相等（result 的 ref 形态除外，按 toolCallId 比对 preview/byteSize）。
- **缺口重拉**：单元测试模拟 version 跳号，断言触发 snapshot 重拉且最终状态一致。

### 1.5 工作量粗估

约 3～4 人日：协议类型与瘦身纯函数 0.5 日，主进程接线 0.5 日，渲染端组装器 + version 缺口处理 1 日，ToolCallCard 按需加载 0.5 日，测试迁移与新增 1～1.5 日。

## 2. 改进项 2：渲染端事件合帧批处理

### 2.1 问题定位

- 每个 IPC 事件是独立 macrotask，`turnProjectionService.apply`（`turnProjectionService.ts:42-56`）逐事件同步执行一次完整 Redux dispatch + store notify + React commit。
- `pendingConfirmStore.syncFromProjection`（`pendingConfirmStore.ts:50-71`）无论确认列表是否变化都 `this.notify()`（70 行），导致 `usePendingConfirmSnapshot` 订阅方（ChatView 等）每事件重渲染。
- `ChatView` 中 `contextScalars`（`ChatView.tsx:139-142`，`selectContextSummaryScalars`，定义在 `src/renderer/services/contextHistorySummaryService.ts:137`）随每次投影消息 patch 重新计算。

### 2.2 优化方案

#### 2.2.1 合帧调度器（`turnProjectionService.ts`）

把 `apply` 拆成「入队」与「flush」两阶段：

```ts
type QueuedProjection = { frame: TurnProjectionFrame; receivedAt: number }

// 每个 turnId 一条队列；事件先进队列，按 rAF（窗口可见）或 16ms setTimeout 合帧
const queues = new Map<string, QueuedProjection[]>()
let flushScheduled = false
```

flush 时对每个 turn 的队列做：

1. **消息 patch 合并**：队列内全部事件依次过 `reduceAssistantFact` 推进本地消息（纯函数，廉价），最终只对最终消息做一次 `routePatchMessage` → 一帧最多一次 dispatch。
2. **即时事件直通**：`confirm-requested`、`tool-confirmed`、`source-completed/failed/cancelled/timeout` 不入队等待——confirm 事件到达时立即 flush 当前队列后同步处理（确认弹窗是交互入口，延迟 16ms 虽可接受，但直通实现更简单且无歧义）；终态事件 flush 后立即处理并清掉该 turn 队列。
3. **usage-updated 合并**：一帧内多个 usage 事件只保留最后一个（现状 `applyProjectedUsage` 有 `window.api.usageSet` 回写，降频同时减少 IPC 回写次数）。
4. **指标**：`TurnProjectionMetric` 增加 `mergedCount` 字段，便于回归观测合帧率。

注意与改进项 1 的关系：即使改进项 1 尚未落地（仍是快照协议），合帧也成立——快照天然可合并，一帧内多个快照只保留 version 最大的一个即可。因此改进项 2 可以先于改进项 1 独立上线。

#### 2.2.2 pendingConfirmStore 浅比较（`pendingConfirmStore.ts`）

`syncFromProjection` 在重建 `next` 列表后与现有项做逐字段浅比较（key：`requestId + toolUseId`，字段：`toolName/riskLevel/status 相关标量`，`input`/`diff` 等对象比较引用—— reducer 对未变化的 toolCall 复用引用，见下文 2.2.3）：无变化则不写回、不 notify。`remove`/`rejectAllForSession` 已有「长度变化才 notify」的先例（114-124 行），语义对齐。

#### 2.2.3 引用稳定性前置

合帧的收益依赖「未变化的 toolCall 对象引用不变」。两处保证：

- 主进程/本地 reducer：`reduceAssistantFact` 对各事件类型用 `map` 且对未命中项返回原对象（`assistantFactAggregator.ts:92-116` 已是此形态），天然满足。
- Redux patch 路径：`patchDisplayEntryMessage` 每次重建 displayEntries/messages 数组，但 entry.message 的替换只发生在目标 id 上；确认未变化的 message 对象引用在 patch 后保持（若现有实现已满足则只需补测试断言，不满足则在 `patchMessage` 内对未命中 entry 复用原引用）。

#### 2.2.4 contextScalars 降频

`selectContextSummaryScalars` 的计算挂在 ChatView 渲染路径上；合帧后投影 patch 频率已降为每帧一次，该项随之自然降频，无需单独改造。若 profiler 仍显示其为热点，再考虑把摘要服务改为外部 store + `useSyncExternalStore` 按值订阅（列为可选后续，不在本项默认范围）。

### 2.3 兼容性 / 风险分析

| 风险 | 评估与对策 |
| --- | --- |
| 确认弹窗延迟 | confirm 事件直通（flush 后立即处理），不进入等待队列；新增测试断言「confirm-requested 到达后同一 microtask 内 pendingConfirmStore 可见」 |
| 终态丢失 | 终态事件触发 flush + 立即处理 + 清理队列；dispose / 会话切换时 flush 所有残留队列 |
| 合帧导致「打字机」观感变化 | 文本 delta 从「每事件一帧」变「每帧一批」，16ms 窗口下用户无感知；如主进程事件本身突发到达，观感反而更平滑 |
| rAF 在后台标签/隐藏窗口不触发 | Electron 单窗口隐藏时 `backgroundThrottling` 生效；合帧调度需回退 `setTimeout(16ms)`，保证后台会话的 pendingConfirm/usage 状态仍推进 |

### 2.4 验收标准

- **dispatch 频率**：50 次工具调用 + 穿插 content-delta 的 fixture，Redux `patchMessage` dispatch 次数 ≤ 事件数 / 4，且每 16ms 窗口内 ≤ 1 次。
- **notify 频率**：无确认状态变化的事件流期间，`pendingConfirmStore` notify 次数为 0。
- **即时性**：`confirm-requested` 事件到 `pendingConfirmStore.getItems()` 可见的延迟 < 1ms（同步直通）；终态事件到达后 `chatStatus` 在同一帧内更新。
- **回归**：现有 `turnProjectionService.test.ts`、`turnProjectionConfirmLifecycle.test.ts`、`pendingConfirmStore.test.ts` 全部通过（用 fake timers / 手动 rAF 驱动）。

### 2.5 工作量粗估

约 1.5～2 人日：合帧调度器 1 日，pendingConfirmStore 浅比较 0.5 日，测试调整 0.5 日。

## 3. 改进项 3：流式气泡渲染优化（ToolCallCard memo + 时间线增量缓存）

### 3.1 问题定位

- `ChatBubble.tsx:236-265`：`activityModel` useMemo 依赖 `message.toolCalls` 数组引用，投影 patch 每事件产生新数组 → 每事件全量执行 `buildAssistantActivityTimeline` + `groupActivityTimeline`，N 个 toolCall 时 O(N)。
- `ToolCallCard.tsx:89`：普通函数组件，无 `React.memo`；ChatBubble 每次重渲染时 N 张卡片全部重渲染。卡片内部 `label`/`paramPreview`/`resultStr` 等 useMemo（267-298 行）因 `record` 引用未变时可命中，但组件函数体本身（含大量状态判定、`resolveEffectiveShellOutputMode` 等）仍每事件执行 N 次。
- 展开卡片的大 result：`resultStr` useMemo（287-298 行）以 `record.result` 引用为依赖，引用稳定时不会重复 `JSON.stringify`；但渲染处 `truncate(displayedResultText, 4000)`（571-578 行）截断后仍生成大字符串，且 `displayedResultText` 在搜索态下可能携带完整文本。

### 3.2 优化方案

#### 3.2.1 ToolCallCard 加 React.memo

`ToolCallCard` 导出改为 `memo(function ToolCallCard(...) {...}, comparator)`。comparator 采用显式字段比较（与 `ChatBubble` 底部 524-542 行的既有风格一致）：

- `record`（引用比较即可，依赖 2.2.3 的引用稳定性保证）、`confirmMode`、`focus`、`workDir`、`shellConfig`、`sessionMetadata`、`messageId`、`sessionId`、`activeSearchTarget`；
- `onConfirm`/`onCancel`/`onOpenFile`：ChatBubble 内联箭头函数（`ChatBubble.tsx:397-406`）每渲染生成新引用，会击穿 memo——需上移到 ChatBubble 层用 `useCallback` 按 `(toolId, approved)` 形态稳定化，或改为传 `confirmTool`/`cancelTool` 原函数 + `record.id`，在卡片内部绑定。
- `toolCalls` prop（仅 `handleTerminalBeforeDispose` 用于 scrollback 回写，`ToolCallCard.tsx:192-206`）：传整个数组会每事件变化，改为传「写回调」或在 effect 内通过 ref 读取最新数组，从 props 中移除。

#### 3.2.2 时间线增量缓存

`buildAssistantActivityTimeline` 的输出具有追加特性：toolCalls/skillHints 只增不减，新事件只影响尾部（最后一个 toolCall 状态翻转、新 toolCall 追加、segment 关闭）。在 `ChatBubble` 中以 useRef 缓存上一次输入（`toolCalls` 长度、末条 toolCall 的 id+status、content/thinking 尾段引用）与输出，命中「纯追加」时只重建尾部条目并复用前缀数组（前缀条目的对象引用不变，`groupActivityTimeline` 分组结果中已完成批次也可整体复用）。

实现位置：把增量逻辑放在 `src/shared/assistantActivityTimeline.ts` 的包装函数 `appendActivityTimeline(prev, message)`（纯函数，可单测），ChatBubble 侧只负责用 useRef 持有 prev。若审计后发现「纯追加」判定分支复杂易错，退化为：timeline 条目级 memo——以每个 toolCall 的引用为 key 缓存其渲染入参，时间线仍全量构建但条目对象复用，配合 3.2.1 的 memo 使卡片不渲染。**优先做条目级 memo，增量构建仅在 profiler 证明时间线构建本身是热点后再做。**

#### 3.2.3 大 result 渲染按需化

- `resultStr` useMemo 已有引用缓存，保留；补充：当 result 序列化后超过阈值（与改进项 1 的 64KB 对齐）且用户未展开时，不生成完整字符串（现状 `showDetail` 已短路，确认无遗漏分支即可）。
- 展开时超长文本默认只渲染前 4000 字符（现有 `truncate` 行为）+ 「查看完整内容」入口（配合改进项 1 的 `chatGetToolResult` / artifact 路径）。
- 搜索态 `displayedResultText` 携全文的分支（313-315 行）仅在命中片段时启用，保持现状。

### 3.3 兼容性 / 风险分析

| 风险 | 评估与对策 |
| --- | --- |
| memo 比较遗漏导致卡片不更新 | comparator 显式列出全部 props，参考 ChatBubble 既有比较器；为 confirming→executing→completed 各状态迁移写 render probe 测试 |
| onConfirm 稳定化改变确认行为 | 确认/取消回调语义不变，仅绑定位置移动；现有 confirm 生命周期测试（`turnProjectionConfirmLifecycle.test.ts`）兜底 |
| scrollback 回写 | `patchShellTerminalScrollback` 需要最新 toolCalls 数组；改用 ref 读取保证写到的是最新引用，行为不变 |
| 增量时间线边界 | 纯追加判定失败时必须回退全量重建，不允许产出缺条目的时间线；共享 fixture 比对全量/增量输出一致性 |

### 3.4 验收标准

- **卡片渲染次数**：50 张 ToolCallCard 的 fixture 中，单条新 tool-result 事件（经合帧）到达后，重渲染的卡片数 ≤ 2（新追加 + 状态翻转的那张），render probe 断言。
- **时间线构建**：纯追加事件不触发前缀条目对象重建（引用相等断言）；100 个活动条目的气泡，单帧内 `activityModel` 相关耗时 < 2ms。
- **大 result**：展开含 400KB result 的卡片，首次展开 JSON.stringify 只发生一次；折叠/展开切换不重复计算。

### 3.5 工作量粗估

约 2 人日：ToolCallCard memo + 回调稳定化 1 日，条目级 memo / 时间线缓存 0.5 日，render probe 测试 0.5 日。

## 4. 实施顺序与回归测试要点

### 4.1 实施顺序（Phase 划分）

| Phase | 内容 | 上线性质 | 粗估 |
| --- | --- | --- | --- |
| Phase 1 | 改进项 2（合帧 + pendingConfirmStore 浅比较） | 纯渲染端，快照协议下即生效，先行兜底 | 1.5～2 人日 |
| Phase 2 | 改进项 3（ToolCallCard memo + 条目级时间线缓存） | 纯渲染端，与 Phase 1 可并行开发 | 2 人日 |
| Phase 3 | 改进项 1（增量 frame 协议 + 大 result 瘦身 + 按需拉取） | IPC 协议变化，最后做；落地后 Phase 1 的合帧逻辑从「快照择新」切换为「frame 归并」，接口已预留 | 3～4 人日 |

理由：Phase 1/2 不改协议、风险低，落地后即使 Phase 3 延期，卡顿也已大幅缓解（每帧一次 commit + 卡片 memo 消除 O(N) 渲染）；Phase 3 解决字节量根因，但需要跨进程改协议与测试迁移，放在性能基线已建立之后便于量化对比。

每 Phase 收尾建议建立与 `chat-message-list-*-remeasure-gate.md` 同款的门禁复测记录：固定 fixture（50 次工具调用、含 400KB grep result）前后对比 React commit p95、长任务数、IPC 累计字节量。
