## 0. 问题与根因分析

### 0.1 现象

Agent 一轮中发生大量工具调用（典型场景：多轮 grep / read_file / run_shell，含大体积 grep 结果）时，聊天区滚动、输入、按钮响应明显卡顿，且随工具调用次数增多卡顿加剧。

### 0.2 数据链路与字节量级

一条 turn 的事实事件链路：

1. 主进程 `TurnRuntime.consume`（`electron/turnRuntime.ts:59-66`）每消费一个事实事件，经 `onEvent` 回调向渲染进程发送 `webContents.send('chat:turn-projection', { turn, event })`（`electron/main.ts:360-363`）。
2. 其中 `turn.assistantMessage` 是**含全部历史 tool result 的整条消息快照**。工具结果持续累积在同一条消息的 `toolCalls[].result.data` 中（reducer：`src/shared/assistantFactAggregator.ts:93-94`，`tool-result` 事件就地写入对应 toolCall）。
3. 单条工具结果体积可观：grep 单次输出上限约 400KB（`electron/tools/builtinExecutors.ts:827` 截断标记 `[输出过大，仅展示前 400KB]`），read_file 单次上限为 `READ_FILE_MAX_CHARS`。
4. 渲染端 `initTurnProjectionBridge`（`src/renderer/services/turnProjectionService.ts:42-56`）对每个事件**同步**执行：`routePatchMessage`（→ Redux dispatch）→ `pendingConfirmStore.syncFromProjection` → 终态/usage 处理，无 throttle / 合帧。

设一轮中有 N 个工具事件，第 k 个事件到达时快照体积约为 O(k · S)（S 为单条 result 平均体积），则整个 turn 的 IPC 序列化 + 结构化克隆 + 渲染端反序列化总字节量为 O(N² · S)。N=50、S=100KB 时，总传输量约 125MB，且每次反序列化都发生在渲染主线程，直接阻塞 UI。

### 0.3 三层叠加的渲染开销

| 层 | 代码证据 | 开销 |
| --- | --- | --- |
| IPC / 反序列化 | `electron/main.ts:360-363` 发送整条 assistantMessage | O(N²) 字节，主线程结构化克隆 |
| Redux / store | `chatSlice.patchMessage`（`src/renderer/store/chatSlice.ts:169-176`）经 `patchDisplayEntryMessage` 重建整个 displayEntries 数组并 `syncMessagesFromEntries` 重建 messages 数组；`pendingConfirmStore.syncFromProjection`（`src/renderer/services/pendingConfirmStore.ts:50-71`）每事件无条件 `notify()` | 每事件一次完整 dispatch + 订阅者通知 → ChatView 级重渲染 |
| React 组件 | `ChatBubble.tsx:236-265` `activityModel` useMemo 以 `message.toolCalls` 等为依赖，每事件全量重建时间线（`buildAssistantActivityTimeline` + `groupActivityTimeline`）；`ToolCallCard.tsx:89` 为普通函数组件、无 `React.memo`，N 张卡片每事件全量重渲染；展开卡片在 `ToolCallCard.tsx:287-298`（`resultStr` useMemo）、`571-578` 渲染处对大 result 做 `JSON.stringify` | 每事件 O(N) 卡片重渲染 + O(N) 时间线重建 |

此外主进程侧同样有放大：`checkpointTurnAtomically`（`electron/database/operations.ts:1136-1155`）把全部 toolCalls `JSON.stringify` 后同步写 SQLite；`tool-result`、`confirm-requested`、`tool-confirmed` 等事件属于立即 checkpoint 类别（`src/shared/turnCoordinator.ts:256-264`），每个 tool-result 都触发一次全量序列化写库（调度路径见 `src/shared/turnCoordinator.ts:266-303`）。主进程写库不是本次渲染卡顿的直接原因，但与改进项 1 的「大 result 瘦身」共享同一份数据结构调整。

### 0.4 结论

卡顿是「快照式 IPC（O(N²) 字节）× 逐事件同步 dispatch × 无 memo 的 N 卡片全量重渲染」三者相乘的结果。按收益排序的三个改进项：

1. **改进项 1**：turn-projection 快照 IPC 改增量 + 大 result 瘦身 —— 消除 O(N²) 字节根因。
2. **改进项 2**：渲染端事件合帧批处理 —— 把每事件一次 dispatch/commit 降为每帧一次。
3. **改进项 3**：流式气泡渲染优化（ToolCallCard memo + 时间线增量缓存）—— 把每事件 O(N) 组件工作降为 O(1) 摊销。

三项按基础设施、旧协议优化、新协议切换分阶段上线；改进项 2/3 只有在投影基础设施和 identity 归一化就绪后才具备独立验收条件。

## 0.5 投影一致性模型（所有后续章节的约束源）

### 0.5.1 不变量

1. 事实唯一性：只有主进程 `TurnCoordinator`/DB 产生或持久化领域 `Message`；renderer 不生成事实 ID、时间戳、状态转换或 segment 边界。
2. 投影隔离：`ProjectedMessage`、ref、preview 和加载态只能存在于 renderer projection store/result cache，不能进入 `Message`、DB、备份或模型上下文。
3. 单调显示：同一 turn 的可见状态不得从高版本回退到低版本；恢复、分页和终态接管均遵守此规则。
4. 终态闭合：只有事实提交屏障完成并 adopted/released 后，才能解除 running 并推进 queued drain。
5. 工具结果不可变：tool call 进入 terminal 后，其 `resultRevision` 固定；无关 frame 不使其缓存失效。
6. 有界性：frame/recovery buffer、projection store、result cache 和归一化工作均有 per-turn 与全局数量/字节上限。

### 0.5.2 版本语义

| 概念 | 作用域 | 用途 | 规则 |
| --- | --- | --- | --- |
| `frameSeq` | turn | IPC 顺序、去重、缺口检测 | 连续递增 |
| `coveredFrameSeq` | turn | snapshot 覆盖范围 | 可覆盖 `<=` 的 frameSeq |
| `resultRevision` | tool call | result cache/ref 身份 | terminal 后固定、精确匹配 |
| `commitVersion` | 持久化 turn/message | 证明事实已提交 | 接管要求 `>= expected` |
| `displayGeneration` | renderer view | 防止页面异步结果回写 | 仅由 renderer 校验 |
| `turnLifecycleToken` | session/turn | 保护后台 turn 异步流程 | 随 turn 生命周期固定 |

任何 cache key、恢复判断或 IPC 参数必须使用对应语义，禁止用一个通用 `version` 代替。

### 0.5.3 状态所有权矩阵

| 状态 | 权威/用途 | 唯一 Writer | Reader | 可含 ref |
| --- | --- | --- | --- | --- |
| Runtime turn | 主进程实时事实 | `TurnCoordinator` | projection/terminal IPC | 否 |
| DB `Message` | 持久化事实、API baseline | DB 层 | API、历史分页 | 否 |
| API overlay | 未被 baseline 覆盖的领域消息 | message gateway | API context resolver | 否 |
| Projection overlay | 流式展示派生状态 | projection store | display selector | 是 |
| Redux display base | 领域展示状态 | chat slice | display selector | 否 |
| Tool-result cache | renderer 展开数据 | result loader | `ToolCallCard` | 是 |
| Pending confirms | 确认索引 | projection reconciler | 确认 UI | 不需要 |

`routePatchMessage` 只写领域路径；`routePatchProjectedMessage` 只写 projection；`adoptTurnProjection` 只原子更新 Redux 内部的领域 base 与 projection slice，绝不声称能事务性更新模块级 API overlay。

### 0.5.4 统一状态转移

| 当前状态 | 输入 | 动作 | 下一状态 |
| --- | --- | --- | --- |
| streaming | 连续 `frameSeq` | 入队/合帧应用 | streaming |
| streaming | `frameSeq > expected` | 有界缓存并请求 snapshot | recovering |
| recovering | frame | 有界缓存，不更新可见事实 | recovering |
| recovering | snapshot | 裁剪旧帧、连续重放 | streaming / terminal-projected / recovering |
| streaming | 连续 terminal frame | 保留 terminal projection，请求 commit | committing |
| committing | frame/snapshot | 按版本校准，不提前 release | committing |
| committing | committed `Message` | 校验后 Redux 内原子接管 | adopted |
| adopted | release barrier | 清 running，允许 queued drain | released |
| 任意活动态 | buffer/cache 超限或不可恢复错误 | 保留最后安全视图，允许重试 | recovery-failed / commit-failed |
| recovery-failed | retry | 清 buffer，重新请求 snapshot | recovering |
| commit-failed | retry | 复用同一 requiredCommitVersion waiter | committing |
| failed | cancel/abandon | 向主进程确认终态，reject confirms，清理并释放 | released |
| failed | retry 次数耗尽 | 等待用户 retry 或 cancel/abandon，不自动 drain | failed |

确认即时处理仅适用于连续 frame 且非 recovering；终态也不得绕过此表。

## 1. 改进项 1：turn-projection 快照 IPC 改增量 + 大 result 瘦身

### 1.1 问题定位

- `electron/main.ts:360-363`：`onEvent` 把剥掉 `executionConfig` 的完整 `TurnStarted`（含 `assistantMessage` 全文）发给渲染进程。
- `src/shared/assistantFactAggregator.ts:62-126`：reducer 本身是增量的（每事件只改一处），但投影协议丢弃了这个增量信息，改为整包重发。
- `src/renderer/services/turnProjectionService.ts:42-56`：渲染端拿到快照后整体 patch，无法利用「本次只有一条 toolCall 变了」。

### 1.2 优化方案

采用**分层增量协议**：投影事件不再携带整条消息，而是携带主进程 reducer 已经确定好的「事件语义 + 最小补丁」。快照用于新订阅者加入和缺帧恢复，且必须覆盖活动态与最近终态；不得继续把 `chatListActiveTurns` 作为唯一恢复源。

#### 1.2.1 确定性投影 patch（`src/shared/` 新增 `turnProjectionProtocol.ts`）

渲染端本地维护独立的 renderer-only view model，并按主进程生成的确定性 patch 更新。持久化 `Message` 始终只包含 `ToolCallResultPersisted`；投影 ref 不进入该类型、Redux 的领域消息或 API overlay。

```ts
export type ProjectedMessage = Omit<Message, 'toolCalls'> & {
  toolCalls?: ProjectedToolCallRecord[]
}

export type ProjectedToolResultRef = {
  kind: 'tool-result'
  turnId: string
  toolCallId: string
  resultRevision: string
}

export type ProjectedToolResult =
  | { kind: 'legacy-inline'; value: ToolCallResultPersisted }
  | { kind: 'inline'; resultRevision: string; value: ToolCallResultPersisted }
  | { kind: 'ref'; resultRevision: string; ref: ProjectedToolResultRef; preview: string; byteSize: number; truncated: true }

// revision 只属于已存在的 result；calling/confirming/executing record 合法地没有 result。
export type ProjectedToolCallRecord = Omit<ToolCallRecord, 'result'> & {
  result?: ProjectedToolResult
}
```

frame 描述 reducer 前后状态差异；renderer 只执行字段赋值、按 ID 完整替换或追加，不推断业务状态。

```ts
// 与 AssistantFactEvent 一一对应，但负载已经过瘦身。
// 所有会影响事实状态的时间戳、ID、状态转换结果由主进程生成。
export type TurnProjectionPatch = {
  // message 为 reducer 产出的完整字段替换值；包含 segment 边界和终态 status。
  message?: Partial<Pick<ProjectedMessage, 'content' | 'contentSegments' | 'thinking' | 'skillHints' | 'status'>>
  // record 为按 id 完整替换值，包含 status、confirmedAt/completedAt、进程身份字段及瘦身后的 result。
  toolCall?: { id: string; record: ProjectedToolCallRecord }
  usage?: SessionUsage
  requiredCommitVersion?: number // 仅 terminal patch；来自主进程 checkpoint tracker
}

export type TurnProjectionFrame = {
  turnId: string
  requestId: string
  sessionId: string
  assistantMessageId: string
  frameSeq: number
  coveredFrameSeq?: number
  eventType: AssistantFactEvent['type']
  patch: TurnProjectionPatch
}

// 冷启动 / 缺口重拉的完整快照；可覆盖活动态和最近终态。
export type TurnProjectionSnapshot = {
  turnId: string; requestId: string; sessionId: string
  assistantMessage: ProjectedMessage   // renderer-only 快照，仅在 projection 通道出现
  coveredFrameSeq: number
}
```

关键点：**渲染端不重新执行事实 reducer**。`reduceAssistantFact` 的 `now`、`createId` 等依赖会影响时间戳、ID、segment 边界和 duration；即使两端调用同一函数，也不能保证结果一致。主进程必须在 reducer 执行后生成带确定值的 patch（例如完整 `ToolCallRecord`、`SkillHintRecord` 和终态字段），渲染端只按 patch 更新 view model。共享 reducer 继续用于主进程事实构建和协议 fixture 校验，但不能作为渲染端事实重建机制。

#### 1.2.2 大 result 瘦身（`ProjectedToolResult`）

`tool-result` 是字节量主体。分两级处理。投影 ref 只存在于 `ProjectedMessage`，完整结果加载后写入 renderer 专用缓存，不回写持久化消息：

- **投影内联上限**：`result.data` 序列化后超过阈值（建议 64KB，常量 `PROJECTION_INLINE_RESULT_MAX_BYTES`）时，投影中替换为 `{ ref: ProjectedToolResultRef, preview: string（前 2KB）, byteSize: number, truncated: true }`。完整数据渲染端按需经新 IPC `chatGetToolResult({ messageId, toolCallId, expectedResultRevision, displayGeneration })` 拉取；返回值必须带 `resultRevision`，renderer 仅在 revision 与 generation 均匹配时写入 result cache。内联小结果同样携带 `resultRevision`，但不要求单独加载。
- **DB 层不动**：`checkpointTurnAtomically` 仍写完整消息（包括完整 result）。DB 是事实源，投影只是视图协议；这样不改持久化格式、不影响搜索语料、不影响 `sessions/<id>-<date>/` 明文备份。

不做「大结果落盘为 artifact、消息里只存引用」的持久化结构改造——那会同时牵动 DB schema、API 上下文（模型需要看到完整 result）、搜索和备份，远超本次范围。仅投影层瘦身即可消除 IPC 字节量。

#### 1.2.3 主进程改动点

| 文件 | 改动 |
| --- | --- |
| `electron/turnRuntime.ts` | `onEvent` 回调签名增加投影 frame 构造；瘦身在发往渲染前的边界函数 `toProjectionFrame(turn, event)` 中完成（新文件 `electron/turnProjectionFrame.ts`），不污染 Runtime |
| `electron/main.ts:360-363` | 改为发送 `TurnProjectionFrame`；`usage-updated` 等不改消息的事件只发标量 |
| `electron/preload.ts` / `src/shared/api.ts` | `chat:turn-projection` 负载类型更换；新增 `chatGetToolResult` invoke 通道 |
| `electron/appIpc.ts` | 注册 result、projection snapshot 和 complete-message handler；校验 session/generation/revision，并调用 committed tracker await API |
| `src/shared/turnCoordinator.ts` / `electron/checkpointQueue.ts` / `electron/committedVersionTracker.ts` | 记录 required/committed version，提供 checkpoint 完成等待、失败重试与重启恢复 |

瘦身边界函数必须是纯函数并单测：给定 `AssistantFactEvent` + 当前消息，产出 frame，断言大 result 被替换为 ref + preview。

主进程新增 `committedVersionTracker`（由 `TurnCoordinator`/`CheckpointQueue` 驱动），按 turn 保存 `requestedCommitVersion`、`committedVersion`、`inFlight`、`lastError` 和 waiters。terminal checkpoint 入队时写入 `requiredCommitVersion`，成功后更新 tracker 并 resolve 等待者；失败区分可重试与永久失败，进程重启后从 turn record 恢复 committedVersion。`chat:get-complete-turn-message` 只能调用 tracker 的 await API，禁止自行轮询 DB；多个 renderer 请求共享同一 waiter。

#### 1.2.4 渲染端改动点

| 文件 | 改动 |
| --- | --- |
| `src/renderer/services/turnProjectionService.ts` | 接收 frame 或 legacy snapshot，维护 `Map<turnId, ProjectedMessage>`，按 `turnLifecycleToken` 处理后台 turn；不得因 view generation 变化丢弃基线 |
| `src/renderer/store/turnProjectionSlice.ts` | 新增 renderer-only 状态：按 `sessionId/turnId/messageId` 保存 `ProjectedMessage`、version、生命周期和加载态；禁止与 `chatSlice.messages`/`displayEntries` 混用 |
| `src/renderer/store/turnProjectionSelectors.ts` | 提供按 messageId/turnId 查询投影、合成基础领域消息与投影字段的 selector；投影只覆盖同 ID 的 streaming assistant message |
| `src/renderer/services/chatRunnerService.ts` | 新增 `routePatchProjectedMessage`，只更新 projection slice/live projection，不调用 API overlay；`routePatchMessage` 继续只处理完整 `Message` |
| `src/renderer/components/Chat/ChatView.tsx` | 列表渲染时通过 selector/hook 合成 `DisplayProjectedMessage`，处理分页基础消息与活动 turn 投影的优先级 |
| `src/renderer/components/Chat/ChatBubble.tsx` / `ToolCallCard.tsx` | props 和 timeline 输入改为 `DisplayProjectedMessage`/`ProjectedToolCallRecord`；ref 使用 preview，完整结果来自 renderer 专用 result cache |
| `src/renderer/services/projectedToolResultStore.ts` | 按 `displayGeneration + sessionId + messageId + toolCallId + resultRevision` 缓存 preview/ref/full-data；加载结果只更新此 store，不更新领域消息 |
| `src/renderer/services/pendingConfirmStore.ts` | `syncFromProjection` 输入为投影确认投影，使用稳定 fingerprint 比较 |

合成规则：projection store 中存在活动 turn 时，selector 以分页/领域消息为基础，按 `assistantMessageId` 覆盖对应展示项；没有投影时直接返回领域消息。会话切换只卸载 UI 订阅，不清理后台 turn 的 projection、buffer 或 barrier；切回时按 session/turn 重新订阅。只有 turn released、明确删除/替换、应用级 dispose 或后台淘汰恢复流程才清理。终态 snapshot 到达并完成校准后，先用完整领域 `Message` 更新 `chatSlice`/API baseline，再删除该 turn 的 projection。

#### 1.2.5 断线 / 重连一致性

- **权威恢复接口**：新增 `chat:get-turn-projection-snapshot({ turnId })`，按 turnId 返回主进程内存中的活动态或最近终态快照；内存不存在时从 turn record/DB 恢复，并经过与 frame 相同的 result 瘦身函数。该接口不能过滤 `completed`/`failed`，并校验 session 与请求归属。
- **恢复状态机**：每个 turn 维护 `idle | recovering | failed` 状态；frame 缓存设数量和字节上限，超限即进入 `failed` 并清理队列。发现 `frameSeq > expectedFrameSeq` 后暂停应用并缓存后续 frame；快照返回后先应用 snapshot，再丢弃 `frameSeq <= coveredFrameSeq` 的缓存，按 `frameSeq` 连续重放剩余 frame。重放再次发现缺口时重新拉取快照；失败则展示可重试错误，不得静默保留 streaming 状态。
- **终态处理**：终态 frame 与普通 frame 走同一队列和版本裁剪流程，不得提前清空队列。若缺口后首先收到终态 frame，仍必须先取得覆盖终态的 snapshot，再完成重放和清理。
- **与 `checkpointTurnAtomically` 的一致性**：checkpoint 写 DB 的是主进程 reducer 产物；渲染端只应用主进程确定的 patch，不回写事实。snapshot 是恢复时的权威基线，终态后也以 snapshot/DB 结果校准。
- **API overlay 边界**：新增 `routePatchProjectedMessage`，只更新 renderer live/Redux projection store，禁止调用 `routePatchApiContextMessage`。`routePatchMessage`、DB patch、会话备份和 API overlay 继续只接受完整领域 `Message`；当前 turn 的完整 assistant message 只能从 DB/终态事实快照获取。
- **终态提交屏障与接管**：连续终态 frame 到达后保留 terminal projection，进入 `committing(expectedCommitVersion)`，调用 `chat:get-complete-turn-message({ turnId, expectedCommitVersion, displayGeneration })`。主进程仅在 checkpoint 完成且 `commitVersion >= expectedCommitVersion` 时返回完整领域 `Message`。renderer 校验 session、messageId、`displayGeneration` 和 commitVersion 后，以单一 `adoptTurnProjection` action 原子更新 Redux 内领域 base 并删除 projection；API overlay 不参与该 action，后续上下文统一读取已提交 DB baseline。成功后才 resolve `adoptionBarrierBySession`、release running 和 drain queue；失败或版本落后则保留终态 projection，进入可重试状态，不闪回或删除。

### 1.3 兼容性 / 风险分析

| 风险 | 评估与对策 |
| --- | --- |
| patch 与事实状态不一致 | patch 在主进程 reducer 后生成；共享协议 fixture 校验投影 patch 应用结果与主进程快照一致，禁止渲染端自行生成 ID/时间戳 |

### 1.4 验收标准

- **单事件 IPC 字节量上限**：构造 50 次工具调用、每条 grep result 400KB 的 fixture，统计 `chat:turn-projection` 单事件负载，`content-delta` / `tool-progress` 事件 ≤ 8KB，`tool-result` 事件 ≤ 64KB + preview 开销；整轮累计字节量从 O(N²·S) 降为 O(N·S_inline)，50×400KB 场景总传输 < 4MB（现状约 125MB）。
- **渲染端局部处理耗时**：`TurnProjectionMetric.durationMs` p95 < 4ms；另以 Long Task 与 React Profiler 门禁覆盖 IPC 反序列化和 React commit，不能仅凭该局部指标证明整体 p95。
- **正确性**：50 次工具调用结束后，渲染端 view model 与主进程权威 snapshot 逐字段一致；result 的 ref 仅允许存在于投影 view model，完整 result 通过带 `version` 的按需 IPC 获取并校验后缓存。
- **缺口恢复**：覆盖“缺口后立即终态”“恢复期间继续到帧”“snapshot 新于触发帧”“重复 delta/skill-hint 不重复应用”“再次缺口”和 snapshot 失败。
- **类型边界**：`ProjectedMessage` 与 `Message` 分离；`ProjectedToolResult` 保留 `success` 等判别字段但不能赋值给 `ToolCallResultPersisted`；投影更新后 UI 可读取 preview，API overlay、DB patch 和会话备份入口均不得收到 ref。

约 4～5 人日：协议类型与 patch 生成/瘦身纯函数 1 日，主进程接线与内存快照读取 0.5 日，渲染端机械应用与 version 恢复状态机 1～1.5 日，ToolCallCard 按需加载 0.5 日，测试迁移与新增 1～1.5 日。

## 2. 改进项 2：渲染端事件合帧批处理

Phase 1 仍使用旧协议适配类型 `QueuedSnapshotProjection`，不依赖 Phase 3 的 `TurnProjectionFrame`。adapter 将旧 `{ turn, event }` 转为内部快照操作：一帧只保留最高 version 的 snapshot，同时独立保留 usage、confirm 和终态事件语义；归一化后写入 Phase 0 的 projection store，不调用 API overlay。

### 2.1 问题定位

- 每个 IPC 事件是独立 macrotask，`turnProjectionService.apply`（`turnProjectionService.ts:42-56`）逐事件同步执行一次完整 Redux dispatch + store notify + React commit。
- `pendingConfirmStore.syncFromProjection`（`pendingConfirmStore.ts:50-71`）无论确认列表是否变化都 `this.notify()`（70 行），导致 `usePendingConfirmSnapshot` 订阅方（ChatView 等）每事件重渲染。
- `ChatView` 中 `contextScalars`（`ChatView.tsx:139-142`，`selectContextSummaryScalars`，定义在 `src/renderer/services/contextHistorySummaryService.ts:137`）随每次投影消息 patch 重新计算。

### 2.2 优化方案

#### 2.2.1 合帧调度器（`turnProjectionService.ts`）

把 `apply` 拆成「入队」与「flush」两阶段：

```ts
type QueuedProjection = { frame: TurnProjectionFrame; receivedAt: number }

// 每个 turnId 一条队列；事件先进队列，按 rAF（窗口可见）或 16ms setTimeout 合帧
const queues = new Map<string, (QueuedSnapshotProjection | QueuedProjection)[]>()
let flushScheduled = false
```

flush 时对每个 turn 的队列做：

1. **消息 patch 合并**：队列内按 version 顺序将每个 frame 的 `patch` 机械应用到内存 view model，最终只对最终投影视图调用 `routePatchProjectedMessage` → 一帧最多一次 dispatch；不得触发 API overlay。
2. **即时事件直通**：`confirm-requested`、`tool-confirmed`、`source-completed/failed/cancelled/timeout` 不入队等待——confirm 事件到达时立即 flush 当前队列后同步处理（确认弹窗是交互入口，延迟 16ms 虽可接受，但直通实现更简单且无歧义）；仅当该 turn 不处于 `recovering` 且版本连续时，终态事件才可在 flush 后处理并清掉队列，否则必须交由 1.2.5 的恢复状态机处理。
3. **usage-updated 合并**：一帧内多个 usage 事件只保留最后一个（现状 `applyProjectedUsage` 有 `window.api.usageSet` 回写，降频同时减少 IPC 回写次数）。
4. **指标**：`TurnProjectionMetric` 增加 `mergedCount` 字段，便于回归观测合帧率。

旧协议阶段只执行 `QueuedSnapshotProjection` 的合帧；新协议上线后再启用 `QueuedProjection.patch`。两种 adapter 共用 projection store 和 flush 入口，因此每个阶段均可独立编译验收。

#### 2.2.2 pendingConfirmStore 语义 fingerprint 去重（`pendingConfirmStore.ts`）

`syncFromProjection` 先提取只包含展示/交互所需字段的稳定值投影，并对 `input`、`diff`、`mcp`、安全提示等嵌套字段生成规范化 fingerprint（包含字段删除）；相同 fingerprint 不写回、不 notify，变化才更新。该比较不依赖跨 IPC 或 renderer 内部对象引用；后续若引用稳定可作为快路径，但语义 fingerprint 始终是正确性依据。

#### 2.2.3 引用稳定性边界

跨 IPC 的结构化克隆不会保留对象引用。旧快照协议下只做有界元数据归一化：已处于 `completed/failed/rejected` 的同 ID record 直接复用，不读取或比较 `result.data`；活动记录只比较 status、progressSeq、确认元数据等有界字段。异常修正通过 status/version 或 record 数量变化触发整项替换；不得 stringify、hash 或 deep-equal 历史 result。

- `normalizeProjectedMessageIdentity(previous, next)` 是纯 renderer 函数，不能生成事实字段，只负责有界元数据比较和引用复用；性能门禁测量 50×400KB structuredClone snapshot，不得重复扫描历史 result。
- Redux patch 路径：`patchDisplayEntryMessage` 每次重建 displayEntries/messages 数组，但 entry.message 的替换只发生在目标 id 上；确认未变化的 message 对象引用在 patch 后保持（若现有实现已满足则只需补测试断言，不满足则在 `patchMessage` 内对未命中 entry 复用原引用）。

#### 2.2.4 contextScalars 降频

`selectContextSummaryScalars` 的计算挂在 ChatView 渲染路径上；合帧后投影 patch 频率已降为每帧一次，该项随之自然降频，无需单独改造。若 profiler 仍显示其为热点，再考虑把摘要服务改为外部 store + `useSyncExternalStore` 按值订阅（列为可选后续，不在本项默认范围）。

### 2.3 兼容性 / 风险分析

| 风险 | 评估与对策 |
| --- | --- |
| 确认弹窗延迟 | confirm 事件直通（flush 后立即处理），不进入等待队列；新增测试断言「confirm-requested 到达后同一 microtask 内 pendingConfirmStore 可见」 |
| 终态丢失 | 仅版本连续且非 recovering 时才 flush、处理并清理终态队列；否则交由恢复状态机；dispose / 会话切换时按规则清理残留队列 |
| 合帧导致「打字机」观感变化 | 文本 delta 从「每事件一帧」变「每帧一批」，16ms 窗口下用户无感知；如主进程事件本身突发到达，观感反而更平滑 |
| rAF 在后台标签/隐藏窗口不触发 | Electron 单窗口隐藏时 `backgroundThrottling` 生效；合帧调度需回退 `setTimeout(16ms)`，保证后台会话的 pendingConfirm/usage 状态仍推进 |

### 2.4 验收标准

- **dispatch 频率**：50 次工具调用 + 穿插 content-delta 的 fixture，Redux `patchMessage` dispatch 次数 ≤ 事件数 / 4，且每 16ms 窗口内 ≤ 1 次。
- **notify 频率**：无确认状态变化的事件流期间，`pendingConfirmStore` notify 次数为 0。
- **即时性**：仅在版本连续且不处于 recovering 时，`confirm-requested` 事件到 `pendingConfirmStore.getItems()` 可见的延迟 < 1ms；恢复期间优先保证顺序正确性。终态事件到达后仅在同样条件满足时于同一帧内更新 `chatStatus`。
- **回归**：现有 `turnProjectionService.test.ts`、`turnProjectionConfirmLifecycle.test.ts`、`pendingConfirmStore.test.ts` 全部通过（用 fake timers / 手动 rAF 驱动）。

### 2.5 工作量粗估

约 2～2.5 人日：合帧调度器 1 日，确认 fingerprint 与旧快照归一化 0.75～1 日，测试调整 0.5 日。

## 3. 改进项 3：流式气泡渲染优化（ToolCallCard memo + 时间线增量缓存）

### 3.1 问题定位

- `ChatBubble.tsx:236-265`：`activityModel` useMemo 依赖 `message.toolCalls` 数组引用，投影 patch 每事件产生新数组 → 每事件全量执行 `buildAssistantActivityTimeline` + `groupActivityTimeline`，N 个 toolCall 时 O(N)。
- `ToolCallCard.tsx:89`：普通函数组件，无 `React.memo`；ChatBubble 每次重渲染时 N 张卡片全部重渲染。卡片内部 `label`/`paramPreview`/`resultStr` 等 useMemo（267-298 行）因 `record` 引用未变时可命中，但组件函数体本身（含大量状态判定、`resolveEffectiveShellOutputMode` 等）仍每事件执行 N 次。
- 展开卡片的大 result：`resultStr` useMemo（287-298 行）以 `record.result` 引用为依赖，引用稳定时不会重复 `JSON.stringify`；但渲染处 `truncate(displayedResultText, 4000)`（571-578 行）截断后仍生成大字符串，且 `displayedResultText` 在搜索态下可能携带完整文本。

### 3.2 优化方案

#### 3.2.1 ToolCallCard 加 React.memo

`ToolCallCard` 导出改为 `memo(function ToolCallCard(...) {...}, comparator)`。comparator 采用显式字段比较（与 `ChatBubble` 底部 524-542 行的既有风格一致）：

- `record`（引用比较即可，依赖 2.2.3 的引用稳定性保证）、`confirmMode`、`focus`、`workDir`、`shellConfig`、`sessionMetadata`、`messageId`、`sessionId`、`activeSearchTarget`；
- `onConfirm`/`onCancel`/`onOpenFile`：ChatBubble 内联箭头函数（`ChatBubble.tsx:397-406`）每渲染生成新引用，会击穿 memo——需上移到 ChatBubble 层用 `useCallback` 按 `(toolId, approved)` 形态稳定化，或改为传 `confirmTool`/`cancelTool` 原函数 + `record.id`，在卡片内部绑定。
- `toolCalls` prop（仅 `handleTerminalBeforeDispose` 用于 scrollback 回写，`ToolCallCard.tsx:192-206`）：传整个数组会每事件变化，改为传「写回调」或在 effect 内通过 ref 读取最新数组，从 props 中移除。

#### 3.2.2 时间线增量缓存

`buildAssistantActivityTimeline` 的输出具有追加特性：toolCalls/skillHints 只增不减，新事件只影响尾部（最后一个 toolCall 状态翻转、新 toolCall 追加、segment 关闭）。在 `ChatBubble` 中以 useRef 缓存上一次输入（`toolCalls` 长度、末条 toolCall 的 id+status、content/thinking 尾段引用）与输出，命中「纯追加」时只重建尾部条目并复用前缀数组（前缀条目的对象引用不变，`groupActivityTimeline` 分组结果中已完成批次也可整体复用）。

实现位置：把增量逻辑放在 `src/shared/assistantActivityTimeline.ts` 的包装函数 `appendActivityTimeline(prev, message)`（纯函数，可单测），ChatBubble 侧只负责用 useRef 持有 prev。若审计后发现「纯追加」判定分支复杂易错，退化为：timeline 条目级 memo——以每个 toolCall 的引用为 key 缓存其渲染入参，时间线仍全量构建但条目对象复用，配合 3.2.1 的 memo 使卡片不渲染。**优先做条目级 memo，增量构建仅在 profiler 证明时间线构建本身是热点后再做。**

#### 3.2.3 大 result 渲染按需化

- `resultStr` useMemo 已有引用缓存，保留；补充：当 result 序列化后超过阈值（与改进项 1 的 64KB 对齐）且用户未展开时，不生成完整字符串（现状 `showDetail` 已短路，确认无遗漏分支即可）。
- 展开时超长文本默认只渲染前 4000 字符（现有 `truncate` 行为）+ 「查看完整内容」入口（配合改进项 1 的 `chatGetToolResult` / artifact 路径）。
- 搜索态 `displayedResultText` 携全文的分支（313-315 行）仅在命中片段时启用，保持现状。

### 3.3 兼容性 / 风险分析

| 风险 | 评估与对策 |
| --- | --- |
| memo 比较遗漏导致卡片不更新 | comparator 显式列出全部 props，参考 ChatBubble 既有比较器；为 confirming→executing→completed 各状态迁移写 render probe 测试 |
| onConfirm 稳定化改变确认行为 | 确认/取消回调语义不变，仅绑定位置移动；现有 confirm 生命周期测试（`turnProjectionConfirmLifecycle.test.ts`）兜底 |
| scrollback 回写 | `patchShellTerminalScrollback` 需要最新 toolCalls 数组；改用 ref 读取保证写到的是最新引用，行为不变 |
| 增量时间线边界 | 纯追加判定失败时必须回退全量重建，不允许产出缺条目的时间线；共享 fixture 比对全量/增量输出一致性 |

### 3.4 验收标准

- **卡片渲染次数**：50 张 ToolCallCard 的 fixture 中，单条新 tool-result 事件（经合帧）到达后，重渲染的卡片数 ≤ 2（新追加 + 状态翻转的那张），render probe 断言。
- **时间线构建**：纯追加事件不触发前缀条目对象重建（引用相等断言）；100 个活动条目的气泡，单帧内 `activityModel` 相关耗时 < 2ms。
- **大 result**：展开含 400KB result 的卡片，首次展开 JSON.stringify 只发生一次；折叠/展开切换不重复计算。

### 3.5 工作量粗估

约 2 人日：ToolCallCard memo + 回调稳定化 1 日，条目级 memo / 时间线缓存 0.5 日，render probe 测试 0.5 日。

## 4. 实施顺序与回归测试要点

### 4.1 实施顺序（Phase 划分）

#### Phase 0：renderer 投影基础设施

建立统一内部 `ProjectionOperation`、`turnProjectionSlice`、`turnProjectionSelectors`、`routePatchProjectedMessage`、`ProjectedMessage` 的 UI 合成入口、`adoptionBarrierBySession` 及 session/turn 生命周期清理；旧 snapshot adapter 接入。Phase 0 同时交付旧协议终态 overlay 收口：连续 terminal snapshot 后从已完成 checkpoint 读取完整 `Message`，移除 streaming assistant overlay；若提交尚未完成则保留 overlay 但阻止下一轮上下文/queued drain，直到可重试接管成功。此阶段不宣称降低 IPC 字节量，只建立可被 Phase 1/2 独立使用的存储和状态机。
