# 会话新建删除卡顿诊断与修改计划

## 1. 现象

打包安装后，在桌面端执行“新建会话”或“删除会话”时，操作反馈明显延迟，表现为按钮点击后界面短时间卡顿。

当前证据表明，主要延迟发生在 renderer 等待 Electron IPC 返回期间，并非单一 React 列表重渲染问题。

## 2. 调用链与根因判断

### 新建会话

调用链：

```text
renderer AppShellInner.createSession
  -> window.api.sessionCreate
  -> electron/appIpc.ts session:create
  -> createSession(SQLite)
  -> backup.backupImmediate
  -> sessionBackupManager.backupSession
  -> mkdir + 写 session.json + 创建消息临时文件 + fsync + rename
  -> IPC 返回
  -> renderer dispatch(upsertSession/setSession)
```

新建 IPC 在返回前强制执行空会话备份。即便没有消息，也会触发文件创建、原子替换和 `fsync`，使 UI 状态更新被备份 I/O 阻塞。

### 删除会话

调用链：

```text
renderer 删除操作
  -> window.api.sessionDelete
  -> electron/appIpc.ts session:delete
  -> clearSessionToolResources
  -> deleteSession(SQLite transaction)
  -> deleteSessionUsage
  -> db.flushSave()
  -> clear decision cache（同步 SQLite 操作）
  -> 删除附件目录
  -> 删除会话备份目录
  -> IPC 返回
  -> renderer 更新会话列表/当前会话
```

删除路径包含同步 WAL checkpoint（`flushSave`），并串行等待附件和备份目录递归删除。历史消息、附件或 WAL 较大时，这些操作会放大主进程阻塞时间；renderer 直到 IPC 完成后才更新界面，因此卡顿被直接暴露给用户。

## 3. 修改目标

1. 会话元数据提交后尽快完成 IPC，让 renderer 立即得到可用结果。
2. 将非必要的备份、附件清理和缓存维护移出用户操作临界路径。
3. 保持删除的数据一致性、安全检查和资源最终清理能力。
4. 后台清理失败必须可观测、可重试，不能静默丢失。
5. 不改变正在运行会话的 busy guard、确认状态和 turn 生命周期语义。

## 4. TDD 推进计划

### 第一阶段：建立基线

- 增加 `session:create` 延迟行为测试，验证 IPC 返回不再等待空会话备份。
- 增加 `session:delete` 行为测试，验证数据库删除和 UI 所需结果不等待大文件清理。
- 增加失败测试，覆盖后台备份/附件删除失败时的日志与重试调度。
- 记录现有 focused tests、全量测试和两个 renderer/shared typecheck 基线。

### 第二阶段：新建链路解耦

- 保留 SQLite 会话创建的同步一致性。
- 将空会话备份改为可取消、可观测的后台调度，避免 `backupImmediate` 阻塞 IPC 返回。
- 确认重复点击和应用退出时不会产生悬挂备份任务或错误覆盖。

### 第三阶段：删除链路解耦

- 保留运行中会话的拒绝逻辑和数据库删除事务。
- 删除成功后立即完成 IPC 返回所需的状态变更。
- 将备份目录、附件目录及会话级资源清理放入后台清理任务。
- 评估并移除删除路径上的强制 `flushSave`；如确有持久化边界要求，改为不阻塞 UI 的受控落盘策略。

### 第四阶段：恢复与异常处理

- 应用启动时扫描未完成清理任务并重新执行。
- 后台清理采用幂等操作，目录不存在视为成功。
- 记录 sessionId、清理阶段、错误和重试次数。
- 验证清理失败不会复活已删除会话，也不会影响新建会话。

## 5. 预计涉及文件

- `electron/appIpc.ts`：调整 `session:create`、`session:delete` IPC 临界路径。
- `electron/debouncedSessionBackupManager.ts`：补充后台备份/删除任务的调度、取消和失败处理。
- `electron/sessionBackupManager.ts`：复用现有幂等删除能力，必要时增加清理任务入口。
- `electron/database/operations.ts`：评估 `deleteSession` 中强制 checkpoint 的边界，不先改变事务语义。
- `src/renderer/App.tsx` 及相关会话状态逻辑：仅在 IPC 返回契约变化时调整。
- 对应 `*.test.ts`：先测试后实现，覆盖正常、重复、失败、退出恢复场景。

## 6. 验收标准

- 新建空会话时，IPC 不等待文件备份完成，界面先完成会话切换。
- 删除会话时，IPC 不等待大附件/大备份目录删除，界面先移除会话。
- 运行中会话仍被正确阻止删除。
- 后台清理失败有日志，并能在后续启动或重试中恢复。
- 不出现已删除会话重新出现在列表、备份覆盖新数据或资源泄漏。
- focused tests、`npm test`、`npm run typecheck:shared`、`npm run typecheck:renderer` 均通过。
- 修改完成后进行一次性能复测，分别覆盖空会话、大消息历史和大附件目录。

## 7. 风险与边界

- “数据库已删除、文件尚未清理”是短暂可接受状态，必须保证清理任务幂等且可恢复。
- 不能为了降低点击延迟而绕过运行中会话保护、确认授权或 turn coordinator 状态管理。
- 暂不引入新的存储层或额外跨进程协议；优先复用现有 backup manager、数据库和启动流程。
