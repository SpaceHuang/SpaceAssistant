# 失败 Turn 的继续与重试体验改进方案

**状态：实现完成（TDD）；待产品评审**
**日期：2026-10-02**
**范围：功能与体验优化；复用现有 Turn、History 与 continuation 能力，不调整 Agent 总体架构。**

## 1. 问题与目标

当一个执行时间较长的 Turn 在末尾失败时，之前已经完成的模型步骤和工具工作可能已记录在 History，但用户从聊天框输入“继续”或点击“重试回复”时，普通新 Turn 不会稳定地继承上一失败 Turn 的过程信息。模型从原始请求重新规划，可能重复工作，也可能在看到已被部分修改的文件后把自身先前的写入误认为外部改动。

典型场景：Agent 已完成文档开头的修改，在改中间部分时失败；用户发起下一 Turn 要求继续，模型没有上次的修改过程，只读取到当前文件与原始预期不同，于是抱怨“文件中途被人改过”。

本方案的目标是让后续 Turn 在用户表达承接意图时了解上一失败 Turn 的目标、已完成步骤、失败原因和副作用状态；同时让用户能选择从已验证检查点继续执行，或从原请求重新回答。**过程上下文承接**与**执行检查点续跑**是两种独立能力：前者只给模型可审计的背景事实，不重放旧工具；后者依据已验证 History 继续执行。

## 2. 当前代码行为

### 2.1 已有能力

- 聊天失败消息已经可同时展示“重试回复”和“继续上次执行”两个动作。`ChatBubble` 将两者分别交给 `retryAssistant` 与 `continueAssistant`。
- “继续上次执行”通过 `chatResolveRetryContext` 找到来源 Invocation，再调用 `chatContinueFromCheckpoint`。主进程从规范 History 校验已结算检查点，建立关联来源 Invocation、检查点摘要和目标 Invocation 的 continuation 记录，并幂等地启动续跑。
- 检查点恢复会重建已提交的工具结果；未结算工具调用、未解决审批、取消/中断或安全拒绝等状态不允许自动续跑。安全快照变化时也会拒绝。
- 普通“重试回复”通过原用户消息构造 `reuse-user` 提交，并排除失败 assistant 尝试。其语义是重新回答原请求，而不是继续旧 History。
- 用户直接输入“继续”目前走通用 `submitOutbound`，成为新的用户输入；不会自动绑定到失败 Turn 的检查点。
- 一般新 Turn 的上下文构造没有明确的“承接最近失败 Turn”契约。即使文件工具的调用结果和部分成功写入已留在来源 Invocation History，也不能保证新 Turn 的模型输入包含这些过程事实。

### 2.2 用户感知问题

1. **“重试回复”容易被理解为接着做。** 实际上它从原请求重新生成，已有步骤可能重复执行。
2. **同一句“继续”因入口不同而含义不同。** 按钮会续跑检查点，输入框会开启新的普通 Turn。
3. **续跑入口需要被发现。** 用户必须识别两个近似按钮的差别；失败发生较久或消息列表较长时尤其容易选择错误。
4. **检查点不可续跑时过程信息仍会丢失。** 执行副作用可能已经部分发生，但后续普通 Turn 既没有安全执行检查点，也没有结构化的来源摘要可供模型理解当前文件状态。
5. **续跑不可用时反馈不够具体。** 当前提示是通用的 continuation 不可用，用户难以理解为什么只能重新开始。

### 2.3 部分副作用为何会造成错误归因

工具执行的持久结果属于来源 Invocation 的 History；新的普通 Turn 通过会话消息上下文构造请求。两者不是自动合并的同一份 transcript。若新请求只包含原始对话文本，模型会从文件当前内容推断状态，却不知道哪些变化来自上次自己的成功工具调用。

部分文件修改尤其需要区分三类事实：

| 来源 History 事实 | 新 Turn 可收到的信息 | 后续处理原则 |
|---|---|---|
| 已结算成功的 `edit_file` / `write_file` | 工具名、目标文件、结果摘要；若已有可靠回执则含写入摘要/版本指纹 | 明确标为上次 Agent 已完成的修改；续作前仍读取当前文件并核对，避免盲目覆盖后续变更 |
| 已结算失败的写调用 | 失败类别与工具返回的诊断；不把预览或计划字段当作写入证明 | 标记为失败尝试；除非结果明确证明，否则文件副作用按未知处理 |
| `tool-call-started` 后无完成结果 | 已派发但结果未知的调用及目标 | 不说“没改动”或“已经改好”；要求先检查当前文件/外部状态，不自动重放 |

上下文摘要必须从 canonical History 的结构化事件生成，不能仅凭 UI 活动描述、错误文本或 `autoApprovedWrite` 预览元数据推断文件已写入。

## 3. 方案决策

### 3.1 统一动作名称与优先级

当失败消息具备可续跑检查点时，将“继续上次执行”设为主要动作；将“重试回复”改为语义明确的次要动作“从头重试”。当检查点不可续跑时，只展示“从头重试”，并用简短提示说明原因或表示该操作会重新执行原请求。

两个动作的定义固定如下：

| 动作 | 执行语义 | 上下文来源 | 已完成工具是否重跑 |
|---|---|---|---|
| 继续上次执行 | 从最近一个完整、已提交检查点请求模型处理下一步 | 原 Invocation History 中的已提交上下文与工具结果 | 不重跑已结算工具 |
| 从头重试 | 从原始用户请求重新生成答案 | 原 user message；排除本次及同一请求关联的失败 assistant 尝试 | 可能再次调用，外部副作用不回滚 |

“重新生成”仅表示从原请求重新开始；界面和确认文案避免把它称作“继续”。

### 3.2 将输入“继续”作为有条件的恢复意图

将短语继续先解释为**上下文承接意图**，而不是必然执行检查点续跑。在当前会话存在唯一、最近的失败 Turn 且没有更新的已接受任务时，以下精确短语表达承接意图：

- `继续`、`继续执行`、`接着做`
- `接着刚才的修改`、`继续上次的任务`
- 可配置本地化等价表达；首期至少覆盖中文 UI。

实现采用确定性的意图标记或精确短语匹配，不依赖额外模型分类。可以带有明确新要求的输入（例如“继续检查第二个文件”）仍作为普通新消息，但若它紧随唯一失败 Turn，普通新 Turn 的上下文仍应自动附带该失败 Turn 的过程摘要；不能因为不精确匹配短语就丢失承接关系。

匹配成功时，按当前状态选择处理方式：

1. 若输入是精确续跑短语且没有附件，且来源 Turn 存在完整、安全的检查点，默认启动 checkpoint continuation。
2. 若输入带有任何附件（无论文本是否只是“继续”），不走 checkpoint continuation。创建普通新 Turn，将附件按既有消息/多模态上下文路径作为该 Turn 的用户材料，并附带结构化的失败 Turn 过程摘要和来源引用。模型必须结合新附件与来源摘要，再对照当前文件/外部状态继续；旧工具调用不重放。
3. 若检查点不能安全续跑但来源 History 可完整读取，创建普通新 Turn，并附带结构化的失败 Turn 过程摘要和来源引用。模型必须先对照当前文件/外部状态再继续；旧工具调用不重放。
4. 若来源 History 不完整、存在未知副作用或来源无法确认，仍保留用户新输入和附件，但摘要标记“执行结果未知”，要求模型先检查实际状态。不得杜撰已完成/未完成结论。

若当前没有失败 Turn，则把输入作为普通新消息处理。若存在多个可能目标，不能静默选取其中一个，也不能把短语当作普通任务送给模型后丢失其承接意图；持久化为 `needs_source_selection`，保留原文/附件，并让 UI 提供候选失败消息供用户选择，或显式改为普通新 Turn。用户选择/改为普通输入必须以原 request ID 幂等完成。

#### 输入受理、路由与幂等持久化

输入框的继续意图必须由主进程通过同一个出站受理操作完成“来源选择、资格校验、占用检查点或创建普通/排队 Turn、记录输入结果”。Renderer 不得先查询失败目标，再独立调用 continuation IPC；也不得在续跑拒绝后用新 request ID 重新提交原文。

建议复用 `chat:submit-outbound` / OutboundAcceptor，增加可选的 continuation intent 字段；它保留普通出站请求的同一 `requestId`、原文、附件和 session 身份。主进程按 session 单写者/既有受理顺序，在一个持久化事务边界内完成路由决策：

1. 以 `requestId` 幂等登记输入意图，包括原文/附件引用或内容摘要、session、创建时间、初始状态；同 ID 且载荷不同必须拒绝为 idempotency conflict。
2. 在同一受理序列点重新核验候选来源是当前唯一相关的失败 Turn，且其后没有更新的已接受 Turn 或排队任务；同时从持久 History 重算续跑/摘要资格，不信任 Renderer 预检。
3. 若检查点可续跑，原子创建或取回 continuation 记录、占用来源 checkpoint，并将 intent 记录绑定 `continuationId`、source invocation/checkpoint 摘要、target turn/invocation 和状态。被消费的短语作为 UI 可见的用户操作记录保存，但标记为 `consumed_as_continuation_intent`，不得注入恢复 transcript。
4. 若输入包含附件，即使文本精确匹配“继续”，路由类型固定为普通上下文承接 Turn；同一事务将用户消息及附件引用写入该 Turn/队列，并绑定来源摘要引用。该附件消息通过现有 canonical user message 与多模态内容转换送入模型，不能只存入 intent 记录或诊断元数据。
5. 若不满足检查点续跑但允许普通上下文承接，原子创建或排入一个普通 Turn，将该请求绑定来源摘要引用，并把原输入/附件正常保留在该 Turn。
6. 若来源歧义或持久化/History 状态不确定，按产品策略创建普通 Turn（保留原输入和附件并携带 `unknown` 摘要）或返回明确可重试拒绝；不得先消费输入再丢弃，也不得在原子决策后改用新 ID 静默重投。

**附件路由契约：** 精确短语无附件才允许走不新增用户消息的 checkpoint continuation。精确短语带附件、带附加文本（无论是否带附件）都走普通新 Turn；其 canonical user message 必须包含完整原文和附件，普通 Turn 请求的多模态转换必须能实际读取附件。来源摘要作为独立的结构化上下文附加，不能覆盖、代替或重排用户附件。受理记录保存附件 message/asset ID、顺序、类型和内容摘要/版本校验信息；续传或请求重放必须引用相同附件身份并校验可读性。附件缺失、不可读或校验失败时不得把请求标为已消费并启动执行，应返回同 request ID 的可恢复失败状态，或在执行前要求用户重新附加。

输入意图记录至少持久化 `requestId`、`sessionId`、原始用户输入/附件关联、解析出的 intent、路由结果、来源失败消息 ID、source turn/invocation ID、checkpoint sequence/hash（续跑时）、continuation ID 或普通 turn/queue ID、状态、拒绝原因码及时间。状态至少区分 `accepted_continuation`、`accepted_turn`、`queued`、`needs_source_selection`、`rejected_retryable` 和终结拒绝。敏感附件内容沿用当前消息存储与访问控制，不复制进诊断日志。

已提交的受理结果是唯一重试依据：同一 `requestId` 的 IPC 重投或响应丢失后查询必须返回同一 intent 与同一目标，不得再启动第二个 Turn/continuation。队列排水和并发新输入必须遵守同一 session 受理序列；若原子持久化事务无法确认提交结果，保持 `commit_uncertain` 并先对账，禁止按新 request ID 自动回退提交。

### 3.3 普通新 Turn 的失败过程上下文

当新的用户输入被判定为承接最近一条失败 Turn 时，主进程在组装该 Turn 的模型上下文时附带一个受限大小的“上次执行摘要”。它是**新的上下文材料**，不是恢复 transcript，不改变普通 Turn 身份，也不授权旧工具调用自动重放。

摘要至少包括：

- 来源用户任务、失败 Turn/Invocation 标识及失败原因；正文引用遵循当前消息上下文权限和隐私处理规则；
- 按模型轮次/工具调用顺序列出的已提交工作摘要，尤其是成功的文件写入/编辑：工具、相对路径、操作结果及可用的变更回执；
- 最近一次失败操作及工具给出的错误类别/诊断；
- 工具结算状态：已成功、明确未执行、已失败但副作用不确定、派发后结果未知；
- 提醒模型先读取当前目标文件并与已记录的自身修改对照，再做后续编辑；若当前内容与已知回执不一致，应报告差异或询问用户，不直接指责“被人改过”。

摘要应通过专用的 continuation-context envelope 或等价的结构化消息注入，字段显式标注为“历史事实/状态未知”，避免把系统生成内容伪装成用户原话或模型最终回复。首期只附最近一个相关失败 Turn，设置明确 token 上限；超限按“任务目标、成功副作用、最后失败、未知状态”优先级压缩，并保留来源 Invocation 与 History 序号以供审计。

承接信号的作用域应有限：用户明确说“继续/刚才/上次”时引用最近相关失败 Turn；若当前输入明显是独立新话题则不注入。用户紧接失败 Turn 发送普通文本时，可在 UI 提示“将参考上次失败执行摘要”，提供取消关联选项；不把所有历史失败 Turn 默认灌入每个新请求。

### 3.4 入口共用同一资格与执行逻辑

聊天框短语入口与失败气泡按钮必须进入同一主进程续跑资格与 checkpoint 占用逻辑；输入框走具备持久输入意图的出站受理协议，气泡按钮使用显式来源 ID 和幂等键。两者不要求共享同一个 IPC，但不允许 Renderer 自行拼接 History 或恢复工具参数。续跑资格由主进程基于持久事实判断，至少包括：

- 目标失败消息、Invocation、原始 user message 与 session 身份一致；
- 来源 History 完整且检查点校验通过；该响应的工具调用均已结算；
- 不存在未知副作用、未解决审批、用户取消/中断、安全拒绝；
- 当前安全快照仍符合原执行约束；
- 同一检查点的重复请求幂等，不启动第二个活跃 continuation。

UI 可以展示资格结果和原因码对应的本地化说明，但不得把 UI 资格缓存当作执行授权。

### 3.5 新 Turn 上下文承接不等于执行续跑

过程摘要承接可用于检查点不可续跑的失败场景，但本身不能改变副作用边界：

- 只向模型描述已完成事实和未知事实；不将来源工具调用作为待执行队列复制。
- 成功文件修改仍需读取当前文件并核验现状；来源成功结果不是当前文件内容锁，也不证明其后未被用户或其他进程修改。
- 来源工具失败不能简单转换成“没有副作用”；执行器返回前后可能存在不确定性时要标记未知。
- 当前 Turn 生成的新工具调用仍按现有安全审批、读前写和并发控制执行。
- 历史摘要不携带或扩大原 Invocation 的授权；新的写操作走当前 Turn 的安全检查。

### 3.6 失败消息与续跑状态展示

- 原失败消息保留，作为失败原因和执行进度的锚点，不因续跑或从头重试而移除。它的 message ID、失败正文和失败原因保持稳定。
- continuation 结果作为关联的后续执行显示，视觉上标明“接续自上次执行”，并允许用户查看来源失败消息。
- 从头重试创建关联的新执行/assistant 消息，使用明确的 retry-of/source-failure 关系指向原失败消息；不通过 `removeMessage` 隐藏或删除来源失败消息。等待受理、已排队、受理失败和再次失败时，来源失败消息都继续显示。
- 原失败消息可以折叠呈现，但不得从消息投影或持久层移除；关联的重试/续跑状态就近显示，避免多个尝试时用户失去因果锚点。
- continuation 进行中禁用重复启动入口；请求超时重试沿用同一幂等键。
- 续跑完成、再次失败、被取消或因未知副作用中断时，状态显示在关联执行上，并根据状态更新下一步可用动作。
- 不可续跑时解释主要原因，例如“有工具执行结果未确认，无法自动续跑”或“安全设置已变化，请重新确认”。不暴露内部异常堆栈。

## 4. 交互流程

```text
Turn 失败
  ├─ 有已提交且安全可续跑的检查点
  │    ├─ 点「继续上次执行」 ─┐
  │    └─ 输入「继续」 ──────┴─> 幂等启动 continuation -> 从检查点下一模型步继续
  │
  │    点「从头重试」 -> 原始用户输入重新生成（可能重跑工具）
  └─ 无安全可续跑检查点
       ├─ 输入「继续」/后续任务 -> 新 Turn + 失败过程摘要 -> 先核对文件/副作用现状再继续
       └─ 点「从头重试」 -> 原始用户输入重新生成
```

## 5. 实施范围与阶段

### 阶段 1：明确现有按钮语义

- 将失败气泡主次动作改为“继续上次执行”和“从头重试”。
- 根据主进程提供的恢复资格决定按钮可见性和说明；不要仅凭错误字符串判断。
- 移除重试前的失败消息删除行为；将重试产生的新执行与来源失败消息关联，并在被拒绝、进入排队及再次失败时持续保留来源消息和失败原因。
- 续跑失败时展示可本地化、可行动的拒绝原因；未知副作用使用独立提示，不呈现成普通可重试错误。

### 阶段 2：接入短语继续

- 在主进程现有出站受理操作内增加窄范围的 continuation intent 解析与受理协议；该协议持久化输入、执行路由、占用检查点或创建普通 Turn/队列项，并返回可幂等查询的既定结果。
- 解析依赖当前会话最近相关失败、承接意图、来源身份和持久化状态；其余输入内容保留为新 Turn 的用户要求。
- 只有精确续跑短语且无附件时，才在同一原子受理流程中复用现有 continuation 创建/占用能力；禁止 Renderer 先查再调用 `chat:continue-from-checkpoint`。
- 精确短语带附件或附加文本时，原子路由为普通上下文承接 Turn；附件经 canonical user message 和现有多模态请求转换送达模型，失败摘要作为独立上下文随请求提供。
- 检查点不可续跑但 History 可读时，为普通新 Turn 注入有大小上限的结构化过程摘要；工具状态未知时明确标注，并要求模型检查当前实际状态。
- 摘要生成复用 canonical History 与现有工具结果/事件，不从 renderer 活动文案构造事实；不要求改变 History 总体模型。
- 持久化输入意图到最终路由结果的映射；相同 request ID 重试必须取回相同结果，提交不确定时先对账。
- 若续跑被拒绝且需要转普通 Turn/队列，使用同一输入意图和 request ID 原子转换，不二次提交、不丢原文/附件。
- 在失败消息处展示短语已触发的续跑或上下文承接状态；若资格检查拒绝，输入不得静默丢失。

### 阶段 3：收敛状态与恢复文档

- 更新聊天交互文档、本地化字符串和测试用例，明确续跑、从头重试、普通新输入的差异。
- 将本方案与 [工具错误恢复与 Turn 连续性改进计划](./tool-error-recovery-and-turn-continuity-plan.md) 对齐：本方案定义用户意图和体验；底层继续复用该计划所述 History、工具结果回灌与副作用恢复边界。
- 核对该连续性计划中阶段 C 的状态，避免把仓库已经存在的 continuation 协议再次列作尚待设计的工作。

## 6. 不在本方案范围内

- 不修改 Agent 核心循环、SDK 分层、History 总体模型或全局 Turn 身份协议。
- 不允许重放 `tool-call-started` 未结算的调用，不恢复已取消或被安全策略拒绝的执行。
- 不将任意包含“继续”的长文本交给自动恢复，也不让模型判断应恢复哪个失败 Turn。
- 不自动从头重试模型/工具，也不宣称先前外部副作用可以撤销。
- 本方案不改变工具错误在原 Turn 内回灌模型的处理规则；该部分由工具错误恢复计划负责。
- 不默认把所有历史失败 Turn 注入每个新 Turn；只有明确承接意图或紧邻失败后可解释的跟进输入才携带对应摘要。

## 7. 验收标准

### 体验

- 具备续跑资格的失败消息将“继续上次执行”作为主动作；次动作清楚写为“从头重试”。
- 无续跑资格时不显示会产生错误承诺的继续操作，并显示用户可理解的主要原因。
- 在唯一目标失败、无新用户输入的情形下输入精确的“继续”会启动 continuation；模型收到的恢复上下文包含原始 user 输入和所有已提交工具结果，不包含新的“继续”消息。
- 输入“继续”的原文、附件关联、解析结果、来源身份、检查点摘要、消费状态与最终 continuation/Turn/queue ID 在持久化记录中可追溯；模型上下文不会把已消费短语伪装成新的任务内容。
- 无附件的精确“继续”可走检查点续跑；“继续”带附件必须走普通 Turn，附件以正确顺序和内容出现在模型实际多模态请求中，失败过程摘要作为独立上下文同时可见。
- 输入“继续”与附件受理后，附件身份、顺序、类型、内容版本与目标 user message/Turn 可审计；响应丢失重试仍引用相同附件，不重复也不丢失。
- 附件读取/校验失败时不将意图标记为已消费，不启动模型或工具；可用同一 request ID 恢复或明确要求重新附加。
- 来源选择、检查点占用与输入受理并发时，单次路由结果原子确定；不能出现输入被消费但无 continuation/Turn、两个目标同时启动或因新任务到达而恢复过期来源的情况。
- 队列排水与并发新任务服从同一 session 受理顺序；竞态拒绝后的原请求只可转成同 request ID 的普通 Turn/队列项或明确可重试状态。
- IPC 响应丢失后同 request ID 重发返回既有受理结果，executor/continuation 启动次数仍为一次；持久化提交状态不确定时不自动换 ID 重放。
- 在检查点不可续跑但来源 History 可读取时，输入“继续”会创建普通新 Turn，并收到失败过程摘要；摘要至少正确指出已成功修改的文档/区域、失败步骤和工具状态，不触发旧工具重放。
- 部分文档写入后中间步骤失败的回归场景中，后续 Turn 能识别上次已完成的写入；模型会先读取当前文档、对照摘要继续编辑，不把自身已知的成功改动误称为外部修改。
- 输入“继续检查剩余文件”等带新任务内容的文本仍作为新用户 Turn 原样处理，同时携带相关失败摘要（若上下文关联规则判定为承接）。
- 新话题不携带无关失败 Turn 摘要；用户可取消错误的上下文关联。
- 多个失败目标、未知副作用、审批未完成、来源身份不匹配或安全快照变化时，不自动选择或运行 continuation；用户文本保留且原因清楚。
- continuation 与来源失败消息关联呈现；进行中重复点击/重复发送不产生第二个 continuation。
- 从头重试前后、重试受理拒绝、进入队列、重试再次失败时，原失败消息 ID、失败正文和原因仍可见；新执行通过稳定来源关系关联到该失败消息。
- 从头重试与检查点续跑交替点击时，来源失败消息不消失；每个新执行都保留正确的来源 message/turn/invocation 关联。
- “从头重试”继续遵循既有 retry context 规则：排除同一原始 user message 关联的失败 assistant 尝试，并明确其可能重跑外部工具。

### 安全与持久化

- 已结算工具调用在 continuation 中不再次执行。
- 存在未结算 `tool-call-started` 时不自动续跑，也不把可能已发生的副作用显示为“未执行”。
- 普通新消息、续跑短语和显式按钮三类入口的 session、来源 Invocation、用户消息及幂等关系可审计。
- 错误/超时重试沿用同一个 continuation 请求幂等键；用户主动另开一次操作时按当前 continuation 状态规则拒绝或创建新请求，不重复占用同一检查点。

## 8. 定向测试场景

- 失败气泡按钮文案、主次顺序、资格不同时的显示与拒绝原因。
- 精确续跑短语、带额外内容的“继续”及相似但非命中的表达。
- 用户输入被接受与 continuation 资格查询之间发生新消息/任务竞态时，不恢复过期的失败目标。
- 对同一来源短语连续触发、IPC 响应丢失后重试、并发点击，验证 continuation 幂等。
- 输入意图与新 Turn/队列受理竞争、队列排水与 continuation 占用竞争、History/DB 提交响应不确定时，验证原子结果、可恢复状态与不丢输入。
- 无附件短语、精确“继续”加图片/文件附件、带附加文本并带附件分别验证路由；断言附件进入模型实际消息而非只进入持久元数据，来源摘要不覆盖用户材料。
- 附件引用损坏/读取失败、输入意图响应丢失后重试，验证不误标消费、不漏附件、不生成重复执行。
- 同一 request ID 同 payload 重投返回既有结果；同一 request ID 不同 payload 明确冲突；客户端响应丢失后不重复启动。
- 已提交成功工具结果随 transcript 恢复且 executor 调用数不增加。
- 普通新 Turn 的摘要重建覆盖部分成功写入、后续工具错误、失败工具副作用未知三种状态，并逐项断言模型实际收到的上下文材料。
- History 缺损或结果冲突时摘要拒绝将写入标成成功；模型被要求先核对现实文件状态。
- 摘要达到 token 上限时保留来源、已提交写入事实、终止原因和未知副作用标记。
- 未结算工具、未知副作用、审批、安全拒绝、取消、中断、配置变化均拒绝自动续跑。
- 从头重试仍排除所有关联失败 assistant 尝试，并保持原始用户请求上下文。
- 从头重试点击后、出站受理拒绝/排队后及新尝试再次失败后，来源失败消息仍在 renderer 消息列表并可通过重试关系定位。

## 9. 风险与产品选择

1. **短语匹配歧义：** 承接信号不能吞掉附加任务内容；识别短语后仍须保留用户输入全文作为新 Turn 要求或 continuation 附加指令。
2. **输入接受竞态：** 资格解析必须和主进程当前会话状态校验组合；不能在 Renderer 读取一次状态后延迟使用。
3. **副作用事实准确性：** 工具结果、History 追加和文件状态可能不一致；摘要保留 `unknown`，不从预览元数据推断成功。
4. **上下文范围与 token 成本：** 只注入明确相关的最近失败过程，并限制长度；长期任务不得无限复制工具输出。
5. **续跑拒绝文案：** 错误码需映射到面向用户的短说明；技术性 checkpoint/hash 细节留在日志与诊断信息。
6. **自动续跑可见性：** 用户发送短语后需在原失败消息上看到正在续跑或已将过程摘要带入新 Turn 的状态，避免看起来输入被吞掉或又启动了全新任务。
