# 存储设置占用刷新卡顿开发与自动化测试计划评审

- 日期：2026-10-10
- 对象：`docs/plan/storage-settings-profile-latency-development-plan.md`
- 结论：**Request changes：6 项阻断需在执行前修正。**
- 评审范围：静态核对执行顺序、已通过的优化方案、现有同步采集与维护实现、自动化验收设计。本次未实施功能，未运行测试或性能基准。

计划已将可信索引、维护排空和代际隔离映射到具体任务及测试，方向正确。以下问题会使计划无法可靠兑现取消合同、性能证据或只读采样结论。

## 1. [P1] cooperative cancel 未定义同步采集中的取消通道和有界排空

**位置：** 3.2.1–3.2.2（第 81–82 行），4.2.2–4.2.4。

计划要求 worker 收到取消后关闭 SQLite 并退出，以此作为维护 drained 条件，但实现任务仅指定 cooperative cancel、finally-close 和超时传播。当前采集使用同步 SQLite `.get()`/`.all()`/`.iterate()`、连续 JSON.parse/hash 循环；例如 `electron/database/sessionStorageProfile.ts:194` 起事件遍历在一个同步调用中运行。将函数搬到 worker 后，这些操作仍阻塞该 worker 的事件循环，普通取消消息和 worker 内定时器无法在执行期间被处理。finally-close 也只有在同步函数实际退出后才会运行。

因此，fake worker 能响应取消不证明真实同步采集能够响应。对长 SQL 或超大 payload，若维护等待 cooperative cancel，超时不一定释放读连接；若只拒绝 Promise 就恢复维护准入，则又违反 drain 合同。

**必须调整：** 在 3.2 阶段确定真实可执行的取消策略。可以用共享取消标志在可分块的循环中检查，并为不可中断 SQL/单次解析设置主进程 watchdog；超时或无法协作退出时明确终止 worker，等待实际线程退出后再认定资源已释放。强制终止不能依赖 JS finally 执行，须以退出后的 SQLite 锁释放证据验收。另一可接受方案是允许同步任务完成后退出，但明确等待上限及维护拒绝/恢复规则，不能将其宣称为即时取消。

**自动化要求：** 使用真实 worker 和合成数据库，在同步 CPU 工作及 SQLite 读快照持有期间取消/超时；断言在规定上限内任务结束、后续 checkpoint 成功、后续采集可运行。覆盖 worker 没有机会处理取消消息的情况，不能只用 fake worker 或异步延迟验证。

## 2. [P2] 优化前性能基线被排到所有实现之后

**位置：** 第 0 节，7.1.1–7.1.4（第 166–169 行），依赖摘要（第 199 行）。

已通过的优化方案要求 Phase 0 先取得 SQL、正文审计、文件扫描等分段耗时，再实施迁移与拆分。当前第 0 节只有环境/正确性基线和样本发现器；版本化性能 fixture、分段指标与运行阈值全部位于第 7 节，即在重构、worker、coordinator、IPC/UI 完成后才建立。

按当前“不可跳项”的顺序，无法留下同一 fixture、同一测量方法的优化前响应性和耗时证据，也无法用分段数据指导扫描优化。若只对最终实现跑基准，测试通过仍不能说明原卡顿被消除，最终结果自身还可能成为门槛依据。

**必须调整：** 将 fixture builder、分段计时、主进程事件循环/轻量 IPC 探针及优化前基准运行前置到第 0 节，且在改变 collector 执行模型前保存脱敏合成指标。固定版本、规模、重复次数和统计口径；最终第 7 节使用相同 fixture/探针对新实现复测。明确阈值确定时点及产品目标，不从最终被测实现的结果直接推导通过阈值。

**自动化要求：** 同一基准能分别测量原同步 handler 和最终 worker handler，报告概览延迟及主进程响应性；保留优化前失败/高延迟作为预期基线证据，不让“失败任务不得继续”的规则阻断必要的 RED/基线记录。

## 3. [P2] 真实安装文件变化不能直接证明采样器写入

**位置：** 数据安全边界、第 14 行失败停步规则、7.4.5（第 193 行）。

计划读取真实安装的活动数据库，但未要求或验证外部写入者静止，同时将 DB/WAL/SHM 的身份、大小、mtime、表行数任一变化直接判为采样失败。真实 SpaceAssistant 的会话写入、后台维护或 checkpoint 都可能改变这些指标；即使采样 worker 完全只读，也会触发该失败判定。只读 SQLite 在 WAL 模式下对共享内存的协调行为也不能简单用 SHM mtime 作为应用层写入判据。

这种前后比较不能归因到采样器；按失败停步规则，它可能在合成验证全部通过后阻断完成，且与“不可安全采样则 skipped/不可用”的完成定义没有明确衔接。

**必须调整：** 将确定性的无写入证明放在无外部写入者的临时 fixture 中，验证只读打开、禁止写 SQL/维护调用以及持久数据无变化。真实采样需要选择并写明策略：自动确认目标静止后采样，无法确认则 skipped；或允许活动只读采样，将外部变化记为 concurrent-change/inconclusive，不据此归因采样器写入，也不作为无写入证明。不得为消除变化而操作真实应用数据、停止会话或绕过 WAL。明确 skipped/inconclusive 是否完成该任务及如何继续后续报告。

**自动化要求：** 注入独立写连接在采样期间提交，证明该情形与采样器违规写入被区别处理；测试 missing、不可安全采样、并发变化的终态均与最终完成定义一致。

## 4. [P2] 失败停步规则与 RED 任务的完成条件冲突

**位置：** 执行约定第 12–14 行，以及所有独立 RED/GREEN 任务。

计划要求 RED 测试先失败，同时要求“完成验收后”才进入下一项、“失败时不得越过失败任务”。按字面执行，1.1.1 的预期失败就会阻止 1.1.2 实现；1.2.1 的现有语义锁定测试通常本就通过，也不能强制制造 RED。2.1.3 的禁止正文 fallback 测试在正确完成 2.1.2 后可能立即通过，不能因此认定任务未达标。

**必须调整：** 将一组行为的测试、实现、回归合并为一个任务，RED/GREEN 作为任务内部步骤。明确“因目标行为缺失而产生的预期 RED”是有效阶段证据，导入失败、fixture 错误等非目标失败才需停步；现有行为锁定允许初次 GREEN 并说明原因。既有不相关测试失败应记录、归因并定义处理门槛，不能要求先修复任意仓库问题才能开展本需求。

## 5. [P2] 前置任务引用尚未交付的 IPC/采集接口，依赖顺序不自洽

**位置：** 3.1.3、3.1.6、4.2.1–4.2.4、5.1–5.2、6.1，以及 `0 → 1 → 2 → 3 → 4 → 5 → 6 → 7`。

第 3 节要求测试“IPC 返回明确错误”并迁移 SQLite/审计/文件枚举，第 4 节要求维护状态可由 IPC 返回并接入压缩入口，但 overview/audit 采集任务直到第 5 节才交付，新 IPC 合同与错误映射直到第 6 节才实现。执行者必须提前实现后续任务，或用 fake 路径暂时代替真实行为，两者都不满足“唯一执行清单、不可跳项、每项独立验收”。第 3 和第 7 节还重复安排入口定位和加载失败的实现，无法保证后者存在真实 RED。

**必须调整：** 先交付可直接调用的 overview/audit collector，再实现线程外适配器；worker client 阶段只验收 client 合同，不声称尚未接入的 IPC 已通过。coordinator 可注入已完成的 client，随后将维护屏障和 profile IPC 作为同一接入任务交付，避免实际入口短暂绕过协调器。第 7 节定位为真实编译/打包运行回归，不重复实现已交付的路径解析与错误合同。列出每个任务的明确依赖、目标文件和验收命令。

## 6. [P2] 缺少任务总量限制、应用关闭和并发维护的合同与测试

**位置：** 3.2、4.1–4.2、6.2；已通过方案 Phase 3 的并发上限与关闭清理要求。

single-flight 仅合并相同 key，不能限制 overview/audit、不同数据库或不同代际的 worker 总数。计划没有定义队列上限、审计与概览竞争策略，也没有将 coordinator 关闭接入 `electron/main.ts` 的 before-quit 清理链。现有主进程已有 shutdown 截止时间和数据库关闭协调，新增 worker 必须参与资源释放。否则退出期间可能仍启动任务，或读事务/未完成 Promise 留到强制退出。

此外维护屏障只覆盖“维护与读任务”，没有明确两次维护请求的互斥。如果两次请求都等待 drain，一个维护的 finally 恢复准入可能提前解除另一个维护的屏障。renderer 防重复点击不能覆盖多个 IPC 调用方。

**必须调整：** 增加 coordinator 生命周期任务，规定全局/每库并发上限、排队或拒绝策略、关闭时停止准入与终止/排空截止时间；将其接入应用 shutdown。维护操作按数据库串行化或明确拒绝第二次请求，屏障只能由持有者释放。测试 overview/audit 并行请求、跨代际任务、关闭期间新请求、超时退出、未完成 Promise，以及两个维护请求的交错，证明不会提前恢复准入。

## 任务拆分与建议执行顺序

目前按每个 RED/GREEN 分成两项，粒度过细；真实样本发现器又被放在核心开发之前，增加主路径依赖。建议以以下可独立验收的行为包作为任务，内部保留测试先行和命令证据，约 10–12 项即可，不必为追求数量机械合并：

1. 环境、现有正确性基线、版本化 fixture 和优化前性能证据。
2. shared DTO、编译期合同及严格采集兼容基线。
3. overview collector：可信索引、未知分类、物理扫描与完整性规则。
4. 显式 audit collector 和 CLI/cleanup estimate 兼容。
5. worker client/入口：真实执行、错误、取消、超时及资源释放。
6. coordinator：身份、代际、缓存、single-flight、任务并发限制。
7. 维护串行化、排空屏障、失败失效与 IPC/preload 接入。
8. 应用关闭集成及实际 worker/SQLite 维护竞态回归。
9. 设置页概览和审计状态、请求生命周期、维护后刷新及本地化。
10. 编译和打包运行 smoke test、优化后性能对比、全量测试及类型检查。
11. 独立只读样本工具与可选真实采样；不可用/并发变化按明确终态记录。

每个任务应列目标文件、前置依赖、关键验收及证据位置。上述顺序允许纯 collector 先完成，但真实 IPC 只能在 worker 与维护屏障同时具备后切换。

## 非阻断建议

- 7.2.5 当前只检查包内 worker 文件及路径；增加从编译产物和打包目录实际启动 Electron worker、打开合成 SQLite、返回结果并退出的自动 smoke test，以验证运行时模块加载而非仅文件存在。
- 0.5 先实现、0.6 后写测试与 RED → GREEN 约定不一致，建议调换。执行约定要求只修改任务列出的文件，但多数任务尚未列出具体目标文件，开始实现前应补齐文件范围。
- 1.1 的 shared 类型合同应明确包含 `typeTests/` 编译期校验；Vitest 运行时测试不能代替跨层类型边界检查。
- 第 6 节新增未知状态、采集时间及审计 UI，需列出 i18n 资源、类型生成和 `npm run i18n:check`，避免以硬编码文本完成组件测试。
