§0TL;DR

现象：每次输入指令，主进程冻结 15–34 秒，应用几乎失去响应。

直接原因：会话存储正处于「legacy messages 表 → canonical 事件流」的迁移期。读路径采用读时验证的信任模型——每次读取都同步执行「canonical 全量重建 + 与 legacy 双向字节级对比」（L2 兜底分支一遍；其中每条流的 payload 实际被解析两遍），对比失败回退 legacy 但没有失败负缓存，下一次输入原样重付全款。活跃会话的事件流已累积约 150MB（事件内嵌完整请求快照，O(n²) 膨胀），单次重建+对比即 15–34 秒，全部跑在主进程事件循环上。

判断：迁移验证本质是一次性的离线工作，把它放在每次指令执行的热路径上不是合理权衡，是设计失误。摊销假设（L1 缓存命中后近零成本）被击穿：未割接会话的消息写入触发器持续删除 eligibility（L1 快路径门禁）、mismatch 无负缓存、活跃流的状态承载事件触发全量回读。

改进方向（详见 §4/§5）：验证出栈——读路径只消费持久化结论（内容指纹 + 退避键控的负缓存 与 eligibility），一致性改由写路径增量维护 + 后台异步重验保证；事件负载停止内嵌全量快照。P0 即包含重验异步化（v2 前置，评审 B1）：负缓存命中期间读路径立即走 legacy，全量重验在后台预算化分片执行——读路径永不阻塞等待对比。P2 拆为 P2a（requestSnapshot 瘦身，唯一消费方比较前即剥离 messages，小改动拿大头）与 P2b（context 基线增量链，大改造单独评估）。

目标事件循环时间线（线框示意）

等价性论证：去掉「读时验证」为什么不破坏 fail-closed B1 张力正面回应

  • 不变量保持：读出的正文仍只有两种来源——已验证的 canonical 投影，或 legacy 本体。任何时刻都不返回「未验证的 canonical 正文」，fail-closed 语义不变。
  • 负缓存键控（v2 重设计）：mismatch 结论不与 watermark 等值绑定——那会在活跃会话上每轮失效（每轮 append 多个事件必推进 cursor，B1）。改为：内容指纹（canonical 事件区间聚合哈希 + legacy 消息摘要）标识「同样的输入」，退避窗口（mismatch 后 N 轮 / 指纹未变期间）内直接走 legacy。指纹变化 ≠ 立即同步重验，而是「立即走 legacy + 登记后台重验」——安全侧（不放过新分叉的验证机会）与性能侧（读路径不阻塞）同时成立，代价是把重验延迟到后台窗口，与现状「mismatch 回退 legacy」的实际行为等价。
  • 永久分叉的诚实处理：重验 N 次仍 mismatch 且无对应 repair 义务的会话标记 permanent，转长期 TTL；不假装它会被修复。清除路径不依赖 recordProjectionRepairResult 钩子（mismatch 与 repair 队列现状无接线，B2）。
  • 迁移目标不受损：eligibility 判定从「读时碰运气」改为「后台确定性推进」，割接（cutover）收敛速度反而可度量、可门禁。

§5改进路线图（P0 → P3）B1/B2/B3/B4 重构

P0

止血：指纹+退避负缓存 · 重验异步化 · 去重复读

目标：读路径永不阻塞等待全量对比——mismatch 活跃会话读路径 < 2s（v2 前置重验异步化，B1）；其他会话 < 2s。①–⑤⑦改动小、无 schema 破坏、可独立发布；⑥ 涉及启动编排与多入口并发，需先过实施评审（v2 复审放行范围）。
改动点
① 独立 rejection 表（B2.3 决断：不与 eligibility 同表，避免接入 5 类既有触发器的整行 DELETE 语义）：canonical_session_projection_rejections(session_id PK, fingerprint, watermark_seq_at_record, event_count, attempts, retry_after, last_reason, permanent)；显式豁免 v46 cursor 维护触发器（schema.ts:1806-1825 现状全表清空 eligibility，若同机制会引发集中重验风暴，B2.2）。
② 键控（M1 收紧：读路径检测必须 O(1)）：读路径的变化检测只用水位/计数类 O(1) 元数据——event_count + watermark_event_id + legacy 消息行数/max(rowid)；逐事件 kind/turn 签名与 content-hash 只在后台重验时计算（重验结果连同完整指纹一并写回 rejection 表），legacy 摘要挂在 getMessages 返回路径上捎带累计。命中条件 = O(1) 元数据未变 或 退避窗口未到（attempts 指数退避，上限 7 天）；O(1) 元数据变化 ≠ 同步重验，而是「立即走 legacy + 登记后台重验」。
③ 重验异步化（P0 必备）：读路径命中负缓存 → 立即返回 legacy + 若指纹已变则登记重验任务；后台队列分片让步执行（单片 ≤50ms），完成后刷新 rejection / 转 eligibility。轮次终态后与启动空闲期触发。
④ 清除路径三分：指纹变化（触发后台重验）/ 退避到期（后台重验）/ 显式动作（repair 对应义务完成、用户重建索引）。不依赖 repair 成功钩子。
⑤ 同轮读合并（评审建议 4.1 边界）：memo 作用域 = 单次 runToolChatSession 调用；任何 appendHistoryEvents / appendBatch 写入即失效（否则续轮拿到缺上一轮 tool result 的过期 transcript）；memo key = requestId 解析后的 invocationId（避免重试串流）。toolChatLoop:1026/1065 复用、hostedTurnHandoff:218 复用、单次读内按 invocationId memoize readSync。
⑥ 启动顺序解耦（v3 新增 · R7① · v4 补 N1/N2 设计，实施前需过实施评审）：createMainWindow 提前至 db open + 最小 IPC 注册之后；canonical-history recovery / ledger reconcile / spill GC 等重恢复改为窗口就绪后的后台分片任务（复用 ③ 的重验队列基础设施）。
N1 并发设计（决断：admission 按会话互斥为主，入口延迟为降级选项）：(b1) 把「会话级恢复未完成」纳入统一调用级准入（admission）的排队理由——所有 turn 驱动入口（渲染 IPC、飞书 :1424、butler :1433、微信 :1435）统一经 admission 排队等待目标会话恢复完成，而非只覆盖渲染输入；(b2) IM/butler 进程级启动可保持现状时序（它们本就在全部恢复 await 之后才启动，现状无损失），但其触发的 turn 受 (b1) 约束；(b3) 会话台账 JSONL 文件级互斥：恢复写 repair 事件（main.ts:694-755 getSessionEventSink）与 turn 执行读 ledger 必须按会话单写者顺序化（WAL/runInTransaction 只覆盖 SQLite，不覆盖 JSONL）；(a) 降级选项：若 admission 集成复杂度超预期，P0-⑥ 先落地「IM/butler 延迟到后台恢复完成后启动」（与现状时序等价，无回退风险），(b3) 仍必须做。重排时逐对核对已明写的顺序不变量：persisted-orphan cleanup 先于 runtime recovery（:822-823）、admission 活跃段清零先于门构造（:1206-1207，反序会读入幻影票据）、usageStats 版本快照先于 IM/butler 启动（:1074-1077）、butlerScheduler.start 晚于 initTray（:1427-1432 托盘前提校验）；每对补回归测试。
N2 过渡态设计：「恢复未完成期间历史读走 legacy」的假设不成立——中断态会话投影 throw CANONICAL_SESSION_CONTENT_UNAVAILABLE（sessionTranscriptProjection.ts:318/322/329），且首屏自动选中的 list[0] 恰是最可能中断的会话。方案：分页/投影读路径对「恢复中」会话返回显式 recovering 过渡态——legacy 骨架行照常返回（内联守卫 :320 本就快速），canonical-backed 正文先以骨架/占位呈现，ChatView 显示「会话恢复中」横幅；恢复完成经事件推送（复用 session/turn 桥）刷新正文。禁止静默吞异常（ChatView :465 静默 catch 不再扩散）。splash 改造：showStartupStatus 现为窗口前独立 splash 且主窗口 show 后即销毁（main.ts:200-233/:419），需延后关闭或改造为窗口内进度条。
⑦ 首屏入口回归（v3 新增 · R7②）：负缓存/结论查询位于 readSessionTranscriptProjection 汇聚点，天然覆盖 chatGetMessagePage / getProjectedMessages / turn display 等首屏入口；为 chat:get-message-page 与会话切换补「mismatch 会话首屏 <500ms」红绿测试；并入 N2 过渡态测试（v4）：中断态会话首屏 → recovering 骨架 + 横幅、恢复完成后事件推送刷新、恢复期间该会话 turn 在 admission 排队。
验收
（两档）
mismatch 活跃会话（最差案例）：读路径 < 2s（负缓存/退避命中，legacy 直返）；每轮至多一次后台重验，重验期间 UI 无冻结。其他会话：输入指令 → 首个流式 delta p95 < 2s。session.transcript.read durationMs p95 < 500ms。启动（v3）：进程启动 → 主界面可交互 p95 < 5s（恢复后置分片）；首屏/切换会话 chatGetMessagePage p95 < 500ms。
风险
负缓存 stale → O(1) 元数据变化检测 + 后台重验兜底；观察期保留 shadow 日志核对降级正确性；v46 触发器豁免需单测锁定（负缓存不随 cursor 维护被清空）。⑥ 专属：admission 排队语义扩展到 IM/butler 后需回归「远程消息在恢复期间到达」场景（排队不丢弃、恢复后按序放行）；JSONL 会话台账单写者互斥需并发红绿测试；启动重排逐对核对四组顺序不变量（:822-823 / :1206-1207 / :1074-1077 / butler 晚于 initTray）；recovering 过渡态不得静默吞异常。
P1

读路径去重放：一致性改由写路径维护

目标：命中路径 < 50ms；canonical 对比彻底离开用户请求路径（含后台队列也只做增量窗口）。
改动点
① 同事务维护投影缓存（全新机制，评审建议 4.2 拆分表述）：watermark/commit_order 推进已是现状（agentHistoryStorage.ts:85-98），P1 新增的是 append 事务内增量更新投影缓存（新增消息追加），替代「eligibility 被消息触发器删 + 读时全量重放自证」。② 状态承载事件的工具转换校验增量化：维护 per-invocation pending tool/approval 视图（写时更新），校验查视图而非 readSync 活跃流全量。③ 字节级对拍收窄到增量窗口：turn 终态后对拍「自上次结论以来的新增事件」，全量对拍仅后台周期巡检。④ cutover / shadow 消费同一份结论与 memoize 快照。
验收
主进程单次事件循环阻塞 max < 200ms（perf_hooks monitorEventLoopDelay 常驻采样）；活跃会话 L1 命中率 > 90%。
风险
写路径复杂度上升 → 增量更新与全量重建的等价性用对拍测试锁定（红绿回归：增量结果 == 全量结果）；写路径故障回退 = 清缓存走 legacy，与现状兜底一致。
P2a

requestSnapshot 瘦身（小改动拿大头）B4.3 拆分依据

目标：消除每轮 O(n) 冗余写入的主体；改动半径最小。
改动点
代码事实支撑：重建器 rebuildClaudeMessagesFromHistory 不读 requestSnapshot（基线来自 context-committed/compacted 事件）；唯一消费方 assertHistoryRequestCompatibility（turn.ts:637-676）比较前已 withoutMessages() 剥离 messages。因此 ① 事件写入时 requestSnapshot 仅保留 route + request 除 messages 外的字段（messages 可留长度/哈希供诊断）；② 存量不回填，读取端对 pre/post 格式统一按「有 messages 忽略、无 messages 兼容」处理（消费方本来就是可选字段跳过，pre-snapshot 事件已有跳过先例）。
验收
新增每轮事件字节与轮次无关（O(1)，基准测试）；canonicalHistory 重建行为零变化（对拍测试）。
风险
丢失请求正文取证能力 → 若需保留，messages 走 spill 引用（复用既有 spillStore，属「扩一类字段」而非新建机制）；requestSnapshot 完整性断言测试同步调整。
P2b

context 基线增量链 + 双版本读路径 + transcript 表瘦身（大改造，单独评估）

目标：重建成本与「基线 + 增量」线性；完整终止 O(n²)。工作量为独立立项，不与 P2a 绑定。
改动点
① 「基线 + 增量链」触及 invocation-context-committed.messages 全量基线语义，消费方必须逐一枚举改造（B4.1）：validateCanonicalInvocationMessages（要求完整 content）、mirrorCanonicalContextMessages（legacy 镜像需正文）、requiredUserMessage 逐字节匹配、foldClaudeSessionSnapshots 身份链校验、L1 seed 伪造成 context-committed 事件的路径（sqliteAgentHistory.ts:954-958）、recovery 修复器。② 双版本读路径是全新工作项（B3）：readSync 现状对 schema 不匹配硬失败（HistoryCorruptionError 'unsupported schema version'），「旧格式读兼容」不存在现成机制，需实现版本化解码层 + 红绿测试。③ session_transcript_entries.messages_json 纳入瘦身（B4.2）：每轮终态存完整 transcript JSON，同属 O(n²)，改为增量游标 + 基线引用。
验收
同规模会话重建耗时较改造前下降 ≥ 80%；混合新旧格式库读写回归全绿。
风险
改造半径大 → 独立技术设计先行；存量迁移默认关闭、审批后执行（沿用 A-07 cleanup gate 授权纪律）。
P3

执行模型与治理：长任务出主进程 + 观察门禁补课

目标：任何 O(会话) 计算不再可能冻结 UI；性能问题自此有门禁兜底。
改动点
① 全量重建/审计/对拍迁移到 worker_threads（WAL 只读连接并发安全；写操作仍由主进程单连接串行化）。先以 probe:sqlite 同款探测方式验证目标 Electron 版本在 worker 中加载 node:sqlite 的可用性，再锁定架构（评审建议 4.3）。② repair 治理：workspace-root-rejected 等不可自愈分类标记 terminal-failed，退出零退避；单流 pending <10 条的立即重试改为带最小间隔。③ 观察门禁协议落地（R-06/R-07）：复用已落地的 sessionProjectionObservation.ts + report CLI，补 owner 批准的阈值/样本数/观察窗口，纳入发布自检；monitorEventLoopDelay 超阈值告警进 agent 日志。④ 数据库膨胀止血（用户侧配套）：老会话归档、可选 VACUUM。
验收
repair 队列单调收敛（无永久 pending）；每次发布携带真实 profile 读延迟 p95 证据。
风险
node:sqlite 单连接约束 → worker 仅只读，写经消息回主进程；治理动作触碰真实数据 → 沿用现有授权/审批纪律。

依赖关系：P0 独立可先行；P1 依赖 P0 的读适配表；P2a 与 P0/P1 并行（数据层写入格式，读端天然兼容）；P2b 依赖 P2a 与 P1 的结论沉淀，独立立项；P3 的 worker 化承接 P0 后台队列的升级。每阶段收尾跑定向测试 + 真实 profile 只读观察，全量回归按仓库测试纪律执行。

§7风险与回滚

不破坏迁移既有投资
  • eligibility / cutover / dual-write / spill / repair 全套机制保留，只改变验证发生的位置与时机；rejection 表是独立新增的读侧结论，不动 eligibility 语义与既有触发器。
  • fail-closed 不变量（永不返回未验证 canonical 正文）以等价性测试锁定，改造前后行为对拍。
  • P0 memoize 的正确性边界（评审建议 4.1）：写入即失效 + invocationId 键控，防「续轮拿到缺上一轮 tool result 的过期 transcript」这一最大陷阱。
回滚路径
  • P0 负缓存带开关（config），异常时关闭即回到现状行为（代价是恢复卡顿，不丢数据）；rejection 表独立，回滚即停止读取，无需清理。
  • P1 增量投影失败 → 写路径清缓存 + legacy 兜底，与现状降级路径一致；kill switch（config.sessionStorageCanonicalApiRead 等）沿用现有体系。
  • P2a 消费方天然兼容可选字段（pre-snapshot 跳过先例）；P2b 新事件格式版本化解码层独立立项，旧读取路径保留可读 v1；存量压缩默认关闭、审批后执行。
配套的用户侧即时缓解（不等代码发布）
  • 当前卡顿会话（事件流 ~150MB）新建会话续聊，单次重建成本立即趋近于零。
  • 归档/删除不再使用的大会话；.agent/logs 历史日志（单日最高 488MB）可清理归档。
