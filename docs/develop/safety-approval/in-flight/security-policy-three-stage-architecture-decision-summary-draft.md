## 第 0 层【人必读｜约 5 分钟】

**一句话**：现在的毛病是「安全策略已经作出裁决，代码后面又改判一次」——用户已经授权安全审核 Agent 批准对外发送，消息仍在后面被一段硬编码逻辑拒掉。本方案把判决收敛成三段：**只观测事实 / 由策略统一裁决 / 执行前只校验「要执行的是不是被批准的那件事」**；迁移期间**不改变任何现有安全档位的效果**。

**只有 3 分钟的话**：读 D1、D2、D5，其余可后看。

### 需要你决定的事项

> 以下 7 项都是**价值 / 体验 / 风险容忍度 / 成本**问题，不是技术问题——技术可行性与事实核对已由评审完成。它们在原计划 §6 已被记为「已对齐」，此处的作用是请你**复核或否决**，而不是从零决策。

**D1｜标准档要不要允许「安全审核 Agent」替人点头，把消息或数据发给外部渠道？**
- 背景（不必先读方案）：系统有宽松 / 标准 / 严格三档安全设置——宽松不问直接放行，严格必须真人确认。本项只决定**标准档由谁点头**。
- 与现状的关系：与当前行为一致，本方案不改档位效果；请你确认的是这个档位映射本身能不能接受。
- 选项：A 保持「标准档由 Agent 审批」；B 标准档也改为必须真人确认。
- 选 A 的用户可见后果：标准档不再弹真人确认框，发不发由 Agent 决定；判断错时消息已经发出、取不回来。
- 依据强度：档位与代码的逐一核对尚未完成；「标准档是否会因此更常误发」没有任何数据。
- 我的推荐：A。你不决定＝按现状（A）继续。
- 下钻：B-01、§2.2、P2-02。

**D2｜「工作目录之外的文件写入」在标准档也交给 Agent 审批，可以吗？**
- 背景（不必先读方案）：Agent 默认只能改当前工作目录里的文件，写到目录外本来要经过审批。本项决定**标准档由谁批准这类越界写**。
- 与现状的关系：与当前行为一致；写入对象的身份、软/硬链接、原子写仍由执行层独立校验，不因谁批准而放松。
- 选项：A 宽松与标准档由 Agent 审批、严格档真人；B 标准档就改为真人。
- 选 A 的用户可见后果：越界写不再打断流程；但 Agent 判断错时会真的改到目录外的文件，且不可逆。
- 依据强度：机制路径已核对；Agent 误批的实际概率没有数据。
- 我的推荐：A，但**B 是本次唯一建议你重新想一次的点**——这是方案里唯一把「Agent 可批准越界写」放进默认档位的决定。
- 下钻：B-02、§2.2、P2-04。

**D3｜遇到敏感内容时，标准档要不要改为真人确认？**
- 背景（不必先读方案）：探测器发现消息里有敏感内容（如密钥样式、批量导出）时，现在是分类器直接拦；改造后它只报告「发现了什么」，由档位规则决定动作——宽松档 Agent 放行，标准与严格档真人确认。
- 选此方案的用户可见后果：标准档用户在敏感内容外发时会被打断（体验损失），换来敏感内容始终由真人把关。
- 依据强度：探测器的覆盖范围和误报率没有实测数据。
- 我的推荐：接受。你不决定＝按此执行。
- 下钻：B-03、P2-05。

**D4｜探测器「无法判断」时，按现行设置执行，不因未知就自动收紧，接受吗？**
- 背景（不必先读方案）：内容检查会出现「不确定 / 不可用」的结果。当前取向是按档位照常执行，而不是一律拦下。
- 后果：正常操作不会被误伤；代价是确实无法判定的内容会按既定档位放行。
- 我的推荐：接受（与改造前保持一致；要收紧属于单独的产品决定，不混在本次重构里）。
- 下钻：B-04、P2-05。

**D5｜这次交付到底承诺到哪一步？**
- 背景（不必先读方案）：一部分验证需要仓库里没有的东西——正式安装包、对应的生产日志/数据库、真实外部渠道（微信、飞书、远程 MCP 服务）的测试账号。当前没有自动获取这些资源的路径。
- 选项：A 只承诺「源码修复完成」（全量测试 + 完整构建通过），外部验证一律列为「待外部验收」；B 承诺「原生产问题已复现并修复」。
- 选 B 的代价：要先备齐正式包与生产数据/测试账号，它们会成为**开工前的阻塞项**；选 A 时它们只是收尾时明示的未验项。
- 我的推荐：A。你不决定＝按 A。
- 下钻：§8、P5-04、P5-05、P5-08。

**D6｜本轮要不要顺手做这两件「以后能省事」的事？**
- 背景（不必先读方案）：
  - 一是**远程请求使用的工具目前有一套独立的放行判断**，与桌面共用的一套规则其实是两套实现，改一边容易漏另一边；本轮拟合并为一套（需要逐条核对远程侧全部放行判断，回归面变大）。
  - 二是现在有若干硬性安全限制（例如撤销授权后旧许可失效、递归审批保护）**散落在代码各处，说不清共几条、归谁维护**；本轮拟建一份「系统底线清单」并加自动检查，防止以后有人再在策略之后偷偷加一层改判。
- 选项：A 本轮两件都做；B 只做规则统一，清单与自动检查留到下一轮。
- 选 A 的代价：周期变长、涉及文件面更广；收益：消除双实现、堵住同类问题复发的入口。
- 我的推荐：A（两轮评审都确认这两件与主线相关，未发现应当删除的任务）。
- 下钻：§3、P2-06、P3-01～05。

**D7｜回退方式：按「一个策略领域一个提交」推进，每个领域可单独回退，接受吗？**
- 背景（不必先读方案）：本次改动横跨桌面、远程渠道和各个执行器；若堆成一个大提交，出问题只能整体回退。
- 代价：提交数量变多，每个领域都要各自的行为对照；收益：出回归时只回退一个领域。
- 我的推荐：接受。
- 下钻：§7。

### 不需要你决定（Agent 负责；列在此处是为了不占用你的时间）

- 审批什么时候失效：按「完整决策依赖」判断，而不是只比规则有没有改过（机制问题）。
- 安全规则的匹配顺序：保留现有分层判断语义，不改「从上往下第一条命中即生效」（事实问题，评审已核对代码）。
- 任务先后顺序与依赖环路（第二轮、第三轮评审已关闭）。
- 全量测试 / 完整构建 / 门禁的运行范围（仓库既定纪律）。

## 第 1 层【人机共读｜概要，人工可选】

**要解决的问题**：策略裁决之后仍存在散落各处的代码判决（gate、通道适配器、执行器），导致「已批准却被拒绝」，且无法从审计判断谁做的决定。

**三阶段职责**（细节见原计划 §2.1）
1. 事实生产：只报告观测结果与覆盖状态，不做 allow / confirm / deny
2. 策略决策：唯一产出 allow / require-confirm / deny，并记录命中规则、回答者、理由
3. 执行前校验：只核对授权是否存在、是否对应本次调用、对象是否仍一致；不重新做风险分类

**迁移原则**：先保持既有策略效果；有意改变默认行为的产品调整必须单独提出，不作为重构的隐含副作用（B-10）。

**阶段与出口证据**

| 阶段 | 一句话 | 出口证据 |
|---|---|---|
| P0 | 建基线与边界 | 源码基线、候选 inventory、行为矩阵、外部证据缺口清单 |
| P1 | 事实生产改为纯事实输出 | 旧限制仍由兼容消费者执行，行为等价矩阵逐格一致 |
| P2 | 统一策略决定、逐项移除决策后覆盖 | 每个域有 rule ID 或删除证明；档位矩阵落地 |
| P3 | 底线登记与新增硬编码门禁 | registry 覆盖 + CI 能阻断未登记改判 |
| P4 | 统一执行前授权检查 | 每通道有「executor 未调用」的负例 + 正常 dispatch 正例 |
| P5 | 最终验收与旧逻辑清理 | 源码关闭（全量测试 + 完整构建）与可选发布关闭分开 |

**已核查的关键断言**（供引用，不重复论证）

| 断言 | 证据 | 结论 |
|---|---|---|
| 三阶段划分与依赖链 P4-01 契约 → P2-10 失效协议 → P4-03 集成无环路 | review v2/v3 | 通过 |
| Phase 1 不会提前移除生效限制（兼容消费者 + shadow + P1-09 等价门槛） | review v1 第 3 项 → v2 | 已修复 |
| 「全局首条匹配」不再被当作现有语义 | review v1 第 2 项 → v2 | 已修复 |
| 外部证据（正式包 / 生产数据）不再阻塞源码开发 | review v1 第 5 项 → v2 | 已修复 |
| 阶段收尾全量测试与最终完整构建已入任务 | review v1 第 6 项 → v2 | 已修复 |

## 附录：本次试点的观察

1. **真正的取舍全部埋在 §6 表格里**，正文没有任何一处告诉读者「这是价值判断、它影响谁、你要不要否决」。而且一旦被记为「已对齐」，后续就没有人再复核了——这是最值得修的写作问题。
2. **人做 5 分钟的决策，需要先读 596 行**。分层后，第 0 层可以定位到全部价值判断，规格细节按需下钻。
3. **原文档缺「用户可见后果」这一层描述**：例如「宽松直接放行」只有机制含义，没有说用户会看到什么差别、什么情况下会被打断。人类层需要的是后果，不是机制。
4. **进度复选框与方案混装**：§4 定义了 `- [ ] / - [～] / - [x]` 的状态维护方式，§5 内嵌全部任务状态。方案基线会随每次勾选漂移，验证了「稳定规格 × 易变编排」应当拆分的判断。
5. **第 0 层可压到 1 页**：本文件第 0 层覆盖 7 个决策项 + 明确划出的「不需要你决定」边界。
6. **（2026-10-16 修订）人类层的两类典型缺陷已改掉，其中第二条推翻了「越短越好」的直觉**：
   - **黑话**：初稿出现 `outbound`、`permit`、`registry`、`remote policy` 等内部词，读者得先掌握仓库术语才读得懂。修订后人类层只用业务说法（对外发送、越界写、系统底线清单），内部词与编号一律降为行末「下钻」入口。
   - **过度简洁**：初稿 D6 只写「是否并入 remote policy 对账与底线登记 registry」，等于要求读者先翻到 §3/§5 才知道在决定什么。修订后每个决策项**自带背景、选项与后果，不打开任何其他文档即可裁决**。
   - 代价是第 0 层从 55 行涨到约 70 行：**人类层要设长度下限（信息完整度），而不是只设上限**；为压行数而丢背景，是把阅读成本转嫁给读者。
