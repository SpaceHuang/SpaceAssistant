# 工具调用安全审核性能调研与优化方案

> 2026-10-29；代码基线 `990d1e2e` 加当前工作区未提交改动。实测来自本机已有安全审计日志，并非构造模型请求；时间均为北京时间。本文是方案草案，不代表安全行为变更已获批准。

Codex 同类机制及可借鉴点见 [Codex 审批缓存实现对比](./Codex审批缓存实现对比.md)。

## 结论【人必读】

**真实日志证实：同一个指令回合内，连续编辑文件时会反复启动安全审核，后续编辑没有因为首次审核通过而免审。** 抽样的两个回合中，首次编辑审核分别耗时 12.254 秒和 2.481 秒；后续编辑仍逐次审核，平均分别耗时 14.313 秒和 3.064 秒。其中一个回合的 7 次编辑审核合计等待 98.131 秒；另一个回合的 18 次编辑审核合计等待 54.567 秒。各回合的审核时间区间均未重叠，所以在这两个样本中这些等待确实逐次累加。

对同一任务中同一文件的连续正常编辑，用户的意图通常是“完成这项修改”，而不是逐字确认每次替换。**每追加一个字都重新询问安全审核 Agent，是授权粒度设计过细，不是安全审核职责的必然要求。** 同样的问题应按工具能力系统处理：搜索复用获准搜索范围，文件修改复用获准目标范围，其他工具则按其实际能力和风险设定不同边界；参数变化本身不等于授权变化。

授权范围不是无限制的：目标变为敏感文件、目录外文件，或动作转为外发、执行、删除、扩大破坏范围等，仍须按相应策略重新裁决。普通文件的内容变化本身不触发重新审核；脚本、可执行程序和固定 CI 清单不消费缓存。

### 复核方法【机｜人工可跳过】

在项目根目录运行下面的只读脚本；它不输出会话 ID、路径或正文。排序基于审核完成时间，累计时长基于日志已有 `latencyMs`；需核对时间区间无重叠后才能把累计时长解释为串行等待。本日志由本机应用产生，测试安装或不同工作目录可能写入其他位置。

```bash
python3 - <<'PY'
import collections, json, statistics
p = '.agent/logs/SecurityAudit-20261029.log'
events = []
with open(p) as f:
    for line in f:
        try:
            events.append(json.loads(line))
        except ValueError:
            continue
groups = collections.defaultdict(list)
for e in events:
    if e.get('event') == 'confirm.outcome' and e.get('actor') == 'agent':
        groups[(e.get('sessionId'), e.get('requestId'))].append(e)
for rows in sorted(groups.values(), key=lambda r: min(e['ts'] for e in r)):
    rows.sort(key=lambda e: e['ts'])
    edits = [e for e in rows if e.get('toolName') == 'edit_file']
    overlap = sum(b['ts'] - b['latencyMs'] < a['ts'] for a, b in zip(rows, rows[1:]))
    if not edits:
        continue
    later = [e['latencyMs'] for e in edits[1:]]
    print({'edit_count': len(edits), 'first_ms': edits[0]['latencyMs'],
           'later_ms': later, 'later_mean_ms': round(statistics.mean(later)) if later else None,
           'edit_total_ms': sum(e['latencyMs'] for e in edits),
           'outcomes': dict(collections.Counter(e.get('outcome') for e in edits)),
           'all_reviews': len(rows), 'all_review_total_ms': sum(e['latencyMs'] for e in rows),
           'overlapping_intervals': overlap,
           'unique_invocations': len({(e.get('actorRef') or {}).get('invocationId') for e in rows})})
PY
```

## 安全审核的目标和工作边界【人机共读】

安全审核保护用户委托与资产安全：识别越出用户任务的操作、不可信材料诱导的越权、敏感信息或凭据访问及外发、持久化削弱安全、破坏性操作和事实不完整等风险。它不是业务 Agent 的逐字审稿员，也不负责决定文案每个字是否可以写入。

当前实现的证据：`electron/skills/bundled/securityApprovalSkill.ts` 将动作内在风险和用户授权分开判断，把工作目录内常规读写列为 low / medium；任务无关、已证实的恶意注入及信息不足是拒绝依据。桌面端由宿主提供的用户任务是可信证据，模型自己声明的“用户已授权”和文件/网页内容不能替代用户指令（`approvalAgent.ts`）。这些是当前审核器的判断口径，不等于宿主已经实现任务级文件授权。

安全边界应按**主体、用户任务、操作能力、目标范围和风险变化**划定：任务授权修改某文件时，可以覆盖同一任务内多次正常修改；每次仍由宿主核查实际目标、当前策略与授权状态，并保证敏感路径、链接替换、明确要求人工确认等规则不能被复用绕过。高风险外发、命令、凭据或敏感位置有各自授权边界，不能从普通文件编辑授权推导出来。脚本、可执行程序和固定 CI 清单的修改不消费写入缓存；普通文件不因为内容变化而反复送审。已有敏感路径、系统路径及强制真人确认等策略仍然生效。

## 为什么部分调用反复审核【人机共读】

- **审核单位是单次工具调用**：`electron/confirmation/agentChannel.ts` 每次创建独立 invocation，`approvalAgent.ts` 创建内部会话并启动审核；它们没有产出可在当前任务的后续编辑中使用的文件范围授权。
- **已有文件被硬性排除在快通道外**：`toolCallGate.ts` 的 `targetMayUseFastTrack` 仅允许工作目录内不存在的目标通过新建 `write_file` 快通道。`evaluateFileToolAutoApproval` 本身已有 `edit_file` 的修改体量判断，但 gate 最终仍不允许已有文件编辑使用结果。标准档的默认写规则因此将普通编辑送交 Agent。
- **现有“记忆”不是任务授权**：`decisionCacheWriter.ts` 不允许将 Agent 回答写入用户确认记忆；直接将单次 approve 记成用户授权会混淆主体。而单次执行 permit 绑定的是具体调用及材料，无法代表同一任务对目标文件的持续授权。系统目前缺少同时表达任务范围、资源和有效期的机制。
- **每次复核和每次模型审核是两件事**：`agentSdkSafetyPolicy.ts` 的执行前重检与文件身份校验仍需要；性能问题是把每次业务编辑都重新送进模型审核，而非宿主对每次执行进行轻量边界核对。

复查入口：`rg -n 'targetMayUseFastTrack|file-fast-track' electron/confirmation/toolCallGate.ts`；`rg -n 'editCharSpan|targetKind' electron/tools/writeFileAutoApproval.ts`；`rg -n 'MEMORY_WRITE_NOT_HUMAN_ANSWERER' electron/confirmation/decisionCacheWriter.ts`；`rg -n 'invokeApproval|latencyMs' electron/confirmation/agentChannel.ts`。

## 缓存命中的核心粒度【人必读】

**同一个工具、同一种操作、同一个对象，且仍处在批准的安全边界内，才能复用；内容变化不必然造成未命中。** 这是用户明确提出的方案原则。缓存只在当前会话的主进程生命周期内有效；期限不扩大工具和对象范围。

| 已批准的调用 | 后续调用 | 是否复用 |
| --- | --- | --- |
| `edit_file` 修改 A | `edit_file` 继续修改 A 的其他文字 | A 为普通目标、已有持续批准且当前任务允许时命中；内容变化本身不使缓存失效。 |
| `edit_file` 修改 A | `edit_file` 修改 B | 不命中，B 是不同对象。 |
| `edit_file` 修改 A | `run_shell` 执行 `rm A` | 不命中，工具与操作均不同；即使目标还是 A 也不能沿用。 |
| `edit_file` 修改 A | `write_file` 覆盖 A | 默认不命中，工具和覆盖语义不同；只有未来明确设计并批准等价能力映射才可互通。 |
| `grep` 在目录 D 搜索 | `grep` 在同一目录 D 搜索不同关键词 | 存在可复用范围批准且当前策略和任务约束允许时可命中；搜索根与递归范围须相同，仍需检查敏感边界。 |
| `grep` 在目录 D 搜索 | `grep` 搜索目录 E 或扩大到 D 的父目录 | 不命中；搜索范围发生变化。 |
| `run_shell` 执行某命令 | 不同命令或会改变目标/副作用的参数 | 默认不命中；必须识别命令、完整参数、工作目录、重定向和网络影响，不将 shell 当成单一安全能力。 |

这里的“对象”由工具能力定义：文件工具是规范化后的目标文件，搜索是搜索根及允许的递归范围；Shell 涉及命令及其可解析的目标和副作用，不能仅按字符串中的文件名或 `run_shell` 工具名判断。多对象调用须逐一验证全部对象，不能只验证第一个。浏览器和 MCP 等需要各自定义可识别的对象和操作；事实不足时回退原审核，不能猜测相同。

授权或 Agent 审核结果可由策略允许缓存，记录必须区分来源；命中后继续运行当前 deny、强制真人确认和安全事实检查。不能把一条“审批通过”视为跳过所有安全检查的通行证。若单次结果不足以支撑跨调用同工具同对象复用，先按策略获取足够的授权或审核范围；复用粒度不得超过实际批准的范围。

## 技术方案：统一审核缓存与逐次边界校验【人机共读】

### 适用范围与目标【人必读】

同一套机制覆盖**所有工具及所有现有链路**：桌面、飞书、微信和自动任务。安全审核 Agent 或用户的批准，凡能准确确定工具、操作、对象及适用安全边界，且当前策略允许复用，均可写入会话级缓存。工具本来就直接放行时不增加模型审核；当前策略禁止复用、要求真人逐次确认，或对象/风险无法可靠识别时仍走原规则。各链路均接入，不代表一条缓存自动跨链路共用：记录绑定链路及可验证主体，避免把桌面批准错误用于其他用户、远程聊天或无人值守任务。

这是统一机制与实际缓存命中两层含义：**覆盖所有工具和链路**，但每个调用是否可安全命中取决于它的操作、对象、事实覆盖和生效规则。不能因为缺少某工具的日志就将其排除，也不能因为所有工具都接入就用同一种粗粒度 key 放行。

### 缓存键与对象匹配【机｜人工可跳过】

每个缓存记录绑定 `lane + sessionId + 已验证主体 + 授权域及版本 + tool + operation + 对象集合 + 执行环境 + policyVersion`。必须全部匹配；不同会话或链路不共享。桌面主体由主进程所在 userData/profile 确认，飞书与微信绑定宿主验证的渠道及 owner，自动任务绑定任务授权记录及 revision；无法确定主体则 miss。

| 能力 | 精确匹配内容 | 可变化的内容 |
| --- | --- | --- |
| 文件操作 | 工具名、操作、规范化目标文件、工作目录/环境；移动同时包含源与目的地。`edit_file` 和 `write_file` 分别记录。 | 普通文件的替换文字；每次仍执行当前策略、任务约束及路径身份核验。 |
| 目录搜索 `grep` | 工具名、规范化搜索根、单文件或递归范围、工作目录/环境。 | 搜索词和过滤条件仅在不改变已授权根、递归边界及安全策略时变化。 |
| `run_shell` | 完整命令及参数、工作目录、解析后目标、重定向和网络等执行边界。 | 仅将经测试证明等价的 shell 包装规范化；复杂命令即使材料精确相同，也须有可验证的完整对象契约；动态展开或隐含对象不可验证时 miss。 |
| MCP / 浏览器 / CLI / 出站 / Toolkit | 精确工具及子操作、连接或 capability 身份、账户主体、全部资源和接收者、版本及执行边界。 | 仅登记的对象契约明确允许且不改变对象/权限的参数可变化；其他参数精确匹配。无法验证全部对象时 miss。 |

**多目标**：本次调用的源、目的地和其他实际目标必须全部提取。缺任一对象或调用对象集合与本次范围批准不一致则 miss。按当前方案，一次范围批准覆盖完整对象集合；不拼接多条独立批准扩大权限。空对象集合不得作为通配符。对象不同、工具不同或操作不同均不命中。

**对象覆盖契约**：每种可缓存的能力必须由宿主登记版本化识别器，明确枚举操作涉及的对象、提取来源、隐含状态、环境绑定和可逐次验证的覆盖条件；不能证明全部对象和状态时 miss。当前仅为文件工具和 grep 定义上述识别口径；其他能力在对应识别器及边界测试完成前均 miss，统一入口仍执行原策略。空集合仅在登记契约明确证明该操作无对象时可表示无对象，绝不作为通配符。参数齐全、通用 facts 的 `complete`、服务端自报或工具描述均不能证明对象覆盖完整。对登记契约要求精确匹配的参数，JSON 对象键排序、数组保序；非法或截断时 miss。参数摘要只是额外约束，不可代替对象证据。比较摘要在主进程内使用会话随机 HMAC 密钥，不写日志或持久存储；主体和对象不得由模型自述伪造。

### 单次批准与会话范围批准【机｜人工可跳过】

现有 `ApprovalVerdict.approve` 只批准本次调用，不生成会话缓存。新增 `reuseApproved + scopeCandidateDigest`，主进程将候选工具、操作、完整对象集合、执行环境、sessionId 与授权版本打包并计算摘要；安全审核 Agent 在首次审核中同时判断本次与该候选范围，无需额外发起一次模型请求。`approve`、`reuseApproved=true`、摘要一致且共享策略允许该 Agent 授予该范围，才建立 Agent 来源的会话缓存；旧版/缺字段/拒绝/超时/摘要不同均只按现有流程处理本次调用，不缓存。用户的单次确认也不自动升级为会话授权；只有现有确认通道能够明确表达且用户实际选择会话范围确认时才产生 user 来源记录；否则仍是单次批准，不新增界面。用户和 Agent 来源不可混淆。

缓存作为当前策略的输入，先执行 deny、locked、人工逐次确认与当前任务约束；宿主验证当前任务确实允许本操作，才可消费缓存。宿主已有结构化授权时直接校验；否则只在当前权威用户消息和首次批准时冻结的可信上下文逐字一致且完整时复用原判断，使用会话 HMAC 对比；消息不同、截断、证据缺失或指代不清时 miss，进入原审核。不得将模型理由当成新的用户授权。明确只读任务不能借旧写入缓存放行。

拟新增共享策略规则 `review-cache-scope-grant-v1` 和 `review-cache-current-task-constraint-v1`，分别产生范围写入与当前任务约束的 decision trace。facts 只报告观察、来源及覆盖；final-check 只核对已批准的身份、对象、授权代次、permit 和执行材料，不重新评估业务风险。新增规则必须遵守项目安全策略优先级。

**策略消费顺序与来源**：唯一消费位置为共享 Policy Engine，在收集并变换全部命中规则后裁决；gate 不自行放行。先执行 deny、逐次真人确认和用户显式覆盖；再按现有引擎顺序检查旧用户 deny 记忆及出站特殊规则。旧 deny 一旦按现有规则生效，优先于新 allow；未满足旧记忆查询前置条件时保持现有判断，不扩大旧记忆作用域。然后逐一检查全部有效 ask / auto-evaluator：每条均须显式声明允许该来源复用；任何一条不允许即不能消费新缓存，按原策略继续。新旧 allow 同时可用时先按原逻辑处理旧用户记忆，新缓存仅在原逻辑仍需审核且全部约束通过时消费；任一拒绝或未完成的强制检查不可被 allow 覆盖。所有命中规则、来源及拒绝消费原因写 decision trace。

| 场景 | Agent 来源会话缓存 | user 来源会话缓存 |
| --- | --- | --- |
| 桌面普通工作区文件编辑，默认 `default-write-execute-ask` 经标准档转换为 Agent 审核 | 对该规则新增显式例外；仅 `edit_file` / `write_file` 普通目标且满足对象、任务和写入回执条件 | 对该规则登记 user 来源例外；仅用户明确批准会话范围时消费，单次确认不可 |
| 飞书 / 微信普通文件 `im-low-risk-edit`、`im-low-risk-create` 经标准档转换为 Agent 审核 | 对这两条新增显式例外，同样受当前渠道和主体约束 | 对这两条登记 user 来源例外；仅用户明确批准会话范围时消费 |
| 用户显式 ask / override、locked 人工要求、未声明来源例外的 ask 或显式审核 | 不可 | 不可；维持原确认和旧记忆规则 |
| MCP、出站、Shell、其他工具规则 | 当前无新缓存例外，走原策略；已有用户记忆按原规则 | 当前无新缓存例外，已有用户记忆按原规则 |
| 自动任务 `automation-default-confirm` 及其授权、deny 规则 | 不增加例外；保留原规则，已授权直接 allow 的路径无需缓存 | 不增加例外；保留原规则 |

例外以规则 ID、有效动作和来源登记，用户覆盖、其他同时命中的未许可规则以及策略版本变化都使其失效。允许 user 来源仅表示消费资格，不创建新的确认交互或隐含用户选择。该表是初始登记全集；扩充其他能力必须同时提供对象契约、明确策略例外和测试，不能因通用机制接入自动获得例外。

### 脚本、可执行程序和固定配置清单【人机共读】

**确定的边界**：同一工具、操作和对象的会话级缓存，对普通文件的后续写入可按现有策略复用；如果本次修改的目标是脚本、可执行程序或下列固定 CI 配置，不消费写入缓存，重新走现有安全审核或真人确认。这里的“拦截”指拦截缓存复用并进入相应审核，**不是自动禁止修改**。这是本方案的规则，当前代码尚未实现。

可执行判定是对写入目标逐项检查，任一条件命中即重新审核：

1. **脚本后缀**：路径扩展名匹配预先登记的脚本类型，固定集合为 `.sh`、`.bash`、`.zsh`、`.py`、`.js`、`.mjs`、`.cjs`、`.ts`、`.ps1`、`.bat`、`.cmd`、`.rb`、`.pl`、`.php`；统一以 ASCII 小写比较。此集合是 v1 完整清单，编码为版本化策略数据并由测试固定。该口径会把普通源码文件中的同类后缀也交回审核，这是这一取舍的直接影响。
2. **执行权限或格式**：已有目标在 POSIX 平台的 `mode & 0o111 != 0`，或已有目标及拟写入结果以 `#!`、ELF `7f 45 4c 46`、Mach-O/fat 标准魔数或 `MZ` 加合法 PE 签名开头；PE 偏移上限为 1 MiB。Windows 不检查 POSIX 执行位。文件信息/材料无法检查时不使用缓存，走原策略；不能声称文件头识别能覆盖所有脚本。
3. **固定 CI 配置路径**：仅匹配以下三项清单，不读取或解析配置内容，也不推断实际执行效果。命中后不消费缓存，进入现有审核。

   | 仓库根目录相对路径 | 匹配范围 |
   | --- | --- |
   | `.github/workflows/*.yml`、`.github/workflows/*.yaml` | `*` 只匹配该目录下单层文件名，不匹配子目录 |
   | `.gitlab-ci.yml` | 仓库根目录下该文件 |
   | `.circleci/config.yml` | 仓库根目录下该文件 |

   根目录以宿主已解析的 Git 工作树根为准；非 Git 工作目录以当前工作目录为根。先按现有路径防护解析实际目标和链接，再将规范化后的目标转换为根目录相对路径，按路径段比较（不按子串）；路径字母统一按不区分大小写匹配，以免大小写变体绕过。根目录或目标无法可靠解析时缓存 miss 并走原策略。此清单是明确边界：不包含 CI 的其他配置文件、引用文件或子目录，也不按内容、用途、外部注册或猜测执行效果扩展。
4. **其他文件**：未命中上述条件，且目标身份和现有路径/策略事实完整时，不因写入内容发生变化重新审核。文件 A 的编辑缓存不授权编辑 B，也不授权通过 Shell 删除或执行 A；每次仍核对当前策略和单次执行许可。

**已有安全规则始终优先**：敏感/系统路径、用户禁止、locked 规则及要求真人逐次确认的规则不因缓存放宽。项目现有 `pathClassifier.ts` 和 `shellSensitivePaths.ts` 已提供部分路径分类；脚本/可执行目标及固定 CI 清单的上述分类与缓存联动尚未实现。

**明确的覆盖限制**：该规则不试图识别所有可能自动执行的入口。因此清单之外的 CI 文件、计划任务配置、服务配置或其他由第三方程序消费的数据文件，可能间接触发执行，但不会仅因这一规则被重新审核；若它们命中现有敏感路径或其他现有策略，则仍按现有规则处理。不能把此方案描述为能识别全部持久化或自动执行风险。这是本方案明确的覆盖边界；实现不得宣称覆盖清单之外的间接执行。

**验收**：① 已有 A 文档的范围缓存，继续通过相同工具编辑 A 的文字 → 不因文字变化调用审核 Agent；② `A.py`、`A.sh` 或有执行位的无后缀文件继续修改 → 不消费缓存，走现有审核；③ 新目标材料以 shebang/受支持的可执行文件头开始 → 不消费缓存；④ 修改清单中的 `.github/workflows/build.yml`、`.gitlab-ci.yml`、`.circleci/config.yml` → 不消费缓存，走现有审核；⑤ 修改清单之外的 `.github/workflows/nested/build.yml` 或 `docs/build.yml` → 不因 CI 清单额外送审；⑥ 根目录或目标类型无法解析 → 缓存 miss，原策略继续；⑦ 同名不同路径、不同工具或不同命令 → 缓存不命中。各项检查决策 trace、审核和 executor 调用次数。

### 会话级生命周期【人机共读】

缓存只保存在主进程内存，以 `lane + sessionId` 分区，归会话运行时所有；同一会话内可跨工具调用和对话回合复用，但每次仍须满足当前任务约束，不跨会话、不跨应用进程重启。回合结束、短暂暂停或单次工具失败不清空会话缓存；会话删除、会话运行时销毁、应用退出或进程崩溃时清空。会话运行时已销毁后重新打开历史会话，或重启应用后，需要重新审核并建立内存记录；仅切换界面不会销毁仍存活的运行时。缓存没有固定时间 TTL、数据库表、持久化迁移或重启恢复；已有的 SQLite 用户确认记忆保持自身原有生命周期，不与新缓存合并。

容量上限：每会话最多 512 条、整个进程最多 4096 条；单条对象与元数据序列化后最多 16 KiB，超限不缓存。只存摘要和必要元数据，不保存正文；容量不足时淘汰最近最少使用的 active 条目，先撤销并推进代次，不能淘汰在途条目来让在途许可继续生效；没有可淘汰条目则放弃新记录。淘汰仅导致 miss、回退原策略。会话清理时销毁该会话 HMAC 密钥，进程退出时销毁所有密钥。

用户撤销、权限/策略版本变化、对象身份发生不受信替换或会话主体变化时，立即撤销相关条目；新调用重新走当前策略。缓存命中也要重新采集必要事实、核对当前用户任务和授权代次，并签发本次专属 permit。会话取消仅撤销该回合未完成的许可，不自动删除会话缓存；删除会话或明确撤销范围时清除。终止或变化与缓存读取并发时，先标记撤销、推进代次，再通知未消费许可和活动 lease；订阅后及 claim 前再次比对代次。失败、取消、迟到或不确定的审核结果不能写入缓存。

### 文件身份与故障恢复【机｜人工可跳过】

现有 `safeAtomicWrite` 返回的 `FileIdentity` 来自提交后的路径回读，不能证明它属于刚提交的临时对象，**禁止用现有返回值激活或推进缓存**。主进程对同一 canonical target 使用跨会话、跨链路的目标锁，覆盖待写标记、单次许可校验、受控原子写和身份推进；该锁不约束外部进程。

**受控提交证据**：增强目录 writer，在临时文件完整写入并同步后、提交前，从仍打开的可读文件句柄采集设备号、文件号及内容摘要；提交后保持句柄打开，以句柄再取身份和内容摘要，同时对目标路径执行不跟随链接的身份检查，确认二者设备号、文件号相同，单链接、文件类型、大小及摘要与拟写材料一致，并核对父目录和授权代次。回执携带的是句柄所证明的身份及摘要，不能用路径回读替代预期身份。任一检查不可用、身份或内容不符，不产生可信回执；平台不支持保留句柄完成提交时，该平台文件写入缓存保持关闭。仅比较 inode 不能发现原位改写，必须检查内容；摘要与身份再次用于下次命中前的检查。检查不提供防止外部进程在检查后再次修改的锁定保证，仍须沿用现有执行前校验；本方案不声称消除操作系统层面的外部并发竞争。

**首次批准与缓存命中均遵循同一协议**：首次范围批准时记录处于 `pending_first_write`，不得被其他调用命中；该次写入提交且取得上述可信回执、父目录及授权版本未变化后才转为 `active`，绑定回执身份和摘要。后续命中写先将条目标为 `write_pending`，取得同等回执后更新并转回 `active`。若任何其他工具或会话写入同一对象，既有条目先撤销；不能因为路径相同而自动推进身份。当前回执增强实现并通过故障注入前，文件写入缓存不得启用。

写入失败、取消、提交结果不确定、身份或代次不匹配均撤销相关条目；提交已经发生或不能确定是否发生时，报告已提交或提交结果不确定，不能误报未执行。外部替换或修改在检查中被发现时 miss；进程崩溃丢失所有内存条目，重启后不恢复。无需数据库事务或 `write_pending` 持久化；文件身份推进不延长会话或扩大范围。

### 验收【机｜人工可跳过】

- 同会话、同工具/操作/文件 A 获得会话范围批准后，修改 A 的不同普通文字不重复调用审核 Agent；文件 B、其他工具或当前任务明确只读不命中。单次批准不产生缓存。
- 多对象调用必须覆盖全部源与目标；遗漏一个或与范围不一致即进入原策略。Shell 当前无对象契约和消费例外，均 miss；未来登记能力后还须验证完整命令、工作目录及对象，复杂表达式仅精确匹配材料仍不足以命中。
- 同参数但服务端隐含选择 A 变为 B、参数完整但实际对象未知均 miss；只有登记契约可验证全部对象和环境且参数匹配才可命中。动态展开不可验证时 Shell 精确命令也 miss。
- 对首次写入和命中后写入分别注入 rename / link 后外部替换、原位改写、父目录不变、取消及回执检查失败；不得激活或推进缓存，已提交或不确定的结果不得报未执行。测试外部变化在回执后、下次检查前发生时导致 miss。
- 验证策略矩阵：多个命中规则中任一未许可时不消费；用户 override、真人确认、适用的旧 deny、出站规则优先；默认普通编辑 Agent 例外可命中，IM、MCP、出站、自动任务和 user 来源按各自行处理。验证缓存容量和淘汰仅造成 miss。
- 不同会话、不同链路、不同主体、会话删除、进程重启均不可命中旧记录；同会话跨回合仅在当前任务约束可核验时命中；新消息与冻结证据不同且无结构化授权时 miss。策略/权限变化、撤销、首次批准后原子写入、缓存命中后原子写入、其他会话/工具写入同一目标、外部替换、取消和迟到结果均验证身份推进或撤销正确，executor 不越权调用。
- 脚本、可执行文件与 CI 清单不消费写入缓存；`.cpp` 普通文件不因后缀被排除。测试覆盖权限位、文件头、Git 工作树根、CI 路径及解析失败。
- 与真实审计日志对照，统计首次及后续调用的 Agent 审核次数、每次等待、缓存命中和回退原因；分别覆盖桌面、飞书、微信和自动任务的可达链路。执行安全边界定向测试和 `npm run check:system-invariant-registry`。

本方案为文档规格，当前代码尚未实现会话级 Agent 审核记忆；缓存关闭时全部回到现有策略与审核流程，不改变既有用户确认记忆。
