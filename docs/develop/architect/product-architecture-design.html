01产品目标与架构不变量

要落地的三类能力 —— 自动审批、SubAgent、后台（管家）Agent —— 都需要可独立发起、可无窗口、可嵌套的 Agent 调用；而今天的 Core 把「跑一次 Agent」等同于「跑一轮会话回合」。所以这一轮不是加功能，而是把 Core 的调用方式打开。

六条架构不变量（全文的「宪法」）

后面每一节都是它的展开。展开条目看职责与边界。

一次调用可独立发起不变量 1

不要求窗口、不要求用户在场、不要求它是某个用户回合的一部分。但会话仍然要有，它是归属与落盘的载体；且「会话」不等于「用户会话」—— 归属与可见性是两个维度，内部调用有自己的会话，只是归属 internal、可见性 hidden。真正禁止的只有两件事：会话与窗口 / 回合的存活绑死；「会话只能由用户消息催生」。

已解决 20260917（偏差 1）：sender 已从调用契约移除，改为事件出口 emitFactEvent / emitSessionEvent；窗口存活判定已删除

Core 不认识业务身份不变量 2

审批 Agent、SubAgent、管家 Agent 都是调用方，不是 Core 的变体。

安全门控不可绕过，标准只有一套不变量 3

判定顺序、fail-closed 兜底、底线规则不接受配置替换；「谁回答确认」可插拔，且与「从哪个入口进来」正交。父级的审批不向子调用泄漏：子调用的放行集合是替换而非继承，父批过的那一次不构成子那一次的授权。

可见性不由 Agent 自己声明不变量 4

Agent 只声明归属意图；能不能进用户会话列表、能不能被跨会话搜索到，由宿主与存储决定。

内部调用是证据与输入，不是授权不变量 5

审批 / SubAgent 的记录必须落盘（安全审计加 Agent 自我优化），但「上次批过」不构成「这次批准」。

先持久化，再投递（只约束终态与结果）不变量 6

需要送达、可重试、可补投的东西 —— 消息终态、调用结果、汇报通知 —— 必须先落盘再投递。投递不可达不等于失败：投递是驱动源路由，Agent 只声明意图。过程性事实流（工具活动、文本与思考增量、进度心跳）不受此约束：直接投递，不以落盘为前提，投递侧允许丢失。判据是「丢了会不会损害真相」。

并且：「不丢」不等于「一定被看到」。落盘保证结果永远可查，投递只是尽力而为，所以补投必须有界（带 TTL、被更新结果取代、送达后不重复），否则「不丢失」会变成「无限打扰」。

四条判据（决定一块东西该放哪层）

  1. 换了它，执行语义或安全语义会变吗？会 → Core 或 Safety，不可被配置替换。
  2. 它被调用方伪造，会越权吗？会 → 必须在 Core / Safety 侧有不可覆盖的校验。
  3. 它只是「把宿主的东西装配成一次调用」吗？是 → Runtime；它决定「何时发起、结果给谁」吗？是 → Driver。
  4. 删掉它，系统还正确吗（只损失质量或便利）？是 → Utils。

依赖方向：五条纪律

  • Core 不 import 任何宿主模块，只使用注入的端口。
  • Runtime 是唯一的装配点：Profile、Tools、Skill、模型解析、事件出口实现都在这里装成一次 Invocation；运行期才发起的嵌套调用也不例外。Driver 不直接调 Core。
  • Safety 在 Core 的判定路径上，不可绕；它读的「生效规则」随 Invocation 传入，自己不去读库，也不依赖 Runtime（只依赖端口）。
  • 准入在 Runtime、配额状态在 Storage：跨调用的全局约束不属于任何一次调用，因此不进 Core 的 limits；嵌套调用同样过准入、不豁免。
  • Storage 被 Core（经两个端口）、Safety、Runtime、Driver 共同使用，不反向依赖任何人；Utils 可被任何一层使用，但不得持有语义。

三处最容易放错

Safety 不能放进 Runtime

Runtime 是「改配置就改行为」的地方，而安全底线恰恰不能随配置改变 —— 放进去等于「配置可以关掉安全」。

Storage 不能算 Utils

会话归属、可见性、审计只追加、保留期都是语义，不是便利设施；把它当 Utils，结果就是「顺手把审计也删了」。

桌面界面不能从 Driver 摘出去

窗口 / 托盘 / IPC 面是同一个驱动源的三个实现部分。

04一次回合：六块依次上场

以「用户点发送」为例，六块依次上场 —— 括号里是同一位置的其它驱动源。这条链路就是全部：界面在第 2 步之后不再参与。

三条推论

界面只是观察者

第 2 步之后就没有界面参与。无窗口、纯后台、远端触发走的是同一条链路 —— 这也是「窗口关闭不等于回合失败」的由来。

审批与 SubAgent 不新增链路

它们分别落在第 4 步的「回答者」与「嵌套调用」位置，复用同一条链路、同一套策略与审计。审批 Agent 两者兼具：在回答者位置上发起一次嵌套调用。

业务模块不在链路上

文件浏览、搜索、设置等由界面直接调用主进程的业务模块。只有当 Agent 把它们当工具使用时才进入链路 —— 这也是「用户直接操作界面不经过工具门控、Agent 调用必须经过」的由来。

05进程边界：主进程与渲染进程

先把三件被混在一起的事分开：特权、职责、承载。特权决定「必须在哪里」，职责决定「属于谁」。

维度回答的问题决定什么
特权谁需要 OS 权限、密钥、文件系统访问必须在主进程（Electron 安全边界），这不是架构选择
职责它属于六块中的哪一块它受哪些规则约束
承载它实际跑在主进程还是渲染进程实现位置，可迁移

四条边界原则

  1. 特权决定「必须在哪里」，职责决定「属于谁」。文件读取既服务「文件树界面」，也是 Core 的工具 —— 同一份底层能力，两个消费者。
  2. 业务功能不属于六块中的任何一块 —— 它是与 Agent 正交的「应用域」，与 Agent 只有两种关系：共享底层能力，或被 Agent 当工具使用。
  3. 渲染进程只有两类东西：驱动源的界面与业务界面。渲染进程不做决定 —— 不发起 / 排队 / 重试 / 取消，不拼系统提示，不自己跑技能路由。
  4. IPC 面按领域切，不按实现方便堆在一起。今天 appIpc.ts 把 Agent 驱动协议与桌面功能堆在同一个文件里 偏差 10。

一条容易被争论的规则

同一个能力被两个入口使用时，用户直接操作界面不经过工具门控，Agent 调用必须经过。理由不是「界面更可信」，而是安全模型的标的是 Agent 的自主操作：用户自己动手不等于 Agent 替他动手。

渲染进程的信任级别：它处在不可信边界（contextIsolation，只暴露 window.api），任何「渲染进程说了算」的地方都是安全缺口。今天只剩驱动权（偏差 9）：回合发起与出站消息分类仍在渲染端；技能路由与系统提示拼装已于 2026-09-16 收回主进程（偏差 12 已解决）；后台 / 定时调用已由事件出口与显式 lane 从窗口解绑（偏差 1、21 已解决）

交互只有两个方向

  • 主进程 → 渲染：事实流、失效通知、确认请求、投递结果。
  • 渲染 → 主进程：用户意图（发消息、取消、批准或拒绝、切换会话、改设置）。
  • 没有第三条：渲染进程不得「查询之后自己累积成真相」。

06驱动源与结果投递

「窗口 / 托盘 / 菜单被塞进主进程」是 Electron 的约束，不是架构意愿。真正的同级切法是驱动源：回答「谁发起、何时发起、结果返回给谁」—— 一共四类，桌面只是其中之一。

与归属联动：投递到桌面，结果要在一个可见的地方出现（管家会话分区可见）；投递到 IM，走回复通道。投递目标决定结果落在哪，也就决定了会话归属与可见性的选择，两者要一起定。

07Runtime：准入、装配与定制入口

Runtime 回答三个问题，顺序也是它们发生的顺序：这次调用能不能跑（准入：并发、速率、配额）→ 这次调用带什么（装配：Profile / Tools / Skill / 模型解析）→ 过程往哪里说（事件出口实现）。

准入：这一轮新增的一层，也是最容易漏掉的一层

层管什么谁施加状态
单次调用内轮数、时长、单次 token 上界、调用内并发（工具并发与子调用 fan-out）Invocation.limits，Core 施加随调用，不持久
跨调用全局并发数、速率、lane 配额Runtime 的准入（新增）Storage：跨重启不丢
触发时刻编排定时、事件、重试节奏Driver（触发源）配置数据

没有它，管家 Agent 加定时与事件源一上线就会爆：多个定时任务同一分钟触发，单看都「合法」，合起来把配额和机器打满。为什么放在 Runtime：所有调用都经过它，它是唯一的公共前置；Driver 是多个并行驱动源、没有中心，全局判定放进去会变成「各驱动源各判一次」的竞态。

四条硬要求

  1. 准入不判定安全：只回答「现在能不能跑」，不回答「这次该不该放行」—— 后者永远是 Safety 的事。
  2. 交互式优先于后台：用户在前台点发送的调用，不该被后台 Agent 排队挡住（是优先级，不是先来先服务）。
  3. 不能静默丢弃：处置只有四种且必须由调用方声明 —— 排队、延后、降级、拒绝（落审计）。
  4. 可观测：排队与拒绝要落审计或事件出口，否则用户无法回答「我的定时任务为什么没跑」。

嵌套调用也要过准入，但优先级按「谁在等它」定

嵌套调用例子准入语义
关键路径上的同步依赖审批回答者（invokeApproval）优先级继承正在等待它的那条调用；有界等待：超出上界即视为「拿不到裁决」，不能让一条工具调用无限期挂在准入队列里
可放弃的派生SubAgent、工具内派生调用同权排队；被拒时把「资源不足」作为工具结果回灌父调用，让父自己换方案

准入拒绝永远不构成安全结论：审批调用拿不到配额时，Safety 得到的事实是「无法获得裁决」，不是「裁决为否」。审计上两者必须可区分（cause=unavailable 对 cause=agent-deny），否则「配额不足」会被统计成「审批判定危险」。处置仍是 fail-closed，但不接受静默 fail-closed。

自锁风险必须提前定：同步依赖是由一条正占着配额的调用派生的。若全局并发上界是 N，而 N 条调用同时等各自的裁决，谁都拿不到位，全体互锁。准入必须自带回旋机制：给同步依赖留保留位，或让调用在等待裁决期间让出已占的位。

定制入口：能用数据定制的，不开放成 Hook

层级形态判据
声明式数据（首选）Profile / PolicyRule / Skill / 工具声明加数据不加代码；改完可枚举、可审计
注入式端口（受控开放）events.*、factsProvider、answerer、ToolExecutor、getApiKey / 模型解析、loadContext、persist、translate、limits / signal必须由外部给实现，且实现只做三类动作：补事实、给实现、报事实

写死（不开放）安全门控本体、上下文装配顺序、可改写的生命周期 Hook一动就等于安全语义或执行语义变了

永不开放改写的理由：参数一旦被改写，「历史记录 / 审计 / 界面 / 实际执行」四者就不再一致，「这次执行是谁改的」无法回答。要改工具行为就换或包一个 ToolExecutor；要改「怎么想」就改 Skill。

「给审批看什么」要拆成两半

一半谁提供时机内容

宿主补充的事实factsProvider 端口运行期注入宿主才知道的上下文：页面状态、会话位置、最近的相关操作

为什么不合并：前者属于工具契约（换工具就换），后者属于宿主环境（换宿主就换）。审批看到的必须是两半的并集，且标注每一项来自哪一半 —— 审计要能回答「这个结论是基于谁提供的事实」。

模型与思维强度：档位是数据，服务与凭据是端口

内容层形态

用哪个服务、端点、凭据B. 端口（宿主解析）resolveModel(profile.model) → { serviceId, baseUrl, getApiKey }

为什么服务和凭据不能在 A：API Key 是不能落盘的秘密，服务是用户机器上的运行时状态；写进 Profile 就等于把秘密写进一份可复制、可同步的配置。为什么模型和强度必须在 A：「谁付账、谁定档」—— 让被调用的模型自选，它就会自我升级成本。

五条硬规则

  1. 发起时解析、调用内冻结：调用中途换模型会破坏上下文一致性与审计口径。
  2. Profile 只声明意图，宿主负责可行性：不满足时按安全与成本侧定死的规则降级或失败。
  3. 默认必须是「继承」：子调用不声明模型时，继承父调用解析后的那个模型，不得静默解析成另一个具体模型。
  4. 解析失败必须 fail loud：静默换一个能用的模型是最坏选项 —— 审计里记的模型与实际执行的不是同一个。
  5. 子调用的思维强度默认关闭：思维强度是成本项，不是能力项；父调用的档位不自动下传。

SubAgent 要覆盖模型怎么办：Profile 声明可选档位集合（白名单加成本上界），父 Agent 只能在集合内选 —— 可以降档省钱，不能提档。审批 Agent 是特例：它的模型能力下限由安全侧强制，因为判断质量本身就是安全属性。

08Core：内核边界与调用契约

Core 的边界由一个问题定义：这一次调用要什么、结果往哪里说；除此之外的一切（谁发起、记在哪、给谁看）都在外面。

负责什么，不负责什么

属于 Core不属于 Core

上下文装配（裁剪 / 注入，与 context-injection-refactor-plan 同源）行为逻辑（意图识别 → 方案 → 请求确认 → 执行 → 回复，属 Skill）
工具执行（direct / planned、plan / execute 分离、结果形态）投递与通知（回复飞书 / 微信、发桌面通知，属调用方的工具）
安全门控（策略判定 → 确认 → 授权 → 审计）审批标准本身（属安全策略模块）
事实与事件产出（UI 事实 / 台账 / 审计，出口可插拔）会话列表语义与归属展示（属宿主与存储）
预算与取消的执行记忆与自我优化的策略（属存储与 Profile 输入）

一条硬规则：Core 不认识业务身份。它只认识 lane、Profile 提供的配置、事件出口。审批 Agent、SubAgent、管家 Agent 都不该让 Core 里多出一个 if。

「上下文从哪来」要说死：messages 只是本次调用的新增输入，历史不经它传入。完整上下文由 Core 在循环内装配：① 经 loadContext 按会话锚点装载已有历史与可寻址材料；② 与本次 messages 增量及 additionalContext 合并；③ 应用裁剪与注入规则。历史不能改由调用方装载，否则装配规则随调用方分叉，「同样的历史必须产生同样的上下文」立刻失效。

  • 不出现 sender：出网点是接口，无 UI 时是 no-op 或转投别的通道。已解决 20260917（偏差 1）：sender 已删除，出口允许全 no-op
  • 不出现「必须先有一个活跃的用户回合」：会话可以随手创建、可以短命、归属由调用方声明。这里禁的是「回合」，不是「会话」。

  • 不出现 isWebContentsAlive 这类存活判断：调用存亡只由取消、超时、错误决定。已解决 20260917（偏差 1）：存活判定已删除，调用存亡只由取消 / 超时 / 错误决定

会话锚点与认领

  1. 会话必须有，session 是必填入参。没有会话锚点，五件事同时失去着落：审计归属、预算归属、恢复锚点、并发隔离、幂等落点。要拆的是「会话与用户回合的绑定」，不是会话本身。审批与 SubAgent 各有一条独立会话，归属 internal、可见性 hidden。唯一不需要会话的是单次模型调用（分类器式）。

  3. 认领语义：多个输入同时到达时，「谁先被处理」必须确定且可审计（先到先服务，或按显式优先级）。

维度例子嵌套调用语义错一分的后果

  2. 提供事件出口（允许全部 no-op）。
  3. 提供预算与取消信号。
  4. 不绕过 Core 直接执行工具，否则等于绕过策略与审计。

09Safety：策略引擎与确认通道

Safety 管两件事：该不该放行（策略引擎）与由谁来定夺（确认通道）。引擎在内、内容在外，底线不可放宽；回答者可插拔，语义不可外置。

策略规则：四问与三条判据

问题答案理由
判定时机（工具执行前必经）Core 内，不可绕它是安全不变量；外置就等于「一个可以跳过的步骤」
判定引擎（decide() 纯函数）Core 内，作为内部机制而不是 Hook无宿主依赖、可单测；结论必须由 Core 自己算出
规则内容（默认规则、套餐、用户覆盖、locked 底线）Core 外（安全策略模块 / 配置数据）随产品与用户变化，属策略数据，不属于执行框架
某次调用用哪套规则调用方解析后随 Invocation 传入与 tools / model 一样，是输入的一部分

但有一半不能外置：底线。「内容在外」的前提是放宽方向必须受阻。locked: true 的规则不能被下调为 allow，也不能被覆盖。目标形态是把这条不变量提到接口上：Core 只接受「可收紧、不可放宽」的规则集；相对底线放宽任何一条，Core 拒绝这次调用并落审计。「不可放宽」在子调用上的具体形状是「不继承」：子调用的放行集合是替换而非继承，父批过的那一次不构成子那一次的授权。

规则要有「来源」维度。已解决 20260919（偏差 3）：生效规则带来源标注（内置默认 / 套餐 / 用户覆盖 / 迁移），审计落 ruleOrigin，被遮蔽规则的痕迹保留目标形态下每条生效规则都能回答来源（内置默认 / 套餐 / 用户覆盖 / 迁移），并保留被遮蔽规则的痕迹。

不得为缺失的托管值静默提供默认值。托管值缺失时只有两种合法行为：按显式声明的默认兜底，或失败并落审计。最坏的做法是「取不到就回退到内置常量」，它把配置错误变成静默的行为差异。

连续拒绝要有回退阈值。同一调用内连续 3 次被拒时，从「继续尝试」退到更保守的行为。今天这个计数器与「工具执行失败」共用，安全拒绝会被执行失败带着触发中止两者必须分开计数，且安全拒绝的阈值应更高。

三条判据（决定任何东西该在里还是在外）

  1. 「它变了，产品的安全语义变了吗？」变了 → 在外（策略模块），且变更要走 settings.policy-change 审计。
  2. 「它被调用方伪造，会不会造成越权？」会 → Core 侧必须有不可覆盖的校验（底线、fail-closed）。
  3. 「把它改坏（放宽或收紧）之后，安全路径本身是否失效？」会 → 进不可变集。

确认通道：五条规则

  1. Driver 不做安全判定：它能把 'y' 这个字符串带回来，但无权判定「这次批准有效」。今天 PendingDecision = 'y' | 'n' | 'timeout' 把管道事实与语义结论混在一个枚举里
  2. Safety 不自己发消息：只产出「决策请求」，由 Driver 投递。这是「确认通道可插拔」的前提。
  3. 审计必须区分「没送到」与「送到了没人回」：它们是不同的安全事实。今天 mapToolOutcome 把两者统一压成 timeout
  4. lane 不是回答者：回答者由 Profile 解析、与 lane 正交。已解决 20260919（偏差 4）：通道改为二维解析 —— 回答者种类（user / agent / deny）与 lane 正交，传输通道由 lane 派生
  5. 端口形状不预设「单次同步问答」：回答者可以本身是一次 Core 调用，端口必须容纳「多轮 + 有界预算 + 有界输出」。

多轮回答者的装配与发起

环节谁负责说明
装配Runtime（装配期）构造回答者实现，注入审批 Profile（模型档 / 封闭只读工具集 / 轮数与预算上界 / 有界输出契约）与一个 invokeApproval 调用器
解析Safety（运行期）按 Profile 与 lane 解析出用哪个回答者；只在规则与缓存都未命中时咨询它
发起回答者实现（运行期）经 invokeApproval 发起一次嵌套 Core 调用；同样过策略门控、过准入、落审计
归还Safety端口只回 ConfirmOutcome —— 装配细节对 Safety 不可见

递归边界与两个集合

硬约束：审批调用自身的工具调用不再进入确认流程。不能依赖「它不会调危险工具」的约定，否则就是「审批套审批」的无限递归。

  1. 兜底语义是 fail-closed，且不可静默。若豁免被配置破坏、或递归深度上界被触发，结论是拒绝；必须落审计且能与正常拒绝区分（cause=recursion-blocked 对 cause=agent-deny）。
  2. 这条豁免不该是可配置规则，因为它不是授权，是递归终止条件。用户可调的是审批 Profile 的能力集合，但「不再对这批工具做确认」不允许被覆盖。
  3. 因此它不属于 locked 底线集，属于「不可变集」 —— 破坏这条路径的恰恰是收紧。
集合约束目的判据
底线集（locked）不可放宽（可收紧）防越权：安全标准只有一套「用户把它改宽，会不会越权？」
不可变集放宽与收紧都不允许保安全路径可运行：递归终止条件、fail-closed 兜底、审计成对「它被改坏，安全路径本身是否失效？」

回执校验：两条通道，形状不同、目标相同

通道合法授权来源校验靠什么明确不做的
远端（飞书 / 微信）远端用户身份：发送者与授权对象匹配、回执 id 配对、时效不把「管道事实」（收到 'y'）当成「语义结论」（批准有效）
桌面本机用户结构：requestId 配对、一次性消费、来源绑定不做用户身份认证

桌面通道的信任假设要显式写出：它把「本机用户」当作合法授权来源，但不把渲染进程当作诚实的执行者。两句不矛盾：「渲染进程不可信」防的是它伪造来源，不是「用户点的那一下不可信」。

为什么渲染端发来的「批准」仍能构成放行：它不是作为「渲染进程的声明」被接受，而是作为主进程自己提出的待决请求的回答被接受。于是回执校验只需三件事，且都在主进程：配对（回执必须对应真实存在、未过期、未被消费的待决请求）、来源绑定（回执必须从该请求被投递到的那个驱动源回来，不跨通道）、不可自授权（没有对应待决请求的「批准」一律拒绝并落审计）。

边界要写出来：桌面回执能证明的是「有人在这台机器上回答了这个请求」，不能作为「用户本人确认」的身份凭据 —— 审计口径按前者写。

两个特例

  • 自动审批：审批 Agent 是回答者的一种实现，且永远一事一议 —— 裁决不写缓存。管家 Agent 不感知审批 Agent 存在，它看到的仍然是「一次工具调用 + 一次安全流程」。
  • 无回答者：fail-closed 是兜底，不是降级目标。

10Storage：协议在内，实现在外

耦合确实重 —— Core 的入口直接持有数据库句柄、循环里直接查询 10 处以上。但根因不是「该不该合并」，而是 Core 的执行单元被定义成了存储里的三行数据；耦合的根在执行模型，不在存储。

结论：Storage 不并入 Core，但要切成三份

谁持有内容
Core记录的形状与不变量：调用记录与事件的字段、只追加、序号单调、终态收敛、归属维度；以及两个端口 loadContext() / persist()
Storage实现：SQLite 还是 JSONL、迁移、索引、清理、保留期、加密
Safety审计与决策缓存的语义：不可改写、独立物理隔离、准入门槛

和 第 9 节「策略规则」 是同一个道理：协议的形状在内，存储的实现在外。为什么不能把 Storage 并进 Core：① 今天有四类使用者要访问存储（Core、Safety、Runtime、Driver），合并后要么都进 Core（Core 变成上帝对象），要么它们绕过 Core 直接访问 —— 那就是今天的状态，只是多了一层假封装；② 审计会失去独立性，用户删会话顺手把审计删了。

真正的解法是反向的：把 Core 对存储的依赖压到两个端口 —— loadContext(invocation) 与 persist(InvocationResult)，Core 不认识表、事务与 SQLite。loadContext 只按会话锚点取回原始材料，装配（裁剪与注入）留在 Core 不下沉。这既保证装配规则唯一，也让 Core 能脱 SQLite 单测。

三条验收标准

  1. Core 能脱离 SQLite 跑单测。已解决 20260919（偏差 2）：Core 已脱库，appDb 不再是入参；用内存端口实现即可跑完一个完整回合
  2. 换一种存储实现（例如把某个 Agent 的记录落成 JSONL）不需要改 Core。
  3. 存储不可用时 Core 的行为有明确约定（fail-closed 还是降级），而不是未定义。

归属与读取

先把两个词对齐：「内部会话」与「内部调用记录」是同一实体的两个视角 —— 会话是执行期视角（上下文载体、执行独占、预算归属），内部调用记录是存储期视角（落盘形态、可检索、可锚定血缘）。

  1. 先有归属谓词，再谈列表过滤：归属做成闭合的联合类型（用户 / 远端 / 自动化 / 内部）加一条纯谓词「这条记录该不该进用户列表」；列表只看这个谓词，不散写条件。
  2. 物理分层优先于逻辑过滤：内部调用落到子目录或独立表空间，与用户会话天然分家。过滤靠「记得写对」，分层是「不写也进不去」。
  3. 血缘锚定，不是复制，也不是共用会话：SubAgent 的会话锚在父 turn、审批的会话锚在确认请求。
  • 两级读取：列表只读轻量元数据（id / 标题 / 时间 / 归属 / 可见性），进入会话才读全量消息。今天列表是拉全表，量一上来就是瓶颈
  • 读上限：全量读取要有硬上限，超过就分片或拒绝。

一条容易被忽略的硬要求：同样的历史必须产生同样的上下文。一旦引入「某些工具结果被替换掉」这类压缩决策，就必须可重放（记下哪些被替换过），而不是每次装配时重新判断。否则同一份历史能装出两份不同的上下文，任何基于上下文一致性的能力都会变成概率事件。

这个问题必须先答 —— 它决定契约里能不能出现函数与句柄，越晚定越贵。三种形态的账：

形态追加开发代价持续成本本产品三条业务线建议
A · 同进程库≈ 0（P1 – P5 本来就在契约路径的预算里）无收益已满现在做

理由不是 A 便宜，而是 A 的收益今天就能全部兑现，B / C 的收益对本产品是 0：自动审批、SubAgent、后台管家三条业务线本来就跑在同一个进程里，B 买到的进程隔离与多语言宿主对它们没价值。改造面口径：从 electron/toolChatLoop.ts 按静态 import 展开得 368 个本地模块、2.0 MB / 5.35 万行；切开核心与外壳后，核心内真正耦合宿主的只剩 4 文件 / 3 个能力（app · safeStorage · shell）—— 所以 SDK 化是一次边界手术，不是重写。

拍板后立刻要落的三条硬约束

  • 契约里禁止函数与句柄：端口表达为「宿主实现的服务接口」，本地绑定时把对象直接塞进去；唯一例外是绑定层适配器，不进契约
