# 三个典型产品架构对照小结（以六块主干为基线）

> 定位：本文是三篇对照研究的**汇总读本**，不引入新的外部事实。行号级证据见三篇原文；本文只做两件事 —— 把三家横向拉平到**我们的模块框架**上，给出差异与优劣裁决。
> 姊妹篇（外部实现的对照研究，非基线）：`docs/develop/architect/codex-architecture-comparison-and-learnings.md`（Codex）、`docs/develop/architect/dsh-architecture-comparison-and-learnings.md`（DeepSeek Harness）、`docs/develop/architect/claude-code-architecture-comparison-and-learnings.md`（Claude Code）。
> 基线（我们的方案）：`docs/develop/architect/product-architecture-design.md`（六块主干与四条判据）、`docs/develop/architect/agent-core-roadmap.md`（业务预期与工作块）。
> 状态：待评审 ｜ 基线：工作区 HEAD ｜ 摸排日期：2026-09-12

**一句话**：三个产品都在回答同一个问题 —— 「一个 Agent 内核怎么被多种场景复用」。它们给出的答案分别是**协议化**（Codex）、**插件化**（DSH）、**单宿主化**（Claude Code）。我们的理想态与 Codex 的形状最接近，与 DSH 的机制最互补，而 Claude Code 是与我们最像、也最能照出痛处的一面镜子。

**怎么读**：§1 三家画像 → §2 六块基线总表 → §3 逐块差异与优劣 → §4 三家优劣总账 → §5 三家收敛处（印证我们）→ §6 三处分歧与我们的选择 → §7 借鉴清单（按我们的块归档）→ §8 修订建议覆盖核查 → §9 总结。

## 1. 三家画像

| 产品 | 形态 | 组织范式 | 一句话 |
| --- | --- | --- | --- |
| Codex | Rust 多 crate；长驻 app-server + 协议客户端 | **协议优先** | 把 Agent 做成可被任意客户端驱动的服务，一切（调用、事件、扩展）先变成协议 |
| DSH | TS 插件树（Cordis）；profile + patch 组装 | **组装优先** | 不存在特权内核，能力靠插件叠加；扩展点是 seam，安全靠单调守卫 |
| Claude Code | 单进程 TS CLI；一进程一套循环 | **入口优先** | 终端是唯一原生宿主，其余入口（SDK / IDE / 远程 / daemon）都是事后接上去的 |

**三家共同点**（也是我们已拍板的方向）：会话日志是真相、模型历史是派生物；工具调用过一层统一门控；上下文需要多档压缩；子 Agent 需要独立上下文与模型。

**三家共同缺口**：都没有「无人值守但仍在安全决策」的形态 —— 这正是我们的 C1 / C2 要补的那一格。

## 2. 六块基线总表

| 我们的块 | 我们（理想态） | Codex | DSH | Claude Code | 与我们的距离 |
| --- | --- | --- | --- | --- | --- |
| **Core** | 推理循环、上下文装配、工具执行、事实与事件产出；对外只暴露 Invocation（messages / profile / events / limits / signal），不认识业务身份、不读库、不认识窗口 | 同职责；对外是 `TurnInputRequest` + `Op`，契约里带幂等、附加上下文、追踪、干预与恢复 | 同职责；会话日志是唯一真源，模型历史是派生；resume 与 agentPreset 是一等公民 | 同职责；但装配结果（约 20 项）直接灌进循环参数，执行态是约 50 字段的可变上下文对象 | 形状最像 CC，完整度最像 Codex |
| **Safety** | 策略引擎 + 门控 + 确认通道 + 审计；引擎在内、内容在外、底线不可放宽；回答者可插拔且与入口正交 | 四层：平台沙箱 / 策略引擎 / 权限剖面交集 / Guardian 审批代理；档位含按类别给权的 `Granular` | 三个独立 seam（审批 / 沙箱 / 权限预设）；单调守卫把「只能收紧」做成类型事实 | 权限模式栈 + 8 种规则来源 + 三个回答者 handler + 自动分类器；但底线可被模式或远程开关放宽 | 三家都比我们细；机制上 DSH 最贴底线主张，清单上 CC 最全 |
| **Runtime** | 显式一层、唯一装配点；声明式数据优先，注入式端口次之，明确不开放兜底 | 装配在 Core 内部完成，输入来自配置层栈 | 装配 = 组装插件树（agent preset 按会话挂载）；能力描述符 + 启动前校验 | **没有这一层**；装配数据散在 settings / agents / skills / plugins 四处，在调用点被拼起来 | CC 是反证，Codex 与 DSH 是旁证 |
| **Driver** | 四类驱动源（桌面 / 远端 / 定时 / 事件）；都不直接调 Core；结果投递走一次路由 | 每个入口都是协议客户端；同一协议、传输可换（进程内 / UDS / stdio） | 驱动源是「宿主 × 载体」组合；job 有身份与生命周期 | 终端是唯一原生宿主；SDK / Bridge / Remote / daemon-worker 都是后加的 | 我们与 Codex 同构 |
| **Storage** | 协议在内、实现在外；归属、可见性、只追加、保留期是语义而非便利 | rollout 只追加 JSONL 是真相，thread-store 是可重建派生；血缘在存储层 | 日志持久化 / 派生投影 / 通用键值三层分开；格式有 generation 纪律 | 只追加事件日志（Entry 是 20 种变体的联合）；子 Agent 物理分文件、逻辑同链；列表只扫顶层 | 三家一致指向「真相与派生分离」 |
| **Utils** | 日志 / 脱敏 / 路径安全 / 加解密 / i18n / 纯逻辑；持机制、不持语义 | 另有可观测性独立成层（otel / analytics / diagnostics） | util 刻意不持有语义；另有生成式目录与新鲜度校验 | 一致，但体量远大于我们 | 我们边界更清晰，缺「可观测性单列」视角 |
| **业务模块**（应用域） | 与 Agent 正交，不属六块；共享底层能力不等于同一层 | **印证**：文件 / 搜索 / 配置 / MCP / 插件都是工具或客户端功能 | **不成立**：能力包默认同时服务工具与界面 | **不成立**：文件、搜索、LSP、终端都以工具形态存在 | 只有 Codex 正面印证我们的切法 |
| **横切：后台 / 定时 / SubAgent** | 后台是 C1 / C2 两条业务线；SubAgent 是块 3；会话有归属 × 可见性 | 有 daemon、后台终端、子 Agent，但没有「管家」形态；exec 有「最终结果 / 事件流」两种消费形态 | 有 jobs / schedule / webhook 管道与完整 subagent seam，但后台工作会话内、无投递保证 | 有 durable cron（含 catch-up）、任务类型联合、完整子 Agent 设计；但无界面时确认一律自动拒绝 | SubAgent 三家都能给现成答案；后台管家只有我们要做 |

## 3. 逐块差异与优劣

### 3.1 Core：调用契约

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 调用入参 | session / messages / profile / events / limits / signal 六项 | `TurnInputRequest`（含 thread_settings、additional_context、trace） | Agent / Session / Turn，agentPreset 随 header 持久化 | `QueryEngineConfig` 约 20 项 + 可变 `ToolUseContext` |
| 会话在前还是在后 | 必须有（归属与落盘的载体），但不等于用户回合 | thread 是前提，但支持 idle-start | 会话可寻址，resume 是一等公民 | 一实例一会话，`submitMessage` 一回合 |
| 中途干预 | 无 | `Op::Interrupt` + steering | inbox 认领 + 定时不插队 | 命令队列 + 逐 Agent 寻址 drain |
| 崩溃恢复 | 无 | `Op::RecoverTurn` + `SuspendTurnOutcome` | resume + preset 持久化 | 无 |
| 幂等 | 无 | `client_id` | inbox 认领语义 | 无 |

**优劣与结论**：

- 只有我们和 Codex 把「一次调用」当成一等的对外契约；**Codex 最完整**，我们缺的是「跑道管理」（幂等 / 恢复 / 干预），而不缺方向。
- 最该抄的一条：**`client_id` 幂等与恢复语义** —— 管家 Agent 被定时唤起时，「这次调用是否已经跑过」必须能被回答。
- steering 我们暂不做，但**契约里要预留**；「不要求窗口」这一条 DSH 给了更好的措辞：病根是 session 与窗口、回合的存活被绑死，不是 session 本身。

### 3.2 Safety：策略、门控与审批通道

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 分层 | 策略引擎 + 门控 + 确认通道 + 审计 | 沙箱 / 策略 / 权限剖面 / 审批代理四层 | 审批 / 沙箱 / 预设三个 seam | 模式栈 / 规则 / 回答者 / 分类器 |
| 底线不可放宽 | 不可被配置替换，`locked` 不可下调 | 权限集合交集，只能收紧；不支持即 fail-closed | 单调守卫：返回类型里没有 allow | **可被 `bypassPermissions` 与企业策略放宽** |
| 档位语义 | 调范围，不调宽严 | `Granular` 按类别给权 | permission preset | 5 种模式，含 bypass |
| 规则来源 | 未建模 | 配置层栈 | 单调叠加 | 8 种 source + 被遮蔽规则检测 |
| 确认通道 | 回答者可插拔、与入口正交 | Guardian 保留 issuing context 与 cancel | 确认权限由 live runtime root 决定 | 三个 handler 并列 + 显式短路顺序 |

**优劣与结论**：

- **DSH 的单调守卫**是我们「可收紧不可放宽」的最佳落法：把它从文档里的一句话变成接口形状。
- **Codex 的权限交集**给了 SubAgent 与降级场景一个数学上正确的机制；我们保留规则级 `locked` 底线，在能力集合这一层引入交集。
- **Claude Code 是明确的反面教材**：远程开关能翻转安全底线。我们的底线不接受配置替换，也不接受远程开关。
- 我们缺**规则来源维度**；否则用户一定会问「我设的 allow 为什么没生效」。

### 3.3 自动审批（Safety 的执行侧）

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 裁决者 | 审批 Agent（Core 的调用者） | Guardian（隔离的同步 reviewer） | 审批 seam（不绑定实现） | 无工具的单次分类器调用 |
| 缓存 | 永不写裁决缓存，一事一议 | 证据可复用、授权不复用 + authorization version | 无 | **无裁决缓存**，每个动作真调一次 |
| 成本可观测 | 待建 | 三类预算 + 超时 + 连续拒绝窗口 | 能力描述符 + 显式拒绝 | 每次记 model / usage / durationMs / 阶段 / 折算成本 |
| 给审批看什么 | factsProvider（宿主补事实） | 扩展选 policy 与 evidence，core 强制 review | 只带锚点与理由，不带参数副本 | 工具自述 `toAutoClassifierInput` |
| 缺应答者 | fail-closed | 强制复审条件 | `unavailable`（而非放行） | 自动拒绝（由远程开关决定失败方向） |
| 复审 | 待建 | `require_fresh_review` | 闭集词汇 | 两阶段（fast / thinking）+ 拒绝计数回退 |

**优劣与结论**：

- 三家**共同印证**「裁决不缓存」，CC 给出了最直接的证据（分类器结果里没有缓存字段，只有成本遥测）。
- 我们要补两条：**裁决是一等可观测对象**（成本 / 延迟 / 阶段 / 证据规模），**证据可复用但授权不可复用**。
- **CC 的审批者是无工具单次调用，我们已选了另一条路**：块 2 方案已定审批 Agent 带封闭只读工具集、侦查轮数 ≤3（`docs/develop/architect/confirmation-answerer-and-auto-approval-design.md` §4.4）。这属块 2 的详细设计取舍，不是架构层决策；架构层只需守一条形状约束 —— **确认通道不被预设为单次同步问答**。

### 3.4 Runtime：装配与模型

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 装配位置 | 显式一层，唯一装配点 | Core 内部，输入来自配置层栈 | 插件树组装（preset + patch） | 无此层，散在四处 |
| 定制形态 | 声明式数据优先，注入端口次之 | 配置层栈 + 受约束 Hook | 插件 + seam 三件套 | settings + plugin |
| 模型选择 | 档位是数据、服务与凭据是端口 | 模型目录承载能力（推理档、工具形态、审批覆盖面） | 能力描述符 + 启动前校验 | 4 层解析链，默认 `inherit` |
| 思维强度 | 分档，可随调用覆盖（待建） | `supported_reasoning_levels` | 能力位声明 | effort 字段；fork 继承、普通子 Agent 关闭 |
| 解析失败 | 待定 | fail loud | `UNSUPPORTED_CAPABILITY` | 静默外降（我们不学） |

**优劣与结论**：

- 我们「独立 Runtime 层」的切法**得到 CC 的反证**：它没有这一层，代价是装配散乱、按入口分支。
- 两条硬规则从 CC 抄：**默认必须是 `inherit`**、**解析失败必须 fail loud**。
- **子 Agent 的思维强度默认关闭** —— 它是成本项，不是能力项。

### 3.5 Driver：驱动源、投递与决策往返

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 驱动源 | 桌面 / 远端 / 定时 / 事件 | TUI / exec / SDK / IDE / MCP | 宿主 × 载体组合 | 终端（唯一原生）+ bridge / remote / daemon |
| 与内核的关系 | 不直接调 Core | 跨 crate 协议；同协议不同传输 | 插件树内 | 同进程直连 |
| 长驻服务 | 主进程兼任 | app-server + daemon + transport | 无（进程内） | 无 |
| 结果消费形态 | 投递是一次路由 | 默认最终结果 / `--json` 事件流 | 无投递保证 | 打印模式 / 事件流 |
| 后台投递 | 待建 | 连接级广播 | 会话内 | 命令队列 + 逐 Agent 寻址 |

**优劣与结论**：

- **Codex 的「同一协议、传输可换、客户端可多」比 daemon 化本身更值得学**；我们的 Invocation 目前只是函数签名，没有「线上形态」。
- **exec 的两种输出形态**正是管家 Agent「静默落盘 or 推送结果」的现成参照：同一份执行，两种消费。
- **CC 的命令队列 + 逐 Agent 寻址**是「确认回复不轮询」的现成机制。

### 3.6 Storage：会话、归属与可见性

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 真相 | 关系型主存储（既有决策） | 只追加 JSONL | 日志 + 投影 + 通用键值 | 只追加事件日志 |
| 派生 | 待建 | thread-store 可重建 | projection seam | 列表只扫顶层 |
| 归属 | 归属 × 可见性（已拍板） | 血缘在存储层 | header 携带组合 | 子 Agent 物理分文件 |
| 读取 | 待建 | 反向扫描 + ordinal | 投影 | 两级读取 + 读上限 |
| 内部调用 | 落盘（证据与输入，不是授权） | 保留 issuing context | 事件日志 | sidechain 锚定父链 |

**优劣与结论**：

- 三家一致：**真相只追加、索引可重建、派生视图不能声称它没显示的东西**。
- **CC 的「归属靠物理分层」**是我们「内部调用不进用户列表」的最小落形：不靠过滤，靠不放在同一张表或同一个目录。
- 我们保留 SQLite 主存储，但要学**可扩展的条目联合** —— 会话事实会持续变多，固定结构会先撑不住。

### 3.7 SubAgent

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 定义 | 待建 | agent registry / role | 一个 seam + 多个提供方 | AgentDefinition 数据（定义即配置） |
| 工具裁剪 | 待建 | 子 Agent 能力集 | 能力描述符 + 显式拒绝 | 全局 disallow + 异步白名单 + 定义减集或交集 |
| 权限 | 不能绕过门控 | 权限交集 | 单调守卫 | **父级审批不泄漏**（allow 是替换不是继承） |
| 模型 | 待建 | 角色 / 模型 | 能力声明 | 4 层链，默认 inherit |
| 上下文 | 按调用隔离 | 独立上下文 | 独立会话 | 逐字段 opt-in（共享必须显式点名） |
| 会话归属 | 不落用户列表 | 血缘 | 独立会话 | 物理分文件 + 父链锚定 |
| 递归守卫 | 待建 | AgentPath | delegationDepth | 读不会被压缩重写的位置 |

**优劣与结论**：

- **CC 给了最完整的一份现成设计**；DSH 给了最干净的 seam 形状。
- 最锋利的三条：**无人类应答者就不给问人的工具**（这是工具集裁剪，不是运行时判断）、**父级审批不泄漏**、**上下文隔离逐字段 opt-in**。
- 反面教材：隔离靠逐字段手工维护，漏一项的后果是静默的（后台任务永不注册、永不被杀）。

### 3.8 后台与无人值守

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 无窗口执行 | C1 目标 | 支持（app-server） | 支持（headless / sdk） | 支持（print / daemon-worker） |
| 无窗口时确认 | 审批 Agent 兜底 | Guardian 兜底 | 审批 seam + 运行时所有权 | **自动拒绝**（放弃安全决策） |
| 定时 | C2 的一部分 | 无（宿主负责） | jobs / schedule（会话内） | durable cron + 错过的任务显式补跑 |
| 任务类型 | 归属 × 可见性 | 后台终端 + 中断分离 | job 接口形状与预检纪律 | `TaskState` 联合 + 纯谓词 |
| 结果投递 | 一次路由 + 送达记录 | 事件广播 | 无投递保证 | 静默 / 通知 |

**优劣与结论**：

- **三家都支持「跑在后台」，只有我们打算支持「在后台安全地做决定」** —— 这就是 CC 空着的那一格。
- 可直接抄的两条：**durable 的 catch-up 语义**（错过就要显式补跑，不能静默丢）、**任务类型做成联合 + 纯谓词**（先有归属谓词，再谈列表过滤）。

### 3.9 界面与 Core 的耦合（跨块）

| 关注点 | 我们 | Codex | DSH | Claude Code |
| --- | --- | --- | --- | --- |
| 界面是否进内核契约 | 不进（经事件出口出去） | 不进（协议） | 不进（插件） | **进**：`renderToolUseMessage` 是 Tool 必填成员 |
| 无界面时的行为 | 正常（事件照发） | 正常 | 正常 | 确认自动失败 |
| 证据 | 不变量 1 与偏差 1 | TUI 是独立 crate | headless profile | 连没有渲染端的远端 stub 也不得不实现渲染方法；AgentTool 直接操作界面 JSX |
| 代价 | 待付（今天 `sender` 必填） | 无 | 无 | 两个 bridge 文件约 215KB；`ToolUseContext` 约 50 字段 |

**优劣与结论**：CC 用最锋利的证据告诉我们 **呈现一旦进入内核契约，就再也拿不出来**。我们的方向正确，要守住。

## 5. 三家收敛处（对我们的印证）

| 结论 | Codex | DSH | Claude Code | 对我们的意义 |

## 6. 三处分歧，以及我们选哪边

| 分歧 | Codex | DSH | Claude Code | 我们选 | 理由 |
| --- | --- | --- | --- | --- | --- |
| 安全底线能否被配置放宽 | 不能（交集只收紧） | 理论可被 patch 换掉 | **能**（模式 / 远程开关） | 与 Codex 同侧 | 底线一旦可配，「标准只有一套」就无从谈起 |
| 扩展点开放到什么程度 | 12 类 Hook + 五道约束 | 一切皆插件，可逆 | 27 事件 + 可改写参数 | 分层开放：观察与装配可开，裁决路径不开 | 开放的是装配与观察，不是判定 |
| 后台形态 | app-server 长驻 | 插件内 jobs | daemon-worker 绕过 | 主进程内，作为 Driver 的一种驱动源 | 单机桌面不需要新进程域 |
| 会话存储形态 | JSONL 唯一真相 | 日志 + 投影 | 事件日志 | SQLite 主存储 + 可扩展条目联合 | 我们的量级与搜索诉求不同 |
| 上下文的组织 | 53 个命名 fragment | 插件贡献片段 | 压缩三档 + 可重放替换 | 片段注册表（待重构） | 三家一致指向片段化 |
| 审批者是否需要工具 | 隔离 reviewer（有预算） | 纯 seam | 无工具单次调用 | **已决（块 2 方案）**：封闭只读工具集 + 侦查轮数 ≤3 | 架构层只需保证确认通道不预设为单次同步问答；排期上块 2 依赖调用级隔离 |

## 9. 一句话总结

**三个产品用三种方式证明了同一件事：Agent 内核必须能被多种调用方复用，而这要求内核不认识任何具体的调用方。**

- **Codex** 证明了「协议化」是最可演进的工程手法：调用、事件、扩展都先变成可枚举的协议，安全用集合运算与显式预算表达。
- **DSH** 证明了「不可放宽」可以做成类型事实：单调守卫、能力描述符、确认权限由运行时所有权决定。
- **Claude Code** 证明了「呈现一旦进入内核契约就拿不出来」，也证明了「后台可以跑，但后台的安全决策没人做」。

我们要做的，是**用 Codex 的协议化改造调用与事件，用 DSH 的机制守住底线，用 Claude Code 的现成设计填充 SubAgent 与后台的细节，然后补上三家都空着的那一格：无人值守时，仍然由审批 Agent 安全地做决定。**
