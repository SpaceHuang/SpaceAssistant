# Agent SDK 的形态：库、服务，还是库加托管子进程

> 定位：**决策记录**。回答一个具体问题 —— 把 Agent 六大模块拆成可复用的 SDK 时，它的物理边界画在哪：同进程库、独立服务，还是库加托管子进程。
> 状态：**已拍板（按同进程库推进）** ｜ 基线：工作区 HEAD ｜ 评估日期：2026-09-15
> 数据口径：改造面由 `electron/toolChatLoop.ts` 出发按静态 import 展开依赖闭包得到（含 `@/` 别名解析，不跟随动态 `import()`）；人日是**按改造面量级推的估算**，用于比较三种形态的相对成本，不是排期承诺，误差可能 ±50%。
> 上游：`product-architecture-design.md` §11（七类 SDK 化缺口的清单覆盖）。本文只回答「边界画在哪」，不改写理想态。

**一句话**：按**同进程库**推进 —— 它几乎就是关键路径 A 的副产品，同时是今天唯一有收益的形态；契约按「可远程」的形状定义（禁止函数与句柄），把服务形态的门票以 0 成本留出来。

---

## 1. 结论

| 形态 | 追加开发代价 | 持续成本 | 对本产品三条业务线 | 建议 |
| --- | --- | --- | --- | --- |
| **A 同进程库** | ≈ 0（P1 – P5 本来就在关键路径 A 的预算里） | 无 | 收益已满 | **现在做** |
| B 独立服务 | 15 – 27 人日 | 运维、协议兼容、跨进程排障 | 收益 0 | 出现信号再做 |
| C 库 + 托管子进程 | 6 – 12 人日 | 三平台构建与子进程管理 | 收益 0 | 需要隔离时先补它 |

**已拍板：A。** 契约按可远程的形状定义，物理边界留在本进程。理由不是 A 便宜 —— 是 A 的收益今天已经能全部兑现，而 B / C 的收益对本产品是 0。

## 2. 口径：改造面有多大

| 项目 | 规模 |
| --- | --- |
| 依赖闭包（从 `electron/toolChatLoop.ts` 静态展开） | **368 文件 / 2.0 MB / 5.35 万行** |
| 其中 `src/shared/` | 77 文件 / 380 KB，已零 electron 依赖 |
| 闭包内直接 `import 'electron'` | 26 文件，其中 **15 个是 `import type`**（类型擦除，零成本） |
| 值引用宿主机 API 的 | **11 文件 / 10 个符号**（`app`、`safeStorage`、`shell`、`BrowserWindow`、`IpcMain`、`Menu`、`Tray`、`dialog`、`nativeImage`、`nativeTheme`） |
| 其中桌面外壳与 IM 驱动源 | 7 文件：`appIpc` 102 KB、`feishu/feishuIpc` 21 KB、`wechat/weChatIpc` 13 KB、`tray`、`menu`、`feishu/feishuCliFlow`、`externalLink` |
| **核心内真正需要端口化的** | **4 文件 / 3 个能力** |

那 4 个文件与它们要的宿主能力：

| 文件 | 宿主能力 | 用途 |
| --- | --- | --- |
| `electron/tools/builtinExecutors.ts`（52 KB） | `app` | 路径与 userData |
| `electron/llmSystemPrompt.ts`（3 KB） | `app` | 同上 |
| `electron/secureApiKey.ts`（1 KB） | `safeStorage` | API Key 加密 |
| `electron/mcp/mcpOauthService.ts`（12 KB） | `shell` | 拉起授权浏览器 |

**这是本文最重要的发现**：「26 个 electron 依赖」在切开核心与外壳之后收敛成 **3 个能力**。SDK 化不是重写，是一次边界手术 —— 大部分「吓人的数字」来自桌面外壳与 IM 驱动源，而它们本来就该在宿主侧。

## 3. 三种形态都要付的公共成本

| 块 | 内容 | 量级 |
| --- | --- | --- |
| P1 契约层 | Invocation、事件 union、四态结果、端口接口 | 2 – 4 人日 |
| P2 宿主能力端口化 | 上表 4 个文件 + 3 个端口 + 调用方适配 | 2 – 3 人日 |
| P3 消掉单实例状态 | 4 处模块级状态 + 2 个注册表，成本主要在回归测试 | 3 – 5 人日 |
| P4 切走驱动源与桌面外壳 | 约 35 – 45 文件 / 280 KB 迁到宿主侧，机械但要修边界处的类型泄漏 | 3 – 5 人日 |
| P5 包边界 + 护栏 + 验收闭环 | workspaces、`exports`、lint 规则、CI 断言、`createAgentRuntime` 与「不启动 Electron 跑完一个回合」 | 3 – 5 人日 |
| **合计** | | **13 – 22 人日** |

P1 – P4 就是关键路径 A（偏差 1、2）本身。**所以 A 形态的边际成本只有 P5。**

## 4. 三种形态逐项展开

### 4.1 A · 同进程库

**收益**：延迟最低（工具结果不跨边界）；直接复用宿主的文件、浏览器与终端句柄；npm 一行安装；调试栈完整；无运维。**对本产品三条业务线 —— 自动审批、SubAgent、后台管家 —— 收益已经全部兑现**，因为它们本来就跑在同一个进程里。

**一次性代价**：≈ 0，即 P1 – P5。

**持续性风险**：
- 与宿主同权，**安全底线只能靠 API 形状挡** —— 偏差 15「底线不可放宽」在进程层强制不了。
- 宿主进程崩了，Agent 一起崩。
- 宿主必须 TS / JS。
- 多实例完全依赖 P3 治干净；治不干净就只能「一进程一个 runtime」。
- 升级跟着宿主走。

**何时够用**：宿主可信、同语言、产品内复用 —— 就是今天。

### 4.2 B · 独立服务

**收益**：真正的进程级隔离 —— 子进程可以**真的不给凭据与文件系统权限**，这是「底线不可放宽」唯一能在机制层落地的方式；崩溃隔离；任意语言宿主；独立升级与灰度；一个服务天然跑多租户；远端团队可用。

**追加代价（15 – 27 人日）**：
- 协议 schema、序列化、事件流、cancel、版本与能力协商：5 – 8
- 进程生命周期与崩溃恢复：3 – 5
- 鉴权与凭据隔离：2 – 4
- 跨进程可观测性（因果链、排障）：2 – 4
- 平台打包与分发：3 – 6

**真正的硬骨头**：今天的契约大量不可序列化（`sender`、数据库句柄、闭包端口）；工具结果是传输大头（浏览器截图、shell 输出）—— 而 `oversizedToolResult` / `toolResultLimits` 今天已经在做裁剪，说明这个压力本来就存在，只是被同进程掩盖了。

**对本产品三条业务线：收益 = 0。**

### 4.3 C · 库 + 托管子进程

**形态**：对外仍是库 API，进程边界由库自己管。**这个项目已经在用这个形状** —— Playwright 就是「库 API + 浏览器子进程」。

**收益**：拿到 B 的隔离（进程边界、最小权限），保留 A 的易用（无部署、无鉴权、无多租户），还能按需把重工具放进子进程。

**追加代价（6 – 12 人日）**：子进程协议、进程生命周期管理、二进制与三平台打包 —— 不需要付鉴权、多租户、运维那几笔。

**风险**：调试成本介于 A 与 B 之间；子进程崩溃要能被库感知并重启；Windows / macOS / Linux 构建矩阵是实打实的开销。

**何时值得**：需要隔离，但不想让使用者运维。

---

## 5. 为什么现在不选 B

- **双变量返工**：契约形状还没稳定就同时动「协议设计 + 核心重构」两个变量，返工概率翻倍。
- **收益为 0**：B 买到的是隔断与多语言宿主，而三条业务线今天全在同一进程、只用 TS。
- **会先付最贵的那笔**：B 的传输层要求契约可序列化，而契约的可序列化设计本来就能在 A 里免费完成 —— 先做 A 再做 B，B 的代价是 15 – 27 人日；先做 B 再做 A 的核心重构，等于把 P1 – P4 重做一遍。

## 6. 决定之后立刻要落的三条硬约束

这三条都不额外增加工作量 —— P5 的护栏本来就要写，它们只是多加几条断言：

1. **契约里禁止函数与句柄。** 端口表达为「宿主实现的服务接口」；本地绑定时把对象直接塞进去即可。唯一例外是绑定层的适配器，不进契约。
2. **端口一律是接口，不是闭包。** 今天 `toolChatLoop.ts:409` 的 `getApiKey: () => Promise<string | null>` 这类签名要换成接口方法；这样同一份契约在进程内与进程外都成立。
3. **一次调用必须能表达多实例并存**（instanceId 或 runtime 句柄），并据此消掉四处模块级状态：`tools/builtinExecutors.ts:1300`、`confirmation/audit.ts:11`、`mcp/mcpToolExecutor.ts:24`、`remote/confirmId.ts:6`。

配套的验收：`createAgentRuntime(deps)` 之后，**不启动 Electron** 就能跑完「带工具调用的回合 + 一次确认 + 一次拒绝」。

## 7. 升级信号：什么时候回头补 C / B

| 信号 | 动作 | 代价 |
| --- | --- | --- |
| 宿主不可信（要跑别人写的 Agent） | 补 C | 6 – 12 人日 |
| 需要多语言宿主 | 补 C（库退化成薄封装） | 6 – 12 人日 |
| 要把安全底线落到进程层（偏差 15） | 补 C | 6 – 12 人日 |
| 一个宿主跑多租户、或远程团队消费 | 在 C 之上补 B 的鉴权与部署 | 额外 9 – 15 人日 |

这些信号一个都没出现之前，C / B 都是提前付费。

### 边界说明

- 本文不改写 `product-architecture-design.md` 的理想态；它只回答 SDK 的**物理边界**画在哪。
- **A 不是妥协。** 三条业务线跑在我们自己的进程里，B / C 的收益对它们是 0 —— 那是给外部复用者准备的，不该算进本产品的重构预算。
- 「契约按可远程形状定义」不等于现在就做服务化：它只是**把不花钱的选项留住**，让 C / B 变成加法而不是重写。
- 与 `rewrite-vs-refactor-cost-assessment.md` 的结论同向：先锁契约，后换实现。本文是同一个顺序在 SDK 边界上的应用。
