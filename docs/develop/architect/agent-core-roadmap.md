# Agent Core 演进规划（Roadmap）

> **这份文档是规划，不是方案。** 它只回答四个问题：我们要支持什么、架构方向是什么、今天卡在哪、未来有哪几块工作。
> 每一块工作各自有独立的技术方案文档（见 §9），本文不展开实现细节。
>
> 状态：待评审 ｜ 基线：工作区 HEAD ｜ 摸排日期：2026-09-12

**一句话**：Agent Core 今天把「跑一次 Agent」等同于「跑一轮会话回合」；而接下来要做的三类新能力 —— 自动审批、SubAgent、后台（管家）Agent —— 需要的都是**一次可独立发起、可无窗口、可嵌套的 Agent 调用**。
所以这一轮的重点不是「加功能」，而是**把 Core 的调用方式打开**，让不同调用方复用同一套推理循环、工具框架、确认机制与审计。

---

## 1. 目标：未来要支持什么，架构上的要点是什么

| # | 需求 | 一句话 | 架构要点 |
| --- | --- | --- | --- |
| A | 自动审批 Agent | 需要确认的工具调用由 Agent 依据事实自动裁决，而不是弹卡片等人 | ① 标准只有一套 ② 一事一议，裁决不写缓存 ③ 不可用时 fail-closed ④ 可归因、可审计 ⑤ 它自己也是一次 Core 调用（只读工具、快模型、有界输出） |
| B | SubAgent | 主 Agent 通过工具调用派生一个子 Agent，独立上下文与模型，结果回灌父上下文 | ① 嵌套执行域：模型/工具/预算/取消/事件归属按调用隔离 ② 子 Agent 同样过策略与审计，不能成为绕过审批的后门 ③ 深度、并发、预算都要有上界 |
| C1 | 纯后台 Agent | 托盘 / 无窗口状态下 Agent 照常运行，界面只是观察者 | ① 窗口关闭不等于回合失败 ② 事件不丢，重开窗口能看到过程与结果 ③ 无窗口时确认必须有归宿 |
| C2 | 后台管家 Agent | 远程指令托管 + 定时 / 事件任务托管（C1 的业务载体） | ① 它是 **Core 的调用者 + 一份 Profile + 一个 Skill**，不是硬编码定制 ② 一次调用要能带上自己的模型 / 工具 / Skill / 策略档 / 会话域 ③ 全自动决策走审批 Agent，管家不感知审批 Agent 存在 ④ 确认回复回到同一会话、起新 Turn ⑤ 会话有独立的归属与可见性（见 §1.4） |

### 1.1 自动审批 Agent

**要什么**：工具调用被策略判为「需要确认」时，由 Agent 给出批准 / 拒绝并说明理由；理由要能回到发起方手里。

**架构要点**：

- **标准唯一**：没有「严格 / 宽松」两套判据，始终是「用户不盯着也不会出问题」。所谓的自动审批档位，调的是**放行范围**，不是放行尺度。
- **一事一议**：裁决不写决策缓存。缓存的语义是「把用户的意志固化下来」，而 Agent 不是授权源头。
- **fail-closed**：Agent 不可用、超时、输出不可解析，一律拒绝，并且理由要明确告知发起方，让它能改方案。
- **可归因**：审计必须能区分「用户批的 / 规则批的 / 缓存批的 / 审批 Agent 批的」，并记录依据。
- **它也是 Core 的调用者**：只读工具集、快模型、有界输出、免二次审批（否则审批套审批）。
- **可追溯、可复盘**：裁决与侦查过程必须落盘（审计 + 后续优化），但记录是**输入与证据，不是授权**（见 §1.5）。

### 1.2 SubAgent

**架构要点**：

- 一条**不经 Turn、不经 UI** 的调用入口：给定消息、工具集、模型、预算、事件出口就能跑。
- **嵌套执行域**：模型、工具快照、预算、取消信号、事件归属按「调用」隔离，而不是按 session 共享（后者是今天的默认）。
- **不绕过安全**：子 Agent 的工具调用同样经过策略门控与审计。
- **有界**：最大深度、fan-out、子预算、单次时长。

### 1.3 纯后台 Agent 与后台管家 Agent

**纯后台**：Agent 的存活条件只由取消 / 超时 / 错误决定；窗口是观察者，不是运行前提。无窗口时确认走审批 Agent 或 fail-closed，不允许静默挂起。

**管家 Agent**（业务定义，2026-09-12 对齐）：

| 托管类型 | 输入 | 流程 | 产出 |
| --- | --- | --- | --- |
| 远程任务托管 | 飞书 / 微信 / 其他远端的简单指令 | 意图识别 → 方案制定 → **向输入方请求确认** → 安排执行 → 回复结果 | 回复到原输入方 |
| 自动化任务托管 | 用户配置的定时 / 事件触发 | 按配置执行任务 | 落库；按最近可用入口同步；或静默落盘 |

**架构要点**：

- 管家 Agent **不是对 Agent 逻辑的硬编码定制**：它自身不含编排逻辑，只有一份 Profile —— 来源身份（lane）、确定性加载的 Skill（行为逻辑全在这里）、专属工具集、模型档位、安全策略档。
- 宿主只提供三件事：**唤醒、配置注入、投递工具**。
- 因此对 Core 的要求可以收成一句话：**「一次调用能携带自己的配置，并在无窗口下跑完」**。
- 单次托管 = **一次 Core Turn + 专用会话域**。不需要「任务一等实体」，不需要 Core 内建调度器，也不需要宿主投递编排。

### 1.4 会话的归属与可见性

**问题**：今天「会话」一个概念同时承担四件事 —— 上下文容器、执行独占单位、配置载体、界面列表项。新的调用方对四件事的需求并不一样：

| 调用方 | 上下文载体 | 执行独占 | 自己的配置 | 出现在用户会话列表 |
| --- | --- | --- | --- | --- |
| 桌面聊天 | 要 | 要 | 要 | 要（主列表） |
| 远端 / 自动化管家 | 要（确认回复回到同一会话起新 Turn） | 要 | 要 | 可选（独立分区，不与日常会话混排） |
| SubAgent | 要（独立 transcript） | 要（不能占住父会话） | 要（自己的模型与工具集） | **不要** |
| 审批 Agent | 要（一次裁决内的多轮侦查） | 要 | 要 | **不要** |

**架构要点**：

- 把两个属性从「会话」里拆出来，作为独立维度，而不是新增「N 种会话类型」：
  - **归属**：`user` / `remote` / `automation` / `internal`（子调用、审批）。决定策略 lane、审计归属、预算与配额。
  - **可见性**：`primary`（主列表）/ `section`（独立分区）/ `hidden`（不进列表）。决定列表加载什么。
- **内部执行不落「用户会话」，但要落「内部调用记录」**：SubAgent 与审批调用都不产生用户可见的会话，也不进会话列表；它们的执行轨迹、裁决与成本必须落盘（见 §1.5）。它们本来就是**归属为「内部」的会话**（不进列表、可见性 hidden），不是伪造出来的用户会话；记录按血缘锚定：子调用挂父 turn、审批挂确认请求。长跑场景的差别只在保留期与是否跨重启延续上下文，不在「有没有会话」。
- **可见性不能由 Agent 自己声明**：它和 lane 一样是安全语义，必须由调用方 Profile 在发起时注入并冻结，否则等于 Agent 可以把自己对用户隐藏。
- **hidden 不等于不可审计**：隐藏会话仍进审计与落库，但默认排除在会话列表、跨会话搜索、会话备份 / 导出之外。

**一句话**：「列表加载哪些会话」的答案不是硬编码哪几种 Agent，而是 `visibility` 上的一个查询条件。

### 1.5 内部调用的落盘：证据与输入，不是授权

**要什么**：审批调用与 SubAgent 都必须落盘 —— 消息、工具调用、裁决与依据、模型与成本。用途有两个：**安全审计**（说清「凭什么批的」）与**后续优化**（把历史裁决作为新裁决的输入）。

**分三层，用途不同**：

| 层 | 内容 | 用途 | 形态 |
| --- | --- | --- | --- |
| 审计层 | 每次裁决：发起方、lane、工具与参数摘要、结论、依据、模型、耗时、成本 | 安全审计 | 复用现有安全审计日志（独立文件、物理隔离、按天切分、保留 180 天） |
| 轨迹层 | 审批 / 子调用的完整消息序列（Profile 提示、侦查工具调用与观察结果、最终裁决） | 复盘、自我优化 | 需要新载体：**内部调用记录** —— 即归属 `internal`、可见性 `hidden` 的内部会话（§1.4），与用户会话分表存放 |
| 上下文层（可选） | 跨裁决延续的记忆（如「本任务内已经裁决过什么」） | 一致性与成本 | 由调用方 Profile 声明；**仅作输入，不是授权** |

**锚点**：SubAgent 记录锚在**父 turn**（父子关系明确）；审批调用锚在**确认请求**（它是横向服务，被任何 lane 触发，不属于某个父 turn）。两者都**不落用户会话行**。

**三条硬边界**：

1. **记录是证据与输入，不是授权**：记录可以被检索、可以作为审批 Agent 的输入（例如「本任务内已裁决过哪些调用」），但**不能跳过裁决**、不能变成「同签名直接复用上次结论」 —— 那等于把 Agent 的判断固化成授权，与 §1.1 的「一事一议」是同一条不变量。
2. **与用户数据面隔离**：用户删会话不能删掉安全审计；Agent 不能改写自己的裁决记录（只追加）。
3. **脱敏优先**：审批看到的是文件内容、命令、URL，落盘会形成新的泄露面。建议默认只落脱敏后的轨迹加可复现引用（路径、行号、命令哈希），原文默认不落、按需可配置。

**已有可复用的**：安全审计已是独立物理隔离的 JSON Lines 文件、写入前脱敏、保留 180 天（`electron/confirmation/securityAuditLog.ts:14`、`:43`、`:48`）；事件类型里已有 `confirm.request` / `confirm.outcome`（`src/shared/confirmation/types.ts:236`）；读取器与设置页展示也已具备（`electron/confirmation/securityAuditReader.ts`、`src/renderer/components/Config/ToolsSecuritySettingsTab.tsx:500`）。缺的是「裁决过程」这一层，以及 `actor` 里的 `agent` 口径（现取值 `'user' | 'system' | 'migration'`，`src/shared/confirmation/types.ts:233`）。

## 2. 方向：架构上想达成什么效果

**效果一：一个 Core，多种调用方。**
同一套推理循环同时服务桌面聊天、IM 远程、审批 Agent、SubAgent、管家 Agent。差异**用数据表达，不用代码分支表达**。收敛之后差异面只有五项：**消息、工具集、模型、策略上下文、事件出口**（今天是 20+ 个构造参数加若干全局配置）。

**效果二：窗口是观察者，不是运行前提。**
「解耦渲染进程」不等于删掉 `sender`，而是把三条性质不同的线分开处理：

| 线 | 今天 | 目标 |
| --- | --- | --- |
| 通知线（活动心跳、文件树刷新、浮动通知、标题建议） | 直连 `webContents.send` | 抽象为事件出口；无 UI 时 no-op 或转投其他通道 |
| 生命周期线（回合是否存活） | 窗口没了回合就失败 | 只由取消 / 超时 / 错误决定 |
| 驱动线（谁发起、排队、重试、取消） | 渲染端 | 主进程权威，渲染端只是其中一个 driver 实现 |

**效果三：安全不打折。**
策略标准唯一；确认的**末端回答者**可插拔（人 / 审批 Agent / 无回答者 fail-closed），且与「从哪个入口进来」（lane）正交；任何 Agent 都不得绕过策略；所有裁决可归因、可审计。
**审批 Agent 不新增链路**：它在「回答者」位置上发起一次**嵌套 Core 调用**（由 Runtime 装配、经 `invokeApproval` 发起、同样过策略门控、准入与审计；准入不豁免，优先级继承等待方，详见基线 §5 嵌套调用准入）—— 这是全文唯一一条「判定路径回到 Core」的边，详见基线 §2.6、§7.2。

## 3. 架构边界与对外接口（摘要）

**完整阐述见 `docs/develop/architect/product-architecture-design.md`**（产品架构理想态：全景视图、目标与不变量、六层划分、逐层边界与接口、进程边界、偏差清单）。本节只留摘要，供工作块划分使用。

- **全景**：两个进程 —— 渲染进程承载界面交互（驱动源界面 加 业务界面）；主进程承载 **Agent 模块（六块主干）** 与 **业务模块（应用域的主进程侧能力）**，以及被 Electron 强制放在主进程的窗口外壳。中间只有一条 `window.api` 桥，IPC 面分「Agent 驱动协议」与「业务功能协议」两类。
- **边界**：Core 只负责一次调用内的推理循环、上下文装配、工具执行、事实与事件产出、预算与取消的施加点。它不认识业务身份，也不回答「谁发起、何时发起、记在哪、给谁看」。
- **不变量**：一次调用可独立发起；Core 不认识业务身份；安全门控不可绕过且标准唯一；可见性不由 Agent 自己声明；内部调用是证据与输入、不是授权；终态与结果先持久化再投递（过程性事实流不受此约束）。
- **接口**：一次调用（Invocation）= `session` + `messages` + `profile` + `events` + `limits` + `signal` → `InvocationResult`（status / messages / usage / events）。其中 `session` 必填（归属与落盘锚点），`messages` 只是**本次新增输入** —— 历史由 Core 经 `loadContext` 端口装载（基线 §6.2、§8）。四个刻意不出现的东西：`sender`、**必须先有一个活跃的用户回合**、确认回答者、`isWebContentsAlive`。
- **扩展点**：声明式数据优先（Profile / PolicyRule / Skill / 工具声明），其次注入式端口（events / factsProvider / answerer / ToolExecutor / 凭据解析 / loadContext / persist / translate / limits）。安全门控与上下文装配顺序**不开放**，也不提供可改写的生命周期 Hook。
- **策略**：引擎在内，内容在外。两条不可混淆的约束：**底线集**（`locked`）不可**放宽**（防越权）；**不可变集**（递归终止条件、fail-closed 兜底、审计成对）放宽与收紧**都不允许**（防安全路径静默停摆）——`locked` 拦不住收紧，两者不可合并（基线 §7.1 第三条判据、§7.2）。
- **模型**：档位（模型与思维强度）是 Profile 数据，服务与凭据是宿主端口。
- **分层**：Core / Safety / Runtime / Driver（驱动源）/ Storage / Utils 六块；Storage 与 Core 之间是「协议在内、实现在外」。
- **驱动源**：桌面界面、远端输入方、定时、事件四类；桌面只是其中一个，窗口与托盘被放进主进程是 Electron 的约束。
- **投递**：Agent 声明意图（`deliver(preference, payload)`），宿主做驱动源路由；**终态与结果**先持久化再投递（过程性事实流不受此约束），默认单目标、可重试、不可达则**有界**补投（TTL 与取代，见基线 §4.2）。

**理想态与今天的偏差清单（24 条）**见 `docs/develop/architect/product-architecture-design.md` §10 —— 重构规划可以直接按它排期（1 – 12 为 Agent 主线，13 – 14 为横切关注点，15 – 16 为对照研究，17 – 20 为复用面，21 – 23 为驱动源与准入面，24 为存储面即保留与清理的归属）；该表带「前置 → 后置」依赖列，排期时先读那一列，不要从偏差描述里重推先后。

## 4. 当前的问题

一句话根因：**Core 的「执行单元」被钉死在「由用户消息催生的会话回合」上，而「确认」被钉死在界面上。**

### 4.1 调用契约：存活绑窗口、会话不能独立创建、装配没有声明式入口

**先纠正一个容易被误读的提法**：问题**不是**「跑一次 Agent 必须有会话」，而是下面三条。**Agent 调用必须有会话**，它是归属与落盘的载体 —— 这不是惯例而是约束：一旦没有会话锚点，审计归属（裁决与执行条目沦为孤立事件，说不清这次调用整体做了什么）、预算归属（token 与成本算在谁的配额上）、恢复锚点（确认回复、重试、重开窗口继续看）就同时失去落点。三家竞品也都如此（Codex 的 thread 是身份载体、DSH 要求 `agentPreset` 随 header 一起持久化、Claude Code 连子 Agent 都是**物理分文件的会话**）—— 这是旁证，不是论据。

- **现象 A：存活绑窗口。** `sender: WebContents` 是必填参数，循环每轮开头判活，窗口没了直接返回 `'Window closed'`（`electron/toolChatLoop.ts:389`、`:623`）。
  影响：托盘 / 无窗口下 Agent 实际不可用；IM 链路会落到一个坏的无头兜底实现（`electron/remote/imRemoteAgent.ts:72`），而这条路径的测试把它 mock 掉了，从未真跑过。**这是「Agent 绑界面」的根因。**
- **现象 B：会话不能独立创建。** 执行前必须有 session + user message + assistant message + turn 行，turn 与 requestId 严格配对（`electron/database/schema.ts:100`、`electron/turnRuntime.ts:36`）—— 等于把「跑一次 Agent」定义成了「一轮用户对话」，会话只能由用户消息催生。
  影响：审批裁决、SubAgent、后台触发都拿不到**自己的调用载体**，只能伪造会话或另起一套循环。**要的不是「无会话」，而是「会话便宜到可以随手建一条，并能声明它的归属」。**
- **现象 C：装配没有声明式入口。** 模型按会话或全局优选冻结，工具集由全局配置反推，Skill 靠 LLM 路由加三条来源硬规则。
  影响：「这次调用用哪个模型、带哪些工具、加载哪个 Skill」没有声明式入口 —— **这是管家 Agent、审批 Agent、SubAgent 三者共用的前置能力，目前完全缺失**。（这条与 A、B 无关，是独立的一处。）

### 4.2 会话的归属与可见性：内部调用无处安放

- 现象：会话表没有归属 / 可见性维度，列表查询是全表 `SELECT * FROM sessions ORDER BY updated_at DESC`（`electron/database/operations.ts:120`），唯一的过滤维度是工作目录 profile（`electron/workDirManager.ts:81`、`electron/appIpc.ts:207`）；渲染端也只做搜索框过滤与按时间分组（`src/renderer/components/SessionList/SessionListPane.tsx:24`、`:48`）。
  影响：SubAgent 的会话会直接出现在用户列表里，管家 Agent 的托管会话会与日常会话混排。今天的飞书 / 微信会话就是这样混着的，只能靠名称前缀 `[飞书]` / `[微信]` 区分（`electron/feishu/feishuSessionResolver.ts:14`、`electron/wechat/weChatSessionResolver.ts:16`）。
- 现象：跨会话搜索也只按工作目录 profile 过滤（`electron/database/operations.ts:1231`）。
  影响：一旦出现内部会话，用户的搜索会命中子 Agent 的内部推理。

### 4.3 审批通道：只有「等人」的实现

- 现象：`channelFor` 只认 desktop / wechat / feishu 三个通道，实现都在等人；超时硬编码 5 分钟（`electron/confirmation/channels.ts:107`、`electron/toolConfirmRegistry.ts:16`）。
  影响：自动审批 Agent 无处接入；后台 Agent 遇到危险操作只能挂死或全拒。**这就是「审批依赖界面」的直接原因。**
- 现象：`automation` lane 在类型层和套餐层都已定义，运行层零实现（`src/shared/confirmation/types.ts:18`、`src/shared/policy/policyPackages.ts:20`）。
  影响：自动化触发的工具调用在安全模型里是**无主的** —— 无法按套餐限权、无法归因、无法审计。
- 现象：自动裁决挂点 `AutoEvaluator` 是同步的、只返回 `{approve, reason}`，实现按工具名写死三分支（`src/shared/confirmation/types.ts:295`、`electron/confirmation/toolCallGate.ts:336`）。
  影响：接一个 Agent 审批要改代码；即使接上，也无法表达「谁批的、依据是什么」。
- 现象：审批结论被压成 `approved | rejected | timeout`，拒绝理由只有三个人类语义的枚举，模型最终收到硬编码文案「用户拒绝执行此工具」（`electron/toolChatLoop.ts:1398`、`:1241`、`:1652`）。
  影响：**现场根本没有人**，管家 Agent 被误导，也拿不到理由改方案；更糟的是这条文案会进入连续同错计数，凑满三次直接中止 Turn。
- 现象：写决策缓存时只看 `outcome === 'approved'`，不看回答者是谁，来源一律写 `'user-confirm'`（`electron/toolChatLoop.ts:1580`、`:1607`）；审计 actor 硬编码为 `system`（`electron/confirmation/channels.ts:43`、`electron/confirmation/toolCallGate.ts:368`）。
  影响：一旦接入非人回答者，「Agent 批的」会被记成「用户批的」，**审批裁决从此被固化进缓存**，与「一事一议」直接冲突。
- 现象：审计事件只记录结论摘要（`factsSummary` / `reason`），没有裁决过程的轨迹；而审批调用的完整消息序列今天没有任何载体 —— 因为内部调用没有自己的载体，会话只能由用户消息催生（§4.1 现象 B）。
  影响：出了事说不清「它凭什么批的」；也没有可用于复盘与自我优化的记录，审批会一直是「每次从零开始的单点判断」。

### 4.4 隔离与嵌套：一切都是按 session 共享的

- 现象：文件读缓存、写租约、浏览器会话、MCP 连接、LLM / 工具调用计数都按 session 或进程共享，写租约同 session 直接放行（`electron/toolChatLoop.ts:173`、`:466`、`electron/writeSafety/toolPathLease.ts:27`）。
  影响：父子 Agent 会静默共享缓存与上下文；并发写同一文件拦不住；fan-out 会变成 MCP 连接风暴。今天没有任何 depth / fan-out / 子预算闸门。
- 现象：事实只按 toolUseId 关联到唯一一条 assistant message，渲染端消费整条 turn 快照，没有嵌套与归属维度（`src/shared/assistantFactAggregator.ts:28`、`src/renderer/services/turnProjectionService.ts:25`）。
  影响：子 Agent 的活动无处表达；若沿用父 sessionId，内层事件会混进父会话台账，影响回放与恢复。

### 4.5 渲染耦合：驱动权还在渲染端

- 现象：发起、重试与出站消息分类仍在渲染端（`ChatView.tsx` 调 `chat:prepare-turn` / `chat:execute-turn`；`src/renderer/services/chatOutboundClassifier.ts`）。**已收敛**（2026-09-16 复核）：排队与取消已回主进程（`electron/appIpc.ts:838` 的 `chat:get-next-queued-message`、`:996` 的 `chat:cancel-turn`），事实权属、落库与投影也已归 Core；原先「技能路由算两遍且无缓存」「渲染端留着拼系统提示的死代码」两处现象随 `9dfc46d1` 一并消除（基线 §10 偏差 12 已判为已解决，偏差 9 降为部分解决）。
  影响：后台 Agent 必须重建一套控制循环；**「谁发起」目前仍由渲染端独家持有** —— turn 生命周期与「会话是否在跑、谁在等确认」已有主进程权威来源（`TurnRuntime` / `chat:get-turn-displays`、`chat:get-pending-confirmation`），缺的是把「发起」本身也收进驱动源层。

### 4.6 已经就绪、不要重复做功的部分

- 工具框架（direct / planned、plan / execute 分离、invocation 状态机）足够承载新调用方，**不建议重写**。
- 策略引擎是纯函数、规则是声明式数据，lane / 套餐 / `locked` 底线 / DB 覆盖齐备，「有些确认不许被放宽」在代码里已经落地。
- 审计事件已成链（`policy.decision` / `confirm.*` / `cache.*`）。
- 远端链路已复用 Core 跑通一半：进度回推、确认回执、预算、中断、授权与写入租约都在。
- 工具来源与执行授权已收敛主进程，渲染端只读；模型凭据解析与上下文估算两端同源。

## 5. 未来的工作块

一共 4 块，外加 1 块待定。每块可以独立交付、独立验收。

| 工作块 | 解决什么问题 | 主要产出 | 依赖 | 状态 |
| --- | --- | --- | --- | --- |
| 1. 调用契约（Invocation） | §4.1 与 §4.2：存活绑窗口；会话不能独立创建；装配没有声明式入口；会话无法区分归属与可见性 | 一次可独立发起、自带配置与会话锚点的调用 + 五项差异面（消息 / 工具集 / 模型 / 策略上下文 / 事件出口）+ 会话归属与可见性（见 §1.4）+ `messages` 收紧为「本次新增输入」（历史经 `loadContext` 端口装载，见基线 §6.2、§8）；现有三个入口改为它的适配器，行为等价 | 无（公共前置） | 待启动 |
| 2. 审批通道与自动审批 | §4.3：确认只有「等人」通道；裁决不可归因、理由回不去 | 确认回答者可插拔（人 / 审批 Agent / 无回答者）；`automation` lane 落地；审批 Profile；拒绝理由回传；缓存写入准入收紧；裁决过程落盘与可检索（审计 + 复盘） | 块 1 | 方案已成型 |
| 3. 嵌套调用（SubAgent） | §4.4：没有嵌套执行域，没有隔离与上界 | 嵌套调用 + 独立 transcript + 结果回灌；隔离域逐项声明；深度 / 并发 / 预算上界；事件归属先收敛为父工具进度 | 块 1、块 2 | 待启动 |
| 4. 无窗口运行与管家 Agent | §4.1、§4.5：窗口是运行前提；管家 Agent 无处落地 | 生命周期线解绑 + 驱动权归主进程 + 通知出口语义；**跨调用准入与配额**（并发 / 速率 / 优先级，见基线 §5）；Profile 化调用（模型 / 工具 / Skill / 策略档 / 会话域）；两个管家 Profile（远程 / 自动化） | 块 1、块 2 | 待启动 |
| 5. 长期运行（Run 层） | 跨回合、跨重启、自主续跑的运行体 | Run 身份 + 续跑驱动 + 运行域隔离 + 停放 / 恢复 | 块 1 ~ 4 | **待定，可能不做** |

**推进顺序**：块 1 先行，它是其他所有块的公共前置；块 2 与块 1 可以并行；块 3、块 4 都依赖块 2（子 Agent 的确认与管家的自动决策走的是同一条通道）；块 5 只在实测证明「单次托管超过分钟级 / 必须跨重启续跑」时才做。

**为什么块 5 可能不做**：管家 Agent 的单次托管是分钟级 Turn，任务定义是配置数据，触发即起 Turn —— 不需要任务状态机，也不需要 Core 内建调度器。

**为什么块 2 和块 4 不能分开做**：审批 Agent 本身也是 Core 的调用者，它和管家 Agent 需要的是**同一条**「一次调用能携带自己的配置」的能力，两条业务在这里合流。

**为什么是改造而不是重写**：上面四块都在现有代码上原地推进，不做产品级重写。成本对比、证据与「原地换心」的推进顺序见 `rewrite-vs-refactor-cost-assessment.md`。

## 7. 明确不做（非目标）

- 不重写工具框架与 registry，只加「能力集」的声明入口。
- 不重写产品与业务纵深（工具 / MCP / IM 协议 / 界面 / 存储 schema），不按蓝图推倒重来；可整体重写的范围仅限 Core 的内部实现（理由与成本对比见 `rewrite-vs-refactor-cost-assessment.md`）。
- 不引入第二套 Mission / Run 生命周期。
- 不为后台能力放宽确认默认值：新增的只有「逐条由 Agent 判断」这一中间档。
- 不允许任何 Agent 绕过策略层。
- 不把 UI 事实流改造成通用事件总线，只做出口抽象与归属字段。
- 不做分布式调度、跨设备恢复、运行中后端切换。
