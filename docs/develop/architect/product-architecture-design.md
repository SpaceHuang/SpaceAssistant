# SpaceAssistant 产品架构设计与规划（理想态）

> 定位：本文阐述 SpaceAssistant 的**架构理想态** —— 产品要支撑什么、主进程分哪几块、每块负责什么、对外接口是什么、今天差在哪、往哪走。它是方向共识，不是具体方案。
> 上游（业务预期、当前问题、工作块与优先级）：`docs/develop/architect/agent-core-roadmap.md`。
> 下游（具体方案）：`agent-core-roadmap.md` §9 的方案清单，已完成的如 `docs/develop/architect/confirmation-answerer-and-auto-approval-design.md`。
> 参考（外部实现的对照研究，非基线）：`docs/develop/architect/codex-architecture-comparison-and-learnings.md`（Codex）、`docs/develop/architect/dsh-architecture-comparison-and-learnings.md`（DeepSeek Harness）、`docs/develop/architect/claude-code-architecture-comparison-and-learnings.md`（Claude Code）；三家横向汇总见 `docs/develop/architect/three-products-architecture-benchmark-summary.md`。
> 引用约定：`roadmap §N.M` 指规划文档的小节；不带前缀的 `§N` 指本文小节。
> 状态：待评审 ｜ 基线：工作区 HEAD ｜ 摸排日期：2026-09-12

**一句话**：Agent 能力 = **一个内核（Core）加若干装配层与驱动源**。Core 只做一件事：给定这次要什么（session / messages / profile / limits）、结果往哪里说（events），跑完这一次调用。它不认识业务身份、数据库、窗口；桌面界面、飞书 / 微信、定时器、事件源都只是**调用者**，不是宿主。

**为什么现在要做**：接下来要落地的三类能力 —— 自动审批、SubAgent、后台（管家）Agent —— 都需要**可独立发起、可无窗口、可嵌套的 Agent 调用**；而今天的 Core 把「跑一次 Agent」等同于「跑一轮会话回合」。所以这一轮不是加功能，而是**把 Core 的调用方式打开**，让不同调用方复用同一套推理循环、工具框架、确认机制与审计。

**怎么读**：§1 目标与不变量 → §2 全景与主干分层 → §3 – §8 自上而下逐层展开（进程边界与界面交互 → 驱动源 → 装配 → 内核 → 安全 → 存储）→ §9 哪些是承诺、哪些可以改 → §10 今天与理想态的偏差清单（含「前置 → 后置」依赖列，重构规划直接按它排期）→ §11 Agent SDK 化的差距（对照分析，供复用规划引用）。

## 1. 产品目标与架构不变量

### 1.1 要支撑的形态

| # | 形态 | 目标 | 架构落点 |
| --- | --- | --- | --- |
| 基线 | 桌面 Agent | 用户在桌面界面发起对话、多轮工具调用、确认卡片实时交互；界面既是发起方，也是结果的观察者 | §3、§4、§6.2 |
| A | 自动审批 Agent | 需要确认的工具调用由 Agent 依据事实自动裁决，而不是弹卡片等人 | §7.2、§5.2 |
| B | SubAgent | 主 Agent 通过工具调用派生一个子 Agent，独立上下文与模型，结果回灌父上下文 | §6.2、§5.4 |
| C1 | 纯后台 Agent | 托盘 / 无窗口状态下 Agent 照常运行，界面只是观察者 | §4.1、§3 |
| C2 | 后台管家 Agent | 远程指令托管 + 定时 / 事件任务托管（C1 的业务载体） | §5、§8、§4 |

**桌面形态是基线，不是特例。** 它是今天唯一在跑的生产形态，A / B / C1 / C2 都相对它定义；但 §1.2 的六条不变量对它**同样生效** —— 它只是多了一个观察者，不是多了一套规则。

**它也是耦合最重的一处，根因在形态本身**：桌面是唯一「驱动源与观察者重合」的形态，同一处界面既发起回合又承接结果，「谁发起」与「往哪画」混成一件由渲染进程掌管的事，驱动权滑向渲染端。§10 偏差 1、9、11、12 全部落在这一形态上；拆解见 §4.1，结论见 §4.1「为什么这个切法不只是分类学」。

需求细节、优先级与工作块划分见 `roadmap §1`、`roadmap §5`。本节只有一条用意：**这些形态都不该让 Core 里多出一个 `if`** —— 它们的差异全部落在「带什么配置、谁发起、记在哪、给谁看」。

### 1.2 六条架构不变量

全文的「宪法」，后面每一节都是它的展开：

1. **一次调用可独立发起**：不要求窗口、不要求用户在场、不要求它是某个用户回合的一部分。**但会话仍然要有**，它是归属与落盘的载体；且**「会话」不等于「用户会话」** —— 归属与可见性是两个维度，内部调用有自己的会话，只是归属 `internal`、可见性 `hidden`。真正禁止的只有两件事：会话与窗口、回合的存活绑死；「会话只能由用户消息催生」。（今天的反例：`sender` 必填、窗口存活决定回合存亡，见 §10 偏差 1；展开见 §6.2）
2. **Core 不认识业务身份**：审批 Agent、SubAgent、管家 Agent 都是调用方，不是 Core 的变体。
3. **安全门控不可绕过，标准只有一套**：判定顺序、fail-closed 兜底、底线规则不接受配置替换；「谁回答确认」可插拔，且与「从哪个入口进来」正交（§7.2）。**父级的审批不向子调用泄漏**：子调用的放行集合是**替换**而非继承，父批过的那一次不构成子那一次的授权。这是「授权维度一律不继承」的一个取值，完整元规则见 §6.2（§7.1）。
4. **可见性不由 Agent 自己声明**：Agent 只声明归属意图；能不能进用户会话列表、能不能被跨会话搜索到，由宿主与存储决定（`roadmap §1.4`）。
5. **内部调用是证据与输入，不是授权**：审批 / SubAgent 的记录必须落盘（安全审计加 Agent 自我优化），但「上次批过」不构成「这次批准」（`roadmap §1.5`）。
6. **先持久化，再投递（只约束终态与结果，不约束过程性事实流）**：需要送达、可重试、可补投的东西 —— 消息终态、调用结果、汇报通知 —— 必须先落盘再投递。投递不可达不等于失败：投递是驱动源路由，Agent 只声明意图（§4.2）。**过程性事实流（工具活动、文本与思考增量、进度心跳）不受此约束**：直接投递，不以落盘为前提，投递侧允许丢失。判据是「丢了会不会损害真相」—— 它们的终态会落盘，视图可由失效通知重取快照（§4.4、§5.5）。
   **「不丢」不等于「一定被看到」**：落盘保证结果永远可查，投递只是尽力而为。所以补投必须**有界**（带 TTL、被更新结果取代、送达后不重复），否则「不丢失」会变成「无限打扰」（§4.2）。

## 2. 全景视图与主干分层

### 2.1 一张图：两个进程，三层内容

```text
外部世界   用户操作 ｜ 飞书 / 微信消息 ｜ 定时器 ｜ 事件源
                          │
渲染进程   界面交互层
           ├─ 驱动源界面：对话流 · 确认卡片 · 运行态与进度 · 会话列表
           ├─ 业务界面：文件树 · 搜索 · 设置 · Wiki · 浏览器 · 终端
           └─ 外壳窗口（只承载界面，不决定归属）：主窗口容器 · 标题栏 · 浮动通知窗口
                          │  preload → window.api（唯一桥）
           IPC 协议   A. Agent 驱动协议（发起 / 取消 / 确认回执 / 事实投影）
                      B. 业务功能协议（文件 / 搜索 / 设置 / 会话 CRUD）
                          │
主进程     Agent 模块（六块主干）
           Driver ──▶ Runtime ──▶ Core
              │           │          │
              └──────▶ Storage ◀──── Safety
           Utils：日志 · 脱敏 · 路径安全 · 加解密 · i18n · 纯逻辑
           出口实现（归属 Runtime，不是驱动源）：floatingNotification · safeWebContentsSend

           业务模块（应用域的主进程侧能力，与 Agent 正交）
           文件 · 搜索 · 设置 · Wiki · 浏览器 · 终端 · 会话备份导出

           外壳（Electron 强制在主进程，属 Driver 的实现）
           BrowserWindow / Tray / Menu
```

**读法**：从上到下是「意图 → 协议 → 主干」的推导顺序，不是调用顺序；协作顺序见 §2.3。主进程有**两条并列的线**：Agent 模块（六块主干）与业务模块，后者不参与 Agent 回合。窗口外壳虽画在主进程，但与渲染进程的界面同属**一个驱动源**（§4.1）；其中只有**窗口 / 托盘 / 菜单**属它，**浮动通知**虽被同一 Electron 约束塞在主进程，却是**出口实现**，归 Runtime（§4.1 模糊地带）。

### 2.2 三层内容的定位

| 层 | 定位（一句话） | 承载 | 例子 | 归属 |
| --- | --- | --- | --- | --- |
| **界面交互** | 表达用户意图、渲染结果；**不做决定** | 渲染进程（外壳窗口在主进程） | 对话流、确认卡片、文件树、设置页、托盘菜单 | Driver 的界面部分 加 业务界面 |
| **业务逻辑**（应用域） | 与 Agent 正交的产品功能，各自有界面与主进程侧能力 | 渲染进程的业务界面 加 主进程的业务模块 | 文件浏览、跨会话搜索、设置、Wiki、浏览器、终端 | **不属于六块中的任何一块**（§3.2） |
| **主干**（六块） | Agent 能力的骨架：谁发起、装配什么、怎么执行、安不安全、记在哪 | 主进程 | Core / Safety / Runtime / Driver / Storage / Utils | 见 §2.4 |

**一个重要区分**：审批 Agent、SubAgent、管家 Agent **不是新增业务逻辑层**，而是主干的使用方式 —— 差异全部落在「配置什么、谁发起、记在哪、给谁看」（§1.1）。**主干不为任何业务形态加分支**，这是可复用性的全部来源。

### 2.3 协作关系：一次回合经过哪些块

以「用户点发送」为例，六块依次上场；括号里是同一位置的其它驱动源：

1. **意图产生**（渲染进程，或飞书 / 微信、定时器、事件源）：用户点发送，只表达意图（发了什么、点了什么），不决定用哪个模型、哪些工具、要不要确认。
2. **进入主干**（Driver）：桌面走 IPC 驱动协议，远端走 IM 网关，定时 / 事件由主进程内的触发源直接进入。Driver 负责入站解析与身份归属（哪个输入方、映射到哪个会话域与 Profile）。
3. **准入与装配**（Runtime）：先按全局并发、速率与配额**准入**（§5），再解析 Profile（模型档 / 工具能力集 / Skill / 策略档）、解析模型与服务凭据、装配事件出口实现，产出**一个 Invocation**（§6.2）。**Driver 不直接调 Core**（§4.3）。
4. **执行**（Core 加 Safety）：Core 按会话锚点经 `loadContext` 装载历史并装配上下文（§6.2），跑推理循环；每次工具调用都经过 Safety 的门控（规则 → 缓存 → 回答者），安全审计独立落盘。
5. **观察与落盘**（事件出口加 Storage）：执行中的事实经出口流出（无窗口时 no-op，不影响执行），会话台账与内部调用记录由 Storage 落盘。
6. **回投**（Runtime 加 Driver）：调用返回 `InvocationResult`，Driver 按投递路由把结果送回发起方或最近可用入口；视图更新走失效通知（§4.4）。

**三条推论**：

- **界面只是观察者**：第 2 步之后就没有界面参与。无窗口、纯后台、远端触发走的是同一条链路 —— 这也是「窗口关闭不等于回合失败」的由来（§4.1、§3）。
- **审批 Agent 与 SubAgent 不新增链路**：它们分别落在第 4 步的「回答者」与「嵌套调用」位置，复用同一条链路、同一套策略与审计（§7.2、§5.4）。审批 Agent 两者兼具：它在回答者位置上**发起一次嵌套调用**，这是全文唯一一条「判定路径回到 Core」的边（§2.6、§7.2）。
- **业务模块不在链路上**：文件浏览、搜索、设置等由界面直接调用主进程的业务模块，不经过 Agent；只有当 Agent 把它们当工具使用时才进入链路（§3.2）。这也是「用户直接操作界面不经过工具门控、Agent 调用必须经过」（§3.4）的由来。

### 2.4 六块主干与职责

「Core / Runtime / Utils」三分是主轴，展开后是六块 —— 其中两块必须单列，一块要再切一刀：

| 层 | 职责 | 判据 | 今天对应的代码 |
| --- | --- | --- | --- |
| **Core**（Agent 内核） | 推理循环、上下文装配、工具执行、事实与事件产出、执行预算与取消 | 换了它，执行语义就变了；对外只暴露 Invocation | `toolChatLoop.ts`、`tools/`、`assistantFactAggregator`、`sessionEvents` |
| **Safety**（安全与审计） | 策略引擎与门控、确认通道解析、缓存写入准入、审计落盘 | **不可被 Runtime 的配置绕过**；策略内容在外，底线在此 | `src/shared/policy/`、`confirmation/`（含审计日志与读取器） |
| **Runtime**（准入与宿主装配） | **准入**（并发 / 速率 / 配额），加把宿主的东西装配成一次 Invocation：Profile 解析、Tools 与 Skill 供给、模型与服务解析、事件出口实现、Turn 协调 | 只回答「这次能不能跑、带什么、过程往哪里说」 | `turnExecutionConfig.ts`、`effectiveTools.ts`、`skills/`、`llmServiceResolver.ts`、`turnRuntime` / `turnCoordinator`；**出口实现的雏形**：`floatingNotification*`、`safeWebContentsSend`（见 §4.1 模糊地带） |
| **Driver**（驱动源） | 四类发起者：桌面界面、远端输入方、定时、事件；各自负责「怎么收指令、结果怎么回去」 | 只回答「谁发起、何时发起、结果给谁」 | `main.ts`、`tray` / `menu`、`appIpc.ts` / `preload.ts`、`feishu/`、`wechat/`、`remote/` |
| **Storage**（持久化） | 会话与消息（含内部会话 / 内部调用记录）、安全审计文件、决策缓存 | 语义敏感：归属、可见性、只追加、保留期 | `database/`、`sessionBackupManager` |
| **Utils**（支撑） | 日志、脱敏、路径安全、加解密机制、i18n、纯逻辑与类型 | 删掉它不影响语义，只影响质量或便利 | `agentLogger/`、`logSanitize`、`pathSecurity`、`secureApiKey`、`src/shared/` 纯逻辑、i18n 机制（见下方「横切关注点」） |

**关于应用域**：文件浏览、搜索、设置、Wiki、浏览器、终端**不属于以上任何一块**，它们是桌面应用自身的业务功能（§3）：界面上是**业务界面**，主进程侧是**业务模块**。一部分与 Core **共享底层能力**（文件读取既是文件树界面的能力，也是 Core 的工具），但共享能力不等于同一层。

**关于横切关注点（i18n / 日志 / 脱敏）**：它们同时带着「机制 + 内容 + 状态」三种成分，**不该单列成一层**，否则三种判据不同的东西混在一起。§2.5 只看机制那一半，内容与状态另有归属：

| 关注点 | 机制（Utils：删掉只损失质量或便利） | 内容（数据：随产品与领域变化） | 状态（谁持有） |
| --- | --- | --- | --- |
| **i18n** | 渲染端 i18next：`t()`、类型推导、回退、`i18n:check`（`src/renderer/i18n/`） | 翻译资源，zh-CN 为真源（`src/renderer/i18n/resources/`）；主进程菜单**另有一份手写字典**（`src/shared/menuLabels.ts`） | 界面语言属 **Driver**：`config.locale`（`src/shared/domainTypes.ts:718`）加 `localStorage[sa_locale]` 两份副本；给模型 / 远端的输出语言属 **Profile 数据**，已随请求携带（`electron/toolChatLoop.ts:412`），仅缺失时回退查库（`:636`） |
| **日志** | 写盘、按日分文件、JSON Lines（`electron/agentLogger/`） | **事件名与字段的白名单**：事件名是闭合联合（`electron/agentLogger/types.ts:3`），字段经 `projectAgentLogFields` 投影 | 日志目录：开发态项目根 `logs/`、打包态 `{workDir}/.agent/logs`（`agentLogPaths.ts:15`、`:25`）；**目前没有保留期与轮转**（对照：会话台账有保留期，`electron/main.ts:391`） |
| **脱敏** | 通用净化与长度上限：`sanitizeForLog`、128KB 截断（`electron/logSanitize.ts`） | **按领域的字段规则**：飞书一套（`electron/feishu/feishuCliLogFields.ts`）、微信一套（`electron/wechat/weChatCliLogFields.ts`），写入前预处理 | 无独立状态：在**唯一写入入口**施加（`logAgentEvent` 先投影、再 `sanitizeForLog`，`electron/agentLogger/agentLogger.ts:83`） |
| **遥测 / 审计** | 审计写入机制：只追加、独立物理隔离、按天切分、写入前脱敏（`electron/confirmation/securityAuditLog.ts:14`、`:43`） | **事件名与字段口径**：审计事件类型（`confirm.request` / `confirm.outcome`，`src/shared/confirmation/types.ts:236`）与 `actor` 取值集合（`:233`）随合规口径变化 | 位置与保留期由 **Storage** 持有（独立文件、保留 180 天，`securityAuditLog.ts:48`）；判定与写入的接缝在 §7.2、§8 |

**三条规则**：

1. **主进程不产出「文案」，只产出「键 + 参数」**（i18n 的落点）。错误码已是对的样板：主进程抛 `src/shared/errorCodes.ts` 的码，渲染端用 `errorTranslator.ts` 翻译。需要主进程直接显示的地方（菜单、托盘、浮动通知窗口）走注入的 `translate(key, params)` 端口（§5.2），不再自建第二套字典。
2. **日志的内容是「事件名 + 字段」，不是自由文案**。这条今天已是对的，要守住：它让日志同时可审计、可脱敏、可做保留期；退回自由文本，三件事会一起坏掉。
3. **脱敏规则随领域走，机制只有一套，且必须在唯一入口施加**。新增领域（例如新的 IM 平台）只加一组字段规则，不加一套净化器；把净化交给每个调用点「记得调用」，等于把安全性寄托在记性上。

### 2.5 四条判据（决定一块东西该放哪层）

1. 换了它，执行语义或安全语义会变吗？会 → Core 或 Safety，**不可被配置替换**。
2. 它被调用方伪造，会越权吗？会 → 必须在 Core / Safety 侧有不可覆盖的校验。
3. 它只是「把宿主的东西装配成一次调用」吗？是 → Runtime；它决定「何时发起、结果给谁」吗？是 → Driver。
4. 删掉它，系统还正确吗（只损失质量或便利）？是 → Utils。

### 2.6 依赖方向（决定「能不能换」）

- **Core 不 import 任何宿主模块**：它只使用注入的端口（§6.2、§5.2）。
- **Runtime 是唯一的装配点**：Profile、Tools、Skill、模型解析、事件出口实现，都在这里装成一次 Invocation。运行期才发起的嵌套调用（SubAgent、审批）也不例外：装配期解析好的材料被收进一个「调用器」，运行期只填充本次参数（§7.2）。**Driver 不直接调 Core**（今天的 `feishu/`、`wechat/` 是反例，见 §4.3）。
- **Safety 在 Core 的判定路径上，不可绕**；但它读的「生效规则」随 Invocation 传入，自己不去读库（§7.1）。
- **Safety 只依赖端口，不依赖 Runtime**：确认回答者（`answerer`）的实现由 Runtime 在装配期注入。当回答者是「审批 Agent」时，该实现（块 2 方案的 `AgentChannel`）会在运行期发起一次**嵌套 Core 调用** —— 这是全文唯一一条「判定路径回到 Core」的边（§7.2 规则 5、`confirmation-answerer-and-auto-approval-design.md` §4.3）。
  它是**运行期递归，不是结构依赖**：Safety 看不到 Runtime、拿不到 Invocation，只看到一个 `ConfirmationChannel`，把人换成 Agent 它一行不改。递归有界靠两条：审批调用的工具集**封闭只读、在策略层显式免再审批**（否则会「审批套审批」）；轮数 / 深度 / 预算有上界（块 2 方案 §4.4）。**若豁免被配置破坏、深度上界触发，结论是 fail-closed 并落一条可区分审计**（`confirm.outcome` 的 `cause=recursion-blocked`）。它归**不可变集**而非 `locked` 底线集：`locked` 只拦放宽，拦不住收紧引发的停摆（§7.2）。
- **准入在 Runtime、配额状态在 Storage**：跨调用的全局约束（并发 / 速率 / lane 配额）不属于任何一次调用，不放 Core 的 `limits`；由 Runtime 在装配前施加，状态落 Storage（§5）。**嵌套调用同样过准入、不豁免**，但优先级按「谁在等它」定：同步依赖继承等待方的优先级且有界等待，可放弃的派生同权排队（§5）。
- **Storage 被 Core（经两个端口）、Safety、Runtime、Driver 共同使用**，它不反向依赖任何人（§8）。
- **Utils 可以被任何一层使用**，但不得持有语义。

### 2.7 三处最容易放错

- **Safety 不能放进 Runtime**。Runtime 是「改配置就改行为」的地方，而安全底线恰恰不能随配置改变 —— 放进去等于「配置可以关掉安全」。
- **Storage 不能算 Utils**。会话归属、可见性、审计只追加、保留期都是语义，不是便利设施；把它当 Utils，结果就是「顺手把审计也删了」。
- **桌面界面不能从 Driver 里单独摘出去**。窗口 / 托盘 / IPC 面是同一个驱动源的三个实现部分（§4.1）。

**一处今天的越界**：`electron/confirmation/toolCallGate.ts:185` 直接读数据库（`args.appDb ? loadEffectivePolicyRules(args.appDb, lane) : DEFAULT_POLICY_RULES`）—— Safety 因此依赖 Storage 与宿主配置，是「Safety 与 Runtime 混在一起」的表现。

## 3. 进程边界：主进程与渲染进程

主干之外还有两块：**界面交互**（渲染进程的界面，加被 Electron 强制放在主进程的窗口外壳）与**业务逻辑**（应用域）。定位见 §2.2，本节说清它们与主干的边界规则。

### 3.1 三个维度

先把三件被混在一起的事分开：

| 维度 | 回答的问题 | 决定什么 |
| --- | --- | --- |
| 特权 | 谁需要 OS 权限、密钥、文件系统访问 | **必须**在主进程（Electron 安全边界），这不是架构选择 |
| 职责 | 它属于六块中的哪一块（§2.4） | 它受哪些规则约束 |
| 承载 | 它实际跑在主进程还是渲染进程 | 实现位置，可迁移 |

### 3.2 四条边界原则

1. **特权决定「必须在哪里」，职责决定「属于谁」**。需要特权的能力放主进程；属于哪一层由职责决定。典型例子：文件读取既服务「文件树界面」，也是 Core 的工具 —— **同一份底层能力，两个消费者**。
2. **业务功能不属于六块中的任何一块 —— 它是与 Agent 正交的「应用域」**。文件浏览、搜索、设置、Wiki、浏览器、终端都是应用域，各自有界面与主进程侧能力。它们与 Agent 只有两种关系：**共享底层能力**，或**被 Agent 当工具使用**。
3. **渲染进程只有两类东西**：驱动源的界面（对话流、确认卡片、运行态）与业务界面（文件树、搜索、设置、Wiki、浏览器、终端）。**渲染进程不做决定** —— 不发起 / 排队 / 重试 / 取消，不拼系统提示，不自己跑技能路由；它只表达用户意图并渲染结果。
4. **IPC 面按领域切，不按实现方便堆在一起**。今天 `electron/appIpc.ts` 把 Agent 驱动协议与桌面功能堆在同一个文件里（§10 偏差 10）；目标是一个域一个协议模块，各自持有通道、类型与 preload 命名空间。

### 3.3 渲染进程面对的域与归属

| 域 | 归属 | 与 Agent 的关系 |
| --- | --- | --- |
| Agent 驱动协议（发起 / 取消 / 确认回执 / 事件投影） | Driver（桌面驱动源） | 是 Agent 的入口与出口 |
| 会话与消息 | Storage 的查询面加 Driver 的视图 | 真相在 Storage；列表按归属与可见性过滤 |
| 文件浏览 | 业务模块 | 与 Core 的 `read_file` / `list_directory` **共享底层能力** |
| 搜索 | 业务模块 | 同一套索引；跨会话搜索必须受归属与可见性约束（不能搜到内部调用） |
| 设置 | 业务模块 加 Safety 的配置面 | 安全档位变更要落审计 |
| Wiki / 浏览器 / 终端 | 业务模块 | 同时可能是 Core 的工具实现 |
| 托盘 / 菜单 / 标题栏（Electron 外壳） | Driver（桌面驱动源） | 用户点它是一次**输入**（发起来源）；外壳本身被 Electron 强制放在主进程 |
| 浮动通知 | Runtime 的出口实现 | **输出**，不是驱动源：它是「通知与进度」出口的一个实现（§5.5、§4.1 模糊地带） |

### 3.4 一条容易被争论的规则，以及交互的两个方向

**一条容易被争论的规则**：同一个能力被两个入口使用时，**用户直接操作界面不经过工具门控，Agent 调用必须经过**。理由不是「界面更可信」，而是安全模型的标的是 **Agent 的自主操作**：用户自己动手不等于 Agent 替他动手。

**渲染进程的信任级别**：它处在不可信边界（contextIsolation，只暴露 `window.api`），任何「渲染进程说了算」的地方都是安全缺口。目标形态下渲染进程只表达意图（发了什么、点了什么），所有决定回主进程。**今天还剩什么**（2026-09-16 复核）：只有**驱动权**（偏差 9）；这里原先举的两个例子 —— 渲染端为界面提示重跑一遍技能路由、残留一段拼系统提示的死代码 —— 已于 `9dfc46d1` 收回主进程，见偏差 12。**这不代表桌面确认回执不可信**，桌面通道的信任假设与校验见 §7.2。

**交互只有两个方向**：

- **主进程 → 渲染**：事实流、失效通知、确认请求、投递结果。
- **渲染 → 主进程**：用户意图（发消息、取消、批准或拒绝、切换会话、改设置）。
- **没有第三条**：渲染进程不得「查询之后自己累积成真相」（§4.4 规则 1）。

## 4. Driver：驱动源与接入协议

### 4.1 四类驱动源，桌面只是其中之一

「窗口 / 托盘 / 菜单被塞进主进程」是 **Electron 的约束，不是架构意愿**：`BrowserWindow` / `Tray` / `Menu` 只能在主进程创建。所以桌面驱动源由三部分组成：渲染进程的界面、主进程的窗口外壳、两者间的 IPC 协议 —— **三者是同一个驱动源的实现，不该与 IM 网关并列。**

真正的同级切法是**驱动源（Driver）**：回答「谁发起、何时发起、结果返回给谁」。一共四类：

| 驱动源 | 交互方式 | 今天在哪 |
| --- | --- | --- |
| 桌面界面 | 窗口、托盘、对话流 | 渲染进程（界面本体）加主进程（Electron 强制部分） |
| 远端输入方 | 飞书 / 微信消息 | 主进程（IM 网关、确认回执、进度回推） |
| 定时 | 无 | 主进程（待建） |
| 事件 | 无 | 主进程（待建） |

**IPC 面里其实混了两类东西**（今天都躺在 `appIpc.ts`，边界模糊）：

- **Agent 驱动协议**：发起回合、取消、确认回执、事件投影 —— 属于桌面驱动源的实现。
- **桌面应用功能**：文件浏览、跨会话搜索、设置、会话 CRUD —— 与 Agent 架构无关，是桌面应用自身的业务功能（§3）。

**为什么这个切法不只是分类学**（三条实际影响）：

1. **它决定驱动权归属**：桌面只是「一个驱动源」，那「谁发起回合」就不能由渲染进程独家持有（即 `roadmap §4.5`）。主进程必须是驱动权威，桌面只是它的一个客户端。
2. **它决定事件出口的语义**：只有把桌面当作「一个驱动源」，「无窗口时事件 no-op 或转投别的驱动源」才成立（§5.5）。
3. **它决定新入口的接入成本**：以后新增一个输入方（企业微信、Slack、HTTP API），只需要新增一个驱动源，Core 与 Safety 不动。

**一个模糊地带**：`floatingNotification` 与文件树刷新看着像「桌面专属」，但触发源可能来自任何驱动源（IM 触发的任务也要刷新文件树）。正确形态是**通知出口的一个实现**，由宿主按可用性选择（与 §5.5 一致）。它今天被放进主进程桌面外壳（`BrowserWindow` 只能在主进程创建）、§2.4 一度把它列在 Driver 行，都是**描述现状，不是归属**：它不发起调用、不接收指令，只往外投递通知，属**出口**（Runtime 的装配物）。**托盘与菜单不同**：用户点它是一次**输入**，那才是驱动源。

### 4.2 结果投递：一次驱动源路由

管家 Agent 执行完要「把结果汇报给用户」时，「推到哪」不是 Agent 或 Core 能回答的问题，它是**驱动源路由**。先分清三种投递目标：

| 目标类型 | 什么时候出现 | 路由难度 |
| --- | --- | --- |
| **回复型**（reply-to） | 远端任务托管：向输入方请求确认、回复结果 | 无 —— 发起者与回执通道都是确定的 |
| **指定型** | 任务配置写明「推到微信」或「只落盘」 | 低 —— 按配置走，不可用时按规则降级 |
| **路由型**（最近可用入口） | 自动化托管：定时 / 事件触发，没有发起者；或发起者已不可达 | 高 —— 需要可达性判定、降级链、补投 |

**分层：Agent 声明意图，宿主决定落点**

- **Agent / Skill 决定**「要不要汇报、汇报什么、什么优先级」—— 这是意图声明。
- **宿主（驱动源层）决定**「发给哪个驱动源、怎么发、失败怎么办」—— 这是投递路由。
- 所以接口是 `deliver(preference, payload)`：Skill 给偏好（给谁、多急），宿主解析成具体驱动源并执行。**Agent 不该知道 chat_id、窗口句柄这类东西。**

**核心不变量：先持久化，再投递（作用域：终态与结果）**

这条**只约束需要送达的终态与结果**（消息终态、调用结果、汇报通知）。**过程性事实流不受约束**（工具活动、文本与思考增量、进度心跳）：直接投递、不以落盘为前提、允许丢失 —— 判据是「丢了会不会损害真相」，它们的终态会落盘，视图可由失效通知重取快照（§4.4、§5.5）。把流式增量也纳入「先落盘」，等于把界面延迟绑在磁盘写上，而它不承载真相。

投递不可达不等于失败 —— 结果必须已经落盘（`roadmap §1.5`），然后：

1. 投递可重试，且需要**送达记录**（哪条结果、投给哪个驱动源、何时、结果如何），否则多入口会重复打扰同一个人。
2. 默认**单目标**；要向多个入口同时推送，必须显式声明。
3. 全部不可用时是「**延后补投**」而不是丢弃：用户下次出现在任一驱动源时补上。这才是「最近可用入口」的完整语义。

**「用户下次出现」需要三个前提，缺一个都会变成打扰**：

| 前提 | 要什么 | 缺了会怎样 |
| --- | --- | --- |
| **可达性信号** | 各驱动源上报自身可达性（在线 / 离线）与「用户出现」事件，投递层订阅 | 投递层只能猜「谁在」，或挨个试一遍 |
| **送达记录** | 哪条结果、投给哪个驱动源、何时、结果如何（见上） | 同一结果在多个入口重复送达 |
| **有效期策略** | 每条结果带 **TTL** 与**取代键** | 三天前的定时任务结果在用户开机时弹出 |

**有效期策略最容易被漏掉，因此提到不变量层面**：**「不丢」不等于「一定被看到」**。落盘保证结果永远可查（用户主动查也能看到），投递只是尽力而为，所以补投必须**有界**：

- **TTL**：超过有效期不再补投，标记为「未送达且已过期」并落审计（不是「失败」，结果并未丢失）。
- **取代**：同一取代键产生更新的结果时，旧结果不再补投（新的「今日股价」取代旧的）。
- **送达即止**：送达记录命中后不再补投。

**这三条必须由产生结果的一方声明，投递层不猜**：只有 Skill 与任务配置知道结果的有效期与取代关系（「构建失败」几小时内都有价值，「该开会了」过点即失效）。`deliver(preference, payload)` 要带上这份策略；**缺失时按显式声明的默认兜底**（有限 TTL）—— 与 §7.1「不得为缺失的托管值静默默认」同一条纪律。

**一个实现陷阱**：不要把「最近可用入口」做成「在 Runtime 里到处找 sender」。今天 `floatingNotificationManager` 与 `safeWebContentsSend(sender, ...)` 就是这样：投递点散落各处，没人能保证不重复打扰。正确形态是驱动源层暴露唯一投递入口，各驱动源注册自己的可达性与投递实现。
**与归属联动**：投递到桌面，结果要在一个可见的地方出现（管家会话分区可见）；投递到 IM，走回复通道。**投递目标决定结果落在哪，也就决定了会话归属与可见性的选择**，两者要一起定。

### 4.3 接入：路由、传递与决策往返

这一块天然压在几层的接缝上，分法是**「谁定语义、谁提供管道」**：

| 关注点 | 归属 | 今天的代码 |
| --- | --- | --- |
| 入站解析与身份归属（哪个输入方、映射到哪个会话域与 Profile） | **Driver** | `electron/remote/imInboundGuard.ts`、`imRateLimit.ts`、`imProcessedStore.ts`、`imSessionResolver.ts`、`imCommandRouterHelpers.ts` |
| 请求 → 一次调用的装配 | **Runtime** | `electron/remote/turnExecutionAdapter.ts` |
| 出站投递（可达性、重试、有界补投、送达记录） | **Driver** | `electron/remote/imRemoteOutbound.ts`、`remoteProgressCoordinator.ts` 与平台适配器 |
| 传输细节（限流、去重、退避） | **Driver 的实现**，通用部分下沉 **Utils** | `imRateLimit.ts`、`imProcessedStore.ts` |
| 决策请求的语义（问什么、谁能答、多久过期） | **Safety** | `electron/remote/remoteConfirmPolicy.ts`、`confirmId.ts` |
| 回执管道（把回答带回来） | **Driver** | `pendingRequestRegistry.ts`、`imConfirmReply.ts` |
| 回执的真实性与有效性校验 | **Safety**（不可外置） | 今天散在 `remoteConfirmPolicy` 与 `remoteWriteAuthorization` |
| 审计 | **Safety** | `imAuditLogger.ts`、`remoteSessionSwitchAudit.ts` |
| 预算与中断 | **Safety 定限权**，Runtime 与 Driver 施加 | `remoteTaskBudget.ts`、`remoteTaskController.ts` |
| 写授权与租约 | **Safety** | `remoteWriteAuthorization.ts`、`remoteWriteGrantRegistry.ts` |

**一条接缝上的规范**：**Driver 不直接调 Core**。今天 `electron/feishu/feishuRemoteAgent.ts:46` 与 `electron/wechat/weChatRemoteAgent.ts:48` 直接调 Core 的 `runToolChatSession`，跳过 Runtime 装配，代价是每加一个平台就复制一遍装配逻辑（模型、工具集、策略档各自凑）。新驱动源（定时 / 事件 / 新 IM）必须走 Runtime 装配。

### 4.4 视图更新：事实、失效通知与界面语义

「消息列表要不要刷新」这类问题今天混了三条不同的路径，分开就清楚了：

| 关注点 | 归属 | 形态 |
| --- | --- | --- |
| 发生了什么（工具活动、增量、usage、终态） | **Core 产出，Runtime 投影** | 事实流（带序号，可重放） |
| 有哪些会话、哪些消息（真相） | **Storage** | 按归属与可见性过滤的查询 |
| 怎么排序、怎么分组、怎么显示 | **Driver（界面）** | 视图语义，Runtime 不该知道 |
| 「需要重新查了」 | **Runtime 的统一出口** | 失效通知（scope 加版本，不携带真相） |

**三条规则**：

1. **事实流不承担列表真相，只承担变化通知**。渲染端不该从字节流里自己累积出「真相」（今天的病根之一）。事实流只说明「某会话的某 turn 变了」（带序号）；Driver 收到后按序号合并，序列断裂就取快照补齐。序号与版本的分工见下。
2. **失效通知与内容投递分开**。把结果送到用户面前（§4.2）和让各 Driver 的视图与 Storage 保持一致是两件事。失效通知是**广播**，只带 scope 与版本（如 `session-list`、`session:<id>`）；Driver 收到后自己去 Storage 取。真相只有一份，不会在 N 个 Driver 之间复制。
3. **不要让 Core 产出 UI 语义事件**（例如 `session-list-changed`）。那等于把宿主的视图模型塞进内核 —— 会话列表是**应用概念**，Core 只认识「一次调用的过程与结果」。

**版本号的权威源要定死**，否则「跳号重取」在多驱动源、多窗口下会变成频繁全量重取。上表里的「序号」与「版本」是两个不同的号，别混：

| 号 | 属于谁 | 权威源 | 怎么用 |
| --- | --- | --- | --- |
| **事实流序号** | 一次调用的过程序列 | **会话台账**（已落盘的事实流） | 用于**重放与对齐**：序列断裂说明这次没跟上，取快照补齐 |
| **scope 版本** | 存储里的一个查询域（`session-list`、`session:<id>`） | **Storage**，在事务内递增 | 单调即可，**只比较、不要求连续** |

**Driver 侧的动作是「版本比较」，不是「跳号判定」**：Driver 持有「我上次读到的版本」，通知版本更高就重取，否则忽略。丢一条通知**不会漏**（下一条版本更高，仍会触发重取），收到多条**也只重取一次**（版本相同即忽略）。版本号有唯一权威源（Storage），本来就不需要连续。

**今天的形状**（2026-09-16 复核）：**turn 这一层已经落地** —— `TurnDisplay` 自带版本号（`src/shared/turnDisplayProtocol.ts`），`chat:get-turn-displays` 按「我读到的版本」只回差量，`chat:get-pending-confirmation` 走独立快照链路、与普通展示分流，历史分页 `chat:get-display-message-page` 从 Storage 取；事实侧仍由 `chat:turn-projection` 推送（`electron/main.ts:368`、`src/renderer/services/turnProjectionService.ts`），会话台账另一路落盘（`electron/sessionEvents.ts`）。**还没收敛的是列表与失效通知**：会话列表仍靠**拉全表**（`electron/database/operations.ts:119`），UI 失效通知仍**直连**（文件树刷新、工具面变更走 `safeWebContentsSend`）—— 把后者收敛成「失效通知」这一种出口形态，就是偏差 11 剩下的那一半。

**一条判据**（决定某段 UI 更新逻辑放哪）：

- 只需要知道「有变化」→ 走出口通知（Runtime）
- 需要知道「变化成什么」→ 查 Storage，或读投影快照
- 决定「怎么显示 / 排序 / 过滤」→ Driver

## 5. Runtime：准入、装配与定制入口

Runtime 回答**三个**问题，顺序也是它们发生的顺序：

1. **这次调用能不能跑**（准入）：并发、速率、配额。
2. **这次调用带什么**（装配）：Profile / Tools / Skill / 模型解析。
3. **过程往哪里说**（出口）：事件出口实现。

**准入是这一轮新增的一层，也是最容易漏掉的一层。** `Invocation.limits` 管**单次调用内**的上界（轮数、时长、单次 token、**调用内并发**）；**跨调用的全局约束**（同时跑几个后台 Agent、总 token 速率、每个 lane 的配额）不属于任何一次调用，必须有公共前置，那就是准入。**没有它，管家 Agent 加定时与事件源一上线就会爆**：多个定时任务同一分钟触发，单看都「合法」，合起来把配额和机器打满。

| 层 | 管什么 | 谁施加 | 状态 |
| --- | --- | --- | --- |
| 单次调用内 | 轮数、时长、单次 token 上界、**调用内并发**（工具并发与子调用 fan-out） | `Invocation.limits`，Core 施加 | 随调用，不持久 |
| **跨调用全局** | 并发数、速率、lane 配额 | **Runtime 的准入**（新增） | **Storage**：跨重启不丢 |
| 触发时刻编排 | 定时、事件、重试节奏 | Driver（触发源） | 配置数据 |

**为什么是 Runtime，而不是 Driver、也不是新增一层**：所有调用都经过 Runtime（§2.6 的唯一装配点），它是唯一的公共前置。Driver 是**多个并行驱动源**、没有中心，全局判定放进去会变成「各驱动源各判一次」的竞态；新增一层「Scheduler」也要先回答「谁调用它」，答案仍是「Runtime 调」，等于多一层转发。**它与「谁发起」（Driver）是两件事**：Driver 决定「要不要发起」，Runtime 决定「发起之后现在能不能跑」。

**四条硬要求**：

1. **准入不判定安全**。它只回答「现在能不能跑」，不回答「这次该不该放行」—— 后者永远是 Safety 的事（§7.1）。两者必须分开，否则「配额不够」会被误当作「拒绝授权」，审计口径立刻失真。
2. **交互式优先于后台**。用户在前台点发送的调用，不该被后台 Agent 排队挡住 —— 这是**优先级**而不是先来先服务（先到先服务只在同优先级内成立，§6.2 认领语义）。
3. **不能静默丢弃**。处置只有四种且必须由调用方声明：**排队**（等一会儿）、**延后**（下一个触发时机再来）、**降级**（换更省的 Profile）、**拒绝**（落审计）。默认行为必须显式，不允许「取不到配额就悄悄不跑」（同 §7.1 的纪律）。
4. **可观测**。排队与拒绝要落审计或事件出口，否则用户无法回答「我的定时任务为什么没跑」。

**嵌套调用也要过准入，但优先级不按「谁发起」定，按「谁在等它」定。** 审批回答者与 SubAgent 都是运行期才发起的嵌套调用（§2.6），**不豁免准入**：它们是真实的模型调用、有真实成本，而且可被触发（构造大量需要审批的工具调用就能打爆配额）。豁免等于给安全路径开资源后门，也违反「所有调用都过 Runtime」。两类的等待语义不同：

| 嵌套调用 | 例子 | 准入语义 |
| --- | --- | --- |
| **关键路径上的同步依赖** | 审批回答者（`invokeApproval`） | 优先级**继承正在等待它的那条调用**（交互式等就是交互式，后台等就是后台）—— 不提升也不降级，避免后台的审批插到前台用户前面（硬要求 2 的推广）。**有界等待**：超出上界即视为「拿不到裁决」，不能让一条工具调用无限期挂在准入队列里（上界随 Profile 声明，与轮数、预算同处一处，§5.4） |
| **可放弃的派生** | SubAgent、工具内派生调用 | **同权排队**。被拒时把「资源不足」作为**工具结果**回灌父调用，让父自己换方案（缩范围 / 换工具 / 报告用户），而不是整条调用失败 |

**准入拒绝永远不构成安全结论**（硬要求 1 的推论）：审批调用拿不到配额时，Safety 得到的事实是「**无法获得裁决**」，不是「裁决为否」。审计上两者必须可区分（`confirm.outcome` 的 `cause=unavailable` 对 `cause=agent-deny`），否则「配额不足」会被统计成「审批判定危险」，安全指标与审计口径同时失真。处置仍是 **fail-closed**（工具调用被拒），不存在「拿不到裁决就放行」；但不接受**静默** fail-closed：必须落审计，并给调用方**可区分的理由**（同硬要求 3、4）。原因拆开后，「该自动批却被拒」就从模糊抱怨变成可定位、可告警的准入事实。

**自锁风险必须提前定**：同步依赖是由一条**正占着配额**的调用派生的。若全局并发上界是 N，而 N 条调用同时等各自的裁决，谁都拿不到位，全体互锁。准入必须自带回旋机制，二选一：给同步依赖留**保留位**（并发上界中划出固定份额），或让调用在等待裁决期间**让出**已占的位。缺了这条，管家 Agent 一上量就会「全都在等审批、全都没在跑」地假死，而且是静默的。

定制入口的原则是：

> **能用数据定制的，不开放成 Hook。** 定制优先走数据（Profile / 规则 / Skill / 工具声明）；只有「必须由外部提供实现」的地方才开放端口。回调越多，行为越难推理、越难审计，而审计与安全是这套 Core 的第一约束。

### 5.1 声明式数据（首选：加数据，不加代码）

| 扩展点 | 定制什么 | 形态 | 现状 |
| --- | --- | --- | --- |
| Profile | 模型档、工具能力集、Skill 加载声明、system 附加、策略档（lane） | 配置数据，随调用携带 | 缺（`roadmap §5` 块 1） |
| PolicyRule | 什么条件下 allow / ask / deny / confirm-every-time | 声明式规则 + DB 覆盖 | 已有（`policy_rules` 表）；里外拆分见 §7.1 |
| Skill | Agent 的行为逻辑：怎么想、按什么步骤做 | Markdown 技能 + 硬规则加载 | 已有，硬规则缺「按 Profile 指定」一档 |
| 工具声明 | 有哪些工具、默认开关、对谁可见 | 配置 + 注册表 | 已有 |

**管家 Agent 就是这条路的样板**：它不写新代码，只是「一份 Profile + 一个 Skill + 一组自己的工具 + 一个自己的会话域」的调用方。

### 5.2 注入式端口（必须由外部给实现）

| 端口 | 谁实现 | 语义约束 |
| --- | --- | --- |
| `events.*` | 调用方 / 宿主 | 只观察，不改变判定；允许全部 no-op |
| `factsProvider` | 宿主（可选） | **只补充事实**（宿主才知道的上下文：页面状态、会话位置、最近的相关操作），不产出结论 |
| `answerer` | Runtime 装配实现，Safety 按 Profile 与 lane 解析选择 | 只在规则与缓存都未命中时被咨询；结果仍要过缓存准入、审计与 fail-closed。实现可以是人（桌面 / IM），也可以是**一次嵌套 Core 调用**（审批 Agent，§7.2） |
| `ToolExecutor` | 工具层 | 进程级注册；执行结果仍过结果契约校验（`electron/tools/types.ts:164`） |
| `getApiKey` / 模型解析 | 宿主 | 按调用解析凭据与服务，不落日志（`electron/toolChatLoop.ts:409`） |
| `loadContext` | 存储适配器 | **只装载不装配**：按会话锚点返回已有历史与可寻址材料（未经裁剪的原始材料）；裁剪与注入在 Core（§6.2、§8） |
| `persist` | 存储适配器 | 桌面会话 / 内部会话（审批、SubAgent）/ 管家会话域三选一（`roadmap §1.4`、`roadmap §1.5`） |
| `translate` | 宿主（持有界面语言的一端） | 只做「键 + 参数」到文案的映射；主进程不硬编码文案（§2.4 横切关注点） |
| `limits` / `signal` | 调用方 | **单次调用内**的预算与取消，Core 只负责施加；跨调用的全局配额不在这里，见 §5 导言的准入 |

**「给审批看什么」要拆成两半**，因为来源与时机不同：

| 一半 | 谁提供 | 时机 | 内容 |
| --- | --- | --- | --- |
| 工具自述的审批可见输入 | **工具声明**（不是端口） | 装配期，随工具注册 | 这个工具被确认时该呈现什么：目标路径 / 命令 / 影响面。**声明为空表示「本工具无安全相关性」，必须与「忘了声明」可区分** |
| 宿主补充的事实 | `factsProvider` 端口 | 运行期注入 | 宿主才知道的上下文：页面状态、会话位置、最近的相关操作 |

为什么不合并：前者属于**工具契约**（换工具就换），后者属于**宿主环境**（换宿主就换）；合在一起，工具作者要为宿主上下文负责、宿主要替每个工具补参数，两边都做不好。**审批看到的必须是两半的并集，且标注每一项来自哪一半** —— 审计要能回答「这个结论是基于谁提供的事实」。

### 5.3 分层开放：开放装配与观察，不开放判定与改写

定制入口不是「开放或不开放」的二元选择，而是**四层**，越往下越慎：

| 层级 | 形态 | 判据 |
| --- | --- | --- |
| **声明式数据**（首选） | Profile / PolicyRule / Skill / 工具声明 | 加数据不加代码；改完可枚举、可审计（§5.1） |
| **注入式端口**（受控开放） | §5.2 的九个端口 | 必须由外部给实现，且实现只做三类动作：补事实、给实现、报事实 |
| **事件回调**（受约束开放） | 工具调用前后、确认请求三类 | 见下方五道约束；不接受自定义事件名 |
| **写死**（不开放） | 见本节末尾三条 | 一动就等于安全语义或执行语义变了（§2.5 判据 1） |

**五道约束**（任何开放的 Hook 必须同时满足）：

1. **声明式**：配在 Profile / 配置数据里，不是代码注入；谁的定制在生效，必须能从配置读出来。
2. **事件集固定且可枚举**：只接受闭合清单里的事件名（§5.5），不接受自定义。
3. **进程外优先**：能走外部命令（stdin / stdout）解决的就不要进内核进程 —— 隔离故障与信任边界。
4. **schema 校验加能力位**：入参必须校验；Hook 能拿到哪些字段、能不能影响流程，由能力位决定，且**默认最小**。
5. **冲突与顺序显式**：多个 Hook 同时命中时的裁决顺序固定、可测、并落审计，不靠注册先后。

**永不开放（写死）**：

- **安全门控本体**：判定顺序（规则 → 缓存 → 回答者）、fail-closed 兜底、缓存写入准入都不接受替换。
- **上下文装配顺序**：裁剪与注入规则必须与 `docs/develop/context-injection-refactor-plan.md` 同源，不允许调用方自己拼一份（今天渲染端还留着这样一段遗留代码）。
- **可改写的生命周期 Hook**：不提供 `onToolCallStart → 改写参数` 这类回调。要改工具行为就换或包一个 `ToolExecutor`；要改「怎么想」就改 Skill。

**不开放改写的理由**：参数一旦被改写，「历史记录 / 审计 / 界面 / 实际执行」四者就不再一致，「这次执行是谁改的」无法回答。行为定制必须落在可枚举、可审计的地方 —— 这也解释了为什么「观察」可以开放而「改写」不行。

以上规则今天唯一的反例是 `AutoEvaluator`：它让外部**直接给出结论**（同步返回 `{approve}`、按工具名写死，`src/shared/confirmation/types.ts:295`、`electron/confirmation/toolCallGate.ts:336`），违反的正是「注入式端口只做补事实、给实现、报事实三类动作」。目标形态：拆成 `factsProvider` 补事实、`answerer` 在末端受控给结论（§5.2）。

### 5.4 模型与思维强度：档位是数据，服务与凭据是端口

| 内容 | 层 | 形态 |
| --- | --- | --- |
| 选哪个模型（角色档 / 具体 model id） | A. Profile 数据 | `profile.model = { role: 'fast' ／ 'standard' ／ 'strong', modelId? }` |
| 思维强度（分档，不是开关） | A. Profile 数据 | `profile.reasoning = { effort: 'low' ／ 'medium' ／ 'high' }` |
| 其余推理参数（maxTokens / temperature） | A. Profile 数据 | 同上 |
| 用哪个服务、端点、凭据 | B. 端口（宿主解析） | `resolveModel(profile.model) → { serviceId, baseUrl, getApiKey }` |
| 能力校验与降级 | 宿主给能力，规则由 Core / 安全侧强制 | 见下 |

**为什么服务和凭据不能在 A**：API Key 是不能落盘的秘密，服务是用户机器上的运行时状态；写进 Profile 数据，就等于把秘密写进一份可复制、可同步的配置。

**为什么模型和强度必须在 A**：「谁付账、谁定档」。模型档位是成本与质量的选择，属于调用方的声明；让被调用的模型自选，它就会自我升级成本。这与「可见性不能由 Agent 自己声明」是同一条不变量。

**SubAgent 要覆盖模型怎么办**：Profile 声明**可选档位集合**（白名单加成本上界），父 Agent 只能在集合内选。例如 `spawn_subagent` 的 Profile 允许 `['fast', 'standard']`：父 Agent 可以降档省钱，不能提档。

**审批 Agent 是特例**：它的模型能力**下限**由安全侧强制（必须支持分档 effort、不得低于某一档），因为判断质量本身就是安全属性。注意「快」不等于「弱」：快模型配中等 effort 是合理配置，但要守住质量下限。

**今天的状态**：

- 雏形已有：`TurnExecutionConfig` 就是 model / llmServiceId / maxTokens / enableThinking 的冻结快照（`src/shared/assistantFactAggregator.ts`）。唯独 `baseUrl` 混在里面 —— 它属于宿主解析结果，不该出现在可声明层。
- 但方向是倒的：这份配置由 session 加全局配置推导（`electron/turnExecutionConfig.ts:15`），模型绑在会话上，没有「按调用携带」的入口。
- 思维强度还是全局布尔（`thinkingEnabled`，`src/shared/domainTypes.ts:734`），没有分档、不能按调用覆盖；模型元数据里也没有「支不支持 thinking」这一项（`ModelEntry`，`src/shared/domainTypes.ts:678`）。
- 服务与凭据已经是端口形状（`resolveLlmCredentialsForModel`，`electron/llmServiceResolver.ts:461`；`getApiKey`，`electron/toolChatLoop.ts:409`）。要做的是从「按模型名加活跃服务」扩展成「按 Profile 的角色档解析」，已有 fast 档先例可复用（`resolveFastPreferredModelName`，`electron/llmServiceResolver.ts:510`）。

**五条硬规则**：

1. **发起时解析、调用内冻结**：现在的冻结语义是对的，保留 —— 调用中途换模型会破坏上下文一致性与审计口径。
2. **Profile 只声明意图，宿主负责可行性**：模型是否存在、服务是否可用、是否支持该 effort，由宿主校验。不满足时按**安全与成本侧定死的规则**降级或失败，不允许 Profile 自己写「不满足就换便宜的」。
3. **默认必须是「继承」**：子调用不声明模型时，继承父调用**解析后的那个模型**（连档位别名一起继承），不得静默解析成另一个具体模型。（继承语义的元规则见 §6.2）
4. **解析失败必须 fail loud**：档位解析不出来时，要么按第 2 条由宿主按定死规则降级并落审计，要么让这次调用失败。**静默换一个能用的模型是最坏选项**：审计里记的模型与实际执行的不是同一个，成本与质量口径同时失效。
5. **子调用的思维强度默认关闭**：思维强度是成本项，不是能力项；父调用的档位不自动下传，子调用要打开必须在自己的 Profile 里显式声明。它与规则 3 不冲突：模型无零成本档故默认继承，思维强度有零成本档故默认取该档，同属「成本维度可降不可升」（§6.2）。

### 5.5 事件出口：Core 往外说什么

| 出口 | 内容 | 谁消费 | 无 UI 时 |
| --- | --- | --- | --- |
| UI 事实 | 工具活动、思考与文本增量、子调用进度 | 渲染进程 | no-op，或缓存待重开窗口补播 |
| 会话台账 | 原始增量与步骤事件 | 回放 / 恢复 | 照常落盘 |
| 安全审计 | 策略判定、确认、缓存、裁决依据与成本 | 审计页 / 合规 | 照常落盘（独立文件） |
| 通知与进度 | 文件树刷新、浮动通知、标题建议、IM 心跳 | 桌面 / 远端输入方 | no-op，或转投 IM |

前两个今天已经是可注入的 sink（`emitFactEvent`、`emitSessionEvent`，`electron/toolChatLoop.ts:421`、`:423`）。剩下的是把同一模式推广开：**出口是接口，宿主给实现**。`sender`（`:389`）与 `floatingNotificationManager`（`:419`）这种「直接把宿主对象递进来」的写法，收回成出口实现。

一条硬语义：**出口默认只持有「观察」能力位，控制能力必须显式授予**。观察与可控是**能力**差异，不是事件类别差异：默认任何出口抛错或不可用都不得改变工具的执行结论（现有安全审计已是这个语义：写失败降级重试，绝不因日志故障改变判定，`electron/confirmation/securityAuditLog.ts:43`）。确实需要「出口反向影响流程」时，必须为该出口单独授予能力位，并在审计里留痕。

**上表说的是「往哪里说」，事件名另需一张闭合清单。** 准入判据只有一条：**每个事件必须有明确的 owner**（谁产出、谁消费、是否落审计），不做全铺。今天看得见的缺项至少有五类：

| 缺项 | 为什么需要 |
| --- | --- |
| 会话与调用的起止 | 后台调用的「开始 / 结束」今天是隐式的，观测不到 |
| 压缩前后（上下文装配的两次边界） | 压缩改变了模型看到的历史，必须能与裁决、成本对齐 |
| 配置变更（尤其安全档位与策略） | 安全语义的变更必须可归因到「谁在什么时候改的」 |
| Skill 与指令加载 | 「这次 Agent 为什么这么做」的第一手依据 |
| 子调用起止 | SubAgent 与审批调用的归属和嵌套关系（§8、`roadmap §1.5`） |

## 6. Core：内核边界与调用契约

Core 的边界由一个问题定义：**这一次调用要什么、结果往哪里说**；除此之外的一切（谁发起、记在哪、给谁看）都在外面。

### 6.1 负责什么，不负责什么

| 属于 Core | 不属于 Core |
| --- | --- |
| 一次调用内的推理循环（模型 → 工具 → 结果回灌，直到收敛） | 谁发起、何时发起（触发器、调度、webhook、用户点击）—— 触发归 Driver，准入与配额归 Runtime（§5、§2.3 第 3 步） |
| 上下文装配（裁剪 / 注入，与 `docs/develop/context-injection-refactor-plan.md` 同源） | 行为逻辑（意图识别 → 方案 → 请求确认 → 执行 → 回复，属 Skill） |
| 工具执行（direct / planned、plan / execute 分离、结果形态） | 投递与通知（回复飞书 / 微信、发桌面通知，属调用方的工具） |
| 安全门控（策略判定 → 确认 → 授权 → 审计） | 审批标准本身（属安全策略模块） |
| 事实与事件产出（UI 事实 / 台账 / 审计，出口可插拔） | 会话列表语义与归属展示（属宿主与存储） |
| 预算与取消的执行 | 记忆与自我优化的策略（属存储与 Profile 输入） |

一条硬规则：**Core 不认识业务身份**。它只认识 lane、Profile 提供的配置、事件出口。审批 Agent、SubAgent、管家 Agent 都不该让 Core 里多出一个 `if`。

### 6.2 一次调用（Invocation）

```text
Invocation
  ├─ session       必填：调用的归属与落盘锚点（既有会话 id，或新建会话的归属与可见性声明）
  ├─ messages      本次新增输入（可为空）—— 会话历史由 loadContext 装载，不从这里传入
  ├─ profile       模型档 / 工具能力集 / Skill 加载声明 / system 附加 / 策略档（lane）
  ├─ events        事件出口：UI 事实 / 台账 / 审计 / 通知（允许全部 no-op）
  ├─ limits        单次调用内的上界：轮数、时长、token、调用内并发（工具并发与子调用 fan-out）
  └─ signal        取消

→ InvocationResult
  ├─ status        completed | cancelled | failed | denied
  ├─ messages      本次调用产生的消息（供父调用回灌、供落盘）
  ├─ usage         token 与成本，按调用归属
  └─ events        或经由出口流式产出
```

**`limits` 只装单次调用内的上界，不含全局并发**：跨调用的并发数、速率、lane 配额由 Runtime 的**准入**施加，状态落 Storage，不进 `limits`（§5）。`limits` 里的「并发」指**调用内并发**：一次调用内同时发起的工具执行与子调用 fan-out 的上界，只在这条调用活着时有效。两者的区别不是粒度，而是**判定时刻**：调用内并发由 Core 在循环里施加，全局并发必须在装配之前施加（同 §5「Driver 决定要不要发起，Runtime 决定现在能不能跑」）。

**「上下文从哪来」要说死，否则会与 §8 的存储端口打架**：`messages` 只是**本次调用的新增输入**（用户新发的消息、确认回复、父调用交给 SubAgent 的初始任务；定时触发可以没有），**历史不经它传入**。完整上下文由 Core 在循环内装配：① 经 `loadContext` 端口按会话锚点装载**已有历史**与可寻址材料；② 与本次 `messages` 增量及 `additionalContext`（调用方给的可寻址材料）合并；③ 应用裁剪与注入规则，产出最终上下文。**历史不能改由调用方装载**，否则装配规则随调用方分叉（Runtime、IM 网关、后台触发各一份），「同样的历史必须产生同样的上下文」（§8）立刻失效，压缩与重放也失去统一落点。**`loadContext` 因此是 Core 的端口，不是 Runtime 的**：接口形状在 Core、实现由 Storage 注入、调用方在 Core 内部 —— 「Core 不认识表与 SQL」与「装配规则唯一」的唯一交点（§5.2、§8）。

四个刻意「不出现」的东西，每一个都对应今天的一处耦合：

- **不出现 `sender`**：出网点是接口，无 UI 时是 no-op 或转投别的通道（今天 `sender` 是必填位置参数，`electron/toolChatLoop.ts:389`）。
- **不出现「必须先有一个活跃的用户回合」**：会话可以随手创建、可以短命、归属由调用方声明；调用不以「存在一个活跃的用户回合」为前提（今天的 P0-1）。这里禁的是「回合」，不是「会话」。
- **不出现「由谁来回答确认」**：调用方只声明策略档与 lane，回答者由安全模块解析；调用方也不知道这次是否发生过确认，它只会看到「工具被拒绝 + 理由」。
- **不出现 `isWebContentsAlive` 这类存活判断**：调用存亡只由取消、超时、错误决定（今天 `electron/toolChatLoop.ts:623` 每轮检查窗口存活，失败即 `'Window closed'`）。

**六项之外，还需要「跑道管理」的四个字段**：不改变「这次要什么」，但决定调用能否被安全地重复、观测与恢复：

| 字段 | 语义 | 为什么必须有 |
| --- | --- | --- |
| `clientId` | 调用方给的输入 id，作为幂等键 | 定时与事件驱动会出现同一指令被投递两次；没有幂等键就只能靠事后去重 |
| `additionalContext` | 结构化、可寻址的附加上下文（键值对），不是往 system 里拼字符串 | 管家 Agent 要挂远程指令原文、审批要挂确认请求锚点；拼进字符串就无法单独裁剪、无法单独审计 |
| `trace` | 随调用传递的追踪上下文 | 一次后台调用横跨 Driver、Core、审批、Storage 四段，没有 trace 串不起来 |
| 中断语义 | 调用停下来之后是「可恢复」还是「已失败」 | 今天窗口一关回合就失败；目标形态下「当前没有活跃执行者」与「失败了」是两件事，调用方必须能区分 |

**明确预留、本轮不实现**：`steering`（回合进行中再注入输入）。契约里留位置，避免将来加它时改形状。

**会话锚点与认领**（三条，回答「会话到底算不算前提」）：

1. **会话必须有，`session` 是必填入参**：Agent 调用以会话作为归属与落盘的载体。这不是惯例而是硬约束 —— 没有会话锚点，五件事同时失去着落：① **审计归属**，裁决与执行条目变成孤立事件，说不清「这次调用整体做了什么」；② **预算归属**，token 与成本算在谁的配额上无从施加；③ **恢复锚点**，确认回复、重试、重开窗口继续看，都要先找回上下文；④ **并发隔离**，隔离边界只能靠进程内约定、无法声明；⑤ **幂等落点**，`clientId` 没有宿主，重复投递只能靠事后去重。三家也都如此（Codex 的 thread 是身份载体、DSH 的 session header 必须持久化、Claude Code 连子 Agent 都物理分会话）—— 这是**旁证，不是论据**：它说明这是系统性约束，不是我们独有的技术债。
   要拆的是**「会话与用户回合的绑定」**，不是会话本身：调用方可以随手创建会话、声明归属（用户 / 远端 / 自动化 / 内部）、带着它 resume 或 fork（`roadmap §1.4`）。**审批与 SubAgent 各有一条独立会话**，归属 `internal`、可见性 `hidden`，不进用户会话列表（「不落用户会话行」说的是可见性），但具备会话的一切性质：上下文载体、执行独占、预算归属、审计锚点。SubAgent 的会话承载独立 transcript，血缘锚在**父 turn**；审批调用的会话锚在**确认请求**上（§8、`roadmap §1.5`）。**唯一不需要会话的是单次模型调用**（分类器式，如 Claude Code 的 `sideQuery`），它不属于 Agent 调用，不受本节约束。
2. **一个会话一个执行器实例、每个回合一次调用**：确认回复到达就在同一会话上起**新 Turn**，而不是让某个回合在原地等（`roadmap §8` 已决）。后台场景里这条尤其重要 —— 它决定管家 Agent 不需要轮询确认进展。
3. **认领语义**：多个输入同时到达时，「谁先被处理」必须确定且可审计（先到先服务，或按显式优先级），不接受「谁先抢到算谁的」。

**字段的继承语义：一条元规则。** 以后每新增一个 Invocation 字段，都要先回答「嵌套调用里它怎么取值」。判据只有一条：**看它属于授权维度还是成本质量维度**。

| 维度 | 例子 | 嵌套调用语义 | 错一分的后果 |
| --- | --- | --- | --- |
| **授权**（谁能做什么） | 策略放行集合、能力位、回答者 | **不继承**：替换或取交集（§7.1） | 多继承一分就是**越权** |
| **成本与质量**（花多少、要多好） | 模型档、思维强度、上下文预算、调用内并发 | **默认继承，且可降不可升**（§5.4） | 多继承一分只是**多花钱** |
| **身份与归属** | 会话归属、可见性、审计归属 | **不继承**：子调用有自己的归属（`internal`） | 混进父的归属就是**串扰** |
| **附加材料** | `additionalContext` | **不继承**：显式传入 | 靠血缘传递就**不可寻址、不可审计** |

**授权与归属错一分的后果不可接受，所以宁可不继承；成本与质量错一分可接受，所以默认省事。** 两条连带硬要求：**凡是「可降不可升」的维度，父侧必须给出上界**（如 Profile 声明可选档位集合），否则「可降」无从判定；**凡是「替换」的维度，父侧必须给出完整集合**，不能靠「没写的就沿用父的」来省略。
**这条元规则也解释了 §5.4 里看似矛盾的两条**：模型默认**继承**（§5.4 规则 3），思维强度默认**关闭**（§5.4 规则 5）。同属成本维度，差别只在**有没有零成本档**：模型必须有一个值，故默认继承父解析后的那个；思维强度可以没有（关闭即零成本档），故默认取零成本档。两者都满足「不高于父」。

### 6.3 对调用方的四条反向要求

1. 声明身份（lane / Profile）：策略、审计、预算都按它归属。
2. 提供事件出口（允许全部 no-op）。
3. 提供预算与取消信号。
4. 不绕过 Core 直接执行工具，否则等于绕过策略与审计。

## 7. Safety：策略引擎与确认通道

Safety 管两件事：**该不该放行**（策略引擎，§7.1）与**由谁来定夺**（确认通道，§7.2）。

### 7.1 策略规则：引擎在内，内容在外，底线不可放宽

「PolicyRule 该在 Core 里还是外面」要拆成四问，答案不同：

| 问题 | 答案 | 理由 |
| --- | --- | --- |
| 判定**时机**（工具执行前必经） | **Core 内，不可绕** | 它是安全不变量；外置就等于「一个可以跳过的步骤」 |
| 判定**引擎**（`decide()` 纯函数） | **Core 内**，作为内部机制而不是 Hook | 无宿主依赖、可单测；结论必须由 Core 自己算出（`src/shared/policy/policyEngine.ts:296`） |
| 规则**内容**（默认规则、套餐、用户覆盖、`locked` 底线） | **Core 外**（安全策略模块 / 配置数据） | 随产品与用户变化，属策略数据，不属于执行框架 |
| **某次调用用哪套规则** | 调用方解析后随 Invocation 传入 | 与 tools / model 一样，是输入的一部分 |

**今天的方向是对的，接缝错了**：`decide()` 已经是纯函数，但 gate 自己读库 —— `args.appDb ? loadEffectivePolicyRules(args.appDb, lane) : DEFAULT_POLICY_RULES`（`electron/confirmation/toolCallGate.ts:185`），Core 因此直接依赖宿主的配置存储。目标形态：**effective rules 由调用方解析后随 Invocation 传入，Core 不再 import 数据库**。好处有三个：判定保持纯、可脱离宿主测试；审批 Agent / SubAgent / 管家 Agent 的策略来源各不相同，Core 不需要知道；用户改安全档位不需要 Core 参与。

**但有一半不能外置：底线。**「内容在外」的前提是**放宽方向必须受阻**。今天已有这个形状：`locked: true` 的规则不能被 `loose` 下调为 allow，也不能被 `custom` 覆盖（`electron/confirmation/policyRulesRuntime.ts:61`、`src/shared/policy/policyPackages.ts:113`），并有测试把守（`FAIL_CLOSED_IDS`）。目标形态是把这条不变量提到接口上：**Core 只接受「可收紧、不可放宽」的规则集**；相对底线放宽任何一条，Core 拒绝这次调用并落审计。（**可收紧**不只是「相对底线」，还包括「相对父调用」：子调用的放行集合只能取交集，见下。）
**除了底线，还有一类东西不能进配置。** 底线管的是「不许改宽」，但有一类东西**连收紧也不行** —— 安全路径自身的可运行性依赖它们（递归终止条件、fail-closed 兜底、审计成对，§7.2）。底线防越权，这类东西防**静默停摆**，所以两条判据之外要补第三条（见下）。

**「不可放宽」在子调用上的具体形状是「不继承」**：子调用的放行集合是**替换**而非继承，父批过的那一次不构成子那一次的授权，父的 allow 规则不自动下传。交集定上界，替换防泄漏（§1.2 不变量 3、`roadmap` 块 3）。它是 §6.2「字段的继承语义」元规则在安全维度上的取值：授权类字段一律不继承。

**规则要有「来源」维度。** 今天 `PolicyRule` 只有内容与 `locked`，没有「谁设的」，于是「**我设的 allow 为什么没生效**」无法回答：是没命中、被更高优先级的规则遮蔽，还是被套餐变换掉了？目标形态下每条生效规则都能回答来源（内置默认 / 套餐 / 用户覆盖 / 迁移），并保留**被遮蔽规则的痕迹**（哪条被哪条盖住）。否则排障只能靠读代码。

**不得为缺失的托管值静默提供默认值。** 托管值（策略规则、套餐、回答者配置）缺失时只有两种合法行为：按**显式声明的默认**兜底，或失败并落审计。最坏的做法是「取不到就回退到内置常量」，它把配置错误变成静默的行为差异 —— `toolCallGate.ts:185` 正是这个形状，数据库句柄没传进来时判定悄悄按内置规则走。把 effective rules 变成必填输入，消除的就是这一类静默回退。

**连续拒绝要有回退阈值。** 同一调用内**连续 3 次**被拒（今天常量是 `MAX_CONSECUTIVE_SAME_TOOL_ERROR = 3`，`electron/toolChatLoop.ts:284`）时，从「继续尝试」退到更保守的行为：要么终止这次调用并明确告知，要么换更保守的通道（例如要求人工）。**但这个计数器今天与「工具执行失败」共用**（安全拒绝也走同一入口，`:1661`），安全拒绝会被执行失败带着触发中止。两者必须分开计数，且安全拒绝的阈值应更高：管家 Agent 更需要「换个方案」而不是「整个 Turn 中止」（块 2 方案 §4.6）。

**三条判据**（决定任何东西该在里还是在外）：

1. 「它变了，产品的安全语义变了吗？」变了 → 在外（策略模块），且变更要走 `settings.policy-change` 审计。
2. 「它被调用方伪造，会不会造成越权？」会 → Core 侧必须有不可覆盖的校验（底线、fail-closed）。
3. 「把它改坏（放宽**或收紧**）之后，安全路径本身是否失效？」会 → 进**不可变集**（既不可放宽、也不可收紧，§7.2 递归边界）。它保护的不是权限，是路径的可运行性。第 2 条只覆盖「放宽」，这一条补的是**收紧**：两条判据都通过的东西，仍可能因为被收紧而让安全路径停摆。

**一个边界提示**：lane 是策略的**输入维度**，不是策略本身。lane 的枚举属于 Core 协议（它同时决定审计归属与预算），「某个 lane 用哪套套餐」属于外面。

### 7.2 确认通道：回答者可插拔，语义不可外置

**不可换的**：判定顺序（规则 → 缓存 → 回答者）、fail-closed 兜底、缓存写入准入。**可以换的**只有末端回答者。

| 关注点 | 归属 | 今天的代码 |
| --- | --- | --- |
| 决策请求的语义（问什么、谁能答、多久过期） | **Safety** | `electron/remote/remoteConfirmPolicy.ts`、`confirmId.ts` |
| 回执管道（把回答带回来） | **Driver** | `electron/remote/pendingRequestRegistry.ts`、`imConfirmReply.ts` |
| 回执的真实性与有效性校验 | **Safety**（不可外置） | 今天散在 `remoteConfirmPolicy` 与 `remoteWriteAuthorization` |
| 回答者解析（人 / 审批 Agent / 无回答者 fail-closed） | **Safety**，按 Profile 与 lane 解析 | 待建：`docs/develop/architect/confirmation-answerer-and-auto-approval-design.md` |

**五条规则**：

1. **Driver 不做安全判定**：它能把 `'y'` 这个字符串带回来，但无权判定「这次批准有效」。今天 `PendingDecision = 'y' | 'n' | 'timeout'`（`electron/remote/pendingRequestRegistry.ts:1`）就是把管道事实与语义结论混在一个枚举里。
2. **Safety 不自己发消息**：不能直接调平台 API，也不能直接 `webContents.send`；它只产出「决策请求」，由 Driver 投递。这是「确认通道可插拔」（桌面 / IM / 审批 Agent / fail-closed）的前提。
3. **审计必须区分「没送到」与「送到了没人回」**：今天 `mapToolOutcome` 把两者统一压成 `timeout`（`electron/confirmation/channels.ts:20`）。它们是不同的安全事实：前者说明确认机制失效（该告警或降级为 fail-closed），后者是正常超时。Driver 应上报**管道事实**（`delivered` / `delivery-failed` / `no-response` / `cancelled`），由 Safety 映射成结论并落审计。
4. **lane 不是回答者**：今天 `channelFor({ lane })` 按 lane 硬编码返回通道（`electron/confirmation/channels.ts:107`），把「从哪进来」与「谁来回答」绑死。目标形态下回答者由 Profile 解析、与 lane 正交。
5. **端口形状不预设「单次同步问答」**：回答者可以是人，也可以**本身是一次 Core 调用**（块 2 的审批 Agent 即此形态：只读工具集、侦查轮数有上界、输出有界结构化）。端口必须容纳「多轮 + 有界预算 + 有界输出」，否则将来从问答式改造成 Agent 调用要重做端口。这条自带一个排期依赖：**多轮回答者依赖调用级隔离**（与 §6.2、块 3 同源）。

**多轮回答者的装配与发起**（回答者 = 审批 Agent 时）。这是「Safety 内部要发起 Core 调用」的落法，四个环节各归其位：

| 环节 | 谁负责 | 说明 |
| --- | --- | --- |
| 装配 | **Runtime**（装配期） | 构造回答者实现（块 2 方案的 `AgentChannel`），注入审批 Profile（模型档 / 封闭只读工具集 / 轮数与预算上界 / 有界输出契约）与一个 `invokeApproval` 调用器 |
| 解析 | **Safety**（运行期） | 按 Profile 与 lane 解析出用哪个回答者；只在规则与缓存都未命中时咨询它 |
| 发起 | **回答者实现**（运行期） | 经 `invokeApproval` 发起一次**嵌套 Core 调用**；这次调用同样过策略门控、同样过准入、同样落审计（§5 嵌套调用准入） |
| 归还 | **Safety** | 端口只回 `ConfirmOutcome` —— 模型、工具集、轮数这些装配细节对 Safety 不可见 |
**Safety 拿不到也不需要 Invocation**，这是「回答者可插拔」的结构含义：换成 Agent，Safety 不改一行；换成 fail-closed，也不改一行。

**递归边界**（硬约束，不是优化）：审批调用自身的工具调用**不再进入确认流程**。不能依赖「它不会调危险工具」的约定，否则就是「审批套审批」的无限递归（块 2 方案 §4.4）。有三个点必须写死：

1. **兜底语义是 fail-closed，且不可静默**。若这条豁免被配置破坏（例如被 `custom` 覆盖成 `ask`）、或递归深度上界被触发，这次内部确认的结论是**拒绝**，不是放行 —— 「拿不到裁决」永远不等于「批准」。同时必须落审计，且要能把它与**正常拒绝**区分开（`confirm.outcome` 的 `cause=recursion-blocked` 对 `cause=agent-deny`）。所以 `cause` 不是可选装饰，而是**要求必填**的判定结果维度（块 2 方案 §6、§7）：否则「配置把自动审批改坏了」会表现成「审批突然开始拒绝一切」，排查时看不出原因。这条拒绝还要作为明确理由冒泡到调用方（§6.2「不出现由谁来回答确认」：调用方只看到「工具被拒 + 理由」）。
2. **这条豁免不该是可配置规则，因为它不是授权，是递归终止条件**。用户可调的是审批 Profile 的**能力集合**（工具集只能收窄，规格见块 2 方案 §4.1）；但「不再对这批工具做确认」不允许被覆盖。原因不是「配置不可信」，而是**这类改动不会以「更安全」收场**：收紧成 `ask` 会让审批调用再次进入确认、撞上深度上界、全线 fail-closed —— 自动审批**静默停摆**；放宽则毫无意义（它本来就是 allow）。**在这里收紧破坏的不是权限，而是安全路径本身的可运行性。**
3. **因此它不属于 `locked` 底线集，属于「不可变集」。** 今天 `locked` 的语义是**「不可放宽」**（防越权），**拦不住收紧** —— 而破坏这条路径的恰恰是收紧。两个集合目的不同，不能合并：

| 集合 | 约束 | 目的 | 判据（§7.1 第三条） |
| --- | --- | --- | --- |
| **底线集**（`locked`） | 不可**放宽**（可收紧） | 防越权：安全标准只有一套 | 「用户把它改宽，会不会越权？」 |
| **不可变集** | 放宽与收紧**都不允许** | 保**安全路径可运行**：递归终止条件、fail-closed 兜底、审计成对 | 「它被改坏，安全路径本身是否失效？」 |

至于落法，二选一、语义相同：**在判定引擎内作为递归守卫表达**（与 fail-closed 同级，按 lane 识别，只认识 lane、不认识业务身份，符合 §6.1 的硬规则），或仍用规则表达但标进不可变集。**冻结的不是「引擎行为」，而是「终止条件不得进入用户可配置的规则集」**，引擎行为本来就归引擎（§7.1 第一、二问）。

**回执校验在两条通道上形状不同，目标相同。** 「真实性」在两条通道上含义不同，不写清，这条规则在桌面通道上就是悬空的：

| 通道 | 合法授权来源 | 校验靠什么 | 明确不做的 |
| --- | --- | --- | --- |
| 远端（飞书 / 微信） | 远端用户 | **身份**：发送者与授权对象匹配、回执 id 配对、时效（今天的形状在 `remoteConfirmPolicy`、`remoteWriteAuthorization`） | 不把「管道事实」（收到 `'y'`）当成「语义结论」（批准有效） |
| 桌面 | **本机用户** | **结构**：`requestId` 配对、一次性消费、来源绑定 | **不做用户身份认证** |

**桌面通道的信任假设要显式写出**：它把「本机用户」当作合法授权来源（他在自己的机器上、对自己的数据做决定），但**不把渲染进程当作诚实的执行者**（§3.4）。两句不矛盾：「渲染进程不可信」防的是它**伪造来源**，不是「用户点的那一下不可信」。

**为什么渲染端发来的「批准」仍能构成放行**：它不是作为「渲染进程的声明」被接受，而是作为**主进程自己提出的待决请求的回答**被接受 —— 授权的基础是**主进程提出的问题**（连同策略判定与请求 id），不是渲染端的声明。于是回执校验只需三件事，且都在主进程：

1. **配对**：回执必须对应一个真实存在、未过期、未被消费的待决请求（`requestId` 一次性消费，重放无效）。
2. **来源绑定**：回执必须从该请求**被投递到的那个驱动源**回来，不跨通道 —— 桌面请求的回执不能从 IM 进，反之亦然。
3. **不可自授权**：渲染进程只能回答主进程提过的问题，**不能凭空构造一次批准**；没有对应待决请求的「批准」一律拒绝并落审计。

**边界要写出来，而不是假装不存在**：若本机已被攻陷到能任意篡改渲染进程或主进程内存，则超出本产品的信任模型（与 `safeStorage` 同一条边界）。**桌面回执能证明的是「有人在这台机器上回答了这个请求」，不能作为「用户本人确认」的身份凭据**，审计口径按前者写。

**两个特例**：

- **自动审批**：审批 Agent 是回答者的一种实现，且**永远一事一议** —— 裁决不写缓存（`roadmap §8`，已决）。后台 / 管家场景下，「全自动」意味着 Profile 把回答者固定为审批 Agent；而管家 Agent **不感知审批 Agent 存在**，它看到的仍然是「一次工具调用 + 一次安全流程」。
- **无回答者**：fail-closed 是兜底，不是降级目标。

## 8. Storage：协议在内，实现在外

**「耦合重」先说准确**：它确实重 —— Core 的入口直接持有数据库句柄（`appDb?: AppDatabase`，`electron/toolChatLoop.ts:411`），循环里直接查询 10 处以上，涵盖会话元数据（`:543`、`:1363`）、MCP 工具快照（`:596`、`:923`）、locale 回退（`:636`，界面语言正常由请求携带）、暴露面策略规则（`:594`）、决策缓存写入（`:1580`）、诊断（`:471`）。

但根因不是「该不该合并」，而是 **Core 的执行单元被定义成了存储里的三行数据**（session + user message + assistant message，外键约束见 `electron/database/schema.ts:100`；turn 与 requestId 严格配对见 `electron/turnRuntime.ts:36`）。耦合的根在**执行模型**，不在存储。

**结论：Storage 不并入 Core，但要切成三份。**

| 谁持有 | 内容 |
| --- | --- |
| Core | **记录的形状与不变量**：调用记录与事件的字段、只追加、序号单调、终态收敛、归属维度；以及两个端口 `loadContext()` / `persist()` |
| Storage | **实现**：SQLite 还是 JSONL、迁移、索引、清理、保留期、加密 |
| Safety | **审计与决策缓存的语义**：不可改写、独立物理隔离、准入门槛 |

和 §7.1 是同一个道理：**协议的形状在内，存储的实现在外。**
**为什么不能把 Storage 并进 Core**（两条硬理由）：

1. **今天有四类使用者要访问存储**：Core（上下文装配、事实落库）、Safety（决策缓存读写、审计落盘）、Runtime（会话元数据、模型冻结）、Driver（会话列表、跨会话搜索、备份导出）。合并之后只有两个结果：要么这四类都进 Core（Core 变成上帝对象），要么它们绕过 Core 直接访问 —— 那就是今天的状态，只是多了一层假封装。
2. **审计会失去独立性**。不可改写、独立文件、保留期是安全语义（`roadmap §1.5`）。审计一旦变成「Core 往 Storage 写的一条普通记录」，就会跟着 Core 的清理与删除语义走 —— 用户删会话顺手把审计删了。与 §2.7「Storage 不能算 Utils」是同一条理由。

**真正的解法是反向的**：不是把 Storage 拉进 Core，而是把 Core 对它的依赖压到两个端口 —— `loadContext(invocation)` 与 `persist(InvocationResult)`，Core 不认识表、事务与 SQLite。两个端口**由 Core 调用、由 Storage 实现**（§5.2）：`loadContext` 只按会话锚点取回**原始材料**（已有历史、可寻址上下文），**装配（裁剪与注入）留在 Core** 不下沉。这既保证装配规则唯一（§6.2），也让 Core 能脱 SQLite 单测（注入内存实现即可）。等块 1 的 Invocation 契约落地，「执行单元 = 三行数据」的前提消失，耦合收缩成端口依赖。

**三条验收标准**（判断这个切法是否成立）：

1. Core 能脱离 SQLite 跑单测（今天不能，`appDb` 是入参且被直接使用）。
2. 换一种存储实现（例如把某个 Agent 的记录落成 JSONL）不需要改 Core。
3. 存储不可用时 Core 的行为有明确约定（fail-closed 还是降级），而不是未定义。

**归属与读取：从最小落形到完整。**

**先把两个词对齐**：**「内部会话」与「内部调用记录」是同一实体的两个视角**：会话是执行期视角（上下文载体、执行独占、预算归属），内部调用记录是存储期视角（落盘形态、可检索、可锚定血缘）。审批与 SubAgent **都有会话**，归属 `internal`、可见性 `hidden`，只是落盘时不进用户会话表。§1.2 不变量 1 与 §6.2 的「会话必须有」对它们同样生效。

归属怎么落，三条（从最小到完整）：

1. **先有归属谓词，再谈列表过滤**：归属做成闭合的联合类型（用户 / 远端 / 自动化 / 内部）加一条纯谓词「这条记录该不该进用户列表」；列表只看这个谓词，不散写条件。
2. **物理分层优先于逻辑过滤**：内部调用（审批、SubAgent）落到子目录或独立表空间，与用户会话天然分家。过滤靠「记得写对」，分层是「不写也进不去」—— 前者漏一处就是泄露面。
3. **血缘锚定，不是复制，也不是共用会话**：SubAgent 的会话锚在父 turn、审批的会话锚在确认请求（`roadmap §1.5`）；锚是存储里的一条边，既不把父的内容抄一份，也不意味着两者共用一条会话。

读取形态，两条：

- **两级读取**：列表只读轻量元数据（id / 标题 / 时间 / 归属 / 可见性），进入会话才读全量消息。今天列表是拉全表（`SELECT * FROM sessions ORDER BY updated_at DESC`，`electron/database/operations.ts:120`），量一上来就是瓶颈。
- **读上限**：全量读取要有硬上限，超过就分片或拒绝，避免一份坏数据把主进程读爆。

**一条容易被忽略的硬要求：同样的历史必须产生同样的上下文。** 一旦引入「某些工具结果被替换掉」这类压缩决策，就必须**可重放**（记下哪些被替换过），而不是每次装配时重新判断。否则同一份历史能装出两份不同的上下文，任何基于上下文一致性的能力（命中率、重放、恢复后继续同一个 Turn）都会变成概率事件。

**产品层面的两条约定**（`roadmap §1.4`、`roadmap §1.5`）：

- **归属与可见性**：会话有归属维度（用户 / 远端 / 自动化 / 内部），列表与搜索按可见性过滤；SubAgent 与审批调用**不落用户会话行** —— 落的是归属 `internal`、可见性 `hidden` 的内部会话。
- **内部调用记录**：审批调用锚在确认请求上、SubAgent 锚在父 turn 上；只追加、不构成授权。

## 9. 对外承诺与内部实现

| 类型 | 内容 |

## 11. Agent SDK 化的差距（对照分析）

§10 的验收主体是本产品自己的三条业务线 —— 自动审批、SubAgent、后台管家。把六块主干拆成可复用的 Agent SDK 会多出一层要求，而这一层只对**外部复用者**成立：库要能嵌进别人的进程、依赖方向要能被机制锁住、实现要能换掉、还要有不启动 Electron 就能跑的验收。**凡是只对这一层成立的缺口，§10 里一条都没有。**

下表把「SDK 化还差哪些工作」的七类缺口逐条对着 §10 定位。**表里判的是 §10 原有 16 条时的状态 —— 它是 17 – 20 的推导过程**：判为「未列」的四类已于 2026-09-15 补为偏差 17 – 20。判定口径：**已列** = 偏差表里有对应条目；**半覆盖** = 原则写在本文章节里、条目不在偏差表；**未列** = 两处都没有。可视化版本见 `docs/develop/architect/product-architecture-design.html` 第 13 节图 G。

| SDK 缺口 | §10 里的对应 | 判定 | 还差什么 |
| --- | --- | --- | --- |
| ① 契约层：入口签名本身就是对外承诺 | 1、2（公共前置） | 已列 | 清单从「Core 依赖了谁」写，没有从「入口签名就是契约」写 |
| ② 依赖护栏：包边界、`exports` 映射、lint 规则、CI 断言 | 无 | **未列 → 已补 17** | 原清单的「应该往哪走」全是架构方向，没有一条是「用什么机制把方向锁住」 |
| ③ 单实例假设：模块级可变状态 → 一个进程一个 runtime | 无 | **未列 → 已补 18** | 需要 `createAgentRuntime(deps)` 这类形态；今天有四处模块级状态 |
| ④ 环境端口：凭据、事件出口、`translate`、时间源 | 1、5、13 | 半覆盖 | 前三者都在；缺 clock / 时间源 |
| ⑤ 存储 · 安全 · 工具面 | 2、15 | 半覆盖 | 「协议在内、实现在外」只停在 §8 的原则上；工具自身的宿主耦合无人过问 |
| ⑥ 发布工程：包拆分、版本节奏、分发形态 | 无 | **未列 → 已补 19** | 无 workspaces，宿主与 provider 依赖混装；SDK 形态（库 / 进程）未定 |
| ⑦ 验证闭环：不启动 Electron 跑完一个回合 | 16 同类，验收对象不同 | **未列 → 已补 20** | 16 验收的是安全机制是否成立，不是可复用性 |

### 11.1 已列：清单里有落点

- **契约层** ← 偏差 1、2。这两条是清单的公共前置，方向（事件出口取代 `sender`、收敛成 `loadContext()` / `persist()` 两个端口）与 SDK 化的要求同向。差的只是视角：清单从「Core 依赖了谁」写，没有把「入口签名本身就是对外承诺」写成条目 —— 而 SDK 的使用者只看得见签名。
- **凭据端口** ← 偏差 5。端点与凭据留在宿主端口，不写进可声明的执行快照。
- **事件出口** ← 偏差 1 与 §5.5。今天已有雏形，只是以函数注入的形式躺在入口参数里：`electron/toolChatLoop.ts:409` 的 `getApiKey`、`:421` 与 `:423` 的 `emitFactEvent` / `emitSessionEvent`。
- **i18n** ← 偏差 13。主进程只产出「键 + 参数」，直接显示处走注入的 `translate`。
- **安全** ← 偏差 15。档位只调范围、不调宽严 —— 原清单里唯一带强校验语义的条目，与「SDK 不能把安全底线做成可配置」完全重合。

### 11.2 半覆盖：原则在文档里，条目不在偏差表

- **存储实现必须可替换**。§8 的承诺是「协议在内、实现在外」，但偏差 2 只要求把依赖收敛成两个端口，没有一条说实现必须能换。而今天的存储是 Electron 内嵌的 `node:sqlite`（`DatabaseSync`），SDK 恰恰不能依赖它 —— 这条只停在原则上，落不到排期里。
- **业务身份不能进 Core**。`electron/toolChatLoop.ts:460` 在 Core 内部按 `remoteContext.source` 推导 `requestLane`，直接违反 §6.1。它可以归入偏差 1 的伞下（Core 依赖驱动源），但没有单列，容易被漏掉。
- **时间源要端口化**。日志按日分文件、保留期、数据库时间戳都隐式取系统时间；偏差 13 与 14 都碰到了日志，都没有提这件事。

这三条都不必新增行，就地补进偏差 1、2、13 的描述即可。

### 11.3 未列（现已补为 17 – 20）：文档与偏差表两处都没有

- **依赖护栏**。原清单的「应该往哪走」全是架构方向，没有一条是「用什么机制把方向锁住」：没有包边界、没有 `exports` 映射、没有 ESLint `no-restricted-paths`、没有 CI 断言。今天的规模是：从 `electron/toolChatLoop.ts` 出发按静态 import 展开依赖闭包（含 `@/` 别名），可达 **368 个本地模块，其中 26 个直接 `import 'electron'`**；全仓非测试文件里直接 import electron 的有 35 个。对照之下 `src/shared/` 177 个文件**零** electron 依赖 —— 底子是有的，缺的是把这条线固定住的机制。
- **单实例假设**。`electron/tools/builtinExecutors.ts:1300` 的模块级 `const registry`、`electron/confirmation/audit.ts:11` 的 `let singleton`、`electron/mcp/mcpToolExecutor.ts:24` 的 `globalSemaphore`、`electron/remote/confirmId.ts:6` 的 `globalConfirmIds`，以及 `registerChatCancel` / `registerToolRevocationRequest` 这两个注册入口 —— 今天**一个进程只能跑一个 runtime**。对单窗口桌面产品没有影响，所以当初摸排没把它算作偏差；对「嵌进别人的进程」是直接否决。
- **发布工程**。没有 workspaces，`package.json` 把渲染端、宿主与 provider 依赖混装。偏差清单全是代码内偏差，不含构建与发布维度；而「SDK 是库，还是进程 / 服务」这个决定会反过来影响契约形状。
- **验证闭环**。偏差 16 是原清单里唯一的验证类条目 —— 而可复用性的验收由后来的 20 承接；16 验收的是「机制在代码里是否真的成立」，对象是安全裁剪，不是可复用性。SDK 需要的是另一种验收：`createAgentRuntime(deps)` 之后，不启动 Electron 就能跑完「带工具调用的回合 + 一次确认 + 一次拒绝」。

### 11.4 建议怎么补

- **②③⑥⑦ 已补为偏差 17 – 20**，不新增关键路径：全部挂在 1、2 之后，17 / 18 / 19 依赖列写 `1、2 → 20`，20 是这一组的验收节点（依赖列 `1、2、17、18、19 → —`）。工作块划分见 `agent-sdk-shape-decision.md` §3（P1 – P5）。
- **④⑤ 就地补描述**，不新增行（见 §11.2）。
- **排期含义**：SDK 化约等于「关键路径 A 的第二张脸」—— 它要的边界就是偏差 1、2 要的边界。但第 0 步必须把**契约与包边界护栏**一起做：没有护栏，其余几类改完还会退化回去。
- **已拍板**：按**同进程库**推进 —— 契约按「可远程」的形状定义（禁止函数与句柄），物理边界留在本进程；形态对比、代价与升级信号见 `docs/develop/architect/agent-sdk-shape-decision.md`。
