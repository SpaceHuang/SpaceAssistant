# T03 一次性通知投递（完成）

## RED / GREEN

新增两个 RED/GREEN 崩溃窗口用例：

- `delivery.test.ts`：队列已返回并持久化固定 request key 的 receipt，但触发器写入 `messageId` 的 CAS 失败。首次投递返回 write conflict；重试再次使用相同 key，获得原 receipt，并将同一 messageId 写回触发器。
- `processSource.test.ts` 使用真实 SQLite：owner 不可见时拒绝通知且无队列 receipt；恢复 owner 后投递，模拟 `messageId` CAS 失败，关闭并重开 SQLite，再以新的 recovery scanner 扫描。scanner 不重新 enqueue，从原 receipt 补回 trigger.messageId，数据库中该 request ID 仍只有一条请求记录。
- `recovery.test.ts`：RED 显示 scanner 读到 durable receipt 后没有把 `messageId` 修回 matched trigger；GREEN 在恢复扫描时对当前 revision 做 CAS 绑定，并在 CAS 冲突时留待下次扫描。
- `recovery.test.ts` 对 persisted receiver Turn 的 `failed`、`cancelled`、`timed-out` 终态分别记为通知 Turn 失败，并保留原 outcome；`completed` 保持独立成功状态。

结合 T02 的精确 source-gap/到期/body-free 事实测试与目标删除后通知 owner 的 SQLite 集成，以及 receiverStarter 的 busy/cancel/turn receipt 测试，已覆盖 T03 要求的队列唯一、忙时不重复、来源缺口与 receiver Turn 结算区分、目标不可用时不创建新会话。
