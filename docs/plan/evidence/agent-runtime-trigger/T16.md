# T16 宿主接线与持久恢复

## RED → GREEN 与交付

- recovery / delivery / checkpoint、exact Turn terminal bus、receiver starter、history source facts 和 SQLite admission 边界均采用先写失败边界用例再实现的顺序，见同目录 T10–T15 及各模块定向测试。
- 本轮主进程装配 TypeScript 检查先 RED：`AppDatabase` 错传至 `DatabaseSync` 安全快照 API；改用 `getDbConnection(db)` 后通过。
- 固定随机序列 RED：seed `0x51a7` 在 step 2 证明 SQLite update 允许 terminal trigger 复活成 matched。`sessionStorage.commands.runtimeTriggers.update` 增加状态转移条件后，同一 seed 通过。
- S-01 RED：public HistoryPort 首次 context final-check 失败后，下一条不含 context ID 的 raw `model-request-started` 曾绕过 runtime admission 模板进入普通 History；TDD 测试复现后，`createSessionHistoryPort` 改为模板存在而无 context 凭据即拒绝。回归同时确认首次失败事务无 event、无 admission，raw transcript 无法成为正常历史。
- T16 修复与边界回归：sync waiter 重启后持久失败关闭；显式 cancel 会唤醒在线 SDK wait；sync event 匹配 source target 而非 receiver；IM receiver 使用其可信 queue scope 对应的 feishu/wechat 策略 lane。
- T19 性能发现反向补强 T16：postStep 不再每次重读整段 History。public SessionHistoryPort 暴露 bounded `readEventsAfter`，SQL adapter 核验 session/sequence/cursor 并按页 hydrate；每个 hosted Turn 的 `SettledStepFactsTracker` 首次 complete snapshot 后只应用新增页。Track scoped History 包装器逐 invocation 转发且保持 allowlist。

## 主进程装配

- main 按 lifecycle 创建 host service、当前授权快照、authorization binding、固定 requestId delivery、runtime source context 与 admission；TurnRuntime 所有 `runtime-trigger:` 起始在 source/provider 前经过共同 authorization gate。
- recovery 在应用 handler/starter 发布后启动，并在 `before-quit` 关闭；扫描 waiting 五源，恢复 matched 项时先读取既有 receipt，不产生第二条输入，使用普通 prepare/dispatch path 启动准确 receiver Turn，按持久 terminal 结果收敛 trigger。
- source context 仅从当前授权的 matched 记录提取，并以 JSON/untrusted boundary 传入 SDK；SQLite History 的首次 context 与 `result_json.admission` 同事务 final-check 由 T15/T16 生产接线复用。
- 在线同步 checkpoint 使用已确认的 `callbackTimeoutMs=5000`、`maxPauseMs=60000`；只在 SDK pause accepted 已持久化后投递。进程重启无法恢复内存 pause，因此遗留 waiting sync 以 `sync-waiter-lost-on-restart` 失败收敛。
