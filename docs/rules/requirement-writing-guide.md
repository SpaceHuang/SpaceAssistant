# 需求写作指南

> **定位**：写**需求 / 需求基线**时读本篇。
> **通用层**（读者分层与人机分工、写作流程与门禁、人类决策层 R1–R8、通用自检）定义在 [`document-writing-guide.md`](document-writing-guide.md) §8–§11（元指南）；本篇只写**需求特有**的部分，不重复。
> **适用范围**：`docs/requirement/**` 的需求 / 需求基线文档，以及要提交真人评审或交给设计实施的临时需求草案。
> **覆盖范围**：一份需求怎么写清楚（价值、范围、交互取值引用、验收与指标、跨文档一致性）。**不覆盖**：交互判据本身（在 [`interaction-design-guide.md`](interaction-design-guide.md)）、文档库的组织（在 [`docs-guide.md`](docs-guide.md)）。
> **来源与维护**：见 [`-sources.md`](requirement-writing-guide-sources.md)（按需查阅，日常不必加载）。
> **一句话**：需求的产出不是"设计草案"，而是**可判定的用户可见行为 + 边界 + 验收口径**；而且**需求阶段比方案阶段更依赖人机协同**——方案里的取舍多数能被证据判定，需求里的取舍多数不能。

## 0. 四条前提

1. **价值先行。** 开篇必须说清四件事：**为什么做**（解决用户 / 业务 / 安全上的什么问题）、**不做会有什么损失**、**做了会带来什么收益**，以及这些收益与损失落到哪一类价值上。它是需求的第一个判断，并且**引领全篇**：价值落点决定了后面的范围取舍、打断策略与验收口径（例如价值主要在安全侧，就不能用"体验优先"的措辞去放宽确认）。价值说不清的需求，后面的规则一定会互相打架。
2. 需求回答"用户会看到什么、系统允不允许、什么时候必须先问用户"；**不回答"怎么实现"**。
3. **需求是方案的上游。** 需求里留白的地方，实现会分裂成几种不同体验；评审的原话是"不能留给技术设计自行选择"。判定句：**同一句话，设计者能否做出两种都合规的实现？能，就是没写完。**
4. 验收对象是**用户可见行为**，不是内部字段、类型或代码形态。

## 1. 人机协同（本篇重心）

需求阶段的决策密度高于方案阶段：价值排序、范围取舍、体验代价、打断频率、默认行为、误触风险——**这些没有"证据答案"**，只能由人定；而它们恰好决定了后续所有实现的自由度。所以需求文档的分工要比方案更明确。

### 1.1 按能力分工

| 决策类型 | 谁定 | 在需求文档中的形态 |
|---|---|---|
| 做不做、先做哪个、本期不做什么 | 人 | 范围三清单（§5） |
| 体验取舍：会不会被打断、默认行为是什么 | 人 | 决策项 D（§1.2） |
| 何时必须问用户、问到什么粒度 | **人定规则，机器执行** | 判据见[交互设计指南](interaction-design-guide.md) I1–I5；需求里只写本需求的取值（§4） |
| 风险容忍：不确定时先做还是先验证 | 人 | 开放决策表（§5） |
| 验收是否可判定、指标是否可观测 | Agent | 验收映射与指标三要素（§6） |
| 事实：既有能力 / 旧需求是否与本需求冲突 | Agent | 现状核查（§3 第 1 步） |
| 跨文档废止与同步、术语一致 | Agent | §7 |

### 1.2 需求版的人类层三件套

沿用元指南 §8.2 的第 0 层骨架（一句话 / 决策清单 / 不需要你决定），但**需求的人类层要额外回答四个问题**：

1. **价值**（§0-1）：为什么做、解决谁的问题、不做损失什么、做了收益什么——这也是全篇的写作线索。
2. **用户会经历什么？**（会看到什么、会不会被打断、多久、能否撤销）
3. **什么时候系统必须先问用户？**（触发条件与粒度，见 §4）
4. **不做会怎样？**（不做的后果、被排除的方案与理由）

只写"功能是什么"而不写这四个问题的需求，评审只能替作者做价值判断。

### 1.3 与方案阶段的关键差别：宁可早冻结

方案里"选哪个实现"常常有证据可依，允许在设计阶段收敛；需求里的取舍没有证据，**必须在使用它之前定下来**。因此：

- 需求的人类决策应在需求定稿前关闭；确实定不了的，写进**开放决策表**（§5），标明"必须在哪个节点前选定"与关闭条件——**不允许用"或 / 建议 / 视情况"糊在正文里**。
- 判据：如果同一处留白会让设计者、实现者、验收者各自得到不同结论，它就不是"实现细节"，而是需求缺陷。

## 2. 读者分层（需求版）

沿用元指南 §8 的三层，仅调整读者与内容：

| 层 | 读者 | 内容 |
|---|---|---|
| 第 0 层 决策层 | 决策人、产品负责人（不读代码） | 价值、范围、体验取舍、询问策略；**语言与格式规则同元指南 §10 的 R1–R8** |
| 第 1 层 行为规格 | 设计者 | 可判定的用户可见行为：归属、默认、优先级、打断时点 |
| 第 2 层 验收与边界 | 验收者 / 评审 Agent | AC、指标口径、边界与例外、非目标 |
| 附录 | 追溯 | 现状核查结论、开放决策、变更记录 |

**元指南 §10 的 R1–R8 全部适用**，需求侧尤其吃四条：**R2（裁决条目自包含）**、**R5（写后果不写机制）**、**R7（可裁决性检验）**、**R8（界面 / 开关 / 数据格式 / 对外接口 / 外部渠道行为不得以"推荐默认值"承载）**。

## 3. 写作流程（需求版）

通用流程见元指南 §9；需求侧的差异如下（其余步骤与门禁相同）：

| 步 | 需求侧的动作 | 产出 | 门禁 |
|---|---|---|---|
| 1 现状 | 核查**既有能力与旧需求**：本需求是否与现有行为冲突、是否废止某条旧结论 | 现状核查表（含"与哪份旧文档冲突 / 废止"） | 不存在"我们以为是这样"的断言 |
| 2 行为模型 | 写清状态、归属与**优先级**：多条规则同时成立时谁赢 | 行为规则表 | 每条规则只有一个出口，冲突有裁决顺序 |
| 4 反例 | 场景矩阵**必须包含"意图不明 / 歧义"路径**（这是需求缺陷最集中的地方） | 场景矩阵 + 开放决策表 | 歧义场景都有确定行为 |
| 5 验收 | 从用户目标正向推 AC；指标要可观测 | 验收映射 + 指标口径 | 每条 AC 可判定；指标有事件、分母、阈值 |
| 6 范围 | 本期 / 不做 / 未来再引入 三清单 | 范围清单 | 非目标不得与目标互相抵消 |

## 4. 交互内容：引用，而不是自定判据

涉及用户确认、打断、默认行为的需求条款，**不要在本文件中自创判据**——按 [`interaction-design-guide.md`](interaction-design-guide.md)（I1–I5）确定，需求里只写**本需求的取值**：

- 何时问、一次覆盖哪些；
- 拒绝 / 取消 / 超时分别怎么走；
- 批准的有效范围与时效；
- 默认值，以及打断的成本（频率上限、误触、降级）。

写法要求：**结论 + 引用**，不写判据推导。交互决策的取值属于人的决定（§1.1）；Agent 负责把它写清，并检查是否出现"同一段描述能导出两种实现"（§0-3）。

**涉及新增界面时**：条款里只要出现界面语义（"用户可查看 / 显示 / 面板 / 列表 / 展开 / 开关 / 入口 / 按钮 / 提示 / 状态展示"），就必须出**界面归属卡**（5 行，见[交互设计指南](interaction-design-guide.md) I8），并**作为决策项交项目负责人批准**后，需求才成立——不允许以"可观测性""状态说明""本期推荐值"等形式承载界面要求（元指南 §10 R8）。

> **归属说明**：本节原为 R7–R11 五条交互规则，复核后判定为**串层**——那是"交互该长什么样"（设计规范），不是"需求文档该怎么写"（写作规范）；已抽取为独立的《交互设计指南》，并删除其中两条实现层要求。迁移记录见[交互指南的来源附录](interaction-design-guide-sources.md)。

## 5. 范围、非目标与开放决策

**三清单**（缺一不可，且不得互相抵消）：

1. **本期做**：按用户价值排序，而不是按实现难度。
2. **明确不做**：写清不做的后果，避免读者以为遗漏。非目标**不得与目标互相抵消**——反例：把唯一的出站门闩排除在"本期之外"，等于目标不可达。
3. **未来再引入**：已在本期交付的通道/能力，不得在同一文档里被描述成"未来再引入"（自相矛盾会让设计者按空实现）。

**开放决策表**（需求层的"待定项"，替代正文里的"或/建议"）：

| 列 | 要求 |
|---|---|
| 决策点 | 一句话，含至少两个选项 |
| 现状 | 当前文档怎么写、以及会派生什么差异 |
| 必须在哪个节点前选定 | 例如"设计稿评审前""实现启动前" |
| 关闭条件 | 凭什么算关闭（选定 + 同步改了哪些 AC） |

**"推荐默认值"的禁用清单**：只有**可逆、无界面、无外部行为**的内容才可以用"推荐默认 / 建议值"承载。涉及下列任一项的，**一律升为决策项或开放决策表条目，由人批**（元指南 §10 R8）：新增或改动**界面**；新增或改动**开关 / 配置项**；**数据格式与持久化字段**；**IPC / 对外接口**；**外部渠道行为**（IM、远程）。

## 6. 验收口径与成功指标

- **每条 AC 可判定、可执行**：能写出用例；同一段文字不会有两种都合规的断言。
- **区分"验收项"与"推荐项"**：推荐项不得写成 AC（写了要么被当硬要求，要么评审会问为什么不验收）。
- **指标三要素**：可观测事件 + 分母 + 阈值。"显著下降""足够低""一次操作内""不高于基线"**不算指标**——它们无法用于上线判断。
- **以用户可见行为描述**：断言"用户看到什么、能不能撤销、会不会被打断"，而不是内部字段取值。

## 7. 跨文档一致性

- **废止关系要写清**：本需求替代/废止哪份旧需求的哪条结论；被废止的文档**何时**同步改字（同步义务与落地时点都属于交付物）。
- **前置依赖要写清**：依赖的前置需求必须与它"同版本可验收"，不允许"先合免确认、后补绑定"。
- 术语与旧规格名一致；改名时在本文档写明新旧对应，避免评审与实现各自沿用不同口径。

## 8. 反模式 → 对应步骤

| 反模式 | 属于哪一步没做 | 精简例证 |
|---|---|---|
| 需求与既有能力 / 旧需求冲突 | 流程第 1 步（现状） | 需求称"模型投影不脱敏"，而现有链路本就是脱敏；把既有文件名"现状"写错 |
| 验收口径不可判定 / 不可实现 | 第 5 步（验收） | 要求的字段在类型层面无法返回；指标写"显著下降" |
| 多条业务规则同时成立却没有裁决顺序 | 第 2 步（行为模型） | "用户显式路径优先"与"材料必须放在固定目录下"不可兼得 |
| 涉及交互的条款没有取值，或触发条件写成"有影响就问" | 第 4 步 + [交互设计指南](interaction-design-guide.md) | 触发条件写成"有影响就问"→ 逐文件询问；或需求自行发明交互判据 |
| 范围过宽 / 非目标写错 / 分期自相矛盾 | 第 6 步（范围） | 把唯一的出站门闩排除在本期之外；本期已交付的能力写成"未来再引入" |
| 用户可感知后果缺失 | 元指南 §10 的 R5 / §1.2 | 只写机制，不写会不会打断、取消后留下什么 |
| 留白被当成"实现细节" | 第 4 步（反例）+ 开放决策表 | 同一请求存在三种打断时机，交给设计决定 |
| 只写功能、不写价值 | 第 0 步（价值先行） | 全篇只有行为规则，读者无法判断该不该做、优先级怎么排 |

## 附录 A 提交评审前自检清单（需求特有项）

通用层八条（第 0 层三问、事实与复现命令、承诺配对、未验证项、裁决条目已过 R7、R8 的"推荐默认值"禁用清单）见元指南 §11，本清单不重复。

1. 开篇价值陈述齐备（为什么做 / 解决什么用户·业务·安全问题 / 不做损失 / 做了收益），且后续范围与验收口径与之一致；人类层回答了四问：值不值得做 / 用户经历什么 / 何时必须问用户 / 不做会怎样。
2. 现状核查完成：与既有能力、旧需求的冲突与废止关系已写清。
3. 每条业务规则只有一个出口；多条规则冲突时有裁决顺序。
4. 涉及交互的条款已按《交互设计指南》I1–I5 写出**本需求的取值**（何时问、粒度与频率、四条路径、批准语义、默认与成本），而不是自创判据。
5. AC 可判定、可执行；验收项与推荐项分开；指标具备事件 + 分母 + 阈值。
6. 范围三清单齐备，非目标与目标不互相抵消。
7. 跨文档废止与同步义务已写明落地时点。
8. 没有以"推荐默认值 / 建议 / 视情况"承载界面、开关、数据格式、对外接口或外部渠道行为；涉及新增界面的，已出**界面归属卡**（5 行）并获批（《交互设计指南》I8）。
