> **本文件位置**：`docs/rules/docs-guide.md`（2026-10-15 定稿）—— 属「仓库级长期规范」层（`docs/rules/`），**独立于 9 主题体系**。该层的路由见 [`README.md`](README.md)，文件清单与用途分类见 §9.1。

## 0. 环境纪律：会话可能丢帧（判定一律以磁盘为准）

本环境的会话管理**在出错重试时会丢失部分消息与工具结果**（2026-10-15 由用户确认）。整理工作全程依赖工具读写，因此本节**优先于本指南其余内容**。

| 现象 | 真相 | 应对 |
| --- | --- | --- |
| `write_file` / `edit_file` 返回 `ok:false`（如「未读校验失败」） | **可能已落盘，也可能没落**；结果里的 `bytesWritten` 数字**不能当证据** | 复读该文件确认；确认未落盘再重试 |
| 同上返回 `ok:true` | 仍可能没落盘（实测发生过） | 同上 |
| 会话里看不到某次操作 | **不代表没发生** | 以磁盘为准 |
| `grep` 返回「无匹配」或只回部分行 | **可能漏报**（实测：查一个词只回了一行，而文件里其实有好几处） | 关键判定改用 `read_file` 读原文 |

**四条硬性规则**：

1. 判定「文件是否存在 / 内容是什么 / 谁写的」，一律以当下的 `read_file` / `ls` / `git log` 为准，**不依赖会话记忆**；
2. 内容与预期不符时，先按第 1 条复核；**不要**据此推断「有其他写入者」—— 本轮曾因此误判（把丢帧后仍落盘的自有产出当成他人写入）；
3. 每次写入后**复读一次**；`ok:false` 时尤其必须复读再决定是否重写（避免覆盖已落盘内容）；
4. 「是否已改成功 / 是否还有残留」这类判断，用 `read_file` 分段读原文，**不要只凭 `grep` 的计数或"无匹配"下结论**。

---

**三条不可通融的硬约定**（沿用 `docs/develop/architect/README.md`、`docs/develop/interface/README.md` 的既有做法，见计划 §1.3）：

1. 现状文档写「**核对基线提交**」，不写行号；
2. 每条结论给**可复现命令**（`rg -n` / `git log -S`）；
3. 跨目录引用一律**带路径**。

## 2. 目标结构

### 2.1 组织原则（计划 §2.1）

1. **主题即二级目录**：主题边界对齐**代码域 / 产品模块**，不对齐时间。
2. **一主题一入口**：每主题只有一份 `README.md`（索引 + 状态表）与一份 `history.md`（流水账）。
3. **现状与历史分离**：现状文档只描述「今天代码是什么样」；变更过程一律进 `history.md`，避免现状文档再次腐化。
4. **归档可追溯**：原件 `git mv` 进 `archive/<主题>/`，**文件名不改、内容不改**，靠归档索引 + history 反查。
5. **一切结论可复现**：现状文档与 history 条目都要能由命令重放。

### 2.3 单个主题目录的标准形态（计划 §2.3）

```text
docs/develop/<主题>/
├── README.md                # 索引：现状文档清单 + 状态表 + 归档指引 + 核验记录入口
├── <模块>-现状.md            # 现状文档：只写与最新代码一致的事实，带核对基线与可复现命令
├── history.md               # 迭代流水账（§4）
├── in-flight/               # 草稿箱：未实施/未收口的在途项（收录前须过 §3.0 核验）
└── baseline-check-<日期>.md # 主题 baseline 核验记录（§6.5）

docs/requirement/<主题>/
├── README.md
├── 需求基线.md               # 当前生效的需求口径（替代 develop 侧的现状文档）
├── history.md
└── in-flight/
```

> `requirement` 侧形态与 `develop` 相同，**只是把「现状文档」换成「需求基线.md」**，已完成需求同样进 `archive/`。

> **空目录不被 git 跟踪（实测坑）**：`in-flight/` 在没有条目时是空目录，**不会进版本库**——因此从整理分支合并回 `main` 后，空的 `in-flight/` 会「消失」。往 `in-flight/` 放第一篇文档时**必须先 `mkdir -p`**，否则 `git mv` / `mv` 会报 `No such file or directory`。同理适用于任何依赖"目录存在"的操作。

### 2.4 归档形态与约定（计划 §2.4）

```text
docs/develop/archive/<主题>/        # 已完成迭代原件
docs/requirement/archive/<主题>/
docs/develop/archive/INDEX.md       # 归档总索引：旧路径 → 新路径
docs/requirement/archive/INDEX.md
```

| 项 | 约定 |
| --- | --- |
| 搬运方式 | `git mv`（保留历史），**文件名不改、内容不改**；仅允许在 `archive/INDEX.md` 补「原路径 / 状态 / 取代者」 |
| 归档判定 | 迭代已完成且结论已并入代码；已被新文档取代；或属过程产物；或方向已否 |
| 为什么内容不改 | 归档件是**历史证据**，改了就失去可追溯性；「现状」一律写在主题目录，不回头改归档件 |
| 索引 | 主题 `history.md` 每条「出处」列直接链到归档件；`archive/INDEX.md` 提供一次性全量映射 |
| 副作用 | 归档件正文里的相对链接按**搬迁前布局**书写，搬迁后可能失效——这是「内容零改动」的直接后果，属**预期**，不回头修 |
| 特殊件 | 0 字节空文件不搬运，原地删除（计划 §8-5）；`.tsv`/`.json` 证据类随宿主文档进归档 |

### 2.5 术语对齐：用现役术语 `agent-sdk`（计划 §2.6）

`agent-core` 是 `Agent SDK`（`packages/agent-sdk`，包名 `@spaceassistant/agent-sdk`）的**早期设计方案名称**；代码侧 `agentCore|agent-core` 零匹配。

| 旧称（历史文档里） | 现役术语 | 处理 |
| --- | --- | --- |
| Agent Core / Core / agent-core | **Agent SDK** / `packages/agent-sdk` / `agent-sdk` | 主题名、README、现状文档、history **一律用现役术语**；历史**文件名不改**，在 `archive/INDEX.md` 与主题 README 的「术语沿革」注明旧称 |
| `docs/develop/interface/`（目录名） | **agent-sdk 接口说明** | 并入 `agent-sdk/`；其 README 本就自称「agent-sdk 接口说明」 |
| Agent Host / Hosted Runtime | 现役同义 | 保持，不新造词 |

落地规则：① 新增与改写的文档只用现役术语；② 归档件正文不改，旧称只在索引与 README 里对照；③ **不做全仓批量替换旧称**，避免制造无意义 diff。

## 3. 归属判定：每篇文档怎么落位

### 3.0 状态核验（前置动作，不能跳过，计划 §3.0）

**文档里那行「状态：」不能作为判定依据**——计划 §1.5 实测抽查 4 篇，3 篇状态字段已过期。每篇文档在做去留判定前先跑三步，结果记进 `docs-inventory.tsv` 的「代码证据」列：

1. **提交检索**：`git log -i --date=short --format='%ad %h %s' --grep='<关键词>' -30`
2. **路径检索**：`git log --date=short --format='%ad %h %s' -25 -- <该主题代码路径>`
3. **符号检索**：`rg -n '<文档承诺的类型/函数/文件>' <代码路径>`

| 文档自述 | 代码证据 | 判为 |
| --- | --- | --- |
| 已实施 / 已落地 | 有对应提交 + 符号 | **A 或 B** |
| 待实施 / 修订中 | **却有**对应提交 + 符号 | **已完成（自述滞后）**：按 A/B 处理，并在 history 记「状态滞后，以代码为准」 |
| 待实施 | 无提交、无符号，但依赖项已就绪 | **C 草稿箱**，头部标「在途；依赖已就绪」 |
| 待实施 | 无提交、无符号，前置也不具备 | **C 草稿箱**，头部标「在途；前置未就绪」 |
| 已废弃 | 符号已从代码移除 | **D**；若符号仍在，先与需求方确认再定 |

> **两条硬性禁止**（来自整理分支执行记录，是对 C 类误判的更正）：
> ① **C 类不得仅凭文档自述判定**——每篇至少要有一条「专属符号命中」或「分支合入提交」的**正向证据**才可进 `in-flight/`；
> ② **超过 7 天未更新却仍判为 in-flight 的文档，必须再核一次**——多数老文档其实已开发完。取「最后更新时间」须看搬迁前基线：`git log -1 --date=short --format='%ad %s' 17236274 -- docs/develop/<原文件名>`。

### 3.1 四类去向（计划 §3.1：每篇只允许一个去向，必须逐篇落定）

| 去向 | 含义 | 处理 |
| --- | --- | --- |
| **A 现状（baseline）** | 描述的目标形态/契约**今天仍成立** | 留主题目录；按 §3.2 校核后可能合并多篇为一份；写核对基线 |
| **B 归档（archive）** | 迭代已完成、结论已进代码；或被取代；或属过程产物 | `git mv` 进 `archive/<主题>/`（**已定：一律搬迁**），内容零改动 |
| **C 草稿箱（in-flight）** | 未实施、或实施中未收口，但仍有价值 | 留主题目录 `in-flight/`，头部统一标注 `状态：草稿（未实施）` 或 `状态：实施中（进度见 history.md）` |
| **D 废弃（deprecated）** | 功能方向已否（如 Plan 模式） | `git mv` 进 `archive/<主题>/`，头部补一行「已废弃，见 xxx」 |

**过程产物一律归档（B），不再逐篇讨论**（整理分支执行记录）：命中即归档——`*evidence*`、`*audit*`、`*review*`、`*gate*`、`*remeasure*`、`*acceptance*`、`*verification*`、`*test-plan*`、`*implementation-matrix*`、`*status*`、`*estimate*`、`*manifest*`、`*ledger*`、`*profile*`、`*snapshot*`、release-note，以及 `session-storage-a*/c*/i*/r*/m3-*` 阶段件。

> 注意「C 草稿箱」只收经 §3.0 核验确认「无实现痕迹」或「实施中未收口」的条目；**自述状态滞后（写着"待实施"但代码里已实现）的不进草稿箱**，直接按 A/B 处理。

### 3.2 A 类保留判据（必须**三条全过**，计划 §3.2）

1. **代码可对照**：结论能用 `rg` / `git log` 对到今天的代码或提交，且未失效；
2. **无替代者**：同一话题不存在更新的同类文档（若存在，二选一保留，另一篇进归档并注明被谁取代）；
3. **有读者**：装配方 / SDK 维护者 / 后续迭代确实需要（判据：被引用次数 ≥1，或属接口、规范、运行手册、指南类）。

> **反例警示**：`agent-sdk/runtime/` 属「原地保留 + 按 C 管理」——它代码不可对照（`wake_one`、`bWaitAll`、`namedQuota`、`quotaLease`、`callStateMachine` 全 0 命中且无实现提交），故只能是 C。**A 的判据是「目标形态今天仍成立且代码可对照」，不是「它在主题目录里」。**

### 3.3 B 类归档判据（命中其一即归档，计划 §3.3）

1. 实施计划且**已收口**（文档自述「已实施/已落地/Done」，或代码能证明已实现）；
2. 验收证据 / 复测门禁 / 阶段 todo / 逐提交审计 / 实施记录 → **一律归档**（属过程产物）；
3. **被显式取代**（文首有「现行替代」「已废弃，见 xxx」）；
4. 需求文档对应的功能**已上线且无未决项**。

### 3.4 矛盾消解规则（计划 §3.4）

1. **以代码为准**：先读代码确认现状，再决定哪份文档的结论还成立；
2. **以时间晚者为准**：两份都无代码冲突时取更晚修订的；被淘汰者进归档，头部注明「已被 `<新文档>` 取代」；
3. **不许留双入口**：主题目录里同一话题只能有一份现状文档，其余全部归档；
4. **冲突写进 history**：消解过程（谁与谁矛盾、依据什么判定）写进 `history.md` 对应条目，**不删掉不留痕**。

### 3.5 边界情形处置表（计划 §3.5）

| 情形 | 处置 |
| --- | --- |
| 功能已废弃（如 Plan 模式 4 篇需求、`plan_mode_optimization_design.md`） | **D**：进 `archive/desktop-ui/`，头部补「已废弃，见 `remove-plan-mode-requirement.md`」 |
| 已被取代（如 `file-write-directory-layout-requirement.md`） | **D**：归档，标注现行替代为工作产物管理 |
| 已完成但文档含长期价值（如 `security-policy-single-entry-requirement.md`） | **A**：改写为现状文档；原需求进归档 |
| 完成度自述与代码不符（首尾状态矛盾） | **以代码为准**归档，并在 history 记「文档状态自相矛盾，按代码判定为废弃」 |
| 阶段产物（`session-storage-a01…a12`、`i00…i11`、`c00…c01c`） | **B**：整批进 `archive/storage-session/`，仅 history 保留结论 |
| 本地过程产物（`docs/review/*`、`docs/analyze/*`） | 不动（§1） |
| 空文件（0 字节） | 删除（计划 §8-5） |

### 3.6 写现状文档的方法（**必读**）

**先 `ls` 全量、再按机制族归纳**——不要按「我记得的关键文件」写。实测教训：6 份现状文档中 3 份因「先写后查」而返工（`tools-mcp` 漏 2/3 件、MCP 传输层整族缺失；`im-remote` 漏 9 个机制族；`desktop-ui` 漏 `services` 的 7 族与整个 `store/` 切片）。

> **操作顺序**：① `ls <代码域>` 拿全量件 → ② 按机制族分组 → ③ 每组给一条可复现命令 → ④ 写 `baseline-check` 逐条复算。
> **判断依据**：现状文档的「完备」不看篇幅，看**能否用 `ls` 反查出一份不漏件的清单**。

## 4. 迭代记录规范（`history.md`）

### 4.1 定位（计划 §4.1）

`history.md` 只回答一个问题：**这个模块是怎么变成今天这样的**。它是**流水账**，不是计划、不是现状说明、不是路线图。

- 只写**已发生**的事（代码提交、文档定稿、口径变更、方案被否）；
- 不写「将来要做」「建议做」——那属于 `in-flight/` 或计划文档；
- 一条记录对应一个可复查的提交。

### 4.2 条目格式（计划 §4.2，五列）

| 列 | 要求 |
| --- | --- |
| **日期** | `YYYY-MM-DD`（取提交日期） |
| **提交** | 短 hash（可加分支名；合并类提交只记被合并的主提交） |
| **变更** | 一句话，**动词开头**，说清「改了什么行为」而非「改了哪个文件」 |
| **出处** | 链到需求/计划/评审文档（归档件给相对路径） |
| **影响与结果** | 契约/行为变化、遗留项、是否被后续推翻 |

条目按时间**正序**排列。

### 4.3 粒度与取舍（计划 §4.4）

- **默认一条 = 一次迭代**（一个计划文档对应的完整落地，可能含多个提交）——按 Phase 逐条列会在长主题上爆量；
- **允许单列**：契约/行为发生转向、被后续推翻、跨主题影响、事故修复；
- **聚合**：同一天同主题的琐碎提交（格式化、测试微调）合并为一条，注明「含 N 个提交」；
- **只读类、纯文档提交不进 history**（「口径变更」类除外）；
- 目标长度：一个主题 30–80 条；粗粒度主题（如 `agent-sdk`）必然更长，此时**按模块拆 history 分册**（`history-<模块>.md`，由 README 索引各分册），**而不是把主题拆细**——目录结构不动，只加文件。

### 4.4 存疑小节（计划 §1.4、§4.6）

冲突时**以 `git log` 为准**；文档与记录不一致的写进 history 的「存疑」小节，**不抹平**。

### 4.5 禁止事项（计划 §4.7）

1. 不把现状描述塞进 history（现状归现状文档）；
2. **不写无提交号 / 无日期的条目**（确无提交可挂的，不单列条目，并入相邻条目或写进「存疑」）；
3. 不写「预计」「即将」；
4. **不修改归档件的正文**来「对齐」history；
5. **不用行号当证据**。

### 4.6 取证命令（写进每个 history 文末，计划 §4.5）

```text
git log --oneline --date=short --format='%ad %h %s' -- <代码路径>              # 某模块全部提交
git log --oneline --date=short --format='%ad %h %s' -- docs/develop/<旧路径>   # 文档侧时间线
git log --diff-filter=R --summary --find-renames -- docs/                     # 核对搬迁痕迹
```

## 6. 执行流程

### 6.1 执行载体：独立 worktree（计划 §5.0）

整理本身**就是一次迭代**，不在 `main` 工作区直接改。

```bash
git worktree add .worktrees/docs-consolidation -b codex/docs-consolidation main
cd .worktrees/docs-consolidation
git log -1 --format='%h %ad %s' --date=short     # 记下开工基线，写进第一份核验记录
```

六条约定：

1. **基线锚定开工时的 `main`**：计划与核验记录都记这个值，中途 main 前进不追；
2. **每批一次提交**，提交信息带主题名（如 `docs(agent-sdk): 现状核验 + interface 归位`）；**搬迁与改写分开提交**，便于回退；
3. **merge 回 `main` 的时机**：每批自测（死链 + 索引可达）通过后即可 merge，或攒到终审后一次 merge——二选一，别中途反复 pick；
4. **整理产物必须落在入库路径**：`.gitignore` 忽略 `docs/analyze/`，worktree 内看不到该目录 → 清单、规则、核验记录、模板统一落 `docs/develop/_consolidation/`；
5. **收尾清理**：终审合并后 `git worktree remove`；顺带盘点 `.worktrees/` 陈旧残留，**不动他人正在使用的**；
6. **worktree 内不跑代码测试**：本轮只改文档，验证手段是死链检查与索引可达性。

### 6.2 阶段与 DoD（计划 §5）

| 阶段 | 内容 | 产出 | DoD |
| --- | --- | --- | --- |
| **Phase 0 冻结与立规** | 开 worktree；冻结基线；建主题骨架；定模板；**逐篇状态核验（§3.0）** | `docs-inventory.tsv`（路径/大小/自述状态/**代码证据**/实际状态/主题/去向 A·B·C·D/取代者/理由）、整理规则 | 全部文档有去向；自述与代码不符的已按代码更正；无「待定」残留 |
| **Phase 1 试点** | 选 1 个主题端到端跑通（优先 `tools-mcp` 或 `agent-sdk`） | 该主题 README + 现状文档 + history + archive + INDEX | 复核并确认模板与粒度后，据此修订模板 |
| **Phase 2 分类搬迁** | 按批 `git mv` 归档件；修全仓引用；补归档头 | 每批一次提交 | `git status` 干净；无死链 |
| **Phase 3 现状重写** | 逐主题核验（§6.5）后重写/合并现状文档；删失效描述；写核对基线与证据命令 | 每主题 1–3 份现状文档 + `baseline-check-<日期>.md` | 断言 100% 带命令；漂移/失效项已处置；抽查 3 条复算通过 |
| **Phase 4 history 编写** | 按 §4 生成时间线；与 `git log` 抽样核对（每主题抽 10 条） | 每主题 `history.md` | 抽查条目能在 git 中定位；存疑项已记录 |
| **Phase 5 总账与复核** | 建 `docs/develop/README.md`、`docs/requirement/README.md` 总索引；全仓链接复查；终审 | 两个总索引 + 终审记录 | 任一文档可从总索引两级点到；无指向已搬迁旧路径的链接 |

### 6.3 批次顺序（计划 §6）

| 批次 | 主题 | 顺序理由 |
| --- | --- | --- |
| 0 | 冻结 + 立规 | 没有清单就没法开工 |
| 1（试点） | `agent-sdk`（含 `interface/` 归位；`runtime/` 原地不动） | 已有 README/基准行范例，风险最低 |
| 2 | `storage-session`（最大） | 体量最大、最活跃，**单独成批**，按 a/c/i/r 分 3 个子批次，每子批 ≤15 篇 |
| 3 | `tools-mcp` + `safety-approval` | 两者互有引用（shell 安全边界、脚本安全策略、MCP 超时语义） |
| 4 | `im-remote` | 飞书/微信/远程三簇互相引用 |
| 5 | `desktop-ui` | 需引用 `agent-sdk` 与 `storage-session` 的结论，故排其后 |
| 6 | `knowledge-skills` + `platform-eng` + `architect` | 小主题收口；`architect` 只更新基准行与索引，不搬迁 |
| 7 | 专项：历史一次性项目整组归档 | `2026-10-01` 云 main 恢复 7 篇、`session-ced59b41` 3 篇、`session-d961cc51` 3 篇 |
| 8 | 总索引 + 终审 | 建两个总索引、全仓死链复查、终审 |

> 每批结束**停下来给用户复核**，比一次性做完再验收省返工。

### 6.4 每批收尾动作（计划 §5.1）

一次提交 = 一个批次（搬迁与改写分开提交）；提交信息带主题名；批次结束更新一次总索引，不中途反复改。

### 6.5 主题 baseline 核验流程（计划 §5.2，一轮 7 步）

| 步 | 动作 | 命令 / 产物 |
| --- | --- | --- |
| 1 | 读该主题现状文档头部声明的**核对基线** | — |
| 2 | 取变更窗口：基线之后该主题代码是否动过 | `git log --oneline <基线>..HEAD -- <主题代码路径>`；为空即记「一致（窗口内无变更）」 |
| 3 | 把现状文档结论拆成**可核验断言** A1…An（每条一个能判真假的句子） | 断言表落到 `baseline-check-<日期>.md` |
| 4 | 逐条核验 | `rg -n '<符号>' <文件>`、`git log -S'<符号>' -- <路径>`，必要时读关键函数 |
| 5 | 判定四类 | 一致 / **漂移**（文档旧于代码）/ **失效**（结论已不成立）/ **无法核验**（需真机、外部系统、真实 IM） |
| 6 | 处置 | 漂移 → 改写该条；失效 → 删除该条；两者都记 history；无法核验 → 标注 `待真机核验` |
| 7 | 出**核验记录**并挂到主题 README 索引 | `baseline-check-<日期>.md` |

**一轮 DoD**：断言 100% 带命令与实测；漂移/失效项 100% 已处置或转入 `in-flight/`；无法核验项逐条写明原因与复核条件；核验记录已进主题 README 索引。

**参与分工**：Agent 负责核验、记录、改写与回写 history；用户做**抽查**（每主题抽 3 条断言复算）与「无法核验 / 需产品决策」项的拍板。

**重跑时机**：该主题每次迭代收尾（或每次发版）后重跑一轮；核验记录**按日期累积、不覆盖**（旧记录用于看漂移趋势）。

### 6.6 合并回 `main` 的操作与风险（实测，2026-10-15）

`main` 在整理期间会前进（本轮实测：分支基点之后 `main` 又多了 **90+ 提交 / 473 个文件变更**），且其工作区常有他人或其他会话的在途改动。按下列顺序做：

**第一步：看清分叉与冲突面**

```text
git log --oneline main..<整理分支>            # 我领先 main 的提交
git log --oneline <整理分支>..main            # main 的「新东西」
git diff --name-only <基线>..<整理分支> | sort > /tmp/mine.txt
git diff --name-only <基线>..main     | sort > /tmp/theirs.txt
comm -12 /tmp/mine.txt /tmp/theirs.txt        # 双方都改过 = 潜在冲突（实测只有 2 个文件）
```

**第二步：在 worktree 内先把 `main` 合进整理分支**

```text
cd .worktrees/docs-consolidation
git merge main --no-edit        # 只在 worktree 内跑，不触碰 main 工作区
```

`git mv` 的搬迁 + `main` 的内容修改通常能自动合并（git 把修改跟着 rename 走）；实测 90+ 提交时**零冲突**。

**第三步：确认 `main` 工作区干净 —— 最容易卡住的一步**

`main` 工作区若有未提交改动，`fast-forward` 会因「要改动的文件有本地修改」而**被拒绝**。特别当那些未提交改动正好落在**你搬迁过的路径**上（例：他人正在改 `docs/develop/<某计划>.md`，而你已把它 `git mv` 进 `archive/`）。

→ **不要**擅自 `stash` / `checkout` / 提交他人的在途改动；**先向用户报告并请其处理**。

**第四步：合并后立即归位新增文档**

`main` 上的新文档会落在**旧位置**（平铺于 `docs/develop/`、`docs/requirement/` 根下）。合并后必须逐篇按 §3.0 / §3.1 判归属并 `git mv` 到主题目录，同时更新：`docs-inventory.tsv`、`archive/INDEX.md` 计数、对应主题 `README.md`，必要时 `需求基线.md`。

**第五步**：合并前后各跑一次死链检查（口径见 §7.4）。

## 7. 质量门禁与验收

### 7.1 每批自测（本地可验证）

| 项 | 手段 |
| --- | --- |
| 死链检查（旧路径引用清零） | `rg` 搜旧路径，逐条改指 |
| 索引可达（两级点到） | 从总索引 → 主题 README → 文档，人工走一遍 |
| 搬迁痕迹 | `git log --diff-filter=R --summary --find-renames -- docs/` |
| `git status` 干净 | 无残留半成品 |
| inventory 覆盖 | 当轮全部文档均有去向（对照 `docs-inventory.tsv` 实际篇数） |

### 7.2 整体验收标准（计划 §5 末尾，四条）

1. 四个目录里任一篇文档都能回答「**它为什么存在、依据哪个基线、被什么取代**」；
2. 同主题**不存在两份互相矛盾的现状描述**；
3. 每个主题的 `history.md` 时间线与 `git log` **抽样一致**；
4. 归档件**可反查**（旧路径 → 新路径有索引）。

### 7.3 验收标准 ②③ 的执行细则

**② 双入口检查（同主题不得有两份矛盾的现状描述）**

1. 列出该主题内所有同类文档（含已归档的源文档）；
2. 对可疑的重叠对，**读原文**判断是否同一问题域 —— **「话题相邻」不等于「双入口」**；
3. 实例（本轮）：`渲染进程卡顿优化方案.md`（管**工具调用高频事件**链路）与 `streaming-ui-performance-analysis.md`（管**流式 token 渲染**链路）—— 问题域不同，**不构成双入口**；结论写进 `baseline-check` 的「矛盾与时间线检查」节，现状文档按问题域拆成两条主线；
4. 若确为同一话题 → 按 §3.4 消解（以代码为准、以时间晚者为准），被淘汰者归档并在 `history.md` 留痕。

**③ history 与 `git log` 抽样一致**

1. 每主题抽 3–10 条时间线条目；
2. `git log --oneline -1 <短hash>` 验证该提交存在，且 `--format='%ad %s'` 与条目的「日期 + 变更」对得上；
3. 抽样结论写进该主题 `baseline-check` 的「矛盾与时间线检查」节。

### 7.4 死链检查的具体口径

用脚本解析每篇 `.md` 的 `](目标)` 并判定存在性，**排除三类**：

| 类别 | 理由 |
| --- | --- |
| `/archive/` 内的链接 | §2.4「内容零改动」：相对链接按搬迁前布局书写，断链属**预期** |
| `_consolidation/` 内的链接 | 模板占位符（`./<模块>-现状.md` 等）与记录示例，**不是真链接** |
| 目标落在**未入库目录**（`docs/review/`、`docs/analyze/`、`docs/references/` 等） | §1 只引用不搬迁；本地存在即不算断 |

余下按性质分三类处置：**搬迁引入**（必修，逐条改指新路径）／**原本即断**（接受，记入 `_consolidation/dead-links-<日期>.md`）／**边界目录内**（`docs/废弃/`、`docs/i18n/` 等，本轮不动）。

> 实测口径（2026-10-15）：456 篇 → 活跃断链 76 → 修复 7 处（3 处链接多写一层 `../`、4 处代码引用缺 `../../../`）后，余 69 处全属「预期 / 原本即断 / 边界目录内」。
