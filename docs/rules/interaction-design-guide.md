# 交互设计指南

> **定位**：`docs/rules/` 的专题指南之一（元方法）——管**行为层**：用户与 Agent 之间"什么时候问、默认怎么走、批准算多久"。
> **覆盖范围**：**行为层**——什么时候问、默认怎么走、批准算多久、设置项该不该加。**不覆盖**：呈现层（组件 / 图标 / 样式 / 文案排版）、需求文档的写法、契约与代码实现。
> **核心工具**：`$impeccable` —— **交互方案出炉时扫方案，前端实现完成后扫新增界面元素**（见 §2，两个检查点）。
> **本版范围（v0.1）**：覆盖两类交互——**确认与打断**（I1–I5）、**设置项与开关**（I6–I7）。未覆盖的主题清单见 [`-sources.md`](interaction-design-guide-sources.md)（**未补证据前不写规则**）。
> **来源与维护**：见 [`-sources.md`](interaction-design-guide-sources.md)（按需查阅，日常不必加载）。
> **一句话**：交互里的取舍（打断频率、默认行为、误触容忍度）**没有证据答案**，只能由人定；本指南的作用是给这些决定一套统一判据与检查点。

## 0. 三条前提

1. **交互决策属于人，机制实现属于方案。** 判定句：**把它删掉，用户是否毫无察觉？** 是——那不是交互问题（校验、绑定、编解码格式、执行顺序都属技术方案规格层）。
2. **交互必须给出唯一行为。** 判定句：**同一段交互描述，设计者能否做出两种都合规的实现？能，就是没写完。**
3. **规则没有应急例外。** 交互决策处在需求 / 设计的上游，本指南**不为"时间紧""先实现后补"留通道**。确实排不开时，正确的处理是**推迟这项能力**（保持默认实现），而不是先斩后奏——需要靠例外才能推进，本身就是排期问题，不是规则问题。

## 1. 核心行为规则（I1–I7）

### 1.1 确认与打断（I1–I5）

**I1｜什么时候必须问、什么时候不该问？**
- 触发条件是"**存在两个以上合理选择，且不同选择会产生用户可感知的重要差异**"；不是"只要会有影响就问"——后者会退化成逐项询问，把"不重复确认"的目标架空。
- 用户意图与惯例足够明确时用默认，只在结果处展示，不打断。
- 两条禁令：**不得用猜测代替询问**；**不得"先做再让用户纠正"**。

**I2｜打断的粒度与频率是什么？**
- 一次确认覆盖的范围：同一用途的一组，而不是逐个。
- "首次 / 每次"的口径：每会话、每工作区、还是每次检测。
- 同一对象的持续编辑、用户本轮明确要求修改的：不重复确认。

**I3｜不问、拒绝、取消、超时各自会怎样？**
- 四条路径都要有确定答案：继续（以不需该动作的方式完成）、部分完成、还是明确告知哪部分无法完成。
- 不能只写"不创建""不保存"就结束。

**I4｜用户批准的到底是什么，批准后还算不算数？**
- **用户看到并批准的对象，就是系统实际执行的对象**：出现"提示 A、执行 B"（确认后对象被静默改名、改址、替换）即是用户可感知的缺陷。
- 一次性批准 ≠ 长期授权；"记住 / 以后不再询问"必须是独立、事前明确的选择，并可撤销。
- 存在多个候选时，用户必须能明确指向所批准的那一件；含糊表述不得当成批准。

**I5｜默认值有没有留白？打断的成本写了吗？**
- 不留并列默认（"关闭**或**保持"这类写法）。定不下来的进开放决策表，标明必须在哪个节点前选定。
- 打断是有成本的产品资源：写清频率上限或记忆范围、误触可能，以及用户不回应 / 询问失败时的降级行为。

### 1.2 设置项与开关（I6–I7）

> 背景：**实现逻辑等效 ≠ 体验等效。** 同一件事常有多个实现上等价的方案，但从用户场景看它们有主次：多数情况下存在一个明显更合适的默认，加开关只是把"本该由设计做的决定"转嫁给用户。**Agent 在实现过程中"顺手加一个开关"是最常见的越权行为之一。**

**I6｜默认优先：先问"是否存在明显更好的那一个"**
- 新增任何开关前，先回答：**它解决什么问题、影响谁、两个取值各自服务什么场景、是否有一项在绝大多数场景下都更好？**
- 存在明显更优项时：**直接定默认，不做开关**——把差异写进产品行为，而不是交给用户配置。
- 开关只用于"偏好确实分叉、且无法从场景或惯例推断"的情况；能用更好的交互解决（分组、预设档位、渐进披露）时，不用开关。

**I7｜新增开关必须取得人类产品决策者的明确审批**
- **Agent 不得自行新增**设置项 / 开关 / 配置字段，包括"顺手加一个默认关闭的开关"。
- 提交审批时必须给出四项：① 本质作用与影响面（谁会改、改了会怎样）；② 为什么不能定默认；③ 候选方案与取舍（定默认 / 换成更好的交互 / 加开关）；④ 代价（用户认知成本、组合爆炸、文档与 i18n、后续迁移）。
- **未获明确审批不得落地，本规则无例外。** 不接受"先加上、之后再补审批"，也不接受以"时间紧"为由先做；确实排不开时，处理方式是**推迟这个开关**、保持默认实现（§0-3）。

**开关的成本（写进论证，而不是当口头禅）**
- **认知成本**：用户被迫理解一个本不该由他决定的取舍；
- **组合爆炸**：开关两两组合后的行为矩阵与测试面；
- **长期负债**：仓库既有教训——全局开关一旦存在，安全语义就要额外收敛；"覆盖通用设置"式开关被评审明确记为回退风险；"设置开关不能替代授权范围的明确表达"。

## 2. 核心工具与两个必过检查点：Impeccable

**工具**：`$impeccable` skill（仓库内安装于 `.claude/skills/impeccable/`，hook 状态在 `.impeccable/`；来源与版本锁定见 [`-sources.md`](interaction-design-guide-sources.md)）。

**检查点 A｜交互方案出炉时（写方案 / 需求阶段）**

- 先加载**项目视觉上下文**与该场景的参考（例如桌面操作型 Operate 场景），把现有组件、主题 token、样式作为视觉基线；再对交互方案本身做一次有范围的审查：层级与锚点、可扫读性、状态齐全（hover / focus / disabled / 处理中 / 失败）、键盘可用、窄布局、与既有视觉体系是否一致。
- 产出：所检查的文件与规范基线、发现清单、结论。

**检查点 B｜前端实现完成后（提交评审前）**

- 对**新增 / 改动的界面元素**再扫一遍，看是否存在绕过项目视觉规范的硬编码与风格偏离。hook 会把命中项记入 `.impeccable/hook.cache.json`，形如 `design-system-color:<行号>:<值>` / `design-system-radius:…` / `design-system-font-size:…`；确认无问题的文件标记为已确认。
- 产出：发现清单 + 修正项；**未修项必须逐条写明理由**。

**硬约束**

1. 视觉修正必须沿用既有 token / 组件约定，**不得新增无必要的局部设计变量**。
2. 阻断性的可访问性或溢出问题**不得**以"不修"豁免。
3. 不得借审查重做范围外的界面。

**完成判据**

- [ ] 审查前已加载项目视觉上下文与对应场景参考，并记录所检查的文件与主要规范
- [ ] 对新增 / 改动界面完成一次有范围的视觉与交互审查（菜单层级 / 锚点 / 间距、图标与文案对齐、hover / focus / disabled、颜色对比、处理中与失败反馈、中英文文本长度）
- [ ] 在项目支持的窗口宽度 / 布局下检查（窄窗口、长文本、多元素并存、多行输入、运行状态），无遮挡、裁切、横向溢出或脱离锚点
- [ ] 按发现修正样式，间距 / 字体 / 圆角 / 颜色 / 边框 / 阴影 / 交互反馈沿用既有约定
- [ ] 修正后复查同一状态集合；未修项已逐条记录理由与影响

## 3. 检查清单（设计或评审任一交互时使用）

1. 每个确认点都能回答：**为什么必须问、不问会怎样**（I1）。
2. 单次会话的打断次数有上限预期，或说明了记忆范围（I2、I5）。
3. 不回应 / 拒绝 / 取消 / 超时四条路径都有答案（I3）。
4. 提示内容与实际执行一致；批准的范围与时效明确（I4）。
5. 没有并列默认值；打断的成本与降级行为已写（I5）。
6. **涉及界面的改动过了 `$impeccable` 两个检查点**（方案期、实现后），发现清单与未修理由已记录（§2）。
7. **本次没有新增设置项 / 开关**；若新增，已按 I6 论证过"为什么不能定默认"，并按 I7 取得产品决策者的明确审批（附审批记录）。
