# 文档写作指南（元指南）

> **定位**：管**文档怎么写**，分两层 —— ① **元方法层**：`docs/rules/` 这一层是"某类具有通用性的问题怎么做"的**元方法**（写需求、写技术方案、写执行计划、设计交互、整理文档库……），本指南管**这些元方法本身该怎么写**：结构分层、正文与 sources 的归属、动作导向写法、加载层次与路由、迁移与修订记录（§1–§7）；② **通用文档层**：一切**要交给人决策或评审的文档**（需求、技术方案、执行计划、设计说明）共用的写法 —— 读者分层与人机分工、写作流程与门禁、人类决策层规则 R1–R8（§8–§11）。
> **三层**：元方法（各专题篇）｜**元方法的元方法（本文件）**｜元方法的目录（[`README.md`](README.md)）。
> **篇内路由**：写 / 改指南或长期规范文档 → §1–§7；写需求 / 技术方案 / 执行计划等交付文档 → §8–§11（**通用层**，专题篇不重复定义）；维护与迁移 → §5 + 本文件的 `-sources.md`。
> **覆盖范围**：怎么写一份指南 / 长期规范文档（含本系列自身），以及交付文档共用的通用写法。**不覆盖**：具体领域的规则（在各专题指南里）、`docs/` 文档库的组织（在 [`docs-guide.md`](docs-guide.md)）。
> **来源与维护**：见 [`-sources.md`](document-writing-guide-sources.md)（按需查阅，日常不必加载）。
> **一句话**：文档是**给执行者的动作清单 + 给决策人的决策界面**，不是知识汇编；合格判据只有一条 —— **读者照着它能做出唯一行为**。

## 0. 两条前提

1. **读者是执行者（人 + Agent），不是来学习的读者。** 每条规则都要能落到一次具体动作上；不能执行的内容（背景、感慨、来源考证）不进正文。
2. **同一条规则只在一处定义**，其余位置引用。重复定义必然漂移——本轮就抓到过同一规则散在 4 个文件里的实例（见 sources）。

## 1. 两层结构：正文 + `-sources.md`

| | 正文（`X-guide.md`） | 来源附录（`X-guide-sources.md`） |
|---|---|---|
| 读者 | **使用者**：写方案 / 需求 / 交互的人 | **维护者**：审计、修订、追溯的人 |
| 内容 | 动作、判据、检查清单、工具的调用方式与状态位置 | 出处与先例路径、来源与版本锁定、抽样口径、未覆盖主题（待办）、维护要求、被精简的举证、修订记录 |
| 加载方式 | 任务开始整篇加载 | 按需；文件头声明"日常不必加载" |
| 篇幅纪律 | 按"整篇加载"估算成本，只放动作 | 不限，但按主题分节、可检索 |

## 2. 内容归属判据

- **判据 A（主判据）：这条规则是给"使用者"还是给"维护者"？** 给维护者 → `-sources.md`。
- **判据 B（跨层判据）：删掉它，目标读者是否有感？** 无感 → 不属于该层（例如用户感知不到的机制要求，属于技术方案的规格层，不属于需求）。
- **A 的细化**：出处（先例路径、来源仓库、版本锁定）进 sources；**"怎么用"留在正文**（工具名、调用方式、状态文件位置——排查时要用）。

归属对照（本轮实际用过的例子）：

| 内容 | 归属 |
|---|---|
| 完成判据、检查清单、触发条件 | 正文 |
| 工具调用方式、hook 状态文件位置 | 正文 |
| "完成判据沿用某处先例 P3-T5"、"来源 pbakaus/impeccable，锁在 skills-lock.json" | sources |
| 未覆盖主题清单、"新增规则前先抽样取证" | sources（维护者待办） |
| 修订记录（含被否决的写法） | sources |

**判据 C（本层准入：通用性）**：这条内容是**元方法**（某类具有通用性的问题怎么做），还是**某模块 / 某工程的实现细节**？后者一律进对应主题目录（`docs/develop/<主题>/`），**不进 `docs/rules/`**。

- 反例（应进主题目录）：IM 链路日志排障 → `docs/develop/im-remote/`；构建与打包细则 → `docs/develop/platform-eng/`；UI 图标来源与新增流程 → `docs/develop/desktop-ui/`。
- 正例（属本层）：需求怎么写、执行计划怎么排、交互怎么定、文档库怎么组织。
- **配套三条**：① **外移前先查既有落点**——本次实测发现 IM 现状文档与 `AGENTS.md` 早已互相引用，直接新建文件会制造新的双入口；② **能由代码可靠读出的清单（如 IPC 通道名）不文档化**，只留"去哪读"——文档化即腐化；③ 若 `AGENTS.md` 与既有主题文档重叠（i18n、UI 约定都属于此），`AGENTS.md` 只留**速查要点 + 指针**，细节归主题文档——高频内容可以常驻，但**不得重复定义**。

## 3. 动作导向的写法

1. **规则 = 要求 + 反例 + 检查方法**；能机械筛查的（`rg` 模式）优于靠记忆的。
2. **能挂到流程某一步的才收**；挂不上的多半是"症状描述"，删而不收（技术方案指南 §6 与 sources 维护规则即此判据）。
3. **不写口号**。"证据先于叙述"这类抽象条目无法执行；换成"哪一步做什么 + 判定句"。
4. **判定句优先**：能写成自检问句的规则最耐用（如"同一句话，设计者能否做出两种都合规的实现？能，就是没写完"）。
5. **编号**：每篇独立编号空间（`R*` / `I*` / `Q*` …）；跨篇引用写"篇名 + 编号"；**不引用行号**（行号是快照，引用基线提交或写可复现命令）。**内容迁移到大篇时重新编号**（例：原 §5.1–5.6 → 新 §1–§6），并在原位置留指针（§5-1）。

## 4. 上下文预算与按需加载

**前提**：指南会被注入上下文，**整篇加载是常态**（Agent 通常一次读全文；人也很少只读半篇）。因此"写了但本次用不上"的内容不是免费背景，而是**每次任务重复付费**。设计文档时先设计**加载层次**，再写内容。

### 4.1 四个加载层

| 层 | 内容 | 加载时机 | 规模要求 |
|---|---|---|---|
| **入口层** | "什么任务读哪个文件"的路由（现由 [`README.md`](README.md) 承担；`AGENTS.md` 只保留一行指引） | 每次任务 | 极薄：一行一条，不写好话 |
| **任务层**（正文） | 该任务真正要用的动作与判据 | 按任务类型：**通用层**（本文件 §8–§11；凡交付人决策 / 评审的文档必读）+ **一篇专题篇** | 只放该任务用得上的 |
| **场景层** | 只在部分情形才用得上的内容（如"改设置界面时才读""动界面才做 Impeccable 扫描"） | 按情形 | 拆成独立文件，或加路由句 + 可跳过标注 |
| **证据层**（`-sources.md`） | 出处、口径、举证、维护规则、修订记录 | 审计 / 修订时 | 不限，但分节可检索 |

### 4.2 拆文件还是拆小节：看**加载方能否定位**

- **加载方无法定位**（整篇读取、或被清单整篇注入）→ **必须拆文件**，否则每次都要付全额。
- **加载方能定位**（人按标题跳读；Agent 能用 `grep` / 分段读）→ 可留在同一文件，但**必须在文件头部给路由句**。
- 拆文件有代价：引用跳转变多，且容易演变成"同一规则两处定义"。因此**只拆边界清晰、很少需要交叉引用的部分**；有强交叉引用的内容留在同一文件，用路由句解决。

### 4.3 路由：**导航集中，指针就地**

- **导航集中在唯一入口**："这个任务要读哪些文件、按什么顺序读"只在 [`README.md`](README.md)（**元方法目录**：任务 → 文件 + 定位 + sources 时机）。`AGENTS.md` 只保留**一行指引**与跨文档硬纪律——它是每次加载的位置，把明细也放那里等于路由存在两份（2026-10-16 实测压缩掉约 2.5KB）。
- **规则归属指针就地写**：正文用到另一篇的规则时，直接写「判据见《X》§n」。**指针指规则，不指读物**。三条约束：
  1. **不做导读**：不列"相关篇目 / 阅读顺序"清单——选哪些篇来读属于入口层；正文只在**需要那条规则的地方**给篇名 + 编号（同一指针重复出现时，首次给链接即可）；
  2. **不复制**：被指内容不另写一份（复制即两处定义，见 §0-2）；
  3. **单向、不闭环**：被指篇不反向指回同一规则——规则真源只有一处，避免"读 A 要先读 B、读 B 要先读 A"。
- **禁止的仍是两类**：① 篇头 / 篇尾的**导读清单**（哪些篇一起读、按什么顺序读）；② **双向互链**与"改一处要同步 N 处"的网状引用——N 篇两两引用会产生 N² 条链接，而且藏在元信息块里的链接会被整段跳过（实测发生过）。
- **篇内路由允许且鼓励**：可选小节用下面这行标注，服务于"已加载本篇后决定读多少"：

```markdown
> 篇内路由：只做 X 读 §a、§b；做 Y 时再读 §c，其余可跳过。
```

**判据：导航问入口层；规则定义在哪，就近指到哪；不复制、只单向。** `-sources.md` 属证据层，维护者之间的追溯引用不受本节限制。

**不常读的内容不得以"以后可能有用"留在正文**——去处是 `-sources.md` 或独立文件。

### 4.4 加进正文前的三问

1. **本次任务的读者会用到它吗？** 用不到 → sources 或独立文件。
2. **它是给使用者还是维护者？** 维护者 → sources（§2 判据 A）。
3. **加上它，正文的常驻成本涨多少，值吗？**

**长度纪律（两条并存，别只取一条）**：人类可见层**设信息下限**（要自包含，不为压行数丢背景，见 §10 的 R3）；必读正文**设成本上限**（用"拆出去"而不是"砍掉背景"来控制总量）。

## 5. 版本、迁移与修订记录

1. **同一规则迁移**：新位置写规则（按 §3-5 **重新编号**），**旧位置留指针**，sources 记"从哪搬到哪、为什么、用什么判据"。**依据条目随内容一次性迁移**到新篇的 `-sources.md`（原处留指针）——不留"正文在 B 篇、依据仍在 A 篇"的中间态。
2. **改动与搬迁分开**（沿用 `docs-guide` 的提交纪律）。
3. **被否决过的写法要留痕**：例如"时间紧时的应急例外"被明确否决，就要记下来，否则后人会再提一遍。
4. 规则被新证据推翻：**先改正文，再在 sources 记结论变化与证据**。

## 6. 新增一篇专题指南之前

1. **先抽样取证**：回 `docs/review` 看这一类问题集中在哪；没有证据的主题不写规则。
2. **先判层**：呈现层 / 行为层 / 文档层 / 实现层，避免与既有指南重叠；重叠时先判"层归属错误"还是"规则写错"。
3. **先设计加载层次**（§4.1）：一开始就决定哪些内容进正文、哪些拆成场景文件、哪些留 sources，并给正文写路由句——**不要写完再想办法瘦身**。
4. **命名成对**：`X-guide.md` + `X-guide-sources.md`。
5. **登记入口**：更新 [`README.md`](README.md)（元方法目录：新增/改名篇目各一行）与 `docs-guide` §9.1 的文件清单（否则后人找不到）；`AGENTS.md` 的一行指引保持成立。
6. **复查常驻成本**：存在**只在一部分任务中需要**的完整主章节（≥1 个）时，即按 §4.2 判断拆分；行数只作参考信号（当前样本：一篇 284 行的指南拆为 163 + 99 行，两端加载量分别降约 43% / 65%）。

## 7. 检查清单（写完或改完一篇指南后逐条过）

1. 正文里每一条都是**使用者能执行的动作或判据**；没有维护者待办、没有出处考证。
2. 出处、先例、来源锁定、未覆盖主题、维护规则、举证、修订记录都在 `-sources.md`。
3. 同一条规则在整个系列里**只定义一次**；其余位置是指针而非复制。
4. 每条规则都有反例或判定句；没有口号式条目；挂不上流程步骤的已删除。
5. 编号唯一，跨篇引用带篇名；全文无行号引用。
6. 涉及迁移或否决时，已在对应 sources 留下记录。
7. 新增或重命名文件后，**入口已同步**：`docs/rules/README.md`（元方法目录，新增/改名篇目各一行）+ `AGENTS.md` 的一行指引仍然成立（`docs-guide` §9.1 的用途清单也同步）。
8. 已按 §4 判断加载层次：不常读的内容已外移或拆出；内容多时正文头部有**篇内路由**句；跨文件只留**单向、就地**的规则归属指针（导航只在入口层，不列相关篇目清单）；没有"以后可能有用"式的堆积。
9. 涉及拆分 / 迁移时：新篇已在**入口层**登记（`AGENTS.md` 短表 + `README.md`），原篇留指针且已重新编号，依据条目已随迁，**新篇不反向指回原篇**。

# 通用文档层（§8–§11）

> **适用**：一切**要交给人决策或评审**的文档 —— 需求、技术方案、执行计划、设计说明。纯过程记录（`history.md`、评审记录）不适用。
> **用法**：专题篇说明**本类文档各层放什么、产出物叫什么**；通用规则（分层、分工、流程、R1–R8、自检）只在本层定义，专题篇不重复。

## 8. 读者分层与人机分工

### 8.1 三层读者与合格判据

| 层 | 读者 | 语言 | 合格判据 |
|---|---|---|---|
| **第 0 层 决策层** | 决策人、负责人（不读代码、只看这一层） | **只用业务语言** | 每个决策项**不打开任何其他文档即可裁决** |
| **第 1 层 概要层** | 人机共读 | 允许工程词，首次出现给一句释义 | 能判断"方向与风险是否可接受" |
| **第 2 层 规格层** | 实现者 / 评审 Agent | 内部语言不设限 | 每条可核查、可执行、可复现 |
| 附录（证据 / 核销 / 未验证项） | 追溯与复核 | 命令与原始证据 | 每条断言带复现命令与基线 |

篇幅纪律：第 0 层**设信息下限、不设行数上限**（§10 R3）；第 1 层宜短，内容多就下移；第 2 层与附录不限。

### 8.2 第 0 层的固定骨架

```markdown
一句话：问题是什么、本次改了什么（不含内部词）
只有 3 分钟的话：先读哪几项
需要你决定的事项：D1..Dn（写法见 §10）
不需要你决定（Agent 负责；写出来是为了不占用你的时间）
```

### 8.3 人机分工按能力划，不按篇幅划

| 只有人能决定（必须进第 0 层） | Agent 该自己做完（不该占人时间） |
|---|---|
| 价值排序：先做哪个、不做哪个 | 事实核查：现状到底是不是这样（带命令可复核） |
| 体验取舍：两种行为差异，用户更喜欢哪个 | 逻辑闭合：类型 / 字段 / 状态转移是否自洽 |
| 风险容忍：这点安全回归换那点体验，值不值 | 边界推演：竞态、崩溃、重复、取消、旧数据 |
| 不可逆承诺：迁移、删除、外部对接、排期 | 机制设计：屏障、幂等键、补偿、回滚 |
| 对"未验证假设"拍板：接受风险还是先验证 | 验收覆盖与用例可达性 |

判据：**能被证据回答的问题不是决策项**。把"我还没查的事实"包装成"请你决策"，是最常见的浪费人力的方式。

### 8.4 读者标记与 ID 体系

- **读者标记**：每节标题后标注 `【人必读】` / `【人机共读】` / `【机｜人工可跳过】`。人读不完，往往是因为不知道该跳过什么。
- **ID 体系**：每类实体一套 ID（决策 `D-*`、验收 `AC-*`、不变量 `INV-*`、事实 `F-*`……），**互相引用而不互相复制**；真源唯一，第 0 层只指向、不重写；层与层之间必须**可双向追溯**（"这个决策变了，哪些规格与验收随之失效"要答得上）。

## 9. 写作流程与门禁

每一步的产出是下一步的输入；**缺产出不得进入下一步**。产出物名称按专题篇的叫法。

| 步 | 动作 | 产出物 | 门禁 |
|---|---|---|---|
| 0 立项 | 从用户目标写可观测结果；写"不做清单" | 验收边界卡 | 目标能用一句可观测的话表述 |
| 1 事实 | **先查后写**：`ls` 拿全量 + 读代码；每条断言带基线提交与复现命令 | 事实卡 + **绕过通道清单**（哪些入口不经过你要建的那道门） | 不存在"我记得"式断言 |
| 2 模型 | 先写不变量、状态与所有权矩阵、生命周期与崩溃恢复路径 | 模型卡 | 每个状态有唯一 writer、唯一提交点、唯一恢复者 |
| 3 契约 | 术语一名一义；类型 / 字段 / 错误码 / 缺省值定到唯一位置 | 契约卡 + 术语表 | 文档内闭合；同一算法不在两处描述 |
| 4 反例 | 自扮评审：按场景矩阵（正常 / 并发 / 超时 / 取消 / 重启 / 重复 / 乱序 / 部分失败 / 旧数据）逐格走，写结论或"不适用 + 理由" | 场景矩阵 + 决策记录 | **不存在两种都合规的解读** |
| 5 验收 | 从目标正向推 `AC-*` → 可执行断言 → 用例（含竞态与故障注入） | 验收映射表（AC ↔ INV ↔ 用例） | 每条 AC 有可达用例；不用代码形态指标代替行为证据 |
| 6 阶段 / 范围 | 按文档类型落：方案写阶段与迁移，需求写范围三清单 | 阶段表 / 范围清单 | 每阶段可独立验收、可回退；非目标与目标不互相抵消 |
| 7 自评 | 实现者视角复读 + pre-mortem | 未验证 / 待定 / 需人拍板清单 | 没有"我不确定却写成确定"的句子 |

**第 2 步（模型）与第 4 步（反例）最容易被跳过，也是评审火力最集中的两步。** 各专题篇只给本类文档的产出物与门禁**差异**。

## 10. 人类决策层写作规则（R1–R8）

> 人类层不是第 2 层的**摘要**，而是独立的**决策界面**。摘要追求"少信息"，界面追求"自足"——这是下面各条的共同出发点。
> **适用对象是"裁决条目"：文档中任何要求读者做取舍或批准的条目** —— 决策项 `D-*`、边界与选项清单、不可逆承诺、门禁取舍、开关审批……**不限第 0 层**。第 0 层只是它们最集中的地方；散在正文里、作者以为"技术读者能懂"而实际由人拍板的条目，是最常见也最容易漏的一类。

**R1｜只用业务语言，内部标识只出现在"下钻"入口**
- 要求：禁用代码标识符、模块名、内部编号；无法回避时写「业务说法（内部：xxx）」，或移到行末下钻。业务词（微信、审批、档位）可保留，首次出现给一句释义。
- 反例：`标准档允许「安全审核 Agent」批准 outbound 发送吗？`
- 正例：`标准档要不要允许「安全审核 Agent」替人点头，把消息或数据发给外部渠道？`
- 检查（近似筛查，命中后人工判定）：
  ```
  rg -n '`[^`]+`|[a-z]+[A-Z][A-Za-z]*|[A-Z]{2,}|§' <裁决条目所在区段>
  ```

**R2｜裁决条目自包含：不打开任何其他文档即可裁决**
每条裁决条目必须含六要素：①背景（这件事是什么、影响谁）②要决定什么（A/B 选项）③每个选项的后果（用户可见 / 不可见、代价；写法见 R5）④可逆性 ⑤依据强度（哪些已验证、哪些没数据）⑥推荐 + "你不决定时默认怎么走"。
- 反例：`范围取舍：本轮是否就并入 remote policy 对账（P2-06）与新建底线登记 registry（P3-01~05）？`——读者必须翻到 §3 / §5 才知道在决定什么。
- 正例：先用两句解释"远程工具目前有一套独立的放行判断，与桌面共用的一套规则其实是两套实现，改一边容易漏另一边"，再给 A/B 与代价。
- 检查（唯一可靠的是人测）：把单条**单独摘出来**发给没参与项目的人（或隔天自己读），记录他提出的疑问数；**目标为 0**。

**R3｜长度设下限，不设上限**
- 合格标准是"六要素齐全"，不是"行数少"。行数只作反向信号：超过约 10 行的 D 项，检查是否该拆成两个决策。
- 反例：为把人类层压到某个行数目标而删掉背景——那是**把作者的理解成本推给读者**；正确方向相反：宁可加长，也要让决策人自足。

**R4｜编号只做下钻，不承担说明职责**
- `B-01`、`P2-06`、`§2.2` 只能出现在行末「下钻：」里。编号对作者是索引，对读者是谜语。

**R5｜写后果，不写机制**
- "选 A 会怎样"用用户能感知的差异表述（会不会被打断、能不能撤回、会不会改错文件）；机制词（许可、摘要、原子写）只在解释"为什么不可逆 / 为什么安全"时出现。

**R6｜同一概念全篇同一业务词**
- 不要一处写 `outbound`、一处写"对外发送"。在交付文档附录维护一张"业务词 → 内部词"对照表（起步示例见 `-sources.md`）。

**R7｜可裁决性检验：不翻代码、不读其他文档，就能回答"选哪个、代价是什么、不决定会怎样"**
- 要求：裁决条目要写成**"破坏了会怎么表现"**，不写**"内部命题名"**。命题名（单一真源、canonical 流、端口、事务封装、幂等键、不变量、适配器）对作者是压缩，对读者是一项任务——必须翻译成用户 / 数据 / 渠道上可见的表现。
- 与 R1 的分工：R1 抓**外部标识符**（代码符号、模块名、编号）；R7 抓**内部命题名**（中文技术术语）。
- 反例：`canonical 事件流是模型面事实的唯一真源，消息表与 UI 不得各自维护第二份。`——读者要先去翻源码，才知道"现在到底存了几份、不这么定会怎样"。
- 正例：`同一次对话的内容现在被分别保存在几处（模型那份、数据库那份、界面那份）。请决定：允许多处各自保存，还是规定只有一处保存、其余都从它派生？选"各自保存"——改动其中一处时另两处可能没跟上，表现为历史消息对不上、界面显示的与模型记得的不一致；选"单一来源"——所有改动都要经过同一处，短期改动成本上升。你不决定时默认：维持现状，但涉及写入的改动必须标注影响面。`
- 检查：
  1. **"3 个月后的自己"测试**：隔一段时间、没跟进这块的读者能否直接裁决？不能 → **改写条目，不是加解释**。
  2. 内部命题名筛查（命中即逐条改写）：
     ```
     rg -n 'canonical|单一真源|真源|端口|事务|幂等|不变量|封装|适配器' <裁决条目所在区段>
     ```
- 反面情形要认出：**把调研结论的压缩包当作交付物**——"我调研完，把结论递给你"不是决策界面；读者看不懂时，实际发生的是**设计权被默认交给作者**。

**R8｜不得用"推荐默认值 / 建议 / 视情况"绕过裁决**
- 要求：只有**可逆、无界面、无外部行为**的内容才可以用"推荐默认值"承载。出现下列任何一项，**必须写成裁决条目（R1–R7）并由人批**：
  1. 新增或改动**界面**（含状态展示、列表、面板、提示、展开查看）；
  2. 新增或改动**开关 / 配置项**（含会话级、默认开启、隐藏式的）；
  3. **数据格式、持久化字段、迁移**；
  4. **IPC / 对外接口**；
  5. **外部渠道行为**（IM、远程、真机路径）。
- 反例：需求把"用户可查看某次请求实际采用的只读快照和加载原因"写成"状态与可观测性"条目，并声明"其余推荐默认值不代表用户已确认全部产品取舍"——界面要求以"推荐值"身份通过审批，实现阶段由写代码的 Agent 决定界面放哪、长什么样。**"其余为推荐默认值"不能当界面 / 开关 / 格式的通行证。**
- 检查：搜出文档里的"推荐默认 / 建议 / 视情况 / 可选"，逐条看是否落在上列五类；命中即升为裁决条目。

## 11. 交付前自检（通用层）

1. 裁决条目（含第 0 层）：每条六要素齐全，能单独摘出来给外行裁决（疑问数 = 0）。
2. 裁决条目：无代码标识符、模块名、内部编号；编号仅在"下钻"。
3. 第 0 层：写清了"不需要你决定"的边界，且未把事实问题伪装成决策。
4. 事实：每条断言带基线提交与复现命令；列出了绕过通道。
5. 承诺配对：强断言（原子 / 实时 / 幂等 / 永不 / 不丢）都有机制与验证点。
6. 未验证项与假设已显式列出，并标明由谁拍板。
7. 裁决条目已过 R7：不翻代码、不读其他文档即可裁决；内部命题名已改写为"破坏了会怎么表现"。
8. 涉及界面 / 开关 / 数据格式 / 对外接口 / 外部渠道行为的条目，已作为裁决条目交人批（R8；界面另有交互指南 I8 的界面归属卡）；没有一条是以"推荐默认值"身份通过的。

各专题篇的自检清单补本类文档的**特有项**，不重复以上八条。
