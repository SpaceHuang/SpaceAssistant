# 技术方案写作指南

> **定位**：写**技术方案**（规格、验收、迁移、回滚）时读本篇。
> **通用层**：读者分层与人机分工、写作流程与门禁、人类决策层规则 R1–R8、通用自检定义在 [`document-writing-guide.md`](document-writing-guide.md) §8–§11（元指南）；本篇只写方案特有的写法，不重复。
> **篇内路由**：写方案正文 → §0–§1；**准备评审**（人必读 / 人机共读层）→ §2；规格层逐项自查 → §3；**提交评审前的人层↔机层一致性校验** → §4；改稿 → §5；反模式 → §6；交人评审前 → 附录（通用自检见元指南 §11）。
> **来源与维护**：见 [`technical-plan-writing-guide-sources.md`](technical-plan-writing-guide-sources.md)（按需查阅，日常不必加载）。
> **一句话**：写作的目标不是表达设计，而是让别人得到**唯一行为**——**真人只审决策，机器审规格**。

## 0. 两条前提

1. **方案不是表达的载体，而是规格 + 决策记录 + 证据包。** 出现「原子 / 实时 / 幂等 / 永不 / 不丢」这类结果词时，同行必须给出机制与验证点；给不出，说明机制还没想清。
2. **写作顺序决定质量。** 「背景 → 目标 → 设计 → 步骤 → 验收」是**阅读顺序**，不是**论证顺序**。按阅读顺序写，就会在写"设计"时才第一次面对现状与状态转移，于是只能就地打补丁。`docs-guide` §3.6 已实测：6 份现状文档中 3 份因"先写后查"返工。

## 1. 读者分层（方案版）

三层读者的通用规则、第 0 层固定骨架、人机分工、读者标记、ID 体系的一般要求见元指南 §8；方案侧只需落定下列内容：

| 层 | 读者 | 本层放什么 |
|---|---|---|
| **第 0 层 决策层** | 决策人、负责人（不读代码、只看这一层） | 决策项 `D-*`：价值取舍、不可逆承诺、风险容忍（分工见元指南 §8.3） |
| **第 1 层 概要层** | 人机共读 | 方向、范围、主要风险与排除方案 |
| **第 2 层 规格层** | 实现者 / 评审 Agent | 不变量 `INV-*`、契约、状态与所有权、验收 `AC-*`、迁移与回滚 |
| 附录（证据 / 核销 / 未验证项） | 追溯与复核 | 事实 `F-*`、核销记录、待定项与未验证项 |

**ID 体系（方案侧）**：决策 `D-*`、不变量 `INV-*`、验收 `AC-*`、事实 `F-*` 各成一套，**互相引用而不互相复制**；真源唯一，第 0 层只指向、不重写；层间引用必须**可双向追溯**（"这个决策变了，哪些规格与验收随之失效"要答得上）。

**适用面（裁决条目）**：方案主体里需要人拍板的条目 —— 边界声明、技术选项、不可逆承诺、承重墙改动 —— 同样是**裁决条目**，按元指南 §10（R1–R8）写：只出现在第 0 层是不够的。

**界面改动（触发线）**：方案里出现界面语义（用户可查看 / 显示 / 面板 / 列表 / 展开 / 开关 / 入口 / 按钮 / 提示 / 状态展示）时，必须先拿到获批的**界面归属卡**（5 行，见[交互设计指南](interaction-design-guide.md) I8）；**未获批不得排入阶段**，也不接受"先实现、界面待评审"。

**需求外扩声明**：方案相对需求**新增的交付面**（新 UI、新 IPC、新持久化字段、新开关、新状态模型）必须逐条列出并注明来源条款；**来源条款不是决策项（或只是"推荐默认值"）时，先回去补需求决策，再排阶段**——"需求里一句话变成方案里一个阶段"是加戏的高发点。

## 2. 评审包（人必读 / 人机共读层）【RP-1~RP-6】

> **定位**：人必读、人机共读这两层不是"给不便读代码的人准备的摘要"，而是**一场方案评审的全部输入**。
> **唯一合格判据**：把这两层单独摘出来交给没跟进过本模块的评审者，他不打开代码、不翻其他文档、不追问作者，即可裁决。
> **缺任一件 = 未准备好评审**，不得提交——不是"建议补充"。**读者看到的症状**常见为"细节都对，但看不出它要动哪些模块、会不会动公共接口、体量多大"。

### 2.1 六件与它们回答的问题

| 件 | 评委要回答的问题 | 必须给出的形式 | 缺了的后果 |
|---|---|---|---|
| RP-1 一句话变更（第 0 层） | 这次改变的是什么 | 现状 A → 目标 B，一行 | 读完不知道在审什么 |
| RP-2 链路图 | 从系统哪里插进去、谁调谁 | 一张图：现状 / 目标，标出插入与替换点 | 无法判断"这个改法在系统上成立吗" |
| RP-3 变更面表 | 改哪些单元、各是干什么的、谁新建 / 改造 / 复用 | 表：单元｜作用简述｜改动类型｜对应 `D/INV`｜跨边界 | 只能现场翻代码，评审退化为"内行对暗号" |
| RP-4 契约面六面 | 动没动公共契约、谁要跟着改 | 六面逐面给"改 / 不改"结论 | 影响面靠猜；下游同步义务漏项 |
| RP-5 量级与拆分判断 | 多大体量、该不该拆 | 计数 + 拆分结论（含"不拆"的论证） | 体量过大被当成一个阶段硬塞 |
| RP-6 待批准清单 + 自曝三处（第 0 层） | 这次签什么字、哪里最可能被推翻 | 清单 + 三处弱点及各自的推翻条件 | 签字范围模糊；评委只能全文扫 |

RP-1、RP-6 属第 0 层，语言按元指南 §10（R1–R8）；RP-2~RP-5 属第 1 层（语言边界见 §2.7）。六件都要能下钻到规格层 ID，但**不得把规格层内容复制上来**。

### 2.2 RP-2 链路图

- 节点名**必须复用 RP-3 的单元名**，不得另造一套命名（否则两处开始漂移）。
- 必须能看出三件事：新环节插在哪两个单元之间；谁调用谁；每个状态**唯一 writer 是谁**。
- 反例：把链路写成连续散文（"gate 采集事实后经策略裁决签许可，执行器消费"）——能读懂过程，但画不出位置，也数不出单元。
- 检查：让没读过代码的人照图说出"新增环节在哪两个单元之间"，说不出即不合格。

### 2.3 RP-3 变更面表

一行一个单元：

| 单元 | 作用简述 | 改动类型 | 对应 `D/INV` | 跨边界 |
|---|---|---|---|---|

**作用简述**：一句话、**≤20 字**，说"它在系统里干什么"，不说"这次为什么改它"；需要补充时只允许加一句括号，且括号里写**谁依赖它**，不写实现细节。

- 不合格：`工具调用关卡相关逻辑`、`策略模块`（读者据此判断不了该不该动它）。
- 合格：`工具调用关卡：拦下调用、采集事实、交策略裁决（gate / permit 依赖它）`。
- 判据：**读者据此能否判断"该不该动它、动它会牵连谁"**；两个都答不出，重写这句，不是加长。

**改动类型（五类，按顺序归类）**：

| 类型 | 定义 |
|---|---|
| `新建` | 本次新出现的单元 |
| `改造` | 只改单元内部，外部依赖方无感 |
| `改承重边界` | 模块间接口 / 存储读写接口 / **唯一 writer 或提交点迁移**——本仓库内部、不越产品边界，但调用方多或受边界门禁约束 |
| `改对外契约` | 跨进程（IPC / 预加载）、跨包（`packages/*`）、落盘格式与迁移、对外数据（错误码、规则表、配置项） |
| `复用不改` | 本次不动，须写凭什么够用；未验证的写 `复用不改（待验证）` 并下钻未验证项 |

1. 本次新建？→ `新建`。
2. 改它的形状（签名 / 字段 / 枚举 / 表结构 / 唯一 writer / 提交点）吗？→ 否 → `复用不改`。
3. 依赖方是谁？→ 只在单元内部 → `改造`；→ 本仓库其他模块、不越产品边界 → `改承重边界`；→ 跨进程 / 跨包 / 落盘 / 对外数据 → `改对外契约`。

第三步必须写出**依赖方是谁**。反例：给 agent-sdk 的历史端口加一个**可选方法**，按"形状变不大"归 `改造`——实际所有宿主适配器都要实现、落盘事件随之变；再如**把会话写入的 owner 从一处挪到另一处而签名一行未变**，按"签名未变"会被归 `改造`，但它正是承重墙改动（有五类中唯一能装它的 `改承重边界`）。

**必须同时列出三类单元**：要改的、要新建的、复用不改的。**取证对象 ≠ 改动对象**——事实卡里 `rg` 命令命中的路径不属于本表，除非它确实要改。

**检查**：
1. 同一正则抽两次、比对差集（表有正文无 = 幽灵单元；正文有表无 = 漏登）：
   ```
   rg -oE '(electron|src|packages)/[A-Za-z0-9_./-]+' <方案> | sort -u    # 正文全部路径
   rg -n '^\|' <变更面表区段>                                            # 表内单元
   ```
2. 必须能数出：改既有 N 个、新建 M 个、复用 K 个，其中 `改对外契约` J 个、`改承重边界` P 处。数不出即不合格。

### 2.4 RP-4 契约面六面

固定六面，逐面给结论；**①② 是承重面，单独设面并要求附门禁结果**：

| # | 契约面 | 必须回答的子问题 | 证明方式 |
|---|---|---|---|
| ① | **agent-sdk 接口契约** | 宿主端口（`AgentHostPorts` 及其子端口）是否新增字段、改可选性、改语义？事件与历史契约（`HistoryEvent` 种类、`HistoryPort` 方法签名）是否变？审批记录（`answerer` / `status` / `cause` 枚举）是否新增取值——旧数据解析会不会因此拒绝？包公开导出是否新增？是否引入 SDK 对宿主的新反向依赖？ | `npm run check:agent-sdk`、`npm run typecheck:agent-sdk` |
| ② | **会话存储接口契约** | 会话 / 消息 / 历史的唯一 writer 是否变化、写入是否仍走 `runInTransaction`？表结构或持久化字段是否新增 / 迁移 / 需旧数据兼容？读写接口签名是否变、调用方有哪些？是否影响 `sessions/` 明文备份的导出与恢复？消息事实归属是否被破坏？ | `npm run check:session-storage-boundary`、`npm run check:session-storage-cleanup-boundary`、`npm run check:message-fact-ownership` |
| ③ | 进程间通道（IPC / 预加载暴露面） | 是否新增或改变通道、参数、返回形状？谁要同步改？ | 通道名以 `electron/preload.ts` 为准，本节不维护清单 |
| ④ | 共享类型（`src/shared/`） | 领域类型的字段、必填性、判别式是否变？ | `npm run typecheck:shared` |
| ⑤ | 其他持久化格式与迁移 | 数据库 schema、设置、快照是否改变？未知 / 旧数据如何处置？ | 迁移与回退实体须在规格层可指认 |
| ⑥ | 领域数据格式 | 规则表、配置项、稳定错误码这类被读取或对外的数据是否变？ | 各数据的加载器与既有校验 |

- **禁止沉默**：缺一行即视为未回答。"不知道 / 待定"必须改写成"待确认问题 + 谁在什么节点回答"。
- ①② 写"不改"时同样要给依据（例："审批记录已含 `agent` 取值，回执按调用绑定已有字段"），或直接附门禁通过结果。
- **门禁只证明边界未被破坏，不证明语义未变**：①② 任一面为"改"时，必须给出"旧数据 / 旧调用方仍能工作"的验证方式（测试名或命令），否则视为未回答。
- 判定句：**评委不打开代码，能否回答"这次会不会动 agent-sdk / 会不会动会话存储"？** 答不出即不合格。
- 命令名以 `package.json` 的 `check:*` 脚本为准，本表不维护完整清单（清单会腐化）。
- 与 §1「需求外扩声明」的分工：外扩管**相对需求新增了什么交付面**；本节管**动了哪些既有的对外形状**。
- 反例（本仓库实测）：方案正文反复出现审核回执、回答者、`approve / deny / needs-human`，附录用 `rg` 查回答者适配层字段，但**全文没有一句"agent-sdk 改不改"**；初判其实不改（回答者端口只承载装配材料，审批记录已有 `agent` 取值），唯一待确认的是"转人工"是否需要新枚举值——**这个待确认点本身就该写在表里**。

### 2.5 RP-5 量级与拆分判断

必须报出：改既有单元数 / 新建单元数 / 复用单元数 / `改对外契约` 行数 / `改承重边界` 处数 / 新增持久化字段数 / 新增错误码或对外数据项数 / 阶段数。

**拆分门槛**：`改对外契约` ≥2 行，**或** `改承重边界` ≥2 处，**或** RP-4 六面中 ≥2 面为"改" → 必须**拆成多份方案**，或写一段"为什么不拆"的论证（要给依据，不能写"关系密切"）。

### 2.6 RP-6 待批准清单与自曝弱点

- **待批准清单**：本次评审要批的**范围**，逐条列（例："已定：D-01~D-07 / 待批：持久化字段格式、界面归属卡、新增错误码 / 外部验收项：真机与真实渠道"）。未列入清单的内容**不属本轮评审范围**。
- **自曝三处弱点**：作者自认最可能被推翻的三处，每处写"什么证据会推翻它"。评委集中打这三处，评审时长可预期。
- **小方案压缩**：六件不得缺项，但可一件一行（3–5 行完成）。判据仍是"评委能否据此裁决"，不是"是否达到某个体量"。

### 2.7 语言边界（对 R1 的有意分界）

- RP-2~RP-5 **允许**出现组件名、路径、内部标识——否则"可核查"无从谈起。
- 约束两条：① 每个组件名首次出现时给作用简述；② **不得进入第 0 层**（RP-1、RP-6 用业务语言，内部词只放行末"下钻"）。
- 这是对元指南 §10 R1 的**有意分界**：评审包的可核查性优先于"人层无内部词"的纯粹性。不得以 R1 为由把 RP-3 / RP-4 改写成纯业务叙述——那样正好取消了它们存在的理由。

## 3. 规格层（第 2 层）写作要求

写作流程、产出物（事实卡 / 模型卡 / 契约卡 / 场景矩阵 / 验收映射表）与门禁按元指南 §9 走；本节只写方案在规格层的逐项要求——均为评审高频项，逐条给出要求与反例症状：

| 内容 | 要求 | 反例症状 |
|---|---|---|
| 不变量 | 写"不可违反的性质"，每条被流程与测试引用 | 目标散落在各章，互相冲突 |
| 状态与所有权 | 每个状态**唯一 writer**、唯一提交点、唯一恢复者 | 一个字段承担四种职责（排序 / 新鲜度 / 缓存键 / 提交校验） |
| 契约 | 类型给形状、字段给归属层与缺省值、错误码稳定 | 只给类型名；期望值由被校验对象自己填充（自证） |
| 失败与恢复 | 枚举崩溃窗口，每个窗口给唯一恢复动作 | 只在 catch 里恢复却声称支持崩溃恢复 |
| 并发与原子性 | 给锁顺序、临界区、幂等键、可等待屏障 | 宣称"一个 action 原子更新两套状态" |
| 承诺配对 | 每个强断言同行给机制与验证点 | "原子 / 实时 / 不可变"只有形容词 |
| 验收 | 从目标正向推导；用例可达且可执行 | 规则永不命中，用例天然不可达；以"代码行数归零"当验收 |
| 迁移与阶段 | 迁移算法、事务边界、完成标记语义、精确回退实体；每阶段定义输入 / 输出 / 出口证据 / 可回退实体 | 把"幂等 CREATE TABLE"当版本迁移；跳过失败仍打完成标记；阶段不可独立回退 |
| 测试 | 按不变量与协议组织，含竞态 / 故障注入 / 对拍 | 测试跟着补丁走，全绿却不覆盖跨渠道不变量 |

配套纪律：**排除方案也要写**（选了什么、为什么排除另一个）；**不确定必须显式化**（写成"待定项 + 影响 + 谁拍板"，不要用"或 / 建议 / 视情况"糊过去）。

## 4. 人层 ↔ 机层一致性【X-1~X-3】

> **定位**：人层写的是**论断与承诺**，机层写的是**证据与规格**。单向校验都不够：只查"人层→机层"会纵容空口承诺，只查"机层→人层"会纵容悄悄加戏。
> **定性：提交评审的硬门禁。**人层与机层不一致的方案不得提交——不是"建议自查"。

**X-1｜人层的每一句论断，机层必须有证据（防空口承诺）**
人层每条承诺、能力、效果 → 机层至少一条 `INV-*` + 一条 `AC-*` + 一个证据类型（代码事实 / 自动化测试 / 未验证项）。
- 反例（实测）：人层写"不做集中预授权，与相邻方案独立"，机层除附录一行外没有任何隔离验证条目。

**X-2｜机层的每一个新增面，人层必须有业务语言的对应句（防悄悄加戏）**
"新增面"是封闭六类：①新单元 ②新持久化字段 ③新错误码或稳定失败分类 ④新开关或配置项 ⑤新版本或迁移路径 ⑥**新增跨模块 / 跨包依赖方向**（含 SDK 对宿主的反向依赖）。
命中任一，人层必须有一句"这会让用户 / 数据 / 渠道看到什么变化"，或明确写"对用户不可见，因为 X"。
- 反例（实测，同一份方案三处）：机层新增 5 个稳定失败分类、1 个持久化字段、1 套版本解析器，人层零提及；其中持久化字段在人层只以"若需新增字段则另行审批"的条件句出现，**评委会误以为这次不改数据格式**。
- 检查：
  ```
  rg -n '新增|新字段|新错误码|新分类|新版本|迁移|开关|依赖' <方案> | rg -v '附录'
  ```
  逐条看：命中处若只在机层，就是加戏。

**X-3｜数量对账：人层报的数 = 机层实际的数**

| 锚点 | 人层说法 | 机层条目 | 对账 |
|---|---|---|---|
| 能力面 | | | ✓ / ✗ |
| 阶段 | | | |
| 新增持久化字段 | | | |
| 新增错误码 / 失败分类 | | | |
| 受影响的公共契约面 | | | |
| **agent-sdk 面结论**（改 / 不改 + 依据或门禁结果） | | | |
| **会话存储面结论**（同上） | | | |
| 未验证项 | | | |
| 决策 ↔ 不变量 ↔ 验收 | | | |

- 这类漂移最难被发现：不是"没提"，而是"提的数不一样"（人层写五类，机层十一组；人层写"无真机数据"，机层列五项未验证事项）。
- 检查：
  ```
  rg -n '[一二三四五六七八九十]+ ?(类|项|个阶段|组)|[0-9]+ ?条' <第 0 层与第 1 层区段>
  ```
  每个数字都要能在机层数出同样的条数。

**不一致了怎么办**：机层偷偷加的 → 删除，或升为决策项 / 写进 RP-6；人层空口承诺的 → 删掉该承诺，或补规格与验收。**不允许"先提交、评审时再说"**。

**人测（X-1 / X-2 的唯一可靠判据）**：把第 0 层 + 第 1 层单独摘出，只给这份评审包，要求读者回答六问——改哪些单元 / 动哪些契约 / 谁受影响 / 什么不可逆 / 哪三处最可能出问题 / 这次要批什么。**答不出的题数目标为 0。**

## 5. 修订纪律

1. 每轮修订先交**核销表**（上轮问题 → 本轮状态 → 证据），再审新风险。不要用"已补写"当关闭依据。
2. **同一处 / 同一概念被第二轮指出 → 停止局部修补，回退到模型层重写那一节。** 判据：如果修一处要跟着改三处无关章节，说明模型错了。
3. 修订要区分"改模型"与"改文字"；前者重新跑元指南 §9 的第 4 步（反例）与第 5 步（验收）。

## 6. 反模式 → 对应步骤

反模式本身是**结果**；下表把它挂到"哪一步没做"（步骤编号沿用元指南 §9），以便修复而不是记口号。

| 反模式 | 属于哪一步没做 | 典型例证 |
|---|---|---|
| 方案的"现状前提"与代码不符 | 第 1 步（事实） | 称"产物绑定原工作目录"，实现却会回退到当前工作目录 |
| 反复在相邻边界出同类问题 | 第 2 步（模型） | 问题不在某个 IPC 字段，而在"一致性模型未先于实现建立" |
| 一个词 / 一个字段多义，或留"二选一" | 第 3、4 步 | 一个版本号兼做排序、新鲜度、缓存键、提交校验 |
| 承诺超出可执行边界 | 第 4 步（承诺—机制配对） | 宣称"原子接管"，却无法与模块级状态共事务 |
| 验收不可达 / 不可判定 | 第 5 步 | 阶段声称完成的 AC 依赖下一阶段 |
| 人类层看不懂 / 看不完 | 元指南 §10（R1–R8） | 决策项写 `outbound`；只给编号需翻详情；写成只有调研过才看得懂的命题 |
| 评审包缺件，评委只能现场翻代码 | 第 0 / 1 层没准备评审输入（§2） | 方案里十几处代码路径全部以 `rg` 取证形式散落在附录，人层零解释；全文没有一句"公共接口改不改"；看不出体量与是否该拆 |
| 人层与机层不一致（空口承诺 / 悄悄加戏） | §4（X-1~X-3） | 机层新增 5 个失败分类、1 个持久化字段、1 套版本解析器，人层零提及；人层承诺"与相邻方案独立"，机层无隔离验证条目 |
| 规格与进度混装、基线漂移 | 执行计划指南 §1 | 方案文档内嵌任务复选框与状态维护约定 |

## 附录 提交评审前自检清单（方案特有项）

通用层八条（第 0 层三问、事实与复现命令、承诺配对、未验证项、裁决条目已过 R7、R8 的"推荐默认值"禁用清单）见元指南 §11，本清单不重复。

1. 模型卡：不变量、状态所有权、销毁与恢复路径完整。
2. 契约：文档内闭合，术语一名一义，无"二选一"。
3. 验收：每条 AC 有可达用例；竞态 / 崩溃 / 迟到 / 重复已覆盖。
4. 迁移与阶段：算法、事务边界、完成标记语义、回退实体齐备；每阶段可独立编译、回退、验收。
5. 排除方案已写明：选了什么、为什么排除另一个。
6. 待定项与未验证项已显式化（影响 + 拍板人）。
7. 进度与任务清单已出方案：方案内不出现复选框与状态维护约定。
8. 涉及界面的改动已附**获批的界面归属卡**（《交互设计指南》I8）；未获批项没有排进阶段。
9. **需求外扩声明**已逐条列出（新 UI / IPC / 持久化字段 / 开关 / 状态模型），且每条来源都是决策项。
10. **评审包六件齐备**（RP-1~RP-6）：变更面表每单元有 ≤20 字作用简述与五类改动类型（含"复用不改"凭什么够用）；链路图节点名与单元名一致；契约面六面逐面有结论，承重面 ①② 为"改"时附门禁结果与"旧数据 / 旧调用方仍能工作"的验证方式。
11. **人层 ↔ 机层一致**（X-1~X-3）：对账表无 ✗；机层每个新增面在人层都有对应句或已升为决策项；人层每句承诺都有 `INV-*` + `AC-*` + 证据类型。
