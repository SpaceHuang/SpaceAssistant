# 技术方案写作指南

> **定位**：写**技术方案**（规格、验收、迁移、回滚）时读本篇。
> **篇内路由**：只写方案正文 → §0–§4；交人评审前 → §3 + 附录 B；自查 → 附录 B。
> **上位规则**：写法约定见 [`document-writing-guide.md`](document-writing-guide.md)（元指南）。
> **来源与维护**：沿用 [`technical-plan-writing-guide-sources.md`](technical-plan-writing-guide-sources.md)（草稿阶段未迁移）。
> **一句话**：写作的目标不是表达设计，而是让别人得到**唯一行为**——**真人只审决策，机器审规格**。

## 0. 三条前提

1. **方案不是表达的载体，而是规格 + 决策记录 + 证据包。** 出现「原子 / 实时 / 幂等 / 永不 / 不丢」这类结果词时，同行必须给出机制与验证点；给不出，说明机制还没想清。
2. **写作顺序决定质量。** 「背景 → 目标 → 设计 → 步骤 → 验收」是**阅读顺序**，不是**论证顺序**。按阅读顺序写，就会在写"设计"时才第一次面对现状与状态转移，于是只能就地打补丁。`docs-guide` §3.6 已实测：6 份现状文档中 3 份因"先写后查"返工。
3. **人机分工按能力划，不按篇幅划。**

| 只有人能决定（必须进第 0 层） | Agent 该自己做完（不该占人时间） |
|---|---|
| 价值排序：先做哪个、不做哪个 | 事实核查：现状到底是不是这样（带命令可复核） |
| 体验取舍：两种行为差异，用户更喜欢哪个 | 逻辑闭合：类型 / 字段 / 状态转移是否自洽 |
| 风险容忍：这点安全回归换那点体验，值不值 | 边界推演：竞态、崩溃、重复、取消、旧数据 |
| 不可逆承诺：迁移、删除、外部对接、排期 | 机制设计：屏障、幂等键、补偿、回滚 |
| 对"未验证假设"拍板：接受风险还是先验证 | 验收覆盖与用例可达性 |

判据：**能被证据回答的问题不是决策项**。把"我还没查的事实"包装成"请你决策"，是最常见的浪费人力的方式。

## 1. 读者分层

| 层 | 读者 | 语言 | 篇幅 | 合格判据 |
|---|---|---|---|---|
| **第 0 层 决策层** | 决策人、负责人（不读代码、只看这一页） | **只用业务语言** | 1 页内；**设信息下限，不设行数上限** | 每个决策项**不打开任何其他文档即可裁决** |
| **第 1 层 概要层** | 人机共读 | 允许工程词，首次出现给一句释义 | ≤ 2 页 | 能判断"方向与风险是否可接受" |
| **第 2 层 规格层** | 实现者 / 评审 Agent | 内部语言不设限 | 不限 | 每条可核查、可执行、可复现 |
| 附录（证据 / 核销 / 未验证项） | 追溯与复核 | 命令与原始证据 | 不限 | 每条断言带复现命令与基线 |

第 0 层固定骨架：

```markdown
一句话：问题是什么、本次改了什么（不含内部词）
只有 3 分钟的话：先读哪几项
需要你决定的事项：D1..Dn（规则见 §3）
不需要你决定（Agent 负责；写出来是为了不占用你的时间）
```

**ID 体系**：决策 `D-*`、不变量 `INV-*`、验收 `AC-*`、事实 `F-*` 各成一套，**互相引用而不互相复制**；真源唯一，第 0 层只指向、不重写。层与层之间的引用关系必须可双向追溯（"这个决策变了，哪些规格与验收随之失效"要答得上）。

**读者标记**：每节标题后标注 `【人必读】` / `【人机共读】` / `【机｜人工可跳过】`。人读不完，往往是因为不知道该跳过什么。

## 2. 写作流程与门禁

每一步的产出是下一步的输入；**缺产出不得进入下一步**。

| 步 | 动作 | 产出物 | 门禁 |
|---|---|---|---|
| 0 立项 | 从用户目标写可观测结果；写"不做清单" | 验收边界卡 | 目标能用一句可观测的话表述 |
| 1 事实 | **先查后写**：`ls` 拿全量 + 读代码；每条断言带基线提交与复现命令 | 事实卡；**绕过通道清单**（哪些入口不经过你要建的那道门） | 不存在"我记得"式断言 |
| 2 模型 | 先写不变量、状态与所有权矩阵、生命周期与崩溃恢复矩阵 | 模型卡 | 每个状态有唯一 writer、唯一提交点、唯一恢复者 |
| 3 契约 | 术语一名一义；类型 / 字段 / 错误码 / 缺省值定到唯一位置 | 契约卡 + 术语表 | 文档内闭合；同一算法不在两处描述 |
| 4 反例 | 自己扮演评审：按场景矩阵（正常 / 并发 / 超时 / 取消 / 重启 / 重复 / 乱序 / 部分失败 / 旧数据）逐格走，写结论或"不适用 + 理由" | 场景矩阵 + 决策记录 | **不存在两种都合规的解读** |
| 5 验收 | 从目标正向推 `AC-*` → 可执行断言 → 用例（含竞态与故障注入） | 验收映射表（AC ↔ INV ↔ 用例） | 每条 AC 有可达用例；不用代码形态指标代替行为证据 |
| 6 迁移与阶段 | 每阶段定义输入 / 输出 / 出口证据 / 可回退实体 | 阶段表（顺序与依赖理由） | 每阶段可独立编译、回退、验收 |
| 7 自评 | 实现者视角复读 + pre-mortem | 未验证 / 待定 / 需人拍板清单 | 没有"我不确定却写成确定"的句子 |

**第 2 步和第 4 步是最容易被跳过、也是评审火力最集中的两步。**
**本篇不覆盖任务级写法**（任务粒度、依赖顺序、状态标记、完成判据登记）：那属于[执行计划写作指南](execution-plan-writing-guide.md)的范围。

## 3. 人类决策层写作规则（R1–R6）

> 人类层不是第 2 层的**摘要**，而是独立的**决策界面**。摘要追求"少信息"，界面追求"自足"——这是下面六条的共同出发点。

**R1｜只用业务语言，内部标识只出现在"下钻"入口**
- 要求：禁用代码标识符、模块名、内部编号；无法回避时写「业务说法（内部：xxx）」，或移到行末下钻。业务词（微信、审批、档位）可保留，首次出现给一句释义。
- 反例：`标准档允许「安全审核 Agent」批准 outbound 发送吗？`
- 正例：`标准档要不要允许「安全审核 Agent」替人点头，把消息或数据发给外部渠道？`
- 检查（近似筛查，命中后人工判定）：
  ```
  rg -n '`[^`]+`|[a-z]+[A-Z][A-Za-z]*|[A-Z]{2,}|§' <文档第 0 层区段>
  ```

**R2｜决策项自包含：不打开任何其他文档即可裁决**
每个 D 项必须含六要素：①背景（这件事是什么、影响谁）②要决定什么（A/B 选项）③每个选项的后果（用户可见 / 不可见、代价）④可逆性 ⑤依据强度（哪些已验证、哪些没数据）⑥推荐 + "你不决定时默认怎么走"。
- 反例：`范围取舍：本轮是否就并入 remote policy 对账（P2-06）与新建底线登记 registry（P3-01~05）？`——读者必须翻到 §3 / §5 才知道在决定什么。
- 正例：先用两句解释"远程工具目前有一套独立的放行判断，与桌面共用的一套规则其实是两套实现，改一边容易漏另一边"，再给 A/B 与代价。
- 检查（唯一可靠的是人测）：把单个 D 项**单独摘出来**发给没参与项目的人（或隔天自己读），记录他提出的疑问数；**目标为 0**。

**R3｜长度设下限，不设上限**
- 合格标准是"六要素齐全"，不是"行数少"。行数只作反向信号：超过约 10 行的 D 项，检查是否该拆成两个决策。
- 反例：为把第 0 层压到 55 行而删掉背景。试点修订后第 0 层由 55 行涨到约 70 行，多出来的部分是**把读者的理解成本换到作者侧**——方向正确。

**R4｜编号只做下钻，不承担说明职责**
- `B-01`、`P2-06`、`§2.2` 只能出现在行末「下钻：」里。编号对作者是索引，对读者是谜语。

**R5｜写后果，不写机制**
- "选 A 会怎样"用用户能感知的差异表述（会不会被打断、能不能撤回、会不会改错文件）；机制词（许可、摘要、原子写）只在解释"为什么不可逆 / 为什么安全"时出现。

**R6｜同一概念全篇同一业务词**
- 不要一处写 `outbound`、一处写"对外发送"。在文末或第 2 层入口维护"业务词 → 内部词"对照（附录 A 是起步版）。

## 4. 规格层（第 2 层）写作要求

逐条给出反例式提醒，均为评审高频项：

| 内容 | 要求 | 反例症状 |
|---|---|---|
| 不变量 | 写"不可违反的性质"，每条被流程与测试引用 | 目标散落在各章，互相冲突 |
| 状态与所有权 | 每个状态**唯一 writer**、唯一提交点、唯一恢复者 | 一个字段承担四种职责（排序 / 新鲜度 / 缓存键 / 提交校验） |
| 契约 | 类型给形状、字段给归属层与缺省值、错误码稳定 | 只给类型名；期望值由被校验对象自己填充（自证） |
| 失败与恢复 | 枚举崩溃窗口，每个窗口给唯一恢复动作 | 只在 catch 里恢复却声称支持崩溃恢复 |
| 并发与原子性 | 给锁顺序、临界区、幂等键、可等待屏障 | 宣称"一个 action 原子更新两套状态" |
| 承诺配对 | 每个强断言同行给机制与验证点 | "原子 / 实时 / 不可变"只有形容词 |
| 验收 | 从目标正向推导；用例可达且可执行 | 规则永不命中，用例天然不可达；以"代码行数归零"当验收 |
| 迁移 | 迁移算法、事务边界、完成标记语义、精确回退实体 | 把"幂等 CREATE TABLE"当版本迁移；跳过失败仍打完成标记 |
| 测试 | 按不变量与协议组织，含竞态 / 故障注入 / 对拍 | 测试跟着补丁走，全绿却不覆盖跨渠道不变量 |

配套纪律：**排除方案也要写**（选了什么、为什么排除另一个）；**不确定必须显式化**（写成"待定项 + 影响 + 谁拍板"，不要用"或 / 建议 / 视情况"糊过去）。

## 5. 修订纪律

1. 每轮修订先交**核销表**（上轮问题 → 本轮状态 → 证据），再审新风险。不要用"已补写"当关闭依据。
2. **同一处 / 同一概念被第二轮指出 → 停止局部修补，回退到模型层重写那一节。** 判据：如果修一处要跟着改三处无关章节，说明模型错了。
3. 修订要区分"改模型"与"改文字"；前者重新跑第 4 步（反例）与第 5 步（验收映射）。

## 6. 反模式 → 对应步骤

反模式本身是**结果**；下表把它挂到"哪一步没做"，以便修复而不是记口号。

| 反模式 | 属于哪一步没做 | 典型例证 |
|---|---|---|
| 方案的"现状前提"与代码不符 | 第 1 步（事实） | 称"产物绑定原工作目录"，实现却会回退到当前工作目录 |
| 反复在相邻边界出同类问题 | 第 2 步（模型） | 问题不在某个 IPC 字段，而在"一致性模型未先于实现建立" |
| 一个词 / 一个字段多义，或留"二选一" | 第 3、4 步 | 一个版本号兼做排序、新鲜度、缓存键、提交校验 |
| 承诺超出可执行边界 | 第 4 步（承诺—机制配对） | 宣称"原子接管"，却无法与模块级状态共事务 |
| 验收不可达 / 不可判定 | 第 5 步 | 阶段声称完成的 AC 依赖下一阶段 |
| 人类层看不懂 / 看不完 | §3（R1–R6） | 决策项写 `outbound`；只给编号需翻详情 |
| 规格与进度混装、基线漂移 | 执行计划指南 §1 | 方案文档内嵌任务复选框与状态维护约定 |

## 附录 B 提交评审前自检清单

1. 第 0 层：每个 D 项六要素齐全，能单独摘出来给外行裁决（疑问数 = 0）。
2. 第 0 层：无代码标识符、模块名、内部编号；编号仅在"下钻"。
3. 第 0 层：写清了"不需要你决定"的边界，且未把事实问题伪装成决策。
4. 事实卡：每条断言带基线提交与复现命令；列出了绕过通道。
5. 模型卡：不变量、状态所有权、销毁与恢复路径完整。
6. 契约：文档内闭合，术语一名一义，无"二选一"。
7. 承诺配对：所有强断言都有机制与验证点。
8. 验收：每条 AC 有可达用例；竞态 / 崩溃 / 迟到 / 重复已覆盖。
9. 迁移：算法、事务边界、完成标记语义、回退实体齐备。
10. 拆分明细：进度与任务清单已出方案；计划不新造验收。
11. 未验证项与假设已显式列出，并标明由谁拍板。
12. 执行计划：见[执行计划写作指南](execution-plan-writing-guide.md)的自检清单（§6，9 条）。
13. 已按元指南 §4 判断加载层次；不常读的内容已外移；正文头部有路由句。
