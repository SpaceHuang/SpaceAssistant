# 执行计划写作指南

> **定位**：写**执行计划**（任务拆解、顺序与依赖、进度标记）时读本篇。
> **篇内路由**：只排任务顺序与依赖 → §3；维护进度标记 → §5；交付前自查 → §6。
> **上位规则**：写法约定见 [`document-writing-guide.md`](document-writing-guide.md)（元指南）。
> **来源与维护**：依据条目仍在 [`technical-plan-writing-guide-sources.md`](technical-plan-writing-guide-sources.md)（"§5 依据"一节；草稿阶段未迁移）。
> **一句话**：执行计划是**易变编排层**——回答"谁在什么时候做什么、按什么顺序、凭什么算做完"，**不重新定义**方案已定的验收与不变量。

## 1. 与方案篇的分工：单向真源

**分界线不是"方案 vs 计划"，而是"稳定规格 vs 易变编排"。**

| | 技术方案 | 执行计划 |
|---|---|---|
| 内容 | 不变量、契约、状态与边界、验收、迁移与回滚、决策记录 | 任务拆解、顺序与依赖、进度与状态、执行中的偏差 |
| 读者 | 决策人 + 实现者 / 评审 Agent | 执行 Agent + 追踪者 |
| 变更频率 | 低（改动需重新评审、需标注基线） | 高（每次推进都变） |

规则：

1. **验收与不变量的真源在方案**；计划只引用 ID，**不得新造验收要求**（"阶段声明完成 AC-01~AC-15，其中 4 条依赖下一阶段"是典型缺陷）。
2. **进度只进计划**：方案里不出现复选框、百分比、任务状态。
3. **阶段切分属方案，任务清单属计划**：方案保留"阶段边界 + 依赖理由 + 每阶段出口证据 + 可回退实体"。
4. **任务先后关系（DAG）属计划**，它随任务集增删而变。
5. 计划的每条任务必须写"完成哪条 AC、用什么证据验收"。

**何时可以不拆**：单次、单阶段、一天内完成、无需独立验收、无需中断恢复 → 可写短方案内嵌任务清单。判据一句话：**计划会不会需要在不改方案的前提下被重写？**

## 2. 任务粒度

一个任务 = **一组可验证的不变量 + 一个可独立验收的交付单元**。三条判据同时成立才算粒度合适：

1. **能独立验收**：有自己的产物与证据，不依赖尚未完成的任务（反例：阶段一声称完成 15 条 AC，其中 4 条依赖阶段二才实现的能力）。
2. **配对的 GREEN 只依赖已完成编号的实现**：拆分后必须**同步修订验收范围**——若一项"只实现描述注册、不承担调用事实提取"，却仍保留调用级用例，第一个 GREEN 永远无法通过。
3. **范围单一**：一个任务只接通一条链路或一个契约（反例：一个任务同时接通 assembler、channel、dispatcher；或同时涉及服务器身份、schema 能力描述、副作用、数据流、账号权限、完整度）。

两种反向错误都要避免：**过宽**（多契约 / 多模块堆一项，失败无法定位）与**机械拆分**（拆出的子项自身不可验收）。低风险准备工作（版本记录、文档盘点）宜合并为基线记录，避免大量状态切换却没有新增可审查成果；内容重叠的任务应合并。**目标是单项范围与验收证据匹配，不追求任务数量。**

每个阶段还应列出：输入、产出、允许改动的范围、失败回退、本阶段移除哪些兼容代码。否则"阶段可独立验收"只是时间表（反例：Phase 1 依赖 Phase 2 才实现的接口，两阶段都无法独立验收）。

## 3. 顺序与依赖

1. **依赖表是唯一真源**：DAG 只写一处，正文与图示不得各自表述（反例：正文写 P2-10 依赖 P2-01~08，表里写 P2-01~09，评审结论是"无法确定哪份是权威"，并指错到无关的 UI 任务）。
2. **禁止三类环**：任务自依赖；跨阶段环；**验收自环**（典型：最终验收以"各阶段关闭门槛"为前置，而阶段关闭门槛又要求最终验收通过）。
3. **前置必须可判定**：禁止"契约一致后""相关模块就绪"这类模糊前置；每个任务都要能在**所有前置完成**后启动。
4. **前置门禁只能引用比它更早产生的证据**：检查点放在阶段边界，只要求本阶段可完成的证据。判定方法：给每条门禁的每项证据标注**产出任务编号**，若该编号晚于门禁所在位置，即为违规（反例：阶段 1 的门禁要求阶段 3 才实现的回退演练证据；P0 门禁要求"旧文档已修订"，而修订本身排在第 6 阶段）。
5. **门禁必须在当前环境可执行**：门禁分两类——(a) 本机可执行（自动测试、本地构建、可复现命令）；(b) 依赖外部环境（其他操作系统、真机、真实渠道账号、生产数据）。**只有 (a) 能作为开发前置门禁；(b) 一律归入外部验收，不阻塞开发**，并在开工前显式列出。判定句：**若一条门禁在当前机器上无法执行，它就不是门禁，而是外部验收项**（反例：在 macOS 环境下要求先拿到 Windows 的性能测试数据，才能继续开发）。
6. **顺序原则**：环境与基线 → 契约定稿 → 实现 → 集成验收 → **关闭与回退演练** → 启用 / 发布。回退与关闭的测试、实现、演练必须排在启用之前，且启用任务显式引用其证据。
7. **外部资源与平台证据分设门槛**：正式安装包、生产数据、真机、其他操作系统、真实渠道账号，应分设"源码关闭门槛"与"发布 / 启用关闭门槛"；否则缺资源时连源码重构都无法开工。

## 4. 任务登记与完成判据

每个任务的最小登记集（可集中在一张追踪表承载，不必逐条重复）：

| 字段 | 要求 |
|---|---|
| 任务 ID / 动作 | 一句话，动词开头，说清"改了什么行为" |
| 依赖 | 引用 §3 的依赖表 |
| 目标文件 / 模块 | 必须写全——它同时界定"允许改动范围" |
| 产物 | 可审查的交付物（文档 / 类型 / 测试 / 记录） |
| 完成判据 | 覆盖真实边界，不能只覆盖主路径的一个点 |
| 验证命令 / 证据 | 可直接执行的命令或记录路径 |
| 可执行环境 | 本机 / 外部环境——标为"外部"的不得作为开发前置门禁（见 §3-5） |
| 状态 | 见 §5 |

**RED / GREEN 配对**：RED 的"完成"＝已记录"目标行为缺失"导致的**预期失败**（写清用例名与命令），不算故障，允许推进对应 GREEN；GREEN 的"完成"＝对应用例通过 + 必要回归通过。不得为凑"有效 RED"人为制造失败，也不得用无关失败充当 RED。

**环境与基线**：基线测试前先写"依赖就绪判据 + 必要准备步骤"；基线失败要分流——环境故障先修，既有代码失败单独登记范围与影响，必要时先修订计划。

## 5. 状态标记规范

任务状态只用一个标记位维护：

| 标记 | 含义 |
|---|---|
| `- [ ]` | 未开始 |
| `- [～]` | 进行中（已开工，尚未满足完成判据） |
| `- [x]` | 完成（**产物与完成判据都具备证据**） |

约束：

1. **`- [x]` 必须有证据**：产物 + 验证命令 / 记录；"代码已改"或"测试通过"单独不足以关闭。
2. **阻塞 / 待评审保持未完成标记**，并在该任务下注明原因；不要用"进行中"掩盖停滞。
3. **进度变化只改标记与证据栏**，不改任务描述，更不改方案文本。
4. **标记必须真实**：长期全为 `- [ ]` 而实际已开工、或全为 `- [x]` 却无证据，都会被评审直接指出。
5. **写法统一用全角 `～`**，即 `- [～]`。理由：半角 `~` 在部分 Markdown 渲染器 / 编辑器中可能被解析成删除线或下划线，显示效果依赖编辑器实现，不适合承担"进行中"这一语义；全角字符不受语法影响（本仓库既有 in-flight 计划即用全角）。已用半角 `- [~]` 的历史文档在后续修订时统一，不要求批量重写。

## 6. 计划交付前的自检

1. DAG 无自环、无跨阶段环、无验收自环；每个任务前置可判定，且前置完成即可启动。
2. 每个阶段检查点**只依赖它之前的**实现与证据。
3. 拆分后每个 RED 与它配对的 GREEN 范围一致、命令一致。
4. 回退 / 关闭演练排在启用之前，并被启用任务引用。
5. 外部验收项与源码关闭分开，缺资源不阻塞源码任务。
6. 每条任务的目标文件、验证命令、完成判据齐全。
7. 状态标记与真实进度一致，完成项都有证据。
8. 每条门禁的每项证据都产出于它之前（逐项标注产出任务编号，不允许编号晚于门禁位置）。
9. 所有门禁在当前机器上可执行；依赖外部环境的项已单列为外部验收，不阻塞开发。
