## 归纳口径

截至 2026-10-16，`docs/review/` 约有 370 份评审材料，包含同一主题的多轮计划评审、代码复审和修复复核。**数量不等于独立证据数量**；本指南是代表性抽样与仓库既有执行纪律的定性综合，未对每份文档逐篇编码统计。

精读 7 篇跨领域评审：安全策略分层（`session-d961cc51-boundary-policy-layering-technical-plan-review*`）、上下文注入（`context-injection-refactor-plan-review*`）、MCP 超时（`2026-10-13-mcp-timeout-turn-failure-isolation-plan-review*`）、产物目录（`explicit-output-directory-candidate-technical-design-review*`）、渲染卡顿（`renderer-process-jank-optimization-plan-review*`）、Agent SDK Runtime（`2026-10-03-agent-sdk-runtime-design-review.md`、`agent-sdk-architecture-development-plan-review*`）、微信确认（`2026-10-11-wechat-confirmation-*`）；并抽读 plan / design 类评审 200 余条问题标题。

纳入标准：一条建议只有在具备代码依据、可复现结果、后续修复 / 关闭记录，或跨主题重复出现时，才作为较稳定的方法写入正文。

## 试点验证

本指南的人类决策层规则（§3）已在 [`安全策略三阶段决策摘要`](../develop/safety-approval/in-flight/security-policy-three-stage-architecture-decision-summary-draft.md) 上验证过一轮：第 0 层经一次修订（去黑话 + 补齐决策项背景），由 55 行变为约 70 行，随后据此把 R1（语言边界）与 R2（决策项自包含）写成正式规则。

## 局限

1. 规则来自单项目的抽样，尚未在"需求""代码"等其他专项指南上验证。
2. 第 0 层的"人测"（外行读一遍数疑问）目前只在单篇上做过，尚无跨文档统计。
3. 本指南不替代领域安全评审；它约束的是"怎么写清楚"，不保证"设计本身正确"。

## 维护规则

1. 新增反模式前，先确认它**挂得到正文 §2 的某一步**；挂不上的，多为症状描述，应删而不是收。
2. 新增规则时，在本文件补上来源映射与纳入理由；来源文档只用于追溯，其中的历史提交号、测试数字或未完成状态不自动代表当前仓库状态。
3. 规则自身的修订同样走本指南：改动与搬迁分开提交，并在主题 `history.md` 留痕。
4. 若某条规则后续被新证据推翻，先更新正文，再在本文件记录结论变化与证据。
