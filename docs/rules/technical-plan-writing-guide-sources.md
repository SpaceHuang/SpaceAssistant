## 修订记录（2026-10-30）：评审包与人层↔机层一致性

**动因**：评审反馈指出方案文档"细节清晰、整体阐述弱"——人必读 / 人机共读层看不出要改哪些模块、会不会动 agent-sdk 接口、覆盖多少文件，除非拿着文档逐项核对代码。定位结论：缺的不是规格，而是**为评审准备输入**的那一层；原有人层是"决策的延伸"，没有系统视图。

**新增正文两节**：
1. **§2 评审包（RP-1~RP-6）**：六件（一句话变更、链路图、变更面表、契约面六面、量级与拆分判断、待批准清单 + 自曝三处）；变更面表含 ≤20 字作用简述（括号只写"谁依赖它"）与五类改动类型（`新建` / `改造` / `改承重边界` / `改对外契约` / `复用不改`）；契约面六面中 ①② 为承重面（agent-sdk 接口、会话存储接口），要求给结论 + 门禁结果 + 旧数据兼容验证。
2. **§4 人层 ↔ 机层一致性（X-1~X-3）**：X-1 人层论断→机层证据（防空口承诺）；X-2 机层新增面（封闭六类）→人层对应句（防悄悄加戏）；X-3 数量对账。

**试跑依据（2026-10-30）**：以 [`IM标准模式安全审核替代一刀切技术方案.md`](../develop/im-remote/in-flight/IM标准模式安全审核替代一刀切技术方案.md) 的第 0/1 层为样本，试补六件约 65 行（占原文 17%），期间做 6 次代码检索（回答者端口、审批记录类型、策略存储文件、错误码分类）。结果：三个原本答不出的问题（改哪些模块 / 动没动 agent-sdk / 覆盖多少文件）当场可答，并新发现 5 处缺陷（界面归属卡缺失、契约面无结论、能力面数对不上、持久化字段以条件句待批、拆分判断缺失）。**该样本只证明"缺"，尚未证明"补上之后评审效率真的提升"**，需在后续 2–3 份新方案上复核。

**被否决的写法**：
1. 只列路径 + 改动类型、不写作用简述——等于把"这套代码干什么"推给评委。
2. 保持四类改动类型——覆盖不了"唯一 writer / 提交点迁移而签名不变"这类承重墙改动，也覆盖不了"给 agent-sdk 加可选方法"。
3. 把 agent-sdk 与会话存储并入普通"改对外契约"一行——两处有独立门禁与跨版本兼容要求，须单列并附门禁结果。
4. 让评审包做"摘要"、不下钻 ID——摘要不承担可追溯，评审包必须能落到 `D/INV/AC`。
5. 以 R1（人层无内部词）为由把 RP-3 / RP-4 改写成纯业务叙述——已用 §2.7 明确语言边界。

**编号迁移（本次）**：原 §2 规格层 → §3；原 §3 修订纪律 → §5；原 §4 反模式 → §6；新增 §2、§4。篇外无编号引用（`docs/rules/README.md` 与执行计划篇只用文字描述该篇），故未在旧位置留指针。

## 归纳口径

## 局限

1. 规则来自单项目的抽样，尚未在"需求""代码"等其他专项指南上验证。
2. 第 0 层的"人测"（外行读一遍数疑问）目前只在单篇上做过，尚无跨文档统计。
3. 本指南不替代领域安全评审；它约束的是"怎么写清楚"，不保证"设计本身正确"。
4. 评审包（§2）与一致性（§4）的规则来自**单篇**试跑（IM 标准模式方案），尚未在 2–3 份新方案上复核"是否真的降低评审成本"；若后续发现某件长期写不出内容（例如小方案普遍省略链路图），应先改判据，不要直接删件。

## 维护规则

1. 新增反模式前，先确认它**挂得到元指南 §9 的某一步**（或本指南 §3 的规格层要求、§2 的 RP 件、§4 的 X 条）；挂不上的，多为症状描述，应删而不是收。
2. 新增规则时，在本文件补上来源映射与纳入理由；来源文档只用于追溯，其中的历史提交号、测试数字或未完成状态不自动代表当前仓库状态。
3. 规则自身的修订同样走本指南：改动与搬迁分开提交，并在主题 `history.md` 留痕。
4. 若某条规则后续被新证据推翻，先更新正文，再在本文件记录结论变化与证据。
