# IM 安全审核改进需求：少问人，统一设置

日期：2026-10-11（按 `main` 最新代码复核：2026-10-12）  
状态：方案草案，供开发和评审使用；不代表自动审核已启用。当前实现基线 `main` `708270a9` 已包含远程确认的渠道归属展示和 IM 意图/恢复基础设施，尚未实现本文提出的统一 IM 策略域及 IM 标准档自动审核路径。  
详细实现：[开发方案](../develop/2026-10-11-im-security-review-improvement-development-plan.md)

## 1. 要解决什么

用户通过微信或飞书交代任务，通常不会一直盯着手机等确认。安全系统应该先自己判断，真需要用户做决定时再问。

[分析报告](../analyze/2026-10-11-wechat-confirm-every-call-session-51aade6c.md)记录的检索任务有 11 次调用，9 次要求真人确认，7 次因确认超时未执行，约 20 分钟花在等待上。末尾 standard 档对照进一步说明：桌面已经交自动审核的 MCP、未建模脚本、普通文件写入，在 IM 上仍要求真人。原因是 IM 规则没有进入自动审核路径，并非只差一个开关。

另一件事是，设置页虽然叫“安全策略”，微信和飞书仍各有一套档位和配置；同一用户在两个现有渠道需要重复维护策略。

本轮只制定方案，不修改运行代码，不开启现网门禁。报告跨日审计未闭合的部分也不当成已核实事实。

## 2. 本轮明确的原则

1. IM 标准档优先走“确定性检查 → 安全审核 Agent → 必要时人工待办”。固定普通任务集的 IM 结果按绝对门槛验收：11 个合格调用全部自动完成，6/6 项任务完成；公开检索和报时无需真人确认；危险任务未授权派发为零。桌面结果只作旁列观测，不参与通过/失败判定。
2. 自动化比例提高靠准确识别实际影响、充分使用审核和异步等待，不能靠删掉安全检查、把未知动作当只读或把超时当批准。
3. 现有微信、飞书共用一份 IM 安全策略。渠道只负责身份、消息收发和能力适配；本计划不增加生产渠道。
4. 用户委托、网页、附件、转发内容分开看。材料里的命令不能成为授权。
5. 禁止执行、必须真人批准、可自动审核是三种不同情况。“规则锁定”只表示用户不能改规则，不能一律解释为禁止执行。

### 2.1 策略与审批按本次输入入口归属

一次指令的安全策略由**本次指令实际进入系统的可信入口**决定，不由会话最初创建渠道、当前选中的出站渠道或会话是否同时可从桌面访问决定：

- 用户在桌面输入：使用桌面策略；需要用户决定时在桌面审批。
- 用户从微信输入：使用 IM 策略；需要用户决定时在微信审批。
- 用户从飞书输入：使用 IM 策略；需要用户决定时在飞书审批。
- 同一会话从另一个入口发起的新指令，按新指令的入口重新确定策略与审批位置；不得把桌面会话中的旧确认卡片当作 IM 确认，也不得把 IM 待办转成桌面批准。

远程确认只能由原 IM 渠道的已认证入站审批或待办审批入口完成。任何桌面 pending-confirm IPC/兼容 API 对微信、飞书动作都必须拒绝且不得消费确认；不能因用户在桌面打开同一会话就转为桌面审批。桌面代答 Agent 仅适用于本次入口确为 desktop 的动作；远程审核 Agent 的 unavailable、timeout 或无法判定按 IM 异步待办处理，若待办路径不可用则安全失败，不退回桌面确认卡。

审批结果仍绑定渠道、身份、原始会话和精确动作。IM 共用安全规则不代表跨渠道共享 owner、待办或批准。当前代码已通过 `remoteConfirmation` 投影标记和 renderer 过滤，将微信/飞书待确认状态显示为桌面只读状态；这只解决呈现层隔离。现有 `wechat:confirm-response` → `resolveFromDesktop` 主进程路径仍可代答，必须在实施中移除或改为不消费待确认项的拒绝响应；不能把 renderer 无按钮当作主进程隔离。

### 2.2 按 `main` 最新代码核定的实现基线

本需求复核的代码基线为 `main` 的 `708270a9`（包含 `1d4c9bcd`、`ba142372`、`8f1a21fc`，以及微信确认消息 ID 精度修复）。目前可确认：

- 策略包仍按 `desktop`、`wechat`、`feishu`、`automation` lane 处理；`askAnswererFor` 对 `automation` 以外的 ask 仍返回用户，IM 尚未因此进入审核 Agent 路径。
- 远程确认已在共享投影中携带 `wechat`/`feishu` 来源；桌面待确认 store 与交互解析会排除远程确认，工具卡片显示远程等待状态。用户应在对应 IM 渠道审批。
- 微信确认发送适配器现已无损保留平台返回的消息 ID 精度，并尝试建立可引用消息关联；其协议常量仍明确记载真实客户端引用往返未验证，不得把 ID 精度修复或单元/适配器测试写成真实客户端引用验收通过。
- IM 意图归属、Track 持久化、渠道范围校验和恢复/影子门禁基础设施已存在。它们负责远程任务归属、输入范围和恢复，不合并策略配置，也不替代安全策略的最终裁决。

以上为代码现状记录，不改变下列产品目标及验收要求；开发方案和详细计划应复用已有能力，并只为仍缺少的统一策略、事实裁决及安全验收安排工作。

## 3. 一次调用怎么处理

| 检查结果 | 系统做什么 | 是否问人 |
|---|---|---|
| 身份不符、群聊、明确禁止、能力不可用、关键配置坏了 | 拒绝，说明具体原因 | 不问；批准也解决不了 |
| 命中不可变的逐次人工确认规则 | 保存精确动作，发人工待办 | 问一次，不占住执行回合 |
| 工作目录内普通读取等事实充分的低风险动作 | 确定性检查后执行 | 不问 |
| 可自动审核的动作 | 先快通道，再让审核 Agent 判断授权和风险 | 判断通过则不问 |
| 审核无法判断、超时、临时不可用或认为需要人工授权 | 保存待办，继续不依赖该动作的工作 | 有必要才问，不连续重试 |
| 已批准但动作、身份、策略或文件状态变了 | 作废旧批准，重新判断 | 不能拿旧批准执行新动作 |

审核 Agent 沿用统一的 security-approval 技能，不另造“微信审核员”和“飞书审核员”。Agent 批准不能写长期授权缓存。人工普通批准也只管当前动作。

可信事实提取和完整度检查必须先于依赖事实的硬规则。审核补证只能提供线索，由主进程验证后形成新事实快照；新增风险必须重新经过硬禁止、强制人工和外发判断。旧快通道、缓存或 Agent 批准不能授权新快照。提取失败、认证缺失及无法解析时按对应人工或禁止规则处理，不能用自动兜底放行。

## 4. 标准档具体改哪些动作

| 动作 | 本轮目标 | 必要边界 |
|---|---|---|
| 公开信息搜索、MCP 站内检索 | 调用级事实完整时自动审核；重复搜索不逐次问人 | readOnlyHint 和工具名只是线索；必须核实服务器、参数、数据流和副作用 |
| 工作目录内普通读取 | 保留低风险直接执行 | 敏感路径、目录外访问仍按硬约束处理 |
| clean 且远程认证通过的脚本 | 自动审核 | 已发现危险模式、动态执行、未认证等逐次人工规则保留 |
| time.time 等未建模调用 | 允许进入自动审核补证 | “没分析出来”不等于安全；证据仍不足就待办 |
| 在工作目录内新建普通文件 | 自动审核 | 路径规范化、非敏感、非覆盖、内容和目标绑定 |
| 覆盖、删除、批量修改文件 | 首版保留人工，后续按操作细分 | 不用通用 im-write 规则整体放行 |
| 普通网页打开 | 浏览器能力已允许时自动审核 | 不能自动打开被禁用的能力；带私密查询和上传另审 |
| 浏览器点击及飞书资源写入 | 只对已建模、低影响、可验证的子类自动审核 | 高影响、未知 CLI、发消息、改权限仍需人工或禁止 |
| 未命中规则的 write/execute | 可交审核 Agent 补证 | 不得因兜底自动路径跳过能力、边界、人工底线 |
| run_shell、远程浏览器等被禁能力 | 保持原访问控制 | 本轮不顺带开放 |

### 4.1 标准档与严格档的确认体验

| 模式/裁决 | 用户体验与处理 |
|---|---|
| 标准档，动作属于自动审核候选且审核 Agent 成功 approve | 通过最终安全检查后执行，不向用户发确认；这是“标准档自动链路免打扰”的范围 |
| 标准档，命中硬禁止/能力不可用/关键配置故障 | 直接拒绝并说明原因，不向用户发一个批准后也不能解决的确认 |
| 标准档，命中逐次人工底线 | 不调用审核 Agent，按原 IM 渠道创建绑定精确动作的人工待办 |
| 标准档，审核 Agent 明确 deny | 终局拒绝，不创建可批准待办；保留拒绝原因并向用户返回拒绝结果 |
| 标准档，审核 Agent undetermined、timeout 或暂时 unavailable | 不执行，按原 IM 渠道创建绑定精确动作的人工待办；若待办路径不可用则安全失败。不得把失败或不确定解释为通过 |
| 标准档，审核配置错误、递归限制、critical 或 hard-deny | 终局拒绝，不创建批准后可执行的待办 |
| 严格档，动作规则要求人工确认 | 走当前 IM 确认机制；确认码关联原 Track 和精确工具动作，用户在发起动作的微信/飞书渠道回复。硬禁止仍直接拒绝 |

同步确认与异步待办继续使用各自现有的两位确认码/编号入口，不把它们混为同一 waiter。用户输入的短码只用于定位精确待确认项，不是授权本身。确认关联至少绑定 `channel + identityKey + owner + originSessionId + trackId + invocationId/toolUseId`；异步待办还绑定 `todoId + notificationVersion + authorizationEpoch`。Track 不替代身份、通知关联、动作 envelope、事实与策略版本校验。无 Track 关联、串码、跨渠道/身份/Track、过期码或旧通知版本均不得消费或派发；不依赖引用的短编号路径必须按对应渠道做端到端验收。失败时留在原渠道安全待办或 fail closed，不能退回桌面确认。

## 5. 普通回复与主动外发分开

本轮建议保留“回复当前已鉴权 owner 不逐次问人”的产品体验，并将它收敛为统一的受控回复能力：目的地由主进程绑定当前单聊、内容经过外发检查、附件经过路径和内容检查。不能只凭工具名为 reply 就免审。

主动给第三方发消息、发布内容、上传本地资料、修改共享资源权限仍逐次人工批准；不建长期外发授权。即使接收者是 owner，批量导出本地数据和发送敏感附件也不属于普通任务回复。

现有异步审批需求 §5.5 对所有 outbound 要求人工，较早的微信出站需求又要求普通回复免确认。两者有冲突。本方案提出上述精确回复例外，**实施时必须同步修订两份旧文档及出口矩阵，完成评审和测试后才可启用**。例外未就绪时继续执行现有有效约束，不能靠修改 actionClass 绕过。

## 6. 设置只留一份 IM 策略

安全策略页提供“桌面”和“IM 远程”两个用户可选区域。管家保持既有内部策略。IM 区说明“适用于微信、飞书和以后接入的 IM 渠道”，不再各放一个档位选择器。

IM 保留严格、标准、宽松、自定义四档，标准为新用户默认。严格扩大人工确认范围；宽松只扩大已列明的低风险自动范围；自定义支持禁止、直接执行、自动审核、人工批准。各档都不能改变硬禁止、逐次人工底线和外发限制。

共同设置包括：安全档位、规则覆盖、远程能力许可、路径边界、敏感目录、自动审核状态、待办 TTL 和限额、停止远程执行。飞书资源写入等按“能力”显示，注明哪些渠道支持；底层仍使用共同规则，不能再保存成飞书私有安全开关。

渠道页只保留连接信息、凭据、owner 绑定、是否启用渠道等接入设置。微信和飞书的 owner、待办编号、附件记录、审计来源仍隔离；统一策略不等于跨渠道复用身份和授权。

## 7. 老用户升级不能偷偷变宽松

- 两渠道旧设置一致：迁移为一份 IM 配置，保留原行为；按旧行为版本持久保留。门禁开启和重启均不改变旧人工要求；采用新标准档必须另做一次明确的配置切换，并通过启用门禁。
- 旧设置不同：逐项合并，能比较的按较严格值合并；无法比较的自定义规则保留人工或禁止，并在统一设置中展示差异。不能只按档位名称排序。
- 只有一个渠道有明确旧配置：保留该配置；新渠道直接继承统一策略。
- 新用户：标准自动审核档，但在门禁未通过时显示“自动审核未启用”，不能显示自动却实际逐次问人。
- 迁移保存、策略版本和撤销代次一起提交；失败则保持旧有效策略，阻止部分迁移生效。记录迁移结果，保留可恢复的旧快照。
- 用冻结的旧语义解析旧配置，涵盖条件、范围、最终动作变换和能力许可；不能用新 standard 解释旧 standard。迁移结果固定策略行为版本，版本缺失或无法解析时阻止执行；无法表达的条件只能收紧，不能丢掉。schemaVersion 和 revision 不代替行为版本。
- 切换新标准档必须单独展示行为差异并记录用户明确选择，更新 revision/epoch、作废相关待办和授权；门禁只决定自动能力是否可用，不负责切换策略版本。
- 旧字段只用于一次性迁移，之后不再参与运行判断；清理 remoteConfirmPolicy 及 prompt 中的无效描述。

## 8. 待办少打扰，也不能批错

复用现有异步审批：默认 TTL 24 小时，单会话最多 5 个、单身份最多 10 个 pending，创建和预留必须原子限额。普通批准不记忆。

同一精确调用只创建一个待办，补发不延长 TTL。相似查询可以提示“该类动作正在等待授权”，但不能共用批准。待办各有明确目标、影响和原因，逐条编号批准，不提供含糊的“一键全批”。沿用既有明确编号协议，编号耗尽须阻止新建并说明，不能回收旧编号造成错批。

同轮同类动作已有待办时，模型先做独立工作；没有可做的就给已有结果和待办说明。原因必须区分等待人工、用户拒绝、审核超时、策略禁止和配置故障，不能统一报确认超时后继续换参数重试。

自动完成比例 = 无真人批准而成功执行的合格调用数 / 普通任务集全部合格调用数；IM 验收要求固定的 11 个合格调用全部成功自动执行（11/11），6/6 项任务完成，合格搜索/报时无真人批准，危险任务未授权派发为零。桌面结果仅旁列记录，不作为 IM 通过门槛。同时报告整任务完成率、人工通知数、等待时长、失败与拒绝数。不得通过少执行、少检索或把危险调用排出统计来美化结果；测试集和排除项须预先固定。

## 10. 交付与启用顺序

先统一策略数据和设置，再将可信入口来源接入持久 turn context、runtime materials、assembler、确认/待办和恢复派发路径；之后补调用事实与自动审核路径，最后完成异步待办、回复边界和真实派发检查。R13/R14 是独立启用门禁，复用既有 P1-1～P1-7、集成用例、群聊拒绝和关闭恢复；不得用策略 helper、renderer 隐藏或旧版本证据替代真实入口/主进程验收。

微信确认的生产路径必须有可验证的精确回复关联：真实客户端引用往返未验证时，不启用依赖引用关联的批准路径；只有在另有短编号/消息关联协议并通过真实 IM 端到端验收后，才可启用该协议覆盖的范围。不得以桌面代答作为引用关联失败时的兜底。

相关旧文档需要同步：异步审批安全需求、远程私聊安全优化需求、微信出站确认移除需求、安全策略入口需求。冲突条款必须列明替代范围，不允许不同实现各挑一份文档执行。
