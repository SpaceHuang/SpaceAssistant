## 第 0 层：决策层【人必读】

**一句话：** 让 Agent 通过 Wiki 专属能力查找、读取和保存知识，由 Wiki 服务管理页面身份、分类校验、索引和操作日志，避免 Agent 直接操作 Wiki 文件路径。

**只有 3 分钟的话：**

1. Agent 仍负责理解资料、选择类别、归纳和撰写页面内容。
2. Agent 从 Wiki 服务获得当前 SCHEMA 和分类列表；保存时提交 categoryId 与 schema 版本。
3. Wiki 服务校验并保存页面，自动维护索引和日志；Agent 不写索引、日志或 raw 原文。
4. 首版采用单主父级的树状导航；页面类别与逻辑父级分开，跨主题关系用页面链接表达，目录路径由 Wiki 服务管理。
5. D-01 至 D-06 的产品取舍均已决定：分操作工具并按需加载、单主父级树状导航、Agent 提案且用户确认后应用 SCHEMA、服务完全维护索引和日志、在 SCHEMA 内维护结构化分类、在当前聊天中查看和恢复页面历史。公开命名固定为 `memory` 入口及 `memory.wiki_*` 操作；持久化格式和分类区块的具体语法由技术方案定稿。

### 产品决策记录

#### D-01｜助手使用几个知识操作入口？【已决定：A + 按需加载】

背景：现在助手使用通用文件操作来搜索、读取和写入 Wiki，必须理解路径结构；路径选错时会遇到工作目录和共享库之间的访问限制，也可能对错误页面进行操作。

- **A：** 分开提供查找、打开页面、导入资料、读取原始资料、保存页面等明确入口。助手每次选择具体操作，系统更容易把权限限定到该操作和目标。
- **B：** 提供一个通用知识操作入口，由助手传入操作类型和不同形状的参数。入口较少，但错误参数和权限判定需要覆盖更多组合。
- **用户可见后果：** A 的工具选择更明确；采用按需加载后，初始上下文只呈现轻量工具索引，完整参数定义在需要时检索。B 的工具面较短，错误操作的影响范围更难从调用本身判断。
- **可逆性：** 两种方案都能通过后续接口版本调整，但已发布的工具名和参数会形成兼容负担。
- **依据强度：** 现有工具系统支持增加内置能力；当前 Wiki 工作流跨查找、读取、导入和写入多个动作。
- **决定：** 采用 A。页面搜索、打开、来源导入与读取、页面保存等实际操作各自使用独立工具。
- **按需加载：** 参考现有 MCP 延迟加载：初始上下文仅提供 Wiki 工具的轻量索引（工具名和简短用途）；完整参数 schema 不随每轮请求全量注入。Agent 先通过 Wiki 工具发现入口检索能力，再由结果取得匹配操作的完整 schema，之后调用对应的独立操作工具。Wiki 工具发现入口只负责查找和披露 schema，不代替实际操作，也不授予额外访问权限。
- **授权边界：** 已发现或已索引的工具仍须经过原有工具策略、确认、审计和 permit 检查；工具名进入授权集合与 schema 是否随请求披露分开处理，沿用 MCP 延迟加载的授权面与展示面分离方式。
- **公开命名：** 能力发现入口名为 `memory`，Wiki 操作使用 `memory.wiki_*`。本稿后续表格中的 `wiki.*` 是业务动作语义标识，不是最终公开工具名。
- **接口状态：** 操作拆分、按需加载和公开命名均已决定；schema 参数及索引呈现位置由技术方案按现有工具注册与 MCP 延迟加载机制定稿，不改变本决定。

#### D-02｜树状知识页能否有多个父级？【已决定：A】

背景：类别回答“这是什么类型的知识”，树状位置回答“用户从哪个主题入口浏览它”。同一页面可能同时与多个主题相关。

- **A：** 每页只有一个主父页面，其他关联通过页面间链接表达。导航树保持唯一，搜索和页面内容仍可表达多对多关系。
- **B：** 每页可以属于多个父页面。页面能出现在多个导航位置，但移动和页面位置提示需要处理多条路径。
- **用户可见后果：** A 下跨主题内容通过链接到达；B 下同一页可从多个树枝出现，浏览路径更灵活，链接和导航结果也更复杂。
- **可逆性：** 从 A 扩展到 B 需要增加多父关系；从 B 收敛到 A 需要为现有页面选择主父级。
- **依据强度：** 现有页面类别和项目分区是目录式组织，没有多父页面关系的现行约定。
- **决定：** 采用 A。首版启用单主父级树状导航；根页面不提供 parentPageId。类别、唯一主父级和页面间语义关系分别表达，跨主题入口使用页面链接。
- **接口影响：** 创建页面可提交一个 parentPageId；移动页面使用独立 wiki.move_page 设置新的唯一父级。禁止通过多个父级字段或重复页面实现多处导航。

#### D-03｜助手能否修改 SCHEMA？【已决定：A】

背景：SCHEMA 决定分类和知识整理规则。它变化时，助手需要采用新规则；让助手直接改变规则也可能影响后续所有 Wiki 写入。

- **A：** 助手可提出 SCHEMA 修改；用户确认后由专属操作保存。助手不能在普通页面保存时一并改变 SCHEMA。
- **B：** SCHEMA 只由用户在现有管理入口或外部编辑，助手只读取并遵循。
- **用户可见后果：** A 支持在对话中协作调整分类和规则，但每次规则更改需用户确认；B 的规则来源更集中，调整需要用户离开知识整理流程。
- **可逆性：** A、B 均可调整；已应用的新分类可能已经被新页面引用，回退时需要保留旧分类或显式迁移页面。
- **依据强度：** 现行 Wiki 需求允许协作演化 SCHEMA，并规定 SCHEMA 写入需用户确认。
- **决定：** 采用 A。Agent 可提交结构化 SCHEMA 修改提案；用户审阅具体差异并通过现有确认流程批准后，Wiki 服务才应用变更。应用后递增 schemaVersion 并留下审计记录。
- **写入边界：** 提案与应用分为两个专属操作。普通 wiki.save_page 不得修改 SCHEMA；更新操作只接受已批准且版本仍有效的提案，不接受 Agent 自行声明的“用户已确认”字段或凭据。

#### D-04｜索引和日志是否允许人工维护内容？【已决定：A】

背景：索引和日志将由服务根据页面元数据及成功操作生成。当前索引可能含有人工摘要，操作日志也保留了历史记录。

- **A：** 索引和日志完全由服务维护；自定义说明迁移到普通 Wiki 页面。
- **B：** 服务只维护明确标记的生成区块，保留用户维护的自定义区块。
- **用户可见后果：** A 的索引和日志始终反映系统记录的页面与操作；B 可保留手写导航，但生成结果和手写内容需要分区展示。
- **可逆性：** A 可通过普通页面保存自定义说明；B 可在以后移除自定义区块。切换时都需要保留现有文本。
- **依据强度：** 现行默认索引说明由 LLM 在 ingest 后更新，现有需求未明确手写区块的所有权。
- **决定：** 采用 A。索引与操作日志由 Wiki 服务完全维护，不保留可人工编辑的自定义区块。索引中的知识说明迁移为普通 Wiki 页面；既有日志历史作为只读历史记录保留，不伪造为新的操作事件。
- **迁移要求：** 切换前备份并检查现有 index.md 与 log.md；将有价值的人工说明迁为普通页面，保留既有历史日志；完成校验后再由服务接管生成。迁移失败时不得覆盖旧文件或报告切换成功。

#### D-05｜分类定义放在哪里、采用什么格式？【已决定：A】

背景：Agent 需要读懂每个类别的含义，服务需要可靠判断类别是否有效。只在自然语言段落中描述类别，程序可能无法稳定校验。

- **A：** 在现有 SCHEMA 文档中增加格式固定的结构化分类区块，同时保留自然语言规则。用户在一个文档中查看和修改分类及整理规则。
- **B：** 把可校验分类放进独立的 Wiki 分类设置，SCHEMA 文档只保留使用说明。分类管理更结构化，但规则和说明分散在两个地方。
- **用户可见后果：** A 继续以一份 Wiki 规范为入口，编辑时需要遵循规定格式；B 分类配置更像表单，详细规则需要另行查看。
- **可逆性：** 两种方式都可迁移；迁移时需要将分类 ID、名称、说明和父级关系完整保留。
- **依据强度：** 当前 SCHEMA 以 Markdown 自然语言和目录约定为主，新的工具需要运行时校验动态类别。
- **决定：** 采用 A。在现有 SCHEMA 文档中维护唯一的机器可校验分类区块，并保留自然语言整理规则；不另设独立分类配置作为第二份真源。
- **规则：** 服务从结构化区块读取类别 ID、名称、说明、状态和可选父级约束；自然语言段落解释整理策略，不隐式增删类别或覆盖结构化字段。区块语法、边界标记和校验规则在技术方案中定稿。

#### D-06｜页面历史从哪里查看和恢复？【已决定：A】

背景：页面可能被误改或删除，用户需要先查看旧版本再选择是否恢复。入口会决定用户是在当前对话处理，还是离开对话进入 Wiki 面板，也会决定本期是否增加界面。

- **A：当前聊天。** Agent 在当前对话列出版本并展示用户选中的版本；用户选择恢复后，Agent 先在同一聊天完整展示最终页面，再由现有工具确认界面发起批准。不新增 Wiki 面板控件。
- **B：Wiki 面板。** 在现有 Wiki 面板增加历史列表和恢复操作。用户可直接浏览，但本期需扩展面板界面和维护状态。
- **C：延期。** 本期只保留历史快照和冲突诊断，不提供历史浏览、恢复工具或用户恢复入口；用户无法通过本期能力自行恢复页面。
- **用户可见后果：** A 保留对话上下文但需要在聊天中完成选择；B 提供固定页面入口但增加界面；C 不增加交互，但用户遇到误改或删除时不能自行恢复。
- **可逆性：** A 后续可迁移到面板；B 后续可移除但需要迁移使用习惯；C 后续启用恢复前仍须设计入口和确认流程。
- **依据强度：** 本决策由项目负责人在 2026-10-17 的当前会话中明确选择 A；没有新增面板的审批。
- **决定：** 采用 A。历史查看和恢复在当前聊天完成；恢复确认复用现有工具确认界面，Wiki 面板、设置页和文件树不增加专用入口。

**界面归属卡（I8）｜已获项目负责人批准**

| 项 | 决定 |
| --- | --- |
| 放哪个入口 | 当前聊天中与该页面相关的对话；用户可在同一上下文要求列出历史、查看某个版本或恢复。留在这里是为了让页面问题、版本选择和用户指示处于同一上下文。 |
| 形态 | Agent 在聊天中列版本摘要；用户选定后展示目标版本内容。恢复前，Agent 在确认请求紧邻的聊天消息中完整展示最终标题、类别、摘要、父级、正文、来源版本和差异；随后由现有工具确认界面批准该恢复调用。 |
| 样式来源 | 沿用现有聊天消息、工具结果和工具确认组件；不新增专用样式、控件或 token。 |
| 新增还是改造 | 不新增历史面板或 Wiki 面板入口；复用现有聊天渲染与确认流程，仅由新工具返回历史内容和恢复确认材料。 |
| 成本 | 用户需在聊天中完成列版本、查看内容、选择和确认，历史内容较长时会增加对话长度；需维护易读的版本摘要和完整的恢复确认内容，不提供常驻历史浏览器。 |

- **批准记录：** 项目负责人（本仓库用户）于 2026-10-17 在本会话选择“当前聊天”；批准范围为上述入口、形态与不新增 Wiki 面板界面。

### 不需要你决定

- Agent 根据当前 SCHEMA 选择 categoryId；服务负责验证，不让工具定义写死分类枚举。
- 页面正文和摘要仍由 Agent 基于用户请求、Wiki 页面及来源资料整理。
- 保存成功后由服务更新索引、追加操作日志；Agent 不维护这两类文件，人工维护的知识说明放入普通 Wiki 页面。
- 页面历史在当前聊天中查看和恢复；冲突修正由用户明确选择，恢复前沿用现有工具确认界面。
- Wiki 内容继续支持当前页面展示和历史引用；本需求不要求立即替换 Markdown 存储。
- 文件路径不作为 Wiki 页面读写接口；路径只可作为受限的资料导入来源选择。

## 第 1 层：目标与范围【人机共读】

### 1. 价值

当前 Wiki 已集中存放在用户数据目录，并通过 llm-wiki 虚拟路径映射给通用文件工具。Agent 仍需用 read_file、grep、list_directory、write_file 自己查重、选页面、维护 index.md 和追加 log.md。由此产生两类成本：模型必须理解存储布局和通用文件安全规则；Wiki 后台调整路径或索引方式时，模型 Skill 与文件工具行为都要跟着调整。

如果不收窄接口，Wiki 使用会持续依赖模型遵循路径约定，检索和维护行为难以由 Wiki 服务统一校验。完成后，Agent 只需表达检索意图、页面归属、内容和来源；Wiki 服务可独立调整存储、索引和日志实现，同时保留对用户的知识整理体验。

### 2. 目标

| ID | 目标 |
| --- | --- |
| G-01 | Agent 能通过专属 Wiki 操作搜索、打开页面、导入或读取来源、创建或更新页面。 |
| G-02 | Agent 不需要向 Wiki 页面保存操作提供目录路径、文件名或物理存储位置。 |
| G-03 | Agent 根据当前 SCHEMA 选择 categoryId；服务动态校验类别和 schema 版本。 |
| G-04 | 首版采用单主父级树状导航；页面树位置、页面类别和页面间知识关系分别表达，不将目录布局作为 Agent 契约。 |
| G-05 | 页面保存后，索引和成功操作日志自动更新，且可由用户追溯变更。 |
| G-06 | 共享 Wiki 页面与 raw 来源按现有 lane 策略全局共享；projectId 只表示来源，不充当页面或来源 ACL。 |
| G-07 | 保持现有 Wiki 面板、Markdown 页面阅读和旧链接的用户可见体验。 |
| G-08 | Wiki 操作采用独立工具并按需披露完整 schema，降低常驻上下文占用；schema 检索不改变实际操作的授权检查。 |
| G-09 | Agent 可提出 SCHEMA 修改；只有用户通过现有确认流程批准后，Wiki 服务才应用提案并递增版本、保留审计。 |
| G-10 | 索引和操作日志由 Wiki 服务完全维护；迁移时保留历史记录，并将有价值的人工知识说明迁移为普通页面。 |
| G-11 | 类别的机器可校验定义保存在现有 SCHEMA 文档中，自然语言规则继续提供整理指导；类别校验不依赖编译期固定枚举。 |
| G-12 | 保留用户从文件管理器编辑页面、SCHEMA 和 raw 的能力；Wiki 服务在下次相关操作时检测并协调外部变化，保护版本、引用和派生视图。 |

### 3. 范围三清单

**本期做：**

- 定义 Wiki 专属 Agent 操作与参数语义。
- 以轻量能力索引和 schema 检索入口按需披露操作工具定义；Wiki 页面操作保持独立入口。
- 通过专属能力向 Agent 提供 SCHEMA 分类和规则。
- 在现有 SCHEMA 文档中维护机器可校验的分类区块，同时保留自然语言规则；迁移既有分类时稳定映射 categoryId。
- 提供 SCHEMA 修改提案与应用操作；应用前由用户审阅并确认。
- 以稳定页面 ID 进行搜索、打开、保存和引用；创建时可指定一个 parentPageId，移动时通过独立操作修改唯一父级。
- 将索引和日志维护交给服务。
- 在当前聊天中提供页面历史查看与恢复；恢复使用现有确认界面，不增加 Wiki 面板专用入口。
- 明确页面、SCHEMA、raw、索引和日志的外部编辑边界，并在 Wiki 操作时协调外部改动与版本。
- 将资料导入与 raw 读取分别封装；Agent 不写 raw。
- 在切换完成后阻止 Agent 通过通用文件工具继续访问 Wiki 页面、索引、日志和 raw。
- 明确桌面、飞书、微信及自动化通道的 Wiki 范围授权，不扩大现有权限面。

**明确不做：**

- 不要求本期更换底层 Markdown 文件存储。
- 不要求引入向量数据库或新的语义搜索服务。
- 不持续后台监听文件变化，也不因外部文件变化自动执行 Ingest；相关 Wiki 操作时检测并处理外部变化。
- 不新增或改造 Wiki 面板、设置页或文件树界面；页面历史和恢复沿用当前聊天及现有工具确认界面。

### 6. Schema 与动态分类

1. SCHEMA 继续作为 Wiki 领域分类和内容整理规则的可演化来源。它描述知识分类、说明、适用范围、父子约束和 ingest/query/lint 指引。
2. SCHEMA 文档内包含唯一的机器可校验分类区块，至少声明稳定 categoryId、展示名、说明、启用或弃用状态及可选父级约束。该区块是类别身份和状态的唯一机器真源；Markdown 自然语言规则继续说明 ingest/query/lint 等整理策略，不隐式创建、删除或重命名类别。具体区块语法与标记在技术方案中定稿。
3. categoryId 是稳定标识，展示名和说明可调整。工具输入不把当前类别写成编译期固定枚举，服务按当前有效 Schema 校验。
4. Wiki 会话启动时向 Agent 提供当前分类摘要和 schemaVersion；Agent 在类别定义不充分、规则冲突或没有合适类别时，应先读取相关 Schema 规则，再通过 wiki.propose_schema_change 提交分类建议，由用户审阅和确认。
5. Agent 不得在普通 save_page 调用中创建、删除或重命名类别。Agent 可通过 wiki.propose_schema_change 提案；只有用户批准同一 proposalId 的具体差异后，wiki.update_schema 才能应用变更。每次有效变更递增版本并保留审计记录。
6. save_page 提交的 schemaVersion 已过期时，服务拒绝写入并返回当前版本和分类摘要；Agent 刷新规则并重新选择类别。
7. 未知、停用或不符合父级约束的 categoryId 不得自动降级到默认类别。服务返回 category-invalid 和可用类别信息。
8. 已被页面使用的类别不得静默删除。Schema 更新必须保留兼容的弃用类别，或先完成明确的页面迁移；既有页面不得因分类规则变更而丢失。
9. Schema 文档中的结构化区块语法或结构无效时，读取和查询可返回诊断；新建、更新和移动页面写入拒绝，直至管理员修复 Schema。不得从自然语言段落猜测或回退成不受校验的自由写入。
10. 迁移现有分类时，为每个既有类别分配稳定 categoryId，并保留展示名、说明、启用状态和现有父级约束；迁移校验完成前不得启用依赖该区块的写入校验。
11. 用户可通过文件管理器或外部编辑器直接修改 SCHEMA。服务在 get_schema、页面写入、Schema 提案应用前核对当前文件；检测到有效外部修改时生成新的单调递增 schemaVersion 和审计事件。结构无效、类别重复、删除仍被使用的类别或违反现有页面约束时，保留外部文件供用户修复，返回诊断并拒绝依赖 Schema 的写入；最后一个有效 Schema 仅作只读恢复参照，不自动覆盖用户文件。
12. Schema 提案在服务端绑定创建时的 schemaVersion 和内容指纹。用户批准后、应用前若文件内容或版本变化，提案立即失效；update_schema 返回 schema-conflict，不写入、不覆盖，Agent 需基于新版本重新提案并再次取得用户确认。SCHEMA 历史快照可供审阅；回退也作为基于当前版本的新提案处理。

### 7. 分类、树位置与页面关联

- categoryId 描述页面的知识类型，由 Agent 依据当前 SCHEMA 选择。
- 项目标识只标注 raw 来源和页面内容的来源项目，不是页面或来源的授权主体，也不构成按项目过滤或隔离规则。
- 页面以 sourceIds 记录来源；合并来自多个项目的资料时，页面保留全部来源引用和来源项目标注，仍是全局共享页面，不指定唯一 targetProjectId。
- parentPageId 描述用户浏览树中的逻辑父级，不映射为 Agent 可见的目录路径。
- 页面链接或关系描述跨分类、跨项目的语义关联；页面不会因多个关联而被复制。
- 页面 ID 在标题、类别或父级变化后保持稳定。引用使用稳定页面标识；界面可继续展示现有词汇路径作为兼容标签。
- 用户可以通过系统文件管理器或外部 Markdown 编辑器编辑页面。外部标题或路径变化不得更换 pageId；物理移动不改变逻辑 parentPageId。存储位置映射、稳定身份标记和旧路径别名的实现由技术方案确定。若旧版应用或外部编辑器移除了稳定身份标记，且页面路径/历史别名无法唯一关联，服务必须保留文件并报告身份冲突，不得按标题猜测或覆盖。
- 首版树形结构为单主父级；根页面省略 parentPageId，每页最多一个父级，跨主题入口使用页面关系链接。
- parentPageId 与 categoryId 分离；父级必须是可访问的有效页面，不能指向自身或自身后代。
- 归属关系变更由独立 move_page 操作完成，不通过重写文件路径实现。

### 8. 页面保存、索引和日志

1. Agent 在保存前通过 search/open_page/read_page 查找可能重复或需要合并的页面；创建时发现同类别、同父级下的标题冲突，服务返回候选页面，不静默创建重复页。
2. 更新既有页面必须提交 expectedRevision。比较前先协调目标页当前磁盘内容；服务发现 Agent 或外部编辑已推进 revision 时拒绝覆盖，返回冲突页的当前版本；Agent 重新打开、合并后再保存。
3. 页面正文使用 Markdown，以兼容既有阅读和链接体验。页面标题、类别、摘要、父级、来源和版本作为服务可校验元数据。
4. 页面保存成功后，服务根据页面元数据生成索引条目；Agent 不读改索引文件作为检索主流程，也不需要提供目录路径。
5. 服务只在页面变更成功后追加对应操作日志；一次成功变更产生一条可追溯事件。失败写入不得记成成功操作。
6. 索引至少反映页面 ID、标题、类别、摘要、父级、更新时间和来源引用。展示顺序由有效 SCHEMA 的类别顺序及稳定页面排序决定。
7. 日志至少反映事件时间、操作类型、页面 ID、来源 ID、页面 revision 和变更摘要；不得写入 API Key、模型令牌、完整原始资料或与操作无关的消息正文。
8. 索引和日志的维护应与页面变更保持一致。服务无法完成索引或日志更新时，必须能从页面和操作事件恢复；界面不得报告完整成功却留下静默不一致。
9. index.md 与 log.md 可保留为服务生成的 Markdown 兼容视图，以兼容 Wiki 面板和历史链接；不得保留人工编辑区块。切换前备份并检查旧文件，将有价值的人工知识说明迁入普通 Wiki 页面，将既有日志作为只读历史保留；确认迁移完成后由服务接管生成。
10. 对同一工具调用的安全重试不得重复生成页面或重复追加成功日志；不同调用对同一 revision 的并发编辑必须触发版本冲突。
11. 首版不运行持续文件 watcher；在 wiki.search、wiki.open_page、wiki.read_page、wiki.save_page、Schema 读取/应用及索引恢复前，对涉及的文件协调外部变化。搜索返回前，服务必须确保搜索范围内的页面变更已协调；具体扫描或差异检测机制由技术方案确定。外部页面正文或元数据改变后，服务先保存前一快照，再生成新 revision、记录外部编辑事件并刷新索引；search 不得返回已知过期的索引结果。
12. 用户外部重命名或移动页面时，服务按稳定 pageId 识别为同一页面，更新位置映射和索引，并保留旧词汇路径别名；物理移动不改变逻辑 parentPageId，历史 pageId 引用持续打开同页。无法确定身份或发现重复 pageId 时返回 external-change-conflict，暂停该页写入，不静默创建副本或覆盖。
13. 用户外部删除页面时，服务在下次集合核对中将其标记为 tombstone，从活动搜索索引移除，保留 pageId、历史版本和来源记录；旧引用在当前聊天中显示已删除状态，用户可通过历史流程恢复。wiki.restore_page 恢复所选版本的标题、类别、摘要、正文、逻辑父级和来源引用/版本，生成新的 revision 并重新索引，须经现有用户确认流程。
14. 恢复按当前有效 SCHEMA 与页面约束重新校验，不把历史有效视为当前有效。目标类别已停用/删除、历史父级不存在或会形成环路、同类别同父级下标题已被占用、或引用的 sourceRevision 不可用时，返回 restore-conflict 及全部冲突项，不改页面、不推进 revision、不更新索引或日志。服务不得自动换类别、移到根、改标题、替换来源版本或覆盖冲突页面。
15. Agent 可在用户明确选择后为恢复提交 title、categoryId、parentPageId 覆盖项；页面正文、摘要和来源引用仍取自目标版本。目标父级设为 null 表示用户选择根页面。覆盖项仍须通过当前约束校验；确认流程必须展示目标版本及最终将应用的全部页面字段和来源版本，用户确认的正是该结果。若仍冲突则不写入；并发页面版本或 SCHEMA 在确认期间变化也拒绝本次恢复并要求重新读取、选择和确认。
16. 来源历史快照不可用时不恢复或替换成当前来源版本；页面的历史引用保持不变，服务返回冲突诊断。用户如需改变来源引用，必须以普通页面更新明确提交新的 sourceRevision。
17. raw 来源可由用户外部编辑，但 Agent 仍只可读。wiki.read_source 返回当前内容和 sourceRevision，并可按 sourceRevision 读取仍被页面引用的历史快照；外部修改推进 sourceRevision，不自动重跑 Ingest 或改写引用页面。用户外部删除来源时保留 sourceId tombstone、既有引用及所引用版本，读取返回 source-missing；用户恢复文件后服务可重新关联同一来源身份。
18. index.md 与 log.md 是 D-04 决定的服务生成视图，用户可访问文件但外部内容编辑不被接纳为权威数据。下次相关 Wiki 操作检测到缺失或漂移时，服务先保存恢复副本，再分别从页面元数据、服务操作事件重建；恢复副本不并入 index/log，也不改变页面 revision 或 schemaVersion。恢复失败时返回不完整状态且不覆盖唯一可用副本。

### 9. Query、Ingest、Lint 工作流

#### 9.1 Query

1. Agent 获取当前 Schema 摘要，判断用户希望查询的范围。
2. Agent 调用 wiki.search 得到候选页，按需要调用 wiki.open_page 固定版本，再用 wiki.read_page 分段读取正文；搜索命中行可用于从相关位置开始读取。
3. Agent 根据页面和来源证据组织回答；回答中的引用指向稳定页面引用标识，用户可在现有 Wiki 界面打开对应页面。
4. 搜索结果不足时，Agent 可扩大关键词或类别范围，但不得改变当前 lane 的授权范围。
5. Query 过程不要求更新操作日志或页面；用户明确要求归档回答时，通过 wiki.save_page 建立普通页面。

#### 9.2 Ingest

1. 用户显式指定工作目录中的资料，或从 Wiki raw 中选定已有 sourceId。
2. 应用校验并导入来源；Agent 通过 wiki.read_source 读取正文。
3. Agent 根据 SCHEMA 选择 categoryId，搜索全局共享页面，决定创建或合并；sourceIds 表示内容来源，服务记录各来源所属项目用于溯源，不提交目标项目或项目授权字段。
4. Agent 对一个或多个页面调用 wiki.save_page。每次保存都经过 Schema 和 revision 校验。
5. Wiki 服务自动维护索引和成功操作日志，并返回创建、更新、冲突或拒绝结果。
6. 批量 Ingest 保留现有 maxBatchIngest 上限和显式触发语义；单批部分成功时逐页返回结果，不把整批报告成全成功。
7. 导入 raw 与整理 Wiki 页面是两个可区分操作。导入失败不得启动后续整理；Agent 永远不能借 Ingest 写回 raw。

#### 9.3 Lint

- Agent 负责理解内容并检查陈旧结论、语义矛盾、来源不足等问题。
- 服务负责检查结构性问题，例如无效 categoryId、缺失父页面、无效页面关系、索引不一致和孤儿页面。
- 修复知识内容通过 wiki.save_page 完成；结构性索引由服务重建。
- 首版不承诺全自动修复；破坏性、批量或无法确定目标的修复必须先反馈问题清单并等待用户指示。

#### 9.4 页面历史查看与恢复

1. 用户在当前聊天要求查看某页历史时，Agent 调用 wiki.list_page_revisions，在聊天中展示版本时间、变更摘要及外部编辑标记；Agent 不替用户预选恢复版本。
2. 用户选择目标 revision 后，Agent 调用 wiki.open_page(pageId, revision) 固定该历史版本，再通过 wiki.read_page 分段读取，并在当前聊天展示所选版本内容及页面元数据。用户可以继续查看其他版本、明确选择恢复或取消。
3. 用户选择恢复后，Agent 提交目标版本和当前版本。若校验发现类别、父级、标题或来源版本冲突，Agent 在聊天中列出全部冲突；只有用户明确选择允许的标题、类别或父级覆盖项后才能再次提交。
4. 无冲突的恢复请求及用户选择的覆盖项，由 Agent 在当前聊天的确认请求之前完整展示最终标题、类别、摘要、父级、正文、来源版本和差异；随后通过现有工具确认界面批准该恢复调用。用户批准后服务重新校验并应用；用户拒绝、取消或确认期间基线发生变化时不修改页面，基线变化时须重新查看并确认。
5. 历史查看和恢复复用当前聊天消息、工具结果和确认体验，不增加 Wiki 面板、设置页或文件树入口。其他 lane 沿用其现有确认交互；无法提供所需用户确认的 lane 拒绝恢复。

### 10. 授权与安全边界

1. 专属 Wiki 工具仍进入现有工具策略、确认、审计和 permit 生命周期，不获得隐式免确认权。
2. facts 阶段只报告工具操作、pageId/sourceId、项目与通道范围、Schema 和 revision 等观测事实；allow/confirm/deny 由策略引擎决定并产生可查询 trace。
3. final-check 仅核验已批准的主体、操作、目标页面或来源、lane 授权范围、Schema 版本及内容指纹、页面 revision 和来源 sourceRevision；应用 SCHEMA 提案时还要核验获批的 proposalId 与对应差异。失败必须在 executor/dispatch 前结束。
4. Wiki 页面和 raw 来源的跨项目共享按本节矩阵执行；不以 projectId、来源目录或页面 project 标注作为 ACL。各操作仍受现有 lane 身份、授权、确认和 permit 限制。
5. raw 内容只允许通过应用导入进入知识库；Agent 对 raw 只有 sourceId 读取能力，没有覆盖、编辑、删除的能力。用户可通过外部编辑器修改 raw，变化不自动触发 Ingest。
6. Wiki 专属工具不可接收 userData 绝对路径、任意目标路径或目录名。只允许 source 导入操作接收受限的当前工作目录相对来源。
7. Wiki 工具执行失败或未授权时，返回稳定错误类别和可解释原因；不建议 Agent 改用 write_file、edit_file、run_shell 或脚本绕行。
8. 专属工具切换完成后，Agent 通用文件工具对 Wiki 虚拟命名空间的读、列目录、搜索和写入均拒绝或引导改用专属 Wiki 工具；工作目录内普通文件工具行为保持现有规则。
9. Wiki 面板、用户手动打开页面和历史引用继续由应用的 UI 读取通路提供；限制的是 Agent 通用文件工具，不是移除用户浏览能力。
10. 任一新增的不可配置系统约束按仓库安全逻辑变更规范登记；locked 策略规则继续由共享 Policy Engine 管理，不能用 invariant 绕过策略评估。

| --- | --- | --- | --- | --- | --- |

应用导入 raw 与 Agent 直接改写 raw 是两种操作。导入只能由现有用户触发的收录流程或显式授权的来源引用启动，应用负责路径校验、复制和记录 projectId；Agent 不能借 `wiki.import_source` 传入任意路径，也不能把导入接口当作覆盖、编辑或删除 raw 的方式。未获得应用绑定的合法来源引用时，所有 lane 均拒绝导入。

#### 10.2 外部编辑、版本冲突与恢复

用户继续可以通过系统文件管理器或外部编辑器直接操作共享目录。页面、SCHEMA 和 raw 的外部内容编辑有效；index.md 与 log.md 是 D-04 决定的服务生成视图，外部内容编辑不作为权威数据，服务检测后备份异常内容并重建。首版不持续 watcher；检测在下次相关 Wiki 操作时发生，摘要如下：

| 对象 | 外部编辑结果 | 冲突与恢复 |
| --- | --- | --- |
| Wiki 页面 | 下一次搜索/打开/保存或集合核对发现内容变化后，原子保存服务最近一次已记录版本，生成新 revision、外部编辑审计事件并刷新索引。首版不运行持续 watcher，因此两次扫描之间发生的多个外部保存只保证协调扫描时的当前文件状态，不承诺捕获每个中间保存。外部改名/移动在稳定身份仍可识别时保留 pageId 和旧路径别名；外部删除形成 tombstone、从活动索引移除并保留已记录历史。 | Agent 用旧 expectedRevision 保存时拒绝且不覆盖，返回当前版本；重新打开后由 Agent 合并并再次保存。用户在当前聊天查看版本，并在现有确认界面确认恢复后的最终页面；删除态引用显示已删除状态，恢复按当前 Schema 和页面约束校验。身份识别冲突时暂停该页写入，不猜测合并。 |
| SCHEMA | 外部有效修改在下次读取或写入检查时形成新 schemaVersion 和审计事件；外部删除或无效内容时返回最近有效版本的只读副本及诊断，所有依赖 Schema 的写入暂停。 | 所有提案绑定版本和内容指纹；批准后、应用前发生外部改变则 proposalId 失效，返回 schema-conflict，不覆盖文件；修复或恢复 SCHEMA 后重新读取、提案并再次确认。历史有效版本保留，回退作为新版本提交。 |
| raw/source | 用户外部编辑推进 sourceRevision；用户删除形成 sourceId tombstone。 | wiki.read_source 返回最新内容及版本；不自动重跑 Ingest，既有页面保留原 sourceId 与引用版本。用户恢复文件后可重新关联同一 sourceId。 |
| index.md / log.md | 外部文本编辑不进入索引或操作事实；缺失或漂移时服务保存恢复副本并从权威页面/事件重建。 | 修复失败时报告不完整并保留恢复副本；不改变 page revision 或 schemaVersion。人工说明应写为普通 Wiki 页面。 |

页面、SCHEMA 以及仍被页面引用的 raw 来源的前一有效快照及修订历史由服务保留，不能因外部改写、改名或删除而静默丢弃。hash、文件身份标记、扫描范围、并发锁和快照存储位置留给技术方案，但技术方案必须满足本节用户可见结果。

### 11. 错误与恢复

| 情况 | Agent / 用户可见结果 |
| --- | --- |
| Wiki 未初始化 | 明确提示初始化 Wiki；不回退到普通工作目录创建知识文件。 |
| Schema 不可读或无效 | 返回 Schema 诊断；写入拒绝，读取已有页面与诊断信息仍可用。 |
| categoryId 无效或已弃用 | 返回当前有效类别；不自动选另一个类别。 |
| schemaVersion 过期 | 返回新版本和受影响的规则摘要；Agent 重新分类后重试。 |
| Schema 提案过期或未获批准 | 返回当前版本或审批状态；不修改 SCHEMA，Agent 刷新规则或重新向用户提交提案。 |
| pageId 不存在或当前 lane 不可读 | 返回未找到或无权访问；不泄露页面是否存在给无权限调用方。 |
| expectedRevision 冲突 | 返回当前 revision 和页面引用；不覆盖并发修改。 |
| restore-conflict | 所选历史版本与当前 SCHEMA、树、标题或来源版本约束冲突时，返回全部冲突项且不修改页面、版本、索引或日志；由用户选择可行覆盖项后重新确认。 |
| external-change-conflict | 页面身份、外部版本或目标状态无法安全协调时，拒绝写入并返回冲突诊断；不猜测合并或覆盖。 |
| schema-conflict | SCHEMA 内容或版本在提案批准后变化时，提案失效且不应用；要求刷新、重新提案和再次确认。 |
| source-missing | 来源已删除时返回 tombstone 状态；保留页面引用与历史 sourceRevision，不伪造当前正文。 |
| sourcePath 越过工作目录或来源引用未获应用授权 | 拒绝导入；不调用后续 Ingest。sourceId 当前 lane 不可读时拒绝读取。 |
| 共享存储暂时不可用 | 不写工作目录副本；返回可重试状态，不伪报保存成功。 |
| 索引或日志派生视图不一致 | 服务先保存恢复副本，再从页面及事件恢复；在恢复完成前标记结果未完成，失败时保留恢复副本。 |

### 12. 兼容与替代关系

- 当前 Wiki 仍采用集中共享语义，物理根由应用管理；Agent 契约不再依赖 llm-wiki/ 下的文件布局。
- Markdown 页面、SCHEMA、raw 和现有用户外部编辑能力保持兼容；Wiki 操作时协调外部版本。索引和日志文件作为服务生成视图，按 D-04 决议不保留人工编辑区块，外部漂移时先留恢复副本再重建；迁移时将说明转成普通页面并保留既有日志历史。
- /wiki query、/wiki ingest、中文命令别名和文件面板的「收录到 Wiki」继续存在，内部改为调用专属 Wiki 能力。
- 本稿评审并实施后，替代旧 Wiki 需求中要求 Agent 用通用文件工具维护 Wiki 页面、index.md 和 log.md 的条款，以及 Wiki Skill 中对应的文件操作步骤。
- Wiki 集中共享存储需求中关于共享根、迁移、项目注册、旧路径别名和现有 lane 安全边界的条款继续有效，除非本稿另经评审明确改动。
- 新接口上线后，当前版本的 Agent 不得同时使用 Wiki 专属写入操作和通用文件工具写入 Wiki；当前版本应对通用文件工具旁路拒绝并引导使用专属操作。
- 应用旧版本的既有代码无法由新版本改写或拦截。用户启动旧版本时，旧 Agent 仍可能按原有方式写入同一 Wiki 文件；本需求不承诺跨应用版本封锁该写入。用户再次启动新版本后，服务按外部文件变化规则扫描、协调并重建派生索引/日志，不以旧备份覆盖旧版本期间的新内容。
- Wiki 页面、SCHEMA、raw、索引和日志继续使用既有集中共享 Wiki 存储位置与文件存储机制。本期只更换 Agent 能力接口，不迁移到数据库或另一存储位置。

### 13. 验收标准

| ID | 验收场景 | 通过条件 |
| --- | --- | --- |
| AC-01 | Agent 查询 Wiki | Agent 使用独立的 Wiki 专属能力检索、打开并分段读取页面；长页面可按有界片段续读或从指定行开始读取，搜索结果提供 matchLine 定位命中段落，打开时固定的 revision 在整次读取中保持一致。工具输入输出不包含物理路径，也不要求调用通用 grep/list_directory/read_file 访问 Wiki。 |
| AC-02 | 动态分类 | 更新有效 Schema 后，Agent 能看到新 categoryId 并据说明选择；服务接受有效类别、拒绝未知或停用类别，拒绝结果不造成页面写入。 |

| AC-04 | 单主父级导航 | 根页面可省略 parentPageId；页面创建和移动后始终最多只有一个父级；服务拒绝无效或当前 lane 不可访问的父级、自身父级和环路；移动不改变 categoryId、pageId 或既有引用。 |
| AC-05 | 并发更新 | 两个调用基于相同 revision 更新同页；一个成功后另一个收到冲突，不静默覆盖。 |
| AC-06 | 自动索引 | 页面创建、更新、移动或类别变更后，索引按有效 Schema 刷新；Agent 没有索引写操作。 |
| AC-07 | 自动日志 | 每次成功页面变更有对应事件；失败、拒绝、版本冲突不产生成功记录；重试同一调用不重复写记录。 |
| AC-08 | raw 只读 | Agent 可在当前 lane 可读范围内读取 sourceId；通过任意通用文件写入或 Wiki 专属能力修改、覆盖或删除 raw 均被拒绝。 |
| AC-09 | 导入边界 | 允许从当前授权工作目录导入支持的文本源；绝对路径、目录、越界路径和不支持文件拒绝，拒绝后不启动 Ingest。 |
| AC-10 | Lane 权限与项目溯源 | A 写入的共享页面和 A 的 sourceId 可由矩阵允许的其他项目会话读取；A/B 来源合并后的页面仍按 lane 全局共享。相同 lane 权限下，不因 projectId 不同而拒绝；无权 lane 仍被拒绝，工具发现和替换 ID 均不能绕过该限制。 |
| AC-11 | 当前版本的文件工具旁路 | 启用新接口的应用版本中，Agent 对 Wiki 挂载路径使用通用文件工具时被拒绝并获得专属工具提示；普通工作目录文件仍按既有规则访问。旧版应用不受新版代码控制，仍可按旧行为写入 Wiki；再次启动新版后按 AC-19/20/21/22 协调外部变化。 |
| AC-12 | 旧链接和面板 | 从聊天历史打开已有 Wiki 引用时，用户仍能在当前 Wiki 面板查看对应内容；移动或改名不使稳定引用失效。 |
| AC-13 | 部分失败 | 一次保存若页面或其必要索引/日志结果未完成，用户和 Agent 不收到完整成功状态；恢复后结果可追溯。 |
| AC-14 | Wiki 工具按需加载 | 初始请求包含真实可调用的 `memory` 发现工具及轻量 Wiki 能力索引，不全量注入各操作的参数 schema；调用 `memory` 后返回匹配操作的完整 schema，并由 tool loop 注入后续请求的可调用工具集合，Agent 可在后续请求调用该独立操作；检索结果不截断 schema，且不绕过操作自身的授权与确认检查。 |
| AC-15 | SCHEMA 提案确认 | Agent 提案后 SCHEMA 保持不变；用户批准该提案对应的差异后，服务才应用变更并递增 schemaVersion、记录审计；用户拒绝、提案过期、版本冲突或伪造确认状态均不得修改 SCHEMA。 |
| AC-16 | 索引和日志迁移 | 迁移预检报告列明旧 index.md 中将转为普通页面的说明区块及无法分类内容、旧 log.md 的只读留存位置；用户通过现有确认体验确认报告后才接管投影。切换前 index/log 均有逐字备份；知识说明迁为普通 Wiki 页面，既有日志作为只读历史保留；切换后文件只由服务生成且无人工编辑区块；目标标题冲突或迁移失败时不覆盖原内容并报告冲突。 |
| AC-17 | SCHEMA 结构化分类 | 服务从 SCHEMA 内唯一的结构化分类区块读取 categoryId 和状态；自然语言段落不能隐式增加或覆盖类别；区块无效或重复 ID 时返回诊断并拒绝依赖该 Schema 的页面写入；迁移保留既有类别并分配稳定 ID。 |
| AC-18 | 跨项目共享与 lane 授权 | 项目 A 导入来源并保存页面后，项目 B 可在其 lane 获准时搜索、打开该页及读取 A 的 sourceId；融合 A/B 来源的页面显示完整溯源集合且不按项目过滤。对相同操作，拒绝结果只由 lane 或工具策略决定，projectId 本身不构成允许或拒绝依据。 |
| AC-19 | 页面外部编辑冲突与恢复 | 外部编辑后搜索反映最近扫描到的新内容；首版不运行 watcher，因此不承诺捕获两次扫描之间的每个中间保存。旧 expectedRevision 保存被拒绝且不覆盖外部版本。外部改名/移动在稳定身份标记仍可识别时保持 pageId、旧别名和逻辑 parentPageId；标记被移除且路径/历史别名无法唯一关联时报告身份冲突并暂停该页写入，不按标题猜测。外部删除形成 tombstone 并保留历史。用户在当前聊天列出并查看版本、明确选择后，通过现有确认界面按 AC-23/24 恢复；不增加 Wiki 面板入口。 |
| AC-20 | SCHEMA 外部编辑冲突 | 提案获批后若 SCHEMA 外部内容变化，应用被拒绝且文件不被覆盖，必须刷新、重新提案并再次确认；无效或缺失的 SCHEMA 返回诊断并暂停依赖其写入，保留最近有效版本供只读恢复。 |
| AC-21 | raw 外部编辑和来源版本 | raw 外部编辑推进 sourceRevision，不自动 Ingest；页面仍引用保存时采用的 sourceRevision，能读取该历史快照。raw 删除形成 sourceId tombstone，用户恢复后同一 sourceId 可重新关联。 |
| AC-22 | 索引与日志外部漂移 | 对 index.md/log.md 的人工修改不成为权威状态；下一次相关 Wiki 操作先保留恢复副本，再从页面/事件重建。重建失败时报告未完成并保留副本，不改变页面 revision 或 schemaVersion。 |
| AC-23 | 历史版本恢复约束 | 恢复旧版遇到当前类别失效、父级删除、父级成环、标题占用或来源版本不可用时，列出全部冲突且不产生任何部分变更。用户明确提供有效覆盖项后，确认内容完整展示最终标题、类别、父级、正文和来源版本；最终写入再次通过当前约束校验。 |
| AC-24 | 恢复 lane 与确认 | 桌面按现有页面写入策略恢复；飞书/微信仅在现有远程确认可用且用户确认确切最终版本时恢复；automation 等无用户确认能力的 lane 拒绝恢复，任何 lane 均不能以项目来源绕过写入策略。 |
| AC-25 | Wiki 服务首次初始化与控制面恢复 | 可信挂载根首次打开时，存量库通过受控初始化进入只读预检，空 Wiki 进入待启用状态；初始化中断可按持久 bootstrap 标记幂等续跑。初始化标记与服务状态缺失/损坏/不匹配时进入恢复状态，不自动清空重建或回退到 legacy；用户从可信备份恢复控制文件后，服务核对根身份与迁移清单；无可用备份时保持只读诊断并要求人工修复，禁止自动清空重建。恢复完成前禁止 Wiki 写入。 |
| AC-26 | 跨页面与 SCHEMA 约束提交 | 当前版本 Wiki 服务的页面创建/更新/移动/恢复、SCHEMA 应用和迁移恢复在同一领域串行化边界内校验完整活动页面集与当前 SCHEMA；并发服务操作不得形成父级环或同类别同父级同标题重复页，SCHEMA 更新不得留下违反新规则的页面。外部编辑不受该锁控制；扫描发现其造成树、标题或 Schema 冲突时，保留外部文件、返回冲突并暂停受影响的服务写入。任何服务冲突或基线变化均不得产生部分提交。 |

### 14. 需覆盖的安全回归矩阵

实现时至少覆盖以下边界：

- 项目溯源与授权：项目 A 页面由项目 B 会话读取，A 的 sourceId 由 B 读取，A/B 来源融合后页面仍全局共享；在同一项目与跨项目情况下分别验证获准 lane 可读、未授权 lane 拒绝；断言 projectId 单独不改变授权结果。
- 写：新建、有效 revision 更新、过期 revision、类别停用、无效/越权父级、自身父级、移动到后代导致环路、旧 Schema 版本。
- 跨对象并发：A/B 双向移动、并发创建同标题、Schema 收紧类别/父级规则与页面写入交错；断言操作串行化后树无环、标题唯一、所有活动页符合当前 Schema，拒绝时无部分提交；用随机合法/非法操作序列断言上述不变量持续成立。
- 生命周期首次初始化：存量集中库无 service 目录、空 Wiki、bootstrap 中断续跑、state 缺失/损坏、seal 与 state 不匹配；断言前两者可达预检/待启用路径，后几者进入恢复状态且不自动重置。
- 操作日志提交边界：首次页面保存的 `domain_committed` 事件即参与本次 log 投影；domain commit 后崩溃、log 写入后 completed 前崩溃与重复恢复均不漏记或重复记成功事件；prepared/conflict 不进入成功日志。
- 来源：当前工作目录文本文件、已有 raw sourceId、跨项目 sourceId、越界路径、绝对路径、目录、二进制文件；跨项目读取按 lane 结果通过或拒绝，不能按 projectId 拒绝。
- 通用文件旁路：read_file、grep、list_directory、write_file、edit_file 对 Wiki、raw、SCHEMA、普通工作目录路径的处理。
- 外部页面变化：编辑后搜索可见；旧 revision 写入不覆盖；改名/移动保留 pageId 和 parentPageId；删除 tombstone 可列历史并经确认恢复；重复或未知身份时停止写入。
- 历史页面恢复：分别构造类别停用/删除、父级删除、恢复父级导致环路、同类别同父级标题冲突、来源快照缺失；断言冲突完整返回且零变更，再验证用户覆盖后重新校验、确认最终状态并写成新 revision；测试远程确认与 automation 拒绝。
- SCHEMA 竞态：提案批准后发生外部修改/删除/格式错误，应用必须失败且不覆盖；重提案需再次确认。
- raw 外部变化：sourceRevision 单调推进、旧引用版本可读、删除 tombstone 保留引用，变化不自动触发 Ingest。
- 派生视图恢复：index.md/log.md 漂移先备份再重建；失败保留备份并返回未完成。
- 并发与恢复：两个会话更新同一 revision；页面保存成功但索引/日志派生失败；同一调用重试。
- 通道：desktop、wechat、feishu、automation × 页面读、页面写、source 读、SCHEMA 应用、raw 写；跨项目与同项目分别按 lane 矩阵得出相同授权结论。
