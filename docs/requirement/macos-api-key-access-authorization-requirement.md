# macOS API Key 访问授权体验改进 — 需求规格

**版本：** 1.0
**日期：** 2026-10-01
**状态：** 已实现，平台验证待完成
**范围：** API Key 安全存储的 macOS 访问授权时机与失败恢复

## 1. 概述

### 1.1 背景

应用使用 Electron `safeStorage` 加密保存 LLM 服务 API Key。现有解密发生在 Agent/模型调用需要凭据时（`electron/llmServiceResolver.ts` 的 `getLlmServiceApiKey`），因此 macOS 可能在首次 Agent 请求时显示系统钥匙串授权/密码对话框。用户无法从系统对话框看出触发者、数据用途和请求时机，容易将其视为异常或恶意提示。

本需求改善授权提示的时机、解释和恢复路径，不改变用户对模型服务的选择和 Key 的用途。

### 1.2 目标

| 编号 | 目标 |
|---|---|
| G1 | 首次需要 macOS 钥匙串访问时，尽可能发生在用户主动保存或验证 API Key 的前台流程中，而非 Agent 已开始工作后 |
| G2 | 在可能出现系统授权框之前，用应用内文案解释原因、请求的访问范围和用户可采取的操作 |
| G3 | 用户拒绝、取消或授权失败时，Agent 不得静默卡住；显示可理解错误并能引导到设置恢复 |
| G4 | 已保存 API Key 的明文不得由主进程返回 renderer，且不得进入日志、错误消息、埋点或普通配置字段；renderer 仅在用户主动输入或替换 Key 时短暂持有本次输入值，并在提交或取消后清除草稿 |
| G5 | 方案与官方代码签名及分发策略相互独立，可分开决策、实施和验收 |

### 1.3 非目标

- 本需求不决定是否、何时或如何为 macOS 分发包申请 Developer ID、签名或公证。
- 不以签名身份为前置条件，不假定未签名应用必然能消除或必然触发某一种系统提示；具体提示受 macOS 版本、Electron 实现、钥匙串访问控制和本机状态影响。
- 不更换加密算法或凭据存储后端；不引入应用主密码、云端密钥托管或明文文件存储。
- 不改变 Agent 对 API Key 的授权语义，也不将 API Key 交给 Agent 模型作为上下文内容。
- 不处理 MCP Secret 等其他凭据的交互，除非实现时共用的授权状态/错误处理自然适用且不扩大需求范围。

## 2. 当前行为与问题

### 2.1 当前实现路径

1. LLM API Key 以密文形式存于 `secrets.llmServiceKeys`。
2. `setLlmServiceApiKey` 在保存时调用 `encryptSecret`。
3. `getLlmServiceApiKey` 在调用方需要 Key 时调用 `decryptSecret`；异常被捕获并归并为 `null`。
4. Agent/模型请求路径因此可能成为首次解密触发点，读取失败也可能被误认为 Key 未配置。

相关实现：`electron/secureApiKey.ts`、`electron/llmServiceResolver.ts`。保存 API Key 的 IPC/配置 UI 应在实施阶段沿调用链进一步确认。

### 2.2 用户影响

- 系统对话框在 Agent 请求期间突然出现，用户不知道是否应输入 macOS 密码。
- 拒绝或取消后，调用方可能只看到“Key 未配置”或通用请求失败，无法判断需要在本机重新授权。
- 对话框的出现频次、是否可预先触发、拒绝后系统行为须在目标 macOS/Electron 组合实测；产品文案不能承诺“只出现一次”或“永不再出现”。

## 3. 产品决策

### 3.1 授权前置流程

在用户保存一个新 API Key 或替换现有 Key 时，保存流程应：

1. 先在应用内说明该 Key 会被本机安全存储保护，首次读取可能由 macOS 请求钥匙串访问授权；授权只用于让 SpaceAssistant 读取已保存的 Key 并向用户配置的模型服务发起请求。
2. 写入密文后，在主进程安全存储层执行一次受控的读取验证，使潜在系统提示尽可能紧邻用户主动保存行为出现。
3. 验证成功后，保存流程成功结束，并记录该凭据在本次运行中已读取成功（仅运行时状态，不持久化授权结论）。
4. 若验证失败，保留可恢复的状态并明确告知用户。不得把已保存的 Key 从主进程回传 renderer；不得将失败当成“Key 为空”而静默继续。用户需要重新输入时，应由用户在设置页主动重新输入。

实现团队需核实 `safeStorage` 的 API 和 macOS 行为是否允许以受控读取将系统授权提示前置。若验证读取不会触发或不能稳定前置授权，应保留同样的应用内预告和失败恢复机制，并在首次 Agent 使用时进入“需授权”状态及明确提示；不应声称已消除系统弹窗。

**建议的保存原子性：** 新 Key 加密并落库后立即尝试解密。若访问验证失败，避免覆盖已知可用的旧凭据；应采用暂存新密文、验证后提交的流程，或回滚到旧密文。存储/加密本身失败则按现有保存失败语义处理。若系统已保存新密文但授权失败，UI 必须明确指出 Key 尚未验证可用，并提供重试/重新输入/取消保存选择，避免呈现为正常成功。

### 3.2 应用内说明文案

说明应在触发受控读取之前出现，简洁覆盖：

- 为什么可能出现系统提示：SpaceAssistant 正在读取刚保存的模型服务 API Key。
- 为什么需要输入密码/批准：macOS 正在保护本机钥匙串中的加密数据。
- 访问用途：仅供本机应用读取凭据，以连接用户配置的模型服务。
- 用户选择：批准继续，或取消并稍后从设置重试；取消不会把密码交给 SpaceAssistant。

推荐中文文案：

> **macOS 可能会请求钥匙串访问授权**
> SpaceAssistant 需要读取你刚保存的模型服务 API Key，才能验证配置并连接该服务。macOS 可能要求你批准访问或输入 macOS 登录密码。该密码由 macOS 的系统对话框处理；SpaceAssistant 不会读取或保存你的 macOS 密码。你可以取消，之后在模型服务设置中重试。

文案不得暗示 Key 只保存在 Apple 钥匙串内部（当前应用先通过 `safeStorage` 加密并保存密文）；宜表述为“macOS 保护的本机安全存储/钥匙串授权”，上线前按实测的 Electron/macOS 行为校正文案。

### 3.3 Agent 运行时恢复

若 Agent 运行时读取凭据失败：

- 将错误区分为“未配置 Key”“安全存储不可用”“系统授权被拒/读取失败”三类；不向用户暴露系统异常堆栈或任何密文。
- 在 Agent 执行尚未发出模型请求前停止本次执行，显示服务名称及“到设置验证/重新授权”的明确入口。
- 保留用户输入和可重试任务状态；用户完成设置中的验证后允许显式重试。
- 不在后台无限重试，不在同一任务中反复触发系统弹窗。
- 日志只记录稳定错误码、服务 ID（必要时脱敏）和阶段，不记录 API Key、密文、系统密码或完整系统异常文本。

如果目前 `getLlmServiceApiKey` 将所有异常归并为 `null`，需要引入主进程内部可区分的结果/错误类型；renderer 只接收安全错误码与可展示说明。

### 3.4 授权状态范围

- 可以在应用进程生命周期内缓存“本次成功解密”的状态，以减少无意义的重复预检；缓存中不应长期保留明文 Key，实际请求仍按现有凭据传递边界执行。
- 授权成功状态不得写入数据库，也不得在应用升级、重启、账户变更或钥匙串状态变化后被视为永久授权。
- 若 Electron/macOS 在每次解密时仍可能显示授权，产品应保留运行时错误路径，不作单次授权保证。

## 4. 交互与状态

| 状态 | 触发 | 用户可见结果 | 后续动作 |
|---|---|---|---|
| 未配置 | 服务没有 Key | 现有未配置提示 | 打开设置配置 Key |
| 待验证 | 保存密文后、读取验证前 | 保存流程显示“正在验证安全存储访问” | 等待系统/主进程结果 |
| 验证成功 | 解密验证成功 | “Key 已保存并验证” | 正常使用 |
| 系统授权取消/拒绝 | 受控读取失败且可归因为授权问题 | 明确说明授权未完成，提供重试/稍后处理 | 留在设置，不启动模型请求 |
| 安全存储不可用 | safeStorage 不可用或平台错误 | 说明不能安全保存/读取，提供平台级排查指引 | 不退化为明文写入 |
| 运行时读取失败 | Agent 首次读取等路径失败 | Agent 停止并提示去设置验证 | 用户验证后显式重试 |

## 5. 安全与隐私要求

1. 加解密只在主进程执行。设置页 renderer 可在用户主动输入或替换 Key 的流程中短暂持有本次输入值，并通过 IPC 请求提交；已保存 Key 不得由主进程返回 renderer。renderer 只接收 Key 是否已配置、验证状态和安全错误码。
2. 验证不得通过把明文 Key 返回 renderer 完成；在主进程内仅确认解密成功或进行必要比较。
3. 不将 macOS 登录密码采集、传递或保存到应用。
4. 不因减少弹窗而降低 `safeStorage` 加密强度，或将密文/明文复制至不受保护配置、日志、崩溃报告。提交或取消后，renderer 应清除输入草稿；不得通过持久化状态、缓存快照或调试工具保留 Key。
5. 失败回滚要避免误删此前仍可用的凭据；替换 Key 的失败结果必须明确。
6. 数据库中既有密文保持兼容；本需求不要求迁移格式。

## 6. 验收标准

### 6.1 功能验收

- 新增 Key 保存流程中，应用内授权说明出现在任何可预期的系统钥匙串授权提示之前。
- 受控读取成功时，保存结果明确为验证成功，随后 Agent 请求不再把“第一次读取”留到任务中触发（系统行为允许时）。
- 用户拒绝/取消系统授权时，配置页给出可理解状态和重试入口；不会误报 Key 未配置或保存成功。
- 替换已有 Key 时，新 Key 验证失败不会静默丢失旧 Key。
- Agent 遇到读取授权问题时，在发出模型请求前终止并给出设置入口；用户重试前不重复触发授权。
- 多个服务的 Key 按服务分别验证，错误提示指出对应服务，不展示凭据内容。

### 6.2 安全验收

- IPC 请求仅可在用户主动发起的明确前台操作中携带本次输入的临时草稿 Key，包括保存、测试连接和获取服务模型。不得由页面初始化、后台轮询、自动重试或与该操作无关的 IPC 携带 Key。IPC 响应、其他 UI 状态、应用日志、遥测及错误展示均不得包含 API Key、密文或 macOS 密码。
- 已保存 API Key 不会由主进程读取接口返回 renderer；renderer 只在用户输入/替换流程中短暂持有输入值，并在提交或取消后清除草稿。
- 测试连接和获取服务模型可以使用未保存的输入草稿，但只限用户明确点击触发的本次操作；错误、日志和遥测必须脱敏。操作结束后按既定保存/取消流程清除草稿，不得为重试而持久化或复制 Key。
- 验收测试应分别确认：输入期间 Key 仅存在于输入控件/临时草稿；保存、测试连接、获取服务模型等明确操作可将本次草稿传给主进程；提交或取消后草稿清除；响应、错误和其余 UI 状态不包含 Key 或密文。
- 配置数据库仍只保存安全存储生成的密文。
- `safeStorage` 不可用时不提供明文回退。
- 冷启动、应用重启后的首次读取仍能正确处理未授权/读取失败；不依赖持久化授权标记。

### 6.3 平台验证矩阵

针对项目支持的 macOS 最低版本与当前主流版本、开发运行和实际分发构建，记录以下结果：首次保存、首次读取、拒绝、取消、重启后读取、替换 Key、升级后读取。分发构建可使用当前实际产物，不要求已具备官方签名。将系统版本、Electron 版本、构建类型和观察到的系统提示记入验证记录；不把某个本机结果外推为所有 macOS 环境保证。

## 7. 技术实施建议

1. 梳理保存 API Key 的 IPC 入口、`setLlmServiceApiKey` 调用和当前 UI 保存事务，定义“加密—暂存—主进程验证—提交/回滚”的原子流程。
2. 将 `getLlmServiceApiKey` 的失败结果从 `null` 扩展为可区分的内部结果；保留现有公开接口兼容层，逐步更新 Agent/模型调用入口。
3. 增加只返回安全状态的“验证服务凭据”IPC；在用户明确保存/点击验证时调用，不由页面初始化或后台轮询触发。
4. 在设置页实现说明、验证中、成功、失败、重试状态；运行时失败卡片复用相同的设置入口。
5. 增加聚焦测试：加密/解密成功、拒绝/解密异常、Key 替换回滚、错误码映射、敏感值不出现在 IPC 结果和日志、Agent 在模型请求前停止。
6. 在真实 macOS 构建验证 `safeStorage` 真实行为；模拟单元测试不能替代系统钥匙串提示验证。

以上为实施建议，不要求为了方案文档阶段改动产品代码。

## 8. 与签名和分发策略的边界

### 8.1 独立决策原则

官方签名、Developer ID、公证、安装器分发渠道、自动更新信任链属于**分发策略**。它们应在独立的分发策略文档/决策中讨论，不作为本功能需求的前提、验收项或延期条件。本需求必须能在当前未带官方签名的产品分发状态下设计和验证。

### 8.2 可能的技术关系

macOS 钥匙串可能基于应用身份、代码签名信息或访问控制策略决定是否再次询问用户。签名身份稳定性可能影响实际提示频率或升级后的访问行为，但这是待实测的环境相关因素，不意味着本需求需要决定签名策略。若实测发现某行为只能通过特定分发身份改善，应把该事实和证据提交给分发策略决策；本需求仍应保留授权前置、清楚说明和失败恢复能力。

### 8.3 明确禁止的耦合

- 不得以“先完成官方签名”为条件才实施本需求。
- 不得承诺“完成签名即可消除密码框”或“签名后只询问一次”，除非针对目标矩阵有可复现证据，并且由分发策略另行接受该承诺。
- 不因当前无官方签名而降级到明文 Key、硬编码主密钥或弱化错误处理。
- 本需求不改变签名身份、entitlements、钥匙串 access group、证书申请或公证配置。

## 9. 待实测与待裁决

| 项 | 当前判断 | 决策要求 |
|---|---|---|
| `safeStorage` 保存后立即解密是否会把系统提示稳定前置 | 需目标 macOS/Electron 实测 | 若不稳定，按运行时恢复兜底，不宣称消除弹窗 |
| 首次调用发生授权提示时，取消和拒绝是否可区分 | 需实测错误形态 | 内部错误分类可保守归为“系统安全存储读取失败”，面向用户统一提供重试 |
| macOS 系统对话框具体措辞及是否要求登录密码 | 取决于系统/本机钥匙串状态 | UI 文案使用“可能要求批准或输入 macOS 登录密码” |
| 保存失败时保留旧 Key 的事务实现方式 | 需检查当前 IPC/数据库事务边界 | 以不丢失旧凭据为产品验收要求 |
| 官方签名是否能改善提示频率或升级连续性 | 属于分发策略研究 | 独立于本需求验证和裁决 |

## 10. 发布与回滚

- 分阶段发布：先提供错误分类、运行时停止与设置恢复；再启用保存后前置验证与 UI 提示，降低系统行为差异带来的风险。
- 通过功能开关或可回退代码路径控制前置验证（若工程实现成本合理）；不得在关闭时移除运行时错误处理。
- 若某 macOS/Electron 组合出现保存后重复授权、保存事务异常或 Key 丢失，回退前置验证入口，保留明确的运行时提示与安全存储。
- 回滚不得清除既有密文或把 Key 迁移为明文。
