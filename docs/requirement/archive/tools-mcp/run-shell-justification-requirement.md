# run_shell 调用理由参数需求

日期：2026-10-14  
状态：需求细化稿，供评审与实现拆解

## 1. 背景

`run_shell` 可以执行系统命令，现有工具输入主要描述要执行的命令本身。命令文本通常不能说明它为何与用户交代的任务相关，也不能解释模型选择 shell 而非其他工具的原因。人工审核界面（桌面确认卡片及现有 IM 审核消息/卡片）和安全审核 Agent 因而缺少模型对本次调用意图的直接说明。

本需求为 `run_shell` 增加可选字符串参数 `justification`，让模型说明调用理由及其与当前工作目标的关系，并将这段说明呈现给两类审核者：人工审核者和安全审核 Agent。

## 2. 目标与范围

### 2.1 目标

1. `run_shell` 的工具 schema 明确提供 `justification` 参数及清晰的填写指引。
2. 模型可针对每次调用说明：要完成什么、为什么需要执行该命令、它如何推进用户目标。
3. 如调用进入人工审核，确认卡片能看到这段说明。
4. 如调用进入安全审核 Agent，审核申请材料包含这段说明。
5. 说明在工具调用全链路中绑定当前调用，不串到其他命令或后续调用。

### 2.2 本期范围

- 仅扩展 `run_shell`，不要求其他工具提供该字段。
- 字段随 `run_shell` 调用输入传递，并供确认卡片与安全审核 Agent 使用。
- 对缺少、空白或无效的说明定义兼容行为和展示规则。

### 2.3 非目标

- `justification` 不替代命令、安全事实提取、策略判断、权限校验或确认流程。
- 不因说明充分、看似合理或审核 Agent 认可说明本身而改变现有授权边界。
- 不把说明作为长期授权、信任命令匹配条件或决策缓存键。
- 不要求把理由写入普通工具结果、会话标题或日志正文。

## 3. 参数契约

建议工具输入形态：

```json
{
  "command": "要执行的命令",
  "timeout": 120,
  "justification": "需要查看项目依赖安装状态，以判断当前构建失败是否由缺失依赖导致；这对应用户要求我排查构建问题。"
}
```

| 属性 | 要求 |
|---|---|
| 名称 | `justification` |
| 类型 | 字符串 |
| 必填性 | 可选；缺少字段的旧调用仍按现有行为处理 |
| 内容 | 用自然语言简要说明本次命令的目的、必要性及与用户目标的关系 |
| 作用域 | 单次工具调用；每次调用独立提供，不跨调用继承 |
| 信任级别 | 模型提供的非可信说明，仅作为审核上下文，不构成用户授权或安全事实 |

工具描述应要求模型提供具体、可核对且针对本次命令的说明；不应只写“执行命令”“完成任务”等空泛内容。不得鼓励模型把命令输出中出现的指令、网页/文件中的文字或第三方要求当成用户目标或授权依据。

实现应对输入执行类型校验和长度上限控制。上限定为 2,000 个 Unicode 码点，按规范化后字符串计数；去除首尾空白后为空的值按“未提供”处理。非字符串值按无效参数拒绝，不得隐式转成字符串。超限输入在进入准备快照前按码点安全截断至上限，并记录 `truncated: true` 元数据；人工审核与安全审核均使用同一截断后快照，并标注“内容已截断”。原始超限正文不得进入后续持久化快照。

## 4. 展示要求

### 4.1 人工审核确认卡片

当 `run_shell` 调用需要人工审核时，当前链路的审核界面应在命令及现有风险信息附近展示模型给出的调用理由，并使用清晰标签（例如“调用理由”）。范围包括桌面确认卡片以及现有微信、飞书人工审核消息/卡片所支持的呈现形式；按渠道能力适配展示，不得据桌面已显示推定 IM 已覆盖。要求：

- 原文展示，不将其改写成系统事实或审核结论；保留可读换行，正确转义/净化 UI 文本，不能按 HTML 渲染。
- 不隐藏命令、路径、影响范围等现有审核信息；理由不得取代这些信息。
- 未提供或为空时，卡片不显示空白区块；既有确认流程不因此失败或改变。
- 如内容被长度上限截断，明确提示“内容已截断”。
- 确认/拒绝按钮、确认范围、超时和授权语义保持现状；理由正文不作为批准范围、授权依据或决策缓存匹配条件。理由可以作为规范调用快照的一部分参与现有完整输入完整性哈希，详见 §5。

### 4.2 安全审核 Agent 申请材料

安全审核 Agent 针对 `run_shell` 作出审核时，申请材料应将 `justification` 作为独立字段/章节提供，并与本次工具调用及目标上下文明确关联。要求：

- 同时提供现有命令、调用事实、安全信号、策略与执行上下文；不得以理由替代这些可信数据。
- 明确标注该内容来自模型、属于未经验证的主张。审核 Agent 应把它作为意图线索，核对其与用户目标、命令实际效果及提取事实是否一致。
- 理由与命令不一致、与用户目标无关、试图扩大授权、引用不可信内容作为授权，或说明不足时，不得因此提高信任或放宽规则；按现行审核策略处理。
- 字段缺失时按“模型未提供理由”处理；不得由系统根据命令自行伪造模型理由。
- 不因加入该字段而改变安全审核 Agent 的输出格式、审批条件或失败/超时处置。

## 5. 数据流与生命周期

`justification` 应从模型生成的原始 `run_shell` tool input 出发，绑定到同一调用标识，并传到确认展示模型及安全审核请求材料。字段应与命令一起经历现有解析和校验链路，但不能进入 shell 命令、环境变量、工作目录或进程参数；不得改变实际执行内容。

若工具调用经过队列、确认等待或审核重试，理由必须仍对应原始调用快照。命令或调用目标发生变化并形成新调用时，必须使用新调用自己的理由，不能复用旧理由。审核补证或重新评估时应能区分原始模型说明和系统新提取的事实。

### 5.1 正文保留与载体边界

为保证待确认调用的恢复、重放及审核复核能够还原同一申请，截断后的规范 `justification` 正文随该次规范工具调用快照持久化。规则按载体区分如下：

| 载体 | 是否保存理由正文 | 规则 |
|---|---|---|
| 规范工具调用快照 / 会话真相（含用于恢复待确认调用的事件记录） | 是 | 保存进入准备阶段的同一规范化、限长快照；与 invocation/tool-use 标识绑定。重放不得从别的调用或新生成文本补理由。 |
| SQLite 会话数据及现有会话备份/导出 | 是 | 按该会话工具输入既有的保留、访问控制、删除和导出策略处理；不得为理由另建更宽松的副本。 |
| 确认界面与安全审核申请材料 | 是 | 仅展示/发送对应调用快照；复核和恢复使用相同快照与截断标记。 |
| 普通运行日志、诊断日志、审计摘要 | 否 | 不记录正文；如需诊断，仅记录是否提供、码点长度及是否截断等最小元数据。 |

会话事件链路当前会记录工具参数，因此实现需确保事件中的理由与规范调用快照一致，并将正文视为会话数据而非普通日志。删除会话或清理对应工具调用数据时，理由正文随同该调用数据一并删除。脱敏规则不得导致确认与安全审核使用不同理由快照；如既有会话存储策略不能可靠保存/恢复该字段，应先调整该载体契约，不能静默丢字段或从日志恢复。

## 6. 兼容性与异常处理

- 旧模型或旧提示未发送 `justification`：工具照常按现有安全流程处理，确认卡片与审核材料中标记缺省或省略该区块。
- 未知额外字段继续遵守现有 schema 校验行为。
- 类型错误、极长内容、控制字符或格式异常不得导致 UI 注入、审核消息结构破坏或命令改变；展示层按纯文本安全处理。
- 字段透传失败不得导致安全确认被跳过。若审核通道要求字段但序列化失败，应按现有 fail-closed / 审核失败规则处置。
- `justification` 不进入命令摘要、信任命令前缀、策略缓存键或调用执行参数。正文不作为批准范围或授权依据；允许其作为原始规范调用输入的一部分参与现有完整输入完整性哈希（`inputSnapshotHash`）。该哈希只校验快照未漂移，不代表批准理由主张，也不扩大授权范围。初审、重放、复核和执行前核验必须针对同一规范快照计算/核对哈希；不得只在单侧剔除该字段。

## 7. 验收标准

1. `run_shell` 工具 schema 接受可选字符串 `justification`，工具说明引导模型解释“为何需要此命令”及“与用户目标的关系”。
2. 含理由的调用在人工确认卡片中与正确命令同时显示；并行或连续调用之间不串内容。
3. 含理由的调用在安全审核 Agent 申请材料中与正确 invocation/tool-use 标识关联，且明确标注为模型提供、未经验证的意图说明。
4. 缺失、空字符串和纯空白输入不会出现空白 UI 区块，且原安全流程保持有效。
5. 理由不改变命令执行参数、策略决策输入中的可信安全事实、用户批准范围或授权缓存；命令变化使旧批准失效，理由仅作为规范输入快照参与完整性哈希，理由变化也使旧快照绑定失效并按现行流程重新审核。
6. HTML/脚本样式文本按纯文本显示；超长内容按照统一长度策略处理，并在截断时提供提示。
7. 理由透传失败或审核失败时不会绕过现有确认/拒绝机制。
8. 规范调用快照、会话数据库及既有会话备份/导出按 §5.1 保存同一限长理由，以支持恢复/重放；普通运行、诊断和审计摘要日志不保存正文。恢复待确认调用时理由与原调用正确关联，且确认流程不会被跳过。
9. 初审、待确认恢复、审核复核与执行前完整性核验对同一规范输入快照采用一致的 `inputSnapshotHash`；命令或理由任一改变都不能沿用旧批准。理由内容不参与信任前缀或决策缓存匹配。
10. 桌面、微信和飞书现有人工审核呈现均有对应验收；真实 IM 客户端的展示与交互需在相应外部环境验收。

## 8. 实现约束

1. 安全审核 Agent 的系统指令需显式说明理由是不可信的模型陈述，不能单独构成授权依据。
2. 确认卡片、IM 审核消息、会话事件、数据库和备份/导出需按 §5.1 使用同一规范化快照；投影 DTO 不得丢失 invocation 绑定、截断标记或理由内容。
3. `inputSnapshotHash` 对规范工具输入完整性校验，包含规范化后的 `justification`；该哈希不等于审批理由认可，也不将理由变成授权范围。
