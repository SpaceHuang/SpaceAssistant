## 1. 背景与目标

IM 远程会话（飞书、微信）目前没有清晰、可靠的模型和思考强度选择入口。远程任务应能跟随桌面「大模型服务」中的语言默认模型，也应允许用户为远程任务单独指定模型；思考强度需要独立配置，缺省为「低」。

本需求在「设置 → 远程操作 → 远程通用设置」增加两项配置：

1. **处理远程任务的大模型**：提供「与默认设置保持一致」及当前可用语言模型选项。
2. **思考强度**：提供产品支持的思考档位，默认「低」。

两项配置对飞书、微信共用，并影响之后开始的 IM 回合。每回合的模型、服务及思考强度必须作为一组可信配置冻结并传到 Agent Loop，不能在装配阶段重新读取另一份可变配置。

**需求优先级：** 本文的远程 Thinking 设置是对 [Thinking 强度设置需求 §7.6/OQ-10](./thinking-effort-settings-requirement.md)“飞书/微信 lane 恒为 `off`”决策的后续产品变更，仅在 IM lane 上覆盖该决定；Butler 和其他非 IM lane 继续遵守原决定。本文与旧文冲突的 IM 条款以本文为准，实施时应同步更新旧文的状态/交叉引用，避免两份规格同时声称相反行为。

## 2. 术语与模型来源

### 2.1 可用模型

沿用多服务模型需求的可用模型定义：模型必须启用，且至少有一个当前启用的 LLM 服务通过 `supportedModelIds` 支持该模型。远程模型列表仅展示其中可作为语言模型使用的条目；不应用视觉专用选择规则。

默认语言模型以 `preferredLanguageModelId` 解析后的当前可用模型为准。若该优选值已失效，按多服务模型需求中的语言模型回退规则取得实际默认模型。界面和运行时必须共用同一解析结果。

### 2.2 继承与显式选择

远程模型选择有两种模式：

- **继承默认**：用户选择「与默认设置保持一致」，或配置从未显式指定远程模型。远程有效模型始终解析为当前默认语言模型；桌面语言默认变化后，之后的新 IM 回合跟随变化。
- **显式指定**：用户选择列表中的具体模型。有效模型固定为该模型，直到用户重新选择继承或另一个模型；桌面语言默认变化不覆盖显式选择。

必须显式保存选择模式（例如 `inherit` / `explicit`），不能仅凭 `remoteDefaultModelId` 是否等于当前默认值推断模式。否则用户显式选中当前默认模型后，默认值日后变化时无法判断是否应跟随。

### 2.3 `remoteDefaultModelId` 的存储语义

`remoteDefaultModelId` 在本需求的新存储语义中统一定义为 **ModelEntry.id**，不是模型显示名，也不是 `supportedModelIds` 之外的服务端模型名。配套的选择模式字段是权威信息；该 ID 表示当前有效选择的物化值。

- 继承模式：`remoteDefaultModelId` 必须与当前解析出的默认语言模型 ID 保持一致。默认语言模型变更时，须在同一配置更新中同步飞书和微信的该物化值；选择模式仍为 `inherit`，因此运行时不得将其误认为固定显式绑定。
- 显式模式：字段保存用户选中的可用模型 ID。
- 服务端请求使用的模型名、服务 ID 和凭据由该模型 ID 解析，不得把数字 ID（例如 `5`）直接当作 provider route 的模型 ID。

若现存版本将 `remoteDefaultModelId` 保存为模型名称，升级时须执行一次性配置迁移：解析名称并写为模型 ID；无法匹配时转为继承模式。迁移完成后，运行时只读取新字段语义，不保留按旧名称读取的分支。

## 3. 设置界面

### 3.1 远程任务模型

- 位置：设置 → 远程操作 → 远程通用设置。
- 标签：**处理远程任务的大模型**。
- 第一项固定为 **与默认设置保持一致**；显示当前解析出的默认语言模型名称作为辅助信息（例如「与默认设置保持一致（deepseek-v4-pro）」）。
- 后续选项与「大模型服务 → 语言模型 → 默认」使用同一个可用模型数据源、同一排序及模型展示组件（名称、服务来源或能力标识按模型设置页现有规则展示）。
- 具体模型选项只显示可用语言模型。不可用模型不得作为新选择项。
- 配置页打开、可用模型变更或默认语言模型变更后，列表和当前选中项应刷新。
- 当前为显式模式但所选模型已不可用时，保留配置以便恢复，展示不可用提示；运行时按 §5.3 处理。不得静默把它显示为另一具体模型而让 UI 与持久状态不一致。
- 点击「与默认设置保持一致」即切换为继承模式并清除/归一显式选择；之后默认语言模型变化会反映在该项的辅助名称和实际运行配置中。

### 3.2 思考强度

- 标签：**思考强度**。
- 选项使用产品统一的 `AgentReasoningEffort` 档位及本地化标签，并根据当前远程有效模型的 `thinkingLevelMap` 更新可用项；模型变更或继承的默认模型变更时同步刷新。`off` 恒可用；基线没有明确排除的档位按现有 fail-open 规则保留。
- 新安装、字段缺失或旧配置迁移后的远程默认值为 **低（`low`）**。
- 此设置独立于桌面全局思考强度与单个桌面会话覆盖；修改桌面全局强度不得改变远程思考强度。
- 若当前模型不支持已保存的请求档位，按统一 `resolveSessionThinkingBinding` 语义向下解析到最近可用档位（`off` 为兜底），只改变本回合有效值，不自动改写用户保存的远程请求档位；设置页应显示有效档位及降级说明。模型明确 `supportsThinking === false` 时仍强制降级为 `off`。

## 4. 数据模型与存储迁移

远程共用配置（`RemoteImCommonConfig`，由飞书和微信配置共同承载）至少需要表达：

| 概念 | 建议字段 | 语义 |
|---|---|---|
| 远程模型选择模式 | `remoteModelSelectionMode: 'inherit' \| 'explicit'` | 独立权威字段，区分跟随默认与用户显式绑定 |
| 远程有效模型 ID | `remoteDefaultModelId?: string` | `ModelEntry.id`；继承时是默认语言模型 ID 的同步物化值，显式时是用户绑定 ID |
| 远程请求思考强度 | `remoteThinkingEffort?: AgentReasoningEffort` | 用户保存的请求档位；有效缺省 `low`，可因模型能力解析为另一有效档位 |

字段可按实现需要调整命名，但不得丢失上述语义。通用设置保存、默认语言模型切换、可用模型迁移应同时更新飞书和微信配置，沿用当前 IM 公共字段的双写方式。旧配置未包含模式字段时：

1. 字段缺失或模型 ID 为空：迁移为 `inherit`。
2. 旧值能匹配当前模型目录中的 ID 或旧模型名称：为避免破坏既有用户明确配置，将其迁移为 `explicit`，并记录解析后的模型 ID。
3. 旧值无法匹配：迁移为 `inherit`，并记录可诊断的迁移事件，不阻断启动。
4. 思考强度缺失或非法：有效值为 `low`；持久化迁移可惰性执行，但读路径不得因此失败。

飞书与微信的公共配置若历史上存在不一致值，主进程必须在开放 IM 入站处理前，或最迟在首条新 IM 回合解析任何渠道配置之前，调用两渠道共用的公共配置归一入口。入口以飞书公共配置为历史冲突迁移源，将归一结果写入飞书和微信；飞书/微信 router 均不得绕过该入口直接用各自历史值准备回合。设置页只展示和修改已归一的公共配置，不承担生产迁移职责。

迁移必须幂等，并使用独立于远程审批/安全配置确认版本的模型配置迁移版本标记。迁移标记仅可与两渠道公共配置的双写在同一持久化事务中提交；若底层存储无法提供单事务，则必须采用可恢复的迁移状态，并在确认两侧写入成功后才标记完成。并发首入需串行化或通过事务/CAS 保证只有一个归一结果。任一读取、写入或提交失败时，不得开始该 IM 回合的配置解析、接受或 Provider 请求；应保留可重试状态，后续启动或入站重试迁移。不得让两个渠道分别退回读取旧值继续执行。迁移需记录来源、版本和结果，避免两个渠道继续各自使用不同的远程模型或 Thinking 配置。

## 5. 运行时解析与 Agent Loop 契约

### 5.1 回合模型解析

每个 IM 回合在准备/接受阶段解析以下绑定：

1. 生产 IM router 在准备 turn 前，以远程模式解析出的有效模型更新/解析会话绑定，并从该会话模型、实际可用服务及远程请求 thinking 档位生成可信执行配置。
2. 将最终模型名、服务 ID、有效 thinking effort、请求 thinking effort（若能力降级）写入 turn execution config；`createAcceptedTurnFromPrepared` 将该配置纳入不可变 `acceptedTurn.config`。
3. `runImRemoteAgent` 必须要求有效的 `acceptedTurn`，并只使用 `acceptedTurn.config` 中冻结的 model/service/thinking 组装 Agent Invocation。缺少 accepted turn 或其中必需字段时，作为内部装配错误在发出 provider 请求前失败；Agent Loop 不得读取全局默认模型、会话当前值或任何回调来补齐缺失配置。
4. 按冻结模型名解析对应 `ModelEntry` 与凭据。`ModelEntry.id` 只用于本地目录身份、能力标记及统计关联；provider route 的能力基线键和 route profile `modelId` 使用基线可识别的 provider 模型标识/模型名。两种身份不得混用。
5. Provider 调用、审批等待后的恢复必须继续使用同一个冻结 accepted turn 配置，不得重新读取桌面默认值、会话当前值或当前远程设置。冻结服务及其凭据无法精确解析时，按 §5.3 失败；不得切换模型或服务。

显式模型对已有远程会话生效规则：**下一个新 IM 回合起生效**。准备回合时将远程有效模型及其服务绑定写入该回合冻结配置，并同步会话模型绑定；执行中的回合不因用户改设置或桌面默认变化而改变。

### 5.2 思考强度解析

远程回合请求档位取 `remoteThinkingEffort`；缺省为 `low`。按当前远程模型解析该请求档位后，得到本回合有效档位：

- 请求档位在该模型可用档位中：有效档位等于请求档位。
- 请求档位被模型基线明确排除：按统一档位绑定规则向下选择最近可用档位；保留请求档位，以便 Invocation 记录 `reasoning.degraded`。
- 模型条目明确 `supportsThinking === false`：有效档位为 `off`，同时保留原请求档位用于诊断/降级记录。
- 模型能力未知：沿用现有 fail-open 规则，使用请求档位；若上游拒绝该 effort，仍走现有 provider fail-soft 降级和记忆逻辑。

turn execution config 分别冻结请求档位和有效档位：`thinkingEffort` 始终是按当前模型能力解析后的有效值；仅在二者不同时携带 `requestedThinkingEffort`。Invocation assembler 必须接收并使用冻结的有效值写入 `profile.reasoning.effort`，同时接收请求值用于生成 `profile.reasoning.degraded: { from, to }`。assembler 不得把请求档位当作执行档位，也不得再次按 `ModelEntry.supportsThinking` 或其他可变数据重新推导；能力校验和降级必须在 turn 配置冻结前完成。不得漏传有效值而落入装配器默认 `off`，也不得使用 `enableThinking` 兼容映射把档位意外改成 `medium`。Provider wire 参数还可能因服务端拒绝 effort 而降级；这不反向改写该 turn 已冻结的 Invocation 模型能力解析结果。

**注意：** `profile.reasoning.effort === 'low'` 不是所有 IM turn 的通用断言。只有远程请求值为 `low` 且当前模型没有明确排除 `low`、也未被 `supportsThinking === false` 整体降级时，最终 Invocation 才应为 `low`。例如当前模型基线对 `deepseek-v4-pro` 的 `low` 映射为 `null`，需按模型可用档位规则解析；而 `deepseek-flash` 的 `low` 有效，可以用来构造最终为 `low` 的正向测试。

### 5.3 配置失效与回退

| 情况 | 行为 |
|---|---|
| 继承模式，默认模型可用 | 使用当前解析出的默认语言模型 |
| 继承模式，优选默认失效但有语言回退项 | 使用多服务模型需求定义的语言模型回退结果 |
| 显式模型仍在可用模型池 | 使用用户指定模型 |
| 显式模型在准备/冻结前不可用 | 不接受该回合；明确失败并提示修复远程模型选择或大模型服务配置。保留显式选择以便模型恢复后继续生效 |
| 准备阶段需要为模型选择服务，且尚未冻结 accepted turn | 按现有服务选择规则，从当前可用服务中选定一个确实支持该模型且凭据可用的服务；选定的模型与服务一起写入待冻结配置。仅此冻结前阶段可以在候选服务间选择 |
| accepted turn 已冻结模型 M / 服务 S | 后续初次执行和审批恢复必须精确解析 M/S。S 已删除、未启用、取消对 M 的支持或缺少/撤销凭据时，在 Provider 请求前明确失败；不得切换到其他服务、默认模型或其他模型，也不得改写 accepted turn 或会话绑定 |
| Provider 返回额度耗尽、余额不足或速率限制 | 当前 turn 以 Provider 错误失败，向用户返回额度/限流诊断和可重试提示；不得在当前 turn 内改用其他服务/模型或重放可能已产生副作用的请求。用户修复额度后可重试，或先调整服务设置再开始新 turn |
| 没有任何可用语言模型或凭据 | 明确失败并提示到大模型服务设置修复；不得尝试 provider 默认模型或把目录数字 ID 作为模型名发请求 |
| thinking 档位被该模型基线明确排除 | 向下解析到最近可用档位，任务可继续，并记录 requested/effective 降级 |
| 模型条目明确不支持 Thinking | 有效档位降为 `off`，任务仍可继续，并记录降级 |

“当前服务下可用”采用多服务设置的可用池规则：所有启用服务的可支持集合并集。准备阶段、accepted turn 冻结前，必须为模型确定一个具体且凭据可用的服务；多个服务均可用时按既有服务解析规则选择，并将选出的 `llmServiceId` 一并冻结。冻结后只允许精确解析已冻结的模型/服务组合，不能再次运行会遍历候选服务的通用解析器来补救失效绑定。若现有凭据解析 API 会在指定服务失败后尝试其他服务，生产冻结路径必须改用精确服务解析，保证解析结果与 accepted turn 一致；不得将密钥写入 accepted turn。冻结绑定失效时，本回合进入明确失败终态并向远程用户返回可操作的服务配置修复提示；审批恢复也遵守此规则。

## 6. 生效与并发

- 设置变更只影响变更后开始配置解析的新 IM 回合。
- 已创建并冻结 execution config 的 turn 使用原模型、服务和 thinking 档位直至终态，包括等待审批后的恢复执行。
- 恢复执行必须继承原 turn 的模型、服务和 thinking 绑定，不重新读取桌面默认值或新的远程设置。
- accepted turn 冻结后，如果原服务被删除、取消模型支持、停用或凭据不可用，初次执行及审批恢复均在 Provider 请求前失败，不请求其他服务/模型、不改写冻结配置或会话绑定，并返回明确的配置修复提示。
- 微信和飞书遵守同一解析规则；渠道专属提示、出站能力不改变模型绑定语义。

## 7. 非目标

- 不新增桌面会话级模型选择器；桌面链路仍按其现有会话/turn 配置工作。
- 不改变定时任务的固定模型与思考强度快照语义。
- 不修改大模型服务页的优选默认算法、模型能力基线或服务选择算法。
- 不在本需求中允许 IM 发送图片或选择视觉模型。

## 8. 验收标准

### 设置与模型列表

- [ ] 远程通用设置显示「处理远程任务的大模型」和「思考强度」。
- [ ] 模型列表第一项为「与默认设置保持一致」，其余与当前可用语言模型目录一致。
- [ ] 新增、启用、禁用模型，或修改服务支持模型/启用服务后，远程模型候选项随可用池更新。
- [ ] 修改语言默认模型后，继承项显示并解析为新的默认模型；显式选项不被改写。
- [ ] 选择继承项后持久化模式为 `inherit`；选具体模型后持久化模式为 `explicit` 且模型 ID 正确。
- [ ] 未触碰旧配置升级为继承模式；有效旧模型绑定迁移为显式模式；无效旧值不会进入 provider 请求。
- [ ] 主进程在首条飞书或微信新回合解析配置前，使用同一幂等迁移入口归一公共配置；旧飞书模型 A / 微信模型 B 升级后不打开设置页，分别或并发收到首条任务时，两回合均冻结为飞书迁移源确定的同一公共选择。
- [ ] 公共配置迁移在两渠道写入成功后才提交独立迁移版本标记；注入读取/写入/提交失败时，不接受回合、不发 Provider 请求，后续启动或入站可重试；成功重试及重启、打开设置页均不改变已归一选择。
- [ ] 远程思考请求强度初始/缺省为低；修改桌面全局 thinking 不改变远程设置。
- [ ] 切换远程模型后思考档位选项按其 `thinkingLevelMap` 更新；`off` 始终可用，未知能力按 fail-open 规则处理。
- [ ] 已保存请求档位在新模型下不可用时，只解析有效档位、不改写持久请求值，UI 显示降级结果。

### Agent Loop 与冻结配置

- [ ] 继承默认时，新 IM turn 的 session、execution config、invocation profile 与 provider request 使用同一模型/服务绑定。
- [ ] 显式选择时，同一组记录使用指定模型及其解析服务。
- [ ] 在 turn 准备后修改桌面默认、远程模型设置或 thinking 设置，不改变该 turn 的有效配置。
- [ ] 所有生产 IM Agent Loop 调用都提供完整冻结 accepted turn；缺失 accepted turn 或冻结配置必需字段时，在 provider 请求前明确失败，不从全局默认模型、会话或回调补值。
- [ ] 审批恢复沿用原 turn 的模型、服务和 effort，不重新解析为新设置。
- [ ] 冻结 M/S1 后分别模拟 S1 缺少凭据、删除、停用或取消对 M 的支持，且 S2 仍支持 M；初次执行与审批恢复均不请求 S2、不改写 accepted turn/会话绑定，并产生明确失败和修复提示。
- [ ] 冻结前存在多个可用服务时，可以按既有选择规则选出 S2 并将 M/S2 一起冻结；冻结后不再遍历或切换服务。
- [ ] Provider 返回额度耗尽或速率限制时，当前 turn 明确失败且错误可见；不触发 overflow 重试、不切换服务/模型。额度恢复后可由用户重试，新的 turn 按当时配置重新冻结。
- [ ] 支持 `low` 的模型下，execution config 请求/有效档位均为 `low`，最终 Invocation `profile.reasoning.effort` 为 `low`。
- [ ] 对显式排除 `low` 的模型，冻结配置保留请求值并带上解析后的有效档位；最终 Invocation effort 与有效档位相同，降级字段可观测。
- [ ] 模型条目明确不支持 thinking 时，requested effort 保留、effective effort 为 `off`，最终 Invocation 为 `off`，并可观测到降级记录。
- [ ] 上游服务拒绝 `output_config.effort` 时沿用现有 provider fail-soft 重试；这不改变该 turn 已冻结的 Invocation profile。
- [ ] 模型目录 ID（如纯数字 ID）不会直接作为 provider 模型名或路由基线 ID；未知/不可用绑定在发出 provider 请求前失败或按规定回退。
- [ ] 微信与飞书公共设置、解析和恢复行为一致。
