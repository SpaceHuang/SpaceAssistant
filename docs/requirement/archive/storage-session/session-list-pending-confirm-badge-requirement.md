## 1. 需求概述

当前只要任一会话存在待用户确认的工具调用，会话列表搜索框下方就会额外插入一张“待确认”卡片。卡片空间有限，通常只能显示截断后的会话名与工具摘要；当多个会话同时等待确认时，卡片会进一步占用会话列表空间，用户还需要在卡片和会话列表之间建立对应关系。

本需求将待确认提示从独立卡片改为会话行内状态：对存在待确认操作的会话，在其会话列表项上展示醒目的“待确认”标签。用户无需阅读额外汇总区，即可直接识别正在等待输入的会话。

原会话列表上方的待确认卡片（`PendingConfirmBanner`）移除；聊天区内真正承载批准、拒绝和风险信息的确认卡片保持不变。

## 2. 问题与机会

### 2.1 当前问题

| 问题 | 用户影响 |
|---|---|
| 独立卡片宽度和高度有限，信息容易截断 | 用户无法快速判断具体是哪个会话在等待确认 |
| 提示卡片与目标会话行分离 | 用户需要二次匹配会话名，再进入目标会话 |
| 多个会话同时待确认时，卡片列表继续挤占侧栏 | 会话列表可视区域缩小，信息密度和层级变差 |
| 同一会话存在多个待确认项时，卡片可能重复展示该会话 | 重复信息增加噪音，却没有提升定位效率 |
| 搜索和日期分组改变会话位置后，顶部卡片与列表关系更弱 | 用户难以形成稳定的视觉映射 |

### 2.2 设计机会

“待确认”是会话级的即时状态，而不是一组需要在侧栏单独阅读的内容。把状态贴近会话标题展示，可以用更少空间建立更明确的状态归属，并让多个待确认会话自然分布在原有列表结构中。

## 3. 目标与非目标

### 3.1 目标

| 编号 | 目标 |
|---|---|
| G1 | 任一会话存在可操作的工具确认请求时，在该会话行显示“待确认”标签 |
| G2 | 多个会话同时待确认时，每个对应会话都独立显示标签 |
| G3 | 同一会话存在多个待确认项时仍只显示一个标签，避免重复堆叠 |
| G4 | 待确认状态产生和解除后，标签即时出现或消失，无需刷新列表 |
| G5 | 移除搜索框下方原有的待确认卡片，释放会话列表空间 |
| G6 | 保持用户进入目标会话并处理聊天区确认卡片的操作路径清晰、可访问 |

### 3.2 非目标

| 编号 | 非目标 | 说明 |
|---|---|---|
| NG1 | 不在会话列表标签上直接批准或拒绝 | 风险详情和决策操作仍只在聊天区确认卡片中提供 |
| NG2 | 不修改确认安全策略、信任规则或超时时间 | 本需求只调整状态入口的展示方式 |
| NG3 | 不移除桌面浮动通知 | 主窗口隐藏、最小化或失焦时，仍需用桌面通知提醒用户 |
| NG4 | 不改变会话排序 | 待确认会话不自动置顶，避免列表在用户操作时跳动 |
| NG5 | 本期不把 Plan `awaiting_approval` 纳入该标签 | P0 仅替换现有 `PendingConfirmBanner` 所展示的工具确认；Plan 审批可后续统一为通用“需要操作”状态 |
| NG6 | 不在标签中展示工具名称、命令摘要或风险等级 | 完整信息由聊天区确认卡片承载，列表只负责识别状态归属 |

## 4. 用户故事

### US-01：识别单个待确认会话

作为同时保留多个会话的用户，当其中一个会话等待我确认工具调用时，我希望该会话行直接显示“待确认”，以便不经过额外提示卡片就能找到它。

### US-02：识别多个待确认会话

作为并行运行多个会话的用户，当多个会话都等待确认时，我希望每个对应会话都显示标签，以便一眼看到待处理事项分布在哪些会话。

### US-03：进入并处理确认

作为看到“待确认”标签的用户，当我点击该会话行时，我希望进入该会话并能快速看到尚未处理的确认卡片，以便完成批准或拒绝。

### US-04：处理后恢复普通状态

作为已完成确认的用户，当该会话不再有任何待确认项时，我希望标签立即消失，以便列表准确反映当前状态。

## 5. 核心规则

### 5.1 待确认状态定义

会话满足以下全部条件时显示标签：

1. `pendingConfirmStore` 中至少存在一项属于该 `sessionId` 的确认请求；
2. 该确认请求所属 `requestId` 仍处于当前运行请求集合中；
3. 该会话仍存在于当前会话列表中；
4. 确认请求尚未被批准、拒绝、取消或超时清除。

上述规则与现有 `useActionablePendingConfirms` 的“可操作待确认项”口径保持一致，避免已失效或孤立的数据残留为假标签。

### 5.2 聚合规则

- 展示维度为会话，不是待确认项。
- 同一会话无论有 1 项还是多项待确认，只展示一个“待确认”标签。
- 不展示数量角标。数量不会改变用户的首要动作：先进入会话，再逐项处理确认卡片。
- 多个会话待确认时，各会话行分别展示标签，不再提供顶部总数汇总。
- 若后续需要暴露数量，应通过标签无障碍名称或 tooltip 扩展，不在 P0 中预留不可见占位。

### 5.3 状态解除规则

以下任一事件导致某项确认不再可操作时，应重新计算对应会话状态：

- 用户批准；
- 用户拒绝；
- 请求超时；
- 会话运行被停止或取消；
- 工具返回结果并清除待确认记录；
- 会话被删除；
- 应用恢复状态后发现该 `requestId` 已不再运行。

仅当该会话的所有可操作待确认项均被清除后，标签才消失。

## 6. 界面与交互设计

### 6.1 会话行布局

标签放在会话标题右侧、行操作按钮左侧，属于会话标题区的一部分：

```text
┌──────────────────────────────────────────┐
│ ◉ 调研浏览器自动化方案   [待确认]  ■  ⋯ │
└──────────────────────────────────────────┘
```

布局优先级从高到低：会话图标、会话标题、待确认标签、运行停止按钮、删除/更多操作。空间不足时：

1. 会话标题先收缩并显示省略号；
2. “待确认”标签必须完整保留，不得压缩为“待…”或被裁切；
3. 既有行操作按钮保持可操作尺寸，不与标签重叠；
4. 不因标签出现而改变会话行高度。

### 6.2 标签视觉

- 文案固定为“待确认”（英文为“Confirm”）。
- 使用紧凑 pill 标签，建议高度 20px、水平内边距 6px、圆角使用现有 pill token。
- 使用 warning 语义色的浅色背景、深色文字和细边框，确保浅色主题下文字对比度达到 WCAG 2.1 AA。
- 不使用大面积实心橙；品牌橙保留给主操作，待确认属于需要注意但尚未失败的状态。
- 可在文字左侧使用 6px 状态圆点或小型警示图标，但图标不得替代文字。
- 不使用持续闪烁、呼吸或位移动画。标签新增/移除最多使用 150–200ms 的淡入淡出；开启 `prefers-reduced-motion` 时取消动画。
- 选中、悬停、运行中、删除中等会话行状态下，标签仍须清晰可辨。

### 6.3 点击行为

- 整个会话选择按钮仍是主要点击区域，标签不新增独立批准、拒绝操作。
- 点击带标签的会话行：
  1. 沿用现有工作目录同步与会话切换逻辑；
  2. 切换到对应会话；
  3. 若该会话存在待确认项，将焦点定位到最早产生且仍可操作的确认卡片；
  4. 若定位期间该项已被其他入口处理，则停留在会话中，不报错，并尝试定位下一项。
- 当前会话已经选中时再次点击，若存在待确认项，也应执行定位，不应因会话未变化而忽略。
- 标签本身不提供 hover 弹层，避免重复呈现会话名或工具摘要。

### 6.4 多项确认的定位顺序

同一会话存在多个待确认项时，默认定位到 `createdAt` 最早的可操作项，帮助用户按产生顺序处理，避免后发请求遮蔽先发请求。处理完成后标签继续保留，直到该会话全部待确认项清空。

### 6.5 搜索、分组与空状态

- 标签跟随会话行参与日期分组，不创建单独分组。
- 搜索结果只展示标题命中的会话；“待确认”状态本身不作为搜索关键词。
- 若待确认会话被当前搜索条件过滤掉，不在搜索框上方恢复旧卡片，也不展示额外汇总提醒。
- 清空搜索后，对应会话标签应立即可见。
- 会话列表为空时不展示任何待确认标签；孤立待确认数据按不可操作项处理。

### 6.6 与运行状态并存

- 会话可以同时为“运行中”和“待确认”；两者不是互斥状态。
- 运行图标/停止按钮沿用现状，“待确认”用文字标签补充，不替换停止能力。
- 当会话进入待确认阶段但运行元数据仍有效时，必须同时满足可停止与可识别待确认两种需求。

### 6.7 重命名与删除

- 会话标题进入行内编辑时，可暂时隐藏标签，为输入框让出空间；退出编辑后按实时状态恢复。
- 删除中的会话行沿用禁用态；标签可保留到删除完成，删除成功后随会话行一起消失。
- 删除失败时，会话行和待确认标签按当前真实状态恢复。

## 7. 可访问性与多语言

### 7.1 屏幕阅读器

- 标签不得只依赖颜色传达状态，必须包含可读文字。
- 会话选择按钮的可访问名称应包含状态，例如：“调研浏览器自动化方案，待确认”。
- 同一会话有多个待确认项时，可访问名称可补充数量，例如：“调研浏览器自动化方案，2 项待确认”；可视标签仍显示“待确认”。
- 状态从无到有时使用克制的 `aria-live="polite"` 通知，例如：“会话‘调研浏览器自动化方案’需要确认”；不要因每次 Store 快照更新重复播报。

### 7.2 键盘

- 标签不得引入额外 Tab 停靠点。
- 会话行继续使用现有键盘焦点和激活行为。
- 焦点样式不能被标签背景遮挡或截断。

### 7.3 i18n 文案

建议新增或调整以下资源：

| Key | zh-CN | en-US |
|---|---|---|
| `session.pendingConfirm.badge` | 待确认 | Confirm |
| `session.pendingConfirm.itemAria` | {{name}}，待确认 | {{name}}, confirmation needed |
| `session.pendingConfirm.itemCountAria` | {{name}}，{{count}} 项待确认 | {{name}}, {{count}} confirmations needed |
| `session.pendingConfirm.announced` | 会话“{{name}}”需要确认 | Session “{{name}}” needs confirmation |

旧资源 `session.pendingConfirm.count` 和 `session.pendingConfirm.aria` 在移除顶部卡片且无其他引用后删除；不得遗留无效文案或类型声明。

## 8. 数据与实现约束

### 8.1 推荐数据派生

不新增持久化字段，不把待确认状态写入 Session 数据库。标签是运行期状态，应从现有可操作待确认项派生：

```typescript
type PendingConfirmBySession = Map<
  string,
  {
    count: number
    firstToolUseId: string
    firstCreatedAt: number
  }
>
```

派生流程：

1. 通过现有口径过滤出 `actionablePendingConfirms`；
2. 按 `sessionId` 聚合；
3. 记录数量及最早待确认项，用于无障碍名称和点击定位；
4. 会话列表渲染时通过 `sessionId` O(1) 查询状态，避免每一行重复扫描全部确认项。

### 8.2 组件调整建议

- 从 `SessionListPane` 移除 `PendingConfirmBanner`。
- 删除无其他用途的 `PendingConfirmBanner.tsx` 及 `.pending-confirm-banner*` 样式。
- 把待确认 Store 的订阅与可操作项过滤提升到会话列表层，或封装为返回按会话聚合结果的 hook。
- 会话项根据聚合结果渲染标签，并把最早 `toolUseId` 传入现有 `setConfirmFocusToolUseId` 定位链路。
- 保持 `pendingConfirmStore.init()` 只初始化一次，避免列表重渲染时重复注册 IPC 监听。
- 不改变 `pendingConfirmStore` 与主进程工具确认协议，不新增 IPC。

### 8.3 与桌面浮动通知的关系

桌面浮动通知和本需求服务不同场景：

- 主窗口可见时：用户通过会话行标签识别待确认会话；
- 主窗口隐藏、最小化或失焦时：桌面浮动通知继续负责唤回用户；
- 用户从浮动通知回到主界面并定位会话后，可在会话行看到同一状态标签；
- 移除的是主窗口会话列表顶部卡片，不是独立桌面浮动通知窗口。

## 9. 异常与边界场景

| 场景 | 预期行为 |
|---|---|
| 单个会话、单个待确认项 | 该会话显示一个“待确认”标签 |
| 单个会话、多个待确认项 | 仍只显示一个标签；点击定位最早项；处理部分项目后标签保留 |
| 多个会话分别待确认 | 每个对应会话都显示标签，无顶部汇总卡片 |
| 待确认会话不是当前会话 | 标签可见；点击后切换并定位确认卡片 |
| 当前会话出现待确认 | 当前选中行即时显示标签，不自动滚动侧栏或抢夺焦点 |
| 请求在用户点击前被其他入口处理 | 进入会话但不报错；若还有其他项则定位下一项，否则标签消失 |
| 待确认会话被搜索过滤 | 不展示旧卡片或额外提示；清空搜索后恢复可见 |
| 会话名称很长 | 标题省略，标签完整保留；标题原有 tooltip 继续可用 |
| 会话正在运行 | 运行态与待确认标签同时展示，停止操作保持可用 |
| 会话被删除或运行被停止 | 清除/过滤失效项，标签随真实状态消失 |
| 应用重启 | 不凭 Session 持久化状态显示标签；仅在恢复出真实可操作请求时显示 |

## 10. 验收标准

### 10.1 功能验收

- [ ] 不存在可操作待确认项时，所有会话行均无“待确认”标签。
- [ ] 某会话产生第一项可操作确认请求后，该会话行即时出现“待确认”标签。
- [ ] 同一会话产生多项待确认请求时，只显示一个标签。
- [ ] 多个会话产生待确认请求时，每个对应会话行都显示标签。
- [ ] 处理同一会话的部分待确认项后，只要仍有剩余项，标签继续显示。
- [ ] 最后一项被批准、拒绝、取消或超时后，标签即时消失。
- [ ] 点击带标签的会话行可切换到该会话，并定位到最早的可操作确认卡片。
- [ ] 当前会话已选中时点击其行，仍可定位待确认卡片。
- [ ] 原搜索框下方待确认卡片不再渲染，也不再占据布局空间。
- [ ] 桌面浮动通知行为不受影响。
- [ ] 会话排序、日期分组、搜索、重命名、删除和停止运行行为无回归。

### 10.2 视觉验收

- [ ] “待确认”文字在常规侧栏宽度下完整显示，不与标题或操作按钮重叠。
- [ ] 标签出现前后会话行高度不变，列表无明显跳动。
- [ ] 长标题优先省略，标签和行操作按钮保持可见。
- [ ] 默认、hover、active、focus、running、deleting 状态下标签均清晰可辨。
- [ ] 标签不使用持续动画，并正确响应 `prefers-reduced-motion`。
- [ ] 标签文字与背景对比度满足 WCAG 2.1 AA。

### 10.3 自动化测试建议

- [ ] 聚合函数：按 `sessionId` 去重、计数并选择最早待确认项。
- [ ] 过滤逻辑：不存在会话、`requestId` 不活跃、已清除的项不生成标签。
- [ ] 组件测试：单会话、多会话、同会话多项、状态清除后的渲染。
- [ ] 交互测试：点击待确认会话调用 `setSession` 和 `setConfirmFocusToolUseId`。
- [ ] 回归测试：无待确认项时，列表 DOM 与原普通会话行行为一致。
- [ ] i18n 类型检查：新增资源完整，旧 Banner 专用资源无残留引用。
