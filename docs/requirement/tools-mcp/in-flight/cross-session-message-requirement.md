# 跨会话消息投递需求说明

> 状态：需求草案，待评审  
> 归属：tools-mcp / 自省工具（`action.session.*`）  
> 范围：允许当前会话中的 Agent 向另一个明确指定的桌面用户会话投递一条消息；目标会话忙时排队，空闲时唤醒执行。  
> 本文定义用户可见行为与验收边界，不规定内部实现。

## 第 0 层：决策层【人必读】

**一句话：** Agent 可以把一条明确内容交给另一个会话；接收会话正在执行时，消息等待其当前执行结束后按队列顺序处理；接收会话空闲时，消息到达后会启动一次处理。

**价值与不做的后果：** 多会话协作目前可以通过读取会话消息了解对方产出，但缺少把审核请求交给指定会话并让它继续工作的闭环。Agent 因而需要用户手动切换会话、复制内容并启动审核，或通过轮询和额外触发器拼接流程。增加投递能力后，一个会话可邀请另一个会话审核自己的结果，并结合既有触发器等待审核会话完成。价值落在协作效率、减少重复操作与减少轮询消耗；不做则跨会话协作仍需人工搬运消息和启动接收会话。

**用户经历：** 发起会话调用自省工具发送内容，得到“已排队/已唤醒”的明确回执；接收会话的消息作为普通会话输入可在历史中看到并按正常规则处理。发送工具调用本身不等待接收会话完成审核。后续等待结果由发起 Agent 使用现有触发器能力完成。

**本轮已明确的行为取值：** 首版仅支持桌面用户会话作为接收方；不支持 remote（飞书/微信）、automation、internal 或 hidden 会话。运行中只追加桌面输入队列，不打断当前执行；空闲时接纳后经桌面会话入口唤醒。该功能不触发渠道外发。工具不承诺审核一定通过或接收 Agent 一定给出结果，只承诺消息被正确接纳并获得执行机会；若输入终止且未创建 Turn，已登记等待方会收到“未执行终态”，不能被表示成审核完成。

**已定行为与剩余评审决策：**

| ID | 决策项 | 选项与影响 |
|---|---|---|
| D-01 | 目标会话范围 | 首版已收敛为桌面用户会话；排除 remote（飞书/微信）、automation、internal、hidden。此范围避免跨渠道消费排序与意外外发，未来扩大范围需单独评审渠道行为。 |
| D-02 | 发送回执承诺 | A. 返回已持久接纳及排队/已请求唤醒状态；B. 等待目标会话真正开始执行后才返回。B 会令发送调用受目标会话负载影响。建议本期选 A。 |
| D-03 | 发送者身份 | 发送来源固定由宿主从当前调用上下文注入，至少可识别来源为 Agent、发送会话 ID 和请求 ID；工具参数不可伪造或覆盖。消息不能被接收端解释为用户本人发言、用户授权或用户批准。 |

## 第 1 层：需求概要【人机共读】

### 1. 目标

1. 在现有自省工具集合中增加跨会话发送能力；通过既有工具发现与调用机制使用，不新增独立顶层工具族。首版接收目标限定为桌面 user-visible 会话。
2. 发送者明确指定目标会话和消息正文；系统验证目标为桌面用户会话且可用。remote、automation、internal、hidden 目标明确拒绝。
3. 消息进入目标会话的持久输入队列，保持与其他已接纳输入一致的先后顺序和去重语义。
4. 目标会话正在运行时不抢占、不取消、不并发启动第二个执行循环；新消息留在队列，等待当前执行结束后依序处理。
5. 目标会话空闲时，在消息接纳后触发既有会话唤醒/启动路径，使消息获得执行机会。
6. 工具返回可区分的接纳结果；目标会话不存在、不可访问、删除中或消息无法接纳时明确失败，不伪报成功。
7. 发送方拿到稳定的队列请求 ID 后，可登记等待该条输入对应的处理 Turn 结束；不要求发送方在消息排队时取得尚不存在的 Turn ID。接收会话的输出再由发送方通过现有会话读取能力检查。
8. 发送方可撤回自己已发送、但接收会话尚未领取处理的消息；撤回与领取并发时只有一个结果获胜，并向发送方准确报告最终状态。

### 2. 用户故事

- 作为正在产出内容的 Agent，我希望把产出与审查要求发送给审查会话，让审查会话自行处理并给出意见。
- 作为接收会话的 Agent，我希望新请求进入我的普通输入队列，当前工作结束后依序处理，避免当前任务被打断或输入丢失。
- 作为用户，我希望发送会话能区分“消息已接纳”和“接收会话已完成审核”，避免把排队误认为审核完成。

### 3. 范围清单

**本期做**

- 一个跨会话发送能力，纳入现有 `action.session.*` 自省能力集合及 `toolkit_find/toolkit_call` 使用路径。
- 明确目标会话、正文与稳定幂等 requestId；发送者身份取自当前可信调用上下文。
- 接收会话的模型输入和可回读历史均能识别该消息来自另一个 Agent/发送会话；该来源信息由宿主绑定，正文中的自称不能覆盖它，也不能构成用户批准。
- 运行中接收会话：只排队；当前 Turn 完成后由原有队列顺序消费。
- 空闲接收会话：消息持久接纳后通知现有运行时启动/唤醒入口；避免依赖轮询。
- 可判定回执：接纳状态、目标会话标识、消息/请求标识；如目标正在运行则说明等待队列，如已请求唤醒则说明等待执行。
- 通过同一自省能力集合提供撤回操作；仅原发送者可撤回，且仅在消息仍处于未领取队列态时成功。
- 撤回成功后，消息不再进入接收会话的模型输入；若已领取、已开始处理或已结束，则返回不可撤回及当前可判定状态，不尝试擦除已发生的模型处理或历史事实。
- 与现有工具审计和会话权限边界一致。

**明确不做**

- 不打断、暂停、取消或抢占接收会话当前模型请求、工具执行或用户确认。
- 不等待目标会话完成处理；不把工具成功回执解释成对方已读、已运行或已完成。
- 不支持 remote（飞书/微信）、automation、internal 或 hidden 接收会话；不向任何 IM 平台发送消息，也不把审核内容合并进平台聊天上下文。
- 不新增独立等待工具族；但需扩展在途 runtime trigger 的事件关联能力，使其可等待一个已接纳队列请求对应的 Turn 完成。
- 不绕过工具策略、会话可见性/授权、队列额度、消息体限制或既有安全审计。
- 不允许根据会话标题模糊匹配目标；必须传入准确会话标识。
- 不新增 UI、通知面板、会话间专用协议或第二套持久化消息存储。

**未来再引入**

- 回复关联/线程化、收件确认、多个接收者、消息模板与附件转发。
- 面向用户的跨会话投递审计与管理界面。
- 按会话配置的自动接受/拒绝策略（若未来需要，单独评审授权与安全边界）。

## 第 2 层：行为规格【人机共读】

### 4. 术语

| 术语 | 定义 |
|---|---|
| 发送会话 | 当前发起自省工具调用的桌面用户会话；身份由运行时上下文提供 |
| 接收会话 | 工具参数中明确指定的目标会话 |
| 消息接纳 | 消息已被持久写入接收会话输入队列，获得稳定请求/消息标识 |
| 排队 | 消息已接纳，但接收会话正有执行占用或前面存在输入，尚未被领取执行 |
| 唤醒 | 对空闲接收会话发出启动/调度请求；不等价于模型已经开始或完成处理 |
| 队列请求 ID | 消息接纳时返回的稳定请求标识；它先于消息领取和 Turn 创建，可用于将等待登记绑定到准确的一条输入 |
| 撤回 | 在消息仍未领取处理时，原发送会话将该输入从可执行队列中取消；不代表删除审计事实或撤销已发生的处理 |

### 5. 行为规则

| ID | 规则 |
|---|---|
| BR-01 | 工具仅允许由桌面 user-visible 发送会话调用，且必须接收精确的桌面 user-visible 接收会话 ID 与非空消息正文。remote、automation、internal、hidden 来源或目标均拒绝。无法从可信上下文取得发送会话身份时失败；Agent 不得通过参数声明或覆盖发送者身份。 |
| BR-02 | 目标会话须存在、未删除并符合 D-01 确定的可访问范围。会话不存在与不可访问对外可返回统一的不可用错误，避免泄露隐藏会话存在性。 |
| BR-03 | 正文进入接收会话的桌面输入队列并成为该会话可见历史的一部分；模型输入和历史回读须保留可信来源语义（Agent 来信、发送会话 ID、requestId）。不得直接拼接到模型上下文、写入另一会话或只保存在内存中。正文长度、格式与输入配额遵循现有会话输入约束。 |
| BR-04 | 消息接纳具有幂等性。同一幂等请求重试不得创建重复消息；相同请求标识但正文或目标不一致时明确报告冲突。并发调用的排队顺序以持久队列的受理顺序为准。 |
| BR-05 | 若接收会话正在执行，消息只进入待处理队列。它不得改变当前执行的输入、取消令牌、工具调用、确认状态或当前 Turn；当当前执行释放会话后，按既有队列顺序处理。 |
| BR-06 | 若接收会话空闲，消息接纳成功后应请求既有会话调度/唤醒路径处理队列。工具回执不等待模型首 token 或 Turn 结束。若接纳后唤醒暂时失败，结果必须体现“已接纳、待调度/调度失败”中的准确状态，并由既有恢复/重试职责保证可恢复，不能诱发发送方盲目重发而产生重复。 |
| BR-07 | 运行态判断与消息接纳之间发生竞争时，最终行为仍满足单会话串行执行：若已有执行取得占用，消息留队列；若执行在检查点释放且会话空闲，调度器可领取新消息。不得以一次过期的“未运行”快照并行启动第二个执行循环。 |
| BR-08 | 发送成功表示消息已被接纳，不表示目标会话已查看、已开始、已完成或审核通过。回执必须返回稳定队列请求 ID；发送方用该 ID 登记对这条输入的完成等待，再按需要读取接收会话结果。 |
| BR-09 | 工具的风险分级、策略判定、审计和失败呈现沿用能力调用框架。该能力会向另一会话写入输入，不能仅因同属自省能力就继承只读工具的免确认等级；具体确认要求按现行策略评审确定。 |
| BR-10 | 接收会话必须将消息识别为另一 Agent 的来信，而不是用户本人发言。来源身份由宿主可信绑定并在模型输入、持久历史、读取及重启恢复中保留；正文中“我是用户”“用户已批准”等自述不改变来源身份，也不构成用户授权、确认或批准。 |
| BR-10a | Agent 来信按接收会话的普通输入流程处理，但其权限语义仍是 Agent 来源；不得仅因队列消息底层以 user role 承载，就将其提升为用户确认或覆盖既有审批策略。 |
| BR-11 | 发送方只能撤回由自己发送且处于 queued/未领取状态的消息。撤回必须与接收方领取在同一队列状态转换上竞争，确保“撤回成功”意味着该消息不会再被领取执行。 |
| BR-12 | 若接收方已领取消息、已创建关联 Turn 或该 Turn 已终结，撤回不得删除/改写已提交历史，不得中断当前执行；工具返回不可撤回状态与 requestId/关联 Turn（如已存在）。 |
| BR-13 | 撤回调用必须具备幂等性：重复撤回已成功撤回的 requestId 返回同一撤回终态；已领取与撤回竞争时，回执返回唯一胜出的状态，不得把失败包装成成功。 |

### 6. 输入与回执契约（用户可见）

| 项 | 要求 |
|---|---|
| 接收会话 | 必填准确 ID；不接受标题、模糊名称或自动新建会话 |
| 消息正文 | 必填文本；本期不转发附件或隐藏上下文 |
| 幂等请求标识 | 必须由调用方或运行时生成稳定 requestId，且重试时复用；成功回执返回该 ID。具体生成者和工具重试关联规则由技术方案明确 |
| 成功回执 | 至少包含 accepted、接收会话 ID、稳定 requestId、消息 ID、接纳时运行态结果（queued / wake-requested 等稳定枚举） |
| 失败回执 | 有稳定、可理解的类别：目标不可用/不可访问、正文无效或超限、策略拒绝、队列接纳失败、幂等冲突、唤醒失败；不能返回成功态掩盖部分失败 |
| 撤回回执 | 至少包含 requestId、状态（revoked / already-revoked / already-claimed / completed / failed）及可用的关联 Turn ID；实际状态枚举由技术方案与队列合同统一 |
| 运行状态 | 只用于回执说明和决定是否需要唤醒；最终串行与消费资格由会话执行所有权/队列领取行为裁决 |
| 接收范围 | 首版仅桌面 user-visible 会话；remote（飞书/微信）、automation、internal、hidden 均拒绝 |

### 7. 状态与冲突裁决

发送请求依次经历：`未接纳 → 已接纳待执行 → 已领取处理 → Turn 终态`，或 `已接纳待执行 → 未执行终态`。未执行终态包括发送方撤回、其他授权取消、接收会话删除/不可用、启动前策略拒绝、唤醒/准备不可恢复失败。已接纳消息不得因工具调用返回、发送会话结束或发送会话删除而自动撤回。重试按幂等标识返回原接纳结果。

裁决顺序：

1. 策略拒绝、目标不合法或输入校验失败时，不写入队列，也不请求唤醒。
2. 队列写入未成功时，不得请求运行；对发送方返回失败。
3. 队列写入成功后，消息事实不能因单纯唤醒请求失败而报告为“未发送”；回执准确区分已接纳与调度状态。
4. 是否并发执行只由目标会话既有执行占用和队列领取规则裁决；运行态观测值不能授权并发执行。
5. 重复调用不得重复入队；不同请求按队列接纳顺序依次处理。
6. 对已按 requestId 登记的等待，任何未执行终态都必须结算一次并唤醒发送会话，载荷语义为“该输入未执行”及准确原因；不得伪报 `turn_completed` 或审核结果。若等待在输入终止后才登记，注册应基于持久终态立即返回/投递同一结算，不得等待一个永远不会创建的 Turn。

**等待结算矩阵：**“等待已登记”指发送方已成功建立以接收会话 + requestId 为键的一次性等待；“后来登记”包括输入已进入相应状态后才注册。

| 输入事实 | 等待先登记 | 输入事实先发生、等待后来登记 | 对发送方的业务含义 |
|---|---|---|---|
| 仍 queued，尚未领取 | 保持等待；不创建 Turn，也不误报开始 | 注册成功并继续等待 | 正在排队，尚无审核结论 |
| 已领取并关联 Turn | 绑定该准确 Turn，等待其终态 | 从持久 requestId→Turn 关联绑定并等待 | 审核处理中 |
| Turn 正常完成 | 关联该 Turn，结算一次 | 注册时立即结算/投递持久 Turn 终态 | 接收 Agent 本轮已结束；不等于审核通过，发送方需读取结果 |
| Turn failed/cancelled/timed-out 等非正常终态 | 关联该 Turn，结算一次并保留实际 outcome | 注册时立即结算/投递持久终态 | 本轮异常结束；不伪报审核成功 |
| 未创建 Turn 即被撤回或其他取消 | 立即结算一次“未执行” | 注册时立即返回/投递同一“未执行”事实 | 输入未执行，且不再等待 Turn |
| 接收会话删除/不可用、启动前策略拒绝、不可恢复准备/启动失败 | 立即结算一次“未执行”及稳定原因 | 注册时立即返回/投递同一终态 | 输入未执行；不能恢复为处理中 |
| 应用重启时仍 queued 或已领取 | 恢复等待与准确关联，不重复通知 | 后登记仍按当前持久状态处理 | 状态连续且最多结算一次 |

若 requestId 对应事实缺失、冲突或不能可靠恢复，等待必须以明确 `source-gap`/失败结果结算并通知发送方；不得继续无限等待，也不得猜测绑定到其他 Turn。

### 8. 场景与失败边界

| 场景 | 需求行为 |
|---|---|
| 目标会话正在生成回答 | 只接纳并排队；当前回答和工具流程继续，当前执行结束后才处理新消息 |
| 目标会话正在等待用户确认 | 消息留在队列中；不得替用户确认，也不得绕过当前确认状态 |
| 目标会话空闲 | 接纳后请求启动；不得要求发送方再次手动打开会话或轮询触发启动 |
| 两次发送与目标空闲转运行同时发生 | 队列顺序稳定；至多一个执行循环取得目标会话运行资格 |
| 接纳成功但唤醒入口暂时失败 | 不重复创建消息；回执表明消息已接纳及调度状态，后续由既有恢复机制重试或可观察地失败 |
| 发送工具超时后重试 | 相同幂等标识返回同一消息接纳结果；不得生成重复审核请求 |
| 接收会话在投递前被删除或不可见 | 统一返回目标不可用，不泄露隐藏会话细节，不创建队列消息 |
| 接收目标是 remote/飞书/微信、automation、internal 或 hidden 会话 | 拒绝发送；不创建队列消息、不启动会话、不向渠道外发 |
| 桌面目标有真实 IM 输入并存 | 首版 Agent 来信进入 desktop scope；只承诺在 desktop scope 内按持久接纳顺序处理，不承诺与 Feishu/WeChat scope 之间全序；Agent 来信不流入 IM inbox 或平台发送出口 |
| 接收端检查来信来源 | 模型上下文与历史回读表明这是来自发送会话的 Agent 来信；正文中伪称用户身份或授权不改变可信来源 |
| 消息超过既有限额 | 明确拒绝并返回上限原因；不得静默截断审核材料 |
| 接收会话收到多条消息 | 依持久队列顺序逐条处理；失败/取消语义沿用既有队列合同，不由本工具私自改写 |
| 接收 Agent 无响应或拒绝任务 | 发送方仍只能看到“已接纳/等待/状态”，不得假报审核结论；通过现有超时/触发器路径处理等待 |
| 撤回与领取同时发生 | 队列原子状态转换选出唯一胜者：撤回先成功则不创建 Turn；领取先成功则撤回返回已领取，且不打断接收会话 |
| 重复撤回 | 返回已撤回终态，不再次修改消息或生成额外事件 |
| 发送方不是原发送者 | 拒绝撤回，且不泄露或修改目标队列状态 |
| 输入未创建 Turn 即终止 | 若等待已登记，立即只结算一次“未执行”并唤醒发送方；若随后才登记，返回/投递同一持久未执行结果，不等待到期，不称为审核完成 |
| 接收会话删除、启动前拒绝或不可恢复启动失败 | 记录可回读的未执行终态；已登记或之后登记的 requestId 等待均收到“未执行”结果及原因 |
| Turn 已创建后失败、取消或超时 | 结算对应 Turn 的真实终态并通知发送方；不得包装为成功完成审核 |

### 9. 验收标准

| AC | 验收断言 |
|---|---|
| AC-01 | Agent 能经现有自省能力发现和调用发送能力，输入接收会话 ID 与正文并收到可判定回执。 |
| AC-02 | 发送会话身份和接收端 Agent 来源来自可信运行时上下文；模型提供伪造发送者字段不能改变来源或审计归属。 |
| AC-03 | 仅桌面 user-visible 发送会话可调用，且仅桌面 user-visible 接收会话可用；remote/IM、automation、internal、hidden 来源或目标均不创建消息、不唤醒、不触发渠道外发，并返回统一不可用/不支持结果。 |
| AC-04 | 有效正文接纳后出现在准确接收会话的输入与历史中，发送会话自身历史不被混写；接收模型和历史读取能区分 Agent 来信，正文伪称用户身份/批准不改变来源或授权语义。 |
| AC-05 | 桌面目标会话忙时，消息排在同一 desktop scope 的现有待处理输入之后；当前 Turn、工具调用与确认流程不受打断。与 IM scope 不承诺跨 scope 全序，且 Agent 来信不会由 IM 消费者领取或向平台外发。 |
| AC-06 | 目标会话空闲时，接纳后触发既有调度路径并开始消费队列；发送工具无需等待目标 Turn 完成。 |
| AC-07 | 忙闲判断与运行资格竞争时，不会为同一会话同时启动两个执行循环；消息最终仍可被队列消费。 |
| AC-08 | 相同幂等请求重试只产生一条消息；幂等键重用但正文或目标变化时返回冲突。 |
| AC-09 | 队列接纳失败不会触发会话执行；接纳成功后的唤醒失败不会被错误报告为未接纳，也不会因重试重复入队。 |
| AC-10 | 发送回执提供可复用的队列 requestId；即使发送工具返回时消息尚在排队、没有 Turn ID，发送方仍能用该 requestId 登记准确等待。 |
| AC-11 | 读取/查询边界、策略审计和能力发现调用遵循既有自省工具框架；写操作风险等级按策略决定，不自动沿用只读免确认。 |
| AC-12 | 两条及以上跨会话消息按同一 desktop scope 的接纳顺序依次处理；不承诺与 Feishu/WeChat scope 的跨 scope 全序，单条失败不造成后续消息越序或重复处理。 |
| AC-13 | 发送方用接收会话 ID + requestId 登记完成等待时，若该输入仍排队，触发器保持等待并在输入被领取时关联新建 Turn；若已领取，则绑定当前关联 Turn；若对应 Turn 已完成，则立即结算/投递一次，不丢失快速完成事件。 |
| AC-14 | 按 requestId 的触发器恢复、取消、重复注册和并发竞争沿用既有触发器幂等及终态规则；不得绑定到同会话的其他消息/Turn，也不得因消息标题或相邻 Turn 推断关联。 |
| AC-15 | 原发送会话能撤回仍 queued/未领取的消息；成功后该消息不可被任何执行入口领取，重启恢复也不会重新执行。 |
| AC-16 | 撤回与领取并发时状态唯一：撤回获胜则无关联 Turn 且不执行；领取获胜则撤回返回 already-claimed/对应终态，不中断执行、不删除历史。 |
| AC-17 | 非原发送会话不能撤回；重复撤回返回稳定终态；已领取、已完成、失败或已取消输入均不会被报告为成功撤回。 |
| AC-18 | 桌面 user-visible、remote/IM、automation、internal、hidden 的目标矩阵结果唯一；remote 输入不会意外外发到原聊天或任何渠道。 |
| AC-19 | 队列消息在正常读取、模型上下文组装、应用重启后恢复时仍保留 Agent 来源；伪造正文不改变来源或审批含义。 |
| AC-20 | 输入撤回、其他取消、会话删除/不可用、启动前策略拒绝、不可恢复启动失败等未创建 Turn 的终止，无论等待先登记还是后登记，均结算为一次明确“未执行”通知；不永久等待、不伪报 Turn 完成。 |
| AC-21 | 已创建 Turn 的 completed/failed/cancelled/timed-out 等终态均准确关联并通知；失败或取消不伪报审核成功。 |

| 队列撤回与终态 | 会话存储已有 queued 输入取消/更新路径及按 scope 的接纳/领取回执 | 复用现有 desktop queue cancellation / receipt；按 requestId 留存来源 owner 和唯一终态，补齐 claim/revoke 竞争与触发器未执行结算所需的最小合同，不另建队列 |

现状核查边界：触发器分支已将触发器投递、队列来源隔离和接收会话启动接入共同 TurnRuntime，相关实现可作为本需求对照的既有模式。当前 `turn_completed` 注册必须提供活动 Turn ID，且注册时校验该 Turn 仍活动；普通队列请求在被领取后才绑定 Turn ID。分支计划记录 `3668a8f0` 的 `npm test`、`npm run build` 和主要边界门禁通过；但当前分支 HEAD 为 `918a12b4`，其后包含额外恢复/幂等修复提交，且工作树有未提交改动，因此该通过证据不代表当前 HEAD 已复验，更不代表功能已经发布。本需求以用户确认的时间顺序为前提：触发器分支须先完成当前版本验证并在本次迭代开始前发布；触发器按队列请求 ID 等待属于本需求对现有触发器的增量改进，须在技术方案中复用已发布触发器服务、存储和投递链路。桌面空闲会话的队列接纳/唤醒仍须沿已发布实现与当前共同启动入口闭合，不得把触发器的事件标记当成普通文本消息，也不得新建平行队列或启动框架。

## 附录：关键边界

- 本需求承诺的是**消息接纳、忙时有序排队、闲时请求启动**，不承诺自动审核质量或审核必然完成。
- 任何唤醒入口都必须遵守单会话串行执行；“检测到空闲”本身不是并发运行许可。
- 发送消息是跨会话写入行为，必须在工具策略层作为写操作审查与审计。
