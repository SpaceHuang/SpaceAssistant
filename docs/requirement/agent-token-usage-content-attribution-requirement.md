## 1. 概述

### 1.1 背景

上游需求 `agent-token-usage-analytics-requirement.md` 已经回答了一类问题：**「我用了多少 token、什么时候用的、哪个会话/模型用的」**——它以时间、会话、模型、APP 版本四个维度做汇总，落点是「感知成本、复盘使用习惯」。

但它在**上游 §10.1** 明确把两项列为长期非目标：

- ❌ 按工具名细分的调用统计与失败率
- ❌ 费用 / 金额估算

于是有一类问题**当前无人回答**：

- 我这次会话的 token，**花在什么内容上**？
- 那 71 个工具声明，每轮都注入，**值不值**？
- 上下文从 1.7 万涨到 33.8 万，**是谁撑大的**？
- 我的 thinking 和正文各占多少？

这类问题的共同点是：**切分维度不是「时间/实体」，而是「内容来源」**。上游文档的四个维度（日期/会话/模型/版本）**切不出这一类结论**——因为同一时刻、同一会话、同一模型的消耗里，system 样板、工具声明、用户消息、工具返回、thinking 是混在一起的。

### 1.2 目标

| 编号 | 目标 |
|------|------|
| AG1 | 把一次请求的输入侧按**内容来源**拆开：system 样板 / 工具声明 / 消息体（再细分为用户消息、历史回复、工具返回、多模态） |
| AG2 | 把输出侧按**生成类型**拆开：thinking / 可见正文 / 工具调用参数 |
| AG3 | 区分**固定成本**（每轮恒定注入）与**增量成本**（随对话增长），使「优化重心在哪一侧」可判定 |
| AG4 | 每个指标都能对应一个**可行动作**（如「未使用工具常驻成本」→ 按需挂载），避免只给一堆无法决策的数字 |
| AG5 | 所有估算值标注估算口径与版本，与协议精确值（三档 + output）分列，**两类数字不混算** |

### 1.3 范围

| 类别 | 说明 |
|------|------|
| **新增** | 输入侧内容来源的归因口径与报表；输出侧类型拆分；固定/增量分离；落盘的 messages 骨架；估算器的可归因升级 |
| **复用** | `surfaceSnapshot` 的三源拆分、`request_usage` 的三档与 output、`tool_call.args` / `tool_result`、`assistant_chunk` 的三类分片、上游文档的归一化口径与 `tool_result` 标注改动 |
| **不变** | 上游文档的两张统计表与其四维度视图、`ContextUsageRing` 单会话视图、现有 `SessionEvent` 结构与事件类型集合 |

### 1.4 一句话定位

> 上游文档回答「**用了多少**」，本需求回答「**花在什么上**」。前者是账本，后者是成本结构剖析。

## 2. 与上游文档的关系

### 2.1 正交而非包含

| | 上游文档 | 本需求 |
|---|---|---|
| 切分维度 | 时间 / 会话 / 模型 / 版本 | **内容来源**（system / tools / messages / output 类型） |
| 数据粒度 | Turn + Step（每次 LLM 调用一行） | **请求内部构成**（一次请求拆成若干来源块） |
| 精确性 | 全部来自协议回报值 | **精确层 + 估算层并存**（见 §4） |
| 典型问题 | 「上月共消耗多少」「哪个会话最耗」 | 「这 33.8 万里，工具返回占多少」 |
| 是否折算金额 | 不做 | **不做**（一致，见 §11.1 `AD5`） |

两者可以共用同一套存储与查询通道，但**指标定义不同、不能互相替代**。

### 2.2 继承的口径（不得另立一套）

以下口径**直接沿用上游文档，本需求不重新定义**：

| 项 | 上游出处 | 本需求的处理 |
|----|----------|--------------|
| `additive` / `subset` 语义归一化 | 上游 §2.2.1 | 直接引用；本需求的输入侧总量以此为基准 |
| `cache_creation` 作为兼容字段、恒为 0 | 上游 §2.2.2 + 上游 C1 | **一致**：保留字段、仅值 > 0 时展示、不作统计指标（见 §11.1 `AD1`） |
| 缓存命中率方案 B | 上游 §2.5 + C3 | 直接引用，不重复定义 |
| 工具调用三分类（成功/失败/未执行） | 上游 §2.4 + C10 | 直接引用；本需求**不做**失败率统计（见 §9） |
| 在 `tool_result` 上标注「未执行」 | 上游 §7.6 + C11 | 直接引用；本需求若需扩展该字段，**沿用同一形态**（加可选字段，不新增事件类型） |
| `source: 'api'` 恒成立 | 上游 §9.3 | 一致；本需求的估算值**不得**写入该字段（那是协议回报专用） |

### 2.3 需要修订上游文档的一处

上游 §10.1 列有「❌ **按工具名细分的调用统计与失败率**」。本需求要做「**按工具/来源的成本归因**」，与之存在字面交集，但**实质不同**：

| | 上游明确不做的 | 本需求要做的 |
|---|---|---|
| 对象 | 工具**调用行为**（次数、失败率） | 工具**相关 token 成本**（声明常驻、返回体量） |
| 判据 | 按 `tool_name` 分组计数 | 按成本构成归因 |
| 典型输出 | 「grep 失败率 3%」 | 「59 个 MCP 工具声明常驻 ≈14,591 tok/轮，零调用」 |

**建议修订**：把上游 §10.1 该条明确限定为「**按工具名的调用次数与失败率**（行为指标）」，并在其后补一句「工具相关的 token 成本归因见 `agent-token-usage-content-attribution-requirement.md`」。这样两条非目标/需求的边界不再含混。

> 该修订**需要上游文档负责人确认**，本需求不擅自改动对方文档（见 §11.1 `AD6`）。

## 3. 术语与口径继承

### 3.1 本需求新增术语

| 术语 | 定义 |
|------|------|
| **来源块（Source Block）** | 一次请求输入侧的一个可归因片段。本需求划分 5 类：system 样板、工具声明、消息体、多模态、其他 |
| **固定成本（Fixed Cost）** | 每轮请求恒定注入、不随对话增长的部分。实测 = `systemTokens + toolsTokens` |
| **增量成本（Incremental Cost）** | 随对话轮次增长的 `messageTokens` 部分 |
| **精确层** | 数据来自 provider 回报字段，非估算。本需求中指三档（input / cache_write / cache_read）与 output |
| **估算层** | 数据来自本地估算器，标注 `estimatorVersion`。本需求中指各来源块的 token 拆分 |
| **常驻成本（Standing Cost）** | 一个工具声明或 skill 条目在每一轮请求中固定占用的 token 量 |
| **命中率** | 沿用上游方案 B，不重新定义 |

### 3.2 标记约定

本文档所有数值均带来源标记，**禁止混用**：

| 标记 | 含义 | 可信度 |
|------|------|--------|
| 【精确】 | provider 协议回报值 | 权威，可作分母/锚点 |
| 【估算】 | 本地估算器输出，须标 `estimatorVersion` | 有系统性偏差，需归一化（见 §4.5） |
| 【派生】 | 由结构化落盘数据聚合/计数得出（如字符数、事件条数） | 准确，但**不是 token 数** |
| 【推断】 | 由前几类间接推算，附算式与前提 | 最低，须显式标注 |

> 纪律：**不得把【派生】【推断】的数值呈现为 token 数而不加标注**。上游文档在同类问题上已有先例（`cache_creation` 仅值 > 0 时展示，避免假阴性空列），本需求沿用该取向。

### 3.3 本文档的编号约定

> ⚠️ **本需求所有编号带文档命名空间前缀；上游编号一律不改。**

**为什么需要这层约定**：上游 `agent-token-usage-analytics-requirement.md` 已占用 `G / M / S / C / D / T / R / DIM` 等全部编号空间（其决策为 `C1`–`C17`、指标为 `M1`–`M7`、验收为 `T1`–`T16`、回归为 `R1`–`R6`）。本需求若对号入座必然撞号——而两份文档是**继承关系**，读者必然对照阅读。实测已出现真实混淆：本文档 §6.2 的指标 `C1`（工具返回体量排行）与上游决策 `C1`（`cache_creation` 定位）**同为 `C1`、含义无关**。

| 类别 | 本需求前缀 | 取值 | 与上游的关系 |
|------|-----------|------|--------------|
| 目标 | **`AG`** | `AG1`–`AG5` | 上游为 `G1`–`G5`（撞） |
| 指标 | **`SRC-`** | `SRC-A1`…`SRC-D4` | 上游为 `M1`–`M7`；本需求保留 `A/B/C/D` **分组语义**（`A` = 固定/增量、`B` = 工具/skill、`C` = 工具返回/消息体、`D` = 输出侧与精确层） |
| 功能验收 | **`AT`** | `AT1`–`AT19` | 上游为 `T1`–`T16`（撞） |
| 回归验证 | **`AR`** | `AR1`–`AR7` | 上游为 `R1`–`R6`（撞） |
| 决策 | **`AD`** | `AD1`–`AD24` | 上游决策为 `C1`–`C17`（撞）；且原 `D` 前缀与本需求指标 `D` 组自撞 |
| 待确认 | `O` | **无**（`O1`–`O10` 全部结清，去向见 §11.2） | 上游无 `O` 编号，保留字母备用 |
| 不变量 | `I` | `I1`–`I7` | 上游无 `I` 编号，**无冲突，保留字母** |

**两条纪律**：

1. **引用上游编号时必须显式带「上游」限定**（如「上游 C11」「上游 §7.6」），不得裸写——否则同一个 `C` 前缀会指向两套体系；
2. **本约定只约束本文档。** 上游文档的编号保持原样，本需求不得改动（用户 2026-09-29 明确要求）。

> ⚠️ **维护纪律**：本表是编号的**单一真相源**。**每次新增 `AT` / `AD` / `O` / `I` 编号时，必须同批更新本表的上界** —— 约定表与正文不一致，会让实施与测试引用错号。

## 4. 数据可得性基线（本需求核心）

> 本章是整个需求的**可行性依据**。结论一句话：**位置原理上全都可区分，用量原理上几乎全都不可精确读取**——所以按内容来源的统计只能建立在估算之上，而估算的输入现在还缺一块。

### 4.1 三层落差

「能不能区分」这个问题必须分三层回答，因为三层的答案不同：

| 层 | 能力 | 结论 |
|----|------|------|
| **协议层**（Anthropic Messages API） | 请求结构确定且封闭；usage 只回报 5 个标量 | 位置全可区分；**用量只给混合值** |
| **传输层**（本产品的 wire 格式） | 实测 `provider: "anthropic"`、`serializationVersion: "anthropic-wire-v1"`；请求由本产品自行拼装 | 位置**完全可控** |
| **落盘层**（`request_header` 事件） | 只写 `system` / `tools` / `surfaceSnapshot` / `cacheBreakpoints` / `messagePrefixStats` | **messages 侧结构未留档** |

**关键推论**：第三层是真正的瓶颈。协议可区分 ≠ 本地可统计——messages 内部的 role 与 block 类型**连原料都没有**，不是「分不清」，是「没存」。

### 4.2 协议层：位置可得，用量不可得

#### 4.2.1 位置：因请求由本产品构造，故 100% 可控

| 想区分的内容 | 协议中的位置载体 | 可区分 |
|---|---|---|
| system | 顶层独立字段（**不在 messages 里**，无 role） | ✅ |
| 工具声明 | 顶层 `tools` 数组 | ✅ |
| 用户消息 | `role: "user"` + `text` block | ✅ |
| 工具返回 | `role: "user"` + **`tool_result` block** | ✅（block 级） |
| thinking | `role: "assistant"` + `thinking` block | ✅ |
| assistant 正文 | `role: "assistant"` + `text` block | ✅ |
| 工具调用参数 | `role: "assistant"` + `tool_use` block | ✅ |
| 多模态 | `image` / `document` block | ✅ |
| 缓存断点 | `cache_control` 标注的位置 | ✅ |

**三个必须点明的协议事实**（直接影响本需求的分类设计）：

1. **Anthropic 没有 `developer` role，也没有 `tool` role** —— 只有 `user` / `assistant` 两个取值。因此「规则 / skill 定义 / 工具声明」这类内容在协议里**没有原生位置**，被迫劈成两半：工具声明进 `tools`，规则与 skill 清单进 `system`。
2. **工具返回不是独立 role，它躺在 user message 的 `tool_result` block 里** —— 所以「用户说的」与「工具返回的」**必须在 block 级区分，message 级分不出来**。一个 user message 可以同时含 `text` 与 `tool_result`（用户在工具执行后追了一句话），此时 message 级口径直接失效。
3. **`tool_result` 不带工具名** —— 它只有 `tool_use_id` 与内容。「这是 MCP 还是内置工具」协议不知道，须由调用侧用 `tool_use.name` 关联（本产品落盘里 `mcp_` 前缀即由此派生）。

#### 4.2.2 用量：协议只回报 5 个混合标量

实测 `request_usage.payload.usage` 的字段（146/146 轮全部如此）：

```json
{
  "input_tokens": 176,
  "output_tokens": 193,
  "cache_creation_input_tokens": 0,
  "cache_read_input_tokens": 25344,
  "cacheSemantics": "additive"
}
```

**混合程度**（这是「不可精确读取」的根源）：

| 标量 | 里面混了什么 |
|---|---|
| `input_tokens` | system + tools + 全部历史 + 本轮工具返回 |
| `output_tokens` | thinking + 可见正文 + tool_use 参数 |
| `cache_creation_input_tokens` | 被写入缓存的整段前缀 |
| `cache_read_input_tokens` | 命中缓存的整段前缀 |

### 4.3 原理上不可得的四件事

以下四条**不是实现没做，是换成任何实现都做不到**（除非改协议）：

| # | 不可得项 | 原因 |
|---|----------|------|
| 1 | `input_tokens` 的内部构成 | 单一标量，且不带任何分段标记 |
| 2 | `output_tokens` 的内部构成 | 尤其 **Anthropic 不单列 thinking token**，它并进 `output_tokens` 一起计费 |
| 3 | 缓存内容的归属 | 只知道缓存了多少，不知道缓存的是什么；缓存是**前缀快照**，天然跨类型混合 |
| 4 | 精确的 block 级 token | 协议不回读任何子段 |

**「可估算 ≠ 可读取」**：任何一个位置维度都能本地 tokenize（本产品的 `surfaceSnapshot` 就是这么做的），但那由**本地估算器**产出，不是服务端返回值——本地估算器的版本号标在 `request_context` 事件的 `budget.estimatorVersion`（实测值 `default-v1`），而 `surfaceSnapshot` 自身只带**内容指纹**（`fingerprint` / `systemFingerprint` / `toolsFingerprint`），**不含版本字段**（实测，见 §7.4）。

**四个边界补充**：

- 协议**有能力**按工具回报用量——新版 usage 有 `server_tool_use: { web_search_requests: N }`，**只覆盖服务端工具**，且是**计数不是 token**。本产品未启用，故实测数据中不存在。这是「协议层面存在工具级计量位置」的唯一先例，可作为需求论证的引用。
- 缓存断点是**分段打的**（实测 `cacheBreakpoints: {count: 2, positions: ["system", "msg:0"]}`），说明协议结构上支持按段切；但 `cache_read` / `cache_creation` **不按断点分**。
- 多模态是唯一「可本地精确复算」的（`image` / `document` block 有官方像素换算规则），但服务端同样不回报，且图片与 PDF 换算规则不同 → 属「可复算的估算」。
- 严格讲可用**差分实验**反推（只发 system 不发 messages，量一次 `input_tokens`，差值即 messages）。**原理可行，但属受控测量、非协议支持**，且受缓存与 tokenizer 边界效应影响。

### 4.4 可区分性对照表

> 每一格标三种状态：**`协议精确可得`** / **`协议不可得但本地可估算`** / **`本地未留档`**。★ 为本需求的新增目标。

| 内容来源 | 位置可区分 | token 可得性 | 现状 |
|---|---|---|---|
| system 样板 | ✅ | 不可得但可估算 | **已 token 级**（`surfaceSnapshot.systemTokens`） |
| 工具声明 | ✅ | 不可得但可估算 | **已 token 级**（`surfaceSnapshot.toolsTokens`） |
| ↳ 工具声明按工具/来源细分 | ✅ | 不可得但可估算 | 可切分，**未单列** ★ |
| ↳ skill 清单（system 尾部） | ✅ | 不可得但可估算 | 可切分，**未单列** ★（见 §5.4） |
| 消息体合计 | ✅ | 不可得但可估算 | **已 token 级**（`surfaceSnapshot.messageTokens`） |
| ↳ 用户消息 | ✅ | 不可得但可估算 | **本地未留档** ★ |
| ↳ 历史 assistant 回复 | ✅ | 不可得但可估算 | **本地未留档** ★ |
| ↳ 工具返回 | ✅ | 不可得但可估算 | **本地未留档** ★（体量【派生】可得，见 §5.5） |
| ↳ 历史压缩摘要 | ✅ | 不可得但可估算 | **本地未留档** ★ |
| 多模态 | ✅ | 不可得但可估算 | **本地未留档** ★（预留） |
| output：thinking | ✅ | 不可得但可估算 | 内容【派生】可得，**token 未单列** ★ |
| output：可见正文 | ✅ | 不可得但可估算 | 内容【派生】可得，**token 未单列** ★ |
| output：tool_use 参数 | ✅ | 不可得但可估算 | 内容在 `tool_call.args`【派生】可得，**token 未单列** ★ |
| 三档（input / cache_write / cache_read） | — | **协议精确** | **已精确**（`request_usage`） |
| output 总量 | — | **协议精确** | **已精确** |
| skill 正文（SKILL.md） | ✅ | 不可得但可估算 | 走 `skills_read` → 落入消息体，**本地未留档** ★ |

**读表要点**：这一列 `协议不可得但本地可估算` 占了绝大多数——**说明本需求的技术路线必然是「估算 + 精确分层」，而不是「去协议里取」**。

### 4.5 两条校准证据（为什么精确层不可省）

#### 证据一：三档相加 = 服务端权威输入量【精确】

抽查 `8db4244b` 会话前 12 轮，`input + cache_write + cache_read` 与 `request_context.contextUsage.pressureTokens` **逐轮精确相等**：

| round | input | cache_write | cache_read | **三档和** | pressureTokens | surfaceTokens（本地估算） |
|---|---|---|---|---|---|---|
| 1 | 176 | 0 | 25,344 | **25,520** | **25,520** ✓ | 17,747 |
| 2 | 1,934 | 0 | 25,600 | **27,534** | **27,534** ✓ | 19,484 |
| 3 | 4,504 | 0 | 27,776 | **32,280** | **32,280** ✓ | 23,015 |
| 4 | 568 | 0 | 32,512 | **33,080** | **33,080** ✓ | 23,557 |
| 5 | 210 | 0 | 33,152 | **33,362** | **33,362** ✓ | 23,812 |

**结论**：三档相加是**服务端权威输入量的精确值**，可作分母与锚点。

#### 证据二：本地估算系统性偏小 30–40%【估算 vs 精确】

同表对照可见：round:1 本地估算 17,747 vs 精确 25,520，**偏低 7,773（−30.5%）**；其余各轮同量级。

**结论（本需求最重要的设计约束）**：

> 内容归因若直接建在 `default-v1` 估算器上，会带 **30–40% 的系统性低估**。因此**必须先有精确层做总分，估算层只做结构占比**，并把估算值按精确总量归一化（见 §6.1 公式）。

### 4.6 落盘现状与改造代价

#### 4.6.1 现有落盘已经很省

`8db4244b` 会话（`events.jsonl` 共 80.92 MB）：

| 事件类型 | 条数 | 字节 | 占比 | 平均 |
|---|---|---|---|---|
| `assistant_chunk` | 277,941 | 78.46 MB | **97.0%** | 296 B |
| `tool_result` | 379 | 1.08 MB | 1.3% | 2,979 B |
| `request_context` | 420 | 0.46 MB | 0.6% | 1,140 B |
| `tool_call` | 379 | 0.36 MB | 0.4% | 986 B |
| **`request_header`** | **146** | **0.23 MB** | **0.3%** | 1,674 B |
| `request_usage` | 146 | 0.05 MB | 0.1% | 370 B |

**关键发现：`system` 字段只在 146 条中的 1 条写了完整内容**（3,934 字符），其余仅写 `systemFingerprint`。即**「指纹 + 变化时才写全量」的模式已经存在**，本需求不必新造。

更能说明问题的是 `messagePrefixStats` 已实现的字段：

```json
{
  "itemCount": 45,
  "prevItemCount": 43,
  "commonPrefixItems": ...,
  "firstDivergedIndex": ...,
  "divergedReason": ...,
  "prevItemDigest": ...,
  "currItemDigest": ...
}
```

**messages 侧的差异检测机制已实现**——它记录「前缀变了多少、从哪分歧、指纹是什么」，**只是没记录分歧内容的构成**。

#### 4.6.2 改造代价评估

> **适用范围**：本节此前评估的是**事件台账**（`events.jsonl`）的增量。归因数据的落位定案为 **SQLite 的 `usage_step_facts` 扩列**（`AD9` / `AD23`），**不进台账** —— 因此台账侧**不再需要任何改动**，本节的台账估算**不再是本需求的代价**，保留仅为说明「台账已经很省、且不宜再往里加东西」。SQLite 侧的代价见本节末。

| 台账落盘策略（**已不采用**） | 估算增量 | 占 80.92 MB |
|---|---|---|
| 每轮全量写骨架（Σ`itemCount` ≈ 5,500 条 × ~200 B） | ≈ 1.1 MB | 1.4% |
| 只在变化时写（复用 `messagePrefixStats` 机制） | < 0.2 MB | < 0.3% |

**实际采用的方案：骨架落 `usage_step_facts` 的 JSON 列**，代价如下：

| 项 | 评估 |
|---|---|
| **行体积** | 按类型汇总的字典 ≈ **300 B/行**（见 §7.2）。相对该行原有列（`input_tokens` 等）约为同量级，**不构成数量级影响** |
| **总量** | 以 1 年重度使用约 **20 万行**（上游 §8.3）计 ≈ **60 MB**。SQLite 可承受；且随 `usage_step_facts` 自带的保留期（上游 C8，默认 365 天）一同清理，**不需要额外治理** |
| **写入 IO** | 与现有 `recordStepUsage` **同一次调用**，无额外往返 |
| **读取解析** | 聚合查询需解析 JSON 列；因只在**按内容来源细分**的报表上用到，不影响上游既有的按天/模型/会话聚合（那些走真列） |
| **schema 迁移** | 扩列（`ALTER TABLE ADD COLUMN`），**不新增表、不改 `UNIQUE` 键**；老行该列为 `NULL`，统计侧按「无归因数据」降级 |
| **隐私面** | 骨架只含 `role + type + 字符数`，**不含正文**。但**类型序列能推出行为轮廓**（何时调工具、结果多大），比纯统计多泄露一层（见 §11.1 `AD4` 已确认接受） |

> 结论：**代价集中在「隐私面多一层」与「schema 兼容」两项工程纪律**；体积与 IO 均可忽略。

### 5.4 skill 清单是可切分的

`request_header.system` 的结构是**两个连续区块**，两会话对比可直接看出来：

| 区块 | 内容 | 字符数 |
|---|---|---|
| 固定样板（前缀） | 工具能力说明 + 工具调用约定 + `ui_locale_preference` | **1,118，两会话逐字节相同** |
| **Skills 清单（尾部）** | `## Skills` + `### Available skills` + 每条 skill 的「名称 + 描述 + read 路径」 | 随 skill 数量变化 |

`## Skills` 在 system 中的**位置固定为第 1118 个字符**（各样本一致）：

| 会话 | skill 条数 | Skills 段字符 | 占 system 字符 | systemTokens | 【推断】Skills tokens |
|---|---|---|---|---|---|
| `8db4244b` | **6** | 2,816 | **71.6%** | 1,124 | ≈ 805（≈72%） |
| `5ad6545f` | **2** | 189 | 14.5% | 374 | ≈ 54（≈14%） |

**两会话的 `systemTokens` 差 750，而前缀逐字节相同** → 差值几乎全部来自 skill 清单（字符差 2,627）。

> 【推断】口径说明：805 由两会话两点线性拟合得出（斜率 0.2855 tok/字符）；另一口径（英文 ≈4 字符/token）给 704。**合理区间约 700–810**，即 system 的七成左右。**这是估算，不是精确计数。**

**两个影响设计的实测细节**：

1. **单个 skill 的描述长度差异达 22 倍**：`shell-setup-guide` 描述 35 字符，`diagram-design` 784 字符。→ **skill 成本不随条数走，随描述长度走**，不能按「每 skill 固定 N tokens」估。
2. **存在两种 skill 形态**：

| 形态 | 例子 | `read` 路径 |
|---|---|---|
| 内联型 | `browser-setup-guide`、`shell-setup-guide` | **空**（`(read: )`） |
| 文件型 | `diagram-design`、`guizang-social-card-skill`、`minimax-xlsx`、`svg-design` | `…\skills\<name>\SKILL.md` |

→ 预留字段时须覆盖两种，否则内联型 skill 的用量无处可归。

**skill 正文（SKILL.md）不在 system 里**：它走 `skills_read` 工具（声明为「读取技能目录中指定技能的完整说明」）→ 返回结果 → 计入 `messageTokens`，**与用户消息、历史回复、其他工具返回混在一起，无来源标记**。各样本实测 `skills_read` 调用次数 **0**（本机零样本，属要预留的一类）。

**一处必须剔除的干扰项**：`toolsTokens` 中有 5 个工具名含 `skill`，但它们是**工具声明**、不是 skill 定义：

- `skills_read`（读技能正文的工具本身）
- `mcp_scys_mcp_skillhubinstallguide` / `skillhubuninstallguide` / `skillhubreportinstalled` / `skillhubupdateguide`（MCP 的技能安装管理工具）

→ 统计时**若按「名字含 skill」归堆，会把它们误算进 skill 成本**。skill 定义只在 system 尾部那一段。

**`5ad6545f` 是最有说服力的反例**：首轮 usage 为 `(3251, 0, 0, 54)`——**`cache_read` 为 0**，缓存根本没建立起来，因此 52.3% 的量按全价走。**短会话 / 新会话的缓存收益极低**，这是不折算金额也能得出的可行动结论。

### 5.7 `tool_result` 与工具名的关联性【派生】

| 会话 | `tool_call` | `tool_result` | 用 `toolUseId` 可关联到工具名 | 关联率 |
|---|---|---|---|---|
| `8db4244b` | 379 | 379 | 379 | **100%** |
| `a7981827`（活跃会话） | 401 | 399 | 399 | **100%** |

**结论**：由于 `tool_call` 事件已带 `name`，且 `toolUseId` 唯一（无重复），**统计侧可以 100% 关联出工具名，无需改动落盘**。

**但存在一类边界**：`a7981827` 出现 `tool_call = 401` 而 `tool_result = 399`（差 2），说明**存在孤儿 `tool_call`**（会话中断 / 批次 `break`，与上游 §2.4.4 描述一致）。此时：

- 孤儿 `tool_call` **有** `name`，可作「发起但未返回」的计数，但**不可作成本归因**（无返回体量，且上游 §2.4.0 已规定孤儿不计入 `tool_call_count`）；
- 反向的孤儿（有 `tool_result` 无 `tool_call`）**未出现**，但落盘策略变更后不能保证。

→ 这引出 §7.3 关于是否**冗余落盘 `toolName`** 的讨论。

## 6. 指标与展现需求

### 6.1 设计原则：每个指标对应一个可行动作

> **统计维度不是分类清单，而是可行动杠杆的索引。**

这条原则是本需求与上游文档在取向上的关键差异：上游是**账本**（回答「多少」），本需求是**成本结构剖析**（回答「值不值、该改什么」）。

**反例（必须避免的输出形态）**：只给「system 1,124 / tools 16,476 / messages 320,875」三个数。它**无法回答「我该改什么」**——三个数都是混合体，且第三个占 94.8% 却不可归因。

### 6.3 归一化公式（本需求核心算法）

由于估算层有 30–40% 的系统性低估（§4.5 证据二），**估算值不得直接作为总量呈现**。采用「精确层做分母、估算层做结构」的两段式：

```text
① 结构占比（估算层内部，可自洽）
   ratio_i = estimatedTokens_i / Σ(estimatedTokens_j)

② 归一化数值（按精确总量摊回）
   attributedTokens_i = ratio_i × Σ(精确输入总量)

   其中 Σ(精确输入总量) = Σ(input_tokens + cache_creation + cache_read)
                        = Σ(pressureTokens)   ← 已验证逐轮精确相等
```

**约束**：

1. 归一化的**分子必须是同一次请求内的估算值**，不得跨请求混用；
2. 归一化后的各块之和 **必须等于精确总量**（这是可断言的恒等式，见 §10.1 `AT7`）；
3. 界面必须能**同时**看到「估算占比」与「归一化数值」，并标注后者依赖精确层；
4. 若某请求缺 `request_usage`（协议未回报），该请求**整体降级为只显示估算占比**，不得参与归一化（否则总量会失真）；
5. **估算器版本必须整体一致**：公式 ① 的分子分母 **必须来自同一个 `estimatorVersion`**，且该版本必须**覆盖一次请求的全部输入**（system + tools + messages 三者），否则占比不闭合、公式 ② 摊回后各块之和不可能等于精确总量（`AT7` / `I4` 同时失败）。据此：
   - 既有 `surfaceSnapshot` 的 `default-v1` 三源**继续服务现有 UI**（`AR1`），但**不得进入归一化公式**；
   - 归因展示使用**整体重估**的 `block-v1`（覆盖全部三源，见 §7.4），system / tools / messages 三者的估算值必须同批产出；
   - **禁止拼接**：不得用 `default-v1` 的 system / tools 配 `block-v1` 的 messages（那正是 `I1` 禁止的混用）。
6. **舍入分配规则**：`attributedTokens_i = ratio_i × 精确总量` 逐项取整后一般不等于总量（尾差累积）。为满足第 2 条的「误差为 0」，采用 **largest-remainder 法**：
   ```text
   a. 各项取整 r_i = floor(ratio_i × 精确总量)
   b. 余量 R = 精确总量 − Σ r_i（0 ≤ R < 块数）
   c. 按 (ratio_i × 精确总量 − r_i) 的小数部分降序，依次给前 R 项各 +1
   d. 并列时按块序号升序（保证确定性、可复现）
   ```
   该规则必须写成**纯函数并单测**（`AT7` 的断言依赖它，否则「严格相等」无法稳定通过）。

- **新增要求：`SRC-B4`（未使用工具常驻成本）必须能下钻到工具名清单**，否则无法执行「裁剪哪几个」的动作。

### 6.5 两个口径：定义、差异与归属

**为什么必须先定义口径**：归因值按区间聚合时，存在两个都合理、但**相差 108 倍**的口径。不区分的话，用户看到「工具返回占 60%」根本不知道分母是哪个。

| | **口径 A：累计读取量** | **口径 B：内容量快照** |
|---|---|---|
| 算法 | 按轮次 Σ（每轮请求都读取整个前缀） | 最后一次请求的 `surfaceTokens` |
| `8db4244b` 实测 | **36,663,396** | **338,475** |
| 含义 | 「这段时间**读取**了多少」= **计费规模** | 「上下文里**装**了什么」= **内容构成** |
| 按天 / 跨会话可加 | ✅ | ❌（多个会话的上下文无法相加） |
| 与上游 KPI 对齐 | ✅ **Σ各来源块 = 上游 `M2` 的「输入 Tokens」** | ❌ 对不上任何 KPI |

**口径 A 定为主口径**，理由是它有一条硬性的可用性优势：

> **它的分解之和能精确等于 KPI 卡片上的「输入 Tokens」** —— 用户在图上看构成、在卡片上看总量，数字对得上。口径 B 对不上任何 KPI（KPI 全是累计量）。

**由此推出两个产品位置**（两者是分工，不是二选一）：

| 口径 | 可加性 | 归属 | 回答的问题 |
|------|--------|------|-----------|
| **A** | ✅ 可加 | **跨会话统计 Drawer**（与上游 KPI 同处，共用筛选） | 这段时间花在什么上 |
| **B** | ❌ 不可加 | **`ContextUsageRing`**（单会话、单时刻，天然不需要相加） | 这个会话的上下文里装了什么 |

> 口径 B 的「不可加」缺陷在单会话视角**不成立**——环本来就是单会话单时刻的视角。

| # | 视图 | 图表选型 | 回答的问题 | 对应指标 |
|---|------|----------|-----------|----------|
| ① | **构成快照**（区间汇总） | **横向堆叠条形**（单条 100% 分段） | 这段时间花在什么上 | `SRC-A1`/`SRC-A2`/`SRC-B2`/`SRC-C3` |
| ② | **构成漂移**（按天） | **堆叠面积图**，X 轴与现有折线图对齐，**Y 轴默认绝对量**（`AD20`；占比可切换） | 构成随时间怎么漂移 | `SRC-A5` + 各来源 |
| ③ | **明细排行** | **表格**（来源 / 工具名 / 量 / 占比） | 具体该砍哪个 | `SRC-B3`/`SRC-B4`/`SRC-B6`/`SRC-C1`/`SRC-C2` |

**① 为何用横向条形而非饼图（`AD19`）**：**第一版只做横向堆叠条形，不做饼图**。原因三条：① 本需求类别通常 5–7 个，瓣数一多肉眼分不出大小；② 饼图上标不下数值，只能靠连线或图例；③ 做两套等于多一个组件、一套测试、两份 i18n 文案，而信息量完全相同。**数据层不受影响** —— 若将来确有需求，加视图不需要动落盘或聚合。

**② 为何 Y 轴默认绝对量而非占比（`AD20`）**：**默认绝对量，占比作为切换项**。选定理由是一条信息量判据：**绝对量不丢失占比信息**（某块明显比别人高即知其占比大），反之占比图看不出绝对规模 —— 所以默认绝对量是**信息更多**的那个选择；而这张图的主要用途是**找浪费**（「工具返回多出来多少 token」），正需要绝对量。反例：若只画占比（归一化到 100%），「工具返回占比从 20% 涨到 60%」可能只是**别的部分没涨**。

**④ 洞察卡片是本需求对用户的主要价值**，也是上游没有的（上游定位是「感知成本、复盘习惯」）。示例（数字均来自 `8db4244b` 实测）：

> **59 个 MCP 工具从未使用，每轮白占 14,591 tokens**
> 建议：按需挂载 MCP
>
> **固定成本只占 5.2%，94.8% 在增量侧**
> 建议：优化重心放在工具结果截断
>
> **grep + read_file 合计吃掉 80 万字符**
> 建议：结果截断 / 摘要回填

**一张图不会让用户知道该做什么，一句话会。**

#### 6.6.3 归因覆盖率

**问题**：口径 A 的恒等式（「构成各段之和 == 区间 KPI 的『输入 Tokens』」）在**混合数据区间永远无法成立**：

1. 归因数据是 **P1 才产生**的 → 此前的全部历史请求**没有归因**；
2. 按 `AT8` / `I5`，这些请求必须**显式降级、排除出归因、不得补 0 冒充**；
3. 排除后构成之和必然 **< KPI 输入总量**；而 `I6` / `AR2` 又禁止改动 KPI 去迁就归因侧；
4. 更底层的事实：**落盘本就不是全量的**（§5.1 已承认 `0aa74763-…`、`c069de05-…` 等会话连台账目录都不存在）——这部分连回填都不可能。

若不处理，从 P1 部署到不可归因数据自然过保留期为止（上游 §6.3 为 100 会话滚动窗口，实际可能数月），`AT14` **在任何含历史的区间都不可能通过**。

**定案**：引入**归因覆盖率**作为一等的展示数字，恒等式改为对**可归面子集**成立。

```text
归因覆盖率 = 可归因请求的精确输入量 ÷ 区间 KPI 输入总量

  分母 = 区间内全部 usage_step_facts 行的 Σ 归一化输入
       = 同区间上游 KPI 的「输入 Tokens」（口径 A 对齐，见 §6.5）
  分子 = 其中「可归因」请求的 Σ 归一化输入

  可归因 = ① 该请求有归因数据（归因列非 `NULL`，含三源与汇总字典）；
           ② 且其估算器版本与当前展示版本一致（见 §6.3 约束 5）
```

**界面规则（硬性）**：

| 情形 | 表现 |
|------|------|
| 覆盖率 = 100% | 正常显示；恒等式成立，不额外提示 |
| 覆盖率 < 100% | **必须显示覆盖率数字**，并说明未归因部分的量（「另有 X tokens 无可归因数据」）；**恒等式只对可归面子集承诺** |
| 覆盖率 = 0%（P1 部署前的历史区间） | 显示空态 + 原因说明（「该区间请求早于归因能力上线」），**不显示构成图、不报错、不补 0** |

**为什么必须显式展示而不是静默**：静默会让用户把「构成之和 < 总量」读成「统计有 bug」。把缺口当作**一等数字**呈现，既诚实又避免了「验收标准自相矛盾」。

**连带**：`AT14` 改写为「恒等式对可归面子集成立 **+ 覆盖率正确显示**」（§10.1），并新增 `AT16` 覆盖混合区间降级形态；新增不变量 `I7`（§10.3）。

#### 6.6.4 洞察卡片的判据与配置（`AD22`）

**第一版不做配置化**：3 条规则**硬编码**，不引入阈值设置项。理由：配置化要连带引入「配置存储 + 校验 + 默认值迁移 + 配置界面」，而收益仅是「用户自己调阈值」，目前**没有这个诉求**。

**规则采用相对判据，而非绝对阈值**（属**设计判据**，非用户决策）。原因是绝对阈值会随用户规模失效 —— 例如「未使用工具 > 50 个」对只接了 5 个 MCP 的用户毫无意义：

| 规则 | ❌ 绝对阈值（不采用） | ✅ 相对判据（采用） |
|------|---------------------|-------------------|
| 未使用工具成本 | 「未使用工具 > 50 个」 | 「**未使用工具占工具声明总成本 > 一半**」或「**Top 10 未使用工具占该成本 > 80%**」 |
| 固定/增量比 | 「固定成本 > 20,000」 | 「**固定成本占比 < 10%**」→ 提示优化重心在增量侧 |
| 工具返回膨胀 | 「单工具返回 > 100K 字符」 | 「**Top 3 工具的返回体量占消息体 > 一半**」 |

**相对判据的好处**：**天然自适应** —— 无论用户接了多少 MCP、会话多长，规则都算得出来，因此**不需要配置化也不会因用户规模不同而失效**。这也正是「不做配置」在长期可行、而非仅仅「省工作量」的依据。

**约束**：

1. 规则条数固定为 **3 条**（对应 `SRC-B4` / `SRC-A3` / `SRC-C1`），第一版不增不减、不配置；
2. 每条必须**同时给出「数字」与「动作建议」**（见视图④示例）——只给数字等于把图又画了一遍；
3. 数据不足时，**对应卡片整张不渲染**，**不得展示空卡片或 0% 卡片**（与 `I5` / `I7` 的「显式降级」一致）。触发条件包括：无可归因数据、覆盖率为 0、**工具维度数据缺失**（后者会使 `SRC-B4` / `SRC-C1` 两条规则失去原料，见 §7.6.5）。

### 6.7 展现层（口径 B）：单会话 → `ContextUsageRing`

**现状（已核实）**：`ContextUsageRing.tsx` 是 28×28 三层环（已用 / 输出预留 / 底色轨道）+ Tooltip；`RADIUS = 10`、`STROKE_WIDTH = 3`。

**数据通路已通**：环的取数逻辑里已经在用 `surfaceTokens`：

```ts
const usage = lastUsage ?? {
  input_tokens: contextProjection?.projectedTokens ?? contextProjection?.surfaceTokens ?? 0,
  output_tokens: 0
}
```

即 `contextProjection.surfaceSnapshot` 那条链**已经通到渲染侧**。本需求不需要新建数据通路，只需把它的**三源拆分**（system / tools / messages）读出来展示。

#### 6.7.1 与环的天然契合（三个同源）

| 维度 | 环 | 口径 B |
|------|-----|--------|
| 时间语义 | 当下 / 最近一次请求 | 最近一次请求快照 |
| 作用域 | 单会话 | 单会话 |
| 分母 | `maximumContext` | 同一件事 |

#### 6.7.2 总量用精确、构成用估算（必须分工）

| 用途 | 用哪个 | 为什么 |
|------|--------|--------|
| **构成占比的锚点** | **「上轮输入」`totalRequestInput`**（三档和，精确；i18n key `tooltip.lastRequestInput`） | 协议回报，权威 |
| **构成拆分** | **`block-v1` 整体重估的三源**（`AD15`） | **唯一**允许进入归一化公式的版本（§6.3 约束 5） |

> **必须用 `block-v1`，不是 `default-v1`**：分工表已按 §6.3 约束 5 / `AD15` 定案。`default-v1` 的 `surfaceSnapshot` **继续服务环的既有口径**（`usedRatio` / `totalRequestInput` 等，见 `AR1` / `AR3`），**但不进入构成归一化** —— 用 `default-v1` 进入归一化公式，恰是 `AD15` 明文禁止的拼接。

实测末轮两者差 **26%**（精确 456,105 vs 估算 338,475），正是 §4.5「估算偏小 30–40%」那条。因此：

> **构成占比必须归一化到「上轮输入」**（复用 §6.3 公式，整体 `block-v1` 口径）。否则环里会出现「各段加起来 ≠ 总量」——**那比不展示更糟**。

**锚点必须是 `totalRequestInput`（Tooltip「上轮输入」行），不是 `estimatedOccupancy`（「预估占用」行）**：

环的 Tooltip 本来就有两行不同的总量（`ContextUsageRing.tsx`；文案 key 见 §6.7.4 清单）：

| 行 | 值 | 语义 |
|----|-----|------|
| 「上轮输入」 | `totalRequestInput` | **上次请求实测**的输入（三档和，精确） |
| 「预估占用」 | `estimatedOccupancy` = `totalRequestInput + lastOutput` | **下次发送前预估**（含上轮输出） |

二者相差一个 `lastOutput`。**构成段必须锚定到前者**，因为构成（`block-v1` 重估的三源）本来就是「上次请求」的快照——**同为上次请求，恒等式 `Σ构成段 == totalRequestInput` 才能精确成立**。这比把等式放宽为「≈」更强：换锚点后恒等式**可以精确成立**，不必放弃断言强度。

**因此**：

- 构成段放在 Tooltip 的「上轮输入」行**之下**，明确属于那一行；
- 构成段**不与「预估占用」行对齐**，两者关系写成 `预估占用 = 上轮输入 + 上轮输出`，让差异**显式可见**，而不是回避；
- 界面必须标注「构成为**上轮请求**的快照」（避免读者误以为它描述的是预估占用）。

**环构成的分期形态**：

构成拆分依赖 `block-v1`，而 `block-v1` 属 **P2**（§8.3）。因此：

| 期 | 环构成段 | 说明 |
|----|----------|------|
| **P1** | **不交付**（环完全不改） | P1 期既无 `block-v1`、骨架 `tokens` 又为 `null`，且 `default-v1` 被禁止入公式 → **没有任何合法数据源**。因此 P1 期**不显示构成段**，环维持原样（由 `AR3` 覆盖） |
| **P2** | 交付（本节的形态规则生效） | 与 `block-v1` 同批上线；`AT15` 于 P2 验收 |

> **为什么 P1 期不采用「降级为字符口径」**（而 Drawer 侧可以）：环的**全部既有数字都是 token 口径**（`usedRatio` / `totalRequestInput` / `outputReserve`），在其中插入一段字符口径会**制造新的口径混用**——正是 §6.7.3 第 3 条警告的那类问题。Drawer 侧有空间做「非 token 口径」的显式标注，环的 Tooltip 没有。

#### 6.7.3 环本身不改，只加构成展示

**理由三条**：

1. **物理上装不下**：28px 环、半径 10、stroke 3 —— 塞 3+ 段目视不可分辨；
2. **语义会冲突**：环现有「已用 + 预留 + 剩余」三段语义，再叠一层构成会歧义；
3. **已有前车之鉴**：`docs/develop/context-usage-accuracy-issues.md` 已记录一处现存缺陷 —— **图片 token 不入环但进 tooltip**（环的 `usedRatio` 不含图片，tooltip 又列出图片 → 两处口径不一致）。

> 这是明确警告：**往这个 tooltip 里继续加口径会放大已有的混乱**。因此新增构成必须**显式声明它是「拆分已用部分」，不参与 `usedRatio` 计算**。

**形态（P2 形态）**：环不变；Tooltip 从「一长串标量」升级为**分组结构**（见 §6.7.4）。P1 期不做此改动（见 §6.7.2 分期形态）。

#### 6.7.4 Tooltip 结构与重排（`AD21`）

**做分组重排**，不采用「只加一段、其余不动」。依据：实测 `ContextUsageRing.test.tsx` 共 **2 个 `describe` / 20 个 `it`，无一个断言渲染顺序或 DOM 结构**，故重排**不会破坏既有断言**（见本节末说明）。

**目标结构**（组标题为新增 i18n key；既有行的文案一律沿用）：

```text
占用
  预估占用            16,617 / 64,000（25.9%）
  上轮输入            12,050
  上轮输出             4,567          ← 仅 > 0 时
  图片                ≤ 待发送 / 已有图片提示（仅存在时）
  思考扣除说明          ≤ 仅 > 0 时
构成（上轮请求快照）                   ← P2 新增（§6.7.2）
  系统提示 / 工具声明 / 消息体 …
缓存
  缓存命中
  缓存写入                              ← 仅 > 0 时
预留
  输出预留            12,000
─────────（沿用 tooltip.separator）
总计                  x / y（z%）
图例                  ■ 已用  ■ 预留  □ 剩余
```

「总计」与「图例」**不归入任何组** —— 它们描述整体，不属于某一类。

**四条硬约束**：

| # | 约束 | 原因 |
|---|------|------|
| 1 | **既有文案字符串一个都不能改** | 见下方清单 —— 它们被 tooltip 相关的 9 个 `toContain` 用例断言覆盖 |
| 2 | **空组连标题一起隐藏** | 例如「缓存」组在 `cache_write = 0` 且无 `cacheRead` 时整组不渲染，**不留空标题**（与上游 `M3b`「仅值 > 0 时展示」的取向一致） |
| 3 | **分组标题走 i18n** | 新增 key 须 `zh-CN` / `en-US` 同步，`npm run i18n:generate-types` 与 `npm run i18n:check` 必须通过 |
| 4 | **`usedRatio` 与环形不受影响** | 重排只动 Tooltip 排版，不改任何计算（`AR3` / `AT15` / `I6` 仍然覆盖） |

**必须保持不变的既有字符串清单**（实测自 `ContextUsageRing.test.tsx` 的 `toContain` 断言）：

| i18n key | 中文文案 | 英文文案 |
|---|---|---|
| `tooltip.estimatedOccupancy` | 预估占用 | Estimated occupancy |
| `tooltip.lastRequestInput` | **上轮输入** | Last request input |
| `tooltip.lastOutput` | 上轮输出 | Last output |
| `tooltip.cacheRead` | 缓存命中 | Cache read |
| `tooltip.cacheWrite` | 缓存写入 | Cache write |
| `tooltip.outputReserve` | 输出预留 | Output reserve |
| `tooltip.total` | 总计 | Total |
| `tooltip.legend` | 图例 | Legend |
| `tooltip.thinkingExcluded` | 已扣除思考约 … | Thinking excluded ~… |
| `tooltip.pendingImages` / `historyImages` | 待发送图片约 … / 已有图片约 … | Pending images ~… / Images in chat ~… |
| `tooltip.noData` | 暂无上下文用量数据 | No context usage data |

> **测试约束的事实（本节的依据）**：`ContextUsageRing.test.tsx` 共 **2 个 `describe` / 20 个 `it`**。断言形态**混用** —— tooltip 相关 **9 个**用例用 `expect(text).toContain('…')` 文本包含断言；其余用例断言的是**值**（`toBe` / `toEqual` / `toHaveLength` / `toBeCloseTo` / `toBeDefined` / `toBeNull` / `toBeGreaterThan` / `toBeLessThan`，以及 SVG 属性值）。**关键结论：20 个用例中没有任何一个断言渲染顺序或 DOM 结构** —— 因此**真正的约束是「tooltip 用例的既有字符串不能变」，而非「不能重排」**。

**工程建议（不需要拍板）**：重排与「新增构成段」**分两次提交** —— 先提重排（纯排版、行为不变、既有测试应全绿），再提构成。这样一旦出问题，能立刻区分是「排版改坏」还是「新数据算错」，无需在混合改动里二分定位。

### 6.8 可信度标注与 i18n（两个展现位置共同适用）

**1. 必须做可信度分层。** 现有 KPI 与折线全是**精确值**（协议回报）；归因是**估算 + 归一化**。混在一起用户会以为同一可信度。因此归因区块整体带「估算」标注，Tooltip 标 `estimatorVersion`（即不变量 `I1` 的界面要求）。

**2. 文案全部走 `t()`。** 沿用上游 `usageStats` 命名空间的做法；`ContextUsageRing` 侧用既有 `contextUsage` 命名空间。需维护 `zh-CN` / `en-US` 两份并运行 `npm run i18n:generate-types` 与 `npm run i18n:check`。

**3. 空态与降级**。无归因数据（老会话 / 无落盘）时显示「无内部构成数据」，**不补 0、不报错**（对应不变量 `I5`）。

## 7. 数据采集改造设计

### 7.1 改造清单（三处，按必要性排序）

| # | 改造 | 必要性 | 改动面 |
|---|------|--------|--------|
| 1 | **messages 骨架落库**（`usage_step_facts` 扩列，**不走事件台账**） | **唯一硬前置** —— 不解开则 `SRC-C3` 永远无法做 | 1 张表扩列 + `recordStepUsage` 入参扩展 |
| 2 | **估算器升级**（`default-v1` → 按 block 类型可归因） | 必需 —— 否则骨架有结构但无 token | 估算器模块 |
| 3 | **`tool_result` 冗余 `toolName` / `toolSource`** | 可选（鲁棒性）—— 实测已可 100% 关联 | 加可选字段（层次已定案：`payload.result` 内，见 §7.3 / `AD10`） |

> 说明：下面各小节按**数据流顺序**展开（§7.2 骨架 → §7.3 冗余字段 → §7.4 估算器），与上表**按必要性排序**的编号不同步，**以各节标题内的序号为准**。

### 7.2 改造一：messages 骨架（落库扩列）

**落位：`usage_step_facts` 扩列，不走事件台账**（`AD23`）。

#### 7.2.1 为什么必须走落库端口，而不是 `request_header` 事件

| 通道 | 入口 | 桌面 | 远程 | butler |
|------|------|------|------|--------|
| **事件台账**（`events.jsonl`） | `emitSessionEvent` | ✅ | ❌ **no-op** | ✅ |
| **用量落库**（SQLite） | `hostUsage.recordStepUsage`（**端口注入**） | ✅ | ✅ | ✅ |

**实测依据**：`electron/remote/imRemoteAgent.ts:213` 硬编码 `emitSessionEvent: async () => undefined` —— 远程会话的**所有**台账事件（含 `request_header`）**从不写入** `events.jsonl`（`toolChatLoop.ts:1288` 的 `request_header` 正是走这条路）。若骨架挂在 `request_header.payload`，**远程永久无骨架**。

而用量落库走的是**端口注入**通道：`toolChatLoop.ts:69` 直接 `import { recordStepUsage }`，在 `:1527` / `:1623` 以 `hostUsage?.recordStepUsage?.({...})` 调用，**不经过 `emitSessionEvent`** —— 因此**三条链路全覆盖**。这正是上游 `C16` 选「`runToolChatSession` 统一收口」的原因。

> **因此骨架与归因数字落在同一行**（同一个 `UNIQUE(session_id, turn_id, step_id)` 键），天然自洽，**不存在跨数据源对齐问题**。

#### 7.2.2 存什么：按类型汇总的字典，不是逐 block 明细

| 维度 | 规定 |
|------|------|
| **键** | `<role>\|<blockType>`（如 `user\|text`、`assistant\|thinking`、`user\|tool_result`） |
| **值** | `{ chars, tokens }`；P1 期 `tokens` 为 `null` |
| **粒度** | 一次请求一份，覆盖全部 messages |
| **不含 `toolName`** | 工具维度的归因由 `tool_result` 落盘聚合提供（`SRC-C1` / `SRC-C2`），**骨架不重复承担** |

**为什么不做逐 block 明细**：归因展示要回答的是「user / assistant / tool_result / thinking 各占多少」（`SRC-C3`），这是**按类型汇总**，**不需要逐条 block**。汇总字典把行体积从「Σ`itemCount` ≈ 35 条 × ~200 B」降到「**~10 个键 × ~30 B ≈ 300 B**」，同时也**消掉了「纯追加 vs 全量」的写入策略问题** —— 后者只在 append-only 的 JSONL 日志上存在（原 `AD16` 的三形态设计因此作废，见 §11.3）。

**落库形态（P2 目标形态）**：

> ⚠️ **`estimatorVersion` 不在这个 JSON 里** —— 它落为 `usage_step_facts` 的**独立真列 `estimator_version`**（理由见 §7.2.3）。此处的 JSON 列只放 `blocks`。

```jsonc
// usage_step_facts 行的归因 JSON 列（版本号另在真列 estimator_version）
{
  "blocks": {
    "user|text":          { "chars": 42,   "tokens": 12 },
    "assistant|thinking": { "chars": 1820, "tokens": 455 },
    "assistant|tool_use": { "chars": 310,  "tokens": 96 },
    "user|tool_result":   { "chars": 8432, "tokens": 2108 },
    "user|image":         { "chars": 0,    "tokens": null }
  }
}
```

#### 7.2.3 设计要点

| 要点 | 规定 |
|------|------|
| **只存汇总，不存正文** | 仅 `role` / `type` / `chars` / `tokens`；**永不落正文** |
| **`estimatorVersion` 的落位与取值（`AD18`，v1.13 明确落位）** | **落位**：`usage_step_facts` 的**独立真列 `estimator_version`**（**不是** JSON 列内）。<br>**为什么必须是真列**：① `I1` 要求按版本分组、**不得混算**；三源真列做 `SUM()` 时若同时要按版本过滤，版本号在 JSON 里就得逐行 `json_extract` —— 既无法建索引，也让每个聚合查询都退化成 JSON 解析；独立真列可直接 `WHERE estimator_version = ?` + 索引。<br>**注意**：原始设计曾把它放在归因 JSON 列内（与 `blocks` 平级）；该写法与真列方案**不能并存**（否则出现两份真相源），现已统一为真列。<br>**取值**：**P1 期取 `null`**（语义即「尚无 token 估算器」）；**P2 起为 `"block-v1"`**。<br>**分组规则**：`null` 组标注「字符口径（无 token 估算）」，**不参与 token 归一化**（与 §6.6.3 覆盖率定义中「可归因」的第二条相容）。 |
| **P1 期的 `tokens` 字段（`AD15`）** | P1 期 `block-v1` 估算器**尚未落地**（§8.3 为 P2）。P1 期 `tokens` **必须取 `null`**，**不得写入 `default-v1` 估值** —— 否则 P1 期与 P2 期 token 口径不同，旧口径会**永久混入**历史数据。P2 上线时按已有数据重新估算回填 |
| **P1 期的展示形态** | 因 `tokens` 为 `null`，P1 期归因展示**只出字符占比**（`chars`），并明确标注「**非 token 口径**」；**P2 起**才切换为 token 归因。**token 恒等式 `AT7` / `AT14` / `AT15` 全部绑定 P2 验收**；P1 只验收字符量与覆盖率的分母侧 |
| **三链路覆盖由通道保证** | 因走 `recordStepUsage` 端口（见 §7.2.1），桌面 / 远程 / butler **天然全覆盖**，无需为某条链路单独接线 |
| **多模态留位** | 键的 `type` 允许 `image` / `document` / `audio` 等取值；`tokens` 允许 `null`（未启用时），**预留而不伪造数值** |
| **历史压缩摘要留位** | `type` 允许 `summary` 取值（当前无数据，为将来留位） |
| **schema 版本** | JSON 列内自带 `schemaVersion`，独立于数据库迁移版本，便于其自身演进 |
| **老数据兼容** | 老行该列为 `NULL` → 统计侧**必须能处理缺失**（降级为「该会话/该请求无内部构成数据」，不得报错、不得补 0 冒充） |

**为什么选择「汇总骨架」而非「全量正文」**：正文体积大、含隐私内容（代码、文档、用户输入），而**归因只需要类型与体量**。这与上游 §6.3 对台账体积的取向一致。

### 7.3 改造三：`tool_result` 冗余 `toolName`（可选）

> ⚠️ **覆盖边界**：该改造挂在 `tool_result` **事件**上（台账通道），因此**对远程链路无效** —— 远程的 `emitSessionEvent` 是 no-op（见 §7.2.1），不会写任何事件。远程的工具名仍只能靠 `tool_use_id` 关联得出（实测关联率 100%，§5.7）。这也是它被列为「**可选**」而非「前置」的原因之一。
>
> **对本需求主线无影响**：工具维度的归因数据走落库端口（§7.6.5），不依赖本改造。

**实测结论：不写也能 100% 关联**（§5.7）。因此这是**鲁棒性改进，不是前置依赖**。

**建议执行，理由三条**：

1. **不依赖跨事件的配对逻辑**：现在 `tool_result` 要取工具名，必须回查同会话的 `tool_call`。若未来 `tool_call` 因保留策略、裁剪或迁移丢失，归因能力**永久失效**；
2. **不依赖命名约定**：目前判断「MCP vs 内置」靠 `mcp_` 前缀这一**脆弱约定**（改名即失效）。若直接落 `source: "builtin" | "mcp" | "skill" | "other"`，则归因不再依赖字符串前缀——**这是比冗余工具名更有价值的改进**；
3. **与上游 C11 同形态**：在 `ToolCallResultPersisted` 上加可选字段，**不新增事件类型、无旧版本降级风险**。

**建议落盘形态**（沿用上游 §7.6 的做法）：

```jsonc
{
  "type": "tool_result",
  "payload": {
    "toolUseId": "…",
    "result": {
      "success": true,
      "data": { … },
      // 上游 C11 已加：notExecuted / notExecutedReason
      // 本需求建议追加：
      "toolName": "mcp_scys_mcp_searchtopic_4e77a8ec",
      "toolSource": "mcp"
    }
  }
}
```

> ✅ **已定案（`AD10`，v1.1）**：与上游一致，放 `payload.result` **内**（与 `notExecuted` 同级）。
>
> **依据（已核实，非推断）**：①上游 §7.6 明确 `recordToolResult` 的第二参数**原样进入** `tool_result` 事件的 `payload.result`，而 `ToolCallResultPersisted` 就是 `payload.result` 的类型，上游的 `notExecuted` / `notExecutedReason` 正定义在其中；②**实测已落地**——样本的 `payload.result` 内实际出现 `notExecuted` / `notExecutedReason`（如 `8db4244b` 各 28 条），证明上游 C11 的改动已实施、且位置就在 `result` 内。

### 7.4 改造二：估算器升级

> **既有版本字段的位置（实测，逐条核对）**：
>
> | 事件 | 字段 | 实测 |
> |------|------|------|
> | `request_header.surfaceSnapshot` | `schemaVersion` / `fingerprint` / `systemFingerprint` / `toolsFingerprint` / `surfaceTokens` / `systemTokens` / `toolsTokens` / `messageTokens` | **无 `estimatorVersion`**（只有内容**指纹**） |
> | `request_context.budget` | `estimatorVersion` | `"default-v1"` |
>
> **两点结论**：① `default-v1` 标在 `request_context`，**不在 `surfaceSnapshot` 里**，两者是不同事件；② 因此新增的归因版本字段**无法「沿用既有字段的命名习惯」** —— 既有字段根本不在同一个位置、也不同名，落位是**新决定**（见 §7.2 与 `AD18`）。

现有 `surfaceSnapshot` 已能产出三源拆分（system / tools / messages），该拆分由本地估算器产出（版本号标在 `request_context.budget.estimatorVersion`）。

**本需求要求**：新增**整体重估**的估算模式 `block-v1`，用于：

1. **重估全部三源**（system / tools / messages）—— **不只是 messages 细分**；
2. 按 `type` 汇总 messages 骨架的 token（→ `SRC-C3`）；
3. 按 skill 清单文本边界切分 system（→ `SRC-B5` / `SRC-B6`）；
4. 按 `reasoning_delta` / `text_delta` / `tool_call.args` 估算输出侧三类（→ `SRC-D1`）；
5. 输出 `estimatorVersion`，使不同版本的数据**可比较分组、不混算**。**该字段落位为 `usage_step_facts` 的独立真列 `estimator_version`**（理由见 §7.2.3）；**P1 期取 `null`，P2 起为 `"block-v1"`**。

#### 7.4.1 为什么必须「整体重估」而非「只重估 messages」

§6.3 公式 ① 的占比**分母要覆盖一次请求的全部输入**，否则占比不闭合、摊回后各块之和不可能等于精确总量（`AT7` / `I4` 同时失败）。而：

| 来源 | 原版本 | 若只换 messages 会怎样 |
|------|--------|------------------------|
| system / tools | `default-v1` | 与 messages 的 `block-v1` **混用** → 直接违反 `I1`（同一报表内不得混用两个版本） |
| messages | `block-v1` | — |

**因此定案**：`block-v1` **必须整体覆盖三源**，归一化的分子分母**整体来自同一版本**。

| 估算器 | 服务对象 | 是否进入归一化公式 |
|--------|----------|-------------------|
| `default-v1`（既有 `surfaceSnapshot` 三源） | 既有 UI（上游 `ContextUsageRing` / 用量环） | **否**（`AR1` 要求其行为不变） |
| **`block-v1`（整体重估三源）** | **本需求的归因展示** | **是**（唯一允许进入的版本） |

> **禁止拼接**：不得用 `default-v1` 的 system / tools 配 `block-v1` 的 messages（这正是 §6.3 约束 5 与 `I1` 禁止的混用）。

#### 7.4.2 约束

- 新旧估算器**不得在同一指标上混用**；界面按 `estimatorVersion` 分组或标注；
- 估算器升级后，**三源拆分（system/tools/messages）的现有效果不得回退**——这是上游与 UI 已在消费的口径（`AR1`）；
- **P1 期**（骨架已落盘、`block-v1` 未上线）：骨架 `tokens` 取 `null`，展示降级为字符口径（见 §7.2 设计要点）；
- **P2 期**：`block-v1` 上线后，按**已有落库数据**重新估算并回填 `tokens`（不依赖台账），同时切换展示为 token 口径。

### 7.5 与上游文档的写入点关系

| 项 | 上游写法 | 本需求 |
|---|---|---|
| 落盘位置 | `request_usage` / `tool_call` / `tool_result` **事件**（`events.jsonl`） | **不改事件**；骨架走 **SQLite `usage_step_facts` 扩列**（§7.2 / `AD23`） |
| 是否新增事件类型 | 否（上游 C11 明确不新增） | **否**（一致）。**除 §7.3 的可选字段外，不改任何事件的 payload** |
| 统计侧存储 | 新增 `usage_step_facts` / `usage_turn_facts` 两张 SQLite 表 | **两张表都扩列**：`usage_step_facts` 放输入侧归因（§7.6.3），`usage_turn_facts` 放工具维度归因（§7.6.5） |
| 写入收口点 | `runToolChatSession` 内局部累计 | **沿用**（不得挂 `finalizeTurn`，见上游 C16）；输入侧归因随 `recordStepUsage`、工具维度随 `recordTurnSummary` 写入 |

> **本需求只改两个既有函数**（`recordStepUsage` / `recordTurnSummary` 的入参与落库列），**不改事件模型、不改台账格式、不新增事件类型**。**唯一的例外是 §7.3 的可选改造**（`tool_result` 追加 `toolName` / `toolSource`）—— 它被明确列为「可选、非前置」，可独立取舍。

### 7.6 归因数据的存储形态（已定案）

> ⚠️ **设计更正**：早前曾认为「统计侧只需读台账聚合、不必写 SQLite」——**该结论错误**。正确结论是**必须落库**，理由见下。

#### 7.6.1 为什么必须落库（O1）

| # | 理由 | 证据 |
|---|------|------|
| **1** | **台账会被清理，不落库则历史永久丢失** | 上游 §6.3：每个 workDir 只保留最近 **100 个会话**，启动时按 `lastAt` 倒序 `fs.rm` 整个目录。上游 C7 原文：「**机会不可逆**……错过即永久丢失」。<br>**本机实证**：写作期间样本 `5ad6545f` 的会话目录**已被该策略清理**（§5.1），其数据现已不可复现 |
| **2** | **性能差 1–2 个数量级** | 本机实测全量解析 3 个会话 = **112.9 MB / 389,709 行 / 2.47 s**（约 45.6 MB/s）。外推 100 会话 × 20 MB ≈ **2 GB → 约 44 s**（Python 口径；Node `JSON.parse` 为原生实现、通常快 2–5 倍，实测量级仍在 **8–20 s**）。对照上游 §8.3 要求：面板首次打开 **< 500 ms**、单维度汇总 **< 200 ms** |
| **3** | **远程链路在台账上完全缺失** | 远程会话**不落任何台账事件**（`imRemoteAgent.ts:213` 的 `emitSessionEvent` 是 no-op），因此归因数据若走台账，远程**永久无归因**；而落库走端口注入通道，**三链路全覆盖**（§7.2.1）。这条是 `AD23` 的直接依据 |

> **必须澄清的一处混淆**：「**不需要实时展示**」≠「**不需要落库**」。报表仍可在打开时聚合查询——那说的是**展示时机**；落库说的是**数据留存**。两者无关。

> ⚠️ **一条论据已作废**：早期版本曾以「台账可独立重建归因数据」作为落库论据之一。**骨架落位改到 SQLite 后该论据不再成立** —— 骨架不在台账里，台账无法独立重建归因。这不影响落库的结论（其余三条已足够），但**不能再用这条理由**。

#### 7.6.2 粒度：与 Step 级严格 1:1

**构造保证（主要依据）**：骨架随 `recordStepUsage` 写入（§7.2.1），**与用量数字是同一次调用的同一行**，键为 `UNIQUE(session_id, turn_id, step_id)` —— 因此 **1:1 是设计上必然成立的**，不依赖事后对齐。

**实测旁证（说明归因数据来源本就与用量同频）**：`surfaceSnapshot`（输入侧三源）所在的 `request_header`，与 `request_usage` 在所有样本中**严格 1:1**：

| 会话 | `request_header` | `request_usage` | requestId 交集 | 差集 |
|---|---|---|---|---|
| `8db4244b`（已完结） | 146 | 146 | **146 = 全部** | **空** |
| `a7981827`（**活跃会话**，读数随时间增长） | 196 | 196 | **196 = 全部** | **空** |
| `945df78b` | 未逐条核对 | — | — | — |

> **两处口径说明**：① `a7981827` 是**活跃会话**，其数字随对话增长而变，**不是固定样本**（见 §5.1）；② 上表数据取自 `events.jsonl`（台账），仅用于说明「归因来源与用量同频」；**落库侧的 1:1 由上面的构造保证成立**，与台账是否可用无关。

> **结论**：**一个 step 行对应一份归因数据，零行数放大**。

#### 7.6.3 落库方案定案：方案 B1（扩列，真列 + JSON 列）

| 方案 | 行数（`8db4244b`） | 相对 step 级 | 是否需新主键 | 结论 |
|---|---|---|---|---|
| 现状 step 级 | 146 | 1× | — | — |
| **方案 B1（扩列）** | **146** | **1×** | 否，复用 `UNIQUE(session_id, turn_id, step_id)` | ✅ **采用** |
| 方案 B2（新表，每 block 一行） | **5,142** | **35×** | 是 | ❌ 否决 |

方案 B2 的放大倍数实测（`messagePrefixStats.itemCount`）：`8db4244b` 平均 **35.2**、最大 **77**；`a7981827` 19×。

**方案 B1 的准确形态是混合**：

| 存法 | 存什么 | 理由 |
|------|--------|------|
| **真列** | 归因来源块：`system_tokens` / `tools_tokens` / `message_tokens` | 常用维度直接 `SUM()`，对齐上游「不必解析 JSON」的取向 |
| **JSON 列** | 输入侧骨架（按类型汇总的字典，§7.2.2）+ `estimatorVersion` | 类型要能扩展（多模态、summary），细分查询少 |

> 该混合形态**在上游已有先例**：`turns` 表的 `usage_json` / `terminal_usage_json` + 真列并存（上游 §6.1 S1）。不是新做法。

#### 7.6.4 一条实现边界

**不得用 `request_context` 作锚点**：它不是 1:1（`8db4244b` 420 条 → 274 去重），因为一个 round 会按不同 phase / surface 发多条（`…:round:1` 与 `…:surface:1`）。因此**若从台账做历史回填，必须以 `requestId` 关联，不能用 seq 邻接**。

> **注**：实时写入路径不存在此问题（骨架与用量同一次调用，见 §7.6.2）；此边界仅约束**回填**场景。
>
> **回填的天然边界**：远程会话不落台账 → **远程历史无法回填**（见 §9.1）。这与上游 C7「回填对远程天然为零」一致。

#### 7.6.5 工具维度数据（明细类指标）的落库（v1.13 新增，补 S3）

§7.6.1 的三条理由（**台账会被清理**、性能、避免两套数据源）**同样适用于工具维度**，但 §7.6.3 只覆盖了输入侧三源；工具维度的原料原本仍留在台账里。本节补齐 —— 否则远程会话的工具明细永久无数据，且台账过保留期后明细历史与构成历史的留存期不一致。

**两类数据、同一张表、两处写入时机**：

| 数据 | 原料 | 写入时机 | 原因 |
|------|------|----------|------|
| **工具声明明细** | `request_header.tools`（每次请求注入的声明数组） | 随 **`recordTurnSummary`**（turn 收口）写入 `usage_turn_facts` | 声明集在 turn 内通常不变。按 turn 存比按 step 存**少 5–10 倍行数**；且 `recordTurnSummary` 同样走端口通道，**三链路全覆盖** |
| **工具返回体量** | `tool_result` 事件 | 同上 | **工具的返回发生在该次 LLM 调用之后** —— `recordStepUsage` 写出时还不知道，只能在 turn 收口时写 |

**形态**（`usage_turn_facts` 新增归因 JSON 列，P2 目标形态）：

```jsonc
{
  "tools": {                       // 声明明细：按工具名的 schema 字符数
    "grep": 1254, "read_file": 900,
    "mcp_scys_mcp_searchtopic_4e77a8ec": 4802
  },
  "toolSource": {                  // 按来源分组的 schema 字符数
    "builtin": 6875, "mcp": 53210
  },
  "toolResults": {                 // 返回体量：按工具名
    "grep":      { "calls": 146, "chars": 501404 },
    "read_file": { "calls": 76,  "chars": 302598 }
  }
}
```

**由此解锁的指标**（此前全部依赖台账）：

| 指标 | 数据来源 | 说明 |
|------|----------|------|
| `SRC-B1` / `SRC-B2` | `tools` / `toolSource` | 工具声明总成本、按来源分组成本 |
| `SRC-B3` | `tools` | 单工具声明常驻成本排行 |
| **`SRC-B4`** | `tools` **与** `toolResults` 的差集 | **未使用工具常驻成本** —— 有声明、无调用记录 |
| `SRC-C1` / `SRC-C2` | `toolResults` | 工具返回体量排行与均值 |

**体积**：工具声明明细按工具名逐个写入，`8db4244b` 为 71 项 ≈ 2.8 KB/turn。因声明集在会话内稳定，**可加变化检测：与本会话上一 turn 相同则只写指纹**（复用 `surfaceSnapshot.toolsFingerprint`）—— 与 §7.2 汇总字典的取向一致；SQLite 行为 upsert，**不存在台账那类「重复追加」问题**。若不启用变化检测，按 1 年约 2 万 turn 估算 ≈ 56 MB，亦可接受。

**一处必须声明的边界**：以上均为**上线后的新数据**。远程会话无台账 → **远程的工具维度历史无法回填**（见 §9.1）；上线后，工具维度明细的留存期由 SQLite 保留策略统一（上游 C8），**不再受台账清理影响**。

**洞察卡片随之闭合**：§6.6.4 的 3 条规则中，`SRC-B4` 与 `SRC-C1` 均依赖工具维度数据 —— 本节的落库使其在**三链路**上都可持续产出。

## 8. 交付分层与推进顺序

> 分层的依据是**数据可得性**，不是实现难度：能做的先做，需要改采集的放中间，需要升级估算器的放最后。

### 8.1 P0 — 数据源零新增（验证层）

> **范围说明**：P0 的「零采集改动」**仅指数据源** —— 这些报表所需字段**现有落盘已全部具备**。但**产品化需要落库**（§7.6：台账会被清理、且全量扫描远超性能要求）。
>
> 因此 P0 的准确定位是：**验证手段 + 报表逻辑**（先用现有台账跑一次性报表，证明这两张报表确实有价值），**不是交付形态**。交付形态必须走 §7.6 的落库方案。

**数据源全部来自现有落盘**，不新增任何字段即可产出：

| 报表 | 数据源 | 实测样例（`8db4244b`） |
|------|--------|------------------------|
| **① 固定成本台账** | `surfaceSnapshot` | system 1,124（其中 skill 清单 ≈805）+ tools 16,476 = 17,600 |
| **② 工具声明成本明细** | `tools[].name` + schema 字符 | MCP 88.6% ≈14,591 tok；Top1 单条 ≈1,317 tok |
| **③ 工具调用回报表** | `tool_call.name` ↔ `tool_result`（`toolUseId` 100% 可关联） | grep 501K / read_file 303K / list_directory 50K 字符 |
| **④ 缓存效率与三档结构** | `request_usage` | 缓存依赖度 97.9% / 新增依赖度 2.1% |
| **⑤ 未使用工具常驻成本** | ② ∩ ③ | 63 个未调用，其中 MCP 59 个（≈14,591 tok/轮） |

**为什么 P0 收益最大**：它已经能回答「MCP 到底占多少、值不值」这个最初的疑问，**不需要任何采集改造**（**报表逻辑与落库仍需开发**）。特别是 ③ —— `tool_result` 的 `result` 字段**已经在落盘里**，所以「哪个工具吃掉了上下文」这个问题**今天就能回答**。

> ③ 的实测价值：grep + read_file + list_directory 合计 **85.4 万字符**，是 `messageTokens` 从 14 涨到 320,875（22,920×）的主因——而它们现在**全部落在 `messageTokens` 这个无法归因的黑盒里**。P0 能把这个黑盒打开一半（工具返回侧）。

### 8.2 P1 — 需补 messages 骨架（唯一硬前置）

| 项 | 内容 |
|---|---|
| 改造 | §7.2 的骨架落库（**`usage_step_facts` 扩列**，不走事件台账） |
| 解锁的指标 | `SRC-C3`（消息体内部构成：用户 / 历史回复 / 工具返回 / 多模态 / 压缩摘要） |
| 新增体积 | **≈300 B/行**（按类型汇总的字典，见 §7.2.2 / `AD23`） |
| 覆盖范围 | **桌面 / 远程 / butler 三链路**（由端口通道保证，见 §7.2.1） |
| 依赖 | 改造二（估算器）才能从骨架得到 token；但骨架的**字符量**在 P1 即可用 |
| **P1 期的验收范围** | **只验收字符量（`chars`）与覆盖率的分母侧**；`tokens` 取 `null`，界面标注「非 token 口径」。**`AT7` / `AT14` / `AT15` 等 token 恒等式绑定 P2 验收**（见 §6.3 约束 5 / `AD15`；环构成亦在 P2 交付，见 §6.7.2 分期形态） |

### 8.3 P2 — 输出侧拆分与估算器升级

| 项 | 内容 |
|---|---|
| 改造 | §7.4 估算器升级（`block-v1`） |
| 解锁的指标 | `SRC-D1`（thinking / 正文 / 工具参数占比）；`SRC-C3` 的 token 值（而非仅字符量） |
| 为何单独一层 | 输出侧三类**内容全在本地**（§5.5），协议不阻碍；难度在估算器，不在采集 |

### 8.4 推进顺序与理由

```text
P0（数据源零新增的报表）
  ↓  收益最大、成本最低，且已能回答 MCP 成本问题
P1（usage_step_facts 扩列，补 messages 骨架）
  ↓  唯一的硬前置；改动面小（扩列 + 一个函数入参），且天然覆盖三链路
P2（估算器 default-v1 → block-v1）
     补上输出侧与 token 归因
```

**不采用「先做 P2 再补 P1」的理由**：P2 若没有 P1 的骨架，输出侧与输入侧的消息归因都缺原料，估出来的只是总量，仍不可归因。

## 9. 边界与不承诺

### 9.1 能力边界（写进需求，避免被当作缺陷）

| 项 | 为什么不做 / 做不到 |
|---|---|
| 服务端精确的 block 级 token | **Anthropic 协议不提供**（§4.3） |
| 精确的 thinking token | 同上；Anthropic 将 thinking 并入 `output_tokens` |
| 缓存内容的归属拆分 | 缓存是**前缀快照**，天然跨类型混合 |
| `user` / `tool_result` 的**精确** token | 即使补落库，仍为估算 |
| 无需差分实验的精确测量 | 差分可提高精度，但属受控测量、非协议支持 |
| 跨会话的 messages 内容比对 | 骨架只存类型与体量，**不存正文**，无法比对内容 |
| **远程会话的历史归因** | 远程**不落任何台账事件**（§7.2.1），因此**远程历史无法回填** —— 只有 P1 上线后新产生的远程回合才有归因。这与上游 C7「回填对远程天然为零」一致 |
| **工具维度的历史明细** | 工具维度的原料（`request_header.tools`、`tool_result`）原本只存在于台账（**会被清理**），故**上线前的工具明细无法回填**；上线后由 §7.6.5 落库留存 |
| **逐 block 明细** | 骨架按类型汇总（§7.2.2），**不保留单条 block**。归因展示不需要它；需要工具维度时走 `tool_result` 聚合（`SRC-C1`） |
| **台账被清理后的历史归因来源** | 台账按会话数清理（上游 §6.3）。**归因数据已落库**（§7.6），故不受影响；但**回填只能趁台账还在时做**（上游 C7） |

### 9.2 与上游一致的明确不做

- ❌ **费用 / 金额估算**（与上游 §10.1 一致；本需求所有指标均不以金额呈现，见 §11.1 `AD5`）
- ❌ 实时（流式进行中）展示
- ❌ 跨设备 / 云端汇总
- ❌ 报表导出与定时推送

### 9.3 本需求明确不做

- ❌ **工具调用次数与失败率**（属上游 §2.4 / 上游 C10 范围，本需求不重复建设）
- ❌ 改写现有 `surfaceSnapshot` 的三源口径（只在其上叠加细分）
- ❌ 按内容来源做**费用**排行（因不做费用）
- ❌ 改动 `ContextUsageRing` 的**环形本身**（三层结构、`usedRatio` 口径、28px 尺寸）—— 详见下方翻案说明

> **边界说明（相对上游 §10.1 的收窄）**：上游 §10.1 列有「❌ 修改 `ContextUsageRing` 的单会话视图」。本需求**将该条收窄为「不改环形本身」**，而**允许 Tooltip 增构成** —— 因为口径 B（内容量快照）的**唯一合理归宿就是环的 Tooltip**：「这个会话的上下文里装了什么」只能在单会话视角回答（§6.7）。这样既不违反原非目标的精神（不改单会话视图的**计算口径与视觉结构**），又给口径 B 一个正式的展示位置。
>
> **上游 §10.1 的同行需同步收窄** —— 拟改文本与 `AD6` 一并处理（**等评审通过后落盘**，见 §11.1 `AD12`）。
>
> ⚠️ **一处边界澄清（必须写明）**：`context-usage-estimated-occupancy-requirement.md` §1.2 将「本地 token 精确计数（tiktoken）」列为**非目标**。本需求**不引入 tiktoken**，只**复用已在产品中运行的 `surfaceSnapshot` 估算器的构成拆分** —— 这是「复用既有估算」，不是「新增精确计数」。该区别需在两份文档中都写明，否则会被误读为违反那份文档的非目标。

| **AD1** | `cache_creation` 恒为 0 怎么处理 | **保留字段、作预留**：当前模型（DeepSeek / GLM 等自动缓存）不单独计费写入，故恒为 0；**模型支持时该字段即可启用**，本次不做特殊处理 | 各样本实测恒 0（§5.6），与上游 C1 / C14 一致 |
