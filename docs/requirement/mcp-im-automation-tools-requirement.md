# IM 与自动化链路开放 MCP 工具需求

- 版本：v1.0
- 日期：2026-10-10
- 状态：需求草案，待开发评审
- 适用链路：飞书、微信远程会话，以及实际使用 `automation` lane 的管家和自动化任务

## 1. 背景与问题

用户已在桌面配置并启用 MCP 服务及工具，但从 IM 发起相同指令时，Agent 无法发现或调用这些工具，导致查询外部资料、处理业务数据等任务无法完成。自动化任务存在相同的能力缺口。

代码核查结果：

| 位置 | 当前行为 | 影响 |
|---|---|---|
| `electron/runtime/invocationAssembler.ts` | 构建 MCP 快照时传入 `remoteContext: materialsLane !== 'desktop'` | IM 和 automation 均被排除 |
| `electron/mcp/mcpToolRegistry.ts` | `mayBuildMcpToolSnapshot` 和快照构建逻辑拒绝 remoteContext | 即使配置已启用，也无法进入模型工具集合 |
| `electron/mcp/hostedMcpRegistry.ts` | 执行注册表按本回合快照注册 MCP executor | 空快照使执行入口同时缺失 |
| `src/shared/policy/defaultRules.ts` | MCP 默认走 `mcp-tool-ask`；只读注解自动放行仅限 desktop | 开放工具后仍需正确接入对应链路审批 |
| `electron/confirmation/approvalAgent.ts` | 审批 Agent 同样使用 automation，但声明封闭只读工具白名单 | 不能仅按 automation lane 一律开放 |

以上是当前代码行为；历史需求或测试中的审批描述不能直接视为当前生产配置。实施时应检查实际回答者解析与有效策略。

## 2. 目标与范围

### 2.1 目标

1. 飞书、微信和普通自动化任务可以发现、加载并调用用户已启用的 MCP 工具。
2. 使用同一套 MCP 配置、工具映射、延迟加载、连接管理及结果适配机制，无需重复配置服务。
3. 保留各链路现有身份校验、权限策略、审批、取消和审计能力。
4. 用户能区分工具未启用、不可用、待授权、被拒绝和执行失败，不再将所有问题表述为“不支持 MCP”。

成功标准：同一已启用工具，在桌面、飞书、微信和普通 automation 回合中均可发现；满足该链路授权条件后可真实执行并返回结果。

### 2.2 范围

| 纳入 | 不纳入 |
|---|---|
| 已配置且已启用的 MCP 服务工具 | 新建 MCP 协议或独立配置存储 |
| 普通 IM 与自动化业务 Agent 的 MCP 工具开放 | 安全审核 Agent 的工具策略调整：策略保持不变，依旧不注入 MCP 工具 |
| IM 与普通 automation 的发现、执行、审批、回传 | 群聊开放、第三方用户身份授权 |
| 延迟加载与直接加载两种模式 | MCP resources/prompts 的新增产品能力 |
| 链路及嵌套调用隔离、执行前复检 | 修改既有 locked 禁止规则 |
| 服务故障诊断与历史记录 | 无人值守自动发起交互式 OAuth 登录 |

本需求开放的是 MCP 工具能力，不自动授予全部工具的无确认执行权。MCP 服务管理能力（如 `action.mcp.add`）保持自身既有策略，不因本次开放而扩大权限。

## 3. 用户场景

| 场景 | 用户指令示例 | 预期 |
|---|---|---|
| 飞书查询 | “通过已配置的知识库服务查询上周发布记录” | 找到相关 MCP 工具，审批通过后查询并回复摘要 |
| 微信业务操作 | “使用项目服务新建一条待办” | 展示或交由现有审批机制判断精确操作，获准后执行并回传标识 |
| 定时汇总 | “每天汇总服务中的未完成事项” | 每次任务重新读取有效配置，经 automation 策略判断后执行 |
| 自动化写操作 | “按任务条件更新业务记录” | 使用 automation 回答者和策略；判不准或审批不可用时不执行，记录阻塞原因 |
| 服务不可用 | 服务停用、凭据失效或工具被移除 | 明确告知原因及恢复入口，不伪造执行成功 |

## 4. 功能需求

### FR-01 统一准入与工具快照

- 对 `desktop`、`feishu`、`wechat`、普通 `automation` 构建请求级 MCP 快照，取消“非桌面即排除”的统一限制。
- 工具准入集合为：已启用服务 ∩ 用户已启用工具 ∩ 当前调用工具裁剪上界 ∩ 链路有效暴露策略 ∩ 可解析执行器 ∩ 工具预算。
- 未启用服务、未勾选工具、服务新发现但未经启用的工具不得自动进入集合。
- 延迟索引、搜索结果、完整 schema 和执行注册表必须来自同一准入快照。延迟模式允许先只展示索引，但不能搜索出被禁止的工具。
- 不通过伪装成 desktop lane 获取 MCP；真实 lane 必须贯穿审批、审计与执行。
- 没有数据库或有效配置时使用空集合并提供可解释诊断，不扫描其他用户配置。

### FR-02 工具发现与延迟加载

- 复用现有 `mcpDeferredLoading`、schema 预算、映射名称、搜索与降级规则，不为 IM 单独复制实现。
- `off`、`auto`、`always` 模式均须在三类新增链路可用；具体阈值和上限沿用现有配置。
- 工具描述应包含服务来源及用途，模型能选择相关工具；不向模型暴露凭据、环境变量值或认证头。
- 搜索不到时区分未启用、权限过滤、预算裁剪、缓存缺失或执行器不可解析；用户回复可合并为简短原因和操作建议。
- 服务工具刷新后从新回合生效；当前回合不得悄悄引入新工具或新 schema。

### FR-03 执行与实时复检

- 使用现有 typed registry、MCP executor、连接管理和结果适配器；禁止新增绕过工具执行协调器的直接调用通道。
- 模型伪造、历史遗留或其他请求的映射名称，无法调用本回合未准入的工具。
- 真正派发前复检服务及工具启用状态、当前身份授权、有效策略、取消状态和工具/schema 版本。工具移除或 schema 变化时终止该调用，提示重新发起。
- 服务 endpoint、认证配置或命令发生变化后，旧授权不得用于新连接；需重新装配和审批。
- 断开连接、token 失效、超时和服务端错误返回结构化失败，不影响无依赖的其他工具；依赖失败结果的步骤不得继续写操作。

### FR-04 IM 审批与身份绑定

- 复用飞书、微信当前有效的确认回答者和同步/异步出口，不新增 MCP 专用审批体系。
- `mcp-tool` 信号进入现有策略引擎；桌面的 `mcp-readonly-allow` 不直接扩展到 IM。服务端 `readOnlyHint` 不能独立成为远程授权依据。
- 需要用户处理时通知应包含服务名称、操作用途、脱敏参数摘要、风险原因和可操作入口，避免只显示映射名。
- 已启用异步审批的环境复用其待办、精确调用绑定、追认及撤销机制；未启用的环境保留现有同步确认，不声称支持异步恢复。
- 异步记录必须能定位原服务、原工具、原参数和原 schema/配置版本。追认后复检通过才执行，不由模型重新生成参数。
- 关闭渠道、解绑或换绑 owner、授权失效、取消任务后，未派发的旧调用不得执行；群聊及非 owner 继续沿用既有拒绝行为。

### FR-05 普通自动化审批

- 管家和其他实际使用 automation 的业务任务可获得 MCP 工具；任务入口需明确声明真实 lane 及调用用途。
- MCP 调用沿用 automation 有效策略及回答者。需要审批的调用交由现有审批 Agent 判断，不挂无人可答的桌面确认卡。
- 审批拒绝、判不准、超时或审批服务不可用时，按 automation 现有失败出口处理：不执行，记录具体原因并按任务通知规则汇报。
- 首版不自动套用桌面历史信任、IM 会话授权或新的永久白名单；允许现有合法的 automation 作用域规则生效。
- 每次定时触发构建新快照，不复用上次任务的授权结果。任务重试不能自动重放结果未知的写调用。
- 本次不解除 automation 对 Shell、本地写入等工具的既有 locked 禁止规则。

### FR-06 审批及嵌套调用隔离

- 使用 automation 的审批 Agent 仍只有 `APPROVAL_READONLY_TOOLS`，其 MCP 索引、搜索结果、schema 和执行注册表均为空。
- 工具裁剪在内置工具和 MCP 上统一生效；不能只裁剪内置工具，然后追加完整 MCP 集合。
- 子调用允许工具集合不得超过父调用和自身白名单的交集；审批递归豁免不能被解释为 MCP 执行授权。
- 调用用途和隔离约束应由可信宿主材料决定，不能依赖模型文本或工具描述自报。

### FR-07 结果、进度与产物

- 文本和结构化结果进入既有工具历史，保留服务来源、原始/映射工具名、状态、耗时及脱敏摘要。
- IM 回传面向用户的摘要；大结果、图片及文件复用既有 MCP 产物安全与渠道附件能力，适配失败时说明可在桌面查看，不泄露本地绝对路径或原始资源 URI。
- 自动化结果关联任务和该次运行，支持排查成功、部分成功、失败和待处理状态。
- 工具返回内容视为外部数据，不能直接修改策略、触发其他操作或变成可信用户授权。
- 工具执行与把结果发往外部渠道是两个授权边界；沿用既有出站审查，工具成功不代表可无条件转发全部内容。

### FR-08 取消、并发与诊断

- 复用当前 MCP 超时、并发限制、取消信号及连接释放机制；多个链路同时执行不能绕过宿主共享限流。
- 停止回合或取消任务后禁止后续派发。已派发的操作按真实结果报告；无法确认是否成功时记录“结果未知”，不得自动重试写操作。
- 日志关联 lane、request/turn/session、任务运行标识（适用时）、serverId、工具名及审批/执行结果。
- 禁止记录 token、认证头、环境变量值及完整敏感参数或结果；用户通知和模型错误同样脱敏。
- 凭据失效时提示到设置完成授权，不在无人值守任务中无限弹窗或反复登录。

## 5. 配置、兼容与需求衔接

- 首版复用现有服务和工具启用配置，不新增重复的 IM/automation MCP 配置列表，也不增加每链路启用开关。各链路差异由有效策略和调用裁剪表达。
- 升级后已启用工具进入新增链路的候选集合；既有服务停用、工具未启用及 locked 规则保持有效。发布说明须告知能力范围扩展和审批行为。
- 不默认调整 `mcp-tool-ask` 或扩大只读注解免确认范围；未来调整需另行定义策略及验收。
- 本需求生效后，替代 [MCP 接入需求](mcp-integration-requirement.md) 中“远程会话不注入”的范围限制和对应验收项；该文档其他凭据、协议、预算和产物要求继续适用。实施时同步修订旧条款和测试，避免规范冲突。
- 升级说明：已启用的 MCP 工具现可在飞书、微信和普通 automation 业务回合中被发现；每次调用仍按真实 lane 策略审批，并在派发前复检配置。MCP 管理能力、审批 Agent 与 locked 规则不扩权。
- IM 异步授权依赖 [IM 异步审批安全需求](remote-im-async-approval-security-requirement.md) 的已实现能力，不将其中未落地功能视为本次开放的前提事实。
- 工具暴露与执行继续遵循 [运行时准入需求](agent-runtime-admission-policy-requirement.md) 的统一契约。

## 6. 异常处理

| 情况 | 处理 |
|---|---|
| 未配置/未启用 MCP | 不注入，提示在设置中配置并启用 |
| 工具因策略或调用白名单排除 | 不展示、不搜索、不执行，说明权限限制 |
| 工具超过预算 | 按原有预算/延迟策略处理，保留裁剪原因 |
| 审批等待/异步挂起 | 零副作用，按真实链路状态汇报 |
| 服务/工具在审批后停用 | 派发前阻断，旧批准不得恢复启用状态 |
| schema 或连接配置变化 | 原调用失效，重新发起及审批 |
| 凭据过期/服务断线 | 返回脱敏诊断与恢复入口 |
| 写调用超时且结果未知 | 不自动重放，提示核实外部系统 |
| IM 结果发送失败 | 区分工具执行结果与投递失败，不能因补发消息重复调用工具 |

## 7. 验收标准

以下为发布必验项；涉及审批的用例须断言执行器调用次数，不能仅检查提示文案。

| 编号 | 场景 | 预期 |
|---|---|---|
| AC-01 | 同一工具分别从 desktop、feishu、wechat、普通 automation 发起 | 均可发现，审批允许后真实执行一次 |
| AC-02 | 服务停用、工具未勾选、服务新增工具 | 三类新增链路均不注入、不搜索、不执行 |
| AC-03 | `off/auto/always` 及 schema 预算边界 | 索引、搜索、schema 和执行注册表符合相同准入集合 |
| AC-04 | 有意伪造映射名或调用其他回合工具 | 拒绝，执行器调用次数为零 |
| AC-05 | 工具裁剪仅允许内置只读工具 | 所有 MCP 暴露和执行入口为空 |
| AC-06 | 审批 Agent 运行于 automation | 保持封闭只读集，无 MCP 工具，无审批递归 |
| AC-07 | MCP 声明只读，但 IM/automation 无合法放行规则 | 进入对应链路审批，不继承桌面只读豁免 |
| AC-08 | IM 同步批准/拒绝/超时 | 按既有出口处理；只有批准的精确调用执行 |
| AC-09 | 已启用 IM 异步：挂起、追认、重复追认 | 挂起零副作用，合法追认至多执行一次 |
| AC-10 | IM 换绑、撤销、关闭渠道及取消发生在派发前 | 旧调用不能执行 |
| AC-11 | automation 审批允许/拒绝/判不准/不可用 | 仅允许分支执行，其余有原因且不挂桌面确认卡 |
| AC-12 | 桌面/IM 信任缓存与新 automation 调用 | 不跨链路扩大授权；有效 automation 规则正常生效 |
| AC-13 | 审批后工具停用、移除或 schema/endpoint 变化 | 复检阻断，不使用旧授权派发 |
| AC-14 | 多链路并发、停止任务、超时 | 限流和取消有效，停止后无后续派发 |
| AC-15 | 写操作结果未知、IM 投递失败、任务重试 | 不自动重复写操作，不将投递失败视为执行失败 |
| AC-16 | 图片、文件、大结果及恶意工具输出 | 沿用安全适配；不越权执行或泄露凭据和路径 |
| AC-17 | 任务多次定时触发、应用重启后运行 | 新回合读取当前配置和策略，不继承旧审批结果 |
| AC-18 | 桌面 MCP、IM 内置工具及普通 automation 回归 | 原有工具预算、策略、历史、取消和产物行为正常 |

建议验证：先运行快照装配、延迟加载、执行注册表、审批隔离及新增链路端到端测试，再执行 `npm test`、`npm run typecheck:shared`、`npm run typecheck:renderer`；涉及界面文案时执行 `npm run i18n:check`。跨层契约变更补充 typeTests。

## 8. 实施拆分与交付要求

1. **准入装配**：将 MCP 准入从 remoteContext 二元判断改为真实 lane 与可信调用约束；统一应用工具裁剪，保证审批 Agent 无 MCP。
2. **执行闭环**：接入既有注册表和 executor，补齐派发前配置/schema/授权复检及取消竞态。
3. **链路适配**：验证飞书、微信和普通 automation 的审批出口、任务状态及结果回传；保持同步/异步实际能力一致。
4. **验证与文档**：完成验收矩阵，修订旧禁止注入条款和断言，提供用户可理解的升级说明。

前三项不能单独作为“已开放”发布：只有发现、执行、审批隔离和结果反馈形成闭环，并通过关键验收后才交付。

开发评审需落实：所有普通 automation 驱动入口清单、当前回答者解析路径、配置/schema 版本的稳定比较方式，以及 MCP 外部写操作可验证的端到端测试夹具。这些实现选择不能改变本文的默认授权和隔离边界。
