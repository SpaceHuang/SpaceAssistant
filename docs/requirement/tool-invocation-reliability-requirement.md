## 1. 概述

### 1.1 背景

本需求来自一次真实 Agent 会话的工具调用全量复盘。该会话共产生 218 次工具调用，其中 13 次返回失败或未执行状态。逐条归因后发现：**绝大多数失败并非模型误用工具，而是工具层与安全审批层的实现缺陷所致**，且其中一部分缺陷会向模型输出错误事实，进而污染最终结论。

本次复盘暴露的问题集中在四类：

| 类别 | 说明 |
|------|------|
| **判定基准不一致** | 同一路径在"能力自述""执行器实际行为""安全审批"三处得到不同结论 |
| **决策信息不完整** | 审批载荷、拒绝文案、错误分类缺失关键上下文，模型无法自纠 |
| **结果语义不可信** | 成功被标记为失败；被静默跳过的搜索被表述为"无匹配" |
| **缺少降级路径** | 无法解析的合法命令被直接拒绝，没有确认或受限执行通道 |

### 1.2 产品价值

| 价值 | 说明 |
|------|------|
| 任务完成率 | 消除"合法操作被误拦"与"入口参数丢失导致的误拒"，降低无效重试 |
| 结论可靠性 | 杜绝"未搜索即报告无匹配""成功却标记失败"导致的错误结论与错误自诊断 |
| 可自纠性 | 失败信息携带判定依据，Agent 能在一次调用内修正，而不是靠猜测 |
| 安全可信度 | 安全策略拒绝必须"理由成立"，避免因误拦削弱用户对安全机制的信任 |
| 可观测性 | 成功/失败的记录语义一致，审计与问题定位不再依赖人工推断 |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **单一事实源** | "工作目录""是否执行""是否成功"必须有唯一权威判定，所有层引用同一结果 |
| **拒绝可解释** | 任何拒绝都要回答三个问题：依据什么规则、基于什么输入、建议怎么做 |
| **失败不等于危险** | 解析失败、信息不足应降级为确认或受限执行，而非等价于高风险 |
| **不撒谎的返回值** | 结果信封的字段不得互相矛盾；"未搜索"不得表述为"无匹配" |
| **降级优先于拒绝** | 在安全边界内，优先提供可执行的替代路径，而非直接终止 |

### 1.4 术语

| 术语 | 含义 |
|------|------|
| 工作目录（workDir） | 当前会话绑定的根目录，文件类工具与 Shell 的执行基准 |
| 安全审批 / 机审 | 在工具真正执行前对调用动作做风险判定并给出放行、拒绝或询问结论的环节 |
| 线索包 | 送入安全审批的结构化调用描述（工具名、动作类别、入参等） |
| 结果信封 | 工具返回给上层的统一结构，含 `success`、`error`、`notExecuted`、`data` 等字段 |
| 假阴性 | 实际存在结果但被报告为"无匹配/不存在"的情况 |

## 3. 问题详情

### R1 工作目录判定基准不统一

**优先级：P0**

#### 问题表现

同一次会话、同一个目标路径，系统不同环节给出了互相矛盾的判定：

| 环节 | 判定 | 实际后果 |
|------|------|----------|
| 能力自述（环境查询） | 工作目录 = 会话根目录 | 作为"事实"返回给模型 |
| Shell 执行器 | 实际 cwd = 会话根目录（`cd` 相对路径可正常进入子目录） | 命令行为与自述一致 |
| 写入类工具 | 判定"在工作目录内"，自动放行、无需确认，文件真实落盘 | 与自述一致 |
| 安全审批 | 判定"在工作目录**外**" | 直接拒绝 |

即：**产品自述的、执行器实际使用的、写入工具自动放行所依据的，都指向同一目录；唯独安全审批使用了另一个基准。**

更严重的后果是信息缺失引发的错误自诊断：模型在被拒后写下"说明当前会话工作目录不是该目录"，并据此改变了后续策略——它没有拿到反驳这一推断的任何信息。

#### 问题根因

1. **路径判定分散在多条互不引用的代码链路中**：写入/读取路径解析、写入工具自动放行判定、Shell 路径分析与审批各自独立计算"是否在工作目录内"，没有共享同一个基准来源。
2. **审批侧的基准来源与对外自述不一致**：能力集合返回的工作目录与审批使用的基准不是同一份数据（可能来自不同的配置读取时机、不同的绑定关系或不同的规范化方式）。
3. **缺少一致性约束**：没有任何机制（测试或运行时断言）要求"自述基准 == 执行基准 == 审批基准"。
4. **写入路径与 Shell 路径采用了不同的判定语义**（本需求不改两者策略，但要求两者引用同一基准）。

#### 预期修复后的效果标准

- [ ] 存在唯一的"会话工作目录"事实源，环境自述、文件类工具、Shell 执行器、安全审批**全部引用同一份数据**，不再各自计算。
- [ ] 对同一路径，四个环节的"是否在工作目录内"判定结果**一致性 100%**，包含以下边界：工作目录根自身、根下新建目录、根下隐藏目录、以绝对路径与相对路径两种写法表达的同一目标、含符号链接的路径。
- [ ] 新增回归测试：在工作目录根下创建一个临时目录并通过 Shell 与写入工具分别操作，断言审批结论与执行结果一致（不得出现"一处放行、一处拒绝"）。
- [ ] 移除任何"审批基准来自另一处配置"的隐式依赖；若工作目录在会话中发生切换，审批基准必须在同一次写入中跟随更新。
- [ ] 环境自述返回的路径与审批实际使用的路径，在规范化（分隔符、大小写、末尾分隔符）后逐字相等。

### R2 拒绝与失败文案不携带判定依据

**优先级：P0**

#### 问题表现

安全拒绝的返回文案只给出结论性描述（如"在工作目录外创建目录"），不包含：

- 判定所依据的工作目录基准是什么；
- 被拒绝的目标路径经解析后的绝对结果是什么；
- 命中的是哪条规则（越界写入、隐藏目录、任务相关性不足、信息不足……）；
- 什么改动可以让该动作通过。

结果是 Agent 只能猜测被拒原因，并给出了**错误的猜测**（把"审批基准错误"猜测为"工作目录不是该目录"），随后又尝试了两次无效的替代方案，浪费了多轮调用与用户等待时间。

#### 问题根因

1. **拒绝消息由审批侧通用模板生成**，模板中不包含基准、解析结果与规则标识等结构化字段。
2. **审批结论未回传结构化诊断**：仅返回自然语言 + 机器可读的拒绝原因枚举，缺少"计算过程"字段供上层组织文案。
3. **"信息不足"类拒绝与"严格禁止"类拒绝共用同一文案结构**，模型无法区分"补信息即可通过"与"无论怎样都不允许"。

#### 预期修复后的效果标准

- [ ] 所有拒绝结果都携带结构化诊断字段，至少包含：命中规则 ID、判定基准（规范化后的工作目录）、解析后的目标绝对路径、阈值或约束参数、建议的替代动作。
- [ ] 用户可见文案在结构化字段基础上生成，并明确区分三类拒绝：
  - **严格禁止**：无论上下文如何都不允许（如提权、磁盘格式化的代码路径）；
  - **条件不足**：补充目标路径、用途说明或改为受信方式后可放行；
  - **越界**：目标超出当前工作目录范围，文案必须写明基准目录。
- [ ] 收到"条件不足"类拒绝后，Agent 仅通过**补充入参或说明**即可重试成功，无需尝试绕行方案（需在验收用例中以"补信息后重试即通过"验证）。
- [ ] 拒绝文案中不得出现可能泄露本机环境敏感信息的路径片段（如用户主目录下的凭据目录展开结果），但必须包含与工作目录相关的基准信息。
- [ ] 拒绝事件被完整写入审计记录，包含规则 ID、基准、目标路径与决策结论，便于事后复盘。

### R3 外部工具调用入参未进入安全审批载荷

**优先级：P0**

#### 问题表现

两次外部（MCP）网络抓取调用带有完整、明确的入参（目标 URL 与返回长度上限），但审批返回的拒绝理由却是：

> "线索包仅有工具名与 mcp-tool 信号，动作内容、目标 URL/路径、参数**全部缺失**，无法解析实际外发目标与数据范围。"

另有同类拒绝把动作类别描述为 `write`（实际为只读抓取），并再次声称"未给出命令、URL、目标路径或涉及文件"。

**参数明明存在，审批却认为参数不存在。** 后果：

1. 一次完全正当的公开只读抓取被误判为"信息不足"而拒绝；
2. Agent 按提示"补充完整调用参数"也无意义——参数根本没有进入审批载荷，补什么都不会改变结论；
3. 动作类别被错误归类为写操作，会进一步推高其风险评级。

#### 问题根因

1. **审批线索包的构造未包含外部工具的实际参数**：线索包只携带工具名与类别信号，未透传 `args`（至少 url / path / 命令原文）。
2. **工具类别映射不准确**：抓取类工具被映射成写类别，导致风险评级与实际行为不符。
3. **"缺失"与"被丢弃"未做区分**：审批侧将"载荷里没有该字段"直接表述为"调用参数缺失"，掩盖了载荷构造缺陷。
4. **未提供补充信息的有效通道**：拒绝文案引导 Agent 补参数，但通道上参数不会被传递。

#### 预期修复后的效果标准

- [ ] 审批载荷包含外部工具调用的关键入参：工具名、动作类别、目标 URL 或路径、请求方法（可判定时）、参数摘要；对超长入参做截断并标注截断。
- [ ] 工具类别映射与真实动作一致：只读抓取不得被归为写操作；判定依据必须在载荷中可追溯。
- [ ] 只读、指向公开地址的抓取类调用，在满足既定可信域名/白名单策略时**不再因"参数缺失"被拒**；确需拒绝时，理由必须指向真实命中的规则。
- [ ] 若确因策略拒绝，Agent 通过补充说明（如用途、来源）可重试成功；该路径需有验收用例覆盖。
- [ ] 审批日志中记录类别映射结果与实际传入的参数字段名（值可脱敏），用于排查映射错误。
- [ ] 线索包构造具备完整性校验：当某类工具未携带其必需参数时，记录"载荷构造不完整"告警，而不是对外表述为"调用参数缺失"。

### R4 工具结果信封的成功/失败语义自相矛盾

**优先级：P0**

#### 问题表现

被复盘会话中有 3 次 Shell 调用，其结果为：

| 字段 | 值 |
|------|-----|
| `success` | `true` |
| `error` | `TOOL_EXECUTION_FAILED` |
| `data.exitCode` | `0` |
| `data.status` | `succeeded` |
| `data.terminationReason` | `process_exit` |
| `data.outputTrust` | `ok` |
| `data.truncated` | `false` |

即**命令确实执行成功并返回了正确输出，却在同一个信封里被标记为执行失败**。这三条恰好承载了本次调研最关键的环境事实，却被呈现为失败态。

该现象在本次复盘过程中被现场复现：分析用的脚本类调用连续多次返回 `success` 缺失/为真 与 `error: TOOL_EXECUTION_FAILED` 并存、同时 `exitCode: 0`、`status: succeeded` 的矛盾组合。

危害有三层：

1. **模型侧**：不可靠的失败信号会诱导模型怀疑已获得的正确事实、重跑命令或改用次优手段；
2. **用户侧**：界面展示错误的失败态，用户对产品可靠性产生怀疑；
3. **审计侧**：无法用该字段做失败率统计，依赖人工逐条判断。

#### 问题根因

1. **结果信封由多层拼装**：执行器结果、输出解码与信任度评估、上层包装各写一部分字段，缺少统一的构造出口与不变量校验。
2. **两个"成功"来源被混用**：既有执行成败（`exitCode`），又有包装层/传输层的成败（`error` 字段），后者在字段缺失或分支遗漏时被填入了默认的失败码。
3. **无契约约束**：没有定义"`exitCode === 0` 且进程正常退出 ⇒ 信封不得携带失败态"这类不变量。
4. **缺少全量一致性校验**：历史事件流中此类矛盾组合从未被批量检出（本次复盘依靠脚本统计才暴露）。

#### 预期修复后的效果标准

- [ ] 定义并文档化结果信封不变量，至少包括：
  - `success === true` ⇒ `error` 必须为空或不存在；
  - `exitCode === 0` 且 `terminationReason === 'process_exit'` ⇒ 不得标记为执行失败；
  - `notExecuted === true` ⇒ 必须给出 `notExecutedReason`，且 `success === false`；
  - 信封中不得同时出现互相矛盾的"成功/失败"信号组合。
- [ ] 信封改为单一构造出口，所有工具结果经统一校验后再返回；校验失败时记录内部告警日志而非产出矛盾信封。
- [ ] 失败码细分：至少区分"执行失败（非零退出码）""执行器异常""策略未执行""用户取消""参数非法"五类，不再使用同一个笼统码覆盖全部情形。
- [ ] 对历史事件流执行一次全量一致性扫描并出具报告；扫描发现的矛盾组合数量在修复后为 **0**（历史数据可保留但需标注）。
- [ ] 界面展示的成功/失败态与 `exitCode`、`status` 一致；已成功执行的任务不得向用户展示失败标记。
- [ ] 新增单元测试：对"退出码 0 + 正常终止"用例断言信封中不存在 `error`；对"非零退出码""超时""被策略拒绝"分别断言其失败码与 `notExecuted` 取值。

### R5 命令语法解析失败直接拒绝、无降级路径

**优先级：P1**

#### 问题表现

两条**合法且只读**的命令被拒绝，理由为：

> "命令语法解析失败，无法进行安全分析"

被拒命令的特征：

- 使用宿主平台主流 Shell 的控制结构（条件判断、分支）与管道到输出格式化命令；
- 只做目录存在性检查、列目录、输出拼接，不含任何写操作或删除操作；
- 命令用途已在调用参数中的用途说明字段写明。

拒绝类型为策略拒绝（未执行），且产品同时提供了"信任列表""拆分为低风险只读步骤"等建议，但因为解析器连命令都没解析成功，这些通道无法被有效使用。结果是任务在关键验证步骤被迫中断。

#### 问题根因

1. **解析覆盖不足**：命令解析器面向简单命令设计（识别引用、基本分段），对平台特定 Shell 的控制结构体（条件块、管道到格式化命令、内联脚本）无法建模。
2. **`无法分析` 被等价于 `不安全`**：解析失败直接映射为策略拒绝，缺少"降级为询问用户""降级为受限执行""仅允许只读子集"等中间态。
3. **缺少解析能力的可观测信号**：模型与用户都无法区分"这条命令真的危险"与"解析器不认识这条命令"。
4. **元语法处理策略过严**：凡含管道、通配符等元语法的命令一律不可进入信任路径，进一步放大了无法执行的场景。
5. **审批层的输出合同是两态，没有"判不了"这个说法**：安全审批只有"允许 / 拒绝"，遇到事实链不完整的命令只能输出拒绝；而既有规定「审批拒绝的结论不可回退为人工确认」，于是"解析器读不懂"这一情况在审批层**进得去、出不来**。（v1.1 补充）

#### 预期修复后的效果标准

> **v1.1 修订说明**：本节原表述为「解析失败一律降级到确认流程（由用户决定）」。该表述忽略了既有的安全审批环节——**审批本身就能读懂相当一部分"解析器读不懂"的命令**，一律转人工会白打扰用户。修订后沿用既有机制的正向推广：**先由审批判定，判定不了才转人工**（判据与既有的"拿不到裁决 → 交给人"同源）。

- [ ] 解析失败不再直接拒绝；解析结论与安全结论解耦，至少支持三种：**可分析且安全**、**可分析且危险**（按既有规则处理）、**无法分析**。
- [ ] 「无法分析」的命令**沿用既有安全审批流程**（不为其新开通道）：审批能判定时按其结论执行或拒绝，用户无感。
- [ ] 审批**判定不了**（事实链不完整）时，**降级为人工确认**，并在文案中标明"该命令使用了当前解析器不支持的结构"。
- [ ] 审批给出**拒绝**的结论时**仍不可回退为人工**（既有规则不变，防止"被拒就问人"形成绕过）。
- [ ] **无人值守链路（automation）维持拒绝**（v1.3 用户决策）：该链路无人类兜底，「无法分析」的命令**不得由审批 Agent 放行**；与现状一致，不构成新增限制。
- [ ] 扩展解析器覆盖平台主流 Shell 的常见只读结构：条件块、管道到列目录/格式化命令、`;` 与 `&&` 组合、变量拼接的路径。覆盖不到时不误判为危险。
- [ ] 对"无法分析"且审批判定不了的调用，允许用户在一次确认后执行，并记录决策来源（用户确认 / 信任列表 / 规则放行）。
- [ ] 拒绝文案明确区分"语法不支持（可确认执行）"与"命中危险规则（不可执行）"，不得共用同一句话。
- [ ] 新增测试用例：至少覆盖 5 条含条件块与管道的只读命令，断言其**不因"解析器不支持"被拒绝**。三种结果都算通过：审批判安全（直接执行）、审批判危险（如实拒绝）、审批判定不了（降级人工确认）；**唯一失败**是被拒绝且原因是"结构不支持"。另设一组用例，将审批置为"无法判定"，断言落到人工确认。

### R6 文本搜索结构性排除目录且不告知

**优先级：P1（危害最高）**

#### 问题表现

被复盘会话的 90 次文本搜索调用中，有 7 次返回 `No matches found`。其中 3 次的搜索目标是**被工具硬编码排除的目录**（依赖安装目录、构建产物目录）：

| 场景 | 模型显式指定的目标 | 返回 |
|------|--------------------|------|
| 搜索发布产物中的语法特性 | 依赖安装目录下的第三方包 `dist` 子目录 | `No matches found` |
| 搜索各依赖声明的运行时版本要求 | 依赖安装目录 | `No matches found` |
| 搜索某工具函数实现 | 第三方包内的具体产物文件 | `No matches found` |

关键危害不在"搜不到"，而在**返回的句式是"我搜过了，没有"**，而非"该路径已被跳过，未搜索"。模型据此在会话结论中写下"已扫描全部产物：**没有**该用法"——**这个"没有"很可能是假的**。模型最终只能靠"搜索工具会遵守忽略规则"这类自行推断才勉强察觉异常。

此外，因构建产物目录同样在排除名单内，"审阅构建产物"这类合法需求在工具层面被直接禁用，且没有开关可以绕开。

#### 问题根因

1. **排除名单在代码中硬编码**，包含依赖目录、版本控制目录、缓存目录、构建产物目录等，且**没有任何参数可以关闭**该行为。
2. **排除逻辑无条件生效**：即使调用方显式指定了被排除目录内的具体路径（甚至具体文件），仍被追加排除规则，导致"显式请求"被静默否决。
3. **结果文案不区分"无匹配"与"未搜索"**：搜索被完全跳过时仍返回统一的"无匹配"文案。
4. **缺少遗漏量反馈**：结果中不体现"本次跳过了哪些目录、多少个文件"。

#### 预期修复后的效果标准

- [ ] 搜索结果为"无匹配"时，必须同时说明**实际搜索范围**：是否发生了目录跳过、跳过目录名、以及被跳过是否可能影响结论。
- [ ] 当调用方**显式指定**的路径位于默认排除目录内时，默认尊重调用方意图执行搜索；如需保留排除，必须返回明确的"已跳过"提示，不得返回"无匹配"。
- [ ] 提供显式通道用于搜索排除目录（如"包含被忽略目录"开关），并在工具说明中公开该行为与默认值。
- [ ] "无匹配"与"因排除未搜索"在返回值结构上可区分（不同字段或不同状态值），模型无需依赖猜测。
- [ ] 返回结果包含遗漏量统计：跳过目录数、是否有目录被跳过。
- [ ] 新增测试用例：在排除目录内放置已知内容并分别以"默认搜索""显式路径搜索""开启包含开关"三种方式搜索，断言结果符合上述语义，且不存在"实际存在却返回无匹配"的情况。
- [ ] 工具说明中明确列出默认排除的目录类别，使用户与模型在调用前即可预期搜索范围。

### R7 工具参数校验把等价默认值判为非法

**优先级：P2**

#### 问题表现

一次搜索调用同时传入按文件计数输出模式、以及"上下文行数为 0"。结果返回：

> "上下文行数、多行、显示行号 仅适用于按内容输出模式"

而"上下文行数 = 0"在语义上等价于"不传该参数"，却被判为非法参数。该次调用被完整浪费，需要改用另一参数组合重试。

同类风险还包括：显式传入与默认值相同的布尔参数（如"多行 = false"、"显示行号 = true"）时，是否也会被同样判错，当前行为不明确。

#### 问题根因

1. **参数校验按"字段是否出现"判定，而非按"字段取值是否产生实际效果"判定**：只要出现了仅适用于某模式的字段名，即报错，未考虑取值等价于未传的情形。
2. **校验逻辑与执行逻辑不一致**：执行路径本身是宽容的（仅当上下文行数大于 0 才生效），校验层却更严格，两层对同一输入给出不同判断。
3. **错误文案未给出合法取值**：只说明"不适用"，未说明"改用哪种写法可以通过"。

#### 预期修复后的效果标准

- [ ] 与默认值等价的显式传参**不得报错**：上下文行数 = 0、多行 = false、显示行号 = true 与不传该字段的行为一致。
- [ ] 仅当"字段取值会产生实际效果"且"与当前输出模式冲突"时，才返回参数错误。
- [ ] 参数校验与执行路径共享同一份判定规则（单一事实源），不得出现校验通过而执行忽略、或校验拒绝而执行本可处理的情况。
- [ ] 参数错误文案必须给出可执行的修正方式：指明冲突字段、当前模式、以及允许的参数组合。
- [ ] 新增单元测试：对"计数模式 + 上下文行数 0""仅匹配文件模式 + 显示行号默认值"等组合断言调用成功。

### R8 文件列表工具错误信息不区分原因

**优先级：P2**

#### 问题表现

两次目录列表调用分别针对：(a) 未构建、确实不存在的产物目录；(b) 未安装的依赖作用域目录。两者返回同一句文案：

> "不是目录或无法访问"

这一文案对"路径不存在""路径是文件而非目录""无读取权限""读取超时"四种情况不做区分。影响：

- 模型无法判断是"目标尚不存在（本就不该继续找）"还是"权限不足（可换路径）"，容易触发无意义的反复试探；
- 用户看到该提示时无法定位真实原因。

#### 问题根因

1. **多个异常分支共用同一句文案**：目录 stat 失败、类型不是目录、读取失败等分支返回了相同错误字符串。
2. **未将底层错误码映射到用户可理解的分类**。
3. **缺少后续建议**：错误信息未提示"是否应改为读取上级目录""是否需要先构建/安装"等下一步动作。

#### 预期修复后的效果标准

- [ ] 目录列表失败时返回可区分的错误分类，至少包含：**路径不存在**、**不是目录**、**无访问权限**、**读取超时**。
- [ ] 每类错误配有明确文案与建议动作（例如"该目录不存在，可先列出其上级目录确认结构"）。
- [ ] 结果信封中保留机器可读的错误分类字段，供上游组织文案与统计。
- [ ] 超时与其他错误不得共用同一文案（超时应提示可重试）。
- [ ] 新增单元测试：分别构造"不存在路径""指向文件的路径""无权限路径"三种输入，断言错误分类与文案各不相同。

## 7. 范围外既有缺口（待立项）

本节记录在 R6 评审核查过程中发现的**既有缺口**。它们与本需求同族（同一规则在不同环节结论不一致），但**属安全边界议题、且处置需产品决策**，因此**明确不在本需求范围**，单列待立项，避免在 R6 里顺手定掉安全语义。

### P-1 敏感路径判定的消费方不一致

**现状**：产品已声明「`.env` / `.env.*` / `secrets/` 是敏感路径」（`electron/shell/shellSensitivePaths.ts:60-61`，含内置前缀 `.ssh` / `.gnupg` / `C:\Windows` / `~/Library` / `/etc` / `userDataDir` 等），但该声明**只对部分工具生效**：

| 工具 | 是否消费 `isSensitivePath()` | 实际行为 |
|------|------------------------------|----------|
| `write_file` / `edit_file` | **是**（`writeFileAutoApproval.ts:26-27`） | 自动放行回落人工确认卡（需确认） |
| `run_shell` | **是**（`shellPathAnalysis.ts:124`、`bashSecurityRules.ts:127`、`psSecurityRules.ts:79`） | 路径违规 → 需确认 |
| `grep` | **否**（R6 落地后部分消费，仅作遍历排除） | 现状：rg 路径搜不到隐藏点文件（非因敏感规则）；walk 回退路径**能搜到** `.env` |
| `read_file` | **否**（只走 `resolveSafeReadPath` 越界防护） | **能读取** `.env` 等敏感文件 |
| `list_directory` | **否**（同上） | **能列出**敏感目录内容 |

**危害**：同一份「敏感路径」声明，在不同工具上给出不同结论 —— 写入被拦、shell 被拦、读取不被拦。这与 R1（工作目录基准不一致）同族，但**更早存在**，且属**安全边界**而非工具可靠性。

**为什么不在本需求范围**：处置需要决定「读取侧应硬拒还是需确认」，属产品决策；且按依赖分析，它触及 `read_file` / `list_directory` / `grep` 的既有可访问性，改动面与安全影响均超出「工具调用可靠性」这一主题。

**与 R6 的边界**：R6 只保证「搜索工具不再把『跳过』表述为『无匹配』」，并确保开启隐藏条目搜索时**不擅自放开敏感文件**；它**不主张、也不实现**「敏感路径在所有工具上一致」。P-1 若日后立项，其结论应作为 R6 敏感排除语义的上位依据。

### v1.3（2026-09-25）：无人值守链路维持拒绝（用户决策）

| 位置 | 改动 |

**决策来源**：**用户于 2026-09-25 明确拍板**。背景是技术方案评审 v1.5 的 N1 揭示了该方案此前的一处**错误断言** —— 「automation 的回答者解析为 deny、不咨询审批 Agent」。实际引擎实现为：automation 的 `ask` 回答者**恒为审批 Agent**（`askAnswererFor('automation') === 'agent'`），生产链路无条件注入审批通道工厂，**审批 approve 即放行执行**。若不加处理，R5 落地后「解析器读不懂」的命令在无人链路上可被审批 Agent 自主放行 —— 这是相对现状（解析失败即拒绝）的**真实行为放宽**。

**用户决策内容**：**不接受**该放宽。理由：常规命令解析器已提供结构化事实，审批 Agent 在事实基础上判断质量有保障；「无法分析」意味着**事实链完全缺失**，审批退化为「读文本猜危险」，而无人链路**没有人类可兜底** —— 故只能 fail-closed。这与「有人值守链路判定不了 → 转交人工」是同一条原则的两面。

**与 §4 非目标的关系**：本决策**维持现状**（今天是解析失败直接拒绝），**不新增任何限制**，与「本需求不降低任何既有安全规则」一致。

### v1.1（2026-09-25）：R5 降级路径对齐既有审批机制

| 位置 | 原文 | 修订后 |
|------|------|--------|
| §3 R5 问题根因 | 4 条 | 补第 5 条：审批层输出合同为两态、没有"判不了"，且"审批拒绝不可回退"，使"解析器读不懂"在审批层**进得去、出不来** |

| §3 R5 效果标准 | 测试断言「结论为降级确认」 | 断言「**不因解析器盲区被拒**」——三种结果都算通过（审批判安全→执行 / 判危险→如实拒绝 / 判定不了→降级人工确认）；**唯一失败**是被拒绝且原因是"结构不支持"。另加「审批无法判定 → 人工确认」专项用例 |
| §5.1 功能验收 | 2 条（进入确认流程 / 可通过确认执行） | 2 条（审批可判定按其结论执行 / 判定不了降级人工确认） |
| §5.3 测试验收 | 1 条 | 补充「不因解析器盲区被拒」口径 + 新增专项用例 |

**修订理由**：原表述把「解析失败」直接等同「必须问人」。但既有的安全审批（`desktop-fail-open-to-user-plan.md`）已具备判定能力，且已确立「拿不到裁决 → 交给人、拿到拒绝裁决 → 不交给人」的分工。R5 应作为该机制的正向推广（"判定不了 → 交给人"），而非另开一条绕过审批的通道——后者会把审批本可自行处理的命令也推给用户。**本修订不改变需求 §4 非目标**（不降低任何既有安全规则；审批「拒绝」的结论仍不可回退）。
