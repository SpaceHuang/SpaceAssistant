# 需求：自定义安全策略完整可配置

## 第 0 层：决策摘要

### 一句话

用户选择「自定义」套餐后，应能调整安全策略页列出的每一条策略规则，包括当前标为系统保护、锁定或只能启停的规则；应用不得以产品预设的风险判断为由，隐藏或拒绝用户对策略动作的修改。

### 为什么做

当安全策略或审批机制误判、出现缺陷，或不适用于用户掌握的实际环境时，用户目前可能无法在应用内调整触发该行为的规则，只能接受阻断或改用其他产品。开放自定义控制，让用户能自行判断风险、恢复工作，同时让产品的预设不再凌驾于用户明确选择之上。

不做的损失是用户遇到错误策略时没有有效的自助恢复路径，影响任务完成和对产品的信任。做了之后，用户可在单一设置页查找并调整具体规则，减少因策略不适配而放弃产品的情况。

### 决策项

| 决策 | 本需求取值 |
|---|---|
| 自定义套餐的覆盖范围 | 所有已展示的策略规则均可修改动作；锁定、系统保护、只读状态不构成例外。 |
| 规则动作范围 | 桌面每条规则均可选禁止、直接执行、人工批准、自动审核；微信和飞书每条规则均可选禁止、直接执行、人工批准。只有“自动审核”是链路级能力差异。逐次人工确认与普通人工批准在界面上统一呈现为“人工批准”，但规则说明须告知默认是否逐次打断。 |
| 用户选择的效力 | 用户选择直接执行或自动审核后，同一规则原有的逐次确认、真人必批或自动审核前置要求均不得继续阻断该操作。其他匹配规则仍可独立要求批准或拒绝。 |
| 停用状态 | 取消独立的规则停用状态。旧停用规则迁移为“直接执行”，这是行为变化：该规则由原先不参与判定变为命中后允许；其他同时命中的规则仍依统一裁决顺序判定。用户可显式改选其他动作或恢复默认。 |
| 规则恢复与套餐切换 | 逐条恢复默认会恢复规则默认动作并使规则参与判定；恢复操作不恢复旧停用状态。套餐切换不清除自定义动作；非自定义套餐暂时使用该套餐动作，切回自定义后恢复原自定义动作。 |
| 能力边界 | 仅执行能力、连接状态、操作系统权限等策略规则之外的真实能力条件不受配置影响。不得把真人必批、硬拒绝、locked 或其他策略约束重新命名为能力限制。 |

### 不需要决策人另行决定

- 是否开放 `script-sensitive-path-confirm`、`path-system-dir-ask`、`lark-unknown-ask`：均纳入「所有已展示规则」的承诺，不逐项豁免。
- 是否继续用 `locked` 表示不可编辑：不继续；界面不得把规则显示为不可修改。
- 不要求用户采用产品推荐的安全档位，也不以风险提示替代用户选择。

## 第 1 层：行为规格

### 1. 目标与范围

在现有统一「安全策略」设置页中，用户将桌面、微信或飞书链路切换到「自定义」后，可以编辑该链路策略规则表中的每条规则。规则范围以设置页当前呈现的适用规则集合为准，包含普通规则、当前 locked 规则、当前只能启用/停用的规则，以及其余由统一策略快照控制的规则。

本需求是对既有统一入口需求中策略编辑能力的扩展；既有统一入口与策略快照要求继续有效。桌面使用桌面策略；微信与飞书共享一份 IM 策略快照，但规则仅在其匹配条件覆盖的链路上生效。修改任一 IM 链路的共享规则时，页面须说明该配置由微信和飞书共用及规则实际匹配范围。

### 2. 用户可见行为

1. 选择「自定义」后，每条适用规则均显示可编辑的动作控件，不显示「锁定」状态，也不因规则原先为 locked 而禁用控件。
2. 动作控件依以下矩阵呈现，不得基于规则的风险等级、`locked` 状态、`humanRequired` 语义或当前默认动作缩减选项：

   | 规则所属链路 | 自定义下每条规则可选动作 |
   |---|---|
   | 桌面 | 禁止、直接执行、人工批准、自动审核 |
   | 微信 | 禁止、直接执行、人工批准 |
   | 飞书 | 禁止、直接执行、人工批准 |

   “人工批准”覆盖逐次确认和一般真人审批要求；恢复默认时仍显示为“人工批准”，并标注该规则默认是逐次询问还是按审批流程处理。“自动审核”只在桌面提供。若某条规则的事实类型无法送入自动审核，桌面仍可选择该动作；运行时按自动审核规则定义处理无法评估的结果，不得静默回退为真人必批。
3. 同一调用同时命中多条规则时，按以下唯一顺序裁决，不按规则在表中的先后位置裁决，也不区分动作是用户设置、默认值还是旧停用迁移所得：

   1. 任一匹配规则为「禁止」→ 拒绝调用。
   2. 没有匹配的禁止规则，且至少一条匹配规则为「人工批准」→ 要求人工批准。
   3. 没有匹配的禁止或人工批准规则，且至少一条匹配规则为「自动审核」→ 交由自动审核；审核结果按其自身定义处理。
   4. 所有匹配规则均为「直接执行」，或没有规则匹配 → 直接执行（若无规则匹配，则按既有兜底规则处理）。

   因此，直接执行表示该规则自身不增加审批或拒绝要求，并不豁免其他同时命中的规则。直接执行与禁止同时命中时禁止优先；直接执行与人工批准同时命中时人工批准优先。优先级与动作来源无关。
4. 用户选择「直接执行」时，该规则不再因自身原有真人必批、逐次确认、`humanRequired` 或自动审核前置要求而拦截；选择「自动审核」时，该规则交由自动审核，不再要求该规则自身的真人确认。其他匹配规则依据上列优先级共同裁决；任何规则均不得因产品锁定而凌驾于用户为该规则选择的动作。
5. 现有「启用/不启用」停用能力取消，不再作为自定义套餐下的用户选项或持久化独立状态。原来被停用的规则升级迁移为“直接执行”动作。这是行为变化：该规则从原先不参与匹配变为匹配后允许，但同时命中的其他规则仍依统一优先级裁决。迁移后的规则行明确标记为“由旧停用设置迁移为直接执行”，用户可改为其他动作或恢复默认。
6. 每条规则显示可理解的名称、触发范围、当前动作、默认动作，以及动作变化后的主要影响。产品不得仅展示内部规则 ID 作为理解变更的依据。
7. 用户更改动作后保存成功即对新发起的调用生效。保存失败时明确告知未成功，不得在界面显示为已生效；并发修改冲突时展示最新状态，用户可重新选择。
8. 每条规则提供「恢复默认」操作。恢复后该规则采用当前默认规则定义的动作并参与判定；其他规则的自定义动作不变。恢复默认不保留或恢复任何旧停用状态。
9. 用户切换到严格、标准或宽松套餐时，该套餐按现有套餐定义生效。用户随后切回「自定义」时，保留原有自定义规则；若套餐升级或规则集合改变，保留仍适用的规则覆盖，并对无法映射的覆盖明确提示。非自定义套餐期间，旧停用迁移动作不生效；切回自定义后按迁移后的直接执行动作生效。
10. 非自定义套餐下规则动作保持只读，用户需先选择自定义才能编辑。
11. 修改记录进入现有安全审计记录，至少可识别链路、规则、修改前动作、修改后动作和发生时间；记录不得包含消息正文或敏感调用参数。
12. 对 IM 入口规则，动作作用于消息进入常规处理前：禁止时不进入处理；直接执行时按既有流程处理；人工批准时先将该消息交给人工审批，批准后才继续处理该消息。对 IM 工具/能力暴露规则，动作作用于对象发布前：禁止时不暴露；直接执行时按既有流程暴露；人工批准时保持对象未暴露，批准后才暴露该对象。审批仅覆盖明确的消息或工具/能力对象，不扩大为长期授权。IM 不提供自动审核动作。

### 3. 策略修改与调用生命周期

保存成功时建立明确的生效界线：界线之后新发起的调用按新策略判定。对已有调用，“执行器开始处理该调用”是唯一生效边界：在此之前保存成功，调用必须按新策略重新判定；在此之后保存成功，不追溯撤销已开始的调用。最终授权核验必须与执行器开始处理绑定为一次不可分割的派发检查；若保存和派发并发，先完成策略保存则派发必须看到新策略，先完成派发检查并开始执行则该调用按旧策略继续。调用是否此前完成过审批或最终核验不改变此边界。

具体处理如下：

| 保存时调用状态 | 保存成功后的处理 |
|---|---|
| 等待人工批准 | 撤销旧审批请求并使其失效；不得再用旧审批结果执行。若新规则仍要求人工批准，则按新规则重新发起审批；若新规则为直接执行或自动审核，则按新规则继续判定，不要求用户完成旧审批。 |
| 等待自动审核 | 取消或废弃旧审核结果，并按新规则重新判定；若新规则仍为自动审核，使用新策略重新审核。 |
| 已批准，或已完成最终授权核验，但执行器尚未开始处理 | 旧批准/核验结果不构成派发授权；执行器开始处理前必须基于最新策略重新判定。新规则为禁止时不得执行；为人工批准或自动审核时须完成对应的新审批；为直接执行时可继续执行。 |
| 执行器已开始处理或外部副作用已开始 | 不承诺撤销已经开始的操作；保存成功后尚未开始处理的后续调用按新策略判定。界面不得把已开始操作描述为已撤销。 |

放宽策略时也使用同一界线：旧等待审批不会因规则放宽而自动视为批准，按上表重新判定；新规则若直接执行或自动审核则进入相应新路径，并继续服从多规则裁决顺序。修改套餐与修改单条动作采用相同生命周期语义。最终授权核验在执行器开始处理的派发边界确认授权材料仍有效、策略版本未过期；它只核验已批准的身份、对象、授权代次、permit 和执行材料，不重新计算业务风险。若策略版本已变化，须退回策略判定阶段按新规则处理。策略保存成功但旧调用无法确认执行器是否已开始处理时，该调用不得基于旧批准继续派发，须进入既有的结果不确定处理并告知用户。

### 4. 边界与优先级

- 自定义规则动作优先于同一规则的套餐动作、默认动作及设置页中针对同一行为的快捷配置；如快捷配置与规则动作存在重复控制，规则动作生效，界面须将快捷配置展示为已被该规则覆盖，且不得呈现矛盾状态。
- 用户将规则改为「直接执行」时，该规则不再要求人工确认或自动审核；将规则改为「禁止」时，该规则应拒绝匹配的操作；将规则改为「自动审核」时由自动审核给出结果，不能附加该规则自身的真人必批。
- 本需求开放策略规则配置，不改变工具是否存在、当前链路是否提供该工具、连接是否可用、操作是否满足执行所需参数等能力条件。能力不可用时应报告实际能力原因，不能伪称为不可修改的安全策略。
- 多条规则同时匹配时按“禁止 > 人工批准 > 自动审核 > 直接执行”裁决；同级动作的结果相同，不受规则排列位置、修改来源或旧停用迁移影响。直接执行只表达该规则自身的动作，不能覆盖其他命中规则的禁止或审批要求。
- 执行期最终授权核验在执行器开始处理时确认授权材料仍有效、策略版本未过期；它只核验已批准材料，不重新计算业务风险。若策略版本变化，退回策略判定阶段，按最新策略重新判定；不得接受保存界线前的过期批准。
- 若事实不足以匹配任何特定规则，按规则表已有的兜底规则继续判定。由于停用状态已取消，不存在通过停用单条规则隐式跳过规则表的行为。

## 第 2 层：验收标准

| ID | 场景 | 可判定结果 |
|---|---|---|
| AC1 | 用户查看任一链路自定义策略规则 | 桌面每条规则均显示禁止、直接执行、人工批准、自动审核四个选项；微信和飞书每条规则均显示禁止、直接执行、人工批准三个选项。`locked`、风险级别、默认真人确认或 `humanRequired` 不减少选项。 |
| AC2 | 用户将 `script-sensitive-path-confirm` 改为直接执行 | 保存后该规则命中的新调用不再因该规则要求逐次确认或真人必批；其他独立命中规则仍按各自动作判定。 |
| AC3 | 用户将 `path-system-dir-ask` 改为直接执行 | 保存后该规则命中的新调用不再因该规则要求人工批准。 |
| AC4 | 用户将 `lark-unknown-ask` 改为直接执行 | 飞书 IM 共享快照显示规则动作为直接执行；该规则命中的新调用不再因该规则要求人工批准。 |
| AC5 | 用户将一条规则改为自动审核 | 桌面该规则命中后进入自动审核；即使默认语义为真人必批，也不再因该规则本身要求真人批准。 |
| AC6 | 用户将一条规则改为禁止 | 该规则命中的操作被拒绝，设置页保留禁止动作。 |
| AC7 | 存在升级前被停用的规则 | 迁移后显示直接执行并参与匹配；这是从“不参与判定”到“按直接执行参与裁决”的行为变化。若没有其他更高优先级命中规则则放行；界面告知迁移来源。 |
| AC8 | 用户对迁移后的规则恢复默认 | 规则采用默认动作并参与匹配；恢复默认不会恢复旧停用状态，其他规则覆盖不变。 |
| AC9 | 用户切换到非自定义套餐再切回自定义 | 非自定义期间套餐动作生效；切回后原自定义覆盖及迁移后的直接执行动作恢复生效。 |
| AC10 | 同一调用同时命中 A=直接执行（包括迁移所得）和 B=禁止 | 调用被拒绝，与规则排列顺序及动作来源无关。 |
| AC11 | 同一调用同时命中 A=直接执行（包括迁移所得）和 B=人工批准 | 调用要求人工批准，与规则排列顺序及动作来源无关。 |
| AC12 | 同一调用同时命中人工批准和自动审核 | 要求人工批准；不得仅因规则排列顺序改为自动审核。 |
| AC13 | 用户保存新规则动作时，调用正等待人工批准 | 旧审批请求失效；新动作是禁止则调用不派发，是直接执行则按新规则继续，是人工批准则重新发起审批，是自动审核则进入自动审核。 |
| AC14 | 用户保存新规则动作时，调用正等待自动审核 | 旧审核结果不再可用；调用按新动作重判，仍为自动审核时启动基于新策略的审核。 |
| AC15 | 调用已批准或已完成最终授权核验、但执行器尚未开始处理时保存禁止动作 | 执行器开始处理前发现策略版本变化，调用按新规则重判并被拒绝；旧核验结果不能派发。 |
| AC16 | 调用已批准或已完成最终授权核验、但执行器尚未开始处理时保存放宽动作 | 按新规则重新判定；若为直接执行则可继续，若为人工批准或自动审核则完成对应的新流程后再执行。 |
| AC17 | 执行器已经开始处理后用户保存新动作 | 已开始的操作不被宣称已撤销；后续尚未开始处理的调用遵守新规则。 |
| AC18 | 新规则下操作是否已开始无法确认 | 不得按旧批准继续派发；进入结果不确定处理并向用户说明。 |
| AC19 | 保存失败或版本冲突 | 界面不显示保存成功或新策略已生效；冲突时呈现最新规则状态供用户重新选择。 |
| AC20 | 查询规则修改审计 | 可区分链路、规则、修改前后动作及时间，且不包含消息正文或敏感参数。 |
| AC21 | 用户将 IM 入口规则设为人工批准 | 对应入站消息在获批前不进入常规消息处理；批准后该消息按原流程继续一次，拒绝或撤销则不进入处理；审批不授权后续其他消息。 |
| AC22 | 用户将 IM 工具/能力暴露规则设为人工批准 | 对应工具/能力在获批前不出现在目标暴露范围；批准后仅暴露该对象；拒绝或撤销则继续保持未暴露，批准不扩展到其他对象或长期授权。 |

## 范围清单

### 本期做

- 自定义套餐下策略规则全集的动作编辑、保存、恢复默认、旧停用状态迁移与切换套餐后的保留行为。
- 将当前 locked 规则和只能启停的保护规则纳入统一编辑能力。
- 为规则提供用户可理解的说明、动作影响、共享链路范围和保存状态。
- 复核重复快捷配置、运行时核验、待审批调用失效与重判、策略审计及默认恢复行为，使用户看到的选择和实际执行一致。

### 明确不做

- 不替用户选择自定义规则动作，不强制其保留某个安全档位。
- 不改变工具能力、外部服务授权、操作系统权限或链路连接能力；这些能力边界不得用于保留本需求所覆盖的策略动作限制。
- 不改变规则事实提取与规则匹配范围；本需求调整动作选择权。
- 不提供任意编写新规则、修改匹配条件或脚本表达式的能力；本期“全部开放”指规则表内现有每条规则的动作均开放。

### 未来再引入

- 自定义规则导入、导出与跨设备同步。
- 新增规则条件编辑器或面向高级用户的策略表达式。

## 现状核查与跨文档关系

- `src/shared/policy/defaultRules.ts` 中包含示例规则 `script-sensitive-path-confirm`、`path-system-dir-ask`、`lark-unknown-ask`；规则结构带有 `locked` 属性。
- `src/shared/policy/policyPackages.ts` 当前桌面支持四种动作，微信/飞书支持三种动作；默认规则可使用的 `confirm-every-time` 当前不在套餐动作选项中。本需求将其用户可见语义归并到“人工批准”，恢复默认仍须呈现默认是否逐次询问。
- `src/shared/policy/policyEngine.ts` 当前另有独立的真人必批判定。本需求要求该判定不能绕过用户对同一规则选择的直接执行或自动审核；多个规则独立命中时，各规则仍各自生效。
- 规则分为 invocation、ingress、exposure 等消费阶段；ingress 的人工批准对象是单条入站消息，exposure 的批准对象是单个工具/能力对象，分别在进入消息处理与发布对象之前拦截，不得把界面可选动作仅实现为 selector 状态。
- `src/renderer/components/Config/ToolsSecuritySettingsTab.tsx` 对 locked 规则显示只读动作；部分 locked deny 规则以启用/不启用开关呈现。`electron/ipc/policyIpc.ts` 分别保存 `disabledRuleIds` 与 `ruleOverrides`。
- `electron/ipc/policyIpc.ts` 将微信和飞书映射到同一 IM 策略快照；共享配置不意味着所有 IM 规则都匹配所有链路，仍由规则自身链路条件决定。
- 策略调用携带快照版本信息。保存后的待审批、待审核或已批准未派发调用须依本需求的生命周期表按最新规则处理；具体失效和重判机制由技术方案定义。
- 既有需求 [安全策略整合后的设置入口单一化](security-policy-single-entry-requirement.md) 记录统一设置入口与策略快照演进。本需求扩展其中「自定义套餐可逐条覆盖」的范围；如旧条文将 locked 解释为不可编辑，应由本需求替代该限制。
- 方案阶段须继续遵守 [`AGENTS.md`](../../../AGENTS.md) 的安全逻辑变更规范：若实现保留任何不可配置系统约束，先登记系统不变量及依据；但系统不变量登记不得用来豁免本需求明确开放的策略动作。

## 后续方案输入

- 技术方案须逐条映射现有规则全集到上述动作矩阵；若某规则类型无法适用矩阵动作，必须以用户可见行为证明其属于执行能力边界，而非策略限制，并补充对应该规则的验收案例。不得留下“实现支持时再开放”的不确定项。
- 技术方案须覆盖旧停用数据迁移、规则动作/恢复默认/套餐切换的完整状态转换，以及等待审批、等待审核、批准后待派发和已开始执行四类调用的并发边界。
