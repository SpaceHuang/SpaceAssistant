# `codex/queued-task-bar-tdd` 复审（v4）

结论：**请求修改，暂不合并**。v3 的草稿清空问题已用编辑轮次保护修复；本轮发现旧请求仍可能覆盖新请求的保存结果。

## 阻断问题

### B1 · 同一消息的旧编辑响应可覆盖较新的已保存正文

位置：`src/renderer/components/Chat/ChatView.tsx:690-701, 739-763`、`src/renderer/services/messageMutationGateway.ts:103-117`。

复现时序：编辑排队项 Q，保存正文 A；在第一次请求未返回时点击“放弃修改”，重新打开 Q，保存正文 B。新 `editRound` 允许第二次保存并保护草稿状态，但两次 `commitQueuedMessageEdit` 都会在 IPC 成功响应后无条件 patch live 快照和 Redux。如果主进程按 A、B 顺序落库，而 B 的响应先于 A 返回（handler 在落库后仍异步等待 `flushBackup`），界面先显示 B，随后迟到的 A 响应把正文改回 A；数据库最终为 B，横条、live 快照与数据库不一致。当前回归测试只让第一请求在新草稿尚未保存时返回，没有覆盖两次保存的反序响应。

建议：为每条消息的提交结果引入单调版本或请求序号，仅将最新提交的响应应用到渲染态；更稳妥的是在同一消息的前一次保存完成前禁止再次保存，并在完成后从数据库事实刷新。补充受控 Promise 测试，按“A 提交 → 放弃并重新编辑 → B 提交 → B 响应 → A 响应”验证最终正文与数据库一致。

## 已核实的修复

- v2 的跨会话迟到响应问题及初次评审的 3 项问题维持修复状态。
