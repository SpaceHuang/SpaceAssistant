# Task Scoping（任务开工标定与验收边界）

## 何时用

任务是多阶段、长会话、或由「自动续跑」目标驱动（例如「推进某方案直到全部完成」）时使用。普通小改动不适用。

## 开工：三步

1. **盘点验收边界**。读完方案 / 需求后，把所有交付项分成两类：
   - **当前环境可验证**：可写单测、typecheck、i18n、增量编译、单元级回归验证的项。
   - **需真机 / 外部系统**：必须开 Electron 窗口、连真实 IM（微信 / 飞书）机器人、浏览器自动化、远程通道才能验收的项。
   把第二类明确列出来，问用户要哪种交付形态：a) 我先做到可单测部分即交付；b) 你给我能跑的环境，我照单补齐；c) 只出清单 + 代码说明。

2. **拆阶段**。按可独立交付、可独立提交、可独立验证切分。每阶段结尾：跑定向测试 + 增量编译 → 提交 → 记一句进度。

3. **产出任务清单 + 测试计划**。直接从方案 / 需求里逐条摘，不要重新推演。输出为 `update_plan` 的阶段清单，作为唯一进度载体。

## 执行纪律（详见 AGENTS.md「Agent 执行纪律」）

- 验证：相关测试一次跑，不单文件逐个跑；typecheck / i18n 只在涉及时跑；增量编译每阶段至多一次。
- 读取：`rg` + 行号 / `Get-Content -TotalCount`；方案读一次后只 grep 小节。
- 改动：先确认既有签名与调用方，避免反向 TDD。
- 上下文：接近约 40 万 token 就总结并交接 / 开新线程。
- 状态：进度用 `update_plan` 一句话 / 清单，不重复输出长状态。

## 收尾核对

按开工时的「验收边界」逐项给交付状态（已交付并验证 / 需真机待验），并把需真机项整理成下一步清单，而不是把整个目标标记为 blocked。
